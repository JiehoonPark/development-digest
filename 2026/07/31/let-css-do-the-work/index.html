CSS가 할 일은 CSS에게 맡기자

날씨 앱에서 흔히 보는 강수량 표시 막대를 떠올려보겠습니다. 개발자 도구를 열어보면 height: 45px 같은 인라인 스타일이 걸려 있는 걸 종종 발견하게 되는데요, 이 45px이라는 숫자는 대부분 JavaScript에서 강수량 데이터를 받아와 계산한 뒤 인라인 스타일로 밀어 넣은 결과입니다. Kevin Powell은 이런 패턴이 흔하지만 바람직하지 않다고 지적합니다. 스타일링과 관련된 계산이라면 CSS에 맡기는 것이 훨씬 낫다는 건데요, 이 글에서는 왜 그런지, 그리고 실제로 어떻게 바꾸면 되는지를 정리해보겠습니다.

문제: JavaScript가 스타일을 계산해서 박아 넣는 방식

가짜 API에서 날씨 데이터를 받아온 뒤, JavaScript 안에서 최대 강수량 값을 기준으로 min 함수 등을 이용해 비율을 계산하고, 그 결과를 style.height에 직접 대입하는 코드를 생각해보겠습니다. 이렇게 하면 동작은 하지만 다음과 같은 문제가 생깁니다.

  • 나중에 스타일을 수정하려고 CSS 파일을 열어봐도 막대 크기와 관련된 코드가 전혀 보이지 않습니다.
  • 한참 헤매다가 결국 JavaScript에서 인라인 스타일을 주입하고 있다는 걸 발견하게 되고, "아, 여기 있었네" 하며 허탈해지는 흐름을 여러 번 겪게 됩니다.
  • 스타일링에 관한 로직(최대 강수량 값, 퍼센트 계산 등)이 JavaScript 안에 숨어버리면서 관심사 분리가 오히려 깨집니다.

해결책: 원시 데이터만 CSS 커스텀 프로퍼티로 넘기기

가장 좋은 방법은 JavaScript에서 계산을 하지 않는 겁니다. 대신 API에서 받은 원시 강수량 값을 그대로 커스텀 프로퍼티로 요소에 심어줍니다.

/* 인라인 style="height: 45px" 대신 */
--precip: 8.2;

개발자 도구로 확인해보면 강수량 정보, 라벨, 시각적 요소와 함께 --precip: 8.2라는 값이 그대로 넘어온 걸 볼 수 있습니다. JavaScript는 더 이상 계산을 하지 않고, 스타일링과 관련된 정보만 CSS로 전달하는 역할만 합니다.

CSS에서 calc()와 min()으로 계산 처리하기

이제 CSS 쪽에서 이 값을 실제 크기로 바꿔줘야 합니다. 먼저 단위가 없는 숫자이기 때문에 그대로 쓸 수는 없고, calc()로 단위를 붙여줘야 합니다.

block-size: calc(var(--precip) * 1px);

여기서는 픽셀, 퍼센트(1%), rem(1rem) 등 필요한 단위를 자유롭게 붙일 수 있습니다. 이 예제에서는 강수량 막대 전체 높이에 대한 퍼센트로 채우는 게 목적이므로, 기존에 JavaScript에서 하드코딩되어 있던 "최대 강수량 10mm"라는 매직 넘버도 CSS 커스텀 프로퍼티로 옮깁니다.

--max-precip: 10;

block-size: min(
  calc(var(--precip) / var(--max-precip) * 100%),
  100%
);

min() 함수를 쓰는 이유는 오버플로우 방지 때문입니다. 예를 들어 하루에 18mm처럼 예상보다 훨씬 많은 비가 내리면 퍼센트 계산값이 100%를 넘어가서 막대가 넘칠 수 있는데요, min()으로 계산값과 100% 중 작은 쪽을 선택하게 하면 자연스럽게 상한선이 걸립니다. 이건 원래 JavaScript에서 하던 로직을 그대로 CSS로 옮긴 것뿐입니다.

참고로 향후에는 더 발전된 attr() 함수를 이용해 이런 값 전달을 더 깔끔하게 처리할 수 있는 방법도 논의되고 있지만, 아직 브라우저 지원이 충분하지 않아서 현재로서는 커스텀 프로퍼티를 활용하는 방식이 가장 현실적인 선택입니다.

왜 이 방식이 더 나은가

"로직이라면 JavaScript에 있어야 하는 것 아니냐"는 반론이 있을 수 있습니다. 실제로 이런 댓글을 자주 받는다고 하는데요, Kevin Powell은 여기에 동의하지 않습니다. 그 로직이 스타일링과 관련된 것이라면 CSS에 있는 게 맞다는 입장입니다.

예를 들어 기획팀에서 "강수량 시각화의 최댓값을 20mm로 바꿔달라"는 요청이 들어왔다고 해보겠습니다. CSS 개발자라면 당연히 CSS 파일부터 열어볼 텐데, 이때 최대 강수량 값이 CSS 커스텀 프로퍼티(--max-precip)로 존재한다면 바로 그 자리에서 값을 수정하고 끝낼 수 있습니다. 반면 이 값이 JavaScript 어딘가에 숨어 있다면 찾는 데 시간이 걸리고, 결과적으로 관심사 분리라는 원칙에도 어긋나게 됩니다.

또한 성능 측면에서도 이점이 있을 가능성이 높다고 언급합니다. JavaScript로 계산을 수행하면 타이밍 측정이 쉬워서 성능 테스트 자체는 더 간편하지만, 시각적 요소에 대한 계산을 CSS로 옮기면 오히려 성능이 개선되는 경우가 많다는 것입니다. 실제로 최근 CSS Day 발표에서 이 주제를 다뤘을 때, 몇몇 참석자들이 자신들의 프로젝트에서 비슷한 개선을 확인했다는 피드백을 주었다고 합니다. 다만 이는 프로젝트마다 다를 수 있으니, 실제로 변경을 적용한다면 반드시 직접 성능을 측정해서 확인해보는 게 좋습니다.

정리

  • 스타일링과 관련된 계산(막대 높이, 채움 비율 등)은 JavaScript에서 미리 계산해 인라인 스타일로 박아 넣지 말고, 원시 데이터만 CSS 커스텀 프로퍼티로 전달하세요.
  • CSS 쪽에서는 calc()로 단위를 부여하고, min()/max() 함수로 오버플로우 같은 경계 조건을 처리하면 JavaScript에서 하던 로직을 그대로 CSS로 옮길 수 있습니다.
  • 최댓값 같은 매직 넘버도 커스텀 프로퍼티로 CSS에 두면, 스타일 관련 변경 요청이 왔을 때 CSS 파일 안에서 바로 찾고 수정할 수 있어 유지보수가 쉬워집니다.
  • "로직은 JavaScript에" 라는 원칙보다 "스타일링에 관한 로직은 CSS에"라는 원칙이 관심사 분리에 더 부합하며, 부가적으로 성능 이점도 기대할 수 있습니다(단, 실제 적용 시 직접 측정해서 검증할 것을 권장합니다).
  • 향후 고급 attr() 함수가 브라우저에 지원되면 이런 값 전달 방식이 더 세련되게 발전할 수 있지만, 지금 당장은 커스텀 프로퍼티 기반 접근이 충분히 실용적인 대안입니다.
💡
UI 상태에 따라 크기나 위치를 동적으로 계산하는 코드를 어디에 둘지는 유지보수성과 성능에 직접적인 영향을 미치므로, 스타일 관련 로직을 CSS로 옮기는 습관은 실무에서 바로 적용 가능한 개선 포인트입니다.
