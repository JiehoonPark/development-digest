CSS가 할 수 있는 계산은 CSS에게 맡기자

Let CSS do the work

📅 2026-07-30📰 Kevin Powell (CSS)🎬 Video
frontend

웹 개발을 하다 보면 스타일 관련 값을 JavaScript에서 계산해서 인라인 스타일로 박아 넣는 코드를 자주 만나게 됩니다. 날씨 앱의 강수량 표시 막대처럼 height: 45px 같은 값이 어디서 나왔는지 추적하려면 결국 JavaScript 코드를 뒤져야 하는 상황이 벌어지는데요. Kevin Powell은 이런 스타일링 로직은 애초에 CSS의 영역이며, CSS로 옮기는 것이 유지보수와 성능 양쪽 모두에 이득이라고 주장합니다. 이 글에서는 그 구체적인 방법과 근거를 살펴보겠습니다.

문제 상황: JavaScript가 스타일까지 계산하는 코드

날씨 서비스의 강수량 시각화 막대를 예로 들어보겠습니다. 기존 방식은 이렇습니다.

  • 가짜 API에서 강수량 데이터를 가져온다
  • JavaScript에서 최대 강수량 값과 min 함수를 이용해 막대가 넘치지 않도록 계산한다
  • 계산 결과를 style="height: 45px" 같은 인라인 스타일로 DOM에 직접 박아 넣는다

이 방식의 가장 큰 문제는 스타일을 수정하려고 개발자 도구를 열었을 때 크기와 관련된 CSS 규칙이 전혀 보이지 않는다는 점입니다. 한참 뒤지다가 결국 인라인 스타일이 적용되고 있다는 걸 발견하게 되고, "아, 여기 있었구나" 하며 허탈해지는 흐름이 반복됩니다. 스타일링에 관련된 정보인데도 그 로직이 JavaScript 안에 숨어 있으니 당연한 결과입니다.

해결책: 원본 데이터를 CSS 커스텀 프로퍼티로 넘기기

가장 좋은 해결책은 간단합니다. JavaScript에서 계산하지 않는 것입니다. 계산된 픽셀 값 대신, 가공하지 않은 원본 데이터를 CSS 커스텀 프로퍼티로 그대로 넘겨주면 됩니다.

--precip: 8.2;

여기서 precip은 강수량 원본 수치일 뿐, 어떤 단위도 붙어 있지 않습니다. JavaScript 쪽에서는 더 이상 계산 로직이 필요 없으므로 관련 코드를 통째로 제거할 수 있습니다. 개발자 도구로 요소를 확인해보면 precipitation-info, precipitation-label 같은 요소들과 함께 --precip: 8.2라는 값만 깔끔하게 넘어와 있는 것을 볼 수 있습니다.

이제 이 값을 CSS에서 실제 크기로 변환해야 합니다.

block-size: var(--precip);

이렇게만 쓰면 8.2라는 값 자체로는 아무 단위도 없어서 동작하지 않습니다. 그래서 calc()를 사용해 단위를 붙여줍니다.

block-size: calc(var(--precip) * 1px);

1px 대신 1%나 1em을 곱하면 픽셀이 아닌 퍼센트나 em 값으로도 얼마든지 변환할 수 있습니다. 어떤 단위가 필요하든 곱하는 값만 바꾸면 되는 것이죠.

최댓값 계산도 CSS로 옮기기

기존 JavaScript 코드에는 최대 강수량을 10으로 놓고, 전체 영역 대비 퍼센트를 계산하는 매직 넘버가 있었습니다. 이 역시 스타일링과 밀접하게 관련된 값이므로 CSS로 옮겨야 합니다.

--max-precip: 10;

그리고 JavaScript에서 주석 처리했던 계산 로직을 min() 함수로 CSS에 그대로 옮깁니다.

block-size: min(
  calc(var(--precip) / var(--max-precip) * 100%),
  100%
);

이렇게 하면 8.2가 8.2%로 변환됩니다. min() 함수를 쓰는 이유는 오버플로우 방지 때문인데요, 만약 하루에 18mm의 폭우가 내려서 계산값이 100%를 넘어가더라도 min()이 100%와 비교해 더 작은 값을 선택하므로 막대가 컨테이너 밖으로 넘치지 않습니다. 이는 기존 JavaScript 로직과 정확히 동일한 동작이며, 단지 그 로직을 CSS로 옮겨온 것뿐입니다.

"로직은 JavaScript에 있어야 한다"는 반론에 대해

이런 방식에 대해 "로직이라면 JavaScript에 있어야 하는 것 아니냐"는 댓글을 종종 받는다고 합니다. Kevin Powell은 이 의견에 동의하지 않는데, 근거는 이렇습니다.

만약 나중에 요구사항이 바뀌어서 "강수량 시각화의 최댓값을 20mm로 변경해달라"는 요청이 들어온다면, 개발자는 자연스럽게 CSS부터 확인하게 됩니다. 강수량과 관련된 스타일이 CSS 안에 있으니까요. --max-precip 값만 CSS에서 바로 찾아 수정하면 나머지는 그대로 잘 동작합니다. 반대로 로직이 JavaScript에 숨어 있다면 이 값을 찾는 것부터 번거로워집니다.

정리하면 이렇습니다.

  • 관심사 분리 관점: 스타일링에 관련된 로직이라면 CSS에 있는 것이 더 자연스럽다
  • 성능 관점: JavaScript가 아니라 CSS가 계산을 담당하면 성능상 이점이 있을 가능성이 크다

성능 측정은 JavaScript 쪽이 타이밍을 재기 훨씬 쉬워서 검증이 상대적으로 수월하지만, 실제로 시각적 요소의 계산 로직을 CSS로 옮겼을 때 성능이 개선되었다는 피드백을 CSS Day 발표 이후 여러 사람에게서 들었다고 합니다. 다만 이는 변경할 때마다 직접 테스트해서 확인해볼 필요가 있는 부분입니다.

향후 개선 방향: attr() 함수

현재는 --precip: 8.2 같은 값을 CSS 커스텀 프로퍼티로 직접 넘겨줘야 하지만, 앞으로는 진보된 형태의 attr() 함수를 이용해 HTML의 데이터 속성값을 CSS에서 직접 가져오는 방식이 가능해질 예정입니다. 다만 현재는 브라우저 지원이 충분하지 않아서, 지금 시점에서는 커스텀 프로퍼티로 값을 넘기는 방식이 현실적인 대안입니다.

정리

  • 스타일과 관련된 값(크기, 비율, 최댓값 등)을 JavaScript에서 계산해 인라인 스타일로 주입하는 방식은 유지보수를 어렵게 만듭니다. 나중에 값을 찾으려면 개발자 도구에서 인라인 스타일을 뒤지는 수밖에 없기 때문입니다.
  • 대신 가공되지 않은 원본 데이터만 CSS 커스텀 프로퍼티(--precip: 8.2 등)로 넘기고, 실제 단위 변환과 비율 계산은 calc()와 min() 같은 CSS 함수로 처리하는 것이 좋습니다.
  • 최댓값 같은 매직 넘버도 CSS 커스텀 프로퍼티(--max-precip: 10)로 관리하면, 나중에 값이 바뀔 때 CSS 파일 안에서 바로 찾아 수정할 수 있습니다.
  • 스타일링에 관련된 로직은 관심사 분리 원칙에 따라 CSS에 두는 것이 자연스러우며, 부수적으로 성능 개선 효과도 기대할 수 있습니다(단, 변경 시 직접 측정해볼 것을 권장합니다).
  • 앞으로 attr() 함수의 브라우저 지원이 확대되면 데이터 속성값을 CSS에서 더 직접적으로 활용할 수 있게 될 전망입니다.
💡
스타일 관련 계산 로직의 위치를 어떻게 설계하느냐는 코드 유지보수성과 성능에 직결되므로, JavaScript와 CSS의 역할을 어디서 나눌지에 대한 실용적인 기준을 제시해준다.
