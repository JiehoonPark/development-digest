14:T392c,<h2>Cloudflare, 오리진 서버 연결의 '헛발질'을 없애다: Automatic Key Exchange</h2>
<p>TLS 1.3 핸드셰이크는 원래 빠릅니다. 단 한 번의 왕복(round trip)만으로 암호화 연결을 맺을 수 있다는 게 TLS 1.2 대비 핵심 개선점인데요. 그런데 여기엔 함정이 하나 있습니다. 클라이언트가 서버에게 아무 정보도 받기 전에, 첫 패킷에서 어떤 키 교환(key agreement) 알고리즘을 쓸지 '찍어서' 보내야 한다는 겁니다. 이 추측이 틀리면 서버는 HelloRetryRequest(HRR)를 보내 다시 시작하게 되고, 결국 한 번 더 왕복이 발생해 지연 시간이 두 배로 늘어납니다.</p>
<p>Cloudflare는 리버스 프록시로서 수많은 오리진 서버와 TLS 연결을 맺는데, 오랫동안 이 첫 번째 추측값으로 X25519를 고정적으로 사용해왔습니다. 널리 지원되는 알고리즘이긴 하지만, 측정해보니 전체 오리진 연결의 약 30%에서는 최선의 선택이 아니었다고 합니다. 이번에 Cloudflare가 발표한 Automatic Key Exchange는 이 '추측'을 '측정'으로 바꾸는 기능인데요, 적용 이후 오리진 연결의 HelloRetryRequest 비율이 약 52%에서 3.7%로 떨어졌고, p90 기준 핸드셰이크 지연이 150ms 이상 단축됐습니다.</p>
<h3>TLS 1.3 핸드셰이크와 '키 교환 알고리즘 추측' 문제</h3>
<p>모든 보안 웹 연결은 서버를 인증하고 공유 비밀 키를 도출하는 TLS 핸드셰이크로 시작합니다. Cloudflare는 리버스 프록시이기 때문에, 사용자 입장에서는 하나의 안전한 연결처럼 보이지만 실제로는 두 개의 독립된 연결이 존재합니다. 하나는 방문자와 Cloudflare 사이의 연결이고, 다른 하나는 Cloudflare와 오리진 서버 사이의 연결입니다. 각 연결은 자체적인 핸드셰이크, 신원 확인, 암호화 키를 갖습니다. Automatic Key Exchange는 이 중 두 번째 연결, 즉 Cloudflare와 오리진 서버 간 연결에 적용되는 기능입니다.</p>
<p>Cloudflare가 오리진에 연결할 때는 TLS 클라이언트 역할을 맡아 핸드셰이크를 먼저 시작해야 합니다. 호스트명과 지원 가능한 키 교환 알고리즘 목록을 담은 ClientHello 메시지를 보내는 식이죠.</p>
<ul>
<li><strong>성공 경로(1 RTT)</strong>: ClientHello에 지원 알고리즘 목록과 함께 하나 이상의 클라이언트 키셰어(keyshare)를 담아 보냅니다. 오리진이 이 선택을 받아들이면 바로 핸드셰이크가 완료됩니다. 이런 예측적 키 교환이 바로 TLS 1.3이 TLS 1.2보다 빠른 핵심 이유입니다.</li>
<li><strong>재시도 경로(2 RTT)</strong>: 오리진이 다른 알고리즘을 선호하면 HelloRetryRequest를 보내 재시도를 요청합니다. Cloudflare는 오리진이 지정한 알고리즘으로 새 키셰어를 만들어 두 번째 ClientHello를 보내야 하고, 이 과정에서 왕복 한 번이 추가로 소요됩니다. 연결 자체는 결국 성공하지만, 마리오카트에서 지름길을 놓친 것처럼 아낄 수 있었던 시간을 그냥 날리는 셈입니다.</li>
</ul>
<p>어느 경로든 최종적으로는 클라이언트 키셰어를 이용해 서버가 공유 키를 생성하고, 서버 키셰어를 돌려받아 클라이언트도 같은 공유 키를 계산합니다. 이후 이 공유 키는 AES 같은 대칭 암호화로 나머지 연결을 보호하는 데 사용됩니다.</p>
<h3>'안전한 추측'의 숨은 비용</h3>
<p>Cloudflare는 오랫동안 오리진 TLS 1.3 연결의 초기 키셰어로 항상 X25519를 고정적으로 사용해왔습니다. 다른 키 교환 알고리즘 지원 여부는 광고만 하고, 실제 첫 시도는 X25519로 밀어붙이는 전략이었죠. 이는 95% 이상의 오리진이 X25519를 지원하고, 지원하지 않는 오리진은 연결이 끊기지 않고 HRR로 처리되기 때문에 안전한 선택이었습니다.</p>
<p>문제는 X25519가 양자 컴퓨터 공격에 취약하다는 점입니다. Cloudflare는 2023년 9월부터 오리진에 양자 내성(post-quantum) 키 교환 지원을 광고해왔는데, 처음엔 X25519Kyber768Draft00, 지금은 표준화된 버전인 X25519MLKEM768을 사용합니다. 다만 '지원을 광고하는 것'과 '실제로 ClientHello에서 해당 키셰어를 먼저 제시하는 것'은 다른 문제입니다. X25519MLKEM768 키셰어는 1,216바이트로, X25519의 32바이트에 비해 훨씬 커서 ClientHello가 단일 네트워크 패킷 크기를 넘어서게 됩니다. TLS 표준은 여러 패킷에 걸친 세그먼트를 허용하지만, 일부 구식 미들박스나 오리진 서버는 ClientHello가 여러 패킷으로 쪼개져 오면 처리에 실패하는 경우가 있습니다. Cloudflare의 이전 조사에 따르면, 양자 내성 키셰어를 먼저 보냈을 때 약 0.34%의 스캔된 오리진이 TLS 핸드셰이크를 완료하지 못했습니다.</p>
<p>그래서 Cloudflare는 연결이 깨지는 위험을 막기 위해 HRR을 일종의 안전장치로 활용해왔습니다. 즉 양자 내성 지원은 광고만 하고 실제로는 고전적인 X25519 키셰어를 보내며, 양자 내성을 지원하는 오리진이 재시도를 통해 요청하도록 한 것이죠. HRR 흐름을 지원하지 않는 오리진의 경우 고객이 수동으로 X25519MLKEM768 키셰어를 먼저 보내도록 설정할 수 있는 옵션도 있었습니다. 2023년부터 현재까지 양자 내성 키 교환 알고리즘을 지원하는 오리진 비율은 0.5%에서 12.8%로 늘었고, 호스팅 스택들이 계속 업그레이드되면서 이 수치는 앞으로도 증가할 전망입니다.</p>
<p>이 방식은 안전하긴 했지만, 두 가지 이유로 불필요한 지연을 발생시켰습니다.</p>
<ul>
<li>OpenSSL, BoringSSL, rustls의 최신 빌드는 모두 X25519MLKEM768을 지원하지만, 고전적인 X25519 키셰어를 처리하는 방식이 빌드마다 다릅니다. 일부 구버전 빌드는 명시적으로 설정하지 않으면 기본적으로 X25519를 그냥 받아들이는 반면, 최신 빌드는 양자 내성 연결을 우선시하기 위해 즉시 HRR을 발행합니다.</li>
<li>오리진의 6% 이상이 X25519보다 P-256이나 P-384를 선호합니다. 이 경우 Cloudflare가 초기 키셰어를 고정적으로 X25519로 보내는 한, 순수하게 고전 암호 연결에서도 매번 HRR로 인한 왕복이 발생합니다.</li>
</ul>
<p>이런 불필요한 왕복을 없애기 위해 Cloudflare는 Automatic SSL/TLS의 일환으로 오리진 서버를 스캔해 정확한 키 교환 지원 범위를 파악하기 시작했고, 이 스캔 결과를 바탕으로 오리진별로 초기 키셰어를 자동으로 맞춤 설정하기로 했습니다. 사이트 장애 위험 없이 양자 내성 연결을 최대한 늘리는 동시에, 해당되는 도메인들의 연결 속도까지 빠르게 만드는 접근입니다.</p>
<h3>Automatic SSL/TLS를 양자 내성 시대로 확장하기</h3>
<p>이제 Automatic SSL/TLS에는 Automatic Key Exchange가 포함됩니다. 수백만 개의 오리진에 대해 키셰어를 추측하는 것은 각 오리진의 설정을 사전에 알 수 없기 때문에 운영상 위험이 따릅니다. 그래서 Cloudflare는 능력치를 추론하는 대신 직접 측정하는 방식을 택했고, 이미 Automatic SSL/TLS를 구동하는 스캐닝 파이프라인을 재활용합니다.</p>
<p>동작 방식은 이렇습니다.</p>
<ul>
<li>TLS 1.3을 지원하는 각 오리진에 대해, 각각 정확히 하나의 키 교환 그룹(X25519, P-256, P-384, P-521, X25519MLKEM768 중 하나)만 제시하는 몇 개의 가벼운 TLS 핸드셰이크를 실행합니다. 이 프로브들을 종합하면 해당 오리진이 지원하는 전체 알고리즘 집합을 알 수 있습니다.</li>
<li>이 능동 스캐닝은 실제 운영 트래픽 경로 바깥에서 이뤄지기 때문에, 실 트래픽이 이 결과에 의존하기 전에 오리진과 그 사이의 네트워크가 더 강력한 키 교환을 실제로 처리할 수 있는지 미리 확인할 수 있습니다.</li>
<li>하나의 도메인은 종종 여러 서브도메인을 통해 서로 다른 능력을 가진 오리진으로 연결됩니다. Cloudflare는 각 서브도메인을 독립적으로 평가하고, 실제 트래픽 볼륨으로 가중치를 부여합니다. 즉 거의 쓰이지 않는 서브도메인이 가장 트래픽이 많은 엔드포인트와 동일한 비중으로 반영되지 않도록, 도메인 전체의 선호도가 실제 HTTP 트래픽 볼륨을 반영하게 만듭니다. 예를 들어 대부분의 트래픽이 www와 api 서브도메인에 몰린다면, 이 두 엔드포인트가 도메인 전체의 키 교환 선호도를 크게 좌우하게 됩니다.</li>
<li>오리진이 지원하는 키 교환 그룹들 중에서, 엄격한 우선순위(양자 내성 하이브리드인 X25519MLKEM768을 최우선으로, 그다음은 오리진이 받아들이는 가장 빠른 고전 알고리즘인 X25519, P-256, P-384, P-521 순)에 따라 가장 강력한 후보를 선택합니다.</li>
</ul>
<p>최적의 키 교환 방식을 파악하면 곧바로 롤아웃을 시작합니다. 새로운 선호값은 우선 해당 오리진 트래픽의 일부에만 적용되고, 시스템은 그 과정에서 실패율과 HRR 비율을 모니터링합니다. 재시도율이 기준선을 넘으면 변경을 롤백하는데, 이는 Automatic SSL/TLS가 오작동 가능성이 있는 암호화 모드 업그레이드를 되돌리는 방식과 동일합니다. 최악의 경우라 해도 롤백 과정에서 발생하는 비용은 롤아웃 기간 동안의 추가 왕복 지연 정도이지, TLS 연결 자체가 깨지는 것은 아닙니다.</p>
<p>오리진 설정은 시간이 지나며 계속 바뀝니다. 고객이 새 로드밸런서로 옮기거나, TLS 라이브러리가 정기 릴리스에서 양자 내성 지원을 추가하거나, 운영자가 오래된 키 교환 알고리즘 지원을 끄는 식이죠. Cloudflare는 매일 모든 오리진을 재스캔하기 때문에, 서버가 양자 내성 지원을 새로 추가하거나 기존에 쓰던 커브 지원을 중단하면 다음 스캔 시점에 바로 새로운 선호값이 반영됩니다.</p>
<p>대부분의 고객은 별도로 설정할 게 없습니다. 오리진이 TLS 1.3을 지원한다면, Cloudflare는 자동으로 오리진이 지원하는 가장 강력한 키 교환 방식을 협상합니다. 예를 들어 오리진이 X25519MLKEM768을 지원한다면, Cloudflare는 이를 우선 사용하고 추가 왕복 지연 없이 양자 내성 키 교환을 맺을 수 있습니다.</p>
<h3>Automatic Key Exchange 설정하기</h3>
<p>Automatic Key Exchange는 기존/신규 도메인 모두에 기본적으로 활성화되어 있어, 대부분의 환경에서는 별도 조치가 필요 없습니다. 원한다면 Cloudflare 대시보드의 <code>SSL/TLS &gt; Overview &gt; Configure &gt; Origin connection &amp; post-quantum encryption</code>에서 독립적으로 관리할 수 있습니다.</p>
<p>Automatic Key Exchange 토글을 켜면 Cloudflare가 오리진을 대역외(out-of-band)로 스캔하고 동적으로 선택한 키셰어를 우선 사용합니다. 반대로 끄면 스캐닝이 중단되고 고정된 정적 기본 키 교환 순서로 돌아갑니다.</p>
<p>이와 함께 Automatic Key Exchange 하위에 새로운 <strong>Compliance requirements(준수 요건)</strong> 설정도 추가됐습니다. 이를 통해 Cloudflare가 오리진 연결에서 사용/광고할 수 있는 키 교환 방식을 필터링할 수 있는데, 설정하면 Automatic Key Exchange를 포함한 모든 오리진 대상 트래픽이 다음 규칙을 엄격히 따릅니다.</p>
<ul>
<li><strong>Post-quantum hybrid</strong>: 협상을 오직 하이브리드 양자 내성 키 교환(X25519MLKEM768)으로만 제한하고, 고전 알고리즘을 완전히 배제합니다. 이 경우 성공한 모든 오리진 TLS 1.3 연결은 양자 내성 보안이 보장됩니다.</li>
<li><strong>Federal Information Processing Standards (FIPS)</strong>: 협상을 FIPS 준수 키 교환 방식으로만 제한합니다.</li>
</ul>
<p>두 옵션을 모두 선택하면 두 기준을 동시에 만족하는 알고리즘이 필요하며, 겹치는 키 교환 방식이 없으면 해당 설정 자체가 거부됩니다. 자세한 내용은 Automatic Key Exchange 공식 문서를 참고하면 됩니다.</p>
<p>이 옵션들을 선택하는 것은 특정 알고리즘을 지정하는 것이 아니라 '의도'를 설정하는 것에 가깝습니다. 덕분에 준수 표준이 바뀌거나 새로운 양자 내성 알고리즘이 등장해도 설정이 자동으로 최신 상태를 유지합니다. 다만 이런 요건들은 신중하게 접근할 필요가 있습니다.</p>
<h3>정리</h3>
<ul>
<li>Cloudflare와 오리진 서버 간 TLS 1.3 연결은 첫 패킷에서 키 교환 알고리즘을 미리 '추측'해야 하는 구조적 특성 때문에, 추측이 틀리면 HelloRetryRequest로 인해 왕복이 한 번 더 발생하고 지연이 늘어납니다.</li>
<li>기존에는 모든 오리진에 X25519를 고정적으로 사용했고, 양자 내성 키 교환은 오리진이 HRR로 요청할 때만 적용하는 보수적인 전략을 썼습니다. 이 때문에 약 30%의 오리진 연결에서 불필요한 지연이 발생했습니다.</li>
<li>Automatic Key Exchange는 각 오리진을 실제로 스캔해(X25519, P-256, P-384, P-521, X25519MLKEM768 각각에 대해 프로브) 지원 알고리즘을 파악하고, 트래픽 볼륨 가중치를 반영해 도메인 단위 선호도를 결정한 뒤, 양자 내성 알고리즘을 최우선으로 첫 시도부터 사용합니다.</li>
<li>그 결과 HelloRetryRequest 비율이 52%에서 3.7%로 줄었고, p90 핸드셰이크 지연이 150ms 이상 단축됐습니다. 동시에 수십만 개 도메인이 별도 설정 없이 양자 내성 오리진 연결을 갖게 됐습니다.</li>
<li>이 기능은 모든 도메인에 기본 활성화되어 있고, 필요시 대시보드에서 직접 끄거나 Post-quantum hybrid/FIPS 같은 준수 요건을 설정할 수 있습니다. harvest-now, decrypt-later 공격과 2029년으로 예상되는 'Q-Day'에 대비해, 수백만 웹사이트 운영자가 암호학 전문가가 될 필요 없이 자동으로 양자 내성을 확보하게 하려는 것이 이 기능의 핵심 목표입니다.</li>
