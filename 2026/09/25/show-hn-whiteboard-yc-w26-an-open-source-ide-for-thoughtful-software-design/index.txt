15:T2368,<p>AI 코딩 에이전트가 만들어내는 코드 변경량이 폭발적으로 늘어나면서, 정작 그 변경을 &quot;이해&quot;하는 일이 새로운 병목이 되고 있습니다. Y Combinator W26 배치에 참여한 Whiteboard는 이 문제를 정면으로 겨냥한 오픈소스 데스크톱 앱인데요, Claude Code나 Codex 같은 코딩 에이전트가 작업 내용을 다이어그램으로 그려서 보여주고, 사람은 그 다이어그램에서 바로 실제 코드로 점프할 수 있게 만든 IDE입니다. 이 글에서는 Whiteboard가 어떤 문제의식에서 출발했고, 어떤 기능을 제공하는지, 그리고 왜 VS Code(Code OSS)를 통째로 vendoring하는 방식을 택했는지 살펴보겠습니다.</p>
<h3>Whiteboard란 무엇인가</h3>
<p>Whiteboard는 사람과 AI 에이전트가 하나의 공용 워크스페이스에서 함께 소프트웨어를 설계할 수 있도록 만든 오픈소스 데스크톱 앱입니다. 이미 쓰고 있는 도구들 — Claude Code, Codex 등 — 에 플러그인 형태로 연결되며, 에이전트에게는 자신의 작업 내용을 앱 내 캔버스에 그림으로 표현할 수 있는 SDK를 제공합니다.</p>
<p>사용 흐름은 간단합니다.</p>
<ul>
<li>macOS 또는 Fedora용 앱을 다운로드해서 실행합니다.</li>
<li>웰컴 화면에서 Claude Code, Codex 등 코딩 에이전트를 연결합니다.</li>
<li>에이전트에게 현재 브랜치를 최신 main과 비교 리뷰하도록 요청하고, 그 결과를 Whiteboard에서 엽니다.</li>
</ul>
<p>팀 측 경험에 따르면 GPT-6 Sol, Claude Opus 5.5 같은 모델이 지능·비용·속도의 균형이 좋아 Whiteboard와 가장 잘 맞는다고 합니다. 아직은 시스템 프롬프트에 올바른 사용 패턴이 완전히 내장되어 있지 않아서, 다음과 같은 예시 프롬프트를 참고용으로 제공하고 있습니다.</p>
<p>새로운 API 변경을 리뷰할 때:</p>
<pre><code>hey, this stack of commits is set up so i can get an [api] to do [objective]
i'd like to see:
proposed api
examples
motivations for this (if available to you in context/in the repo)
and then we can dive into implementation + explaining how things worked.</code></pre>
<p>텔레메트리 추가 변경을 리뷰할 때:</p>
<pre><code>cna you explain to me the telemetry changes form the newest posthog pr https://github.com/devdotfast/whiteboard/commit/4837e107946e27ebad50c282eb0f2585210d2a35 -- what are we tracking, how can we build good dashboards or product waterfalls from it? what do we do for hangs, errors, crashes etc... use whiteboard</code></pre>
<p>마음에 들지 않는 부분이 있다면 클립보드에 복사해서 에이전트에게 넘겨주면, 에이전트가 Whiteboard 위에 다시 그려서 요구사항에 맞춰줄 수도 있습니다.</p>
<h3>왜 이 도구가 필요했나</h3>
<h4>다이어그램에서 코드로</h4>
<p>기존의 순수 HTML 기반 도구들은 스펙이나 다이어그램을 실제 코드와 연결할 손쉬운 방법을 제공하지 못했습니다. 문제는 트레이드오프가 대부분 첫 구현 시도 이후에야 드러난다는 점인데요, Whiteboard에서는 시퀀스 다이어그램, ERD, 혹은 에이전트 트레이스에서 인용된 문구 같은 시각 요소를 클릭하면 곧바로 그 밑에 깔린 코드로 이동할 수 있습니다. 코드를 탐색할 때는 VS Code의 키바인딩과 LSP 지원을 그대로 사용할 수 있습니다.</p>
<h4>시맨틱 diff 뷰어</h4>
<p>일반적인 raw diff 뷰는 노이즈가 너무 많습니다. 그래서 Rust로 AST를 인식하는 시맨틱 diff 뷰어를 직접 만들어, 사용자에게 실제로 유의미한 코드 변경만 보여주도록 했습니다. 기본값으로는 새로 추가된 큰 함수는 의사코드(pseudocode) 요약으로 보여주고, 유닛 테스트나 문서 변경 같은 것들은 접히거나 숨겨집니다. 이 동작은 WASM 기반 플러그인 시스템으로 얼마든지 커스터마이징할 수 있습니다.</p>
<h4>결정 로그(Decision log)</h4>
<p>에이전트가 자율적으로 내린 결정들이 어떤 것이었고, 그것이 전체 변경에 어떤 영향을 미쳤는지 파악하기가 어려웠다는 문제도 있었습니다. 이를 위해 에이전트가 자신의 트레이스를 Whiteboard 위에서 조회하고 링크할 수 있는 도구를 만들었습니다. 이를 통해 사용자가 설정한 요구사항이 어떻게 구현되었는지, 그리고 에이전트가 자율적으로 어떤 판단을 내렸는지를 시각적으로 확인할 수 있습니다.</p>
<h4>오픈소스, 로컬 실행</h4>
<p>Whiteboard는 MIT 라이선스로 배포되며, 로컬 체크아웃 위에서 동작합니다. 팀 단위 호스팅 제품도 계획 중이지만, 언제나 셀프 호스팅이 가능하도록 유지할 방침이라고 밝혔습니다.</p>
<h3>알려진 한계</h3>
<ul>
<li>현재는 Whiteboard 안에서 파일을 직접 편집할 수 없습니다. 필요하다고 느낀다면 이슈로 남겨달라고 안내하고 있습니다.</li>
<li>하나의 리뷰 안에서 여러 저장소를 넘나들며 파일을 탐색하는 기능은 아직 제대로 지원되지 않습니다.</li>
<li>공유 버튼으로 리뷰를 다른 머신과 공유할 수는 있지만, 공유 이후에 리뷰가 업데이트되어도 상대방에게는 반영되지 않습니다. 이 경우 다시 공유해야 합니다.</li>
</ul>
<h3>Code OSS를 통째로 vendoring한 이유</h3>
<p>요즘은 다들 전용 에이전트 TUI나 데스크톱 앱을 쓰다 보니, 정작 텍스트 에디터는 라인 단위 diff를 리뷰할 때만 쓰게 됩니다. 그렇다면 아예 &quot;코드 리뷰&quot;를 위해 만들어진 에디터가 있으면 어떨까 하는 생각에서, 가장 성공적인 오픈소스 에디터를 베이스로 삼는 게 낫다고 판단했다고 합니다.</p>
<p>다른 포크들이 패치 방식을 유지하는 것과 달리 Whiteboard는 Code OSS를 통째로 vendoring 하는 방식을 택했는데, 이유는 두 가지입니다. 첫째, 코딩 에이전트가 패치 방식을 잘 다루지 못한다는 점. 둘째, 요즘 순정 VS Code 코드베이스의 약 45%가 Copilot 관련 코드라서(원문 표현: &quot;~45% of the codebase is Copilot these days 😬&quot;), 굳이 필요 없는 부분까지 패치로 끌고 갈 이유가 없다는 점입니다. 대신 업스트림 Code OSS를 꾸준히 모니터링하면서 보안·기능 패치를 그때그때 병합하는 방식으로 관리하고 있습니다.</p>
<h3>참고한 관점들</h3>
<p>Whiteboard 팀은 이 프로젝트의 문제의식에 영향을 준 글들을 함께 소개하고 있습니다. Geoffrey Litt의 &quot;Understanding is the new bottleneck&quot;은 현대 소프트웨어 엔지니어링의 제약을 잘 정리한 글로 언급되며, Maggie Appleton의 &quot;vibe legacy code&quot;와 Val Town 블로그의 &quot;vibe code&quot; 글은 AI가 생성한 코드가 2025년 이전의 소프트웨어 엔지니어링 개념과 어떻게 맞물리는지를 잘 설명한다고 소개하고 있습니다. 또한 Andrej Karpathy가 LLM 에이전트, 그리고 에이전트를 &quot;junior engineer savants(뛰어난 재능은 있지만 경험이 부족한 주니어 엔지니어)&quot;에 비유한 트윗들도 함께 인용하고 있습니다.</p>
<h3>정리</h3>
<p>Whiteboard는 &quot;AI 에이전트가 코드를 짜는 속도&quot;와 &quot;사람이 그 코드를 이해하는 속도&quot; 사이의 격차를 캔버스 기반 인터페이스로 메우려는 시도입니다. 핵심은 세 가지로 요약됩니다.</p>
<ul>
<li><strong>다이어그램-코드 연결</strong>: 시퀀스 다이어그램, ERD, 에이전트 트레이스 인용문에서 실제 코드로 바로 점프할 수 있고, VS Code 수준의 편집기 경험(키바인딩, LSP)을 그대로 활용합니다.</li>
<li><strong>시맨틱 diff</strong>: Rust로 작성한 AST 인식 diff 뷰어로 노이즈를 걷어내고, WASM 플러그인으로 어떤 변경을 보여줄지 커스터마이징할 수 있습니다.</li>
<li><strong>결정 로그</strong>: 에이전트가 자율적으로 내린 판단을 추적 가능하게 만들어, &quot;왜 이렇게 구현됐는가&quot;를 사후에 재구성할 수 있게 합니다.</li>
