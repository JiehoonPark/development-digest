Shopify, React Native에서 다시 Swift·Kotlin 네이티브로 회귀하다

Shopify is moving from React Native back to Swift and Kotlin

📅 2026-09-11📰 Hacker News (Top)
frontend

Shopify가 2020년 React Native로 전면 전환한 지 5년 만에, 다시 Swift와 Kotlin 네이티브로 돌아가겠다고 발표했습니다. 흥미로운 점은 이 결정의 핵심 배경이 프레임워크 자체의 문제가 아니라 "코딩 에이전트의 성능 향상"이라는 것인데요. 이 글에서는 Shopify가 왜 이런 결정을 내렸는지, 그리고 실제로 어떻게 마이그레이션을 진행하고 있는지 정리해보겠습니다.

2020년의 선택과 2025년의 재검토

Shopify는 2020년 React Native에 올인하기로 결정했고, 이 선택은 매우 성공적이었습니다. 기능을 한 번만 만들어도 됐고, 모바일 경험이 없는 개발자도 앱 개발에 기여할 수 있었으며, 플랫폼 간 기능 격차를 따라잡느라 시간을 낭비할 필요가 없었습니다.

실제로 2025년 1월, Shopify의 엔지니어링 리더는 React Native의 미래가 밝다며 계속 투자하겠다고 밝힌 바 있습니다. 당시 알고 있던 정보를 기준으로는 사실이었고, React Native는 여전히 훌륭한 프레임워크였습니다.

하지만 그 이후 코딩 모델의 성능이 극적으로 좋아지면서 상황이 달라졌습니다. Shopify의 앱과 팀에게 있어 Swift와 Kotlin으로 같은 기능을 각각 구현하는 비용이 예전만큼 크지 않게 된 것입니다. Shopify는 결정이 한때 성공적이었다는 이유만으로 그 결정을 고수하지 않는다는 원칙을 갖고 있는데요, 핵심 전제가 바뀌었다면 처음부터 다시 검토한다는 것입니다. 2020년 결정의 핵심 전제 중 하나가 LLM에 의해 바뀌었기 때문에, 모바일 스택 전체를 원점에서 재평가하게 됐습니다.

왜 다시 네이티브로 돌아가는가

2020년 React Native로 전환한 이유는 세 가지였습니다.

  • 같은 기능을 두 번 만들지 않기
  • 개발자가 스택 전반에서 일할 수 있게 하기
  • 기능 격차를 좇는 대신 가치를 더 많이 출시하기

React Native는 이 세 가지 이점을 꾸준히 제공했습니다. 성능 최적화, 프레임워크 핵심 영역 개선, 프레임워크 업데이트 및 외부 의존성 관리에 상당한 시간과 리소스를 투입해야 했지만, 이는 감수할 만한 트레이드오프였고 React Native를 사용함으로써 얻는 이점이 이러한 투자를 훨씬 상회했습니다.

Shopify는 ChatGPT가 나오기 1년 전인 2021년부터 LLM을 소프트웨어 개발에 활용해왔습니다. 처음에는 기능 구현, 버그 조사 및 수정, 코드 리뷰에 사용했는데, 모델이 발전하면서 LLM에 맡길 수 있는 작업의 복잡도도 함께 커졌습니다. 2025년 말에 이르러서는 단순히 코드를 더 빨리 쓰도록 돕는 수준을 넘어, "소프트웨어를 두 번 만드는 것이 여전히 두 배의 작업을 의미하는가"라는 질문 자체를 던지게 만드는 수준이 되었습니다.

Shopify는 모바일 기술 스택을 재검토하기로 하고, 기존 기술 선택이 여전히 유효한지 확인하기 위한 프로토타이핑에 착수했습니다. 가장 큰 앱들의 핵심 부분을 LLM을 활용해 Swift와 Kotlin으로 다시 만들어봤는데, 결과는 예상보다 훨씬 좋았습니다. 에이전트는 다음과 같은 일을 해냈습니다.

  • iOS 버전을 참조해서 Android 기능을 구현(혹은 그 반대)
  • 개발자가 자신의 주력 스택이 아닌 영역에서도 빠르게 적응하고 효과적으로 기여하도록 지원
  • 공유 스펙, 테스트, 리뷰 체크포인트를 통해 플랫폼 간 기능 동등성을 유지하는 비용을 대폭 절감

네이티브로 전환해도 두 플랫폼에서 소프트웨어를 각각 만들고 유지보수해야 하는 비용 자체가 사라지는 것은 아닙니다. 달라진 것은, 에이전트가 구현·변환(translation)·테스트·리뷰 작업의 상당 부분을 처리할 수 있게 되면서 이 비용이 2020년만큼 결정적인 요소가 아니게 됐다는 점입니다.

Shopify는 React Native로도 빠른 앱을 만들 수 있고, 실제로 그렇게 해왔다는 점을 분명히 했습니다. 이번 전환의 이유는 에이전트가 "구현을 공유하는 이점"을 줄여준 반면, "각 플랫폼에 맞춰 만드는 이점"은 그대로 남아있기 때문입니다. 네이티브로 가면 플랫폼 고유 기능과 퍼스트파티 툴링에 더 가까워지고, 코드와 플랫폼 사이에 놓인 프레임워크·의존성 레이어가 줄어듭니다.

React Native 오픈소스 라이브러리들의 향방

Shopify는 그동안 각 카테고리에서 사실상 표준으로 자리 잡은 오픈소스 라이브러리들을 React Native 생태계에 기여해왔습니다. 전환 과정에서도 커뮤니티에 갑작스러운 영향이 없도록 하겠다는 방침입니다.

React Native Skia — Shopify는 2026년 말까지 계속 스폰서십을 유지하며, 메인테이너인 William Candillon은 그 이후로도 작업을 이어갑니다. 그는 조만간 저장소를 포크해 새로운 이름으로 라이브러리를 배포할 예정이며, 전환이 완료되면 기존 저장소는 아카이브됩니다. 이 라이브러리에 의존하는 앱이 있다면 스폰서십을 고려해달라고 요청했습니다.

FlashList — 주간 다운로드 약 200만 건에 달하며, React Native에서 고성능 리스트를 렌더링하는 기본 선택지로 자리잡은 라이브러리입니다. 생태계에 미치는 영향이 큰 만큼, 호환성을 깨뜨리는 치명적인 이슈는 계속 수정할 예정이며, 장기적인 관리(stewardship)를 맡을 여러 회사와 논의 중이라고 밝혔습니다.

Restyle — 상대적으로 사용자 기반이 작아 저장소를 아카이브하기로 했습니다. 2026년 말까지는 정상 동작하도록 유지하되 그 이후로는 메인테인을 중단하며, 누구든 포크해서 이어갈 수 있고 필요하면 인수인계도 돕겠다고 밝혔습니다.

마이그레이션 전략: 브라운필드 대신 그린필드

Shopify에는 Shopify, Shop, Point of Sale, Inbox 등 수백만 상인과 구매자가 매일 사용하는 대형 앱들이 있습니다. 과거 React Native로 전환할 때는 일부 대형 앱에 대해 점진적 마이그레이션(브라운필드) 방식을 택했습니다. 전체를 새로 짜는 데 몇 년이 걸리고, 그 사이 신규 기능 출시를 멈춰야 했기 때문입니다.

하지만 이번에는 처음부터 다시 만드는 그린필드 방식이 명확한 우위를 보였습니다. 이유는 다음과 같습니다.

  • LLM이 React Native 버전을 참조 삼아 Swift와 Kotlin으로 기능을 구현하는 데 뛰어남
  • 이전의 제약 없이 최선의 방식으로 다시 설계할 수 있는 백지 상태를 제공
  • 프로토타입 결과, 코딩 에이전트 이전에는 불가능했던 속도로 앱을 재구축할 수 있음이 확인됨

앱스토어 쇼핑 카테고리에서 늘 상위권에 오르는 Shop 앱이 첫 번째 마이그레이션 대상이었습니다. AI의 도움으로, 팀은 개념 증명(PoC) 단계에서 앱스토어에 출시된 완전한 네이티브 앱까지 단 12주 만에 도달했습니다.

가장 큰 앱인 Shopify 앱(화면 300개 이상, 홈/잠금화면 위젯, Apple Watch 앱, 컴플리케이션, Siri 단축어 등 포함)의 마이그레이션도 진행 중이며 올해 안에 출시될 예정입니다. 나머지 앱들도 곧 뒤따를 계획입니다.

"슬롭(slop)" 방지하기: Helix 시스템

LLM에게 React Native 코드베이스를 통째로 보여주고 네이티브로 한 번에 변환("one-shot")하라고 시키고 싶은 유혹이 있지만, 이는 실제로 작동하지 않습니다. 사전에 최대한 많은 정보를 수집해서 스펙과 태스크 파일로 얼려놓고 구현하게 해도, 결과적으로는 유지보수가 불가능하고 출시할 수 없는 방대한 코드 더미만 남게 됩니다.

이 문제를 해결하기 위해 Shopify는 Helix라는 시스템을 구축했습니다. Helix는 첫 결과물이 정확할 것이라 기대하지 않고, 불완전한 시도가 좋은 결과가 되기 전까지는 다음 단계로 넘어갈 수 없는 루프를 만드는 방식으로 작동합니다.

개발자가 Helix에 특정 화면을 지정하면, Helix는 React Native 코드를 읽고 몇 분 안에 검토 가능한 작은 순서형 작업 단위(체크포인트)들을 제안합니다. 그다음 체크포인트 단위로 빌드가 진행되는데, 각 체크포인트는 테스트로 동작을 증명해야 하고, 실행 중인 앱과 비교하는 비주얼 리뷰를 통과해야 하며, 두 개의 적대적(adversarial) 코드 리뷰어를 통과하고, 사람의 승인을 받아야 커밋되고 다음 단계로 넘어갑니다. 모든 리뷰의 피드백은 기억되기 때문에, 마이그레이션이 진행될수록 루프는 점점 더 자율적으로 작동하게 됩니다. 이 접근 방식은 매우 효과적으로 작동하고 있으며, 훨씬 짧은 시간 안에 앱을 재구축할 수 있게 해주고 있습니다.

빠른 피드백 루프 만들기

에이전트가 시뮬레이터를 제어하는 부분은 그동안 병목이었습니다. 시뮬레이터가 빌드, 테스트, 반복 작업을 안정적으로 수행하지 못해 계속 지켜보고 있어야 했습니다. 버그를 재현하고, 수정하고, 자율적으로 검증하는 툴링을 만들었지만 느리고 불안정했습니다. React Native의 핫 모듈 리로드가 도움이 되긴 했지만 근본 문제, 즉 시뮬레이터 제어 속도 문제를 해결해주지는 못했습니다. 이는 주로 앱 상태를 확인하고 액션을 수행하고 결과를 검증하기 위해 접근성 트리(accessibility tree)나 스크린샷에 의존하기 때문입니다. 에이전트는 코드를 몇 초 만에 수정할 수 있지만, 결과를 테스트하는 데는 몇 분이 걸립니다. 모델이 아무리 뛰어나도 작업 결과를 빠르게 테스트할 수 없다면 반복 속도는 매우 느리고 수작업에 의존할 수밖에 없는데, 특히 모바일 환경에서는 이 문제가 더 두드러집니다.

Shopify는 앱 아키텍처를 사람과 에이전트 모두를 위해 설계함으로써 이 문제를 해결하고 있습니다. 핵심 원칙은 비즈니스 로직을 UI로부터 완전히 분리해, 데스크톱에서 헤드리스로 실행 가능하게 만드는 것입니다. 그리고 이를 CLI를 통해 에이전트에 제공함으로써, 시뮬레이터를 거치지 않고 밀리초 단위로 반복 작업을 할 수 있게 만들었습니다.

이 CLI를 통해 에이전트는 UI를 건드리지 않고도 앱 상태를 확인하고, 화면 간 이동을 하고, 액션을 수행할 수 있습니다. 이를 통해 매우 빠른 피드백 루프가 가능해지고, 에이전트가 몇 시간씩 자율적으로 작업할 수 있게 됩니다. 시뮬레이터 상호작용이 꼭 필요한 경우에는, 레이아웃이나 접근성 트리를 검사할 필요 없이 CLI가 원격 모드로 시뮬레이터에 연결해 명령어로 UI를 직접 구동할 수 있습니다. 이를 통해 매우 빠른 성능과 E2E 테스트가 가능해졌습니다.

앞으로의 계획

Shopify는 AI를 활용해 모든 모바일 앱을 Swift와 Kotlin으로 마이그레이션할 계획입니다. Shop 앱은 이미 완전한 네이티브 앱으로 출시됐고, Shopify 앱은 진행 중이며, 나머지 앱들도 곧 뒤따를 예정입니다. 다만 속도를 위해 품질 기준을 낮추지는 않겠다고 강조했습니다. 재구축된 모든 앱은 현재 사용자가 기대하는 성능, 안정성, 접근성, 제품 품질을 충족하거나 뛰어넘어야 합니다. 이는 단순히 같은 앱을 다른 언어로 다시 쓰는 작업이 아니라, 사람과 에이전트 모두가 빠르게 이해하고 테스트하고 변경할 수 있도록 앱을 다시 설계하는 작업입니다.

마이그레이션 자체가 목표는 아닙니다. 성공의 기준은 팀이 상인과 구매자에게 이전보다 더 나은 경험을 더 빠르게 제공할 수 있는지입니다. Shopify는 이를 제품 개발 속도, 앱 품질, 그리고 에이전트가 자율적으로 완수할 수 있는 작업량으로 측정하겠다고 밝혔습니다. 향후 Helix, 에이전트 친화적 아키텍처, 에이전트와 함께 모바일 앱을 만드는 방법에 대해 더 깊이 있는 후속 글을 공유할 계획입니다.

정리

  • Shopify는 2020년 React Native로 전면 전환해 큰 성공을 거뒀지만, 2025년 말 코딩 에이전트의 성능이 비약적으로 향상되면서 "같은 기능을 두 번 만드는 비용"이라는 전제 자체가 바뀌었다고 판단하고 다시 Swift/Kotlin 네이티브로 전환하기로 결정했습니다.
  • 프로토타이핑 결과, 에이전트는 한 플랫폼의 구현을 참조해 다른 플랫폼 코드를 생성하고, 개발자의 스택 간 이동을 돕고, 플랫폼 간 기능 동등성 유지 비용을 크게 낮추는 것으로 확인됐습니다. 반면 네이티브가 주는 플랫폼 밀착성과 성능 이점은 그대로 남아 있어, 저울추가 다시 네이티브 쪽으로 기울었습니다.
  • 이번 마이그레이션은 점진적 전환(브라운필드)이 아니라 처음부터 재구축(그린필드) 방식을 택했으며, Shop 앱은 PoC부터 앱스토어 출시까지 단 12주 만에 완료했습니다.
  • "슬롭"을 방지하기 위해 Helix라는 체크포인트 기반 시스템을 구축해 테스트·비주얼 리뷰·적대적 코드 리뷰·사람 승인을 거치는 점진적 루프를 만들었고, 비즈니스 로직을 UI에서 분리해 CLI로 헤드리스 테스트가 가능하도록 아키텍처를 재설계해 피드백 루프를 분 단위에서 밀리초 단위로 단축했습니다.
  • React Native Skia, FlashList, Restyle 등 Shopify가 유지해온 주요 오픈소스 라이브러리는 각각 스폰서십 지속, 스튜어드십 이관 논의, 아카이브 등 서로 다른 방식으로 커뮤니티에 부담이 적도록 정리되고 있습니다.
