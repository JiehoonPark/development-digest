15:T290e,<h2>WebGPU 셰이더 하나로 맥을 멈춰 세우는 법: &quot;Deathray&quot; 취약점 분석</h2>
<p>신뢰할 수 없는 웹사이트가 링크 클릭 한 번만으로 맥 사용자의 화면을 완전히 멈춰버릴 수 있다면 믿으시겠어요? 보안 연구자 Auberon López가 발견한 &quot;Deathray&quot;는 WebGPU의 컴퓨트 셰이더를 악용해 macOS의 WindowServer를 마비시키고 결국 커널 패닉으로 재부팅까지 유도하는 취약점입니다. 이 글에서는 Deathray가 어떤 원리로 동작하는지, 왜 macOS에서만 재현되는지, 그리고 Apple이 이 문제를 어떻게 처리했는지 살펴보겠습니다.</p>
<h3>무슨 일이 일어나는가</h3>
<p>Deathray는 WebGPU 셰이더를 이용해 맥의 그래픽 파이프라인을 통째로 정지시킵니다. 피해자가 해야 할 일은 단 하나, 악성 링크를 클릭하는 것뿐입니다. 이 문제는 Chrome, Firefox, Safari 등 브라우저 종류와 무관하게 macOS 전반에서 재현되며, 저자는 Tahoe(macOS 26)를 탑재한 M-시리즈 맥북에서 테스트를 진행했습니다. 반면 다른 OS에서는 탭이 잠깐 버벅이다가 탭을 닫으면 정상으로 돌아오는 수준에 그칩니다.</p>
<h3>어떻게 동작하는가</h3>
<p>Deathray는 WebGL을 대체하기 위해 등장한 비교적 최신 기술인 WebGPU를 사용합니다. WebGPU는 웹사이트가 GPU에 셰이더를 제출해 실행할 수 있도록 해주는 브라우저 내장 API입니다. Deathray 전체 코드는 작은 파일 하나에 들어갈 정도로 단순하며, 핵심은 아래 세 개의 셰이더입니다.</p>
<p><strong>컴퓨트 셰이더</strong></p>
<pre><code class="language-wgsl">@group(0) @binding(0) var&lt;storage, read_write&gt; data : array&lt;vec4f&gt;;
@compute @workgroup_size(1) fn compute() {
  // no i++, loop spins endlessly
  for(var i = 0u; i &lt; 1;) {
    data[i+1] = data[i];
  }
}</code></pre>
<p><strong>렌더 셰이더</strong></p>
<pre><code class="language-wgsl">@group(0) @binding(0) var&lt;storage, read&gt; data : array&lt;vec4f&gt;;
@vertex fn vert(@builtin(vertex_index) vertexIdx : u32)
  -&gt; @builtin(position) vec4f {
  // attempts to read from same buffer the compute shader writes to
  let datum = data[vertexIdx];
  return datum;
}
@fragment fn frag(@builtin(position) pos : vec4f)
  -&gt; @location(0) vec4f {
  return pos;
}</code></pre>
<p>컴퓨트 셰이더를 보면 <code>i++</code>가 없어서 무한 busy loop가 돌면서 같은 벡터를 버퍼에 계속 복사합니다. 문제는 vertex 셰이더가 바로 이 버퍼를 읽으려 한다는 점입니다. 컴퓨트 셰이더가 무한 루프에 갇혀 있으니 vertex 셰이더는 영원히 진행할 수 없고, 이 정체가 GPU를 사용하려는 다른 프로세스, 특히 macOS의 WindowServer로까지 번져나갑니다.</p>
<p>증상은 매번 조금씩 다르게 나타납니다. 마우스는 움직이는데 화면만 멈추기도 하고, 아예 비치볼(로딩 커서)이 뜨기도 하며, 화면 일부에 마젠타색 잔상이 나타나기도 합니다. 흥미로운 점은 이 순간에도 컴퓨터 자체는 살아있다는 것입니다. SSH 접속은 문제없이 됩니다. 다만 WindowServer를 감시하는 Watchdog이 일정 시간 이상 응답이 없다고 판단하면 커널 패닉을 일으켜 강제로 재부팅시킵니다. 급하다면 전원 버튼을 길게 눌러 강제 종료할 수도 있는데, 문제는 브라우저가 재시작 시 같은 탭을 자동으로 복원할 수도 있다는 점입니다.</p>
<h3>처음 있는 일은 아니다</h3>
<p>사실 Apple이 이런 종류의 문제를 겪은 게 이번이 처음은 아닙니다. 2023년 Imperva의 Ron Masas는 WebGL을 이용한 유사한 공격인 &quot;ShadyShader&quot;를 만든 바 있습니다. ShadyShader 역시 GPU를 독점하는 폭주 루프를 사용했지만, 기술적으로는 무한이 아닌 거대한 중첩 루프 형태였습니다.</p>
<p>Apple은 이에 대응해 CVE-2023-40441(CVSS 6.5, medium)을 발급하고, 폭주 루프를 더 잘 탐지하기 위한 입력 검증을 강화했습니다. 그런데 WebGPU에서는 이 입력 검증이 상대적으로 약한 것으로 보입니다. Deathray의 루프는 누가 봐도 명백한 무한 루프인데도 걸러지지 않으니까요. 저자는 애초에 무한 루프 탐지 자체가 결국 &quot;정지 문제(halting problem)&quot;에 부딪히는 승산 없는 싸움이라고 지적합니다. 근본적으로는 응답 없는 셰이더를 선점(pre-empt)할 수 있는 체계가 필요한데, 저자가 테스트한 다른 모든 OS는 이 부분을 제대로 처리하고 있습니다.</p>
<p>저자는 이 문제가 M-시리즈 칩의 아키텍처와 관련이 있을 수 있다고 추측합니다. M-시리즈에서는 OS 커널이 GPU를 직접 선점할 수 없고, ASC라는 코프로세서를 통해 GPU를 제어합니다. GPU 선점 로직 자체가 이 ASC 펌웨어 안에 들어있다는 것입니다. 이와 관련해서는 Asahi Lina가 M-시리즈 GPU 아키텍처를 상세히 분석한 글을 참고할 만합니다.</p>
<h3>발견 경위</h3>
<p>이 취약점은 상당히 우연히 발견됐습니다. 저자는 Recurse Center에서 WebGPU를 공부하다가 실수로 무한 루프를 작성했는데, 그 순간 컴퓨터가 그대로 멈춰버렸습니다. &quot;이거 매번 이러나?&quot; 싶어 다시 시도해봤더니 정말로 매번 재현됐다고 합니다. 저자 스스로도 이걸 처음 발견한 사람이 자신일 리 없다고 언급합니다.</p>
<h3>Apple에 제보한 결과</h3>
<p>이 문제는 2026년 7월 27일 Apple Security에 제보됐습니다. Apple은 빠르게 문제를 재현했고 수정할 계획이라고 밝히며 (비공개로 처리된) 수정 일정까지 제시했습니다.</p>
<p>그런데 8월 26일, Apple은 태도를 바꿔 &quot;이 보고서에서 보안적 함의를 발견하지 못했다&quot;며 &quot;Apple 제품에 어떠한 변경도 이끌어내지 못했다&quot;고 통보했습니다. 대신 &quot;잠재적 개선 사항 검토&quot;를 위해 다른 팀으로 보고서를 넘기겠다고 했는데, 저자는 이것이 사실상 우선순위가 매우 낮은 이슈로 취급받는 것이나 다름없다고 해석합니다. ShadyShader가 CVSS 6.5의 medium 등급을 받았던 것과 비교하면 다소 의아한 결정이라는 게 저자의 시각입니다.</p>
<p>Apple의 공식 입장은 이렇습니다. &quot;결과가 크래시, 행업(hang), 혹은 복구 가능한 데이터 손실인 경우 우리는 이를 보안 이슈로 간주하지 않는다.&quot; 저자가 이야기를 나눠본 보안 연구자 대부분도 이 판단에 동의하는 편이라고 합니다. 기술적으로 틀린 말은 아니라는 것이죠.</p>
<p>반면 보안 전문가가 아닌 일반 사용자들의 반응은 사뭇 다릅니다. 대부분의 사람들은 &quot;링크를 클릭하는 정도로는 컴퓨터에 실질적인 피해가 없을 것&quot;이라는 암묵적 신뢰를 가지고 브라우저를 사용합니다. Deathray처럼 그 신뢰를 이렇게까지 눈에 띄게 무너뜨리는 사례를 접하면, 일반 사용자 입장에서는 이를 충분히 보안 문제로 느낄 수밖에 없다는 게 저자의 주장입니다.</p>
<h3>저자가 바라는 것</h3>
<p>Deathray는 샌드박스 탈출이나 원격 코드 실행(RCE), 데이터 유출 같은 중대한 취약점에 비할 바는 아닙니다. 하지만 &quot;링크 클릭 한 번&quot;이라는 극도로 낮은 진입 장벽을 생각하면 악용될 경우 상당히 성가신 결과를 낳을 수 있습니다. 저자는 이를 &quot;좀 더 짓궂은 버전의 Rickroll&quot; 정도로 표현하며, Apple이 이 문제를 너무 오래 방치하지 않기를 바란다고 밝혔습니다. 다만 그 해결책이 WebGPU를 기본값에서 비활성화하는 방식은 아니었으면 좋겠다는 바람도 덧붙였습니다.</p>
<p>Apple이 고칠 때까지는, 사람들이 이걸 악의적이지 않은 방식으로 재미있게 활용해봤으면 좋겠다는 것이 저자의 소망입니다. 예를 들어 게임에서 지면 (사용자가 사전에 동의한 상태에서) 실제로 맥이 멈춰버리는 식의 &quot;게임에서 죽으면 진짜로 죽는&quot; 컨셉의 게임을 만들어보는 것도 재미있겠다는 아이디어를 제시하며 글을 마무리합니다.</p>
<h3>정리</h3>
<ul>
<li><strong>핵심 메커니즘</strong>: WebGPU 컴퓨트 셰이더에 무한 루프를 넣고, 같은 버퍼를 읽는 vertex 셰이더를 결합하면 GPU 파이프라인 전체가 정체되고, 이 정체가 macOS의 WindowServer까지 전파되어 결국 Watchdog에 의한 커널 패닉·재부팅으로 이어집니다.</li>
<li><strong>재현 범위</strong>: Chrome, Firefox, Safari를 가리지 않고 macOS(테스트는 M-시리즈 Tahoe 기준)에서 재현되지만, 다른 OS에서는 탭 프리징 정도에 그칩니다.</li>
<li><strong>선례와의 비교</strong>: 2023년 WebGL 기반 ShadyShader(CVE-2023-40441, CVSS 6.5)와 유사한 클래스의 문제지만, Apple이 강화한 입력 검증도 WebGPU의 단순한 무한 루프는 걸러내지 못하고 있습니다.</li>
<li><strong>구조적 원인 추정</strong>: M-시리즈 칩에서는 OS 커널이 GPU를 직접 선점하지 못하고 ASC 코프로세서를 거쳐야 하는데, GPU 선점 로직이 ASC 펌웨어에 있다는 점이 근본 원인일 가능성이 제기됩니다.</li>
