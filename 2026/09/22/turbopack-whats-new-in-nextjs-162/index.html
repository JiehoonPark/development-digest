Turbopack, Next.js 16.2에서 무엇이 달라졌나

Turbopack: What's New in Next.js 16.2

📅 2026-09-22📰 Next.js Blog
frontendtypescript

Next.js 16.1에서 Turbopack이 기본 번들러로 전환된 이후, Vercel 팀은 두 번의 릴리스를 거치며 성능 개선과 버그 수정, 그리고 기존 웹팩 기반 기능과의 파리티(parity) 확보에 집중해 왔습니다. Next.js 16.2에서는 서버 사이드 개발 경험을 크게 개선하는 Server Fast Refresh를 비롯해, 보안·CSS·로더 설정 관련 여러 기능이 추가되었습니다. 이번 글에서는 16.2에 담긴 주요 변경 사항을 정리합니다.

Server Fast Refresh: 서버 코드도 세밀하게 핫 리로딩

지금까지 개발 서버에서 서버 사이드 코드를 수정하면, Next.js는 변경된 모듈뿐 아니라 해당 모듈의 import 체인에 포함된 모든 모듈의 require.cache를 통째로 비워버렸습니다. 이 방식은 실제로 바뀌지 않은 node_modules까지 다시 로드하게 되는 경우가 많아 비효율적이었습니다.

16.2에서는 브라우저에서 사용하던 Fast Refresh 방식을 서버 코드에도 그대로 적용했습니다. Turbopack이 모듈 그래프를 정확히 파악하고 있기 때문에, 실제로 변경된 모듈만 리로드하고 나머지는 그대로 유지할 수 있게 된 것입니다. 이 덕분에 서버 사이드 핫 리로딩이 훨씬 효율적으로 동작합니다.

실제 Next.js 애플리케이션에서 측정한 결과, 애플리케이션 리프레시 속도는 67~100% 빨라졌고, Next.js 내부 컴파일 시간은 400~900% 빨라졌습니다. 이 개선 폭은 작은 "hello world" 스타터 프로젝트부터 vercel.com 같은 대규모 사이트까지 일관되게 나타났습니다.

예시로 든 샘플 사이트의 서버 리프레시 시간을 보면, Next.js 내부 처리 시간은 40ms에서 2.7ms로, 애플리케이션 처리 시간은 19ms에서 9.7ms로 줄어 전체적으로 375% 빨라졌습니다.

이 기능은 16.2부터 모든 개발자에게 기본으로 활성화됩니다. 다만 Proxy와 Route Handlers는 아직 기존 방식을 그대로 사용하며, 이에 대한 지원은 추후 릴리스에서 추가될 예정입니다. 관련 피드백이나 이슈는 GitHub를 통해 제보할 수 있습니다.

Web Worker Origin: WASM 라이브러리 지원 강화

기존에는 Web Worker가 blob:// URL을 통해 부트스트랩되었습니다. 이 방식은 워커 로딩을 간소화하는 장점이 있었지만, location.origin 값이 빈 값으로 설정되는 문제가 있었습니다. 그 결과 importScripts()나 fetch()를 사용하는 워커 코드(주로 서드파티 라이브러리)는 별도 수정 없이는 요청을 정상적으로 처리할 수 없었습니다.

이번에 워커 부트스트랩 코드가 개선되면서 origin이 실제 도메인을 정확히 가리키게 되었고, 상대 경로 fetch 요청도 정상적으로 성공합니다. 이전 버전에서 워커 내부에서 WASM 코드를 실행하다 문제를 겪었던 사용자라면 이번 업데이트로 해결될 가능성이 높습니다.

Subresource Integrity 지원

Turbopack이 이제 Subresource Integrity(SRI)를 지원합니다. SRI는 빌드 시점에 JavaScript 파일의 암호화 해시를 생성해, 브라우저가 파일이 변조되지 않았는지 검증할 수 있게 해주는 기술입니다.

브라우저는 Content Security Policy(CSP)라는 기술을 통해 실행 가능한 JavaScript를 제한함으로써 특정 유형의 보안 취약점을 원천 차단할 수 있습니다. 그런데 일반적인 nonce 기반 CSP 구현 방식은 모든 페이지를 동적으로 렌더링해야 하기 때문에 성능에 영향을 줍니다. Subresource Integrity는 이에 대한 대안으로, 각 스크립트의 해시를 미리 계산해두고 승인된 해시를 가진 스크립트만 브라우저가 실행하도록 허용합니다.

// next.config.js
const nextConfig = {
  experimental: {
    sri: {
      algorithm: 'sha256',
    },
  },
};
module.exports = nextConfig;

동적 import의 Tree Shaking

Turbopack이 이제 구조 분해된 동적 import에도 정적 import와 동일한 방식으로 tree shaking을 적용합니다. 사용하지 않는 export는 번들에서 제거됩니다.

const { cat } = await import('./lib');

이제 이 코드는 tree shaking 관점에서 정적 import와 동일하게 취급됩니다. ./lib에서 export된 것 중 실제로 사용되지 않는 항목은 모두 제거됩니다.

인라인 로더 설정

Turbopack이 import attributes를 통한 import 단위 로더 설정을 지원합니다. 지금까지는 turbopack.rules를 통해 전역적으로 로더를 적용해야 했지만, 이제는 with 절을 사용해 개별 import에 로더를 지정할 수 있습니다.

import rawText from './data.txt' with {
  turbopackLoader: 'raw-loader',
  turbopackAs: '*.js',
};

import value from './data.js' with {
  turbopackLoader: 'string-replace-loader',
  turbopackLoaderOptions: '{"search":"PLACEHOLDER","replace":"replaced value"}',
};

이 방식은 특정 import에만 특별한 처리가 필요할 때, 같은 파일 타입의 다른 import에 영향을 주지 않고 적용할 수 있어 유용합니다. 사용 가능한 attribute는 turbopackLoader, turbopackLoaderOptions, turbopackAs, turbopackModuleType 네 가지입니다.

다만 가능하다면 로더 설정은 여전히 next.config.ts에서 하는 것을 권장합니다. 인라인 로더를 사용한 코드는 이식성이 떨어지기 때문입니다. 이 옵션은 플러그인이나 로더가 생성한 코드에 더 적합합니다.

Lightning CSS 설정

Lightning CSS는 Turbopack이 CSS 압축과 벤더 프리픽스 처리에 사용하는 Rust 기반의 빠른 CSS 트랜스포머입니다. JavaScript에서 Babel이나 SWC가 하는 역할과 비슷하게, 최신 CSS 기능을 구형 브라우저에서도 동작하도록 변환해줍니다. 지금까지는 이런 설정을 Browserslist 설정을 통해서만 조정할 수 있었지만, 이제 실험적인 lightningCssFeatures 옵션을 통해 특정 기능을 항상 트랜스파일하거나 절대 트랜스파일하지 않도록 강제할 수 있습니다.

import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  experimental: {
    useLightningcss: true,
    lightningCssFeatures: {
      include: ['light-dark', 'oklab-colors'],
      exclude: ['nesting'],
    },
  },
};

export default nextConfig;

로그 필터링

Turbopack이 turbopack.ignoreIssue 설정 옵션을 통해 스트리밍 로그에서 나오는 불필요한 경고를 억제할 수 있게 되었습니다. 서드파티 코드나 자동 생성된 파일, 선택적 의존성에서 발생하는 경고를 숨기거나, Next.js 에러 오버레이에서 예상된 에러를 숨기는 데 유용합니다.

특정 코드 경로에서 발생한 로그를 매칭하거나, 제목/설명 문자열 또는 패턴으로 필터링할 수 있습니다.

import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  turbopack: {
    ignoreIssue: [
      { path: '**/vendor/**' },
      { path: 'app/**', title: 'Module not found' },
      { path: /generated\/.*\.ts/, description: /expected error/i },
    ],
  },
};

export default nextConfig;

postcss.config.ts 지원

Turbopack이 기존 .js, .cjs 형식에 더해 postcss.config.ts도 지원합니다.

성능 개선 및 버그 수정

Turbopack 내부 구조에 대한 투자도 계속되고 있습니다. 이번 릴리스에서만 200건이 넘는 변경 사항과 버그 수정이 이루어져 다양한 프로젝트에서의 안정성과 호환성이 개선되었습니다. 데이터 인코딩, 내부 표현 형식, 해싱 알고리즘의 최적화를 통해 메모리 사용량과 빌드 시간도 개선되었습니다. 에러 로그를 더 명확하게 다듬었고, 컴파일러 에러를 더 잘 이해할 수 있도록 진단 정보도 확장했습니다. 또한 16.1 릴리스 이후 누락된 기능을 파악하는 데 GitHub Issues를 적극 참고했다고 밝혔습니다.

Next.js 팀은 다음 릴리스에서 컴파일러 성능 향상과 메모리 사용량 감소에 집중할 계획이라고 예고했습니다.

정리

  • Server Fast Refresh가 기본 활성화되면서 서버 사이드 코드 변경 시 애플리케이션 리프레시는 최대 100%, Next.js 내부 컴파일은 최대 900%까지 빨라졌습니다. 단, Proxy와 Route Handlers는 아직 기존 방식으로 동작합니다.
  • Web Worker의 origin 처리가 개선되어 워커 내에서 fetch()나 importScripts()를 사용하는 WASM 라이브러리가 정상 동작합니다.
  • Subresource Integrity(SRI) 지원으로 nonce 기반 CSP 없이도 성능 저하 없는 스크립트 무결성 검증이 가능해졌습니다.
  • 구조 분해된 동적 import에도 tree shaking이 적용되며, import attributes를 통한 인라인 로더 설정, lightningCssFeatures를 통한 CSS 트랜스파일 세부 제어, ignoreIssue를 통한 로그 필터링 등 개발 편의 기능이 다수 추가되었습니다.
  • 200건 이상의 버그 수정과 내부 최적화로 안정성과 성능이 전반적으로 향상되었으며, 다음 릴리스는 컴파일러 속도와 메모리 사용량 개선에 초점을 맞출 예정입니다.

Turbopack이 기본 번들러로 자리 잡은 이후에도 웹팩과의 기능 격차를 좁히고 실사용 피드백을 반영하는 작업이 빠르게 진행되고 있다는 점에서, Turbopack을 사용 중이거나 전환을 고려 중인 팀이라면 이번 업데이트를 눈여겨볼 만합니다. 특히 대규모 서버 코드베이스를 다루는 프로젝트라면 Server Fast Refresh만으로도 체감 개발 속도가 크게 달라질 수 있습니다.

💡
Turbopack이 웹팩과의 기능 격차를 빠르게 좁히고 있어, 특히 대규모 서버 코드베이스를 다루는 팀은 Server Fast Refresh만으로도 개발 생산성에 큰 영향을 받을 수 있습니다.
