14:T480e,<p>Next.js 애플리케이션을 빌드하면 네트워크 탭에 이름조차 알아보기 힘든 JS 파일들이 잔뜩 나타납니다. 이 파일들이 바로 &quot;청크(chunk)&quot;인데, Turbopack이 여러분의 코드, 의존하는 패키지, 그리고 이를 엮어주는 런타임을 나눠 담아둔 결과물입니다. 이 글에서는 Turbopack이 어떤 기준으로 코드를 청크로 나누는지, 그리고 Next.js 16.3에서 추가된 청킹 개선 사항들을 살펴봅니다.</p>
<h3>청크란 무엇인가</h3>
<p>Next.js 페이지의 네트워크 탭을 열어보면 이런 식의 낯선 이름을 가진 JS 파일들을 볼 수 있습니다. 그중 하나를 열어 압축을 풀어보면 대략 이런 모습입니다.</p>

<p>이게 바로 청크입니다. Turbopack은 하나의 Next.js 앱을 위해 이런 청크를 수십 개 만들어내고, 그 안에는 여러분의 코드, 의존 패키지, 그리고 이를 연결하는 런타임이 들어갑니다.</p>
<p>&quot;청킹(chunking)&quot;이란 어떤 코드를 어떤 청크에 담을지 결정하는 과정입니다. 청킹에는 여러 방식이 있고 각각 트레이드오프가 다릅니다.</p>
<h3>세 가지 극단적인 청킹 전략</h3>
<p>가장 단순한 접근부터 살펴보겠습니다. 앱이 사용하는 모든 JavaScript를 하나의 청크에 담는 방식입니다.</p>
<p>355개 모듈 전부를 <code>app.js</code> 하나(1.09MB)에 담아 모든 페이지에서 로드하는 구조입니다. 이렇게 하면 모든 페이지가 같은 청크를 공유하므로 첫 로드 이후에는 항상 캐시 히트가 발생합니다. 네비게이션은 빠르겠죠.</p>
<p>하지만 트레이드오프도 바로 보입니다. JavaScript가 거의 필요 없는 페이지를 열어도 다른 모든 페이지의 JS까지 함께 내려받게 됩니다. 사이트가 커질수록 페이지 로드는 점점 무거워지고, 장기적으로는 지속 가능한 방식이 아닙니다.</p>
<p>그렇다면 페이지당 하나의 청크로 바꿔보면 어떨까요? 청크가 항상 슬림하게 유지되고 코드를 과도하게 내려받는 일도 없어질 겁니다.</p>
<p>같은 355개 모듈을 8개 청크(1.20MB)로 나누고, 페이지 간에 공유되는 코드는 필요한 청크마다 중복으로 포함시키는 방식입니다. 그런데 이번엔 캐싱을 잃게 됩니다. 모든 페이지가 <code>&lt;Footer /&gt;</code>를 쓴다면 그 코드가 모든 페이지 청크 안에 각각 들어가게 되고, 방문자가 네 개의 페이지를 열면 같은 푸터 코드를 네 번이나 내려받게 됩니다.</p>
<p>그러니 더 세밀한 단위가 필요합니다. 모듈 하나마다 청크를 하나씩 만들면 어떨까요? 그러면 아무것도 과도하게 내려받지 않고, 페이지 간에 공유되는 모듈도 딱 한 번만 다운로드됩니다.</p>
<p>모듈 하나에 청크 하나씩, 총 355개의 별도 청크(1.09MB)로 나누고 각각 한 번씩만 전송하는 구조입니다. 좋아 보이지만 문제가 하나 있습니다. 작은 JS 파일들에 대해 수백 건의 네트워크 요청이 발생한다는 점이죠. 요청 하나하나에는 오버헤드가 따르고, 수백 개가 쌓이면 사이트가 느려집니다. HTTP/2 덕분에 요청 비용이 줄긴 했지만 여전히 각 요청은 오버헤드를 수반합니다. gzip 같은 압축 알고리즘도 파일이 작고 많아지면 성능이 떨어지는데, 압축은 하나의 파일 내에서만 반복 패턴을 찾을 수 있기 때문입니다. 압축 딕셔너리가 도움이 되긴 하지만 이 문제를 완전히 해결하진 못합니다.</p>
<h3>요청 수냐, 코드 양이냐</h3>
<p>결국 남는 과제는 이렇습니다. 다운로드 크기는 최소로, 요청 수도 최소로 만들고 싶은데 이 두 목표는 서로 충돌합니다. 청크 수를 줄이고 크게 만들면 요청은 줄지만, 청크가 커질수록 페이지 간 재사용성은 떨어집니다.</p>
<p>Turbopack의 해법은 작은 청크들을 더 큰 청크로 병합하는 것입니다. 어려운 부분은 어떤 청크를 병합할지, 그리고 언제 병합하는 것이 실제로 이득인지를 판단하는 것입니다.</p>
<p>이를 위해 새로운 개념인 <strong>청크 그룹(chunk group)</strong>을 도입합니다. 청크 그룹은 함께 로드되는 청크들의 집합입니다. 예를 들어 <code>/home</code>에서 쓰이는 모든 청크는 하나의 청크 그룹에 속하고, <code>/blog</code>는 또 다른 그룹에 속합니다.</p>
<p><code>/home</code>용 그룹은 세 개의 청크를 로드하고, <code>/blog</code>용 그룹은 두 개의 청크를 로드합니다. 하나의 청크가 두 그룹 모두에 속할 수도 있는데, 이 경우 이웃 청크와 병합하려면 그 병합이 두 그룹 모두에서 안전해야 합니다.</p>
<p>청크 그룹은 과도한 다운로드 문제를 해결해줍니다. Turbopack은 같은 그룹 내의 청크끼리만 병합하는데, 어차피 같은 그룹의 청크들은 항상 함께 로드되므로 병합해도 페이지가 원래 받아야 할 것 이상을 추가로 받게 되는 일은 없습니다.</p>
<h3>병합이 언제 이득인지 계산하기</h3>
<p>그렇다면 요청 폭주 없이 캐시 히트율을 최적화하려면 어떻게 해야 할까요? 이를 알아보기 위해 두 가지 방문 패턴을 가정해봅니다. 하나는 페이지를 방문하고 바로 떠나는 경우, 다른 하나는 페이지를 방문한 뒤 다른 페이지로 이동하는 경우입니다. (같은 분석은 세 페이지 이상 이어지는 세션에도 자연스럽게 확장됩니다.)</p>
<p><code>&lt;Footer /&gt;</code>의 청크를 A, <code>&lt;VideoPlayer /&gt;</code>의 청크를 B라고 해봅시다. A는 모든 페이지에서 쓰이고, B는 홈페이지에서만 쓰입니다. 둘 다 홈페이지의 청크 그룹에 속하므로 병합 후보가 됩니다.</p>
<p>방문자가 홈페이지를 로드하고 바로 떠난다면, 병합은 항상 이득입니다. 어차피 둘 다 필요했던 청크이니 요청 두 번 대신 한 번으로 끝나기 때문입니다.</p>
<p>두 번째 페이지를 방문한다면 이야기가 달라집니다. 예를 들어 방문자가 홈페이지에서 약관 페이지로 이동한다고 해봅시다. 약관 페이지는 A만 필요하고 B는 필요 없습니다. A와 B가 하나의 파일로 합쳐져 있으므로 이 합쳐진 파일은 약관 페이지에서 쓸모가 없고, 결국 브라우저는 A를 따로 다시 내려받아야 합니다. 결과적으로 방문자는 A를 두 번 다운로드하게 됩니다.</p>
<p>병합이 두 페이지 방문 사이에서 이득을 보려면 두 페이지 모두 A와 B를 동시에 필요로 해야 합니다. 그래야 병합된 파일이 재사용되고 요청 하나를 절약할 수 있습니다.</p>
<p>가능한 모든 내비게이션 시나리오를 정리하면 다음과 같습니다. 각 행은 첫 페이지가 필요로 하는 것 → 두 번째 페이지가 필요로 하는 것을 나타내며, 숫자는 A와 B를 병합했을 때 세션 전체의 요청 수와 다운로드 코드양이 어떻게 바뀌는지를 보여줍니다.</p>
<div class="table-wrapper"><table><thead><tr><th>Navigation</th><th>Change in requests</th><th>Change in code downloaded</th></tr></thead><tbody><tr><td>A → A</td><td>0</td><td>0</td></tr><tr><td>A → B</td><td>0</td><td>0</td></tr><tr><td>B → B</td><td>0</td><td>0</td></tr><tr><td>A → A + B</td><td>0</td><td>+ A</td></tr><tr><td>B → A + B</td><td>0</td><td>+ B</td></tr><tr><td>A + B → A</td><td>0</td><td>+ A</td></tr><tr><td>A + B → B</td><td>0</td><td>+ B</td></tr><tr><td>A + B → A + B</td><td>−1</td><td>0</td></tr></tbody></table></div>
<p>A와 B의 병합을 고려할 때는 A만 쓰는 청크 그룹, B만 쓰는 청크 그룹, A+B를 함께 쓰는 청크 그룹이 각각 얼마나 많은지 계산하고, 각 시나리오의 발생 확률로 병합의 비용/이득을 가중치를 매깁니다.</p>
<p>마지막으로 한 페이지만 방문하는 경우와 두 페이지 이상 방문하는 경우의 확률도 가중치로 반영합니다. Turbopack은 세션의 2/3는 단일 페이지 방문, 1/3은 두 페이지 이상의 방문으로 추정합니다.</p>
<h3>세 가지 청킹 전략 실측 비교</h3>
<p>앞서 다룬 청킹 방식들을 실제로 비교해보겠습니다. nextjs.org를 병합 없음, Turbopack 기본값, 그룹 내 전체 병합이라는 세 가지 설정으로 각각 빌드한 뒤 동일한 순서로 페이지 이동을 수행하며 요청 수와 클라이언트 JS 다운로드량을 측정했습니다.</p>

<p>이 표에서 알 수 있듯 청킹은 결국 균형의 문제입니다. nextjs.org에서 Turbopack의 기본값은 병합 없음 대비 요청 수를 절반 이하로 줄이면서도 코드 다운로드량은 오히려 조금 더 적었습니다. 그룹당 하나의 청크로 최대 병합한 경우는 요청 수를 더 줄였지만 전체 코드량은 10% 더 늘었습니다. 다만 방문자가 페이지를 덜 이동했다면 최대 병합 쪽이 더 유리했을 것입니다. 그룹 내 모든 청크를 하나의 큰 청크로 합치는 방식은 첫 로드에서는 이득이지만 장기적으로는 비용이 큽니다.</p>
<h3>Next.js 16.3의 새로운 청킹 기능</h3>
<p>청킹의 효율을 제한하는 두 가지 요소가 있습니다. 첫째, 병합은 아무도 방문하기 전인 빌드 타임에 결정되기 때문에 브라우저가 실제로 무엇을 캐시하고 있는지에 반응할 수 없습니다. 둘째, 알고리즘은 사람들이 사이트를 어떻게 돌아다니는지를 추측해야 하는데, 이 때문에 단일 페이지 방문에 2/3라는 가중치를 부여하게 됩니다. 이번 여름 Turbopack 팀 인턴십을 하며 이 두 가지 문제와, 애초에 청크에 담기는 코드 양을 줄이는 작업을 함께 진행했습니다.</p>
<h4>더 똑똑한 청크 페칭</h4>
<p>앞서 본 표는 병합의 비용을 보여줬습니다. 방문자가 A가 담긴 페이지를 로드한 뒤 A+B가 필요한 페이지로 이동하면, 병합으로 인해 A를 두 번 내려받게 됩니다. 번들러는 빌드 타임에 브라우저가 이미 무엇을 갖고 있는지 알 수 없으니 이 문제를 피할 수 없습니다. 하지만 런타임은 알 수 있습니다.</p>
<p>Next.js 16.3 이상에서 <code>next.config.js</code>에 <code>experimental.turbopackChunking.generateComponentChunks</code>를 활성화하면, Turbopack이 병합된 청크와 함께 병합되지 않은 버전도 함께 생성합니다. 각 병합 청크를 구성하는 항목들과 그중 이미 로드된 항목들을 추적해서, 요청 시점에 더 저렴한 쪽(병합된 청크 전체, 또는 빠진 조각들만)을 선택할 수 있습니다.</p>
<p>반대의 경우도 마찬가지입니다. 방문자가 이미 병합된 A+B를 로드했다면, A를 단독으로 다시 로드하는 일을 건너뛸 수 있습니다.</p>
<p>이렇게 하면 소프트 내비게이션에서 불필요한 코드를 덜 로드하게 되고, 내비게이션 비용 없이 병합의 이점을 그대로 누릴 수 있습니다. <code>generateComponentChunks</code>를 켰을 때와 껐을 때를 비교한 데모 앱에서 그 차이를 직접 확인할 수 있습니다.</p>
<p>또한 방문자가 도착했을 때 무엇을 캐시하고 있는지 확인할 수 있는 <code>only-if-cached</code> 디렉티브도 실험 중입니다. 이 기능이 완성되면 사이트를 떠났다가 나중에 다시 방문하는 경우에도 동일한 개선 효과를 확장 적용할 수 있습니다.</p>
<h4>애널리틱스 기반 청킹</h4>
<p>Turbopack의 청킹 알고리즘은 사이트에 대해 여러 가정을 세웁니다. 예를 들어 2/3라는 가중치도 하나의 추정치일 뿐입니다. 많은 사이트에 두루 맞는 합리적인 기본값이긴 하지만, 특정 사이트에 딱 맞는 값은 아닐 수 있습니다. 사람들이 실제로 여러분의 사이트를 어떻게 돌아다니는지 알고 있다면, 이제 그 정보를 Turbopack에 알려줄 수 있습니다.</p>
<p><code>next.config.js</code>의 <code>experimental.turbopackChunking</code> 아래에 다음 옵션들을 설정할 수 있습니다.</p>
<ul>
<li><strong>firstPageLoadPriority</strong>: 단일 페이지 케이스와 두 페이지 케이스 사이의 가중치를 조정합니다. 0~1 사이의 값이 높을수록 내비게이션 비용을 감수하더라도 초기 로드 속도를 우선시합니다. 이탈률(bounce rate)을 참고 값으로 삼는 것도 합리적입니다. 기본값은 0.67입니다.</li>
<li><strong>priorityRoutes</strong>: 로드 속도가 가장 중요한 페이지 목록입니다. 이 라우트들에서는 더 적극적으로 청크를 병합합니다.</li>
<li><strong>clusters</strong>: 정규식 배열로 정의하는, 함께 자주 방문되는 라우트들의 그룹입니다. 클러스터 내부에서는 겹치는 청크를 더 적극적으로 병합합니다. 다만 클러스터 안에 A만 쓰는 페이지나 B만 쓰는 페이지가 A+B를 모두 쓰는 페이지와 섞여 있다면 병합을 덜 하게 됩니다.</li>
</ul>
<h4>더 작고 더 적은 청크</h4>
<p>지금까지는 코드를 어떻게 그룹핑할지에 관한 이야기였다면, 이번에는 애초에 내려보내는 코드 자체를 줄이는 기능들입니다.</p>
<ul>
<li><strong>CJS 모듈 트리쉐이킹</strong>: 그동안은 ESM에 대해서만 트리쉐이킹을 지원했기 때문에, CJS 모듈의 사용하지 않는 import/export까지 클라이언트로 전송되고 있었습니다. <code>experimental.turbopackCjsTreeShaking</code>으로 활성화할 수 있으며, 향후 Next.js 버전에서는 기본으로 켜질 예정입니다. 또한 분석 및 트리쉐이킹이 가능한 ESM 모듈의 범위도 확장했는데, 여기에는 동적 import 안의 배럴 파일(barrel file) 지원 개선도 포함됩니다.</li>
<li><strong>공유 Turbopack 런타임</strong>: 페이지별로 따로 있던 런타임 청크를 하나의 런타임 청크로 통합했습니다. <code>experimental.turbopackSharedRuntime</code>으로 활성화할 수 있으며, 첫 로드 이후의 모든 내비게이션에서 블로킹 요청 하나와 약 10KB의 클라이언트 JS를 절약합니다. 이 기능도 나중에 기본값으로 켜질 예정입니다.</li>
<li><strong>더 가벼운 기본 런타임</strong>: 이제 런타임은 기본적으로 WebAssembly와 Web Worker 관련 코드를 포함하지 않습니다. 해당 모듈을 실제로 사용하는 경우에만 이를 감지해 로딩 코드를 삽입합니다.</li>
</ul>
<h3>정리</h3>
<p>Turbopack의 청킹은 &quot;요청 수를 줄일 것인가, 코드 다운로드량을 줄일 것인가&quot;라는 근본적인 트레이드오프를 다룹니다. 모든 코드를 한 청크에 넣으면 캐시 효율은 최고지만 과도한 다운로드가 발생하고, 모듈마다 청크를 쪼개면 다운로드량은 최소가 되지만 요청 수가 폭증합니다. Turbopack은 &quot;청크 그룹&quot; 단위로 병합 범위를 제한하고, 방문 시나리오별 확률을 가중치로 반영해 병합 여부를 결정하는 방식으로 이 균형을 잡습니다.</p>
<p>실제로 nextjs.org에 세 가지 전략을 적용해 비교해본 결과, 기본 설정은 병합 없음 대비 요청 수를 절반 이하로 줄이면서 코드량도 소폭 줄였고, 그룹당 완전 병합은 요청 수는 더 줄였지만 코드량이 10% 늘었습니다. 즉 &quot;정답&quot;은 사이트의 방문 패턴에 따라 달라집니다.</p>
<p>Next.js 16.3부터는 이 문제를 더 정교하게 다룰 수 있는 실험적 옵션들이 추가되었습니다. <code>generateComponentChunks</code>는 브라우저 캐시 상태에 맞춰 병합 청크와 개별 청크 중 더 저렴한 쪽을 런타임에 선택하고, <code>firstPageLoadPriority</code>·<code>priorityRoutes</code>·<code>clusters</code>는 실제 사이트의 트래픽 패턴을 청킹 알고리즘에 반영할 수 있게 해줍니다. 여기에 CJS 트리쉐이킹, 공유 런타임, 경량 기본 런타임까지 더해지면서 애초에 내려보내는 코드 자체도 줄어들었습니다. 대규모 Next.js 서비스를 운영 중이라면 이런 실험적 플래그들을 켜보고 실제 네트워크 탭에서 요청 수와 전송량 변화를 직접 확인해볼 가치가 있습니다.</p>7:[["$","$L13",null,{"crumbs":[{"label":"Dev Digest","icon":"📬","href":"/"},{"label":"2026-09-22","icon":"📅","href":"/2026/09/22/"},{"label":"How Turbopack chunks your JavaScript"}]}],["$","div",null,{"className":"PageContainer_container__5iuf3","children":[["$","header",null,{"className":"ArticleDetailView_header__axaMu","children":[["$","h1",null,{"className":"ArticleDetailView_title__f_QTa","children":"How Turbopack chunks your JavaScript"}],null,["$","div",null,{"className":"ArticleDetailView_meta__ypIUL","children":[["$","span",null,{"children":["📅 ","2026-09-22"]}],["$","span",null,{"children":["📰 ","Next.js Blog"]}],null]}],["$","div",null,{"className":"ArticleDetailView_badges__G8q4T","children":[["$","span","frontend",{"className":"LabelBadge_badge__ZAfPv LabelBadge_frontend__x8P2I","children":"frontend"}],["$","span","typescript",{"className":"LabelBadge_badge__ZAfPv LabelBadge_typescript__V93Gv","children":"typescript"}]]}]]}],[["$","section",null,{"className":"ArticleDetailView_section__DaSgJ","children":["$","div",null,{"className":"ArticleDetailView_translated__8ZNqk","dangerouslySetInnerHTML":{"__html":"$14"}}]}],null],"$L15"]}]]
