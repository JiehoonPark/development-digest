15:T443b,<h2>AI 코딩 시대, CI가 병목이 되다: Linear의 CI 재설계기</h2>
<p>Linear의 CTO Tuomas는 올해 초 &quot;CI 비용이 너무 높다&quot;는 제목의 이슈를 팀원 Mufeez Amjad에게 배정했습니다. 함께 요청한 것은 CI 속도 개선까지. AI 에이전트 덕분에 코드를 작성하는 속도는 기하급수적으로 빨라졌지만, 그 변경 사항을 검증하는 CI는 같은 속도로 따라가지 못했습니다. 모든 PR은 여전히 CI를 통과해야 하기 때문에, 개발 속도가 빨라질수록 CI는 병목이 되어 인프라 비용을 끌어올리고 개발자와 에이전트 모두를 기다리게 만들었습니다.</p>
<p>Linear 팀은 PR이 CI에서 대기하는 시간과 러너가 소비하는 시간, 이 두 가지를 최적화 목표로 삼았습니다. 그 결과 연초 대비 테스트 스위트 규모가 거의 4배로 늘었음에도, PR 대기 시간을 6분 이상에서 5분 초반으로 줄이고 테스트당 러너 시간은 절반 가까이 절감했습니다. 이 글에서는 그 과정에서 적용한 네 가지 축의 최적화—인프라·툴링 업그레이드, 다른 작업을 막는 게이트 작업 최적화, 반복 셋업 제거, 테스트 실행 효율화—를 구체적으로 다룹니다. Linear의 코드베이스는 주로 TypeScript지만, 소개하는 기법 상당수는 언어나 툴체인에 관계없이 적용 가능합니다.</p>
<h3>인프라와 툴링 업그레이드</h3>
<p>가장 초기에 거둔 성과들은 CI 자체를 손대지 않고도 얻을 수 있었습니다. GitHub Actions에서 서드파티 러너로 워크로드를 이전한 것인데요, 더 빠른 CPU, 고성능 스토리지, 개선된 캐시 인프라를 갖춘 머신으로 동일한 파이프라인을 돌리는 것만으로도 전환 전후 이틀을 비교했을 때 작업이 평균 34% 빨라졌고, tsc 같은 일부 워크로드는 52%나 단축됐습니다.</p>
<p>툴체인 현대화도 별도로 큰 효과를 냈습니다. 네이티브 TypeScript 컴파일러인 tsgo로 전환하면서 tsc 체크의 주간 중앙값이 73% 줄어들었고, 이는 타입체킹 자체가 병목에서 완전히 벗어날 만큼 큰 폭이었습니다.</p>
<h4>타입 체커 없이 린트하기</h4>
<p>린트 역시 초기 최적화 대상이었습니다. Linear의 커스텀 린트 규칙 일부는 제약을 강제하거나 자동수정(autofix)을 적용하기 위해 TypeScript 타입 정보에 의존하고 있었는데요, 이 때문에 매 린트 실행마다 규칙을 평가하기 전에 전체 타입 그래프를 먼저 빌드해야 했고, 결국 린트가 CI에서 가장 메모리를 많이 잡아먹는 작업 중 하나가 됐습니다.</p>
<p>이 규칙들을 타입 정보 없이 추상 구문 트리(AST)에 대한 정적 분석만으로 재작성해, 함수형 구조나 가드 패턴을 타입 정보 없이 식별하도록 바꿨습니다. 그 결과 ESLint가 TypeScript를 완전히 배제할 수 있게 됐고, API 린트 시간이 68%, 전체 레포지토리 린트 시간이 55% 줄었습니다. 메모리 사용량도 크게 감소했습니다.</p>
<p>타입 정보 의존성을 제거한 덕분에 이후 Oxlint로의 전환도 훨씬 수월해졌습니다. 순수하게 구문만으로 동작하는 규칙은 이식이 간단하기 때문인데요, Oxlint 자체도 린트에 소요되는 CI 러너 시간을 줄여줬습니다.</p>
<h3>다른 작업을 막는 게이트 작업 최적화</h3>
<p>기반 인프라와 개별 체크가 빨라진 뒤에는, CI를 하나의 시스템으로 놓고 전체를 살펴봤습니다. 그러자 다른 모든 작업 앞에 놓인 작은 작업들이 눈에 들어왔습니다. 모든 실행은 PR이 어떤 경로를 건드렸는지, 그리고 동일한 입력에 대해 이미 테스트가 통과했는지 확인하는 것으로 시작됩니다. 이런 체크는 잡(job) 레벨에서 게이팅하기 때문에 스킵된 작업은 러너를 점유하지 않지만, 동시에 이 체크들이 크리티컬 패스(critical path)에 직접 놓이게 됩니다. 8개의 API 테스트 샤드 중 어느 것도 이 체크가 끝나기 전에는 시작할 수 없어서, 작은 지연도 불균형하게 큰 영향을 미쳤습니다.</p>
<h4>각 작업에 필요한 것만 fetch하기</h4>
<p>여러 워크플로우는 다음에 무엇을 실행할지 결정하는 변경 감지(change-detection) 작업으로 시작합니다. 예를 들어 diff에 데이터베이스 마이그레이션이 포함되어 있는지 확인하고, 관련 데이터베이스 CI 체크를 스케줄링하는 신호를 출력하는 식입니다. 그런데 이 작업들은 실제로는 전체 워킹 트리 중 일부만 필요한데도 전체를 체크아웃하고 있었습니다.</p>
<p>fetch depth를 제한한 결과, 가장 느렸던 게이트가 94초에서 20초로 줄었고, 워킹 트리가 아예 필요 없는 작업에서는 체크아웃 자체를 제거해 27초에서 7초로 단축했습니다. 경로 diff가 필요한 커밋 푸시와 머지 큐 이벤트에서는 이력이 제한된 sparse·blobless 체크아웃만으로 충분하다는 것을 확인해 11초가량을 추가로 절약했습니다.</p>
<p>변경 감지 작업의 중앙값 소요 시간은 26초에서 8초로, p90은 31초에서 12초로, 가장 느린 실행은 138초에서 37초로 떨어졌습니다.</p>
<h4>체크아웃을 더 견고하게 만들기</h4>
<p>러너 인프라를 교체한 뒤, actions/checkout을 사용하는 작업들의 체크아웃 시간이 길어지고 간헐적으로 멈추는 현상이 나타났습니다. 서드파티 러너는 GitHub 네트워크 바깥에 위치하기 때문에 GitHub에 접근하려면 직접 IP 연결에 의존해야 하는데, 제공업체 조사 결과 이 연결에서 간헐적인 성능 저하가 원인으로 밝혀졌습니다. 여러 워크플로우가 체크아웃으로 시작하기 때문에, fetch 하나가 멈추면 전체 CI 실행이 지연될 수 있었습니다.</p>
<p>이런 네트워크 불안정성에 대응하기 위해 actions/checkout을 자체 컴포지트 액션으로 교체했습니다. 이 액션은 백오프를 적용해 재시도하고, GIT_HTTP_LOW_SPEED_LIMIT과 GIT_HTTP_LOW_SPEED_TIME을 설정해 연결이 정체되면 무한정 멈추는 대신 약 30초 후 중단되도록 했으며, sticky disk 위에 영구적인 git 미러를 유지하는 체크아웃 캐시도 활용했습니다. 그 결과 크리티컬 패스 작업이 체크아웃 완료를 기다리며 유휴 상태로 남는 경우가 크게 줄었습니다.</p>
<h4>크리티컬 패스 최소화하기</h4>
<p>크리티컬 패스에 있을 필요가 없는 작업들도 있었습니다. 캐시 마커를 머지 전 마지막 체크의 일부로 기록하고 있었는데, 이 때문에 테스트가 이미 통과했음에도 PR이 머지 큐에서 대기해야 하는 상황이 발생했습니다. 이 쓰기 작업을 테스트 샤드가 끝난 뒤 실행되지만 아무것도 게이팅하지 않는 별도 작업으로 옮겨서, API PR과 머지 큐 진입 건마다 머지 경로에서 42초를 단축했습니다.</p>
<p>이 변경들을 종합하면 캐시 미스 상황에서 API PR의 필수 체크 시간을 약 1분 단축하는 동시에 러너 시작 횟수도 줄였습니다.</p>
<h3>반복 셋업 줄이기</h3>
<p>다음으로는 모든 작업에서 반복되는 셋업 비용, 즉 러너 부팅, 패키지 설치, 빌드 의존성 프로비저닝 등에 주목했습니다. 이런 오버헤드 때문에 실제로는 몇 초짜리 작업인데도 전체 인프라 시간은 몇 분씩 소비하는 경우가 많았습니다. 이를 해결하기 위해 취한 조치들은 다음과 같습니다.</p>
<h4>CI 이미지에 공유 의존성 미리 설치하기</h4>
<p>API 테스트 샤드는 매 실행마다 동일한 Postgres 클라이언트를 apt로 설치하는 데 7~8초씩 소요했습니다. 이를 Node와 클라이언트를 포함한 작은 CI 베이스 이미지로 옮겨서, 각 샤드가 곧바로 실행 가능한 환경에서 시작할 수 있도록 했습니다. 이후 셋업 중 필요한 네이티브 빌드 헤더를 다운로드하는 과정이 간헐적으로 멈추는 것을 발견해, 이 헤더들도 이미지에 미리 포함시켜 테일 레이턴시를 줄였습니다.</p>
<h4>각 작업에 필요한 의존성만 설치하기</h4>
<p>Linear의 코드베이스는 pnpm 워크스페이스로 관리되는 모놀리포입니다. API 테스트 워크플로우는 실제로는 API 패키지와 그 의존성만 필요했음에도 전체 워크스페이스를 설치하고 있었습니다. 설치 범위를 API 패키지로 제한하자 pnpm install 시간이 44~73초에서 16~18초로 줄었습니다. 동일한 패턴을 API 인접 작업들에도 적용했는데, 이 작업들 역시 전체 레포지토리를 설치하고, 이후 실행에서 거의 히트하지 않는 의존성 캐시를 업로드하고 있었습니다.</p>
<h4>재빌드가 더 빠를 때는 캐시하지 않기</h4>
<p>node_modules 캐싱도 테스트해봤지만 재빌드하는 편이 더 빨랐습니다. 캐시 키가 자주 바뀌는 lockfile에 의존하고 있어서, 캐시 히트가 나더라도 복원에 약 28초가 걸린 반면 필터링된 설치는 약 7.5초에 불과했습니다. 캐시는 뚜렷한 이점 없이 저장 시간과 변동성만 늘리고 있었던 셈입니다.</p>
<p>이 세 가지 변경으로 샤드당 셋업 시간이 110~140초에서 67~73초로, 약 44% 줄었습니다.</p>
<p>이 외에도 완전히 피할 수 있는 다른 형태의 반복 셋업들이 있었습니다.</p>
<h4>변하지 않은 셋업 재실행 피하기</h4>
<p>일부 셋업 작업은 입력이 바뀔 때만 반복될 필요가 있습니다. 예를 들어 API 컨테이너는 PR이 스키마를 변경하지 않았을 때조차 매 실행마다 전체 데이터베이스 마이그레이션 이력을 재생하고 있었습니다. 이런 경우 생성된 스키마 스냅샷과 부트스트랩 파일을 로드하는 방식으로 전환해, 컨테이너당 데이터베이스 셋업 시간을 약 12초에서 1~2초로 줄였습니다.</p>
<h4>짧은 체크들을 더 적은 작업으로 묶기</h4>
<p>7개의 독립적인 체크가 각각 러너를 띄우고 레포지토리를 체크아웃하고 의존성을 설치한 뒤 겨우 몇 초짜리 유효 작업을 수행하고 있었습니다. 이들을 2개의 작업으로 통합하고 그 안에서 7개 태스크를 동시에 실행하도록 바꿔서, 동일한 셋업 오버헤드를 지불하는 횟수를 7번에서 2번으로 줄였습니다. 6월 사용량 기준으로 이 변경 하나로 월 약 87,000 러너-분을 절약했는데, 이는 전체 CI 사용량의 11.8%에 해당합니다.</p>
<h3>테스트 실행 효율화</h3>
<p>테스트 샤드의 고정 비용이 줄어든 덕분에 API 스위트를 훨씬 더 공격적으로 병렬화할 여유가 생겼습니다. API 스위트는 워크플로우에서 가장 크고 가장 자주 실행되는 부분 중 하나였기 때문에, 여기서의 개선은 머지 시간에 미치는 영향이 특히 컸습니다.</p>
<h4>테스트 러너 관점에서 작업 균형 맞추기</h4>
<p>Linear가 TypeScript 테스트 스위트에 사용하는 테스트 러너 Vitest는 개별 테스트의 실행 시간이 아니라 파일 단위로 작업을 분배합니다. 이는 유난히 큰 테스트 파일 몇 개가 하나의 샤드를 독점해, 다른 샤드들이 훨씬 일찍 끝났음에도 전체 스위트의 완료를 지연시킬 수 있다는 뜻이었습니다.</p>
<p>테스트 구조는 그대로 유지하면서 이런 큰 파일들을 더 작고 집중된 파일들로 분할한 뒤, 다양한 샤드·러너 구성을 평가했습니다. 연초에 이미 샤드를 3개에서 4개로 늘렸었는데, 이번에 8개로 늘리자 초기 벤치마크에서 크리티컬 작업이 약 19% 빨라지고 비용도 19% 줄었습니다. 변경 일주일 후, 가장 느린 샤드의 소요 시간은 5.25분에서 4.33분으로 줄었습니다.</p>
<h4>엄격한 격리 규칙 하에 모듈 상태 공유하기</h4>
<p>Vitest는 기본적으로 모든 테스트 파일을 격리하는데, Linear의 경우 이는 각 테스트 샤드마다 엔티티, GraphQL, 데코레이터 그래프를 매번 다시 빌드해야 한다는 의미였습니다. 이를 해결하기 위해 <code>isolate: false</code>를 적용한 옵트인(opt-in) vitest 프로젝트를 도입해, 안전하다고 판단된 파일들이 워커 내에서 모듈 레지스트리를 공유할 수 있도록 했습니다.</p>
<p>이것이 단일 최적화로는 가장 큰 성과였습니다. Linear의 사용 규모에서 월간 약 17%의 비용 절감 효과를 냈는데요, 가장 느린 샤드가 약 300~379초에서 약 195초로 줄었고, 전체 API 샤드 러너 시간은 실행당 약 32.8분에서 22분으로 감소했습니다.</p>
<p>동시에 이는 정확성 리스크가 가장 큰 최적화이기도 했습니다. 모든 파일에 옵트인 코멘트를 명시적으로 달아 적용 대상을 표시하고, 필요한 티어다운(teardown) 로직도 추가했습니다. 페이크 타이머를 쓰거나 상태 공유 방식이 안전하게 정리되지 않는 소수의 파일은 격리된 프로젝트에 그대로 남겨뒀습니다. 그리고 현재 대부분의 테스트를 에이전트가 작성하고 있는 만큼, 에이전트 스킬 설정도 이 성능 옵트인을 반영하도록 업데이트해 생성되는 테스트들이 기본적으로 동일한 제약을 따르도록 했습니다.</p>
<h4>샤딩은 셋업 오버헤드에 의해 제한된다</h4>
<p>추가 샤딩은 샤드당 고정 비용이 낮을 때만 이득을 봅니다. 샤드 수를 두 배로 늘리면 셋업에 소요되는 워크플로우 시간도 두 배로 늘어나기 때문입니다. 앞서 소개한 셋업 최적화들이 있었기에 8개 샤드가 실질적으로 가능해졌습니다. 샤드당 110~140초였던 예전 셋업 시간 기준이라면, 8개 샤드는 셋업에만 15~19분을 썼을 것이고, 이는 테스트 자체보다 더 긴 시간입니다. 현재는 셋업이 약 40초 수준이라서, 8개 샤드가 이전 4개 샤드보다 총 셋업 시간이 더 적으면서도 테스트는 두 배 더 병렬화됩니다.</p>
<p>셋업 최적화 이전에는 4개 샤드로 8.3분의 셋업 시간을 썼지만, 최적화 이후에는 8개 샤드로 7.5분의 셋업 시간만 소요됩니다.</p>
<h3>시스템 전체에 걸쳐 누적되는 개선</h3>
<p>만약 올해 초 CI 개선에 의식적으로 나서지 않았다면, 오늘날 테스트 스위트는 약 11분이 걸렸을 것입니다. 이는 현재 개발자들이 기다리는 시간의 거의 두 배에 해당합니다. 그리고 이 작업은 여기서 끝나지 않습니다. Linear의 코드베이스는 계속 성장하고 있고, 현재 매주 약 2,000개의 테스트가 추가되고 있습니다. 이런 속도 속에서 CI를 계속 빠르게 유지하는 것은 앞으로도 지속적인 과제로 남을 것입니다.</p>
<h3>정리</h3>
<p>Linear의 CI 개선 사례는 &quot;AI 코딩 시대에는 코드 작성 속도가 아니라 검증 속도가 병목이 된다&quot;는 점을 잘 보여줍니다. 핵심은 크게 네 가지입니다.</p>
<ul>
<li><strong>인프라·툴링</strong>: 서드파티 러너로 전환해 작업 속도를 평균 34% 높이고, tsgo 도입으로 타입체크 시간을 73% 단축했습니다. 타입 정보 의존 없이 AST 기반으로 린트 규칙을 재작성해 린트 시간을 55%(전체 레포 기준) 줄였습니다.</li>
<li><strong>크리티컬 패스 관리</strong>: fetch depth 제한과 sparse checkout으로 변경 감지 작업의 중앙값을 26초에서 8초로, 네트워크 불안정에 대비한 재시도·타임아웃 로직으로 체크아웃 지연을 줄였습니다. 게이팅에 불필요한 작업은 크리티컬 패스 밖으로 빼냈습니다.</li>
<li><strong>반복 셋업 제거</strong>: 공유 의존성을 CI 베이스 이미지에 미리 설치하고, 모노리포에서 필요한 패키지만 설치하며, 캐시가 오히려 느릴 때는 과감히 걷어냈습니다. 짧은 체크 7개를 2개 작업으로 통합해 월 87,000 러너-분(전체 CI 사용량의 11.8%)을 절약했습니다.</li>
<li><strong>테스트 실행 효율화</strong>: 큰 테스트 파일을 분할하고 샤드를 4개에서 8개로 늘려 19% 속도·비용 개선을 이뤘고, <code>isolate: false</code> 옵트인으로 모듈 상태를 공유해 월 17% 비용 절감이라는 가장 큰 성과를 냈습니다. 단, 이는 정확성 리스크가 가장 큰 최적화였기에 명시적 옵트인과 테어다운 규칙으로 안전장치를 마련했습니다.</li>
</ul>
