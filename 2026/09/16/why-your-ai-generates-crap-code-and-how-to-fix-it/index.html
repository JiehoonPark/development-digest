왜 당신의 AI는 형편없는 코드를 만들어낼까 - agents.md 제대로 설정하는 법

수많은 시간을 들여 agents.md 파일을 수정하고, 각종 skill을 다운받고, 문서를 다듬어봐도 AI는 여전히 똑같은 실수를 반복합니다. 이 글에서는 OpenAI, Microsoft 같은 대기업들조차 agents.md 파일에서 저지르고 있는 흔한 실수를 짚어보고, AI가 실제로 어떤 정보를 받아서 코드를 작성하는지, 그리고 어떻게 하면 이 설정 파일들을 효율적으로 구성할 수 있는지 실제 프로젝트 예시와 함께 살펴보겠습니다.

AI에게 전달되는 정보의 구조부터 이해하기

AI 코딩 에이전트를 설정하기 전에 먼저 알아야 할 것은, 우리가 프롬프트를 보낼 때 실제로는 훨씬 더 많은 정보가 함께 전송된다는 사실입니다. 프롬프트를 보내는 순간 다음과 같은 요소들이 조합되어 AI에게 전달됩니다.

  • 시스템 프롬프트: AI가 어떻게 동작해야 하는지 규정하는 부분으로, Claude Code나 Pi 같은 도구들이 자체적으로 작성합니다. Pi처럼 일부는 사용자가 수정할 수 있지만 대부분은 건드릴 수 없고, 신경 쓸 필요도 크게 없습니다.
  • agents.md 파일: 프로젝트 루트에 위치하는 파일로, 가장 익숙한 설정 파일일 겁니다. 요청을 보낼 때마다 이 파일의 내용 전체가 함께 전송됩니다. Claude Code를 쓴다면 claude.md라는 이름을 강제로 써야 하는데, 사실상 agents.md, claude.md, gemini.md 모두 같은 역할을 하는 동일한 개념의 파일입니다.
  • skill 파일: 특정 작업이 필요할 때 AI가 읽어들이는 마크다운 파일 묶음입니다. 예를 들어 TypeScript 관련 작업을 할 때만 해당 skill 파일의 내용을 불러와 프롬프트에 포함시킵니다.
  • 문서와 코드베이스: 애플리케이션 내 각종 문서와 코드 자체도 필요에 따라 프롬프트에 함께 실려갑니다.

즉, 매 요청마다 원래 작성한 프롬프트 + 시스템 프롬프트 + agents.md 전체 + 필요 시 로드되는 skill 파일들이 하나로 합쳐져 AI에게 전달되는 구조입니다. 이 중 가장 신경 써서 관리해야 할 것이 바로 agents.md입니다. 매 요청마다 통째로 전송되기 때문에, 여기에 문제가 있으면 어떤 프롬프트를 작성하든 그 요청 전체가 오염됩니다.

대기업들도 못 피한 함정: 비대해지는 agents.md

Codex, Airflow, VS Code의 agents.md 파일을 살펴보면 공통적으로 심각한 문제가 하나 보입니다. 바로 파일이 지나치게 비대하다는 점입니다.

Codex 사례를 보면 온갖 정보가 뒤죽박죽 나열되어 있습니다. 아마도 처음엔 작은 agents.md로 시작했다가, 문제가 하나씩 발생할 때마다("아, PR 이름에 접두사가 안 붙었네" 같은 식으로) 새로운 항목을 계속 리스트에 추가해온 것으로 보입니다. 처음에는 좋은 방법처럼 보이지만, 문제를 겪을 때마다 항목을 추가하다 보면 결국 거대한 불릿 리스트가 만들어지고, 이게 매 요청마다 그대로 전송됩니다. 실제로 살펴보면:

  • codex core crate 관련 내용
  • 코드 리뷰 관련 내용 (모든 요청이 코드 리뷰를 하는 게 아닌데도 포함됨)
  • API breaking change 관련 내용
  • 터미널 UI 스타일 컨벤션
  • 코드 컨벤션
  • 스타일 관련 내용이 다른 섹션에서 한 번 더 중복 등장
  • 테스트 관련 내용(스냅샷 테스트 등)

즉, 스타일링 작업을 안 할 때도 스타일 관련 내용이, 테스트를 안 할 때도 테스트 관련 내용이 매번 함께 전송되면서 토큰만 낭비하고 AI의 실제 연산 자원을 갉아먹고 있는 것입니다.

다만 Codex가 한 가지는 잘하고 있는 부분이 있는데, 터미널 UI 스타일 컨벤션 섹션에서 외부 문서로 링크를 걸어두었다는 점입니다. 즉 "스타일 컨벤션은 여기 외부 문서에 있다"라고만 명시하고, 실제 상세 내용은 별도 파일에 분리해둔 것이죠. 이렇게 하면 agents.md 자체는 작게 유지하면서도, 스타일링 작업이 필요할 때만 에이전트가 해당 파일을 열어서 필요한 컨텍스트를 가져올 수 있습니다.

Airflow 사례는 더 심각합니다. 537줄에 달하는 이 파일을 토크나이저에 돌려보니 무려 8,600토큰이나 차지했습니다. 요즘 에이전트들이 수백만 토큰의 컨텍스트 윈도우를 갖고 있다고는 하지만, 실제로 작업해보면 10만~20만 토큰만 넘어가도 출력 품질이 급격히 떨어지는 걸 다들 경험했을 겁니다. 만약 실질적으로 활용 가능한 컨텍스트가 10만 토큰 수준이라면, agents.md 하나가 전체 컨텍스트의 거의 10%를 잡아먹는 셈이고, 이는 도움이 되기는커녕 에이전트의 성능을 오히려 갉아먹습니다.

VS Code 사례는 얼핏 보면 파일 자체가 작아서 괜찮아 보이지만, 실상은 다른 거대한 파일 하나로 링크만 걸어둔 구조입니다. 그 링크된 파일 역시 정보가 과도하게 쌓여있고 외부 링크도 없이 모든 게 뭉쳐있어서, 결국 앞선 사례들과 똑같은 문제를 안고 있습니다.

실전 적용: agents.md를 어떻게 슬림하게 만들 것인가

실제 예제 애플리케이션(백엔드와 프론트엔드를 모두 가진 풀스택 프로젝트)을 가지고 이 문제를 어떻게 해결하는지 보여드리겠습니다. 이 프로젝트의 agents.md는 다른 대기업 사례들만큼 크지는 않지만, 여전히 테스트, 웹 관련 컨벤션, API 컨벤션, CSS, React, TypeScript 등 온갖 정보를 한 파일에 다 담고 있어서 부담스러운 수준입니다. 하지만 모든 요청이 TypeScript나 테스트, CSS, 백엔드 작업을 다루는 게 아니기 때문에, 이 모든 내용을 매번 통째로 보낼 필요가 없습니다.

해결 방법은 간단합니다. agents.md 안에서 특정 작업 영역에 대한 섹션이 만들어지고 있다는 걸 발견하면, 그 내용을 별도의 문서 파일로 분리하는 것입니다.

예를 들어 CSS 관련 섹션이 있다면:

  • documentation 폴더 같은 곳에 css-conventions.md 같은 마크다운 파일을 새로 만듭니다.
  • agents.md에 있던 CSS 관련 내용을 통째로 잘라서 이 새 파일에 붙여넣습니다.
  • agents.md에는 그 내용을 삭제하고 대신 "상세 스타일링 컨벤션은 [해당 경로]를 참고" 같은 형태로 파일 경로에 대한 참조만 남겨둡니다.

이 작업을 API 컨벤션, React, TypeScript, 저장소 구조(repository layout) 등 모든 섹션에 대해 동일하게 반복합니다. 즉, agents.md 안의 내용을 실제 내용 대신 "필요한 정보가 있는 위치에 대한 참조"로 압축하는 것입니다. 이렇게만 해도 agents.md의 크기는 크게 줄어들고, 에이전트는 실제로 필요한 순간에만 해당 문서를 열어서 참고하게 됩니다.

또 하나 거의 모든 agents.md에서 공통적으로 발견되는 것이 "시작하기(getting started)" 혹은 "설정(setup)" 섹션인데, 프로젝트를 처음 실행하고 의존성을 설치하는 방법 등을 담고 있습니다. 이런 내용 역시 매 요청마다 필요한 정보가 아니기 때문에, agents.md에 그대로 둘 필요가 없고 별도 문서로 분리해 참조하는 방식이 적절합니다.

정리

  • 프롬프트를 보낼 때 AI는 여러분이 입력한 텍스트만 받는 게 아니라 시스템 프롬프트, agents.md(= claude.md, gemini.md), 필요 시 로드되는 skill 파일들이 함께 결합된 컨텍스트를 받습니다.
  • 이 중 agents.md는 모든 요청에 예외 없이 전체가 포함되기 때문에 가장 중요하게 관리해야 할 파일입니다. 여기가 비대하거나 지저분하면 모든 요청의 품질이 함께 나빠집니다.
  • Codex, Airflow, VS Code의 agents.md는 문제가 생길 때마다 항목을 계속 추가해온 방식으로 비대해졌고, 그 결과 코드 리뷰·테스트·스타일링처럼 매번 필요하지도 않은 정보까지 항상 함께 전송되며 토큰과 성능을 낭비하고 있습니다. Airflow의 경우 agents.md 하나가 8,600토큰을 차지했습니다.
  • 해결책은 agents.md를 최대한 슬림하게 유지하고, CSS·API·React·TypeScript·설정 방법 등 특정 영역별 상세 내용은 별도의 문서 파일로 분리한 뒤 agents.md에는 해당 파일에 대한 참조(링크/경로)만 남기는 것입니다.
  • 이렇게 하면 에이전트는 평소엔 작은 agents.md만 받고, 실제로 해당 작업(예: 스타일링)이 필요할 때만 관련 문서를 추가로 읽어들여 컨텍스트를 확장할 수 있습니다.
  • 실무에서는 지금 사용 중인 agents.md를 열어 "이 섹션이 모든 요청에 정말 필요한가?"를 자문해보고, 특정 작업에만 해당하는 내용이라면 즉시 별도 문서로 분리하는 리팩토링부터 시작하는 것이 좋습니다.
💡
agents.md 설정 방식은 AI 코딩 어시스턴트의 출력 품질과 토큰 효율에 직접적인 영향을 미치므로, 프론트엔드 개발자가 AI 도구를 팀 단위로 도입할 때 반드시 점검해야 할 실무 포인트입니다.
