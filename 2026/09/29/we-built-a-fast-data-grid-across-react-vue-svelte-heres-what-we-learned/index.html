We built a fast data grid across React, Vue & Svelte – here's what we learned

📅 2026-09-29📰 Echo JS
frontend

SVAR는 데이터 그리드, 간트 차트, 캘린더처럼 기능이 많고 복잡한 UI 컴포넌트를 만드는 팀입니다. 이런 컴포넌트들의 공통점은 하나, 바로 성능입니다. 데이터가 아무리 커져도 빠르고 반응성 있게 동작해야 하죠. 그런데 SVAR는 같은 컴포넌트를 React, Svelte, Vue 세 가지 프레임워크로 동시에 출시합니다. 보통의 프레임워크 비교 글은 한 프레임워크는 깊이 알고 나머지 둘은 문서만 훑어본 사람이 쓰는 경우가 많은데, SVAR는 세 프레임워크 모두에서 실제로 고성능 컴포넌트를 만들어야 했습니다. 조금 무모하지만, 그만큼 얻은 인사이트도 많았다고 합니다. 이 글에서는 SVAR가 데이터 그리드를 세 프레임워크에서 어떻게 빠르게 만들었는지, 그 과정에서 무엇을 배웠는지를 정리합니다.

결론부터 말하면 다소 의외입니다. 빠른 데이터 그리드를 만드는 데 드는 비용의 대부분은 프레임워크와 거의 무관했고, 프레임워크마다 진짜로 다른 지점은 흔히 벌어지는 "프레임워크 전쟁"이 주장하는 것보다 훨씬 좁았습니다. 그래서 이 글은 의도적으로 승자를 가리지 않습니다.

프레임워크와 무관한 성능 문제

데이터 그리드는 이런 비교에 아주 좋은 테스트 케이스입니다. 누구나 한 번쯤 만들어보거나 써봤을 만큼 익숙하면서도, 구조적으로는 단순한 편이라 게으른 엔지니어링을 가장 빨리 응징하는 컴포넌트이기도 합니다. 게다가 다른 컴포넌트와 달리 데이터 양이 매우 큽니다. 1,000행은 평범한 화요일 수준이고, 10,000행도 드문 일이 아니니 미리 대비해야 합니다.

실제로 SVAR React DataGrid가 20만 행, 2만 열을 렌더링하는 데모를 보면 어지러울 정도의 숫자인데도 그리드는 부드럽게 처리합니다.

10,000행을 그냥 직접 렌더링하면 어느 프레임워크든 똑같이 죽어버립니다(요즘 하드웨어가 워낙 빠르니 "죽는다"기보다는 "심하게 느려진다"는 표현이 더 맞을 수도 있습니다). React, Vue, Svelte 모두 결국 브라우저에게 수십만 개의 DOM 노드를 만들고 레이아웃을 잡으라고 요청하게 되고, 병목은 브라우저 자체가 됩니다. 이 지점에서 프레임워크의 차이는 거의 의미가 없어집니다. 이 실패는 비용의 위계를 보여줍니다.

  • HTML을 만드는 작업이 어떤 프레임워크에서든 가장 느립니다.
  • JavaScript 연산은 값싸지만, 컴포넌트 규모가 커지면 더 이상 공짜가 아닙니다.
  • 프레임워크 오버헤드(가상 DOM 대 컴파일된 DOM 연산)는 앞의 두 가지에 비하면 오차 범위 수준입니다.

이 순서를 이해하고 나면 아래에서 소개할 구체적인 기법 대부분이 자연스럽게 납득됩니다.

SVAR 데이터 그리드의 공통 아키텍처

이제 SVAR가 데이터 그리드를 React, Vue, Svelte 각각에서 "프레임워크 네이티브"처럼 느껴지도록 어떻게 설계했는지 살펴보겠습니다.

엔진과 통합 레이어

프레임워크 독립성은 설계할 만한 가치가 있습니다. SVAR 그리드는 프레임워크에 종속되지 않는 코어(데이터 구조, 설정 정규화, 레이아웃 계산 등)와 프레임워크별로 얇게 붙는 통합 레이어로 나뉩니다.

무거운 작업은 전부 코어에서 일어납니다. 통합 레이어는 코어의 상태를 각 프레임워크의 반응형 primitive로 변환하는 역할만 합니다. 이렇게 분리했기 때문에 React, Vue, Svelte 버전을 동시에 유지보수하는 일이 현실적으로 가능해집니다.

굳이 세 프레임워크로 배포할 필요가 없더라도 이 아이디어는 유효합니다. React 앱 하나만 만들더라도, 무거운 로직을 컴포넌트 밖에 두면 테스트하기 쉽고 프로파일링하기 쉬우며 렌더 사이클에서 발생하는 사고에서도 자유로워집니다.

가상화는 선택이 아니라 기본값이다

전체 데이터를 다 렌더링하는 건 애초에 선택지가 아니므로, SVAR의 다른 컴포넌트들과 마찬가지로 그리드는 렌더링 가상화(virtualization)를 사용합니다. 컨테이너의 크기를 측정한 뒤, 화면에 실제로 보이는 행과 열만 렌더링합니다.

동시에 눈에 보이지 않는 플레이스홀더를 그려서, 마치 전체 데이터셋이 렌더링된 것처럼 보이고 동작하게 만듭니다. 스크롤이 발생하면 데이터 스토어에 새로 보여야 할 구간을 요청하고, 이를 일반적인 React, Svelte, Vue 컴포넌트로 렌더링합니다.

세 프레임워크 중 어느 것도 이 작업을 위한 전용 도구를 제공하지 않습니다. 별도의 primitive도, 내장 헬퍼도 없습니다. 가상화는 순수한 DOM 엔지니어링이며 온전히 개발자의 몫입니다. 프레임워크가 하는 일은 단지 결정된 15개 행을 다시 렌더링하는 것뿐이고, 이 부분은 셋 다 잘합니다.

그런데 가상화는 데이터를 렌더링하기도 전에 첫 번째 문제를 일으킵니다. 어떤 행이 보이는지 알려면 컨테이너의 크기가 필요하고, 크기를 얻으려면 뭔가를 렌더링해야 합니다. 닭과 달걀 문제인 셈이죠.

세 프레임워크 어디서나 통하는 패턴은 이렇습니다. 스타일이 적용된 빈 컨테이너를 먼저 렌더링하고, ResizeObserver를 붙인 뒤, 첫 번째 0이 아닌 크기가 들어올 때까지 실제 데이터 렌더링을 미루는 것입니다. 여기서 0은 정상적인 중간 상태입니다. 컨테이너의 높이를 결정하는 CSS가 아직 로딩 중일 수도 있으니까요.

// React, but the same logic ports to Svelte and Vue as is
const [size, setSize] = useState({ height: 0 });
useEffect(() => {
  const element = viewportRef.current;
  if (!element) return;

  const observer = new ResizeObserver(
    ([entry]) => setSize({ height: entry.contentRect.height })
  );
  observer.observe(element);

  return () => observer.disconnect();
}, []);

if (!size.height) return null;
return render();

여기서 React는 다른 두 프레임워크에 없는 도구를 하나 가지고 있습니다. 바로 useLayoutEffect입니다. DOM이 만들어진 뒤, 브라우저가 화면을 그리기(paint) 전에 실행되므로, 컨테이너를 측정하고 상태를 업데이트하면 사용자가 보는 첫 프레임에 이미 보정된 결과가 나타납니다.

// react only
const [size, setSize] = useState({ height: 0 });
useLayoutEffect(() => {
  const element = viewportRef.current;
  setSize({ height: element.offsetHeight });
});

if (!size.height) return null;
return render();

사람들은 useLayoutEffect를 위험한 도구라고 자주 놀리는데, 보통은 그 말이 맞습니다. 하지만 가상화된 컴포넌트의 초기 측정은 이 훅이 제 몫을 하는 몇 안 되는 사례 중 하나입니다.

다만 솔직히 말하면, 실전에서는 결국 ResizeObserver 방식으로 되돌아가게 됩니다. useLayoutEffect 콜백 시점에 레이아웃이 준비되지 않은 경우가 많기 때문입니다. 크기는 외부 스타일시트, 폰트, 이미지 등 아직 로드되지 않은 요소에 의존하기도 합니다. 그러니 어차피 옵저버는 필요하고, useLayoutEffect는 그것을 대체하는 게 아니라 첫 프레임을 최적화하는 보조 수단 정도가 됩니다.

Svelte와 Vue에는 useLayoutEffect에 대응하는 개념이 없습니다. Svelte의 $effect.pre는 DOM이 업데이트되기 전에 실행되어 측정하기엔 너무 이릅니다. onMount와 tick()은 DOM이 존재한 뒤에 실행되지만, 거기서 만든 변경 사항은 다음 프레임에 그려지므로 그냥 ResizeObserver를 쓰는 것과 다를 게 없습니다.

Vue도 같은 구조입니다. onBeforeUpdate는 너무 이르고, onUpdated는 DOM을 볼 수는 있지만 거기서 만든 변경은 다음 렌더링 프레임에 반영됩니다. 그러니 React의 이점은 실재하지만 꽤 좁습니다. 다른 프레임워크들의 설계도 나름의 이유가 있고, 애초에 React가 이 훅을 만든 것도 자기 자신의 렌더 사이클 구조 때문입니다.

SSR에 관한 짧은 이야기

가상화와 서버사이드 렌더링(SSR)은 본질적으로 충돌합니다. 서버는 사용자의 뷰포트에 어떤 행이 들어올지 알 수 없으니, 올바른 구간을 렌더링할 방법이 없습니다. 하지만 실제로 겪어보면 이 문제가 생각만큼 크지는 않습니다.

SSR을 쓰는 이유는 주로 첫 페인트를 빠르게 하기 위해서인데, 이는 가상화가 이미 나름의 방식으로 해결하는 문제입니다. 또 다른 이유인 SEO는 애초에 10만 행 중 15행만 렌더링하는 컴포넌트와는 처음부터 잘 맞지 않습니다.

순수 React나 Vue를 쓴다면 이 충돌을 체감할 일이 거의 없습니다. 하지만 Next.js나 Nuxt를 쓰면 얘기가 다릅니다. 보통 하이드레이션 불일치(hydration mismatch) 오류가 줄줄이 발생하는 형태로 나타나죠. 해결책은 의외로 시시합니다. 그리드를 클라이언트 전용 컴포넌트로 지정하면 오류가 사라집니다. 받아들이고 넘어가면 되는 트레이드오프입니다.

내부 로직: 메모이제이션과 파생 상태

여기서 잠깐 짚고 넘어갈 부분이 있습니다. SVAR는 많은 사용자를 대상으로 컴포넌트를 만들기 때문에, 모든 종류의 React 환경에서 잘 동작해야 합니다. 그래서 여전히 코드에 수동으로 메모이제이션 지침을 넣어둡니다. 만약 여러분이 최신 코드베이스에서 React Compiler를 쓸 수 있는 환경이라면, 컴파일러가 수동 배치보다 훨씬 더 잘 이 작업을 대신해줄 것입니다. 그런 경우라면 아래에서 다루는 useMemo 관련 내용은 무시해도 됩니다. 유효한 기법이긴 하지만 React Compiler가 도입되면 필요 없어지는 기법입니다.

React의 원래 성능 전략은 "HTML 렌더링은 느리고 JavaScript는 빠르니, 컴포넌트 코드를 다시 실행하는 건 괜찮다"는 것이었습니다. 단순한 버튼이라면 이 전략은 완벽하게 통합니다.

하지만 데이터 그리드는 렌더링에 앞서 데이터와 설정을 정규화하고, 레이아웃을 계산하고, 컬럼의 기하 구조를 확정해야 합니다. SVAR의 간트 컴포넌트는 훨씬 더 많은 계산을 합니다. 이 정도 규모에서는 매 렌더마다 모든 걸 다시 계산하는 게 더 이상 괜찮지 않습니다.

useMemo와 useCallback은 React의 표준적인 답이고, 복잡한 컴포넌트에서는 최고의 친구가 됩니다.

// React
const normalizedHeaders = useMemo(() => normalize(columns), [columns]);
const columnCount = normalizedHeaders.length;

Svelte는 같은 개념을 $derived로 표현합니다.

// Svelte
const normalizedHeaders = $derived(normalize(columns));
const columnCount = $derived(normalizedHeaders.length);

Vue는 computed로 표현합니다.

// Vue
const normalizedHeaders = computed(() => normalize(columns));
const columnCount = computed(() => normalizedHeaders.value.length);

내부에서 돌아가는 반응성 메커니즘은 완전히 다르지만, 사용법은 거의 차이가 없습니다. 셋 다 "입력값이 바뀌기 전까지 이 값은 보존된다"는 같은 계약을 값싸게 제공합니다.

실제로 그리드의 가상화 계산 로직(보이는 행 범위, 좌/우/중앙 컬럼 분할, 전체 스크롤 높이)을 포팅할 때, useMemo, $derived.by, computed 사이를 거의 한 줄 한 줄 그대로 번역하는 수준으로 옮길 수 있었습니다. $x, x.value, 평범한 값 사이에서 문법만 바뀔 뿐, 로직 자체는 그대로 이식됩니다. 한 프레임워크를 알면 나머지 둘도 이미 이해하고 있는 셈입니다.

이 유사함 속에 진짜 차이 하나가 숨어 있습니다. React는 의존성 배열을 직접 손으로 작성해야 합니다. SVAR의 renderRows 메모는 여덟 개의 의존성을 나열하는데, 하나라도 빠뜨리면 그리드가 갱신되지 않은 채로 굳어버리는 디버깅하기 아주 괴로운 버그가 생깁니다. Svelte와 Vue는 의존성을 자동으로 추적합니다.

세 프레임워크의 기본 동작이 만드는 차이

프레임워크의 기본 성격 얘기가 나온 김에, 컴포넌트 코드가 언제 실행되는지에 대한 구조적 차이 하나가 모든 것을 좌우한다는 점을 짚고 싶습니다. Svelte와 Vue는 컴포넌트의 setup 코드를 딱 한 번만 실행합니다. React는 함수 본문 전체를 렌더마다 다시 실행합니다.

Svelte나 Vue에서는 "데이터 스토어를 만든다"가 그냥 평범한 한 문장입니다. React에서 같은 의도를 구현하려면 여러 관용구가 뒤섞입니다. 스토어를 위한 useMemo(() => new DataStore(...), []), 이벤트 버스를 연결하기 위한 null 체크가 있는 useRef, 그리고 이펙트 바깥에 유지해야 하는 동기적 첫 렌더 초기화 호출까지 필요합니다. 이펙트는 페인트 이후에 발동되므로 첫 프레임에는 너무 늦기 때문이죠. 하나의 개념에 네 가지 관용구가 필요한 셈입니다.

하지만 이 모델에는 반대급부도 있습니다. Svelte와 Vue는 컴포넌트의 setup 코드를 한 번만 실행하기 때문에, 반응성은 명시적으로 opt-in 하는 무언가가 됩니다. 즉 의도치 않은 재계산이 설계상 거의 발생하지 않습니다. 대신 위험은 다른 곳으로 옮겨갑니다. 애초에 어떤 값을 반응형으로 만드는 걸 깜빡하고, 그 결과 조용히 절대 업데이트되지 않는 무언가를 배포하게 될 수 있습니다. 실무에서는 자동 의존성 추적과 린트 도구가 이런 사례 대부분을 잡아줍니다.

그러니 이건 우열의 문제가 아니라 트레이드오프입니다. React의 모델은 기본적으로 더 위험하지만 완전히 명시적이라 무슨 일이 벌어지는지 항상 확인할 수 있습니다. Svelte와 Vue의 모델은 기본적으로 더 안전하지만 가끔 예상치 못한 곳에서 놀라게 됩니다.

이 말이 모든 걸 useMemo로 감싸야 한다는 뜻은 아닙니다. 대부분의 계산은 신경 쓸 필요가 없을 만큼 값쌉니다. 코드를 읽거나, 더 좋게는 프로파일링을 통해 무거운 부분을 찾아내고, 그 부분만 렌더 사이에 보존하면 됩니다. 그게 이 규율의 전부입니다.

참고: 하나의 스토어, 세 개의 어댑터

SVAR 컴포넌트에서는 메모이제이션만으로 충분하지 않았습니다. 그래서 프레임워크에 독립적인 반응형 스토어를 하나만 두고, 이를 각 프레임워크의 primitive에 맞게 어댑팅합니다.

Svelte는 $store 자동 구독이 붙은 진짜 svelte/store writable을 통해 이 스토어를 소비합니다. Vue는 작은 subscribe() 헬퍼를 통해 ref를 받습니다.

React는 훅을 받습니다. useStore(api, 'name')은 useState와 useEffect 안의 구독을 조합해서 만들어졌습니다. React에는 추가 장치가 하나 더 필요했는데, 바로 변경 카운터를 반환하는 useStoreWithCounter 훅입니다. 배열이 제자리에서(in place) 변경되면 참조 동등성 비교로는 변화를 감지할 수 없기 때문에, 의존성으로 쓸 카운터가 필요했습니다.

만약 단일 프레임워크만 대상으로 한다면 이런 장치는 전혀 필요하지 않습니다. React와 Vue 모두 성숙한 외부 스토어 생태계를 가지고 있고, Svelte 5의 .svelte.js 상태 모듈은 정말 괜찮은 네이티브 선택지입니다. 다만 SVAR는 하나의 스토어로 세 호스트를 모두 서비스해야 했기 때문에 이런 선택지를 쓸 수 없었습니다.
