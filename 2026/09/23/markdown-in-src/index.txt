13:T2692,<h2>마크다운은 이제 소스 코드다</h2>
<p>에이전틱 코딩(agentic coding)이 개발 문화를 빠르게 바꾸고 있습니다. LLM이 코드를 대신 작성해주는 시대에, htmx의 창시자이자 몬태나 주립대 교수인 Carson Gross는 흥미로운 주장을 내놓습니다. 이제 마크다운은 더 이상 문서가 아니라 소스 코드 그 자체로 취급해야 한다는 것인데요. 그는 컨설팅 현장에서 목격한 흐름을 바탕으로, 마크다운을 <code>/src</code> 디렉터리에 코드와 나란히 커밋해야 한다는 구체적인 제안을 내놓습니다.</p>
<h3>컴파일러 비유의 함정</h3>
<p>&quot;LLM은 고수준 명세를 저수준 구현으로 바꿔주는 컴파일러 같은 존재&quot;라는 시각이 있습니다. 이 관점에서는 컴파일러가 만든 기계어를 굳이 들여다보지 않듯, LLM이 생성한 코드도 굳이 들여다볼 필요가 없다는 논리가 성립합니다.</p>
<p>Gross는 이 비유에 동의하지 않습니다. 이유는 여러 가지지만 이 글에서 핵심적으로 짚는 건 하나입니다. 컴파일러 워크플로우는 원본 소스 코드를 그대로 보존하지만, LLM 워크플로우는 대개 그렇지 않다는 점입니다.</p>
<p>오늘날 LLM 코드는 개발자가 기능을 만들어가며 에이전트에 던지는 일련의 프롬프트를 통해 생성됩니다. 그 결과 생성된 코드가 해당 기능에 대한 &quot;그라운드 트루스&quot;에 가장 가까운 존재가 됩니다. Linear, 슬랙 스레드, 위키 등에 기능 설명이 남아있을 수는 있지만, 코드베이스 관점에서는 결국 생성된 코드만이 유일한 소스 오브 트루스로 남습니다.</p>
<p>Gross는 이런 방식이 전문적인 에이전틱 코딩 환경에서는 이상적이지 않다고 봅니다. 휘발성 프롬프트 세션에서 나온 결과물을 그대로 두는 대신, 마크다운을 생성된 코드와 함께 소스 디렉터리에 캡처하고 커밋하는 방향으로 나아가야 한다는 것입니다.</p>
<h3>소스 코드로서의 마크다운</h3>
<p>마크다운이 전통적인 소스 코드와 닮은 점은 다음과 같습니다.</p>
<ul>
<li>플레인 텍스트이므로 diff, grep, PR 리뷰가 가능하다</li>
<li>LLM이 네이티브하게 읽고 쓴다</li>
<li>사람도 별도 도구 없이 읽고 편집할 수 있다</li>
</ul>
<p>사실 마크다운은 이미 <code>AGENTS.md</code>, 각종 스펙 문서, 플랜, <code>TASK.md</code> 등의 형태로 어느 정도 소스 역할을 하고 있습니다. 다만 이를 체계적으로 캡처하는 관행이 아직 표준화되지 않았을 뿐입니다.</p>
<p>Hartley Brody는 &quot;Markdown is the new source code&quot;라는 글에서 작업 중인 마크다운 파일을 <code>.scratch/research/</code>, <code>.scratch/plan/</code>에 보관한다고 밝혔습니다. Gross 본인도 비슷한 목적으로 <code>/tmp</code> 디렉터리를 만들어 쓰는 관행을 채택해왔다고 합니다.</p>
<p>여기서 그는 한 걸음 더 나아가, 이런 파일 중 일부를 기존 소스 코드 옆의 새로운 디렉터리로 승격시키자고 제안합니다: <code>/src/md</code></p>
<p>이 디렉터리에 담기는 마크다운은 전통적인 설계 문서보다 훨씬 저수준입니다.</p>
<ul>
<li>아키텍처 결정 사항을 담는다</li>
<li>소스 레벨 결정 사항을 담는다</li>
<li>저수준 데이터 설계 결정 사항을 담는다</li>
</ul>
<p>프로젝트 매니저나 디자이너가 관리하는 기존 설계 문서보다는, 명세(specification)에 훨씬 가까운 성격을 띱니다(엄밀히 명세는 아니지만요).</p>
<h3>로컬리티(Locality)의 힘</h3>
<p>Gross는 로컬리티를 중요하게 여기는 개발자입니다. 마크다운을 <code>/src</code>로 옮기는 것에는 다음과 같은 강력한 로컬리티 장점이 있다고 설명합니다.</p>
<ul>
<li>코드 모듈이 그 코드의 의도를 설명하는 마크다운을 함께 포함하게 된다</li>
<li>명세가 위키/노션/컨플루언스/지라 어딘가에 떨어져 있는 &quot;유령 같은 원거리 명세&quot; 문제가 사라진다</li>
<li><code>/src</code>의 마크다운은 사람과 에이전트 모두가 소비할 수 있다</li>
<li>에이전트가 코드베이스에 대한 컨텍스트를 얻기 위해 다른 곳을 뒤질 필요가 없어진다</li>
</ul>
<h3>Linear, 위키 같은 도구는 어떻게 되나</h3>
<p>시스템 동작에 대한 다른 소스 오브 트루스가 여전히 존재할 수 있습니다. 다만 그런 도구들은 더 고수준이거나 &quot;프로세스 중심&quot;의 문서 — 고수준 설계 문서, 해결이 필요한 이슈 워크플로우 등 — 를 담당하게 됩니다.</p>
<p>반면 시스템의 핵심적이고 현재이자 정적인 의도된 동작(intended behavior)은 점점 더 소스 디렉터리 안의 마크다운에 직접 담기게 된다는 것이 Gross의 전망입니다.</p>
<h3>테스트는 어떻게 되나</h3>
<p>많은 사람이 온라인에서 &quot;테스트가 새로운 명세다(혹은 원래부터 그랬다)&quot;라고 말합니다. Gross도 어느 정도 공감하지만, 테스트가 사람과 에이전트 사이의 상호작용 매체로는 적합하지 않다고 지적합니다.</p>
<ul>
<li>테스트에는 형식적 절차(ceremony)가 많아서 정작 무엇을 테스트하는지 가려지는 경우가 많다</li>
<li>대부분의 사람이 시스템을 이해하고 싶을 때 다루기엔 너무 저수준이다</li>
<li>Mermaid 다이어그램 같은 고수준 설명이 테스트 코드 안에 자연스럽게 녹아들지 않는다</li>
</ul>
<p>그래서 그는 다음과 같은 역할 분담을 제안합니다.</p>
<ul>
<li><code>/src</code>의 마크다운은 명세(에 가까운 것) 역할을 한다</li>
<li><code>/test</code>(혹은 다른 위치)의 테스트는 그 마크다운을 기반으로 하며, 정확성을 자동으로 확인하는 역할을 한다</li>
</ul>
<p>핵심은 프롬프트로부터 코드와 테스트를 직접 생성하는 대신, 개발자가 <code>/src</code>의 마크다운을 먼저 작업하고 거기서 코드와 테스트를 파생시키는 흐름입니다.</p>
<h3>/src/md 마크다운의 성격</h3>
<p><code>/src/md</code>에 들어가는 마크다운은 시스템의 공식 명세와 고수준 설계 문서 사이 어딘가에 위치합니다.</p>
<p>소스 코드에 복잡도 예산(Complexity Budget)이 있듯, 이 마크다운에도 동일한 개념이 적용됩니다. 문서를 깔끔하고 잘 분리된 상태로, 적절한 추상화 수준으로 유지하려면 세심한 관리가 필요합니다.</p>
<p>개발자는 마크다운과 그로부터 파생된 코드 양쪽 모두를 다뤄야 하므로, 필요할 때 둘을 동기화하는 것도 하나의 중요한 스킬이 될 것입니다. 예를 들어 개발자가 생성된 코드에 대해 빼거나 제약을 거는 식의 수정 작업을 했다면, 그 변경 사항이 다시 마크다운에 반영돼야 할 수도 있습니다.</p>
<p>Gross는 <code>/src/md</code>의 콘텐츠 대부분을 에이전트가 생성해서는 안 된다고 강조합니다. 이 디렉터리는 기본적으로 사람이 작성하고 관리해야 한다는 것입니다.</p>
<h3>/src/md 컨벤션 제안</h3>
<p>이 부분은 글에서 가장 약한, 즉 아직 검증되지 않은 지점이라고 Gross 스스로 밝힙니다. 새로운 아이디어를 소리 내어 생각하며 논의를 제안하는 단계입니다.</p>
<p>그가 제시하는 잠정적인 구조는 다음과 같습니다.</p>
<pre><code>src/
  md/
    README.md            # index of all md, entry point for agents
    TODO.md               # a list of general TODOs open for this module
    OVERVIEW.md            # a technical overview of this module
    features/FEATURE_1.md  # a set of feature-specific documents
    data/DATAMODEL_1.md     # descriptions of data models in the module
    api/API_1.md            # descriptions of APIs the module provides
    infrastructure/INFRASTRUCTURE_1.md  # descriptions of infrastructure used by the module</code></pre>
<p>여기서 <code>features</code>, <code>data</code>, <code>api</code>, <code>infrastructure</code> 디렉터리는 모두 선택 사항입니다. 핵심은 모듈의 동작을 <code>/src/md</code> 안에서 가장 잘 담아낼 수 있도록 적절한 축으로 나누는 것입니다.</p>
<h3>정리</h3>
<ul>
<li>코드가 생성하기 저렴해질수록 진짜 가치를 갖는 것은 코드 뒤에 숨은 의도, 즉 무엇을 하는지, 왜 하는지, 무엇을 하면 안 되는지입니다.</li>
<li>오늘날 이 의도는 휘발성 프롬프트 세션에서 사라지거나 위키, 티켓, 슬랙 스레드 곳곳에 흩어져 있습니다.</li>
<li>Gross는 이 의도를 마크다운으로 캡처해 코드가 생성되는 바로 그 <code>/src</code> 디렉터리에 커밋할 것을 제안합니다. 로컬리티 원칙에 따라 사람과 에이전트 모두가 같은 곳에서 컨텍스트를 얻을 수 있어야 한다는 것입니다.</li>
<li>마크다운은 명세와 테스트 사이의 새로운 계층으로 자리잡습니다. 마크다운이 소스 오브 트루스가 되고, 코드와 테스트는 그로부터 파생되는 산출물이 됩니다.</li>
