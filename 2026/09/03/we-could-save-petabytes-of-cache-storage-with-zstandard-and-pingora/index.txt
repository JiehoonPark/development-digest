15:T38cb,<p>메모리 비용이 무섭게 오르고 있습니다. 지난 1년 동안 RAM과 HDD 가격이 모두 폭등했는데요, Cloudflare처럼 대규모로 분산된 스토리지 제품(대표적으로 CDN)을 운영하는 회사 입장에서는 이미 배포된 메모리를 얼마나 효율적으로 쓰느냐가 곧 서비스 지속 가능성과 직결됩니다. 이런 배경에서 Cloudflare는 캐시 용량을 실질적으로 늘릴 수 있는 방법을 프로토타입으로 만들었습니다. Pingora 안에서 대상 자산을 Zstandard로 인코딩해, 약간의 CPU 비용을 치르는 대신 스토리지와 데이터센터 간 대역폭을 크게 절약하는 아키텍처입니다.</p>
<p>이 글은 Cloudflare의 1.1.1.1 인턴 프로그램 과정에서 만든 &quot;Cache Transcoding&quot;이라는 시스템을 소개하는 아티클을 정리한 것입니다. 캐시에 적합한 응답이 들어오면 디스크에 쓰기 전에 Zstandard(zstd)로 인코딩하고, 이 압축된 형태를 자산이 캐시에 머무는 동안 그리고 Tiered Cache를 통해 데이터센터 간 이동할 때까지 그대로 유지합니다. 클라이언트에게 응답을 내려주기 직전에만 다시 디코딩합니다.</p>
<p>초기 테스트에서 이 인코딩은 대상 자산의 디스크 상 크기를 평균 1/3로 줄였습니다. 오리진을 향하는 프록시에서 추가로 드는 CPU 비용은 작았지만, 이건 명백히 남는 장사입니다. 약간의 CPU 증가로 Cloudflare는 페타바이트 단위의 실질 캐시 용량을 확보하고 데이터센터 간 전송량도 줄일 수 있습니다. 인코딩 비용은 자산이 캐시에 들어올 때 딱 한 번 지불하지만, 스토리지와 대역폭 절감 효과는 그 자산이 재사용될 때마다 계속 발생합니다.</p>
<h3>Zstandard란 무엇인가</h3>
<p>Zstandard(zstd)는 Facebook의 Yann Collet이 개발해 2016년 오픈소스로 공개한 무손실 압축 알고리즘입니다. 무손실이라는 건 압축된 데이터를 디코딩했을 때 원본과 바이트 단위로 완전히 동일하다는 뜻입니다. 즉 자산 자체를 바꾸지 않고 디스크 상의 표현 방식만 바꿀 수 있다는 의미입니다.</p>
<p>zstd는 압축률과 속도의 균형을 목표로 설계되었습니다. Cloudflare가 앞서 진행했던 브라우저 압축 테스트에서 zstd는 Brotli보다 42% 빠르면서도 거의 동일한 파일 크기를 냈고, gzip과 비슷한 속도에서 11.3% 더 작은 파일을 만들어냈습니다. Cache Transcoding은 대규모 트래픽을 다루는 만큼 이 균형이 중요한데요, 인코딩과 디코딩 모두 빨라야 하기 때문입니다. 프로토타입은 zstd 레벨 3을 사용해, 캐시 채우기(cache fill) 작업을 CPU 병목으로 만들지 않으면서도 압축 이점의 대부분을 얻고 있습니다.</p>
<p>Cloudflare는 전통적으로 오리진이 보낸 콘텐츠 인코딩 그대로 자산을 저장해왔습니다. 오리진이 압축되지 않은 응답을 보내면 그 압축되지 않은 바이트를 디스크에 저장하고, 데이터센터 간에도 같은 형태로 전송했습니다. Cache Transcoding은 여기에 캐시 내부 압축이라는 레이어를 하나 더 추가하는 것입니다.</p>
<h3>모든 것을 압축할 가치는 없다</h3>
<p>트랜스코딩이 모든 걸 압축한다는 의미는 아닙니다. 이미지, 비디오, 폰트는 대체로 이미 압축된 상태로 들어옵니다. Cloudflare의 트래픽 샘플에서 이런 미디어는 요청의 21.4%를 차지했지만 바이트 기준으로는 63.3%를 차지했습니다. 이런 걸 다시 압축하면 CPU만 낭비하는 셈입니다.</p>
<p>반면 압축 가능한 텍스트는 다릅니다. HTML, JSON, CSS, JavaScript는 요청의 67.3%를 차지했지만 바이트로는 22.3%에 불과했습니다. 이 텍스트 구간 안에서 약 71%는 Content-Encoding이 설정되지 않은 채, 즉 압축되지 않은 상태로 도착했고 압축 효율도 좋았습니다. Cloudflare의 통제된 테스트 코퍼스에서 대상 자산들은 약 2.8배로 압축되었습니다.</p>

<p>바이트당 인코딩 비용이 디코딩보다 더 비싸지만, 자산은 채워지는 횟수보다 서빙되는 횟수가 훨씬 많습니다. 자산의 표현 방식만 바꿔도 기존 하드웨어로 더 많은 고객 콘텐츠를 저장할 수 있는 셈입니다.</p>
<p>디스크에 저장되는 바이트 수가 줄어들면 서버 하나가 유지할 수 있는 객체 수도 늘어납니다. 이는 캐시 밀도를 높이고, 압축되지 않은 표현이 필요 이상의 공간을 차지해서 유용한 콘텐츠가 밀려나는 상황을 줄여줍니다. 또한 작아진 표현은 Tiered Cache를 거쳐 이동할 때 Cloudflare 데이터센터 간 전송되는 데이터량도 줄여주므로, 백본 사용 효율도 높입니다.</p>
<h3>압축 비용은 딱 한 번만 지불한다</h3>
<p>압축은 절대 공짜가 아닙니다. 인코딩과 디코딩 모두 CPU를 사용하므로, 중요한 질문은 절약되는 바이트가 그 처리 비용을 감당할 만한 가치가 있느냐입니다. zstd 레벨 3(속도와 압축 크기의 균형을 잡은 흔한 기본값)에서 Cloudflare의 모델은 테스트한 트래픽과 재사용 가정 하에 추가 CPU 비용을 몇 퍼센트 수준으로 유지했습니다.</p>
<p>처음에는 인기 콘텐츠에만 트랜스코딩을 적용하는 방안도 고려했습니다. 자주 재사용되는 인기 자산일수록 이득이 클 거라 생각했기 때문인데요, 실제로는 도움이 되지 않았습니다. 디코딩은 자산이 서빙될 때마다 발생하기 때문에, 가장 인기 있는 콘텐츠에만 이 기능을 제한하면 스토리지 절감 효과는 줄어드는데 CPU 절감 효과는 그만큼 줄어들지 않았습니다. 오히려 더 단순한 정책이 더 나은 성능을 냈습니다. 압축 가능한 텍스트 중 4KiB(키비바이트) 이상인 대상을 모두 트랜스코딩하는 방식이 CPU 예산 안에서 측정된 스토리지 이득의 거의 전부를 포착했습니다.</p>
<h3>Cache Transcoding의 동작 방식</h3>
<p>캐시 미스가 발생하면, Pingora 기반 프록시가 디스크에 쓰기 전에 zstd로 본문을 인코딩합니다. 캐시 메타데이터에는 저장된 표현이 압축되어 있다는 사실과 원본 콘텐츠 길이가 함께 기록됩니다. 응답이 프록시를 떠나기 전에는 본문이 원본(identity) 표현으로 다시 디코딩됩니다.</p>
<p>캐시 히트가 발생하면, 저장된 zstd 객체를 디스크에서 읽어 디코딩합니다. Tiered Cache를 사용할 경우 압축된 표현이 상위 티어에서 하위 티어로 압축된 상태 그대로 전달되고, 디코딩은 클라이언트를 향하는 마지막 홉에서만 일어납니다.</p>
<p>완전한 캐시 미스가 발생하면, 상위 티어가 오리진으로부터 원본(identity) 바이트를 가져옵니다. 이 바이트는 한 번 인코딩되어 zstd로 저장되고, 하위 티어로도 압축된 형태로 전달됩니다. 하위 티어 역시 zstd 표현을 저장한 뒤, 요청 경로를 위해 이를 디코딩합니다.</p>
<p>하위 티어에서는 미스가 나지만 상위 티어에 이미 객체가 있는 경우, 오리진은 관여하지 않습니다. 압축된 객체가 캐시 티어 사이에서 직접 이동하며, 네트워크 상에서도 디스크 상에서도 압축된 채로 유지되다가 하위 티어에서 한 번만 디코딩됩니다.</p>
<p>하위 티어에 이미 객체가 있는 경우에는 네트워크 전송이나 인코딩이 전혀 필요 없습니다. 하위 티어는 디스크에서 zstd 바이트를 읽고 디코딩해서 원본 자산을 그대로 전달합니다.</p>
<p>이 과정에서 저장 인코딩 마커가 객체가 두 번 이상 인코딩되는 것을 막아줍니다. 다른 티어로부터 객체를 받는 캐시 레이어는 그 객체가 이미 zstd로 저장되어 있다는 걸 확인하고 그 형태를 그대로 유지합니다.</p>
<h3>왜 특정 텍스트만 트랜스코딩하는가</h3>
<p>가장 빠른 압축 연산은 아예 수행하지 않아도 되는 연산입니다. 그래서 Cache Transcoding은 일련의 적합성 검사(eligibility check)를 통해 이득이 없을 것으로 보이는 콘텐츠를 걸러냅니다.</p>
<p>프로토타입은 다음 조건을 모두 만족하는 200 OK 응답만 트랜스코딩합니다: Content-Encoding이 설정되지 않았고, Content-Type이 압축 가능한 텍스트이며, Content-Length가 알려져 있고 그 값이 최소 4KiB 이상인 경우입니다. 슬라이스 서브요청, 업스트림에서 이미 압축을 적용한 응답, 범위(range) 요청, 이미 압축된 응답, 길이를 알 수 없는 본문, 바이너리 콘텐츠는 모두 변경 없이 그대로 둡니다.</p>
<p>4KiB라는 임계값은 수많은 작은 요청들을 걸러내면서도, 트랜스코딩 대상이 될 수 있었던 바이트 중 겨우 약 1%만 제외시켰습니다. 이 값을 더 낮추면 객체당 오버헤드만 늘고 절약되는 스토리지는 크게 늘지 않습니다.</p>
<p>임계값과 zstd 레벨은 고정된 한계가 아니라 조정 가능한 파라미터입니다. zstd 레벨 3과 4KiB 최소값으로 시작한 이유는 아키텍처를 측정하기 위한 보수적인 출발점이 필요했기 때문입니다. 초기 CPU 예산을 파악한 지금은, 더 높은 압축 레벨이 추가 비용을 정당화할 만큼 압축률을 개선하는지 테스트해볼 수 있는 단계입니다.</p>
<h3>100만 건 이상의 요청으로 검증하기</h3>
<p>Cloudflare는 통제된 테스트 존을 대상으로 프로토타입을 실행하며, 각 요청을 요청 로그, Prometheus 메트릭, Jaeger 트레이스와 상호 대조했습니다.</p>
<p>정확성 검증 캠페인은 캐시 미스, 캐시 히트, 단일 홉 필(fill), Tiered Cache 필 등 다양한 경로를 다뤘습니다. 캐시 키를 다양하게 조정해 각 요청이 특정 경로를 따르도록 만들고, 트레이스를 통해 인코딩과 디코딩이 실제로 어디에서 일어나는지 확인했습니다.</p>
<p>성능 검증 캠페인 하나는 10대의 캐시 서버에 100만 건이 넘는 요청을 전송했습니다. 이 캠페인의 절반은 Tiered Cache를 비활성화한 상태로, 나머지 절반은 활성화한 상태로 진행되어, 로컬 캐시 동작과 캐시 티어 간 전송을 분리해서 측정할 수 있었습니다.</p>
<p>테스트에 사용된 두 자산은 각각 약 195KiB, 272KiB였고 둘 다 약 2.8배로 압축되었습니다. 이는 의도적으로 압축이 잘 되는 테스트 코퍼스였습니다. 아키텍처를 검증하기에는 명확한 신호를 줬지만, 인터넷 상의 모든 텍스트 객체를 대표한다고 보기는 어렵습니다. 측정된 압축률을 전체 플릿(fleet) 차원의 상수로 다루려면 더 넓은 범위의 코퍼스로 검증이 필요합니다.</p>
<h3>한 번 압축하면 여러 번 이득을 본다</h3>
<p>이번 실험이 보여준 건, Cloudflare가 캐싱 서비스 전반에 걸쳐 모든 고객에게 이득이 될 만한 상당한 효율화 여지가 아직 남아 있다는 사실입니다. Cache Transcoding을 위해 만든 이 아키텍처는 테스트한 조건 하에서 이 트레이드오프가 유리하다는 걸 보여줬습니다. 콘텐츠는 그대로 보존되었고, CPU 예산 안에서 동작했습니다.</p>
<p>다음 단계로는 더 높은 zstd 레벨을 평가하고, 더 다양한 콘텐츠 타입과 객체 크기를 테스트하며, 적합성 기준의 여러 파라미터를 튜닝하는 작업 등이 계획되어 있습니다. 향후에는 범위 요청, 이미 압축된 오리진 응답 처리, 그리고 이미 압축을 지원하는 다운스트림 컴포넌트에 디코딩 없이 압축된 객체를 직접 전달하는 방안도 검토할 예정입니다.</p>
<h3>정리</h3>
<ul>
<li><strong>핵심 아이디어</strong>: Cloudflare는 캐시에 저장되는 압축 가능한 텍스트 자산(HTML, JSON, CSS, JS)을 zstd로 인코딩해 저장하고, Tiered Cache를 통한 데이터센터 간 이동 시에도 압축된 상태를 유지하다가 클라이언트에게 서빙하는 마지막 순간에만 디코딩합니다.</li>
<li><strong>효과</strong>: 대상 자산의 디스크 크기가 평균 1/3로 줄었고(테스트 코퍼스 기준 약 2.8배 압축률), 추가 CPU 비용은 몇 퍼센트 수준에 그쳤습니다. 인코딩은 캐시 채우기 시 1회, 디코딩은 서빙할 때마다 발생하지만, 재사용 빈도가 훨씬 높기 때문에 전체적으로 유리한 트레이드오프입니다.</li>
<li><strong>선택적 적용이 핵심</strong>: 이미지·비디오·폰트처럼 이미 압축된 미디어는 대상에서 제외하고, Content-Encoding 미설정 + 압축 가능한 텍스트 + Content-Length 4KiB 이상인 응답만 트랜스코딩합니다. 인기 콘텐츠만 골라 압축하는 방식은 오히려 비효율적이었고, 단순한 크기 기반 정책이 더 나은 성능을 보였습니다.</li>
<li><strong>한계와 후속 과제</strong>: 현재 결과는 통제된 테스트 코퍼스(100만 건 이상의 요청, 10대 서버) 기준이며, 인터넷 전체 트래픽을 대표하지는 않습니다. 향후 더 높은 zstd 레벨, 더 넓은 콘텐츠 범위, range 요청 및 다운스트림 압축 전달 최적화 등이 검토될 예정입니다.</li>
<li><strong>실무 시사점</strong>: 프론트엔드 개발자 입장에서는 직접 구현할 부분은 아니지만, CDN 계층에서 이런 트랜스코딩이 적용되면 오리진에서 압축 헤더를 설정하지 않은 텍스트 자산도 CDN 단에서 자동으로 효율화될 수 있다는 점, 그리고 압축 정책 설계 시 &quot;인기 콘텐츠 우선&quot;보다 &quot;단순한 크기 임계값&quot; 접근이 더 실용적일 수 있다는 인사이트를 참고할 만합니다.</li>
