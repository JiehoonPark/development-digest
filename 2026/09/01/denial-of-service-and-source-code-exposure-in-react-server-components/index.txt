15:T2d40,<p>React 팀이 지난주 공개했던 치명적 취약점(React2Shell)에 대한 패치를 검증하던 중, 보안 연구자들이 패치 자체를 우회하려는 시도 과정에서 추가로 두 종류의 취약점을 발견해 공개했습니다. 이번에 발견된 취약점들은 원격 코드 실행(RCE)으로 이어지지는 않으며, 기존 React2Shell 패치는 RCE 익스플로잇을 막는 데 여전히 유효합니다. 다만 서비스 거부(DoS)와 소스 코드 노출이라는 새로운 위험이 확인된 만큼, 즉시 업데이트가 필요합니다.</p>
<h3>새로 공개된 취약점 개요</h3>
<p>이번에 공개된 취약점은 다음과 같습니다.</p>
<ul>
<li><strong>서비스 거부(DoS) - High</strong>: CVE-2025-55184, CVE-2025-67779, CVE-2026-23864 (CVSS 7.5)</li>
<li><strong>소스 코드 노출 - Medium</strong>: CVE-2025-55183 (CVSS 5.3)</li>
</ul>
<p>주의할 점은, 이전에 공개됐던 패치 자체가 불완전했다는 사실입니다. 만약 이미 19.0.3, 19.1.4, 19.2.3으로 업데이트했다 하더라도 이는 불완전한 패치이므로, 다시 한번 업데이트해야 합니다. 즉, 지난주 취약점 대응을 이미 완료했다고 안심하고 있던 팀이라면 반드시 재확인이 필요합니다.</p>
<h3>즉시 조치가 필요한 이유</h3>
<p>이번 취약점들은 이전에 공개된 CVE-2025-55182와 동일한 패키지, 동일한 버전 범위에 존재합니다. 영향을 받는 버전은 다음과 같습니다.</p>
<ul>
<li>19.0.0, 19.0.1, 19.0.2, 19.0.3</li>
<li>19.1.0, 19.1.1, 19.1.2, 19.1.3</li>
<li>19.2.0, 19.2.1, 19.2.2, 19.2.3</li>
</ul>
<p>영향받는 패키지는 다음 세 가지입니다.</p>
<ul>
<li>react-server-dom-webpack</li>
<li>react-server-dom-parcel</li>
<li>react-server-dom-turbopack</li>
</ul>
<p>수정 사항은 19.0.4, 19.1.5, 19.2.4 버전에 백포트되었습니다. 위 패키지를 사용 중이라면 즉시 해당 수정 버전으로 업그레이드해야 합니다.</p>
<p>기존과 마찬가지로, 앱의 React 코드가 서버를 사용하지 않는다면 영향을 받지 않습니다. 마찬가지로 React Server Components를 지원하는 프레임워크·번들러·번들러 플러그인을 사용하지 않는다면 이 취약점들과 무관합니다.</p>
<p>React 팀은 이런 후속 취약점 발견 자체가 이상한 일이 아니라고 설명합니다. 치명적인 CVE가 공개되면 연구자들이 인접한 코드 경로를 집중적으로 파고들어, 최초 완화 조치를 우회할 수 있는 변형 익스플로잇 기법을 찾아내는 것은 업계 전반에서 흔히 나타나는 패턴이라는 것이죠. JavaScript 생태계뿐 아니라, 예를 들어 Log4Shell 사태 이후에도 커뮤니티가 최초 패치를 검증하는 과정에서 추가 CVE들이 보고된 바 있습니다. 이런 후속 공개가 번거롭게 느껴질 수 있지만, 일반적으로는 건강한 대응 사이클이 작동하고 있다는 신호로 볼 수 있습니다.</p>

<p>일부 React 프레임워크와 번들러는 취약한 React 패키지에 의존하거나, 피어 디펜던시로 걸어두었거나, 아예 포함하고 있었습니다. 영향받는 대상은 다음과 같습니다.</p>

<li>waku</li>
<li>@parcel/rsc</li>
<li>@vite/rsc-plugin</li>
<li>rwsdk</li>
</ul>
<p>업그레이드 절차는 이전 공지 글에 안내된 내용을 그대로 따르면 됩니다.</p>
<h3>호스팅 제공자 완화 조치</h3>
<p>지난번과 마찬가지로 여러 호스팅 제공자와 협력해 임시 완화 조치를 적용해두었습니다. 하지만 이 임시 조치에 의존해서는 안 되며, 앱을 즉시 업데이트해야 한다는 점은 변함없습니다.</p>
<h3>React Native 사용자 안내</h3>
<p>모노레포를 사용하지 않고 react-dom도 쓰지 않는 React Native 사용자라면, package.json에 react 버전이 고정되어 있을 것이므로 추가 조치는 필요 없습니다.</p>
<p>모노레포 환경에서 React Native를 사용 중이라면, 다음 패키지들이 설치되어 있는 경우에만 해당 패키지를 업데이트하면 됩니다.</p>
<ul>
<li>react-server-dom-webpack</li>
<li>react-server-dom-parcel</li>
<li>react-server-dom-turbopack</li>
</ul>
<p>이 취약점을 완화하려면 이 업데이트만으로 충분하며, react와 react-dom까지 업데이트할 필요는 없습니다. 따라서 React Native에서 흔히 발생하는 버전 불일치 오류를 유발하지 않습니다.</p>
<h3>취약점 상세</h3>
<h4>High Severity: 다수의 서비스 거부 취약점 (CVE-2026-23864)</h4>
<ul>
<li>CVSS 점수: 7.5 (High)</li>
<li>발견일: 2026년 1월 26일</li>
</ul>
<p>보안 연구자들이 React Server Components에 여전히 남아있는 추가 DoS 취약점을 발견했습니다. 특수하게 조작된 HTTP 요청을 Server Function 엔드포인트로 전송하면 트리거되며, 취약한 코드 경로와 애플리케이션 설정·코드에 따라 서버 크래시, 메모리 부족(OOM) 예외, 과도한 CPU 사용으로 이어질 수 있습니다.</p>
<p>1월 26일에 배포된 패치가 이 DoS 취약점들을 완화합니다. 참고로, 원래 CVE-2025-55184의 DoS를 막기 위해 배포했던 최초 수정본은 불완전했습니다. 이로 인해 이전 버전들이 여전히 취약한 상태로 남아 있었으며, 19.0.4, 19.1.5, 19.2.4 버전만이 안전합니다.</p>
<h4>High Severity: 서비스 거부 (CVE-2025-55184, CVE-2025-67779)</h4>
<ul>
<li>CVSS 점수: 7.5 (High)</li>
</ul>
<p>보안 연구자들은 Server Functions 엔드포인트로 악의적으로 조작된 HTTP 요청을 전송하면, React가 이를 역직렬화하는 과정에서 무한 루프에 빠져 서버 프로세스가 멈추고 CPU를 계속 소모하게 만들 수 있다는 사실을 발견했습니다. 앱이 별도의 React Server Function 엔드포인트를 직접 구현하지 않았더라도, React Server Components를 지원하기만 하면 여전히 취약할 수 있습니다.</p>
<p>이는 공격자가 사용자의 서비스 접근을 차단하고, 서버 환경의 성능에 영향을 줄 수 있는 공격 경로가 됩니다. 이번에 배포된 패치는 무한 루프 발생 자체를 막아 이 문제를 완화합니다.</p>
<h4>Medium Severity: 소스 코드 노출 (CVE-2025-55183)</h4>
<ul>
<li>CVSS 점수: 5.3 (Medium)</li>
</ul>
<p>한 보안 연구자는 취약한 Server Function에 악의적인 HTTP 요청을 보내면 해당 Server Function의 소스 코드가 안전하지 않게 반환될 수 있다는 사실을 발견했습니다. 이 익스플로잇이 성립하려면, 문자열화된 인자를 명시적으로든 암묵적으로든 노출하는 Server Function이 존재해야 합니다. 예를 들면 다음과 같은 코드입니다.</p>
<pre><code class="language-js">'use server';

<pre><code>0:{&quot;a&quot;:&quot;$@1&quot;,&quot;f&quot;:&quot;&quot;,&quot;b&quot;:&quot;Wy43RxUKdxmr5iuBzJ1pN&quot;}

<p>위 예시에서 보듯 <code>SECRET KEY</code>처럼 소스 코드에 하드코딩된 값이 그대로 노출될 수 있습니다. 이번에 배포된 패치는 Server Function의 소스 코드가 문자열화되는 것을 막아 이 문제를 방지합니다.</p>
<p>다만 이 취약점으로 노출될 수 있는 것은 소스 코드에 직접 박아 넣은 비밀값뿐입니다. <code>process.env.SECRET</code>처럼 런타임에 주입되는 비밀값은 영향을 받지 않습니다. 노출 범위는 해당 Server Function 내부 코드로 제한되지만, 번들러가 얼마나 인라이닝을 수행하느냐에 따라 다른 함수까지 포함될 수 있습니다. 실제 운영 번들 기준으로 반드시 직접 검증해볼 필요가 있습니다.</p>

<p>소스 코드 노출 취약점을 제보한 Andrew MacPherson(AndrewMohawk), 서비스 거부 취약점을 제보한 GMO Flatt Security Inc의 RyotaK와 Bitforest Co., Ltd.의 Shinsaku Nomura에게 감사를 전합니다. 또한 추가 DoS 취약점을 제보한 Winfunc Research의 Mufeed VH, Joachim Viide, GMO Flatt Security Inc의 RyotaK, Tencent Security YUNDING LAB의 Xiangwei Zhang에게도 감사드립니다.</p>
<h3>정리</h3>
<ul>
<li>이번 공지는 지난주 공개된 React2Shell RCE 취약점에 대한 패치를 검증하는 과정에서 발견된 후속 취약점 대응입니다. RCE 자체는 기존 패치로 여전히 막혀 있지만, 새로 발견된 DoS·소스 코드 노출 취약점은 별개로 패치해야 합니다.</li>
<li>영향받는 패키지는 react-server-dom-webpack, react-server-dom-parcel, react-server-dom-turbopack이며, 19.0.4 / 19.1.5 / 19.2.4로 업그레이드해야 완전히 해결됩니다. 이전에 19.0.3, 19.1.4, 19.2.3으로 업데이트했더라도 불완전한 패치이므로 재업데이트가 필요합니다.</li>
<li>next, react-router, waku, @parcel/rsc, @vite/rsc-plugin, rwsdk 등 RSC를 지원하는 주요 프레임워크·번들러를 사용 중이라면 의존성 체인을 반드시 점검해야 합니다.</li>
<li>Server Function이 문자열화된 인자를 응답에 그대로 포함하는 패턴을 쓰고 있다면, 소스 코드에 하드코딩된 비밀값이 노출될 수 있으므로 프로덕션 번들 기준으로 직접 점검해볼 필요가 있습니다. 환경 변수로 관리되는 비밀값은 이 취약점의 영향을 받지 않습니다.</li>
<li>서버를 전혀 사용하지 않거나 RSC를 지원하지 않는 프레임워크·번들러를 쓰는 앱은 이번 취약점들의 영향권 밖입니다. 다만 RSC를 조금이라도 사용한다면 Server Function 엔드포인트를 직접 구현하지 않았어도 DoS에 노출될 수 있다는 점을 유념해야 합니다.</li>
