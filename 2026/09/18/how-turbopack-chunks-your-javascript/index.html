How Turbopack chunks your JavaScript

📅 2026-09-18📰 Next.js Blog
frontend

Next.js 앱을 빌드하면 Turbopack이 알 수 없는 이름의 JavaScript 파일 수십 개를 만들어냅니다. 이 파일들은 어떤 기준으로 나뉘는 걸까요? Next.js 블로그에 게재된 이 글은 Turbopack 인턴십을 진행한 Sam Poder가 청킹(chunking)의 기본 원리부터 Next.js 16.3에서 새로 추가된 청킹 최적화 기능까지를 실제 벤치마크 수치와 함께 정리한 내용입니다.

청크란 무엇인가

이 페이지의 네트워크 탭을 열어보면 이름이 뒤죽박죽인 JavaScript 파일 목록이 보입니다. 그중 하나를 클릭해 압축을 풀면 이런 코드가 나옵니다.

(globalThis.TURBOPACK || (globalThis.TURBOPACK = [])).push([
  "object" == typeof document ? document.currentScript : void 0,
  7284,
  (e) => {
    "use strict";
    function r() {
      for (var e, r, o = 0, t = "", l = arguments.length; o < l; o++) {
        // ...
      }
      return t;
    }
    e.s(["clsx", 0, r, "default", 0, r]);
  },
  395264,
  (e) => {
    "use strict";

//# debugId=e60a5ad0-3ac6-bb3a-e12b-6130e99fb7a6

바로 이게 "청크"입니다. Turbopack은 여러분의 애플리케이션 코드, 의존하는 패키지, 그리고 이 모든 걸 연결하는 런타임을 이런 청크 수십 개로 쪼개서 만듭니다.

"청킹"이란 어떤 코드가 어떤 청크에 들어갈지 결정하는 과정입니다. 청킹 방법은 여러 가지가 있고, 각각 트레이드오프가 있습니다.

세 가지 극단적인 청킹 전략

가장 단순한 방식부터 살펴보겠습니다. 앱이 사용하는 모든 JavaScript를 하나의 청크에 담는 방식입니다.

> 355개 모듈 전체를 1개 청크에 담아 모든 페이지에서 로드 · 1개 청크 · 1.09 MB · app.js

이 청크는 모든 페이지에서 로드됩니다. 모든 페이지가 같은 청크를 공유하니, 첫 로드 이후에는 무조건 캐시 히트입니다. 네비게이션도 빨라지겠죠.

하지만 트레이드오프도 바로 눈에 띕니다. JavaScript가 거의 필요 없는 페이지를 열어도 다른 모든 페이지의 JavaScript까지 함께 다운로드해야 합니다. 사이트가 커질수록 모든 페이지 로드가 점점 무거워지는 구조라 장기적으로 지속 가능하지 않습니다.

그럼 페이지당 하나의 청크로 바꿔보면 어떨까요? 청크가 가벼워지고 불필요한 코드를 절대 과다 전송하지 않게 됩니다. 완벽해 보입니다.

> 페이지당 청크 1개: 같은 355개 모듈을 8개 청크로 쪼갬. 페이지 간 공유되는 코드는 필요한 청크마다 중복 포함됨 · 8개 청크 · 1.20 MB · /docs /learn /blog /showcase /team /governance /telemetry

그런데 이번엔 캐싱을 잃게 됩니다. 모든 페이지가 <Footer />를 쓴다면, 그 코드는 모든 페이지 청크 안에 각각 들어갑니다. 방문자가 페이지 4개를 열면 똑같은 푸터 코드를 4번 다운로드하는 셈이죠.

그렇다면 더 잘게 쪼개야 합니다. 모듈 하나당 청크 하나씩이라면 어떨까요? 아무것도 과다 전송되지 않고, 페이지 간 공유되는 모듈도 딱 한 번만 다운로드될 겁니다.

> 모듈당 청크 1개: 355개의 개별 청크, 각각 한 번만 전송되며 각각 별도의 네트워크 요청으로 처리됨 · 355개 청크 · 1.09 MB

좋습니다, 그런데 사소한 문제가 하나 있습니다. 작은 JavaScript 파일 수백 개에 대한 네트워크 요청이 발생한다는 겁니다. 요청 하나하나에 오버헤드가 붙고, 수백 개가 쌓이면 사이트가 느려집니다. HTTP/2 덕분에 요청 비용이 줄긴 했지만 여전히 오버헤드는 존재합니다. gzip 같은 압축 알고리즘도 파일이 작게 쪼개질수록 성능이 떨어집니다. 압축은 하나의 파일 내에서만 반복 패턴을 찾을 수 있기 때문입니다. 압축 사전(compression dictionary)이 도움이 되긴 하지만 이 문제를 근본적으로 해결하지는 못합니다.

요청 수냐, 코드량이냐

결국 우리가 마주하는 과제는 이렇습니다. 다운로드 용량은 최소화하고, 요청 수도 최소화하고 싶습니다. 그런데 이 두 목표는 서로 충돌합니다. 청크를 적고 크게 만들면 요청 수는 줄지만, 커질수록 페이지 간 재사용성이 떨어집니다.

Turbopack의 해법은 작은 청크들을 더 큰 청크로 병합하는 것입니다. 어려운 부분은 어떤 청크들을, 언제 병합하는 게 정말 이득인지 판단하는 것입니다.

여기서 새로운 용어 하나를 도입해야 합니다. 바로 청크 그룹(chunk group)입니다. 청크 그룹은 함께 로드되는 청크들의 묶음입니다. 예를 들어 /home에서 쓰이는 모든 청크는 하나의 청크 그룹에, /blog에서 쓰이는 청크는 또 다른 청크 그룹에 속합니다.

> 두 개의 청크 그룹, 라우트별로 하나씩. /home 그룹은 청크 3개를 로드하고, /blog 그룹은 청크 2개를 로드함. 하나의 청크는 두 그룹 모두에 속하므로, 이웃 청크와 병합하는 것이 안전하려면 같은 그룹 내에서만 이루어져야 함

청크 그룹은 과다 전송 문제를 해결해줍니다. Turbopack은 같은 그룹 안에 있는 청크끼리만 병합하는데, 어차피 한 그룹 안의 청크는 항상 함께 로드되므로 병합해도 원래 다운로드하지 않던 것을 추가로 다운로드하게 만들지 않습니다.

그렇다면 브라우저에 요청을 과도하게 몰아넣지 않으면서 캐시 히트율을 최적화하려면 어떻게 해야 할까요?

병합이 언제 이득인지 계산하기

이를 파악하기 위해 두 가지 방문 패턴을 상상해봅시다. 하나는 페이지 하나 보고 떠나는 경우, 다른 하나는 페이지를 본 후 다른 페이지로 이동하는 경우입니다. 세 페이지 이상 방문하는 세션에도 같은 분석이 자연스럽게 확장됩니다.

이 두 경우를 놓고 <Footer />와 <VideoPlayer />의 청크를 병합할 때의 비용/이득을 따져보겠습니다. <Footer />의 청크를 A, <VideoPlayer />의 청크를 B라고 부르겠습니다.

A는 모든 페이지에서 쓰이고, B는 홈페이지에서만 쓰입니다. 둘 다 홈페이지 청크 그룹에 속하므로 병합 후보입니다.

방문자가 홈페이지를 로드하고 떠난다면, 병합은 항상 이득입니다. 요청 2개가 1개로 줄고, 어차피 둘 다 필요했던 코드니까요.

두 번째 페이지로 이동한다면 얘기가 달라집니다. 그 페이지가 A와 B 모두를 필요로 하는지, 아니면 하나만 필요로 하는지에 따라 결과가 갈립니다. 예를 들어 홈페이지에서 법률 고지 페이지로 이동한다고 해봅시다. 법률 고지 페이지는 A만 필요하고 B는 필요 없습니다. A와 B가 이미 하나의 파일로 병합되어 있으니, 이 병합 파일은 그 페이지에서 쓸모가 없고, 브라우저는 A만 따로 다시 다운로드하게 됩니다. 결국 방문자는 A를 두 번 다운로드한 셈이 됩니다.

병합이 네비게이션 상황에서도 이득을 보려면, 두 페이지 모두 A와 B를 필요로 해야 합니다. 그래야 병합된 파일이 재사용되어 요청 하나를 절약할 수 있습니다.

가능한 네비게이션 시나리오를 모두 정리하면 다음과 같습니다. 각 행은 2페이지 세션을 나타내며, 첫 페이지가 필요로 하는 것 → 두 번째 페이지가 필요로 하는 것 순으로 표기했습니다. 수치는 A와 B를 병합했을 때 별도로 유지했을 때와 비교해 총 요청 수와 다운로드된 코드량이 어떻게 바뀌는지를 보여줍니다.

네비게이션요청 수 변화다운로드 코드량 변화
A → A00
A → B00
B → B00
A → A + B0+ A
B → A + B0+ B
A + B → A0+ A
A + B → B0+ B
A + B → A + B−10

청크 A와 B의 병합을 검토할 때는, A만 사용하는 청크 그룹, B만 사용하는 청크 그룹, A + B 모두 사용하는 청크 그룹의 개수를 계산합니다. 그리고 각 시나리오가 발생할 확률로 병합의 비용/이득에 가중치를 매깁니다.

마지막으로, 페이지 하나만 방문하는 경우와 두 페이지를 방문하는 경우에도 각각의 확률로 가중치를 부여합니다. 단일 페이지 방문 세션을 2/3, 2페이지 이상 방문 세션을 1/3로 추정합니다.

이 결과가 보여주듯 청킹은 균형점을 찾는 작업입니다. nextjs.org에서는 기본 설정이 병합 없는 경우 대비 요청 수를 절반 이하로 줄이면서도 코드량은 오히려 약간 더 적었습니다. 최대 병합 전략은 요청 수를 더 줄였지만 전체 코드 전송량은 10% 늘었습니다. 다만 만약 네비게이션 횟수가 더 적었다면 최대 병합 쪽이 더 유리했을 겁니다. 그룹 내 모든 청크를 하나의 큰 청크로 합치는 전략은 초기 페이지 로드에서는 이득이지만 장기적으로는 손해였습니다.

Next.js 16.3의 새로운 청킹 기능

청킹의 효과를 제한하는 두 가지 요인이 있습니다. 첫째, 병합은 아무도 방문하기 전인 빌드 타임에 결정되므로 브라우저가 이미 무엇을 캐시하고 있는지에 반응할 수 없습니다. 둘째, 알고리즘은 사람들이 사이트를 어떻게 이동하는지를 추측해야 하는데, 그래서 단일 페이지 방문 비중을 2/3로 가정한 것입니다. Sam Poder는 Turbopack 팀 인턴십 동안 이 두 문제를 해결하는 작업과 함께, 애초에 청크에 들어가는 코드량 자체를 줄이는 작업도 진행했습니다.

더 똑똑한 청크 페칭

앞서 살펴본 표는 병합의 비용을 보여줬습니다. 방문자가 A가 있는 페이지를 로드한 뒤 A + B가 필요한 페이지로 이동하면, 병합 때문에 A를 두 번 다운로드하게 됩니다. 번들러는 빌드 타임에 브라우저가 무엇을 이미 갖고 있는지 알 수 없으니 이 문제를 피할 수 없습니다. 하지만 런타임은 다릅니다.

Next.js 16.3 이상에서 next.config.js의 experimental.turbopackChunking.generateComponentChunks를 활성화하면, Turbopack이 병합된 청크와 함께 병합되지 않은 버전도 함께 생성합니다. 각 병합 청크를 구성하는 항목들과 그중 이미 로드된 항목들을 추적해서, 요청 시점에 더 저렴한 쪽(병합된 청크 전체 또는 누락된 조각만)을 선택할 수 있습니다.

역방향도 마찬가지로 작동합니다. 방문자가 이미 병합된 A + B를 로드한 상태라면, A만 따로 다시 로드하는 것을 건너뛸 수 있습니다.

이렇게 하면 소프트 네비게이션 시 불필요한 코드를 더 적게 로드하면서, 네비게이션 비용 없이 병합의 이점을 그대로 누릴 수 있습니다.

generateComponentChunks: false와 true를 비교한 데모 앱도 공개되어 있습니다.

  • generateComponentChunks: false — component-chunks-demo-off.labs.vercel.dev
  • generateComponentChunks: true — component-chunks-demo-on.labs.vercel.dev

또한 only-if-cached 디렉티브도 실험 중인데, 이는 방문자가 도착했을 때 무엇을 캐시하고 있는지 확인할 수 있게 해줍니다. 이렇게 되면 사이트를 떠났다가 나중에 다시 돌아오는 사람들에게도 같은 개선 효과를 적용할 수 있습니다.

분석 데이터 기반 청킹

청킹 알고리즘에는 사이트에 대한 여러 가정이 들어갑니다. 예를 들어 2/3라는 가중치는 추정치입니다. 많은 사이트에 통하는 합리적인 기본값이긴 하지만, 특정 사이트에 딱 맞는 값은 아닐 수 있습니다. 만약 여러분의 사이트에서 사람들이 실제로 어떻게 이동하는지 알고 있다면, 이를 직접 알려줄 수 있습니다.

next.config.js의 experimental.turbopackChunking 아래에 다음 옵션들을 설정할 수 있습니다.

  • firstPageLoadPriority: 단일 페이지 케이스와 두 페이지 케이스 간 가중치를 조정합니다. 값(0~1)이 높을수록 초기 로드 속도를 우선시하며, 그만큼 네비게이션 성능을 희생할 수 있습니다. 이탈률(bounce rate)이 시작점으로 적당한 값입니다. 기본값은 0.67입니다.
  • priorityRoutes: 로드 속도가 가장 중요한 페이지 목록입니다. 이 라우트들에서는 청크를 더 적극적으로 병합합니다.
  • clusters: 정규식 배열로 정의된, 자주 함께 방문되는 라우트 그룹입니다. 클러스터 내부에서는 겹치는 청크를 더 적극적으로 병합합니다. 반대로 클러스터 안에 A만 쓰는 페이지, B만 쓰는 페이지, A와 B를 모두 쓰는 페이지가 섞여 있다면 병합을 덜 하게 됩니다.

더 작고 더 적은 청크

지금까지는 코드를 어떻게 묶을지에 대한 이야기였다면, 마지막으로 소개할 기능들은 애초에 전송하는 코드량 자체를 줄이는 것에 관한 것입니다. Sam Poder가 이를 위해 작업한 내용은 다음과 같습니다.

  • CJS 모듈 트리 셰이킹: 기존에는 ESM에서만 트리 셰이킹을 지원해서, CJS 모듈의 미사용 import/export가 클라이언트로 그대로 전송되고 있었습니다. experimental.turbopackCjsTreeShaking으로 활성화할 수 있으며, 향후 Next.js 버전에서는 기본 활성화될 예정입니다.
  • 또한 분석 및 트리 셰이킹이 가능한 ESM 모듈의 범위도 확장했습니다. 여기에는 동적 import 안에서의 배럴 파일(barrel file) 지원 개선도 포함됩니다.
  • 공유 Turbopack 런타임: 페이지별 런타임 청크들을 하나의 런타임 청크로 대체합니다. experimental.turbopackSharedRuntime으로 활성화할 수 있고, 첫 로드 이후의 모든 네비게이션에서 블로킹 요청 1개와 약 10KB의 클라이언트 측 JavaScript를 절약해줍니다. 이 기능도 향후 기본 활성화될 예정입니다.
  • 더 가벼워진 기본 런타임: 런타임이 이제 기본적으로 WebAssembly와 Web Worker 코드를 포함하지 않습니다. 해당 모듈을 실제로 사용할 때만 이를 감지해서 로딩 코드를 삽입합니다.

이 새로운 기능들은 Next.js 16.3 이상 버전에서 사용해볼 수 있습니다. 청킹(CSS 청킹 포함)에 대해 더 깊이 알고 싶다면 Tobias의 청킹 트레이드오프와 제약사항에 관한 최근 발표도 참고할 만합니다.

정리

  • 청킹은 요청 수 최소화와 코드 전송량 최소화라는 서로 충돌하는 목표 사이의 균형점을 찾는 문제입니다. 청크 하나로 합치면 캐시 효율은 좋지만 불필요한 코드가 과다 전송되고, 모듈마다 청크를 나누면 낭비는 없지만 요청 수가 폭증합니다.
  • Turbopack은 "청크 그룹" 개념을 도입해 같은 그룹(같은 페이지에서 함께 로드되는 청크들) 안에서만 병합을 수행하며, 두 페이지 방문 시나리오별 확률(단일 페이지 2/3, 다중 페이지 1/3)을 가중치로 병합 여부를 판단합니다.
  • nextjs.org 실측에서 Turbopack 기본 설정은 병합 없는 경우 대비 요청 수를 76개→24개로 줄이면서도 전체 코드량은 오히려 소폭 줄었습니다. 반면 그룹 내 완전 병합은 요청 수를 6개까지 줄였지만 전체 전송량이 10% 늘어, 상황에 따라 최적 전략이 달라짐을 보여줍니다.
  • Next.js 16.3에서는 generateComponentChunks(런타임에 병합/비병합 청크 중 더 저렴한 쪽 선택), firstPageLoadPriority·priorityRoutes·clusters(사이트별 실제 트래픽 패턴 반영), CJS 트리 셰이킹, 공유 런타임, 경
