15:T26e5,<p>CSS로 레이아웃을 만들다 보면 위아래 패딩 값을 똑같이 줬는데도 시각적으로 균형이 안 맞는 경험, 다들 한 번쯤 해보셨을 겁니다. 이건 CSS의 버그가 아니라 폰트 메트릭 자체의 특성 때문에 생기는 현상인데요, 최근 Firefox가 <code>text-box-trim</code>을 지원하면서 드디어 모든 주요 브라우저 엔진에서 이 문제를 CSS 표준 기능으로 해결할 수 있게 됐습니다. 이번 글에서는 이 오래된 문제의 원인과 <code>text-box-trim</code>이 어떻게 작동하는지 정리해보겠습니다.</p>
<h3>왜 위아래 여백이 다르게 느껴질까</h3>
<p>버튼이나 텍스트 박스에 상하 패딩을 동일하게 줬는데도 아래쪽이 더 넓어 보이는 경우가 있습니다. 이는 폰트가 만들어질 때 악센트 기호가 들어갈 공간을 위쪽에, 디센더(g, y, p처럼 베이스라인 아래로 내려가는 부분)가 들어갈 공간을 아래쪽에 미리 확보해두기 때문입니다. 이 여유 공간은 폰트 파일 자체에 내장돼 있어서, 실제 텍스트의 시각적 높이와 요소가 차지하는 박스의 높이 사이에 항상 차이가 생깁니다.</p>
<p>문제는 이 여유 공간의 크기가 폰트마다 다르다는 점입니다. 예를 들어 Josephine Sans 같은 폰트는 전체적으로 텍스트가 위로 쏠려 보이는 특징이 있어서, 위아래 패딩이 같아도 아래쪽 여백이 유독 커 보입니다. 그래서 특정 폰트에 맞춰 매직 넘버(임의로 조정한 픽셀 값)로 여백을 딱 맞춰놔도, 폰트 패밀리를 바꾸는 순간 다시 어긋나 버립니다.</p>
<p>이 현상은 패딩뿐 아니라 <code>gap</code>으로 요소 간 간격을 주는 레이아웃에서도 똑같이 나타납니다. <code>gap</code> 값을 정확히 지정했는데도 실제로는 그보다 넓은 간격처럼 보이는데, 텍스트를 드래그해서 선택해보면 실제 텍스트 영역 바깥에 폰트 메트릭이 만든 여백이 존재한다는 걸 확인할 수 있습니다.</p>
<h3>디자이너와의 스펙 불일치, 원인은 Figma의 &quot;Vertical Trim&quot;</h3>
<p>이 문제가 더 골치 아파지는 이유는 Figma를 쓰는 디자이너들이 이미 이 여백을 눈치채고 있다는 점입니다. Figma에는 텍스트 설정에 <strong>Vertical Trim</strong>이라는 옵션이 있는데, 이걸 켜면 폰트 메트릭이 만드는 상하 여유 공간을 잘라내고 텍스트의 실제 캡 높이와 베이스라인에 딱 맞춰 박스를 그려줍니다. 그래서 디자인 파일에서는 버튼이나 텍스트 주변 여백이 완벽하게 균등해 보이는 겁니다.</p>
<p>그런데 개발자가 디자인 파일에 적힌 값 그대로 CSS 패딩을 적용하면, 디자이너 입장에서는 &quot;값은 똑같은데 왜 여백이 안 맞느냐&quot;는 이야기가 나오게 됩니다. 원인은 Figma가 Vertical Trim으로 폰트 메트릭 여백을 이미 제거한 상태에서 수치를 뽑았기 때문이고, CSS는 지금까지 그런 트리밍 기능이 없었기 때문입니다.</p>
<h3>text-box-trim: 폰트 메트릭 여백을 CSS에서 직접 잘라내기</h3>
<p>이제 CSS에 <code>text-box-trim</code>이라는 속성이 생기면서 Figma의 Vertical Trim과 동일한 작업을 브라우저에서 할 수 있게 됐습니다. 다만 <code>text-box-trim</code>만 선언한다고 바로 효과가 나타나지는 않습니다. 이 속성은 &quot;어느 쪽을 트리밍할지&quot;를 지정하는 역할이고, 실제로 어디까지 잘라낼지는 <code>text-box-edge</code> 속성으로 정해줘야 합니다.</p>
<p><code>text-box-edge</code>의 기본값은 <code>auto</code>인데, 이건 기존 웹사이트들의 레이아웃이 갑자기 깨지지 않도록 지금까지의 동작(즉 폰트 메트릭 여백을 그대로 두는 것)을 유지하기 위한 값입니다. <code>auto</code>는 사실상 상하 모두 <code>text</code> 값을 준 것과 동일합니다.</p>
<pre><code class="language-css">/* 기본값과 동일 - 여백 그대로 유지 */
text-box-trim: trim-both;
text-box-edge: text text;</code></pre>
<p>여기서 상단에 사용할 수 있는 값 중 하나가 <code>cap</code>입니다. <code>cap</code>을 지정하면 박스 상단이 텍스트의 캡 높이(대문자 높이)에 정확히 맞춰지면서 위쪽 여유 공간이 사라집니다. 하단은 선택지가 하나뿐인데, 바로 <code>alphabetic</code>입니다. 이는 알파벳 베이스라인에 박스 하단을 맞추는 값입니다. (참고로 영상 제작자는 왜 <code>baseline</code>이 아니라 <code>alphabetic</code>이라는 이름이 채택됐는지 의아해했는데, 세로쓰기 모드에서는 베이스라인 개념이 다르게 적용되기 때문일 수 있다고 추측하고 있습니다.)</p>
<pre><code class="language-css">.button {
  text-box-trim: trim-both;
  text-box-edge: cap alphabetic;
}</code></pre>
<p>이렇게 하면 박스가 텍스트의 캡 높이부터 알파벳 베이스라인까지 딱 맞게 트리밍되어, 상하 여백이 폰트와 무관하게 항상 일관되게 유지됩니다.</p>
<h3>Figma보다 선택지가 많다: x-height</h3>
<p>흥미로운 점은 CSS의 <code>text-box-edge</code>가 Figma의 Vertical Trim보다 더 세밀한 옵션을 제공한다는 겁니다. 상단 값으로 <code>cap</code> 대신 <code>x-height</code>를 쓸 수도 있는데, 이는 소문자 높이(엑스하이트)에 맞춰 트리밍하는 옵션입니다. 자주 쓰이는 옵션은 아니지만 특정 디자인 상황에서 유용할 수 있습니다. 대부분의 경우는 <code>cap</code>과 <code>alphabetic</code> 조합을 쓰게 될 것으로 보입니다.</p>
<p>또한 상하를 모두 트리밍하지 않고 한쪽만 트리밍하고 싶다면 <code>trim-start</code>(위쪽만) 또는 <code>trim-end</code>(아래쪽만)를 사용할 수도 있습니다. 하지만 대부분은 양쪽 다 트리밍하는 <code>trim-both</code>를 쓰게 될 텐데, 이 경우에는 축약형인 <code>text-box</code> 속성을 사용하는 게 더 간편합니다.</p>
<pre><code class="language-css">.button {
  text-box: trim-both cap alphabetic;
}</code></pre>
<h3>실무에서 주의할 점: 기존 패딩 값이 다 어긋난다</h3>
<p><code>text-box-trim</code>을 도입할 때 반드시 기억해야 할 점이 있습니다. 지금까지 써오던 &quot;익숙한 패딩 수치&quot;가 더 이상 맞지 않는다는 겁니다. 폰트 메트릭이 만들던 여유 공간이 사라지기 때문에, 예전과 똑같은 패딩 값을 넣으면 위아래에 패딩을 아예 안 준 것처럼 보이게 됩니다. 즉, 트리밍을 적용한 뒤에는 기존보다 더 큰 패딩 숫자를 새로 찾아서 써야 합니다. 처음에는 적응이 좀 필요한 부분이지만, 대신 얻는 이득은 확실합니다 — 어떤 폰트를 쓰든 상관없이 캡 높이와 베이스라인 기준으로 항상 동일한 간격이 만들어지기 때문에, 폰트가 바뀌어도 여백이 깨지지 않습니다.</p>
<p><code>gap</code>을 쓰는 레이아웃에서도 마찬가지입니다. 트리밍을 적용하면 간격이 갑자기 사라진 것처럼 보이는데, 실제로는 디센더 등이 그 공간을 파고들어서 시각적으로 좁아 보이는 것뿐입니다. 개발자 도구의 레이아웃 시각화 기능을 켜보면 여전히 지정한 간격이 존재한다는 걸 확인할 수 있습니다. 이 경우도 마찬가지로, 트리밍 전보다 더 큰 gap 값을 새로 설정해줘야 실제로 보기 좋은 간격이 나옵니다.</p>
<h3>언제 쓰는 게 좋을까</h3>
<p>디자이너가 명확하게 특정 여백 수치를 요구하는데 실제 렌더링에서 그 수치가 맞지 않는 상황이 아니라면, 여러 줄로 이어지는 본문 텍스트 같은 곳까지 굳이 트리밍을 적용할 필요는 없어 보입니다. 반면 버튼처럼 한 줄짜리 텍스트에 패딩을 주는 요소들, 즉 한 줄(one-liner) 콘텐츠에는 이 속성이 특히 유용합니다. 지금까지 라인 하이트를 1로 맞추거나 매직 넘버로 센터 정렬을 억지로 맞추던 방식 대신, <code>text-box-trim</code>을 선언하는 것만으로 그 문제를 근본적으로 해결할 수 있기 때문입니다.</p>
<h3>정리</h3>
<ul>
<li>폰트는 악센트나 디센더를 위한 여유 공간을 상하에 내장하고 있어서, 동일한 패딩값을 줘도 시각적으로 위아래 여백이 다르게 느껴지고 이 차이는 폰트마다 다릅니다. <code>gap</code>을 쓰는 레이아웃에서도 같은 문제가 발생합니다.</li>
<li>Figma의 Vertical Trim 옵션이 이 여백을 이미 제거한 값을 보여주기 때문에, 디자이너가 전달한 스펙과 개발자가 그대로 구현한 CSS 결과물 사이에 괴리가 생기는 경우가 많았습니다.</li>
<li><code>text-box-trim</code>(과 <code>text-box-edge</code>, 축약형 <code>text-box</code>)이 이제 모든 주요 브라우저 엔진(Firefox 포함)에 탑재되면서, CSS에서 직접 폰트 메트릭 여백을 잘라낼 수 있게 됐습니다. <code>text-box: trim-both cap alphabetic;</code> 형태로 상단은 캡 높이, 하단은 알파벳 베이스라인에 맞춰 트리밍합니다.</li>
<li>상단에는 <code>cap</code> 외에 <code>x-height</code>도 선택 가능해 Figma보다 세밀한 조정이 가능하며, <code>trim-start</code>/<code>trim-end</code>로 한쪽만 트리밍할 수도 있습니다.</li>
