<p>&quot;청킹&quot;이란 어떤 코드를 어떤 청크에 담을지 결정하는 과정입니다. 이 문제를 푸는 방법은 다양하고, 각 방법마다 트레이드오프가 존재합니다.</p>
<h3>가장 단순한 접근: 청크 하나로 몰아넣기</h3>
<p>가장 간단한 방법부터 시작해보겠습니다. 앱이 사용하는 모든 JavaScript를 청크 하나에 담는 방식입니다. 355개 모듈이 전부 하나의 청크(1.09 MB)에 들어가고, 이 청크는 모든 페이지에서 로드됩니다.</p>
<p>이렇게 하면 모든 페이지가 같은 청크를 공유하므로, 첫 로드 이후의 모든 페이지 이동은 캐시 히트가 됩니다. 내비게이션은 무척 빨라지겠죠.</p>
<p>하지만 트레이드오프도 명확합니다. JavaScript가 거의 필요 없는 페이지를 열어도 다른 모든 페이지의 코드를 함께 내려받아야 합니다. 사이트가 커질수록 페이지 로드는 점점 무거워집니다. 장기적으로는 지속 가능한 방식이 아닙니다.</p>
<h3>페이지당 청크 하나</h3>
<p>대안으로 페이지마다 청크를 하나씩 만드는 방법을 생각해볼 수 있습니다. 이렇게 하면 청크가 슬림하게 유지되고, 필요 이상의 코드를 내려받는 일도 없어집니다. 같은 355개 모듈이 8개 청크(1.20 MB)로 나뉘는데, 페이지 간에 공유되는 코드는 필요한 청크마다 중복으로 들어갑니다.</p>
<p>문제는 캐싱 효과를 잃는다는 점입니다. 모든 페이지에서 <code>&lt;Footer /&gt;</code>를 사용한다면, 그 코드는 모든 페이지의 청크 안에 각각 포함됩니다. 방문자가 페이지 네 개를 열면 같은 Footer 코드를 네 번 내려받게 되는 셈입니다.</p>
<h3>모듈당 청크 하나</h3>
<p>그렇다면 더 세밀하게, 모듈 하나마다 청크 하나씩 만들면 어떨까요? 이렇게 하면 필요 이상으로 코드를 내려받는 일도 없고, 페이지 간에 공유되는 모듈도 딱 한 번만 다운로드됩니다. 355개의 모듈이 355개의 개별 청크(1.09 MB)가 되고, 각각이 별도의 네트워크 요청이 됩니다.</p>
<p>좋아 보이지만 작은(?) 문제가 하나 있습니다. 작은 JavaScript 파일 수백 개에 대해 수백 번의 네트워크 요청이 발생한다는 점입니다. 요청 하나하나에는 오버헤드가 붙고, 이게 수백 개가 되면 사이트 속도가 느려집니다. HTTP/2 덕분에 요청 비용이 예전보다 저렴해졌다고는 해도, 여전히 요청마다 오버헤드는 존재합니다. gzip 같은 압축 알고리즘도 작은 파일이 많아지면 성능이 떨어지는데, 반복 패턴을 파일 하나 안에서만 찾을 수 있기 때문입니다. 압축 사전(compression dictionary)이 도움이 되긴 하지만 이 문제를 근본적으로 해결하지는 못합니다.</p>
<h3>요청 수와 다운로드 용량, 둘 다 잡을 순 없을까</h3>
<p>결국 우리에게 남은 숙제는 이렇습니다. 다운로드 용량은 최소로, 요청 수도 최소로 만들고 싶은데, 이 두 목표는 서로 충돌합니다. 청크를 크고 적게 만들면 요청 수는 줄지만, 커질수록 페이지 간 재사용성은 떨어집니다.</p>
<p>Turbopack의 해법은 작은 청크들을 더 큰 청크로 병합하는 것입니다. 어려운 부분은 어떤 청크들을 병합할지, 그리고 언제 병합이 실제로 이득인지를 판단하는 것이죠.</p>
<p>이를 위해 &quot;청크 그룹(chunk group)&quot;이라는 개념이 필요합니다. 청크 그룹이란 함께 로드되는 청크들의 모음입니다. 예를 들어 <code>/home</code>에서 쓰이는 모든 청크는 하나의 청크 그룹을 이루고, <code>/blog</code>는 또 다른 청크 그룹을 이룹니다. <code>/home</code>의 청크 그룹은 청크 3개를 로드하고, <code>/blog</code>의 청크 그룹은 2개를 로드합니다. 이때 한 청크가 두 그룹에 모두 속해 있다면, 그 청크를 이웃과 병합하는 것은 같은 그룹 안에서만 안전합니다.</p>
<p>청크 그룹은 &quot;필요 이상으로 코드를 내려받는&quot; 문제를 해결해줍니다. Turbopack은 같은 그룹에 속한 청크들만 병합하는데, 어차피 한 그룹의 청크들은 항상 함께 로드되므로, 병합한다고 해서 원래 페이지가 다운로드하지 않던 것을 추가로 다운로드하게 만들지는 않습니다.</p>
<h3>병합의 손익을 어떻게 계산할까</h3>
<p>그렇다면 요청 폭주를 피하면서 캐시 히트율을 최적화하려면 어떻게 해야 할까요? 이를 파악하기 위해 두 가지 방문 패턴을 상상해봅시다. 하나는 페이지 하나만 보고 떠나는 경우, 다른 하나는 페이지를 본 뒤 다른 페이지로 이동하는 경우입니다. (세 페이지 이상의 세션에도 같은 분석이 자연스럽게 확장됩니다.)</p>
<p><code>&lt;Footer /&gt;</code>의 청크를 A, <code>&lt;VideoPlayer /&gt;</code>의 청크를 B라고 해봅시다. A는 모든 페이지에서 쓰이고, B는 홈페이지에서만 쓰입니다. 둘 다 홈페이지의 청크 그룹에 속하므로 병합 후보가 됩니다.</p>
<p>방문자가 홈페이지만 열고 떠난다면 병합은 항상 이득입니다. 어차피 둘 다 필요했던 것을, 요청 2번 대신 1번으로 끝낼 수 있으니까요.</p>
<p>반면 두 번째 페이지로 이동한다면 이야기가 달라집니다. 예를 들어 홈페이지에서 법적 고지(legal) 페이지로 이동한다고 해봅시다. 법적 고지 페이지는 A는 필요하지만 B는 필요 없습니다. A와 B가 하나의 파일로 병합되어 있었으니, 이 병합된 파일은 이 페이지에서는 쓸모가 없고, 브라우저는 A를 따로 다시 다운로드해야 합니다. 결과적으로 방문자는 A를 두 번 다운로드하게 됩니다.</p>
<p>즉 병합이 내비게이션을 거쳐서도 이득을 보려면, 두 페이지 모두 A와 B를 둘 다 필요로 해야 합니다. 그래야 병합된 파일이 재사용되고 요청 하나를 아낄 수 있습니다.</p>
<p>가능한 다른 내비게이션 시나리오들을 정리하면 다음과 같습니다. 각 행은 2페이지 세션을 나타내며, &quot;첫 페이지가 필요로 하는 것 → 두 번째 페이지가 필요로 하는 것&quot; 형식입니다. 숫자는 A와 B를 병합했을 때 전체 세션의 요청 수와 다운로드 용량이 어떻게 바뀌는지(분리했을 때 대비)를 나타냅니다.</p>
<div class="table-wrapper"><table><thead><tr><th>내비게이션</th><th>요청 수 변화</th><th>다운로드 용량 변화</th></tr></thead><tbody><tr><td>A → A</td><td>0</td><td>0</td></tr><tr><td>A → B</td><td>0</td><td>0</td></tr><tr><td>B → B</td><td>0</td><td>0</td></tr><tr><td>A → A + B</td><td>0</td><td>+ A</td></tr><tr><td>B → A + B</td><td>0</td><td>+ B</td></tr><tr><td>A + B → A</td><td>0</td><td>+ A</td></tr><tr><td>A + B → B</td><td>0</td><td>+ B</td></tr><tr><td>A + B → A + B</td><td>−1</td><td>0</td></tr></tbody></table></div>
<p>A와 B의 병합을 검토할 때, A만 사용하는 청크 그룹, B만 사용하는 청크 그룹, A+B를 모두 사용하는 청크 그룹의 개수를 각각 세고, 각 시나리오의 발생 확률로 가중치를 부여해 병합의 손익을 계산합니다.</p>
<p>마지막으로 한 페이지만 방문한 경우와 두 페이지 이상 방문한 경우도 각각의 확률로 가중치를 매깁니다. Turbopack은 세션의 2/3는 단일 페이지 방문, 1/3은 두 페이지 이상 방문이라고 추정합니다.</p>
<h3>세 가지 청킹 전략 비교: nextjs.org 실측 데이터</h3>
<p>앞서 다룬 세 가지 방식을 실제로 비교해보겠습니다. &quot;병합 안 함&quot;, &quot;Turbopack 기본값&quot;, &quot;그룹 내 전체 병합&quot; 세 가지 설정으로 nextjs.org를 방문해, 동일한 순서로 내비게이션을 진행하며 요청 수와 클라이언트 측 JavaScript 다운로드 용량을 측정했습니다.</p>

<p>결과에서 보이듯, 청킹은 저울질의 연속입니다. nextjs.org에서는 기본값 설정이 &quot;병합 안 함&quot; 대비 요청 수를 절반 이하로 줄이면서 다운로드 용량도 약간 더 줄였습니다. 반면 &quot;그룹당 청크 1개&quot;로 최대한 병합했을 때는 요청 수는 더 줄었지만 전체 다운로드 용량은 10% 더 늘어났습니다. 다만 내비게이션 횟수가 더 적었다면 최대 병합 쪽이 더 유리했을 것입니다. 그룹 내 모든 청크를 하나로 합치는 방식은 최초 페이지 로드에서는 이득이었지만, 장기적으로는 비용이 더 컸습니다.</p>
<h3>Next.js 16.3의 새로운 청킹 기능들</h3>
<p>청킹의 효과를 제한하는 요소는 크게 두 가지입니다. 첫째, 병합은 빌드 타임에 결정되기 때문에 누가 방문하기도 전에 이뤄지고, 그래서 브라우저가 이미 캐시해둔 것을 반영할 수 없습니다. 둘째, 알고리즘은 사람들이 사이트를 어떻게 돌아다니는지 추측할 수밖에 없는데, 그래서 단일 페이지 방문에 2/3라는 가중치를 부여한 것도 결국 추정치일 뿐입니다. Turbopack 팀 인턴십 기간 동안 이 두 가지 문제와, 애초에 청크에 담기는 코드의 양을 줄이는 작업을 진행했습니다.</p>
<h4>더 똑똑한 청크 페칭</h4>
<p>앞선 표에서 봤듯, A가 있는 페이지를 로드한 뒤 A+B가 있는 페이지로 이동하면 병합 때문에 A를 두 번 다운로드하게 됩니다. 번들러는 빌드 타임에 브라우저가 이미 무엇을 가지고 있는지 알 수 없기 때문에 이 문제를 피할 수 없습니다. 하지만 런타임은 알 수 있습니다.</p>
<p>Next.js 16.3 이상에서 <code>next.config.js</code>의 <code>experimental.turbopackChunking.generateComponentChunks</code>를 활성화하면, Turbopack은 병합된 청크와 함께 병합되지 않은 버전의 청크도 함께 생성합니다. 각 병합된 청크를 구성하는 항목들과 그중 이미 로드된 항목이 무엇인지 추적하기 때문에, 요청 시점에 병합된 청크와 누락된 조각만 가져오는 것 중 더 저렴한 쪽을 선택할 수 있습니다.</p>
<p>반대의 경우도 마찬가지입니다. 방문자가 이미 병합된 A+B를 로드한 상태라면, A만 따로 다시 로드하는 일을 건너뛸 수 있습니다.</p>
<p>이렇게 하면 소프트 내비게이션에서 불필요한 코드를 덜 로드하게 되고, 내비게이션 비용 없이 병합의 이점만 취할 수 있습니다.</p>
<p>또한 <code>only-if-cached</code> 디렉티브를 활용한 실험도 진행 중인데, 방문자가 사이트에 도착했을 때 이미 캐시된 것이 무엇인지 확인할 수 있게 해줍니다. 이렇게 되면 사이트를 떠났다가 나중에 다시 돌아오는 방문자에게도 같은 개선 효과를 확장할 수 있습니다.</p>
<h4>애널리틱스 기반 청킹</h4>
<p>청킹 알고리즘에는 여러 가정이 들어가 있습니다. 예를 들어 2/3라는 가중치도 결국 추측입니다. 많은 사이트에 대해 합리적인 기본값이긴 하지만, 특정 사이트에 딱 맞는 값이라는 보장은 없습니다. 만약 여러분이 자신의 사이트에서 방문자가 실제로 어떻게 이동하는지 알고 있다면, 그 정보를 Turbopack에 알려줄 수 있습니다.</p>
<p><code>next.config.js</code>의 <code>experimental.turbopackChunking</code> 아래에 다음 옵션들을 설정할 수 있습니다.</p>
<ul>
<li><strong><code>firstPageLoadPriority</code></strong>: 단일 페이지 방문과 2페이지 방문 사이의 가중치를 조정합니다. 0에서 1 사이 값으로, 값이 높을수록 내비게이션 비용을 감수하더라도 최초 로드 속도를 우선시합니다. 이탈률(bounce rate)을 초깃값으로 삼는 것이 합리적이며, 기본값은 0.67입니다.</li>
<li><strong><code>priorityRoutes</code></strong>: 로드 속도가 가장 중요한 페이지 목록입니다. 이 라우트들에서는 더 적극적으로 청크를 병합합니다.</li>
<li><strong><code>clusters</code></strong>: 자주 함께 방문되는 라우트들의 그룹으로, 각 그룹은 정규식 배열로 정의됩니다. 클러스터 내부에서 겹치는 청크는 더 적극적으로 병합합니다. 다만 클러스터 안에 A만 쓰는 페이지, B만 쓰는 페이지, 둘 다 쓰는 페이지가 섞여 있다면 병합을 덜 하게 됩니다.</li>
</ul>
<h4>청크를 더 작고 더 적게 만들기</h4>
<p>지금까지는 코드를 &quot;어떻게 묶을지&quot;에 관한 이야기였다면, 마지막 기능들은 애초에 &quot;얼마나 적게 실어 보낼지&quot;에 관한 것입니다. 이번 작업에서 다음 기능들을 만들었습니다.</p>
<ul>
<li><strong>CJS 모듈 트리 쉐이킹</strong>: 기존에는 ESM에 대해서만 트리 쉐이킹을 지원했기 때문에, CJS 모듈의 사용하지 않는 import/export도 클라이언트로 전송되고 있었습니다. <code>experimental.turbopackCjsTreeShaking</code>으로 활성화할 수 있으며, 향후 버전에서는 기본으로 켜질 예정입니다. 또한 분석하고 트리 쉐이킹할 수 있는 ESM 모듈의 범위도 넓혔는데, 동적 import 안의 배럴 파일(barrel file) 지원 개선도 포함됩니다.</li>
<li><strong>공유 Turbopack 런타임</strong>: 페이지별로 존재하던 런타임 청크를 런타임 청크 하나로 대체합니다. <code>experimental.turbopackSharedRuntime</code>으로 활성화할 수 있으며, 최초 로드 이후의 모든 내비게이션에서 블로킹 요청 하나와 클라이언트 측 JavaScript 약 10KB를 절약합니다. 이 역시 향후 기본값이 될 예정입니다.</li>
<li><strong>더 가벼운 기본 런타임</strong>: 런타임은 이제 기본적으로 WebAssembly와 Web Worker 관련 코드를 포함하지 않습니다. 해당 모듈을 실제로 사용하는 경우에만 감지해서 로딩 코드를 삽입합니다.</li>
</ul>
<p>이 기능들은 Next.js 16.3 이상에서 사용해볼 수 있습니다. 청킹(CSS 청킹 포함)의 트레이드오프와 제약에 대해 더 알고 싶다면 Tobias의 최근 발표도 참고할 만합니다.</p>
<h3>정리</h3>
<ul>
<li>청킹의 본질은 요청 수(오버헤드)와 다운로드 용량(중복 전송) 사이의 트레이드오프를 최적화하는 문제입니다. 청크를 하나로 합치면 캐시 효율은 좋지만 불필요한 코드가 함께 실리고, 모듈마다 청크를 나누면 낭비는 없지만 요청 수가 폭증합니다.</li>
<li>Turbopack은 &quot;청크 그룹&quot; 단위로 안전하게 병합할 수 있는 청크를 판단하고, A/B 두 청크의 병합이 실제 내비게이션 시나리오에서 이득인지 확률적으로 계산해 병합 여부를 결정합니다.</li>
<li>nextjs.org 실측 결과, Turbopack 기본 설정은 &quot;병합 안 함&quot; 대비 요청 수를 절반 이하로 줄이면서 다운로드 용량도 소폭 줄였지만, 그룹 내 완전 병합은 요청은 더 줄어도 전체 다운로드 용량이 10% 늘어나는 등 상황에 따라 최적 전략이 달라집니다.</li>
<li>Next.js 16.3부터 <code>generateComponentChunks</code>(런타임에서 병합/비병합 청크 중 더 저렴한 쪽 선택), <code>firstPageLoadPriority</code>/<code>priorityRoutes</code>/<code>clusters</code>(실제 트래픽 패턴 기반 청킹 튜닝), CJS 트리 쉐이킹·공유 런타임·경량 기본 런타임 같은 실험적 기능이 추가되어, 개발자가 자기 사이트의 방문 패턴에 맞게 청킹 전략을 세밀하게 조정할 수 있게 됐습니다.</li>
<li>실무에서는 우선 <code>experimental.turbopackChunking</code>과 <code>turbopackSharedRuntime</code>, <code>turbopackCjsTreeShaking</code> 같은 실험 플래그를 켜보고, 실제 애널리틱스 데이터를 기반으로 <code>priorityRoutes</code>나 <code>clusters</code>를 조정해가며 자신의 트래픽 패턴에 맞는 청킹 전략을 찾아보는 것이 좋습니다.</li>
