Shopify는 왜 React Native를 버리고 네이티브로 돌아가나: AI가 바꾼 크로스플랫폼의 계산법
via Theo (t3.gg)
▶영상frontend

Shopify가 React Native를 떠나 Swift/Kotlin 네이티브로 회귀한다고 발표했습니다. 이유는 코딩 에이전트(LLM)의 발전으로 '기능을 두 번 만드는' 비용이 2020년 대비 크게 줄어들면서, React Native 도입의 핵심 전제였던 코드 공유의 이점이 상대적으로 약해졌다는 것입니다. Theo는 이 논리가 React Native의 진짜 강점을 놓치고 있다고 지적하고, React Native 베테랑 Jamon은 OTA 업데이트 미언급과 Expo 미채택 문제를 짚습니다. Shopify의 핵심 오픈소스 라이브러리인 React Native Skia는 담당자가 포크해 계속 관리하기로 했습니다.

💡
크로스플랫폼 프레임워크 도입의 핵심 명분이었던 '개발 비용 절감'이 AI 코딩 에이전트로 인해 근본적으로 흔들리고 있다는 사실은, React Native뿐 아니라 Flutter 등 다른 크로스플랫폼 기술 스택 선택 기준에도 영향을 미칠 중요한 신호입니다.
🎬
React 훅 하나로 웹부터 터미널까지: 렌더러의 역할을 실험으로 증명하다
via Traversy Media
▶영상frontend

Traversy Media가 60줄짜리 useTimer 훅 하나를 수정 없이 웹, Electron 데스크톱, React Native 모바일, 터미널(Ink) 등 10개의 서로 다른 React 애플리케이션에 이식하는 실험을 진행했습니다. 이를 통해 React는 상태 변화만 계산할 뿐 실제 화면 반영은 ReactDOM, React Native 렌더러, Ink 같은 별도의 렌더러가 담당한다는 사실을 명확히 보여줍니다. 웹과 Electron은 둘 다 ReactDOM을 쓰지만, React Native와 Ink는 완전히 다른 렌더러와 컴포넌트 체계를 사용합니다.

💡
비즈니스 로직과 렌더링을 분리하는 습관을 들이면 웹, 데스크톱, 모바일 등 다중 플랫폼을 지원하는 프로젝트에서 코드 재사용성을 크게 높일 수 있으며, React와 렌더러의 관계를 정확히 이해하면 새로운 렌더링 타깃(터미널, VR 등)에도 유연하게 대응할 수 있습니다.

via Kevin Powell (CSS)
▶영상frontend
