13:T253e,<h2>Shopify가 React Native를 떠나는 이유, 그리고 이것이 의미하는 것</h2>
<p>Shopify가 React Native를 떠나 다시 네이티브(Swift/Kotlin)로 돌아가겠다고 발표했습니다. 이 소식이 왜 특별히 충격적인지 이해하려면 배경을 좀 알아야 하는데요. Theo는 React Native의 오랜 지지자였고, 과거 Airbnb의 &quot;React Native를 떠난 이유&quot; 아티클이 근거 없이 React Native의 발목을 잡았다는 걸 지적한 영상으로 유명해진 사람입니다. 그리고 그 반대편에서 React Native의 성공 사례로 항상 언급되던 게 바로 Shopify였습니다. Shopify는 React Native로 놀라운 성과를 냈고, 심지어 안드로이드 POS 앱에서는 네이티브 버전보다 더 나은 성능을 보여주기도 했습니다. 그런 Shopify가 이제 방향을 바꾼다는 겁니다. 이 글에서는 Shopify가 공식적으로 밝힌 이유와 그 이면에 숨겨진 맥락, 그리고 이것이 React Native와 모바일 개발 전반에 어떤 의미를 갖는지 짚어봅니다.</p>
<h3>Shopify의 공식 입장</h3>
<p>Shopify는 자사 블로그를 통해 &quot;네이티브가 이제 Shopify 모바일의 미래&quot;라고 선언했습니다. 요지는 이렇습니다. &quot;코딩 에이전트가 모바일 앱을 만드는 비용 구조를 두 번이나 바꿔놓았다&quot;는 것인데요.</p>
<p>Shopify는 2020년에 React Native로 전면 전환하는 베팅을 했고, 이 베팅은 성공적이었다고 스스로 평가합니다. 기능을 한 번만 만들면 됐고, 모바일 배경이 없는 개발자도 앱에 기여할 수 있었으며, 두 플랫폼 간 기능 격차를 쫓아다니는 소모전에서 벗어날 수 있었다는 겁니다.</p>
<p>흥미로운 건 이 발표가 갑작스러운 게 아니라는 점입니다. 이 아티클의 작성자인 Shopify의 Mustafa Ali는 2025년 1월에 &quot;React Native 5년 사용기&quot;를 정리하는 글을 썼는데, 그때만 해도 React Native의 미래는 밝고 계속 투자하겠다는 입장이었습니다. 그런데 그 이후 코딩 모델이 극적으로 좋아지면서, Swift와 Kotlin으로 같은 기능을 각각 만드는 비용이 예전만큼 크지 않게 됐다는 게 이번 전환의 핵심 논리입니다.</p>
<p>Shopify는 이렇게 말합니다.</p>
<p>&gt; &quot;우리는 어떤 결정이 그 당시 성공적이었다는 이유만으로 계속 고수하지 않습니다. 핵심 전제가 바뀌면, 그것이 여전히 옳은 선택인지 다시 물을 준비가 되어 있습니다. LLM은 2020년 우리 결정의 핵심 전제 중 하나를 바꿔놓았습니다.&quot;</p>
<p>즉, 2020년에 React Native를 선택한 이유는 &quot;같은 기능을 두 번 만들지 않기 위해서&quot;였는데, 이제 LLM 덕분에 &quot;두 번 만드는 것&quot;의 비용 자체가 크게 줄어들었으니 그 전제가 무너졌다는 논리입니다.</p>
<h3>실제로 무슨 일이 있었나</h3>
<p>Shopify는 2021년부터, 그러니까 ChatGPT가 나오기도 전부터 LLM을 소프트웨어 개발에 활용해왔습니다. 처음에는 기능 구현, 버그 조사와 수정, 코드 리뷰 정도에 썼지만, 모델이 발전하면서 맡기는 작업의 복잡도도 함께 커졌습니다. 2025년 말에 이르러서는 단순히 코드 작성 속도를 높여주는 수준을 넘어, &quot;소프트웨어를 두 번 만드는 게 정말 두 배의 일인가&quot;라는 질문 자체를 다시 던지게 만드는 수준이 됐다는 겁니다.</p>
<p>이에 Shopify는 실험을 진행했습니다. 자사의 주요 앱 핵심 부분을 Swift와 Kotlin으로 LLM을 활용해 다시 만들어보는 프로토타입이었는데, 결과가 예상보다 훨씬 좋았다고 합니다.</p>
<ul>
<li>에이전트가 iOS 버전을 레퍼런스로 삼아 Android에서 기능을 구현하고, 그 반대도 가능했습니다.</li>
<li>개발자가 자신의 주력 스택이 아닌 플랫폼에서도 효과적으로 기여할 수 있도록 도왔습니다.</li>
<li>공유 스펙, 테스트, 리뷰 체크포인트를 통해 두 플랫폼 간 기능 격차를 유지하는 비용을 크게 줄였습니다.</li>
</ul>
<p>Shopify는 명확히 짚습니다. &quot;네이티브로 간다고 해서 두 플랫폼을 만들고 유지하는 비용이 사라진 건 아니다. 달라진 건, 이제 에이전트가 구현·번역·테스트·리뷰 작업의 상당 부분을 대신할 수 있게 되면서, 2020년처럼 그 비용이 결정적인 요인이 아니게 됐다는 것&quot;이라고요. Shopify는 자신들의 React Native 앱이 실제로 빠르고 잘 작동한다는 점도 인정합니다. 다만 코드를 공유하는 이점이 에이전트로 인해 줄어든 반면, 각 플랫폼에 맞춰 따로 만드는 이점(플랫폼 고유 기능과 퍼스트파티 툴링에 더 가깝게 붙을 수 있다는 점, 프레임워크와 의존성 레이어가 줄어든다는 점)은 여전히 유효하기 때문에 이번 전환을 결정했다는 논리입니다.</p>
<h3>Theo의 반박: 이 논리는 React Native의 진짜 강점을 놓치고 있다</h3>
<p>여기서 Theo는 강하게 이의를 제기합니다. Shopify의 논리는 React Native의 &quot;멀티플랫폼(코드 공유)&quot; 측면에 지나치게 무게를 싣고 있는데, 그는 이것이 React Native의 가장 큰 강점이라고 생각한 적이 한 번도 없다는 겁니다. (이 부분에 대한 구체적인 대안 논리는 영상 뒷부분에서 더 다뤄질 예정이라고 언급됩니다.)</p>
<p>또한 React Native 생태계의 베테랑인 Infinite Red의 Jamon도 실시간으로 의견을 보탰는데, 그는 이렇게 지적합니다.</p>
<ul>
<li>Shopify가 언급하지 않은 React Native의 가장 큰 이점 중 하나로 <strong>OTA(Over-The-Air) 업데이트</strong>를 꼽습니다. 앱스토어 심사 없이 코드를 바로 배포할 수 있는 기능인데, Shopify의 글에서는 이 부분이 빠져 있습니다.</li>
<li>Shopify가 애초에 Expo를 제대로 채택한 적이 없다는 점도 지적합니다. &quot;React Native 앱을 쓰면서 Expo를 쓰지 않으면, 결국 Expo를 처음부터 다시 만드는 데 시간을 쓰게 된다&quot;는 겁니다. React Native에서 네이티브로의 전환은 생각보다 훨씬 뉘앙스가 많은 주제라는 점을 강조합니다.</li>
</ul>
<h3>오픈소스 라이브러리는 어떻게 되나</h3>
<p>Shopify는 그동안 React Native 생태계에 상당한 기여를 해온 곳입니다. 여러 오픈소스 라이브러리가 각 카테고리에서 최고의 선택지로 자리 잡을 정도였는데, 전환 과정에서도 &quot;깔끔하게, 서프라이즈 없이&quot; 넘어가겠다는 입장을 밝혔습니다.</p>
<p>대표적인 예가 <strong>React Native Skia</strong>입니다. 이는 (Flutter와 흔히 연관되는, 원래는 Android/Chrome 계열의) Skia 렌더링 엔진을 React Native에서 쓸 수 있게 해주는 라이브러리로, 단순 네이티브 레이어로는 구현하기 어려운 화려한 애니메이션이나 그래픽 인터랙션(예: 인스타그램 스토리처럼 사진 위에 여러 요소를 레이어링하는 화면)에 특히 강점이 있습니다. Shopify는 이 라이브러리를 계속 관리해온 직원 William(React Native 관련 유튜브 콘텐츠로도 잘 알려진 인물)이 앞으로도 작업을 이어가도록 지원할 계획입니다. 구체적으로는:</p>
<ul>
<li>몇 달 안에 저장소를 포크해서 새로운 이름으로 배포를 시작합니다.</li>
<li>전환이 완료되면 원본 저장소는 아카이브됩니다.</li>
<li>마이그레이션할 충분한 시간을 주기 위해 과정마다 업데이트를 공지합니다.</li>
<li>이 라이브러리에 의존하고 있다면 후원을 고려해달라고 요청하고 있습니다.</li>
</ul>
<h3>정리</h3>
<ul>
<li>Shopify는 &quot;React Native를 통한 코드 공유&quot;의 비용 절감 효과가 LLM 코딩 에이전트의 발전으로 인해 상대적으로 약해졌다고 판단하고, 네이티브(Swift/Kotlin)로 회귀하기로 결정했습니다.</li>
<li>핵심 논리는 &quot;2020년에는 기능을 두 번 만드는 비용이 너무 컸지만, 지금은 에이전트가 구현·번역·테스트·리뷰를 상당 부분 대신해줘서 그 비용이 예전만큼 결정적이지 않다&quot;는 것입니다.</li>
<li>다만 이 논리는 React Native의 강점을 코드 공유(멀티플랫폼)에만 초점을 맞추고 있다는 비판을 받습니다. OTA 업데이트처럼 언급되지 않은 중요한 이점도 있고,애초에 Expo를 제대로 활용하지 않았다는 지적도 나옵니다.</li>
