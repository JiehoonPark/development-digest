멀티 레포 환경에서 AI 에이전트를 다루는 가장 간단한 방법: Home Repo 패턴

여러 개의 저장소(repo)를 넘나들며 코드를 다루는 조직이라면, AI 코딩 에이전트에게 스킬·규칙 파일·위키 같은 공통 리소스를 어떻게 제공할지가 의외로 골치 아픈 문제입니다. Matt Pocock은 너무 당연하고 사소해서 글로 쓸 가치도 없다고 생각했던 자신의 작업 방식을 커뮤니티 세션에서 공유했는데, 예상외로 큰 반응을 얻었다고 합니다. 이 글에서는 그가 "Home Repo"라고 부르는 이 패턴을 소개합니다.

멀티 레포 환경의 문제

대부분의 조직은 하나의 레포만 쓰지 않습니다. 쇼핑몰 레포, 결제 API 레포, 관리자 대시보드 레포 등 수십 개의 저장소를 오가며 작업하는 게 일반적입니다.

레포 하나만 건드릴 때는 문제가 없습니다. 에이전트를 그 레포 안에서 실행하면 그만입니다. 작업 중에 다른 레포(예: 결제 API)도 수정해야 한다는 걸 깨달았을 때도 크게 어렵지 않습니다. 에이전트가 여러 폴더를 동시에 다루면서 쇼핑몰 레포에 PR 하나, 결제 API 레포에 PR 하나를 같은 세션에서 만들어낼 수 있기 때문입니다.

진짜 문제는 여기서 시작됩니다. 매 세션마다 에이전트가 접근할 수 있어야 하는 스킬, 도구, agents.md 같은 규칙 파일, 위키 링크 등을 어떻게 관리할 것인가입니다. 보통은 이런 리소스들을 여러 레포에 중복해서 넣어두게 되는데, 그러면 30~40개 레포에 걸쳐 스킬과 도구를 계속 동기화해야 하는 번거로움이 생깁니다.

대안으로 이런 리소스를 사용자 로컬 홈 디렉터리에 두는 방법도 있습니다. 모든 레포에서 접근은 가능하지만, 사용자 눈에 보이지 않는 곳에 있다 보니 시간이 지나면서 업데이트가 누락되고 팀의 공통 설정과 어긋나기 쉽습니다. 게다가 홈 디렉터리는 원래 사용자가 "팀의 방식"이 아니라 "자기 방식"대로 설정을 바꿔버리는 공간이라는 점도 문제입니다. 결국 멀티 레포 환경에서 일하는 사람들은 딱히 좋은 선택지가 없다고 느끼게 됩니다.

해법: Home Repo

Pocock이 오랫동안 써온 방식은 단순합니다. 자신의 모든 스킬과 규칙 파일, 위키, 커스텀 도구가 살고 있는 전용 레포 하나를 만들고, 에이전트는 항상 이 "Home Repo" 안에서 실행하는 것입니다.

Home Repo 안에서 실행되는 에이전트도 일반 레포와 마찬가지로 쇼핑몰 레포나 결제 API 레포 등 여러 저장소에 동시에 접근해 작업할 수 있고, 필요한 모든 컨텍스트를 끌어올 수 있습니다.

실제 구성 들여다보기

Home Repo의 핵심 구성 요소는 다음과 같습니다.

  • claw.md(또는 agents.md): 레포 구조와 다른 레포로의 경로를 담은 핵심 파일
  • Claude Skills: 공개하고 싶지 않은, 업무상 민감하고 가치 있는 전용 스킬들. 매 세션마다 자동으로 사용 가능
  • 버전 관리되는 설정 파일(settings.json): 여기서 설정을 바꾸면 조직 전체에 즉시 전파됨

가장 중요한 구조적 역할은 claw.md/agents.md가 담당합니다. 이 파일 안에는 매일 다루는 모든 주요 레포로 연결되는 포인터가 들어 있습니다. 예를 들어 스킬 변경 사항은 repos AI skills로, 강의 영상 매니저(커밋 기준으로 가장 활발한 레포) 관련 작업은 해당 경로로, 특정 프로젝트나 AI 코딩 집중 코스 레포 관련 작업은 각각의 경로로 연결됩니다.

이 연결은 복잡한 메커니즘이 아니라 agents.md 안에 적힌 단순한 경로(path) 일 뿐입니다. 새 머신에서 처음 실행할 때 해당 경로에 레포(예: "sandcastle")가 없으면 에이전트가 알아서 클론합니다. 여러 에이전트가 동시에 작업 중이라면 같은 레포 안에서 work tree를 활용합니다. 즉 별도의 초기 설정 작업이 거의 필요 없는 제로 설정(zero setup) 구조입니다. 다만 work tree는 작업이 쌓이다 보면 주기적으로 정리가 필요합니다.

새 레포를 추가하고 싶으면 agents.md 파일만 수정하면 자동으로 전체 설정에 편입됩니다. 이 방식은 대략 20~40개 레포 정도까지는 잘 작동하지만, 400개 레포 같은 규모로는 확장하기 어렵습니다. 그런 경우에는 점진적 공개(progressive disclosure) 기법을 추가로 적용할 수 있습니다. agents.md에서 레포들을 바로 링크하는 대신, "프론트엔드 레포들", "백엔드 레포들", "내부 도구 레포들" 같은 카테고리를 먼저 두고 그 아래에 각 레포 링크를 배치하는 방식입니다. 이렇게 하면 에이전트가 단순한 파일 시스템 탐색 전략만으로도 올바른 레포를 찾아낼 수 있습니다.

참고로 Pocock은 모노레포 애호가입니다. Vercel에서 Turborepo 관련 개발자 관계(DevRel) 업무를 했을 만큼 모노레포에 관심이 많아서, 모든 걸 한 레포로 합칠 수 있다면 그렇게 하는 걸 선호한다고 밝힙니다. 다만 일부는 공개, 일부는 비공개여야 하는 등 정책·조직적 이유로 모노레포가 항상 가능한 건 아니며, 그럴 때 Home Repo가 최선의 대안이 된다고 말합니다.

Home Repo가 가능하게 하는 것: 개인 위키와 도구 생태계

Home Repo를 쓰기 시작한 뒤로 에이전트용 도구를 만드는 데 있어 훨씬 더 과감해질 수 있었다고 합니다. 그는 자신의 Home Repo를 "개인 위키(personal wiki)"라고 부르는데, 사업과 관련된 민감한 데이터를 모두 담고 있는 거대한 백과사전 역할을 합니다. Karpathy 스타일의 LLM용 위키에 가까운 형태로, 청중들이 흥미로워하는 마크다운 파일들의 모음입니다. (이 위키를 어떻게 만들고 갱신하는지는 이후 영상에서 별도로 다룰 예정이라고 언급합니다.)

이 위키는 강의 제작이나 콘텐츠 생산에 쓰이는 풍부한 데이터를 질의하고 추출하는 용도로 실제 업무에 매우 중요하게 쓰이고 있으며, Home Repo가 이미 있으니 이 위키를 호스팅하기에 자연스러운 장소가 됩니다.

더 중요한 것은 도구(tools)입니다. 개인 위키 디렉터리에서 wiki help를 실행하면 Gmail, Slack, Discord, YouTube, GitHub, Gcal, AI Hero, 사이트 차단 도구인 Cold Turkey 등과 연동되는 다양한 커스텀 도구 목록을 볼 수 있습니다. 일회성 HTML 리포트를 게시하거나 "Butter" 타이머에 연동하는 것도 가능합니다. 이런 도구들은 모든 것이 한곳에 중앙화되어 있고 항상 같은 곳에서 에이전트를 실행하기 때문에 위키 안에서 자연스럽게 자라날 수 있었다고 합니다.

그 결과 "Discord에서 이 메시지를 찾아서, 집중 코스 레포로 가서, 거기서 이미 보유 중인 모든 스킬을 활용해 수정 작업을 하라" 같은 지시를 내릴 수 있고, 이어서 강의 영상 매니저 레포에 있는 CVM 스킬을 이용해 실제 강의 콘텐츠를 수정하는 식의 작업까지 한 흐름으로 이어갈 수 있습니다. 즉 Home Repo는 코드뿐 아니라 업무의 모든 조각을 하나로 엮어주고, 에이전트에게 풍부한 데이터 소스와 강력한 도구에 대한 접근권을 부여함으로써 더 나은 작업을 가능하게 하는 연결 고리가 됩니다.

직접 설정하는 법

Pocock은 "The home repo pattern"이라는 글을 작성했고, 글 하단에 자신만의 Home Repo를 설정할 수 있는 프롬프트를 포함해두었습니다. 이 프롬프트는 사용자의 현재 설정 상황을 물어보고, 관리해야 할 모든 레포를 살펴본 뒤, 관련 리소스들을 Home Repo로 옮기는 작업을 시작해줍니다.

정리

  • 문제: 여러 레포를 오가며 작업할 때 스킬, 도구, 규칙 파일(agents.md), 위키 링크 등을 레포마다 중복 관리하거나, 동기화가 어긋나기 쉬운 홈 디렉터리에 두는 수밖에 없었음
  • 해법인 Home Repo: 모든 스킬·규칙 파일·위키·커스텀 도구가 모여 사는 전용 레포를 하나 만들고, 에이전트는 항상 이 레포 안에서 실행. agents.md에 다른 레포로의 경로만 적어두면 필요시 자동 클론되거나 work tree로 처리됨
  • 확장성: 20~40개 레포까지는 단순 링크 방식으로 충분하며, 그 이상 규모에서는 카테고리별로 레포를 묶는 점진적 공개 기법을 추가하면 됨
  • 부가 효과: 모든 작업이 한곳에 모이다 보니 개인 위키와 Gmail·Slack·Discord·GitHub 등을 연동하는 커스텀 도구 생태계가 자연스럽게 커질 수 있었고, 이는 에이전트가 여러 업무 영역을 넘나들며 작업하는 기반이 됨
  • 모노레포가 가능하다면 그게 최선이지만, 정책·조직적 제약으로 불가능한 경우가 많기에 Home Repo가 실질적인 대안이 됨
💡
여러 저장소를 넘나들며 AI 코딩 에이전트를 운용하는 프론트엔드 팀이라면, 스킬과 규칙 파일 중복 관리 문제를 해결하고 에이전트의 활용 범위를 코드 작업을 넘어 업무 전반으로 확장할 수 있는 실용적인 구조를 얻을 수 있다.
