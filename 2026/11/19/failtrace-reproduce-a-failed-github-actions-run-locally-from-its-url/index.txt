18:T3e95,<h2>FailTrace: GitHub Actions 실패를 URL 하나로 로컬 재현하기</h2>
<p>CI가 실패하면 로그를 뒤져가며 &quot;로컬에서는 왜 안 터지지?&quot;를 고민하다가 결국 추측으로 디버깅을 시작하는 경우가 많습니다. FailTrace는 이 문제를 정면으로 겨냥한 CLI 도구인데요, 실패한 GitHub Actions 런(run)의 URL만 붙여넣으면 어떤 job과 step이 실패했는지, 그 커밋 시점의 워크플로우 파일은 어떤 모습이었는지, 로그에서 실제 실패 원인이 무엇인지를 분석해서 로컬 재현까지 시도해주는 오픈소스 프로젝트입니다.</p>
<h3>act와는 다른 문제를 푼다</h3>
<p>GitHub Actions 워크플로우를 로컬에서 돌려보는 도구로는 <code>act</code>가 이미 잘 알려져 있습니다. 하지만 FailTrace는 act와 출발점 자체가 다릅니다.</p>
<ul>
<li><strong>워크플로우 파일이 아니라 &quot;실패한 런&quot;에서 시작</strong>합니다. 정확한 커밋, 재시도 횟수(attempt), job, 매트릭스 조합, 실패한 step까지 자동으로 찾아내므로 별도 설정이 필요 없습니다.</li>
<li><strong>실패에만 집중</strong>합니다. 전체 워크플로우를 재생하는 게 아니라, 실패한 step이 필요로 하는 것만 최소한으로 재현하려고 합니다.</li>
<li><strong>진단 결과(verdict)를 제공</strong>합니다. 지금 단계에서는 실패 원인 진단을, 추후에는 재현됨/재현 안 됨/불안정(flaky) 여부와 CI-로컬 간 차이점까지 알려주는 걸 목표로 합니다.</li>
</ul>
<p>현재 상태는 초기 개발 단계이며, <code>inspect</code>, <code>plan</code>, <code>repro</code> 세 명령 모두 동작합니다. 단, <code>repro</code>는 실패한 step이 <code>run:</code> 스크립트인 Linux job만 지원합니다.</p>
<pre><code>failtrace inspect https://github.com/owner/repo/actions/runs/123456789  # 왜 실패했나?
failtrace plan https://github.com/owner/repo/actions/runs/123456789     # 어떻게 재현할 수 있나?
failtrace repro https://github.com/owner/repo/actions/runs/123456789    # Docker에서 재현</code></pre>
<h3>설치</h3>
<p>macOS/Linux에서는 설치 스크립트로 최신 릴리스를 받고 SHA-256 체크섬까지 검증합니다.</p>
<pre><code class="language-bash">curl -fsSL https://raw.githubusercontent.com/Ri4dH/failtrace/main/scripts/install.sh | sh</code></pre>
<p><code>/usr/local/bin</code>에 쓰기 권한이 있으면 거기에, 없으면 <code>~/.local/bin</code>에 설치됩니다. <code>FAILTRACE_INSTALL_DIR</code>로 경로를 지정하거나 <code>FAILTRACE_VERSION=v0.1.0</code>으로 버전을 고정할 수 있습니다. macOS/Linux/Windows용(amd64, arm64) 사전 빌드 바이너리는 releases 페이지에서 받을 수 있고, Go 1.24+ 환경이라면 다음처럼 설치할 수도 있습니다.</p>
<pre><code class="language-bash">go install github.com/Ri4dH/failtrace/cmd/failtrace@latest</code></pre>
<p>인증은 <code>GITHUB_TOKEN</code> → <code>GH_TOKEN</code> → <code>gh auth token</code> 순서로 토큰을 찾습니다. 공개 저장소라도 로그 API 자체가 토큰을 요구하기 때문에 토큰이 필수입니다. GitHub Enterprise Server도 지원하며, 이 경우 API 베이스가 <code>https://&lt;host&gt;/api/v3</code>로 바뀝니다.</p>
<h3>inspect: 무엇이 왜 실패했는지 보기</h3>
<p><code>inspect</code>는 런 URL, job URL, 특정 attempt URL을 모두 받을 수 있고, <code>--json</code>으로 JSON 출력, <code>-n</code>으로 로그 라인 수 조절, <code>--job</code>으로 특정 job만 볼 수 있습니다.</p>
<p>실제 prometheus/prometheus 저장소의 실패 런을 분석한 예시(축약)입니다.</p>
<pre><code>✗ CI · prometheus/prometheus

<p>로그 끝에는 go.sum 차이로 인한 수백 줄의 diff가 달려 있었지만, FailTrace는 첫 에러 라인(&quot;go mod tidy가 go.mod를 바꿈&quot;)을 중심으로 발췌해 핵심만 보여줬습니다.</p>
<p><code>inspect</code>가 리포트하는 항목은 다음과 같습니다.</p>
<ul>
<li><strong>런 컨텍스트</strong>: 워크플로우, 이벤트, 브랜치, 커밋, attempt</li>
<li><strong>job → 워크플로우 매핑</strong>: <code>test (ubuntu-latest, 1.22)</code>처럼 매트릭스 값이 이름에 들어간 job도 찾아내고 매트릭스 값을 복원</li>
<li><strong>러너 정보</strong>: 요청한 라벨과 로그에 기록된 실제 러너 이미지/버전</li>
<li><strong>실패 step 정의</strong>: run, uses, with, env, shell, working directory (표현식은 이미 치환된 상태로 표시)</li>
<li><strong>진단</strong>: 종료 코드, 에러 애너테이션, 실패한 테스트 이름(Go, pytest, Jest, Vitest, Cargo, RSpec), 그리고 아래와 같은 카테고리 분류</li>
</ul>
<div class="table-wrapper"><table><thead><tr><th>카테고리</th><th>예시 신호</th></tr></thead><tbody><tr><td>test</td><td><code>--- FAIL: TestX</code>, <code>FAILED tests/x.py::test_y</code></td></tr><tr><td>build</td><td><code>error TS2304</code>, <code>undefined: foo</code>, <code>error[E0425]</code></td></tr><tr><td>dependency</td><td><code>npm ERR! code ERESOLVE</code>, <code>missing go.sum entry</code></td></tr><tr><td>lint</td><td>golangci-lint, eslint, ruff 단계</td></tr><tr><td>generated-diff</td><td><code>diff --git</code>을 출력하는 체크 (tidy, codegen, formatter)</td></tr><tr><td>timeout</td><td>최대 실행 시간 초과</td></tr><tr><td>out-of-memory</td><td>exit code 137, heap out of memory</td></tr></tbody></table></div>
<ul>
<li><strong>재현 노트</strong>: 서비스 컨테이너, job 컨테이너, 사용된 secret, 재사용 워크플로우, macOS/Windows 러너 등 로컬 재현을 어렵게 만드는 요소들</li>
</ul>
<p>job이 시작도 못 하고 실패한 경우, 저장소에 파일이 없는 동적 워크플로우, 만료된 로그 같은 엣지 케이스도 조용히 실패하는 대신 설명을 제공합니다.</p>
<h3>plan: 재현 계획 세우기</h3>
<p><code>failtrace plan</code>은 아직 아무것도 실행하지 않고, 어떻게 재현할지 계획만 출력합니다.</p>
<pre><code>failtrace plan https://github.com/owner/repo/actions/runs/123456789
failtrace plan --job 987654321 &lt;run-url&gt;   # 여러 job이 실패했을 때 선택
failtrace plan --json &lt;run-url&gt;            # 모든 환경변수를 포함한 전체 계획</code></pre>
<p>pytest-dev/pytest의 실패 런에 대한 실제 출력(축약)입니다.</p>
<pre><code>Reproduction plan · pytest-dev/pytest

<p>계획을 세우는 방식은 다음과 같습니다.</p>
<ul>
<li><strong>로그가 진실의 원천</strong>: GitHub가 출력하는 step 헤더에서 스크립트, 셸, 환경을 가져오므로 <code>${{ matrix.* }}</code> 같은 표현식이 이미 치환되어 있습니다. 복합 액션(composite action)은 내부 step까지 펼쳐 보여줍니다.</li>
<li><strong>CI가 실제로 테스트한 정확한 커밋</strong>: PR의 경우 GitHub가 만든 머지 커밋이지 PR 브랜치 head가 아닙니다. &quot;로컬에서는 재현이 안 된다&quot;는 흔한 원인 중 하나가 바로 이것입니다.</li>
<li><strong>정확한 툴체인 버전</strong>: 워크플로우의 &quot;3.11&quot;은 러너의 툴 캐시 경로에서 읽은 <code>3.11.18</code>로 구체화됩니다. 로그에 버전이 없으면 <code>go.mod</code>(toolchain 포함), <code>.nvmrc</code>, <code>.python-version</code>, <code>.tool-versions</code>, <code>package.json</code>의 <code>packageManager</code> 같은 버전 파일을 읽습니다.</li>
<li><strong>올바른 베이스 이미지</strong>: job 컨테이너가 있으면 그대로 쓰고, 없으면 실제 job이 받은 러너 이미지와 일치하는 Ubuntu 버전을 고릅니다.</li>
<li><strong>스킵할 것과 플래그 처리할 것</strong>: 캐시, 업로드, 커버리지 리포터는 생략됩니다. 다운로드된 아티팩트, 서비스 컨테이너, secret, 알 수 없는 액션, setup 단계 없이 쓰인 툴(러너에 미리 설치된 것)은 issue로 보고됩니다.</li>
</ul>
<p>Verdict는 <code>ready</code>(누락된 게 없음), <code>partial</code>(실행은 가능하지만 일부가 근사치이거나 누락됨), <code>blocked</code>(실패한 step이 스크립트가 아니라 액션이라 아직 재생할 수 없음) 셋 중 하나로 표시됩니다.</p>
<p>지원하는 setup 액션은 <code>actions/setup-go</code>, <code>setup-node</code>, <code>setup-python</code>, <code>setup-java</code>, <code>setup-dotnet</code>, <code>ruby/setup-ruby</code>, <code>dtolnay/rust-toolchain</code>, <code>actions-rust-lang/setup-rust-toolchain</code>, <code>pnpm/action-setup</code>, <code>pnpm/setup</code>, <code>astral-sh/setup-uv</code>, <code>oven-sh/setup-bun</code>, <code>denoland/setup-deno</code>입니다.</p>
<h3>repro: Docker에서 직접 재현하기</h3>
<p><code>failtrace repro</code>는 계획을 세운 뒤 Docker에서 실행하고 CI의 실패 결과와 비교합니다. Docker(Docker Desktop, colima, OrbStack 등)와 git이 필요합니다.</p>
<pre><code>failtrace repro &lt;run-url&gt;
failtrace repro --keep &lt;run-url&gt;                       # 컨테이너를 유지해서 나중에 확인
API_TOKEN=... failtrace repro --secret API_TOKEN &lt;run-url&gt;
failtrace repro --toolchain node=20.11.1 &lt;run-url&gt;     # 툴체인 버전을 채우거나 덮어쓰기
failtrace repro --platform linux/arm64 &lt;run-url&gt;       # Apple 실리콘에서 네이티브 실행 (더 빠르지만 덜 정확)
failtrace repro --runs 10 &lt;run-url&gt;                     # flaky 여부 확인
failtrace repro --shell &lt;run-url&gt;                       # 실행 후 컨테이너 안에서 디버깅
failtrace repro --report repro.md &lt;run-url&gt;             # 이슈/PR용 Markdown 리포트</code></pre>
<p>stretchr/testify에서 <code>go vet</code>이 Go oldstable에서 실패한 실제 예시입니다. FailTrace는 oldstable을 CI가 사용한 정확한 Go 1.26.9 빌드로 해석하고, CI가 테스트한 PR 머지 커밋을 체크아웃한 뒤 step을 재생했습니다.</p>

<p>재현 환경은 계획이 정한 베이스 이미지에, GitHub Ubuntu 러너가 공통으로 갖고 있는 패키지들(git, curl, 빌드 도구, python3, jq, sudo 등)과 필요한 툴체인을 더해서 구성됩니다.</p>
<h3>정리</h3>
<ul>
<li>FailTrace는 워크플로우 파일을 들고 로컬에서 전체를 재생하는 act와 달리, <strong>실패한 런의 URL 한 줄</strong>에서 출발해 정확한 커밋·attempt·job·매트릭스·실패 step을 자동으로 찾아줍니다.</li>
<li><code>inspect</code>로 실패 원인을 진단(종료 코드, 에러 카테고리, 재현을 어렵게 만드는 요소들)하고, <code>plan</code>으로 재현 가능 여부(ready/partial/blocked)와 정확한 툴체인 버전·커밋(PR 머지 커밋 포함)을 계산하며, <code>repro</code>로 Docker에서 실제 실행해 CI와 비교까지 해줍니다.</li>
<li>특히 &quot;PR 브랜치 head가 아니라 머지 커밋을 테스트했다&quot;는 점, &quot;3.11 같은 버전 지정이 실제로는 3.11.18이었다&quot;는 점처럼 <strong>로컬 재현 실패의 흔한 원인을 자동으로 드러내주는 것</strong>이 이 도구의 핵심 가치입니다.</li>
<li>현재는 초기 단계로 <code>repro</code>는 <code>run:</code> 스크립트가 실패한 Linux job만 지원하며, action 자체가 실패한 경우는 아직 재생할 수 없습니다(blocked 판정).</li>
<li>CI 디버깅에 시간을 많이 쓰는 팀이라면, 특히 PR 머지 커밋 차이나 툴체인 버전 불일치로 &quot;내 컴퓨터에서는 되는데요&quot; 상황을 자주 겪는다면 시도해볼 만한 도구입니다.</li>
