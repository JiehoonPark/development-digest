Jest에서 Vitest로 테스트 1만 개를 3주 만에 옮긴 솔직한 후기, 그리고 AI가 한 일

We Migrated 10,144 Tests from Jest to Vitest in 3 Weeks: The Honest, AI-Assisted Truth

📅 2026-11-03📰 Echo JS
frontendai

테스트 러너를 바꾸는 작업은 "갈아끼우면 끝"인 경우가 거의 없습니다. Subito 프론트엔드 팀은 2026년 8월, Vitest 4를 기준으로 전체 프론트엔드 테스트 스위트를 Jest에서 Vitest로 옮기는 작업을 진행했는데요. 이 글에 등장하는 모든 수치와 벤치마크, 설정 내용은 Vitest 4 기준이며 Vitest 5와는 무관합니다. 약 3주에 걸쳐 8개 저장소를 마이그레이션했고, 파일 개수만 세는 대신 모든 스위트를 실제로 끝까지 돌려서 진짜 숫자를 확인했습니다. 결과는 다음과 같습니다.

  • 실제로 실행된 유닛 테스트 10,144개 (파일 개수가 아니라 실행 기준)
  • 8개 저장소에 걸친 테스트 파일 1,799개
  • 절반만 마이그레이션된 채로 남은 저장소 0개
  • 전체 작업(마이그레이션 + 이후 튜닝 포함) 약 3주 소요
  • 이 작업에 추적 가능했던 Claude Code 세션의 AI 토큰 비용 추정치 약 $751 (아래에서 설명하듯 정확한 청구 금액이 아니라 대략적인 상한선)

이 글은 git 히스토리, PR 본문, 세션 로그에서 직접 뽑아낸 실제 경험담입니다. 같은 고통을 반복하지 않도록, 팀이 처음부터 가지고 있었으면 좋았을 AI 자동화 스킬의 일반화 버전도 공개했습니다(github.com/Subito-it/articles-code/tree/main/jest-to-vitest-migration).

Jest가 아프기 시작한 이유

단순히 "Jest가 느리다"는 추상적인 이유로 마이그레이션을 결정한 게 아닙니다. Jest 유지보수 자체가 엔지니어링 시간을 계속 갉아먹는 실질적인 세금이 되어버렸기 때문입니다. 동시에 새로운 Vite/Next.js 프로젝트의 기본 선택지로 빠르게 자리잡고 있는 Vitest 쪽 생태계 흐름에 올라타고 싶은 이유도 있었습니다.

CommonJS와 ESM의 악몽

next/jest는 기본적으로 node_modules 내부의 어떤 코드도 변환하지 않습니다. 그래서 의존성 패키지가 ESM 전용으로 업데이트되면 Jest의 CommonJS require()가 곧바로 깨집니다. 팀은 transformIgnorePatterns 정규식을 손으로 패치해가며 특정 패키지를 허용 목록에 올려야 했는데, 실제 설정 파일에 남아있던 주석은 이렇습니다.

// ESM-only node_modules that Jest must transform. next/jest overwrites any
// user-supplied transformIgnorePatterns to skip all of node_modules, so we
// allow-list these on the resolved config instead.
const esmPackagesToTransform = ['cookie'];

별개로, 마이그레이션을 결정하기 약 6주 전에는 uuid의 메이저 버전 업데이트가 순수 ESM으로 배포되면서 Jest를 아예 깨뜨린 적도 있습니다. 당시 실제 커밋 메시지는 이랬습니다: "uuid v14가 순수 ESM으로 배포되어 Jest(CommonJS)를 깨뜨린다. uuid()의 유일한 사용처를 네이티브 crypto.randomUUID()로 교체해 의존성 자체를 제거한다." 트랜스폼 설정과 다시 씨름하는 대신 팀은 그냥 의존성을 지워버렸습니다. 테스트 러너가 마이그레이션 계획을 세우기도 전부터 의존성 선택을 좌우하고 있다면, 그건 가설이 아니라 실제로 조용히 쌓이는 비용입니다.

생태계 비대화

저장소마다 jest, jest-mock, jest-environment-jsdom, ts-jest, @types/jest, babel-jest 그리고 저장소별 추가 도구까지, Jest 전용 도구들이 불안정하게 쌓여 있었습니다. Vite 기반 트랜스폼 파이프라인을 쓰는 Vitest로 옮기면서 이 도구 더미를 전반적으로 줄일 수 있었습니다.

성능 신화, 그리고 이를 바로잡은 과정

Vitest가 Jest보다 자동으로 빠르지는 않았습니다. 솔직히 말해 적어도 두 개 저장소에서는, 제대로 튜닝하기 전까지는 기본 설정의 Vitest가 측정상 더 느렸습니다.

워커 캡의 현실

한 저장소에서는 Jest에서 문제없이 쓰던 CI 워커 캡 설정을 그대로 유지했더니, 약 35초였던 테스트 실행이 Vitest에서는 약 3분짜리 느린 실행으로 변했습니다. 실제 테스트 실행 시간 자체는 거의 동일했고, 차이는 거의 전부 풀/워커 오버헤드에서 나왔습니다. 많은 코어를 가진 CI 러너에서 maxWorkers를 2에서 8로 명시적으로 올려 이 문제를 해결했습니다.

벤치마크 스윕

Vitest 설정은 추측이 아니라 측정으로 정해야 합니다. 앞서의 저장소와는 별개로, CI 기준 Jest 베이스라인이 44.4초였던 다른 저장소에서 10코어 머신 위에서 Vitest의 forks 풀로 엄격한 로컬 벤치마크 스윕을 돌렸습니다(파일 146개 / 테스트 683개 기준).

  • 워커 2개: 60.9초
  • 워커 4개: 35.0초
  • 워커 6개: 26.6초 (최적 지점)
  • 워커 8개: 27.0초
  • 워커 10개: 28.5초

워커 숫자를 무작정 늘린다고 6개 이상에서는 좋아지지 않았습니다. "더 빠르다"던 Vitest는 하드웨어에 맞게 튜닝하기 전까지는 기존 Jest CI 베이스라인보다 실제로 빠르지 않았습니다.

풀 선택: 진짜 중요한 설정

Vitest는 여러 워커 격리 풀을 제공하는데, 어떤 풀을 선택하느냐는 속도 문제가 아니라 정합성 문제입니다. 팀은 결국 모든 저장소를 forks 풀로 통일했습니다. forks는 실제 자식 프로세스를 사용하므로 Node가 초기화되기 전에 환경 변수가 제대로 적용됩니다. 반면 대안인 threads는 process.env를 너무 늦게 변경해 TZ 같은 값이 제대로 반영되지 않고, 이로 인해 한 저장소에서 CI상 시간대에 의존하던 스냅샷이 깨지는 문제가 발생했습니다.

forks의 단점은 파일마다 jsdom을 새로 생성한다는 점으로, 기본 설정 기준으로는 더 느립니다(한 저장소에서는 워커 튜닝 전 Jest 대비 약 5배 느린 것으로 측정됐습니다). 그럼에도 forks를 선택한 이유는 그것이 가장 정합성이 높은 옵션이었기 때문입니다. 공유 컨텍스트 풀인 vmThreads가 조용히 숨기고 있던 레이스 컨디션을 피할 수 있었고, 다른 풀에서 발생한 에러 트래킹 호출 관련 자동목킹 결함(다음 절 참고)도 피할 수 있었습니다.

자동목킹의 함정: 수년간 숨어있던 Jest 버그

Jest의 __mocks__/ 디렉터리는 상당히 마법 같습니다. 패키지 이름과 일치하는 파일을 그 디렉터리에 두기만 하면, 테스트 파일이 직접 임포트하지 않은 패키지까지 포함해서 임포트 그래프 전체에 조용히 적용됩니다. 반면 Vitest는 테스트 파일 안에 명시적인 vi.mock() 호출을 요구합니다.

이 조용한 Jest 마법이 사라지자, 테스트들이 흥미로운 방식으로 깨지기 시작했습니다. 공유 내부 텔레메트리 라이브러리에는 백그라운드 동기화 타이머가 있었는데, Jest의 암묵적 목킹이 수년간 이를 억눌러왔던 것으로 보입니다. Vitest 아래에서는 실제 모듈이 실행되고 타이머가 테스트 중에 발동하면서, 서로 독립적인 세 개 저장소에서 각각 따로 처리된 미처리 프로미스 거부(unhandled promise rejection)가 발생했습니다.

별개로, 두 저장소에서는 특정 풀 설정 아래에서 에러 트래킹 SDK 호출이 실행되는 대신 undefined로 귀결되는 문제를 발견했습니다. 원래대로라면 에러를 발생시켰어야 할 테스트 시나리오가, 수년간 조용히 아무 일도 하지 않고 있었던 겁니다. 두 문제 모두 자동목킹에 의존하는 대신 명시적인 mock factory를 사용해 해결했습니다.

가장 위험했던 사례는 이보다 더 조용했습니다. 여러 컴포넌트 테스트가 공유 내부 패키지의 실제 구현을 Jest가 조용히 가로채주는 것에 의존하고 있었습니다. Vitest 아래에서 명시적인 목이 없으니 실제 구현이 대신 실행됐고, 테스트는 시끄럽게 실패하지도 않았습니다. 그저 원래 검증하려던 것과는 다른 코드 경로를 실행하기 시작했을 뿐이며, 이는 Jest가 가려주고 있던 동안 내내 거기 잠복해 있던 거짓 양성(false-positive) 테스트 위험이었습니다.

롤백을 정상적인 과정으로 받아들이기

모든 저장소가 "PR 하나로 깔끔하게 끝"일 거라 기대한다면 그 생각은 접어두는 게 좋습니다. 한 저장소는 마이그레이션 PR을 머지한 직후 비결정적인 플레이키 테스트에 부딪혔고, 팀은 드라마 없이 올바른 결정을 내렸습니다. 되돌림 커밋으로 롤백하고, 제대로 원인을 조사한 뒤, 약 5일 뒤 성공적인 재시도를 랜딩시킨 겁니다. 이건 장애가 아니고 실패도 아닙니다. "완료"라는 판정을 서두르지 않을 때, 이 정도 규모의 변경이 보통 보여주는 모습입니다. 이번 작업 전체를 관통하는 패턴은 승리를 선언하기 전에 반드시 측정하고, 제대로 작동하지 않는 것은 과감히 되돌리는 것이었습니다.

Jest가 실제로 더 나았던 지점

이 글이 일방적인 홍보처럼 읽히지 않도록, 반대편 이야기도 해보겠습니다. Jest는 수년간 그냥 잘 작동했습니다. 안정적이고 꽤 빠른 스위트를 돌리기 위해 풀 모델이나 워커 개수 스윕을 고민할 필요가 아무도 없었습니다. __mocks__/의 자동목킹은 결국 거짓 양성 위험을 숨기고 있었다는 게 드러났지만, 동시에 전이적으로 목킹되는 모든 의존성에 대해 일일이 vi.mock()을 작성할 필요가 없게 해줬습니다. 그리고 적어도 두 저장소에서는 기본 설정 Jest가 기본 설정 Vitest보다 분명히 더 빨랐습니다. Jest가 한 번도 요구하지 않았던 튜닝 작업을 거치기 전까지는요.

스위트가 작고 안정적이며 ESM 의존성 문제와 씨름하지 않는다면, "Vitest로 마이그레이션하라"는 자동으로 정답이 아닙니다. 이는 한 종류의 유지보수 비용을 다른 종류의 비용과 맞바꾸는 일이며, 이번 경우에 결과적으로 이득을 본 건 ESM 마찰, jsdom 인접 도구, 숨겨진 자동목킹 버그라는 팀의 특정 고통 지점이 마침 Vitest의 모델이 잘 해결해주는 지점과 겹쳤기 때문입니다.

현실: AI 없이는 이 일정 안에 불가능했다

AI 지원 없이는 이 마이그레이션을 이 일정 안에 끝내지 못했을 겁니다. 서로 독립적으로 소유된 8개 코드베이스에 걸쳐 수천 개 테스트 파일을 3주 안에 수작업으로 전부 변환하는 건, 이 팀 규모로는 현실적이지 않았습니다. 반복적이고 잘 정의된 수천 건의 기계적 변환 작업은 Claude Code에 위임했습니다.

AI 비용에 대해 정확히 말할 수 있는 부분은 다음과 같습니다.

  • 입력 토큰: 약 25만 개 (세션 로그에서 집계한 실제 수치)
  • 출력 토큰: 약 970만 개 (실제 수치)
  • 캐시 읽기/쓰기 토큰: 약 14.6억 / 약 6,000만 개 (실제 수치)
  • 매칭된 세션: 70개, 8개 저장소 중 7개에 걸침 (공유 컴포넌트 모노레포의 세션은 별도로 채굴되지 않음)
  • 추정 비용: 총 약 $751, 저장소당 평균 약 $107

이 비용 수치에는 두 가지 솔직한 유의사항이 있습니다. 이는 실제 청구서가 아니라, 실제 토큰 수치에 리스트 가격과 추정 캐시 할인 배율을 적용해 산출한 값입니다. 해당 세션들의 실제 청구 금액에는 접근할 수 없었습니다. 또한 세션 관련성 필터가 "migration"이라는 단어가 언급된 모든 세션을 매칭했기 때문에, 이는 "Jest-to-Vitest 마이그레이션에 한정된" 범위보다 넓습니다. 그래서 $751은 이번 작업만의 정확한 비용이라기보다는 상한선에 가깝게 읽는 것이 맞습니다.

팀은 한 가지 단순하지만 강력한 원칙도 지켰습니다. 요즘은 AI에 무엇을 위임하는지에 대해 깊이 이해하는 것이 그 어느 때보다 중요합니다. 실제 작업에 착수하기 전, Jest와 Vitest의 차이를 분석하고 Vitest 문서를 읽으며 코드베이스에 가장 잘 맞는 계획을 이해하는 데 시간을 들였습니다. 이 단계가 없었다면 아마 훨씬 더 많은 토큰을 소모했을 것입니다.

Claude Code가 가져다준 건 단순히 기계적 작업의 속도만이 아니었습니다. 덕분에 엔지니어들은 어떤 풀을 선택할지, 어떤 "수정"이 실제로 도움이 되는지, 마이그레이션 시도를 언제 완료로 판정할지와 같은 진짜 판단이 필요한 일에 시간을 쓸 수 있었습니다.

마이그레이션 스킬 공개

이번 마이그레이션에서 가장 어려웠던 부분은 API 문법 변경이 아니었습니다. 워커 벤치마킹과 풀 선택에 대한 가이드가 전혀 없었다는 점이었고, 바로 거기서 가장 많은 시간을 잃었습니다.

이 스킬은 한 번 작성하고 방치한 게 아닙니다. 처음 만든 뒤 각 저장소가 새로운 풀 버그나 벤치마킹 의외의 결과에 부딪힐 때마다 계속 다듬어나갔고, 그 결과 마지막 저장소가 마이그레이션될 무렵에는 그 이전 모든 저장소에서 얻은 교훈이 이미 녹아들어 있었습니다. 이렇게 지속적으로 다듬는 작업 자체도 마이그레이션 본작업과는 별개로 쉽지 않은 과정이었습니다.

이제 이 스킬을 누구나 쓸 수 있도록 공개합니다. 회사 고유 정보는 모두 제거하고, 스킬이 자라면서 포함하게 된 파일 단위 마이그레이션 규칙만 남겼습니다. 아래 링크에서 받아 여러분의 코드베이스에 바로 적용해볼 수 있습니다.

github.com/Subito-it/articles-code/tree/main/jest-to-vitest-migration

정리

Subito 팀의 사례는 "Vitest가 무조건 더 빠르다"는 통념을 반박하는 동시에, 실제 마이그레이션이 어떤 모습인지 구체적으로 보여줍니다. 핵심은 세 가지로 요약됩니다.

  • 성능은 튜닝의 결과이지 기본값이 아니다: maxWorkers 설정 하나로 35초짜리 작업이 3분으로 늘어날 수도 있고, 워커 개수 벤치마크 스윕으로 최적 지점(이번 사례에서는 6개)을 찾아야만 진짜 성능 이득을 볼 수 있습니다.
  • 풀 선택은 속도가 아니라 정합성 문제다: threads는 환경 변수 타이밍 문제로 시간대 의존 스냅샷을 깨뜨릴 수 있고, vmThreads는 레이스 컨디션을 숨길 수 있습니다. 팀은 느리더라도 정확한 forks를 선택했습니다.
  • Jest의 암묵적 자동목킹은 수년간 버그를 가려온 위험 요소였다: 명시적 vi.mock()으로의 전환 과정에서 타이머 발동, 에러 트래킹 무력화, 거짓 양성 테스트 같은 숨은 문제들이 드러났습니다.
  • AI는 규모의 문제를 해결했지만, 판단력을 대체하지는 않았다: 기계적 변환은 Claude Code에 맡기되, 풀 선택이나 "완료" 판정 같은 엔지니어링 판단은 사람이 직접 내려야 했습니다. 또한 위임 전에 Jest-Vitest 차이를 깊이 이해해두는 사전 학습이 토큰 비용을 아끼는 데 중요했습니다.
  • 마이그레이션 가치는 상황에 달려 있다: 스위트가 작고 안정적이며 ESM 문제가 없다면 Vitest 전환이 자동으로 이득은 아닙니다. 본인 코드베이스의 고통 지점이 Vitest가 해결하는 지점과 겹치는지부터 확인해야 합니다.

테스트 러너 마이그레이션을 고려 중인 프론트엔드 개발자에게, 'Vitest가 무조건 빠르다'는 통념의 함정과 실제 튜닝·디버깅 비용, AI 활용 시 필요한 판단 포인트를 구체적인 수치와 함께 보여줍니다.
