React 드롭다운 INP를 1,256ms에서 96ms로 줄인 방법: 가상화로 마운팅 비용 해결하기

From 1,256ms to 96ms: Fixing INP in a Massive React Dropdown

📅 2026-11-03📰 Echo JS
frontend

Subito의 마켓플레이스에서는 체크박스 스타일 필터로 커스텀 MultiSelect 컴포넌트를 전사적으로 사용하고 있습니다. react-select를 기반으로 완전히 리스킨한 이 컴포넌트는 옵션이 10여 개 정도인 일반적인 필터(상품 상태, 배송 방법 등)에서는 체감상 즉각적으로 동작했습니다. 그런데 신발 카테고리의 "브랜드(Marca)" 필터에 적용하면서 문제가 터졌습니다. 이 필터의 옵션 개수는 무려 1,175개. 모바일 환경에서 드롭다운을 여는 순간 페이지 전체에서 가장 끔찍한 인터랙션이 되어버렸습니다. 이 글에서는 INP를 1,256ms에서 96ms로 끌어내린 과정과, 그 해법이 왜 90줄짜리 작은 훅으로 충분했는지를 살펴봅니다.

문제 상황: 느려진 드롭다운

모바일 기기에서 CPU를 4배 스로틀링한 상태(중급 스마트폰 성능을 근사하는 표준적인 방법)로 Chrome DevTools의 Performance 패널을 열고 세션을 녹화했습니다. "Marca" 드롭다운을 클릭하자 실시간 INP(Interaction to Next Paint) 수치가 폭발적으로 치솟았습니다.

  • 로컬 INP: 1,256ms — "poor" 등급, 실사용자 INP 분포 기준 하위 6%
  • Google이 제시하는 "good" INP 기준은 200ms 이하인데, 이 인터랙션은 그 기준을 6배 이상 초과했습니다.
  • 사용자가 버튼을 누른 뒤 메뉴가 화면에 그려지기까지 1초 넘게 화면이 완전히 멈춰 있었습니다.

왜 이런 일이 벌어졌나

INP는 입력 지연(input delay) → 처리 시간(processing duration) → 표시 지연(presentation delay), 이렇게 세 단계의 지연을 합산해 측정합니다. 이번 케이스에서 문제는 명확히 처리 시간이었습니다. 리페인트를 막아서는 거대한 동기(synchronous) 작업 블록이 원인이었습니다.

근본 원인을 추적해보니 메뉴를 마운트하는 비용 자체가 문제였습니다. MenuList 컴포넌트는 1,175개 브랜드 배열 전체를 그대로 전달받고 있었고, 메뉴를 여는 순간 React는 ~1,175개의 Option 컴포넌트 인스턴스(각각 라벨과 커스텀 체크박스를 포함해 여러 개의 DOM 노드를 생성)를 한꺼번에 생성해야 했습니다. 이 모든 작업이 단 한 번의 동기 커밋 안에서 일어났는데, 정작 화면에 보이는 영역에는 한 번에 6개 행 정도만 들어갈 공간밖에 없었습니다.

해결책: 근본 원인을 정조준하기

전체를 처음부터 다시 짜거나 무거운 서드파티 가상화 라이브러리를 들여오는 대신, 표준 React API만으로 근본 원인을 공략했습니다. 이렇게 해법을 작게 유지할 수 있었던 건 옵션 목록이 가진 특정한 성질 덕분인데, 이는 코드를 본 뒤에 다시 설명하겠습니다.

가상화(virtualization)란

가상화는 리스트의 모든 항목을 렌더링하는 대신, 현재 화면에 보이는 항목과 뷰포트 바로 바깥의 작은 버퍼만 렌더링하는 기법입니다. "Marca" 필터는 1,175개의 브랜드를 갖고 있지만 드롭다운에는 한 번에 몇 개 행만 표시됩니다.

가상화 없이는 1,175개 컴포넌트가 전부 마운트되지만, 가상화를 적용하면 보이는 항목(예: Brand 42~48)과 약간의 버퍼만 DOM에 마운트됩니다. 리스트 자체에서 아무것도 제거하는 게 아닙니다. 스크롤과 검색을 위해 전체 리스트는 그대로 유지되고, 다만 사용자가 지금 볼 수 없는 항목에 대해서는 React 컴포넌트와 DOM 노드를 만들지 않을 뿐입니다. 사용자가 스크롤하면 보이는 창(window)이 이동하면서 React가 새 행을 마운트하고 더 이상 필요 없는 행을 언마운트합니다.

이 접근은 MultiSelect에 특히 효과적입니다. 사용자가 사용할 수 있는 브랜드는 1,175개지만, 어느 순간이든 실제로 보이는 건 약 6개 행뿐이기 때문입니다.

가상화 구현에는 두 가지 방식이 있습니다. 모든 행의 높이가 동일하다고 가정하는 방식과, 각 행의 높이를 하나하나 측정하는 방식입니다. 여기서 다루는 건 훨씬 단순한 첫 번째 방식입니다.

리스트 가상화로 마운팅 비용 해결하기

열림 지연을 고치기 위해 useVirtualScroll이라는 약 90줄짜리 커스텀 훅을 직접 만들었습니다. 개념은 단순합니다. 스크롤 위치를 추적하고, 보이는 행에 더해 빠른 스크롤 시 빈 화면이 깜빡이는 걸 막기 위한 작은 버퍼(OVERSCAN 5개 항목)만 렌더링하는 것입니다.

모든 계산은 단 하나의 숫자, 즉 행 하나의 높이에서 출발합니다. 이 값은 메뉴가 마운트된 직후 DOM에서 직접 읽어옵니다.

// Measure the actual rendered option height once after mount
useLayoutEffect(() => {
  const el = listboxRef.current?.querySelector<HTMLElement>('[role="option"]');
  if (el) {
    const h = el.getBoundingClientRect().height;
    if (h) setItemHeight(h);
  }
}, []);

나머지는 전부 이 숫자를 바탕으로 한 산술 연산입니다.

// How tall the list would be, and which slice of it to render
const totalHeight = totalCount * itemHeight;
const startIdx = Math.max(0, Math.floor(scrollTop / itemHeight) - OVERSCAN);
const endIdx = Math.min(
  totalCount,
  Math.ceil((scrollTop + maxHeight) / itemHeight) + OVERSCAN,
);
const offsetTop = startIdx * itemHeight;

최종적으로 렌더링되는 구조는, 키가 큰(1,175행 × 40px = 47,000px) 빈 컨테이너 div(네이티브 스크롤바가 전체 리스트 길이를 반영하도록) 안에, 실제로 필요한 약 13개 행만 실제로 마운트된 절대 위치(absolutely positioned) 내부 div가 들어있는 형태입니다.

> 라이브 데모와 코드: 이 윈도잉 렌더링 방식을 단순화해 보여주는 CodePen 데모와, 전체 구현이 담긴 GitHub 저장소를 제공하고 있습니다.

함정: 모든 행의 높이가 동일해야 한다

위 네 가지 값의 공통점을 보면 전부 itemHeight에 의존하고 있습니다. 즉 행 하나를 측정하고 나머지 1,174개도 동일하다고 가정하는 것이며, 이 훅은 800번째 행이 실제로 얼마나 큰지는 절대 묻지 않습니다.

이 가정이 깨지면 리스트는 조용히 망가집니다. itemHeight보다 큰 행 하나가 있으면 그 아래의 모든 행이 제자리를 벗어나고, 이 오차는 행이 쌓일수록 누적됩니다. 스크롤을 내릴수록 실제 콘텐츠와 스크롤바가 가리키는 위치 사이의 간극이 벌어지면서 빈 공간, 겹치는 행, 혹은 아예 도달할 수 없는 옵션이 생길 수 있습니다.

흔히 겪는 원인들:

  • 일반 옵션 행보다 크게 스타일링된 그룹 헤더
  • 줄바꿈되는 라벨: "Alexander McQueen"은 넓은 화면에서는 한 줄이지만 좁은 모바일 화면에서는 두 줄이 됩니다.
  • 측정 이후 변하는 행: 회전이나 리사이즈 후 밀도가 달라지거나, 웹폰트가 늦게 로드되는 경우. 측정은 메뉴가 열릴 때 단 한 번만 수행됩니다.

이 훅을 그대로 가져다 쓰기 전에, 본인의 리스트를 먼저 점검해야 합니다. 가상화를 적용하지 않은 상태로, 지원하는 화면 중 가장 좁은 너비에서 메뉴를 열고 서로 다른 행 높이가 몇 종류인지 세어보세요.

new Set(
  [...document.querySelectorAll('[role="option"]')].map(
    (el) => el.getBoundingClientRect().height,
  ),
);
// Set(1) { 40 } → one height everywhere: this technique works
// Set(3) { 40, 64, 88 } → it doesn't, keep reading

Subito의 행들이 이 테스트를 통과하는 건, 컴포넌트 자체가 높이를 균일하게 유지하도록 설계되어 있기 때문입니다. 긴 브랜드명은 줄바꿈 대신 말줄임표(ellipsis)로 처리되고, 그룹 헤더도 특별한 존재가 아니라 체크박스를 가진 일반 행이며 자식 항목은 단순히 들여쓰기만 되어 있습니다. 이는 기술적 결정이면서 동시에 디자인적 결정이고, 바로 이 결정 덕분에 90줄짜리 훅으로 충분했던 것입니다.

행 높이가 균일하지 않다면

이 경우 선택지는 두 가지입니다.

  • 균일하게 만들기: 행 높이를 하나로 통일하고, 줄바꿈 대신 말줄임표를 사용합니다. 보통 가장 저렴한 해법이지만 디자인 변경이 필요하므로 디자이너와 협의해야 합니다.
  • 라이브러리 사용하기: TanStack Virtual이나 react-virtuoso는 모든 행을 측정하고 각 행이 어디에 위치하는지 추적합니다. 이 글에서 본 코드보다 훨씬 많은 코드와, 스크롤 중 재측정되는 행 같은 엣지 케이스까지 다뤄야 합니다. 행 높이가 실제로 제각각이라면 이쯤에서 의존성을 들이는 게 그만한 값어치를 합니다.

핵심은 "직접 가상화를 구현하지 말라"는 게 아닙니다. 이 훅이 90줄인 이유는 모든 행의 높이가 같기 때문이지, 가상화 자체가 90줄짜리 문제여서가 아니라는 점입니다.

결과

로컬 INP (열기)1,256ms ("poor")96ms ("good")
DOM 노드 수 ([role="option"])최대 ~1,175개13개

마운팅 비용을 직접 공략함으로써, 완전히 망가진 인터랙션을 100ms 미만으로 되돌렸고 렌더링되는 DOM 노드 수는 1,000개 이상에서 단 13개로 줄였습니다.

단, 접근성 측면의 트레이드오프가 있습니다. 가상화는 화면 밖 항목을 물리적으로 DOM에서 제거하기 때문에, 브라우저의 네이티브 검색 기능(Ctrl+F)으로는 현재 보이는 창 안에 없는 브랜드를 찾을 수 없습니다. 사용자는 커스텀 검색 바에 의존해야 합니다.

실전 체크리스트

거대한 리스트에서 느린 인터랙션을 마주했다면 다음을 점검해보세요.

  • 무엇이 마운트되는지 확인하기: 메뉴가 6개만 보여주면서 1,000개 컴포넌트를 마운트하고 있다면 첫 번째 용의자를 찾은 것입니다.
  • 모든 행의 높이가 같은지 확인하기: 같다면 이 기법은 약 90줄로 충분합니다. 다르다면 높이를 균일하게 만들거나 각 행을 측정하는 라이브러리를 사용해야 합니다.
  • 보이는 행만 렌더링하기: 스크롤 위치를 추적해 보이는 영역의 행과 작은 버퍼만 마운트하고, 전체 리스트를 마운트하지 않습니다.
  • 아이템 개수가 아니라 DOM 노드 개수를 지켜보기: 리스트가 수천 개의 항목을 담고 있어도, 한 번에 마운트되는 게 몇 개뿐이라면 문제없습니다.

정리

1,100개 항목을 가진 리스트 자체가 본질적으로 성능 문제인 것은 아닙니다. 문제는 브라우저가 다음 프레임을 그릴 틈도 없이 매번 전체를 렌더링하는 것입니다. Subito 사례에서 핵심은 react-select 기반 MultiSelect가 메뉴를 열 때마다 1,175개의 Option 컴포넌트를 동기적으로 전부 마운트하고 있었다는 점이었고, 이를 뷰포트에 보이는 6개 안팎의 행과 약간의 버퍼만 마운트하는 윈도잉 방식으로 바꾸자 INP가 1,256ms에서 96ms로, DOM 노드 수는 1,175개에서 13개로 줄었습니다.

다만 이 90줄짜리 간단한 해법이 가능했던 전제 조건은 모든 행의 높이가 동일하다는 점입니다. 그룹 헤더가 더 크거나, 라벨이 줄바꿈되거나, 리사이즈·폰트 로딩 이후 행 높이가 바뀌는 리스트라면 이 방식은 조용히 깨집니다. 자신의 리스트에 가상화를 적용하기 전에 먼저 getBoundingClientRect().height로 행 높이 종류를 확인해보고, 균일하지 않다면 디자인을 손보거나 TanStack Virtual, react-virtuoso 같은 라이브러리를 고려하는 것이 현실적인 선택입니다.

💡
대량의 옵션을 가진 리스트/드롭다운은 흔한 UI 패턴이지만 무심코 전체를 렌더링하면 INP 같은 핵심 웹 바이탈을 심각하게 해칠 수 있어, 무거운 라이브러리 없이도 표준 React API만으로 해결 가능한 윈도잉 기법과 그 적용 조건을 아는 것이 실무에서 중요하다.
