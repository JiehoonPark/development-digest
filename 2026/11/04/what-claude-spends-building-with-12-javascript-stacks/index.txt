18:T2961,<p>JavaScript 생태계에서는 요즘 AI 코딩 에이전트와 관련된 이야기가 끊이지 않습니다. 이번 JavaScript Weekly #809호에서도 &quot;어떤 프레임워크가 AI 에이전트 작업에 더 유리한가&quot;를 실제로 측정해본 흥미로운 실험이 핵심 기사로 다뤄졌는데요, 이 외에도 npm 보안, Node.js 릴리스 정책 변화, 디자인 시스템 성능 측정 등 실무에 바로 적용할 만한 소식들이 가득합니다. 이번 주 주요 소식들을 정리해보겠습니다.</p>
<h3>Claude에게 12개 스택으로 같은 앱을 5번씩 만들게 해봤더니</h3>
<p>&quot;X 프레임워크가 AI 에이전트 작업에 더 좋다&quot;는 주장은 커뮤니티에서 흔히 들을 수 있습니다. Nolan Lawson은 이 주장을 검증하기 위해 Claude에게 열두 가지 JS 스택 각각으로 동일한 앱을 다섯 번씩 만들게 하는 실험을 진행했습니다.</p>
<p>결과를 분석한 Gautam Parab에 따르면, 실행마다 비용 편차가 상당히 컸고 대부분의 프레임워크 쌍 사이에서 관측된 비용 범위가 서로 겹치거나 맞닿아 있었습니다. 즉, 비용 측면에서는 특정 프레임워크가 압도적으로 유리하다고 보기 어려웠다는 뜻입니다.</p>
<p>반면 훨씬 뚜렷한 차이가 나타난 지표가 있었는데, 바로 브라우저로 전송되는 JavaScript 용량의 중앙값이었습니다.</p>
<ul>
<li><strong>Astro</strong>: 0KB</li>
<li><strong>Hono+htmx</strong>: 18KB</li>
<li><strong>SvelteKit</strong>: 36KB</li>
<li><strong>React Router, TanStack Start, Next.js</strong>: 115~142KB</li>
</ul>
<p>이 수치를 바탕으로 Nolan은 흥미로운 질문을 던집니다. 만약 코드 작성을 AI에게 완전히 맡기는 &quot;핸즈프리&quot; 방식으로 간다면, 애초에 본인이 선택했던 특정 스택을 고집할 이유가 있을까요? 코드를 직접 작성하지 않는 상황에서는 번들 크기나 런타임 특성 같은 결과물 중심의 기준이 더 중요해질 수 있다는 시사점입니다. 벤치마크 코드는 GitHub에 공개되어 있어 직접 재현해볼 수 있습니다.</p>
<h3>악성 핑거프린팅 스크립트, LLM이 분석을 거부하도록 설계되다</h3>
<p>caynvas 핑거프린팅(서로 다른 클라이언트가 canvas 요소를 렌더링하는 미묘한 차이를 이용해 브라우저 환경을 식별하는 기법) 예제를 수집하던 Veritas는 fingerprint.garden에서 공개한 크롤링 결과 중 특이한 안티 분석 기법을 발견했습니다. JavaScript 식별자 이름을 금기시되는 주제들로 지어두고, 보이지 않는 유니코드 문자 안에 프롬프트를 숨겨서 LLM이 해당 코드 작업을 아예 거부하도록 유도한 것입니다. AI 코딩 도구가 보편화되면서 이를 악용하려는 시도도 함께 늘어나고 있음을 보여주는 사례입니다.</p>
