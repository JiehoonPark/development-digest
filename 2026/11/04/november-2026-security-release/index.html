Next.js 2026년 11월 보안 릴리스: 캐시 교차 노출 등 7건 취약점 패치

November 2026 Security Release

📅 2026-11-04📰 Next.js Blog
frontend

Next.js 팀이 2026년 11월, 캐시 관련 취약점을 중심으로 총 7건의 보안 이슈를 수정한 긴급 패치를 공개했습니다. 지난주 예고했던 보안 릴리스가 실제로 배포되었는데요, Cache Components와 use cache를 사용하는 애플리케이션이라면 반드시 확인해야 할 내용들입니다. 각 취약점이 어떤 조건에서 발생하고 어떤 영향을 미치는지 정리해보겠습니다.

패치 버전

다음 버전에서 이번 보안 이슈들이 수정되었습니다.

  • v16.4.5 (Active LTS)
  • v15.5.29 (Maintenance LTS)
npm install next@15.5.29 # for 15.5
npm install next@16.4.5 # for 16.5

가능한 빠르게 의존성을 업데이트하는 것을 권장합니다.

unstable_cache와 use cache 조합에서 발생하는 테넌트 간 캐시 노출 (높음)

GHSA-mfr8-8qww-v76h

Cache Components를 활성화한 애플리케이션에서, 동일한 public use cache 함수를 직접 호출하는 경로와 unstable_cache 내부에서 호출하는 경로가 공존할 때 루트 파라미터(예: 테넌트 식별자) 값 간 캐시 내용이 섞여버릴 수 있습니다.

콜드 캐시 상태에서 unstable_cache를 통한 동시 호출이 루트 파라미터 검증 없이 다른 요청의 결과를 그대로 받아버릴 수 있고, 이 결과는 동일한 인자로 들어오는 이후 요청들에게 해당 엔트리가 재검증되거나 제거될 때까지 그대로 서빙됩니다. 루트 파라미터로 테넌트를 구분하는 구조라면, 결과적으로 다른 테넌트의 데이터가 노출될 수 있습니다.

중첩된 use cache 함수에서의 루트 파라미터 간 노출 (중간)

GHSA-vc7v-qv4w-wrv8

Cache Components와 중첩된 public use cache 함수를 사용하는 애플리케이션에서, 한 루트 파라미터 값에 대해 생성된 콘텐츠가 다른 값에 대한 요청에 서빙될 수 있습니다. 내부의 캐시된 함수가 루트 파라미터를 읽어 빠른 값을 먼저 반환하면서 느린 비동기 값을 함께 반환하고, 외부 함수가 그 느린 값을 기다리지 않고 먼저 끝나버리는 구조에서 발생합니다.

이 경우 내부 함수의 루트 파라미터 의존성이 기록되기 전에 외부 엔트리가 저장될 수 있어, 테넌트·사이트·로케일별 콘텐츠가 해당 라우팅 경계를 넘어 노출될 수 있습니다. 다만 공격자가 임의의 응답 내용을 주입하는 것은 아니며, 애플리케이션이 생성한 콘텐츠가 잘못 재사용되는 형태입니다.

바이너리 인자를 통한 use cache 사용자 간 노출 및 오염 (중간)

GHSA-rhh4-g77r-r9qj

use cache 함수에 전달되는 서로 다른 바이너리 인자가 동일한 캐시 아이덴티티를 생성할 수 있습니다. 애플리케이션이 이런 인자로 사용자나 계정을 구분하고 있고 나머지 캐시 아이덴티티 입력값이 일치한다면, 한 호출자가 다른 사용자의 캐시 결과를 받거나 자신의 결과가 다른 사용자에게 서빙되게 만들 수 있습니다.

보안에 민감한 바이너리 인자를 use cache에 전달하고 그 결과를 여러 호출자가 공유하는 구조에서 영향을 받으며, 임의의 무관한 캐시 엔트리에 접근할 수 있는 것은 아닙니다.

셀프 호스팅 환경의 공유 셸 캐시 오염 (중간)

Cache Components를 활성화하고 Partial Prefetching을 비활성화했거나 설정하지 않은 상태로 next start를 실행하는 셀프 호스팅 애플리케이션에서, 인증되지 않은 요청만으로도 공유 페이지 셸이 오염될 수 있습니다. 조작된 URL이 요청 특정 값을 다른 URL이 사용하는 셸에 저장시켜, 잘못된 서버 렌더링 콘텐츠나 지속적인 404 응답이 발생할 수 있습니다.

영향을 받는 라우트의 조건은 다음과 같습니다.

  • 빌드 타임에 생성되지 않은 값으로 요청된 prerender 가능한 동적 파라미터가 존재
  • prerender되지 않는 더 깊은 파라미터가 최소 2개 이상 존재
  • blocking fallback 셸을 사용
  • 레이아웃이 Suspense 경계 내부에서 더 얕은 깊은 파라미터를 읽는 구조

빌드 타임에 생성된 값이나 Partial Prefetching이 활성화된 구성에서는 테스트 결과 영향이 확인되지 않았습니다.

오래된 압축 응답 프레이밍을 통한 클라이언트 간 응답 주입 및 노출 (중간)

GHSA-pc58-hwjq-p385

공격자가 제어하는 fetch된 Response를 변경 없이 그대로 반환하는 셀프 호스팅 애플리케이션은, 압축 해제된 본문 바이트를 원본 압축 응답의 프레이밍 헤더와 함께 전달할 수 있습니다. 이 불일치는 파이프라인된 요청을 공유 백엔드 커넥션에 큐잉하는 HTTP/1.1 리버스 프록시 뒤에서, 응답이 잘못된 클라이언트에게 할당되는 결과로 이어질 수 있습니다.

해당 커넥션 위의 요청 순서를 조작할 수 있는 공격자는 다른 클라이언트에게 전달될 응답을 주입하거나 다른 클라이언트의 응답을 가로챌 수 있습니다. 이 이슈는 설명된 프록시 동작을 전제로 하며, 모든 리버스 프록시 구성에 적용되는 것은 아닙니다.

Edge 라우트에서 내부 응답 헤더를 통한 쿠키 값 노출 (중간)

GHSA-f3mh-rxg3-f5g2

NextResponse.cookies.set()으로 쿠키를 설정하는 App Router Edge Route Handler와 Pages Router Edge API 라우트가, 내부용 x-middleware-set-cookie 응답 헤더를 통해 직렬화된 쿠키를 노출할 수 있습니다. Set-Cookie와 달리 이 헤더는 동일 출처의 JavaScript가 읽을 수 있어, HttpOnly로 표시된 쿠키라도 값이 노출될 수 있습니다.

영향이 발생하려면 민감한 쿠키가 해당 응답에 설정되어 있어야 하고, 동일 출처에서 공격자가 제어하는 JavaScript가 실행되고 있어야 합니다. 이 자체가 JavaScript 실행 수단은 아닙니다. 재현 테스트에서는 Node.js Route Handler나 cookies().set()으로 쿠키를 설정하는 라우트에는 영향이 없었습니다.

이미지 최적화에서 SVG 거부 우회 (중간)

GHSA-7qx7-33qx-rqx2

허용된 소스에서 가져온 공격자 제어 이미지가 AVIF로 잘못 분류되어 images.dangerouslyAllowSVG: false 설정을 우회할 수 있습니다. 그 결과 이미지 최적화 백엔드가 원본 바이트를 SVG로 식별하고 디코딩하게 되어, 애플리케이션이 Next.js 설정으로 명시적으로 배제한 파서에 도달하게 됩니다.

이미지 소스 allowlist 자체는 여전히 적용됩니다. 이 이슈는 SVG 디코딩이 가능한 네이티브 이미지 백엔드를 전제로 하며, SVG 파서의 리소스 고갈이나 디코더 취약점에 대한 노출을 증가시킵니다. 다만 이 발견 자체가 크로스 사이트 스크립팅이나 원격 코드 실행을 입증하는 것은 아닙니다.

보안 프로그램

Next.js 팀은 Vercel의 Open Source Bug Bounty를 통해 보안 연구자들과 협력하여 Next.js를 비롯한 오픈소스 프레임워크의 보안을 강화하고 있습니다. 해당 프레임워크들의 보안에 기여하고 싶은 분들은 이 프로그램에 참여할 수 있습니다. 보안 프로그램이나 취약점 관리에 관한 문의는 security@vercel.com으로 보낼 수 있습니다.

정리

이번 보안 릴리스는 대부분 Cache Components와 use cache 관련 기능을 중심으로 발생한 테넌트/사용자 간 캐시 교차 노출 이슈라는 공통점이 있습니다. 특히 다음 사항을 확인해보시길 권장합니다.

  • Cache Components와 use cache를 사용 중이라면 높음 등급의 unstable_cache 조합 이슈(GHSA-mfr8-8qww-v76h)를 포함해 즉시 패치가 필요합니다.
  • 셀프 호스팅 환경에서 next start를 운영 중이고 Partial Prefetching을 설정하지 않았다면 공유 셸 캐시 오염 취약점에 노출될 수 있으므로 우선순위를 높여 패치해야 합니다.
  • Edge Route Handler에서 쿠키를 다루는 경우 NextResponse.cookies.set() 대신 cookies().set() 사용 여부를 점검해볼 만합니다.
  • 이미지 최적화에서 dangerouslyAllowSVG: false를 신뢰하고 있었다면 이번 패치 전까지는 우회 가능성이 있었다는 점을 인지해야 합니다.

영향 범위가 제한적인 이슈도 섞여 있지만, 멀티테넌트 서비스를 운영 중이라면 캐시 교차 노출은 치명적일 수 있는 만큼 v16.4.5 / v15.5.29로의 업그레이드를 최대한 빠르게 진행하는 것이 좋습니다.

💡
Cache Components나 use cache, 셀프 호스팅 배포를 사용 중인 Next.js 애플리케이션이라면 테넌트/사용자 데이터가 섞여 노출될 수 있는 심각한 문제이므로, 프론트엔드 개발자도 즉시 버전을 확인하고 패치해야 합니다.
