Rivet: S3 위에서 수십억 개의 Actor를 돌리는 에이전트 오케스트레이션 플랫폼

AI 에이전트를 운영하다 보면 결국 마주치는 문제가 있습니다. 에이전트 하나하나를 샌드박스(VM/컨테이너)로 띄우면 콜드 스타트가 느리고, 추론을 기다리는 동안에도 자원을 통째로 점유하게 됩니다. YC W23 배치의 Rivet은 이 문제를 "Actor"라는 경량 프로세스 모델과 S3 기반 스토리지로 풀어낸 오픈소스 프로젝트입니다. Hacker News에 올라온 Launch 글과 GitHub 저장소 내용을 바탕으로 Rivet이 무엇을 제공하는지 정리해봅니다.

Rivet Actor란 무엇인가

Rivet Actor는 인메모리 상태, SQLite 데이터베이스, WebSocket, 스케줄링 기능을 갖춘 장수명(long-lived) 프로세스입니다. 에이전트, 사용자, 세션, 테넌트 단위로 하나씩 만들어 쓰는 구조입니다.

핵심 특징은 다음과 같습니다.

  • Actor당 72KB: 각 Actor가 샌드박스를 따로 부팅하는 대신 하나의 노드 프로세스를 공유하기 때문에, 서버 한 대가 수십만 개의 Actor를 담을 수 있습니다.
  • p99 콜드 스타트 4.99ms: 이미지 풀이나 VM 부팅 과정이 없습니다.
  • S3 기반 확장성: 모든 데이터가 S3에 저장되므로 클러스터가 수십억 개의 Actor까지 확장됩니다.
  • 유휴 시 하이버네이션, 요청 시 즉시 깨어남: 놀고 있는 Actor는 비용이 발생하지 않고, 다음 요청이 오면 아무것도 손실되지 않은 채 깨어납니다.
  • S3 기반 SQLite, SSD급 속도: p99 기준 durable write 1.07ms, read 1.36ms로, 복제된 SSD 스토리지 대비 약 10.4배 저렴합니다.

주요 활용 사례로는 재시작에도 살아남는 메모리를 가진 멀티플레이어 AI 에이전트, 처음부터 다시 시작하지 않고 재생(replay)되는 워크플로우, AI가 생성한 앱/Actor 실행, 문서당 Actor 하나로 모든 편집자와 동기화되는 협업 편집 등이 있습니다.

코드로 보는 최소 에이전트 예시

Rivet이 제공하는 rivetkit 라이브러리로 에이전트를 처음부터 작성하면 이런 모습입니다.

// server.ts
import { actor, setup } from "rivetkit";
import { db } from "rivetkit/db";
import { streamText } from "ai";
import { openai } from "@ai-sdk/openai";

// One Actor per agent, created on first use: agent.getOrCreate(["agent-123"])
export const agent = actor({
  // 1. SQLite: every agent has its own database, so history survives restarts
  db: db({
    onMigrate: async (db) => {
      await db.execute("CREATE TABLE IF NOT EXISTS messages (role TEXT, content TEXT)");
    },
  }),
  // 2. In-memory state: plain variables that live with the Actor, with no database round trip
  createVars: () => ({ online: new Map<string, string>() }),
  // 3. WebSockets: each client holds a live connection, and the Actor pushes to all of them
  onDisconnect: (c, conn) => {
    c.vars.online.delete(conn.id);
    c.broadcast("online", [...c.vars.online.values()]);
  },
  actions: {
    join: (c, user: string) => {
      c.vars.online.set(c.conn.id, user);
      c.broadcast("online", [...c.vars.online.values()]);
    },
    sendMessage: async (c, text: string) => {
      // Save the message
      await c.db.execute("INSERT INTO messages VALUES (?, ?)", "user", text);
      const messages = await c.db.execute("SELECT role, content FROM messages");

      // Stream tokens to every connected client
      const response = streamText({ model: openai("gpt-5"), messages });
      for await (const delta of response.textStream) {
        c.broadcast("token", delta);
      }

      // Save the response
      await c.db.execute("INSERT INTO messages VALUES (?, ?)", "assistant", await response.text);
    },
  },
});

export const registry = setup({ use: { agent } });
// client.ts (frontend or backend)
import { createClient } from "rivetkit/client";
import type { registry } from "./server";

const client = createClient<typeof registry>();

// Open a WebSocket connection to the agent
const agent = client.agent.getOrCreate(["agent-123"]).connect();

// Listen for realtime events
agent.on("online", users => console.log("online:", users));
agent.on("token", delta => process.stdout.write(delta));

// Call actions on the Actor
await agent.join("nathan");
await agent.sendMessage("how many r's in strawberry?");

SQLite는 재시작에도 히스토리가 살아남도록 Actor마다 독립된 DB를 갖고, 인메모리 상태는 DB 왕복 없이 바로 접근 가능한 일반 변수로 다뤄집니다. WebSocket 연결은 Actor가 모든 연결된 클라이언트에 직접 브로드캐스트하는 방식입니다.

왜 에이전트를 Rivet Actor 위에서 돌려야 하는가

에이전트는 대부분의 시간을 추론(inference) 대기에 씁니다. 이 루프를 샌드박스 안에서 돌리면 CPU 사용률은 낮은데도 VM 전체를 계속 점유하는 비용을 치르게 됩니다.

Rivet은 에이전트 루프를 샌드박스 밖에서 돌리는 방식, 즉 "머리(head)와 손(hands)을 분리"하는 패턴을 취합니다. 에이전트의 상태·메모리·컨텍스트는 Actor 안에 머물고, 코드를 실제로 실행해야 할 때만 도구(tool)를 통해 샌드박스에 접근합니다. 이렇게 하면 메모리 사용량이 크게 줄고, 실행되는 코드의 피해 범위(blast radius)와 신뢰 경계(trust boundary)도 제한됩니다.

Actor에 샌드박스가 꼭 필요할까

에이전트가 샌드박스를 필요로 하는 경우는 자신이 작성한 코드를 실행해야 할 때뿐입니다. Rivet 사용자들은 세 가지 패턴 중 하나를 씁니다.

  • 도구만 쓰는 에이전트: 고객 지원이나 개인 비서 에이전트처럼 tool call, MCP, API 호출만 필요한 경우 샌드박스가 아예 필요 없습니다.
  • 경량 샌드박스를 쓰는 에이전트: agentOS가 V8과 WebAssembly로 JS/Python에 대한 Linux 호환 샌드박싱을 제공합니다. POSIX 파일시스템, 네트워킹 스택, 프로세스 트리를 완비하고 있어 데이터 분석, 파일 처리, 평가(eval), 코드 모드 같은 대부분의 워크로드를 커버합니다.
  • 완전한 샌드박스를 쓰는 에이전트: 기존에 쓰던 샌드박스 제공자를 그대로 유지하면서, 셸이나 파일시스템을 도구로 노출시키는 방식입니다(예: 샌드박스 안에서 명령을 실행하는 bash 도구). Actor는 sleep이나 재시작 이후에도 해당 샌드박스에 다시 연결됩니다.

Actor vs 샌드박스 벤치마크

Rivet이 공개한 수치를 비교하면 다음과 같습니다.

지표Rivet ActorSandbox
콜드 스타트 (p99)4.99 ms1.70 s
인스턴스당 메모리72.4 KB512 MiB
스토리지S3 위의 SQLite샌드박스별 디스크
스토리지 비용10.4배 저렴복제된 SSD

Rivet 수치는 Rivet 3.0.3에서 실행한 "Rivet Actors vs Cloudflare Durable Objects" 벤치마크에서 나온 것이며, 원본 샘플과 재현 스크립트는 공개 저장소에 있습니다. 샌드박스 수치는 E2B 기준으로, 512MiB는 2026년 11월 4일 시점 E2B 과금 문서의 기본 메모리 할당량이고, 1.70초는 2026년 10월 30일 ComputeSDK의 샌드박스 벤치마크에서 가져온 p99 콜드 스타트 값입니다. 스토리지 비용은 S3 Standard와 Amazon EBS gp3 3중 복제본을 AWS 정가 기준으로 비교한 결과입니다.

주요 기능과 배포 옵션

Rivet은 다음과 같은 기능을 기본 제공합니다.

  • 장애 허용: 노드가 죽어도 해당 Actor들이 상태를 그대로 유지한 채 다른 노드로 이동
  • HTTP & WebSocket 네트워킹: HTTP 호출 또는 실시간 WebSocket 연결 모두 지원
  • 엔드투엔드 타입 안전성: 백엔드용 타입 클라이언트, 프론트엔드용 React 훅
  • Cron & 스케줄링: 정해진 시간이나 Actor 스스로 설정한 시점에 깨우기
  • Actor 간 호출: 클러스터 전역에서 key로 서로를 호출
  • 스코프드 JWT: 클라이언트가 접근 가능한 Actor를 제한한 JWT 발급
  • OpenTelemetry: OTel 포맷의 트레이스, 메트릭, 로그

배포는 로컬/자체 호스팅(Docker, Kubernetes, VM — 의존성은 S3뿐), Rivet Cloud(AWS/GCP 완전 관리형 전용 클러스터), BYOC(컨트롤 플레인이 사용자 VPC 안에서 동작하고 Rivet이 관리) 세 가지 옵션을 제공하며, 모든 옵션이 동일한 컨트롤 플레인을 사용합니다. Node.js와 Bun 네이티브 런타임 위에서 동작하므로 커스텀 런타임이 없고, 기존 패키지·툴링·테스트가 그대로 동작합니다.

Cloudflare Durable Objects와의 차이

Rivet은 자체 호스팅이 쉽고 확장 가능한 Durable Objects의 오픈소스 대안으로 자주 언급됩니다. Durable Objects의 몇 가지 제약을 해결했다고 설명하는데, 128MB 메모리 상한이 없고, 10GB SQLite 제한 대신 무제한에 가까운 스토리지를 제공하며, Actor가 무작위로 축출(evict)되지 않고, 커스텀 런타임이 아닌 Node.js/Bun 위에서 동작하므로 런타임을 직접 제어할 수 있습니다. 여기에 커넥션 핸들링, 이벤트 브로드캐스팅, durable 스케줄링과 cron, Vitest 완전 지원, draining을 위한 라이프사이클 훅, Actor 업그레이드 제어 기능이 추가로 제공됩니다.

또한 Postgres, FoundationDB, NATS 같은 별도 의존성이 필요 없고, 오브젝트 스토리지 버킷 하나만 있으면 됩니다. Amazon S3, Google Cloud Storage, Azure Blob Storage뿐 아니라 MinIO, Cloudflare R2, Hetzner Object Storage 같은 S3 호환 스토리지도 지원하며, 로컬 파일시스템 백엔드로 단일 머신에서 테스트해볼 수도 있습니다.

아키텍처 측면에서는 virtual actor 패턴을 구현한다는 점에서 Microsoft Orleans와 가장 가깝지만, 단순 JSON 저장소 대신 SQLite 영속성을 쓰고 모던 런타임을 지원한다는 점이 다릅니다. Erlang이나 Akka는 기본적으로 virtual actor를 제공하지 않지만, 비슷한 기능을 제공하는 생태계 패키지들이 존재합니다. microVM, gVisor, nested virtualization 같은 것도 전혀 필요 없고, 컨트롤 플레인에 WebSocket으로 연결되는 표준 프로세스만 있으면 됩니다(Node.js, Bun, Rust 등 무엇이든 가능).

정리

  • Rivet Actor는 공유 노드 프로세스 위에서 돌아가는 경량 Actor로, Actor당 72KB 메모리와 p99 4.99ms 콜드 스타트를 내세우며 샌드박스 기반 VM/컨테이너(512MiB, p99 1.70초) 대비 압도적으로 가볍습니다.
  • 모든 데이터가 S3에 저장되고 SQLite가 S3 위에서 SSD급 속도(p99 write 1.07ms, read 1.36ms)로 동작하기 때문에, 별도 DB나 메시지 버스 없이 오브젝트 스토리지만으로 클러스터를 수십억 Actor 규모까지 확장할 수 있습니다.
  • 에이전트 루프(머리)와 코드 실행 샌드박스(손)를 분리하는 아키텍처를 권장하며, 실제로 샌드박스가 필요한 경우는 에이전트가 코드를 실행해야 할 때뿐이라는 점을 강조합니다. 도구 전용, 경량 샌드박스(agentOS), 완전한 외부 샌드박스 연동까지 세 단계 패턴을 제공합니다.
  • Cloudflare Durable Objects의 오픈소스 대안을 표방하며 128MB 메모리 상한, 10GB SQLite 제한, 무작위 축출 같은 제약을 없앴고, Node.js/Bun 네이티브 런타임이라 커스텀 런타임 제약도 없습니다.
  • 로컬 개발, 자체 호스팅, Rivet Cloud, BYOC까지 동일한 컨트롤 플레인으로 배포할 수 있어, 실시간 멀티플레이어 AI 에이전트나 세션당 상태를 유지해야 하는 백엔드를 구축하는 프론트엔드/풀스택 개발자에게 인프라 선택지로 검토해볼 만합니다.
