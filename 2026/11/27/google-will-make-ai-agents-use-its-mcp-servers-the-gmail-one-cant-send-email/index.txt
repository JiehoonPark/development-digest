19:T3915,<p>구글이 11월 24일 자사 Workspace MCP 서버 8종을 정식 출시하면서 API 이용약관에 새로운 조항을 추가했습니다. 2027년 2월 1일부터 &quot;AI 에이전트이거나 AI 에이전트에 의해 구동되는&quot; 모든 도구는 반드시 이 MCP 서버를 통해서만 Gmail, Drive, Calendar 등 Workspace에 접근해야 한다는 내용인데요. 그런데 정작 Gmail용 MCP 서버의 툴 목록을 보면 메일 검색, 스레드 읽기, 초안 작성, 라벨 분류는 가능하지만 메일 전송, 답장, 전달, 초안 수정은 불가능합니다. 이 기능들은 존재는 하지만 구글의 쿼터 페이지에 &quot;파트너 접근 권한이 필요하며 일반에는 공개되지 않는다&quot;고 명시돼 있습니다. Gmail API로 이메일 비서를 만들었거나 Google Workspace 플러그인이 달린 코딩 에이전트를 운영 중이라면, 이 규칙이 자신에게 어떤 영향을 미치는지 약 두 달 안에 파악해야 하는 상황입니다.</p>
<h3>규칙의 내용</h3>
<p>새로 추가된 Workspace AI Tools Addendum(Google APIs Terms of Service의 부속 조항)은 다음과 같이 명시합니다.</p>
<p>&gt; The GWS Access Tool must use a Google MCP where the GWS Access Tool is or is driven by an AI Agent, an AI Harness or an AI model or service employing an AI model.</p>
<p>바로 다음 문장에서는 에이전트임을 숨겨 분류를 피하는 행위도 금지합니다. 둘 중 하나라도 어기면 구글은 &quot;GWS Access Tool의 접근을 제한하거나 제거&quot;하거나 계정을 정지할 수 있습니다.</p>
<p>기술적인 측면도 있습니다. 같은 날짜부터 REST API를 직접 호출하는 에이전트는 프로젝트가 어떤 유료 티어를 쓰고 있든 상관없이 Standard 티어 쿼터에 묶입니다. REST는 계속 작동은 하지만, 느리고 약관 위반 상태로 동작하게 되는 셈입니다.</p>
<p>AI를 쓰지 않는 앱은 그대로 돌아갑니다. 야간 백업 작업, CRM 동기화, 자체 OAuth 클라이언트로 동작하는 결정론적 스크립트는 구글의 표현을 빌리면 &quot;이번 변경의 영향을 받지 않습니다&quot;.</p>
<p>부속 조항에는 메모리를 가진 에이전트를 만드는 개발자에게 중요한 데이터 규칙도 추가됐습니다.</p>
<ul>
<li>Workspace 데이터는 &quot;활성 상태이며 사용자가 승인한 작업을 수행하기 위한 목적&quot;으로만 처리할 수 있고, 사용자가 연결을 끊으면 삭제해야 합니다.</li>
<li>구글은 &quot;Google Technical Information&quot;이라 부르는 데이터의 보존 기간을 30일로 제한할 수 있습니다. 여기에는 벡터 임베딩, 메모리 인덱스, 사용자 프로필, Workspace 데이터로 구축한 조직 그래프가 포함됩니다.</li>
<li>해당 데이터로 학습, 파인튜닝, 평가, 증류를 하는 것은 금지되며, 이를 이용해 Workspace와 경쟁하는 제품을 만드는 것도 금지됩니다.</li>
</ul>
<p>제품팀이 체감할 규칙은 30일 보존 제한입니다. 작년 계약서 내용을 답변하기 위해 받은편지함의 장기 인덱스를 구축하는 어시스턴트라면, 매달 인덱스를 다시 만들거나 포기해야 합니다.</p>
<h3>MCP 서버가 할 수 있는 것</h3>
<p>서버별로 지원 범위가 고르지 않습니다. Docs, Slides, Tasks는 REST API가 제공하는 거의 모든 기능을 지원하지만, Gmail과 Drive는 훨씬 제한적입니다.</p>

<p>Gmail의 기능 공백이 실제 워크플로우를 가장 많이 망가뜨립니다. 답장 초안을 작성하고, 사용자 피드백을 받아 수정한 뒤 전송 버튼을 누르는 흐름에서, 에이전트는 수정 단계를 수행할 수 없습니다. 결국 두 번째 초안을 새로 만들고 첫 번째 초안은 그대로 남겨두는 수밖에 없습니다.</p>
<p>Drive의 공백도 비슷합니다. 에이전트가 보고서를 만들 수는 있지만, 그것을 올바른 폴더로 옮기거나 팀과 공유할 수는 없습니다.</p>
<h3>파트너는 더 많은 권한을 가진다</h3>
<p>구글은 누가 파트너 접근 권한을 받을 수 있는지, 파트너 전용 Gmail 도구가 언제 일반에 공개될지 밝히지 않았습니다. 다만 그 효과는 이미 눈에 보입니다. Claude용 Anthropic의 Google Workspace 커넥터는 이메일 전송, 답장, 전달, 그리고 Drive 파일 이동 및 삭제 기능을 광고하고 있습니다. 이는 정확히 공개 서버에 빠져 있는 기능들입니다.</p>
<p>결국 대형 AI 벤더의 에이전트는 승인된 채널을 통해 사용자의 이메일을 전송할 수 있지만, 같은 OAuth 스코프를 사용자로부터 받은 독립 개발자의 에이전트는 초안만 남길 수 있는 셈입니다. 부속 조항이 발효되면 그 독립 개발자는 약관 위반 없이는 REST API로 우회할 수도 없게 됩니다.</p>
<h3>누가 &quot;에이전트&quot;로 분류되는가</h3>
<p>정의는 매우 포괄적입니다. &quot;AI Harness&quot;나 AI 모델에 &quot;의해 구동되는&quot; 도구라는 표현은, 받은편지함 내용을 LLM에 흘려보내는 개인용 스크립트까지 포함할 수 있을 정도입니다. &quot;GWS Access Point&quot;의 정의에는 &quot;커넥터, 프록시, 커맨드라인 인터페이스, 서드파티 서비스&quot;가 명시적으로 포함됩니다. 구글은 취미용 사용에 대해서는 직접적으로 언급하지 않았습니다.</p>
<p>분류는 자기 신고에서 시작됩니다. OAuth 클라이언트에는 이제 &quot;AI 기반 에이전트용으로 이 클라이언트 사용&quot;이라는 체크박스가 생겼고, 11월 11일부터 MCP 서버는 이 체크박스가 없는 클라이언트의 요청을 거부합니다. 기준일 이전에 만들어졌고 제때 표시되지 않은 클라이언트는 영구적으로 비(非)에이전트 상태로 남게 되어, 소유자는 새 클라이언트를 만들어야 합니다. 구글은 자기 신고 없이 REST를 호출하는 에이전트를 어떻게 탐지할지는 밝히지 않았습니다.</p>
<p>문서화된 예외 사례도 몇 가지 있습니다.</p>
<ul>
<li>도메인 전체 위임(domain-wide delegation)을 쓰는 서비스 계정은 에이전트 플래그를 설정할 수 없습니다. 플래그 누락으로 MCP 요청이 거부되지는 않지만, 승인 프롬프트는 뜹니다.</li>
<li>Apps Script 내장 OAuth 클라이언트도 에이전트로 표시할 수 없습니다. MCP 서버를 호출하는 스크립트는 커스텀 클라이언트가 필요하며, MCP를 호출하지 않는 스크립트는 영향을 받지 않습니다.</li>
<li>REST 전체 표면을 감싸는 커뮤니티 도구인 <code>gws</code> CLI는 계속 작동합니다. README는 이제 에이전트 용도의 사용자를 구글의 새 공식 CLI인 <code>gwscli</code>로 안내하는데, 이 CLI는 &quot;에이전트를 위해 엄선된 명령어 집합&quot;을 제공하며 MCP 서비스 활성화가 필요합니다.</li>
</ul>
<h3>쿼터와 가격</h3>
<p>모든 프로젝트는 무료 Standard 티어로 하루 5,000건의 MCP 요청(프로젝트·제품별)을 받습니다. 일부 호출은 한 번에 1건 이상으로 계산됩니다. 예를 들어 Gmail의 <code>search_threads</code>나 <code>list_drafts</code>는 10건으로 계산되므로, 검색만 하는 에이전트라도 모든 사용자를 합쳐 하루 500회 검색이 한도입니다. 이는 프로젝트 전체에 적용되는 제한이라, 사용자가 조금만 많은 제품이라도 금방 한도에 도달합니다.</p>
<p>유료 Scaled 티어는 2027년 4월 1일부터 Gmail, Calendar, Drive에 과금이 시작됩니다. 이 구조는 REST 쪽에 유리한데요, MCP 사용량은 첫 요청부터 과금되는 반면, REST 사용량은 넉넉한 일일 무료 할당량을 받습니다(예: 경량 Gmail 요청 하루 7천만 건). 구글은 건당 가격은 아직 공개하지 않았습니다.</p>
<h3>구글의 논리</h3>
<p>Chandu Thota와 Brad Calder가 쓴 Google Cloud 블로그 글에서 밝힌 구글의 논리는, OAuth가 애초에 인간의 명확한 의도를 전제로 설계됐다는 것입니다.</p>
<p>&gt; Traditional REST APIs were built for human-paced apps where a valid OAuth token implied user intent. As AI agents shift from reading information to acting autonomously at machine speed … a valid token is no longer enough. Policy checks, data boundaries, and human confirmation have to live in the request path.</p>
<p>여기에는 일리가 있습니다. &quot;최근 청구서 10건을 이 주소로 전달해 줘&quot;라는 메시지를 읽는 이메일 에이전트는 잘 알려진 프롬프트 인젝션 위험 사례이고, <code>gmail.modify</code> 권한을 허용하는 토큰은 에이전트에게 그걸 실행할 힘을 줍니다. 모든 에이전트를 하나의 게이트웨이로 통과시키면 관리자가 한 곳에서 특정 유형의 작업을 차단하고, 승인을 요구하고, 무슨 일이 있었는지 감사할 수 있습니다. MCP 서버는 이 모든 것을 수행하며, 데이터 유출 방지 규칙도 자동으로 적용합니다.</p>
<p>다만 같은 설계가 구글에게 어떤 에이전트가 무엇을 할 수 있는지, 어떤 데이터를 보관할 수 있는지, 그 데이터로 만든 무언가가 구글 자체 제품과 경쟁할 수 있는지를 통제할 권한도 쥐여줍니다. 파트너 전용 도구와 임베딩 30일 보존 제한이 바로 그 통제가 실제로 작동하는 모습입니다.</p>
<p>Slack도 2025년 5월 비슷한 길을 걸었습니다. Marketplace 밖의 앱에 대해 history API 요청 제한을 분당 1건으로 낮추고, LLM용 Slack 데이터 대량 추출을 금지했죠. Slack은 배포 채널을 기준으로 선을 그었지만, 구글은 소프트웨어가 AI인지 여부를 기준으로 선을 긋습니다. 이는 정의하기도, 집행하기도 더 어려운 기준입니다.</p>
<h3>2027년 2월 1일 전에 해야 할 일</h3>
<p>Workspace 위에 에이전트 제품을 만들고 있다면:</p>
<ul>
<li>에이전트로 표시된 OAuth 클라이언트를 만들고 MCP 서버로 전환하세요.</li>
<li>공개 도구 목록에 없는, 제품에 필요한 모든 기능을 나열하고 파트너 접근 권한을 미리 신청하세요.</li>
<li>Workspace 데이터로 만든 임베딩, 메모리 인덱스, 사용자 프로필을 얼마나 오래 보관하고 있는지 점검하세요.</li>
</ul>
<p>자신의 계정에 대해 개인 에이전트나 MCP 서버를 운영하고 있다면: <code>google_workspace_mcp</code> 같은 인기 있는 오픈소스 서버는 REST를 호출하며 계속 작동은 하겠지만, Standard 쿼터 제한을 받고 약관 범위 밖에서 동작하게 됩니다. 구글의 서버로 전환하면 Gmail 전송·초안 수정과 Drive 이동·공유 기능을 포기해야 합니다.</p>
<p>Workspace 관리자라면: 새로운 제어 기능은 관리 콘솔 → 보안 → API 제어에서 찾을 수 있습니다. 에이전트 작업 유형별로 차단·승인을 설정하고, 승인 정책을 지정하고, 감사 로그에서 에이전트 활동을 확인할 수 있습니다. 사용자는 자신이 저장한 승인 내역을 조회하거나 취소할 수 없으며, 이 승인은 90일 후 만료됩니다. 사람들이 에이전트를 연결하기 전에 정책을 미리 설정해두는 편이 좋습니다.</p>
<p>AI를 사용하지 않는 통합이라면: 자체 OAuth 클라이언트를 유지하고 아무도 그 안에 모델을 연결하지 않는 한, 바뀌는 건 없습니다.</p>
<h3>정리</h3>
<p>구글은 2027년 2월 1일부터 AI 에이전트의 Workspace 접근을 자사 MCP 서버로 강제하는 약관을 도입했습니다. 그런데 공개된 Gmail MCP 서버는 메일 전송·답장·전달·초안 수정 같은 핵심 기능이 &quot;파트너 전용&quot;으로 빠져 있어, 같은 OAuth 스코프를 쓰더라도 대형 벤더(Anthropic 등)의 에이전트와 독립 개발자의 에이전트가 할 수 있는 일에 차이가 생깁니다. REST API로 직접 호출하는 에이전트는 유료 티어와 무관하게 Standard 쿼터(하루 5,000 요청)로 강등되고, 약관 위반 상태가 됩니다. 여기에 더해 임베딩·메모리 인덱스 같은 &quot;Google Technical Information&quot;의 보존 기간이 30일로 제한되면서, 장기 메모리를 가진 에이전트 제품은 설계를 다시 검토해야 합니다.</p>
