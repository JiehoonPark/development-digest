AI 시대에도 JS 프레임워크 선택은 여전히 '느낌'인가: 실제로 벤치마크해봤다

웹 개발 커뮤니티의 오래된 고질병 중 하나는 많은 결정이 '느낌'에 근거한다는 점입니다. 프레임워크는 "엄청 빠르고", 도구는 개발을 "초강력하게" 만들어주며, 올바른 추상화는 DX와 UX를 동시에 잡아준다는 식의 주장이 근거 없이 쏟아집니다. Alex Russell은 이를 "프론트엔드의 잃어버린 10년"이라 불렀고, Baldur Bjarnason은 프로그래밍을 하나의 팝 컬처라고 표현했습니다. Nolan Lawson은 자신의 블로그에서 이런 흐름에 맞서 사실과 벤치마크로 반박해왔다고 말합니다.

그동안은 이런 '증거 알레르기'가 더 나은 DX를 향한 욕망에서 비롯됐다고 여겨졌습니다. 개발자들이 React에서 JSX를 타이핑하는 느낌을 좋아했고, "가상 DOM이 빠르다" 같은 주장은 그 직관을 사후에 정당화하는 논리에 불과했다는 것이죠(심리학자 Jonathan Haidt도 이 해석에 동의할 법합니다). 그런데 에이전트가 코드를 대신 작성하는 시대가 되어 개발자가 DX에 덜 얽매이게 된 지금도, 여전히 '느낌'이 지배하고 있습니다. "이 프레임워크가 에이전트에게 더 낫다"는 이유로 프론트엔드를 통째로 다시 짜는 사례들이 나오는데, 정작 그 주장을 검증한 벤치마크는 찾아보기 어렵습니다. 그래서 저자는 직접 벤치마크를 만들었습니다.

벤치마크 설계

구조는 단순합니다.

  • PokéAPI를 활용한 작지만 단순하지 않은 포켓몬 앱을 설계한다
  • 에이전트에게 특정 JS 프레임워크/메타 프레임워크(Next.js, Nuxt, SvelteKit 등)로 이 앱을 만들게 지시한다
  • 스펙 준수 테스트 스위트로 결과물을 검증한다(에이전트의 꼼수 방지)
  • 개발 시간, 토큰 소비량, 코드 줄 수, Lighthouse의 성능·접근성 점수로 결과를 평가한다

앱은 포켓몬 목록과 타입, 기술, 각 게임별 데이터를 보여주고 검색·필터링이 가능한 수준입니다. 콘텐츠 중심적이고 상호작용이 적은, Figma나 GMail보다는 위키백과에 가까운 '홀로타입' 하나만 대표한다는 한계는 있지만, 이해하기 쉽고 스펙을 작성·테스트하기 수월하다는 이유로 선택했습니다.

공정성을 위해 각 프레임워크마다 공식 MCP나 스킬을 사용하게 했습니다. "이 프레임워크는 학습 데이터에 잘 반영 안 돼서 우리가 MCP를 만든 거다, 그걸 써야 한다"는 식의 반박을 피하기 위해서입니다. 아키텍처(SSR vs CSR 등)를 과도하게 지정하지도 않았고, "최대한 성능을 뽑아내라"는 지시도 하지 않았습니다. Opus 5.5(high effort)에 스펙만 주고 해당 프레임워크의 최신 버전을 쓰라고 했을 뿐입니다. 각 에이전트는 샌드박스에서 작업했고, Lighthouse로 성능·접근성을 테스트받을 거라는 사실은 몰랐지만 준수 테스트 스위트는 알고 있었습니다.

CSS 방법론도 강제하지 않았습니다. 다만 Tailwind, Bootstrap 등 컴포넌트 프레임워크는 쓰지 못하게 했고, 시각적 일관성을 위해 스펙 토큰 기반으로 디자인하게 했습니다. 이 실험의 초점은 CSS가 아니라 JS 프레임워크, CSR vs SSR, SPA vs MPA 등이기 때문입니다. 결과물은 원시 DOM이 아니라 접근성 트리 기반의 준수 테스트 스위트로 검증했는데, 웹 컴포넌트(shadow DOM)를 쓰는 프레임워크도 있어서 특정 HTML 구조를 강제하지 않기 위함입니다.

실험을 통해 배운 한 가지는, 측정하는 모든 것이 상당히 확률적이라는 점입니다. LLM은 본질적으로 랜덤 단어 생성기라서, 프레임워크나 도구 자체와 무관하게 에이전트가 엉뚱한 방향으로 새서 토큰을 낭비하는 경우도 있습니다. Lighthouse 자체도 일관성이 떨어져서, LCP(Largest Contentful Paint)가 실행마다 다른 이미지를 '가장 큰 요소'로 판단하기도 합니다. 완벽하게 공정한 실험은 어렵지만, 여러 번 반복 실행하는 것으로 어느 정도 보완했고, 분산에 대해서도 최대한 솔직하게 밝히고 있습니다.

이 수치는 Claude Code가 보고하는 API 가격을 그대로 인용한 것으로, 저자가 실제로 지출한 금액은 아닙니다(Max 플랜으로 월 $100 안에서 해결됐다고 합니다).

분산도 눈여겨볼 만합니다. React Router의 중앙값은 Hono+htmx보다 약 $1 비싸지만, React Router의 최저가($2.82)가 Hono+htmx의 최고가($3.19)보다 오히려 쌉니다. 그럼에도 몇 가지 패턴은 분명합니다. SvelteKit, Gracile+Lit, Angular가 확실히 비싸게 나왔는데, SvelteKit은 매 실행마다 에이전트가 SvelteKit v3 마이그레이션 가이드를 읽은 탓으로 보입니다(너무 최신이라 Opus 5.5의 학습 데이터에 없었을 가능성). Gracile도 에이전트가 프레임워크를 잘 몰라서 저장소를 clone하거나 node_modules의 컴파일된 소스를 직접 읽는 경우가 있었습니다. Angular는 전체 코드 크기와 관련 있는 것으로 보입니다(뒤에서 설명).

모든 에이전트가 MCP/스킬/플러그인을 활용한 것도 아니고, 모든 프레임워크에 그런 도구가 있는 것도 아니었습니다.

예를 들어 TanStack Start의 스킬 파일(node_modules 안에 포함)은 5번 중 2번만 발견됐고, Nuxt의 MCP는 한 번도 사용되지 않았습니다. Next.js도 스킬 파일은 1/5, AGENTS.md는 2/5만 읽혔습니다. 이렇게 결과 편차가 큰 것 자체가 LLM의 확률적 특성을 보여주지만, 실제 '바이브 코더'들이 에이전트에게 대문자로 "MCP 써!"라고 소리치는 경우는 거의 없을 것이므로 이 역시 유효한 실험 조건이라고 저자는 판단합니다.

참고로 "Hono+htmx" 조합은 htmx를 실험에 포함시키고 싶어서 Rails/Django 류의 JS 대안으로 Hono를 짝지은 것이고, "Gracile+Lit"은 웹 컴포넌트의 대표 주자인 Lit을 위해 알고 있던 유일한 메타 프레임워크인 Gracile을 선택한 것입니다. 더 나은 후보가 있다면 후속 실험에 반영할 수 있다고 밝혔습니다.

"Vanilla"는 "UI 프레임워크 없이 바닐라 JavaScript/TypeScript + Vite"로 지시한 결과인데, 흥미롭게도 여러 프레임워크보다 성능이 떨어졌습니다. 이는 아무것도 없는 것(혹은 순수 Vite)보다 어떤 프레임워크든 있는 편이 나을 수 있다는 점을 시사합니다. Vite를 기준으로 삼은 이유는 수많은 프레임워크의 기반이 되는, 비교적 표준적이고 중립적인 JS 인프라이기 때문입니다.

결과: 품질

비용뿐 아니라 결과물의 품질도 중요하기에 Lighthouse로 성능·접근성도 측정했습니다. 다만 두 가지 한계가 있습니다. 첫째, 포켓몬 앱은 작아서 실제 대규모 애플리케이션을 대표하지 못합니다. 둘째, Lighthouse와 Core Web Vitals 자체가 SPA에 불리하게 설계돼 있어서, TBT(Total Blocking Time)나 JS 바이트 수 같은 지표에서는 MPA 프레임워크가 거의 자동으로 유리합니다. 앱 내부 성능 지표를 직접 만들어 추가하는 것도 고려했지만, 복잡도와 변동성만 늘어날 것 같아 포기하고 업계 표준 지표만 사용했습니다. 편의상 홈페이지 점수만 보고했는데, 다른 페이지들은 비슷하거나 LCP 등에서 변동폭이 커서 복잡도만 늘기 때문입니다.

결론부터 말하면, Performance·Accessibility·CLS(Cumulative Layout Shift) 점수는 거의 포화 상태라 프레임워크 간 차이가 거의 없습니다.

정리

  • 이 실험은 "AI 시대엔 어떤 프레임워크가 에이전트에게 유리하다"는 식의 근거 없는 주장에 실제 벤치마크로 반박을 시도한 사례입니다. Opus 5.5 에이전트에게 동일한 포켓몬 앱 스펙을 주고 12개 프레임워크/메타 프레임워크로 각 5회씩 구현시킨 뒤 비용, 시간, 토큰, Lighthouse 점수를 비교했습니다.
  • 비용 기준으로는 Hono+htmx, Astro, Nuxt, Vanilla가 가장 저렴했고($2.6~3대), SvelteKit·Gracile+Lit·Angular는 뚜렷하게 비쌌습니다($4대 후반까지). SvelteKit은 에이전트가 매번 v3 마이그레이션 가이드를 읽어서, Gracile은 프레임워크 숙지도가 낮아서, Angular는 코드 크기 자체가 커서 비용이 늘어난 것으로 추정됩니다.
  • 프레임워크 전용 MCP/스킬이 제공돼도 에이전트가 실제로 활용하는 비율은 들쭉날쭉했습니다(Nuxt MCP는 전혀 사용되지 않음, Next.js 스킬 파일은 1/5회만 읽힘). 이는 "우리 프레임워크는 MCP 덕분에 AI 친화적"이라는 주장이 실전에서 보장되지 않을 수 있음을 보여줍니다.
  • "UI 프레임워크 없는 Vanilla+Vite" 조합이 오히려 여러 프레임워크보다 비용·품질 면에서 불리했다는 점은, 적절한 프레임워크를 쓰는 편이 에이전트 입장에서도 더 효율적일 수 있음을 시사합니다.
  • Lighthouse의 Performance·Accessibility·CLS 점수는 프레임워크 간 차이가 거의 없을 정도로 포화 상태였고, 실제 차이는 전송 JS 바이트 수 같은 지표에서 드러났습니다. 다만 Lighthouse 자체가 SPA에 불리하게 설계돼 있어 MPA 계열(Astro 등)이 유리한 구조적 한계도 있습니다.
  • 모든 측정값에 상당한 변동폭(분산)이 존재해, LLM 기반 벤치마크는 본질적으로 확률적이라는 점을 저자 스스로 명확히 인정하고 있습니다. 중앙값 비교만큼 범위(최솟값~최댓값)를 함께 보는 것이 중요합니다.
