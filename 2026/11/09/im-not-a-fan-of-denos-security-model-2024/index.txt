18:T41b9,<p>Deno는 &quot;기본적으로 안전한(Secure by default)&quot; 런타임을 내세우며 권한 시스템을 플래그십 기능으로 홍보합니다. 하지만 이 글의 저자는 이 권한 시스템이 겉보기엔 그럴듯해도 실제로는 근본적으로 안전하지 않고, 오히려 사용자를 잘못된 안전감에 빠뜨릴 수 있다고 지적합니다. 터미널 프롬프트의 구조적 결함과 <code>--allow-run</code> 권한의 허점을 구체적인 PoC 코드와 함께 짚어보고, 왜 &quot;일부 JS API만 필터링하는&quot; 접근 방식이 진짜 샌드박싱이 될 수 없는지 살펴보겠습니다.</p>
<h3>Deno의 권한 시스템이란</h3>
<p>Deno는 V8을 재사용하는 JavaScript 런타임으로, 표준 라이브러리와 패키지 매니저, TypeScript 트랜스파일러 등을 포함하고 있습니다. 이 중 보안 관련 핵심 기능은 권한 시스템인데요, 아이디어 자체는 단순합니다. JS 코드가 외부 세계(파일시스템, 네트워크, 프로세스 실행 등)에 접근하려면 반드시 표준 라이브러리를 거쳐야 하므로, Deno가 그 접근을 허용하거나 막을 수 있다는 것입니다.</p>
<pre><code class="language-shell">deno run --allow-read=/tmp/dir --allow-run=uname code.ts</code></pre>
<p>이렇게 실행하면 <code>code.ts</code>는 <code>/tmp/dir</code>만 읽을 수 있고 <code>uname</code>만 실행할 수 있습니다. 또한 프로그램이 런타임에 권한을 요청할 수도 있어서, 아래처럼 코드를 작성하면</p>
<pre><code class="language-typescript">const r = { name: &quot;read&quot;, path: &quot;/tmp/dir&quot; } as const;
await Deno.permissions.request(r);</code></pre>
<p>터미널에 다음과 같은 프롬프트가 떠서 사용자가 직접 허용 여부를 결정할 수 있습니다.</p>
<pre><code>┌ ⚠️ Deno requests read access to &quot;/tmp/dir&quot;.
├ Requested by `Deno.permissions.request()` API.
├ Run again with --allow-read to bypass this prompt.
└ Allow? [y/n/A] (y = yes, allow; n = no, deny; A = allow all read permissions) &gt;</code></pre>
<p>(참고로 저자는 브라우저 확장 프로그램에도 이런 기능이 있었으면 좋겠다고 덧붙입니다. 현재 확장 프로그램은 특정 웹사이트에 접근이 &quot;필요할 수도 있다&quot;는 이유만으로 모든 웹사이트에 대한 실제 접근 권한을 요구해야 하는 구조이기 때문입니다.)</p>
<h3>프롬프트 자체의 문제</h3>
<p>여기서 저자가 처음 거슬렸던 부분은 이 권한 프롬프트가 표시되는 방식입니다. 이 프롬프트는 PolKit 같은 GUI 창이 아니라, 그냥 stdout에 찍히고 stdin에서 입력을 기다리는 텍스트일 뿐입니다.</p>
<p>터미널의 API는 다소 특이한데, 애플리케이션이 터미널에 보내는 대부분의 명령/요청은 stdout에 출력하는 방식으로 대역 내(in-band)에서 전달되고, 터미널은 stdin으로 데이터를 돌려보내는 식으로 응답합니다. Deno는 프로그램이 아무런 권한 요구 없이 stdout에 임의 데이터를 출력하고 stdin을 읽는 것을 허용하기 때문에, 악성 코드가 터미널에 임의의 제어 명령을 보낼 수 있습니다.</p>
<p>평소에는 큰 문제가 안 됩니다. 터미널이 stdout에 찍힌 내용만 보고 셸 명령을 실행하지는 않으니까요 (그래야 <code>cat</code> 같은 명령으로 임의 파일을 안전하게 출력할 수 있습니다). 하지만 악성 코드가 터미널 상태를 마음대로 조작할 수 있는 상태에서 바로 그 터미널에 보안 프롬프트를 띄우는 건 전혀 다른 이야기입니다. 예를 들면,</p>
<ul>
<li>터미널 색상을 조작해서 프롬프트를 숨길 수 있습니다. (이 이슈는 2026년에 &quot;프롬프트가 일부 보인다(이모지가 보인다)&quot;는 이유와 &quot;AI 에이전트들이 터미널 색상을 바꾸는 경우가 많아서&quot; 유효한 유스케이스라는 이유로 종료 처리되었습니다.)</li>
<li>사용자가 승인 입력을 미리 입력하도록 유도할 수 있습니다.</li>
<li>터미널이 어떤 요청에 대한 응답으로 승인을 stdin에 보내도록 속일 수 있습니다. (터미널은 명령 실행을 막기 위해 Enter를 stdin으로 보내지는 않지만, &quot;계속하려면 Enter를 누르세요&quot; 같은 문구는 너무 흔해서 의심을 사지 않고, 사용자는 실제 프롬프트를 보지 못한 채 넘어가게 됩니다.)</li>
</ul>
<p>저자는 이를 시연하는 asciicast도 공유하면서, 화면에서 보여준 구체적 이슈는 이미 패치되었지만 터미널 색상 문제는 여전히 남아 있다고 말합니다. 그리고 결국 핵심 문제는 &quot;공격자가 통제하는 채널을 보안에 민감한 정보 전달에 사용한다&quot;는 점이라고 강조합니다. 이는 마치 공격자가 제어하는 JS 코드를 웹페이지에서 실행시킨 뒤, 같은 페이지에서 비밀번호를 물어보는 것과 같습니다. 페이지가 안전한 상태인지 알 수 없으니 어떤 입력도 신뢰할 수 없는 셈이죠.</p>
<p>Deno가 표준 이스케이프 코드와 관련된 모든 이슈를 패치한다 해도, 세상에 존재하는 비표준 이스케이프 코드가 무엇인지, 그것들이 프롬프트와 어떻게 상호작용할지는 예측할 수 없습니다. 많은 터미널이 각자의 확장 코드를 가지고 있기 때문입니다.</p>
<p>(참고로 저자는 &quot;그럼 sudo는 어떻게 안전한가?&quot;라는 질문에 대해, sudo는 다른 코드를 실행하기 전에 먼저 비밀번호를 물어보기 때문이라고 설명합니다. sudo를 속이려면 sudo를 입력하기도 전에 터미널 상태를 망가뜨려야 하고, 타이핑하는 동안 눈치채지 못하게 조용히 해야 합니다. 만약 어떤 터미널이 이걸 허용한다면 그건 터미널의 버그라고 봐야 한다는 것입니다.)</p>
<h3><code>--allow-run</code>의 근본적 문제</h3>
<p>위에서 썼던 명령어를 다시 보겠습니다.</p>
<pre><code class="language-shell">deno run --allow-read=/tmp/dir --allow-run=uname code.ts</code></pre>
<p>여기서 <code>--allow-run=uname</code>이 정확히 뭘 의미할까요? 프로그램에는 <code>org.gnu.coreutils.uname</code> 같은 표준화된 이름이 없습니다. <code>/nix/store/8k1dmzr3gwzqdgw45nzj76902ca7g1is-coreutils-full-9.5/bin/uname</code> 같은 고유 경로도 아닙니다. 그냥 &quot;PATH에 등록된 디렉터리들을 하나씩 뒤져서 uname이라는 이름을 찾는다&quot;는 뜻일 뿐입니다.</p>
<p>그런데 자식 프로세스에 전달할 환경 변수는 별도 권한 없이 설정할 수 있습니다. 그렇다면 이렇게 하면 어떨까요?</p>
<pre><code>$ cat t.ts
const command = new Deno.Command(&quot;uname&quot;, {
// my current working directory, can be anything
env: { 'PATH': '/tmp/tmp.7ofmKaNW83' },
});
const { code, stdout, stderr } = command.outputSync();
console.log(new TextDecoder().decode(stdout));
$ cat uname
#!/bin/sh
printf lol
$ deno run --allow-run=uname t.ts
lol</code></pre>
<p>PATH를 공격자가 제어하는 디렉터리로 바꿔치기해서 가짜 <code>uname</code>을 실행시킬 수 있다는 것입니다. 편리해 보이는 인터페이스지만 보안 관점에서는 말이 안 되는 구조라는 게 저자의 지적입니다. 프로그램이 이름만으로 고유하게 식별된다면 좋겠지만 실제로는 그렇지 않고, 그렇다고 가정하는 순간 보안 구멍이 생긴다는 것입니다. 저자는 이 문제를 처음 발견했을 때는 심각성을 체감하지 못해 신고하지 않았다고 밝힙니다.</p>
<h4>LD_PRELOAD로 샌드박스 완전 탈출</h4>
<p>PATH 문제는 고치기 쉬워 보입니다. 런타임 시작 시점의 PATH로 강제 고정하거나, 완전한 경로(fully-qualified path)만 허용하거나, 실행 전에 전체 경로로 프롬프트를 띄우면 되니까요. 하지만 그렇게 고쳐도 안전해지지 않습니다.</p>
<p>PATH가 어떤 실행 파일을 실행할지 결정한다면, 동적으로 링크된 실행 파일(대부분의 실행 파일이 여기 해당합니다)은 실제로 시작되려면 동적 로더가 필요합니다. 동적 로더는 실행 파일을 메모리에 로드하고 의존성을 찾는 등의 역할을 하는 프로그램인데, 문제는 이 동적 로더 역시 환경 변수로 설정 가능하다는 점입니다.</p>
<p><code>LD_PRELOAD</code>는 동적 로더에게 실행 파일을 로드할 때 특정 동적 라이브러리를 함께 로드하라고 지시하는 환경 변수입니다. 동적 라이브러리는 로드 시점에 임의 코드를 실행할 수 있죠. 이를 이용하면 샌드박스를 완전히 탈출할 수 있습니다.</p>
<pre><code>$ cat t.c
#include &lt;stdio.h&gt;
// ask dynamic loader to run this function on load time pretty please
__attribute__((constructor)) void lol() {
puts(&quot;lol&quot;);
}
$ cat t.ts
const command = new Deno.Command(&quot;uname&quot;, {
// ask dynamic loader to load our evil library
env: { 'LD_PRELOAD': '/tmp/tmp.7ofmKaNW83/liblol.so' },
});
const { code, stdout, stderr } = command.outputSync();
console.log(new TextDecoder().decode(stdout));
$ gcc -fPIC -shared t.c -o liblol.so
$ # that's the real uname now!
$ deno run --allow-run=uname t.ts
lol
Linux</code></pre>
<p>저자는 이 문제도 신고했고, Deno 팀은 <code>LD_</code>로 시작하는 환경 변수 설정을 금지하는 방식으로 패치했습니다. 하지만 저자는 이 역시 특정 사례 하나만 막았을 뿐, 더 큰 구조적 문제는 해결하지 못했다고 지적합니다. &quot;단일 명령 실행 권한&quot;이라는 개념 자체가 대부분의 경우 별로 쓸모가 없다는 것이죠. (git-over-SSH처럼 단일 명령 실행만 허용하는 안전한 인터페이스도 만들 수는 있지만, 그러려면 환경과 명령 모두 그 상황을 염두에 두고 설계되어 있어야 합니다.)</p>
<p>예를 들어 스크립트가 사용자에게 데이터(git commit 메시지 등)를 편집하게 하려고 <code>$EDITOR</code>를 호출하고 싶다고 해봅시다. 아주 자연스러운 권한 요청처럼 보이지만, 사실 대부분의 에디터는 설정이 매우 자유로워서 그 자체로 완전한 샌드박스 탈출 수단이 될 수 있습니다. 사용자는 별 생각 없이 <code>--allow-run=vim</code>을 승인하기 쉽지만(&quot;그래, 이 파일 편집하려는 거구나!&quot;), 스크립트가 <code>VIMINIT='!rm -rf /*'</code>를 설정해버리면 모든 파일이 날아갑니다. 대부분의 프로그램은 <code>LD_PRELOAD</code>처럼 생각지도 못한 방식으로 설정 가능하며, 공격자는 그 실행 환경 자체를 통제합니다. &quot;프로그램을 설정하는 특정 방법 하나하나를 패치한다&quot;는 건 해결책이 될 수 없고, 진짜 해결책은 JS 코드뿐 아니라 모든 코드를 샌드박싱하는 것이라고 저자는 강조합니다.</p>
<p>이런 논의가 GitHub 이슈에서 오갈 때 한 Deno 개발자는 이렇게 썼다고 합니다.</p>
<p>&gt; The main thing it protects you against is malicious code that isn't smart enough.</p>
<p>저자는 이 문장을 읽고서야 비로소 이 시스템의 본질을 깨달았다고 말합니다.</p>
<h3>결론</h3>
<p>Deno는 사실상 운영체제가 해야 할 일을 애써 흉내 내고 있습니다. 시스템 콜 필터링 대신 표준 라이브러리 호출을 필터링하는 방식인데, 이 방식은 Deno 표준 라이브러리를 거치지 않는 코드를 실행하는 순간 바로 무너집니다. 겉으로는 멋져 보이는 기능들(런타임 프롬프트! <code>--allow-run=uname</code>!)이 실제로는 보안 위험을 끌어들이며, 사용자가 각 권한과 그 조합이 가진 모든 함의를 이해해야만 안전하게 쓸 수 있다는 암묵적 전제를 깔고 있습니다.</p>
<p>Deno 프로세스는 실제로 샌드박스에 갇혀 있는 게 아니라, 그런 척할 뿐입니다. 저자는 &quot;심볼릭 링크를 따라가면 샌드박스 바깥으로 나갈 수 있다&quot;는 식의 사소한 이슈들은 언급조차 하지 않는데, 결국 모두 &quot;이 프로세스는 샌드박스화되지 않았다&quot;는 하나의 문제로 귀결되기 때문입니다.</p>
<p>이런 유사 샌드박싱이라도 없는 것보다는 낫다고 주장할 수도 있습니다 (어차피 모든 악성 코드가 똑똑한 건 아니니까요). 하지만 저자는 이에 동의하지 않습니다. Deno의 권한 시스템은 잘못된 안전감을 주고, 사람들이 제대로 된 샌드박싱 없이 신뢰할 수 없는 코드를 실행하도록 유인할 수 있다는 것입니다.</p>
<p>Deno 샌드박싱을 안전하게 쓸 수 있는 경우가 있다면 다음 조건을 모두 지킬 때뿐이라고 저자는 말합니다.</p>
<ul>
<li><code>--allow-run</code> 같은 더 위험한 권한은 <code>=cmd</code> 형태로라도 절대 쓰지 않을 것</li>
<li><code>--allow-env</code>도 <code>=VAR</code> 형태로라도 쓰지 않을 것 (환경 변수 설정은 메모리 안전성이 없고 libc 함수에 영향을 줄 수 있기 때문)</li>
<li>터미널이 속을 수 없도록 가능하면 <code>--no-prompt</code>로 실행할 것</li>
<li><code>--allow-{read,write}</code>로 허용한 디렉터리 안의 심볼릭 링크에 주의할 것</li>
<li>리소스 고갈 공격에는 신경 쓰지 않을 것 (CPU를 태우거나 메모리를 할당하는 데는 아무 권한도 필요 없기 때문)</li>
</ul>
<p>특히 비대화형(non-interactive) 환경에서 아무 권한도 없이 신뢰할 수 없는 코드를 실행하고, 리소스 소비는 다른 수단으로 제어한다면 그나마 안전할 수 있습니다. 그럼에도 저자는 이렇게 하는 것조차 권하지 않습니다. 이 경로는 풋건(footgun)으로 가득 차 있기 때문입니다. 결국 완전한 권한을 가진 프로세스 안에서 신뢰할 수 없는 코드를 실행하는 셈이고, OS와 상호작용이 필요한 순간 &quot;아무 권한도 없는&quot; 상태는 더 이상 유지되지 않습니다. 어떤 stdlib API들의 조합이 샌드박스 탈출로 이어지는지 일일이 따지려 들지 말고, 그냥 제대로 된 샌드박스를 쓰라는 게 저자의 결론입니다.</p>
<p>저자는 그래서 자신의 해법으로 &quot;신뢰할 수 없는 건 그냥 bwrap으로 감싸서 실행하라(just bwrap untrusted shit)&quot;고 제안합니다.</p>
<p>마지막으로 저자는 이 글이 Deno 개발자들을 비난하거나 괴롭히라는 초대장이 아니라는 점을 분명히 밝힙니다. 이것은 기술적 견해 차이일 뿐이며, 어떤 기술적 견해 차이도 괴롭힘으로 해결된 적은 없다는 것입니다. 저자는 이미 Deno 팀에 자신의 의견을 전달했고 그들은 동의하지 않았으며, 그것으로 괜찮다고 글을 맺습니다.</p>
<h3>정리</h3>
<ul>
<li>Deno의 권한 시스템은 &quot;표준 라이브러리 호출 차단&quot;에 기반하는데, 표준 라이브러리를 거치지 않는 모든 경로(외부 바이너리 실행 등)에서는 무력화됩니다.</li>
<li>권한 요청 프롬프트가 stdout/stdin이라는 공격자가 통제 가능한 채널 위에서 동작하기 때문에, 터미널 이스케이프 코드 조작으로 프롬프트를 숨기거나 승인을 가로챌 수 있습니다.</li>
<li><code>--allow-run=명령어</code>는 명령어 이름만으로 식별하기 때문에 PATH 조작으로 가짜 바이너리를 실행시킬 수 있고, PATH를 고정해도 <code>LD_PRELOAD</code> 같은 동적 로더 환경 변수로 임의 코드를 주입해 샌드박스를 완전히 탈출할 수 있습니다 (실제 PoC 코드로 입증됨).</li>
<li>Deno 팀은 이런 이슈들을 하나씩 패치(<code>LD_</code> 환경 변수 금지 등)했지만, 저자는 이것이 &quot;단일 명령 실행 허용&quot;이라는 개념 자체의 근본적 결함을 가리지 못한다고 봅니다. 에디터 같은 일상적인 권한 요청조차 설정 파일을 통한 임의 코드 실행으로 이어질 수 있기 때문입니다.</li>
<li>결론적으로 저자는 JS 코드만 필터링하는 유사 샌드박싱 대신, bwrap 같은 OS 수준의 실제 샌드박스를 사용하는 것이 유일하게 신뢰할 수 있는 방법이라고 주장합니다. 프론트엔드/백엔드를 막론하고 &quot;런타임이 제공하는 권한 플래그&quot;에 대한 과신을 경계할 필요가 있다는 메시지입니다.</li>
