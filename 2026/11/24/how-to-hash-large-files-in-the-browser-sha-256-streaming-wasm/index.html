브라우저에서 대용량 파일 해싱하기: SHA-256 스트리밍과 WASM 활용법

How to Hash Large Files in the Browser (SHA-256, Streaming WASM)

📅 2026-11-24📰 DEV Community
frontend

브라우저에서 대용량 파일의 체크섬을 계산해야 하는 경우, 가장 먼저 떠올리는 방법은 crypto.subtle.digest('SHA-256', buffer)입니다. 작은 파일에는 문제없이 동작하지만, 5GB짜리 디스크 이미지 같은 파일을 넣는 순간 이야기가 달라집니다. digest()에는 스트리밍 API가 없어서 파일 전체를 하나의 ArrayBuffer로 메모리에 올려야 하고, 결국 파일 크기만큼 메모리가 늘어나다가 탭이 죽어버립니다.

이 글은 업로드 없이 다운로드한 파일을 공개된 SHA-256, MD5, 혹은 SHA256SUMS 목록 전체와 비교하는 체크섬 검증 도구를 만들면서 겪은 문제와, 그 과정에서 생각보다 시간이 오래 걸렸던 디테일들을 정리한 것입니다.

파일을 조각내 읽고, 스트리밍 해셔에 먹이기

File은 Blob이고, Blob.slice()는 비용이 거의 들지 않습니다. 실제로 바이트를 요청하기 전까지는 뷰만 반환하기 때문입니다. 그래서 루프는 다음과 같이 단순하게 구성됩니다.

const CHUNK = 4 * 1024 * 1024; // 4 MiB

export async function hashFile(
  file: Blob,
  onProgress?: (ratio: number) => void,
  signal?: AbortSignal,
) {
  const { createSHA256 } = await import('hash-wasm'); // lazy: only when needed
  const hasher = await createSHA256();
  hasher.init();

  for (let offset = 0; offset < file.size; offset += CHUNK) {
    if (signal?.aborted) throw new DOMException('Aborted', 'AbortError');
    const end = Math.min(file.size, offset + CHUNK);
    const chunk = new Uint8Array(await file.slice(offset, end).arrayBuffer());
    hasher.update(chunk);
    onProgress?.(end / file.size);
  }

  return hasher.digest(); // lowercase hex
}

핵심은 한 번에 4MiB짜리 슬라이스 하나만 메모리에 살아있다는 점입니다. 그래서 이 메모리 피크는 파일 크기와 무관하게 일정합니다. 덕분에 이 체크섬 도구는 파일 크기 제한이 아예 없는 반면, 같은 서비스의 다른 파일 도구들은 입력을 50MB로 제한하고 있습니다.

여기서 사용한 hash-wasm은 MD5, SHA-1, SHA-256, SHA-512, CRC32에 대해 init / update / digest 방식의 증분 해셔를 제공하며, WebAssembly로 컴파일되어 있습니다. 동적 import()로 불러오기 때문에 실제로 다이제스트가 필요해지기 전까지는 페이지가 이 모듈을 다운로드하지 않습니다.

설계에서 몇 가지 선택은 짚고 넘어갈 만합니다.

  • 4MiB 슬라이스: 메모리를 평평하게 유지할 만큼 작으면서도, 슬라이스당 오버헤드(arrayBuffer() 프로미스 하나, WASM 호출 하나)가 전체 작업량 속에 묻힐 만큼은 큽니다.
  • 한 번의 패스에서 여러 알고리즘 처리: 목록에 같은 파일에 대한 MD5와 SHA-256이 모두 있다면, 두 해셔를 모두 만들어 같은 청크에 대해 각각 update()를 호출합니다. 파일은 단 한 번만 읽습니다.
  • 병렬이 아닌 순차 처리: 파일 세 개를 동시에 해싱하면 슬라이스 세 개가 동시에 메모리에 올라가는 데다 브라우저가 추가로 버퍼링하는 양까지 더해집니다. 순차 처리는 메모리 피크를 예측 가능하게 유지해줍니다.
  • 슬라이스 사이의 취소 처리: 각 읽기 전후로 AbortSignal을 확인합니다. 이미 끝난 파일은 결과를 그대로 유지하고, 나머지는 취소됨으로 표시됩니다.

한 가지 솔직하게 밝혀둘 점은, 이 접근이 보장하는 것은 메모리 사용량이지 속도가 아니라는 것입니다. 5GB짜리 이미지는 여전히 처음부터 끝까지 읽어야 하고, 이게 얼마나 걸리는지는 디바이스와 파일이 위치한 저장소에 따라 달라집니다.

해시 길이로 알고리즘 추측하기

사용자는 해시 값을 붙여넣을 뿐, 드롭다운에서 "SHA-256"을 직접 고르고 싶어 하지 않습니다. 다행히 흔히 쓰는 알고리즘들은 16진수 문자열 길이만으로 구분이 됩니다.

16진수 길이알고리즘
8CRC32
32MD5
40SHA-1
64SHA-256
128SHA-512

이 매핑은 코드 전체에서 단 한 곳, 하나의 테이블에만 둡니다. SHA256 (file.iso) = … 같은 BSD 스타일 라인은 알고리즘이 명시적으로 태그되어 있으므로 이 길이 검사를 건너뜁니다.

실제 SHA256SUMS 목록 파싱하기

사실 해싱 로직보다 이 파싱 작업에 더 많은 코드가 들어갔습니다. 사람들은 릴리스 페이지에 나온 모양 그대로를 그냥 붙여넣기 때문에, 파서는 네 가지 포맷을 순서대로 시도하면서 처음 매칭되는 것을 사용합니다.

  • BSD 포맷 (shasum --tag 출력): SHA256 (normal.zip) = 1c5f…
  • GNU 포맷 (sha256sum / md5sum 출력): 1c5f… normal.zip (바이너리 모드를 나타내는 앞쪽 *는 제거)
  • 단순 다이제스트: SHA256: 1C5F… 형태로, 라벨과 0x, 내부 공백을 제거
  • 이름이 먼저, 해시가 나중: 릴리스 페이지의 표를 그대로 복사했을 때 나오는 형태

이 외에도 실전에서 중요했던 디테일들이 있습니다.

  • UTF-8 BOM을 제거하고, (윈도우에서 생성된 목록을 위해) CRLF 줄바꿈도 허용합니다.
  • 빈 줄이나 #, ;로 시작하는 줄은 건너뜁니다. 파싱에 실패한 나머지 모든 줄은 개수를 세어 이유와 함께 보고합니다. 조용히 버리지 않습니다.
  • 목록은 2,000줄로 제한하고, 잘렸을 경우 원래 목록이 얼마나 길었는지 사용자에게 알려줍니다.
  • 파일명에서 경로와 따옴표를 제거해서, "./dist/a.iso"가 실제 파일 a.iso와 매칭되도록 합니다. 이름 비교는 대소문자를 구분하지 않습니다.
  • 해시 비교는 trim()과 toLowerCase()를 거친 뒤 수행합니다. 출력은 항상 소문자 16진수로, sha256sum, shasum, certutil이 출력하는 형식과 동일합니다.

목록 항목과 파일 매칭하기

가장 고민이 많았던 규칙은 "언제 파일 이름이 중요한가"였습니다.

  • 목록에 해시가 딱 하나만 있고 이름이 없다면, 이름을 무시하고 모든 파일과 비교합니다. "다운로드 페이지에서 해시만 복사해 붙여넣는" 흔한 케이스입니다.
  • 목록에 여러 항목이 있다면 이름으로 매칭합니다. 목록에서 매칭되는 항목이 없는 파일도 (목록에서 가장 흔히 쓰인 알고리즘으로) 해시는 계산해서 "목록에서 찾을 수 없음"으로 표시하고, 사용자가 직접 눈으로 비교할 수 있게 합니다.
  • 같은 이름이 서로 다른 두 해시로 등장하면, 둘 다와 비교해서 표시합니다. 보통 목록이 두 개의 릴리스 버전을 섞어놓은 경우입니다.

비교가 실패했을 때는 "불일치"라는 메시지보다 더 나은 힌트를 줄 수 있는 몇 가지 저비용 체크를 추가했습니다.

  • 파일 크기가 0바이트면 다운로드가 실패했다는 뜻입니다.
  • 1KB 미만이면 에러 페이지를 저장했을 가능성이 높습니다.
  • 해시가 목록의 다른 항목과 일치하면 엉뚱한 파일을 검사하고 있다는 뜻입니다.

결과

출력 결과는 커맨드라인 도구들과 바이트 단위로 완전히 일치합니다. 테스트 샘플인 normal.zip(652바이트)에서는 shasum -a 256이 출력하는 것과 동일한 SHA-256 값을, md5 -q가 출력하는 것과 동일한 MD5 값을 페이지에서도 그대로 보여줍니다. 한 번에 최대 50개 파일을 배치로 처리할 수 있고, 결과는 페이지 내에서 생성한 blob URL을 통해 CSV로 내보낼 수 있습니다.

"아무것도 업로드되지 않는다"는 주장은 직접 확인할 수 있습니다. 검사가 진행되는 동안 DevTools의 Network 탭을 열어보면, 페이지는 자체 코드와 WASM 모듈만 로드할 뿐, 어떤 요청에도 파일 데이터가 담겨 있지 않음을 확인할 수 있습니다.

직접 구현하지 않고 바로 사용하고 싶다면 gingertool.com/en/file-tools/checksum-verifier에서 실제 동작하는 도구를 쓸 수 있습니다.

정리

  • crypto.subtle.digest()는 파일 전체를 메모리에 올려야 하므로 대용량 파일 해싱에는 적합하지 않습니다. Blob.slice()로 파일을 일정 크기(4MiB)씩 잘라 읽고, hash-wasm의 증분 해셔(init/update/digest)에 순차적으로 먹이면 메모리 피크를 파일 크기와 무관하게 일정하게 유지할 수 있습니다.
  • 여러 알고리즘이 필요하면 해셔를 여러 개 만들어 같은 청크에 각각 update()를 호출함으로써 파일을 한 번만 읽도록 설계할 수 있습니다. 여러 파일은 병렬이 아니라 순차로 처리해야 메모리 사용량이 예측 가능합니다.
  • 해시 문자열의 16진수 길이(8/32/40/64/128)만으로 CRC32, MD5, SHA-1, SHA-256, SHA-512를 구분할 수 있어 사용자가 알고리즘을 직접 선택할 필요가 없습니다.
  • 실제 배포되는 SHA256SUMS 파일은 BSD, GNU, 단순 다이제스트, 이름-해시 순서 등 포맷이 제각각이므로, 여러 포맷을 순서대로 시도하는 파서와 BOM/CRLF 처리, 공백 라인 스킵, 대소문자·경로 정규화 같은 디테일이 실제 코드량의 대부분을 차지합니다.
  • 단순히 "불일치" 메시지만 주는 대신 파일 크기 0바이트, 1KB 미만, 목록 내 다른 항목과의 해시 일치 등 저비용 체크로 실패 원인에 대한 힌트를 제공하면 사용자 경험이 크게 개선됩니다.
