1Password, 직원 GitHub 계정 탈취로 인한 보안 사고 공식 발표

1Password Security Incident

📅 2026-11-26📰 Hacker News (Top)
frontendgeneral

비밀번호 관리 서비스 1Password가 2026년 11월 19일 발생한 보안 사고에 대한 공식 업데이트를 발표했습니다. 직원의 GitHub 계정이 탈취당해 소스 코드와 일부 고객 계정 메타데이터가 유출된 사건인데요, 다행히 사용자들이 가장 우려할 볼트(vault) 내용은 이번 사고와 무관하다는 점이 핵심입니다. 어떤 정보가 노출됐고, 1Password가 어떤 조치를 취했는지 원문 내용을 바탕으로 정리해보겠습니다.

무슨 일이 있었나

2026년 11월 19일, 1Password는 공격자가 직원의 회사 GitHub 계정에 접근한 정황을 포착하고 조사에 착수했습니다. 공격자는 탈취한 계정으로 소스 코드에 접근했을 뿐만 아니라, 백엔드 서비스에 악성 코드를 푸시해 고객 관련 관리용 데이터(administrative data)를 다운로드하는 데까지 성공했습니다.

이 과정에서 유출된 정보는 고객의 이름과 이메일 주소, 그리고 계정에 관한 비(非)기밀 내부 메타데이터였습니다. 공격자가 고객의 볼트 내용에 접근하거나 이를 열람할 수 있었던 적은 한 번도 없었다고 1Password는 명확히 밝히고 있습니다.

유출된 정보의 범위

공격자가 다운로드한 것은 일부 사용자에 대한 계정 기록으로, 구체적으로는 다음과 같습니다.

  • 이름과 이메일 주소
  • 계정 및 사용자 식별자, 계정 생성일과 마지막 로그인 시각
  • 공개 키(public key) — 원래부터 공개되는 값이라 보안에 영향 없음
  • Secure Remote Password(SRP) 프로토콜 파라미터 — 이 값만으로는 계정에 접근 불가
  • 초대, 프로비저닝, 계정 복구용 이메일 링크에 포함된 토큰
  • 내부 아키텍처와 관련된 기타 비기밀 메타데이터(버전 숫자 식별자, 파일 숫자 식별자 등)

또한 공격자는 비공개 리포지토리의 소스 코드를 복사하고 CI/CD 시스템에도 접근했습니다. 소스 코드 자체는 고객 데이터가 아니며 사용자 비밀 정보를 포함하지 않지만, CI/CD 시스템에는 제품 동작을 위한 인프라 관련 시크릿이 들어 있습니다. 이에 따라 노출 가능성이 있는 모든 자격 증명(credential)에 대해 로테이션을 진행했으며, 1Password 서비스 가용성이나 제품 보안에는 영향이 없다고 밝혔습니다.

특히 주목할 부분은 프로비저닝 초대 또는 계정 복구 이메일에 포함되는 토큰입니다. 프로비저닝 초대는 SCIM Bridge나 Hosted Provisioning 기능에 한정해서 사용되는데, 이번 사고로 이런 상태에 있던 사용자는 소수였고 이들에게는 개별적으로 통지가 이뤄졌습니다. 이 토큰은 단독으로는 계정에 접근할 수 없고, SSO 로그인 또는 사용자의 등록된 이메일로 전송되는 6자리 코드와 결합해야만 초대·복구 절차를 완료할 수 있습니다. 1Password는 악의적인 제3자가 이 코드를 무작위 대입(brute force)으로 추측할 가능성을 더 낮추기 위해, 코드 체계를 기존 숫자 6자리에서 영숫자 혼합 10자리로 확장했습니다. 이로써 무차별 대입 공격은 사실상 불가능해졌다고 설명합니다.

영향을 받지 않은 것들

1Password는 다음 항목들은 이번 사고의 영향을 받지 않았다고 명시했습니다.

  • 사용자의 볼트와 그 안에 저장된 항목들
  • 볼트를 보호하는 암호 키
  • 계정 비밀번호와 Secret Key (1Password는 이 값들을 애초에 저장하지 않음)
  • 계정 복구 키
  • 1Password 앱과 브라우저 확장 프로그램

1Password가 취한 조치

사고 대응 과정에서 1Password는 다음과 같은 조치를 시행했습니다.

  • 탈취당한 GitHub 계정 비활성화, 탈취된 토큰 폐기, 공격자가 만든 접근 권한 제거
  • 노출 가능성이 있는 모든 내부 자격 증명 로테이션 또는 폐기
  • 초대·복구 이메일에 사용되는 코드를 6자리에서 10자리 영숫자로 변경(예방적 조치)
  • 내부 GitHub, CI/CD, 엔드포인트 통제 강화 및 유사 공격 탐지 규칙 신규 추가
  • 노출된 계정 프로비저닝 토큰을 악용한 계정 탈취나 침해 정황이 내부적으로 없음을 검증
  • 외부 독립 보안 전문가를 투입해 봉쇄(containment) 및 사고 대응 절차의 적절성 검증

사용자가 해야 할 일

1Password는 이번 사고와 관련해 사용자에게 피싱 시도를 각별히 경계할 것을 당부했습니다. 1Password, 초대, 계정 복구 등을 언급하는 예상치 못한 이메일·문자·전화는 의심해야 하며, 1Password는 절대 계정 비밀번호나 Secret Key를 요구하는 연락을 하지 않는다는 점을 강조했습니다. 이 두 정보는 오직 공식 1Password 앱이나 공식 웹사이트에서, 그것도 사용자가 직접 앱을 열거나 주소를 입력했을 때만 입력해야 합니다. Secret Key는 새로운 기기나 브라우저에서 처음 로그인할 때만 필요하므로 안전하게 보관해야 하며, 의심스러운 정황을 발견하면 support@1password.com으로 신고할 것을 권장했습니다.

1Password는 볼트 콘텐츠가 자사 서버 침해로도 노출될 수 없도록 설계되어 있다는 점을 재차 강조합니다. 볼트의 비밀 정보는 오직 사용자만 보유한 키로 암호화되기 때문에, 1Password도, 심지어 서버에 침투한 공격자도 이를 열람할 수 없다는 것입니다. 또한 2015년부터 공개해온 Security Whitepaper를 통해 투명성을 유지해왔으며, 이번 블로그 포스트 역시 새로운 사실이 확인되면 계속 업데이트하겠다고 밝혔습니다.

정리

이번 사고는 직원 GitHub 계정 탈취를 시작으로 소스 코드와 CI/CD 접근, 그리고 일부 고객의 이름·이메일·계정 메타데이터 유출로 이어진 공급망형 침해 사례입니다. 다만 제로-지식(zero-knowledge) 아키텍처 덕분에 볼트 콘텐츠나 이를 보호하는 키는 애초에 공격자가 접근할 수 없는 구조였다는 점이 피해를 제한하는 핵심 요인이었습니다. 프론트엔드·백엔드를 막론하고 개발 조직이라면 소스 저장소 접근 권한 관리, CI/CD 시크릿 로테이션 체계, 그리고 서버가 침해되어도 민감 데이터가 노출되지 않는 설계(종단간 암호화, 클라이언트 측 키 보관)가 왜 중요한지 보여주는 사례로 참고할 만합니다. 또한 초대·복구용 토큰처럼 보조 인증 수단으로 쓰이는 값도 무차별 대입에 안전하도록 충분한 엔트로피를 갖춰야 한다는 교훈도 눈여겨볼 지점입니다.

💡
제로-지식 아키텍처와 클라이언트 측 암호화가 서버 침해 상황에서도 사용자 데이터를 보호하는 실제 사례이자, CI/CD 시크릿 관리와 토큰 엔트로피 설계의 중요성을 보여주는 좋은 참고 자료입니다.
