웹의 URI는 왜 변하면 안 되는가: 팀 버너스리의 1998년 조언
via Hacker News (Top)
💡알면 좋은 정보frontendgeneral

웹의 창시자 팀 버너스리가 1998년에 쓴 이 글은 URI(URL)가 깨지는 것이 기술적 필연이 아니라 조직의 관리 부실이라고 지적합니다. cgi-bin이나 파일 경로처럼 구현 메커니즘을 노출하는 URI, 주제 분류나 담당자 이름이 들어간 URI가 왜 위험한지 실제 NSF 사이트 사례를 들어 설명하고, URI 설계의 핵심 원칙으로 '정보를 최대한 빼는 것'을 제시합니다. URN이 URI 관리 문제의 만능 해결책이 아니라는 점과, 도메인 분리(cgi., secure. 등)도 같은 위험을 안고 있다는 점도 함께 다룹니다.

💡
URL 라우팅 구조, API 엔드포인트, 정적 자산 경로를 설계하는 모든 프론트엔드/백엔드 개발자에게 이 원칙은 지금도 그대로 적용되며, SEO와 사용자 경험, 장기적인 유지보수성에 직접적인 영향을 미친다.

React 컴포넌트를 URL로 공유하는 법: 중복 상태 없이 제대로 만들기
via Sam Selikoff
▶영상frontend

검색 기능이 있는 React 테이블을 URL로 공유 가능하게 만드는 과정에서, useState와 useEffect로 URL을 동기화하는 흔한 접근이 뒤로 가기 버튼 버그를 만드는 이유를 분석합니다. 근본 원인은 검색어가 React state와 URL 두 곳에 중복 저장된다는 점이며, useSearchParams로 URL을 유일한 소스 오브 트루스로 삼고 React state를 완전히 제거하는 방식으로 해결합니다. 이 과정에서 React 공식 문서의 'You Might Not Need an Effect' 원칙이 실제로 어떻게 적용되는지 보여줍니다.

💡
URL 상태 관리는 실무에서 매우 흔한 요구사항이지만 잘못 구현하면 미묘한 네비게이션 버그를 만들기 쉬워, 중복 상태를 식별하고 제거하는 사고방식을 익히는 것이 프론트엔드 개발자에게 중요합니다.
