13:T354a,<p>유튜브에서 스스로를 &quot;2등 TypeScript 유튜버&quot;라고 부르곤 하는 Theo가, 정작 1등이라 인정하는 Matt Pocock의 AI 스킬 저장소를 드디어 제대로 파봤습니다. 이 저장소는 몇 개의 마크다운 파일로만 이루어져 있는데도 GitHub 스타 20만 개를 넘기며 전체 GitHub 프로젝트 중 스타 수 상위 10위 안에 드는 기염을 토했습니다. 이번 글에서는 Theo가 일주일간 직접 설치하고 써본 Matt Pocock의 스킬들과, React 코어 팀 출신이자 현재 Cursor에서 일하는 Lauren(&quot;Potato&quot;)이 만든 PA Stack 스킬 세트를 비교하며 얻은 인사이트를 정리합니다.</p>
<h3>마크다운 몇 개가 스타 20만 개를 받은 이유</h3>
<p>Matt Pocock이 공개한 &quot;AI skills for real engineers&quot;는 처음엔 Theo도 대수롭지 않게 넘겼던 프로젝트입니다. 하지만 시간이 지나면서 Matt가 계속 다듬고 실전에 맞게 개선해왔고, 그 결과 지금은 GitHub 전체에서 손꼽히는 스타 수를 기록하는 저장소가 됐습니다. 특히 그중에서도 &quot;grill me&quot; 스킬에 대한 호평이 많았고, Theo 역시 이 저장소를 다뤄야겠다고 오래전부터 벼르고 있었습니다.</p>
<p>다만 Matt의 스킬만 다루면 이 생태계 전체를 제대로 소개하는 게 아니라고 판단해서, 다른 스킬 저장소들도 함께 살펴봤습니다. 결론부터 말하면 대부분의 스킬 저장소는 그냥 슬롭(slop, 쓸모없는 잡동사니)이라 무시해도 되지만, 딱 하나 예외가 있었습니다. 바로 Lauren(Potato)이 만든 PA Stack입니다. Lauren은 React 컴파일러 개발에 큰 기여를 한 인물로, React 코어 팀 시절의 내공을 살려 놀랍도록 실용적이면서 재미있는 스킬 세트를 만들었습니다.</p>
<p>Theo는 두 저장소의 스킬들을 대부분 감사(audit)하고, 마음에 드는 것들만 골라 실제로 일주일간 사용해봤습니다.</p>
<h3>무작정 복사하지 말 것</h3>
<p>본격적으로 스킬 내용을 파고들기 전에 Theo가 강하게 강조한 원칙이 있습니다. 다른 사람의 설정을 그대로 복사해서는 아무것도 얻을 수 없다는 것입니다. 이런 스킬 세트들은 따라야 할 절차 목록이 아니라, 자신만의 AI 코딩 시스템을 만들 때 참고할 정보로 다뤄야 한다는 게 핵심입니다.</p>
<p>Theo는 이를 코드베이스 비유로 설명합니다. 누군가의 코드베이스를 그대로 복사-붙여넣기해서 이름만 바꾸는 건 좋은 엔지니어가 아니지만, 그 코드베이스를 참고점 삼아 배우면서 자기만의 코드를 만들어가는 건 좋은 엔지니어라는 겁니다. 스킬도 마찬가지로, 남의 설정을 그대로 설치하는 건 비싼 돈 주고 코드 템플릿 사는 것과 다를 바 없고, 엔지니어링 실력 부족을 그대로 드러내는 행위라고 잘라 말합니다. 그러니 모든 스킬을 무작정 설치하지 말고, 최소한 조금 더 나은 출발점에서 시작하라는 조언입니다.</p>
<h3>내 작업 패턴에 맞는 스킬 찾기</h3>
<p>Theo가 실제로 사용한 접근법은 다음과 같은 프롬프트로 시작하는 것이었습니다.</p>
<p>&gt; &quot;PA Stack의 어떤 스킬이 내 작업에 잘 맞을지 파악하고 싶어. 내 메인 머신들(MacBook, LeftBook, BB1)에서의 사용 패턴을 감사해줘. 내 사용 패턴을 PA Stack의 스킬들과 비교해서, 나에게 얼마나 잘 맞고 얼마나 도움이 될지 순위를 매긴 리스트를 만들어줘. 먼저 pull history를 가져온 다음 서브 에이전트를 나눠서 감사 작업을 해줘. 전부 Opus 5로.&quot;</p>
<p>당시 Opus 5 사용량이 넉넉해서 테스트해본 것이라고 하는데, 이 프롬프트에 PA Stack 링크를 걸어주자 AI가 모든 스킬을 가져와서 적합도와 기대 효과, 간단한 이유까지 담은 순위 문서를 만들어줬습니다. 이 결과에서 곧바로 상위로 꼽힌 것이 interrogate, blast radius, technical writing arena, prove it work 스킬 등이었습니다.</p>
<p>이 딥다이브의 시작점은 사실 unslop 스킬에 대한 관심이었습니다. Lauren이 자신의 에이전트가 쓴 글을 올린 걸 봤는데, 평소 Claude가 쓰는 글보다 훨씬 덜 어색해 보였다는 겁니다. 그래서 이 매우 단순한 unslop 스킬을 바로 가져와 써봤습니다.</p>
<h3>스킬의 description은 &quot;설명&quot;이 아니라 &quot;트리거&quot;다</h3>
<p>여기서 Theo는 스킬 시스템을 이해하는 데 중요한 개념 하나를 짚습니다. Potato의 스킬 description에는 재미있는 프롬프팅 디테일이 들어있는데, 예전에 올린 마크다운 개편 영상에서도 언급했듯이 description의 역할은 스킬이 하는 모든 일을 정확히 설명하는 게 아니라는 겁니다. description은 그냥 마크다운 텍스트일 뿐이고, 그 유일한 목적은 필요한 순간에 스킬이 트리거되도록 만드는 것입니다.</p>
<p>이걸 유튜브 썸네일에 비유할 수 있습니다. 썸네일의 역할은 영상 내용을 정확하게 요약하는 게 아니라, 적절한 사람이 스크롤을 멈추고 클릭하게 만드는 것입니다. description도 마찬가지로, 적절한 작업을 하고 있는 에이전트가 &quot;아, 이 스킬이 지금 유용하겠다&quot;라고 판단해서 끌어오도록 만드는 게 목적입니다. 그래서 Theo는 이걸 description이라고 부르지 말고 trigger라고 불러야 한다고 주장합니다. 이런 명명 규칙들이 다 초기 Anthropic 시절, 아직 아무도 뭘 하는지 제대로 모르던 때 정해진 것이라서 지금까지 그냥 관습적으로 쓰이고 있다는 겁니다.</p>
<p>스킬이 작동하는 방식은 간단합니다. 모델은 모든 스킬의 이름과 description만 보고, description을 기준으로 &quot;이 스킬이 지금 유용하겠다&quot;고 판단하면 해당 마크다운 파일 전체를 컨텍스트로 읽어들입니다.</p>
<h3>unslop 스킬 파헤치기</h3>
<p>unslop 스킬이 실제로 컨텍스트에 로드하는 내용은 다음과 같습니다.</p>
<p>핵심은 &quot;AI스러운 패턴을 제거하고 사람 목소리를 넣어 텍스트를 편집하는 것&quot;이며, 프로세스는 이렇습니다.</p>
<ul>
<li>패턴 스캔</li>
<li>다시 쓰기 (의미는 보존, 의도된 톤은 유지)</li>
<li>영혼 불어넣기(add some soul)</li>
<li>셀프 감사 — &quot;이게 왜 딱 봐도 AI가 쓴 것처럼 보이지?&quot;를 자문하고 남은 흔적을 고침</li>
</ul>
<p>&quot;영혼 불어넣기&quot;에 대해서는 이렇게 설명합니다. 패턴 제거는 절반의 일일 뿐, 무미건조하고 목소리 없는 글도 마찬가지로 티가 난다는 겁니다. 구체적인 지침은 다음과 같습니다.</p>
<ul>
<li><strong>의견을 가져라</strong>: 사실을 중립적으로 장단점 나열하듯 쓰지 말고 반응하라</li>
<li><strong>리듬을 다양하게</strong>: 짧은 문장 다음에 여유 있게 늘어지는 긴 문장을 배치</li>
<li><strong>복잡성을 인정하라</strong>: 예시로 &quot;impressive but also kind of unsettling beats impressive&quot;(그냥 impressive보다 &quot;인상적이지만 어딘가 불안하기도 하다&quot;가 낫다)</li>
<li><strong>필요하면 &quot;나&quot;를 써라</strong>: 1인칭이 비전문적인 게 아니다</li>
<li><strong>약간의 흐트러짐을 허용하라</strong>: 완벽한 구조는 딱 봐도 기계가 쓴 티가 난다</li>
<li><strong>구체적으로 써라</strong>: &quot;이건 우려스럽다&quot; 대신 &quot;새벽 3시에 에이전트들이 쉼 없이 돌아가고 있다는 게 뭔가 섬뜩하다&quot; 같은 식으로</li>
</ul>
<p>이 부분에서 Theo는 LLM의 흥미로운 특성 하나를 짚습니다. LLM은 나쁜 예시를 보여주고 좋은 예시를 대비시켜 주면 좋은 쪽을 아주 잘 따라 하지만, 그 예시들에 특정 요소가 빠져 있으면 그 부분은 계속 나쁘게 쓴다는 겁니다. 그래서 예시를 구성할 때 균형을 잘 잡아야 한다는 점을 강조합니다.</p>
<h4>탐지하고 고쳐야 할 패턴들</h4>
<p>스킬 파일에는 구체적으로 탐지·수정해야 할 패턴 목록도 있습니다.</p>
<ul>
<li><strong>내용 없는 미사여구(content puffery)</strong>: &quot;pivotal moment&quot;, &quot;testament to&quot;, &quot;evolving landscape&quot;, &quot;setting the stage&quot; 같은 표현들 — 미사여구를 걷어내고 실제 일어난 일을 말하라</li>
<li><strong>네임드로핑</strong>: 맥락 없이 매체 이름만 나열하지 말고, 하나를 골라 무슨 말이 나왔는지 구체적으로 쓰라</li>
<li><strong>피상적인 -ing 표현</strong>: highlighting, ensuring, reflecting, showcasing 같은 단어들은 그냥 삭제</li>
<li><strong>홍보성 언어</strong>: 모호한 표현들, &quot;you get the idea&quot; 류</li>
<li><strong>M-dash(—) 남용</strong>: 여전히 Opus에서 많이 나온다고 지적 (다른 모델들은 이 부분을 훨씬 잘 따랐다고 함)</li>
<li><strong>챗봇 특유의 문구들</strong>: &quot;I hope this helps&quot;, &quot;Let me know if...&quot; 같은 표현 제거</li>
<li><strong>전문 용어(jargon)</strong>: 관련 섹션 별도 존재</li>
</ul>
<p>특히 Theo가 가장 마음에 들어한 부분은 &quot;어떻게 느껴지는지 말하지 말고 무엇을 하는지 말하라&quot;는 원칙입니다. 예를 들어 &quot;the database stays close at hand&quot;(데이터베이스가 가까이 있다) 같은 감성적인 표현 대신 &quot;SQL returns the exact string sent to the database&quot;(SQL은 데이터베이스로 보낸 문자열을 그대로 반환한다)처럼 훨씬 직접적으로 쓰라는 겁니다.</p>
<p>체크 방법도 명시돼 있습니다. &quot;이 문장이 독자에게 무엇을 하라고, 혹은 무엇을 알라고 말하는가?&quot;를 자문하고 그걸 그대로 쓰라는 것, 그리고 만약 문장을 구체적인 지침·사실·숫자로 다시 쓸 수 없다면 그 문장은 지우라는 것입니다. 마지막 체크포인트는 &quot;이 문장이 다른 프로젝트의 문서에 그대로 들어가도 어색하지 않다면, 이 프로젝트에 대해 아무것도 말하고 있지 않은 것이니 지워라&quot;입니다.</p>
<h3>실제로 적용해보니</h3>
<p>Theo는 GPT-5.6 High와 Opus 5를 오가며 실제로 이 스킬을 테스트했습니다. 예를 들어 Swift UI 앱 관련 코드ex 스레드에서 나온 결과는 다음과 같았습니다.</p>
<p>&gt; &quot;Build 26이 App Store Connect에 업로드됐고 처리도 완료됨. (구체적으로 한 일들을 불릿 포인트로 나열) 퍼블릭 배포는 아직 확인 불가 — App Store Connect 브라우저 세션이 만료됐기 때문. 링크에서 로그인할 것. 자동 배포가 처리하지 않으면 Build 26을 퍼블릭 베타 그룹에 할당하면 됨.&quot;</p>
<p>이 결과는 읽기 매우 쉽고 스캔하기도 편했다는 게 Theo의 평입니다. 또한 새 프롬프트를 실행할 때마다 AI가 스스로 &quot;unslop 작성 스킬을 적용해서 답변을 직접적이고 훑어보기 쉽게 유지하겠다&quot;는 식으로 명시적으로 스킬 적용을 선언하는 것도 확인했습니다. 실제로 나온 결과물도 예를 들어 &quot;T3 Chat, 코딩 에이전트를 위한 오픈소스 컨트롤 센터&quot;처럼 codeex, cloud code, cursor, grok 같은 여러 도구를 오가는 상황을 아주 간결하게 정리해줬습니다.</p>
<p>Theo는 이 스킬이 담긴 좋은 글쓰기 예시를 히스토리에 갖고 있으면 모델이 그 스타일을 따라 할 가능성이 높아지고, 거기에 명시적으로 그 스타일을 따르라고 지시하면 훨씬 더 확실히 따른다는 점도 짚었습니다.</p>
