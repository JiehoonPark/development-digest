16:T3627,<h2>마우스가 지나가기만 해도 열리는 툴팁, 어떻게 고쳐야 할까</h2>
<p>FrontPrep이라는 서비스를 운영하는 개발자 Abhishek Jakhar는 인터뷰 질문 목록 페이지에서 회사 로고에 마우스를 올리면 회사명을 보여주는 툴팁을 붙였습니다. 그런데 며칠간 신경을 긁는 문제가 있었는데요. 커서를 그냥 페이지 위로 쓸고 지나가기만 해도 지나가는 로고마다 툴팁이 즉시 튀어나온 겁니다. 원인은 간단했습니다. 툴팁 딜레이를 0ms로 설정해뒀기 때문에 커서가 로고에 닿는 즉시 툴팁이 열렸던 거죠.</p>
<p>이 문제를 200ms 딜레이로 해결하긴 했지만, 곧 다른 문제가 생겼습니다. FrontPrep 화면에는 같은 인터뷰 질문을 여러 회사가 공유하는 경우가 많아서, 한 줄에 여러 회사 로고가 나란히 붙어 있는 구간이 있습니다. 이런 구간에서 로고 하나에서 다음 로고로 커서를 옮길 때마다 매번 200ms를 기다려야 하니, 오히려 느리고 답답한 UX가 되어버린 겁니다. 이 글은 툴팁 구현 자체를 다루는 글이 아니라, 브라우저 툴바 등 여기저기서 이미 쓰이고 있지만 정작 대부분의 개발자가 인지하지 못하는 이 작은 인터랙션 패턴 하나를 다룹니다.</p>
<h3>문제의 핵심: 딜레이는 필요하지만, 딜레이가 항상 필요한 건 아니다</h3>
<p>핵심 아이디어는 이렇습니다. 툴팁을 여는 데는 딜레이가 필요합니다. 클릭은 항상 의도적인 행동이지만, 호버는 그렇지 않습니다. 커서는 목적지로 가는 길에 어쩔 수 없이 여러 요소 위를 지나가게 되고, 툴팁은 이 호버만으로는 사용자가 정말 툴팁을 열고 싶은 건지 판단할 수 없습니다. 200ms라는 시간이 바로 이 판단의 근거가 됩니다.</p>
<p>하지만 인접한 여러 트리거를 연속으로 오갈 때는 매번 이 딜레이를 다시 기다리게 하면 안 됩니다. 저자가 제시한 해결책은 세 단계로 나뉩니다.</p>
<ul>
<li>로고에 커서를 올리면 툴팁은 200ms를 기다린 뒤 열립니다.</li>
<li>툴팁이 닫히면 300ms짜리 타이머가 시작됩니다. 저자는 이 구간을 &quot;warm window(웜 윈도우)&quot; 혹은 &quot;페이지가 warm한 상태&quot;라고 부릅니다. 이 300ms 타이머가 돌아가는 동안 다른 로고에 커서를 올리면, 툴팁은 대기나 애니메이션 없이 즉시 열립니다.</li>
<li>300ms 타이머가 끝나면 페이지는 다시 &quot;cold&quot; 상태로 돌아갑니다. 이 상태에서 로고에 커서를 올리면 다시 200ms를 기다려야 합니다. 이 단계가 없다면 처음 열린 툴팁 하나가 페이지 전체의 딜레이를 영구히 없애버리는 꼴이 됩니다.</li>
</ul>
<p>전체 흐름을 정리하면 다음과 같습니다.</p>
<pre><code>hover → wait 200ms → tooltip opens (page is now warm)
leave → tooltip closes → 300ms cooldown
  ├─ hover another tooltip before cooldown → opens instantly, page stays warm
  └─ cooldown ends → page is cold, the 200ms wait is back</code></pre>
<p>FrontPrep에서는 실제로 Radix와 Motion으로 툴팁을 구현했지만, 이 글에서는 이해를 돕기 위해 더 단순한 React 버전으로 패턴을 보여줍니다.</p>
<h3>코드로 보는 동작 원리</h3>
<p>커서를 움직일 때 실제로 일어나는 순서 그대로 코드를 따라가 보겠습니다.</p>
<h4>1단계: 로고에 커서를 올린다</h4>
<p>로고에서 <code>onMouseEnter</code>가 발생하면 다음 함수가 호출됩니다.</p>
<pre><code class="language-javascript">function handleEnter() {
  If (tooltips.isWarm) {
    show();
    return;
  }
  openTimer.current = setTimeout(show, tooltips.openDelay);
}</code></pre>
<p>호버가 발생하면 이 컴포넌트는 딱 한 가지만 물어봅니다. &quot;지금 페이지가 warm한가?&quot; warm하다면 즉시 툴팁을 엽니다. 그렇지 않다면 200ms 타이머를 걸고 기다립니다. 여기 등장하는 <code>tooltips</code> 객체는 마지막 단계에서 다룰 <code>TooltipProvider</code>에서 내려오는 값입니다.</p>
<h4>2단계: 툴팁이 열린다</h4>
<p>열리는 동작을 담당하는 <code>show</code> 함수는 다음과 같습니다.</p>
<pre><code class="language-javascript">function show() {
  setInstant(tooltips.isWarm);
  setOpen(true);
  tooltips.markOpened();
}</code></pre>
<p>이 함수는 세 가지 일을 합니다.</p>
<ul>
<li><code>tooltips.isWarm</code>의 값을 <code>instant</code>라는 state에 복사합니다.</li>
<li>툴팁을 엽니다.</li>
<li>provider에게 툴팁이 열렸다는 사실을 알려서 페이지를 warm 상태로 만듭니다.</li>
</ul>
<p>1번을 다시 살펴보면, <code>instant</code> 플래그는 툴팁에 data attribute로 붙는데, CSS가 이 값을 보고 진입 애니메이션을 건너뛰기 위해서입니다.</p>
<pre><code class="language-css">.tooltip[data-instant=&quot;true&quot;] {
  transition-duration: 0ms;
}</code></pre>
<p>이 덕분에 페이지가 warm할 때는 애니메이션이나 딜레이 없이 즉시 툴팁이 열리는 겁니다.</p>
<h4>3단계: 로고에서 커서가 벗어난다</h4>
<p><code>onMouseLeave</code>가 발생하면 다음 함수가 호출됩니다.</p>
<pre><code class="language-javascript">function handleLeave() {
  clearTimeout(openTimer.current);
  If (!open) return;
  setOpen(false);
  setInstant(false);
  tooltips.markClosed();
}</code></pre>
<p>먼저 확인해야 할 것은 지금 툴팁이 열려 있는 상태인지입니다.</p>
<p>예를 들어 커서가 로고를 50ms 만에 지나갔다고 해봅시다. 이는 200ms보다 훨씬 짧기 때문에, <code>handleEnter</code>가 걸어둔 타이머는 아직 돌아가는 중이고 툴팁은 아직 열리지 않은 상태입니다. <code>handleLeave</code>의 <code>clearTimeout</code>이 이 타이머를 취소해서 툴팁이 애초에 열리지 않게 만들고, <code>if (!open) return;</code>이 함수를 그 자리에서 끝내버립니다. 열린 적도 없는 툴팁이니 닫을 것도, 쿨다운을 시작할 것도 없기 때문입니다. 첫 번째 영상에서는 커서가 지나간 경로의 모든 툴팁이 열렸지만, 이제는 같은 경로를 쓸어도 아무 툴팁도 열리지 않습니다.</p>
<p>반대로 툴팁이 열려 있는 상태라면 — 즉 커서가 로고 위에 200ms 이상 머물렀거나, 페이지가 이미 warm해서 호버 즉시 열린 경우 — 툴팁을 닫고 provider에게 이를 알립니다. 그러면 provider는 300ms 쿨다운 타이머를 시작하고, 이 타이머가 끝나기 전에 다음 로고에 커서를 올리면 그 툴팁은 즉시 열립니다.</p>
<h4>4단계: Provider</h4>
<pre><code class="language-javascript">const warm = useRef(false);
const cooldownTimer = useRef(null);
useEffect(() =&gt; () =&gt; clearTimeout(cooldownTimer.current), []);

const tooltips = useMemo(
  () =&gt; ({
    openDelay,
    isWarm: () =&gt; skipWhenWarm &amp;&amp; warm.current,
    markOpened() {
      warm.current = true;
      clearTimeout(cooldownTimer.current);
    },
    markClosed() {
      clearTimeout(cooldownTimer.current);
      cooldownTimer.current = setTimeout(() =&gt; {
        warm.current = false;
      }, warmFor);
    },
  }),
  [openDelay, warmFor, skipWhenWarm]
);</code></pre>
<p>이 패턴 전체가 동작하기 위해 필요한 공유 상태가 바로 여기 있습니다. 페이지는 warm 상태거나 cold 상태 둘 중 하나입니다. 여기서 주목할 부분은 <code>markOpened</code>가 대기 중인 쿨다운을 취소한다는 점입니다. 바로 이 부분이 로고에서 로고로 이동할 때 페이지를 계속 warm하게 유지시켜주는 핵심 장치입니다. 새로 열리는 툴팁이 앞선 툴팁이 시작해둔 쿨다운을 매번 취소하는 구조인 거죠.</p>
<p><code>skipWhenWarm</code> 플래그는 헷갈릴 필요 없이, 데모에서 before/after를 토글하기 위한 용도일 뿐입니다. 이 값을 끄면 provider가 항상 cold 상태로 남아 있어서 개선 전 동작을 볼 수 있습니다.</p>
<p>또 하나 중요한 디테일은 <code>isWarm</code>이 React state가 아니라 ref라는 점입니다. ref 값을 바꾸는 것은 페이지의 모든 툴팁을 리렌더링시키지 않기 때문입니다. 이 ref는 오직 이벤트 핸들러 내부에서만 읽힙니다.</p>
<h3>왜 200ms인가</h3>
<p>150ms보다 짧은 타이머를 쓰면, 커서가 툴팁 트리거 위를 그냥 지나가기만 해도 십중팔구 툴팁이 열려버립니다. 반대로 250ms보다 긴 타이머를 쓰면 의도적으로 호버해도 반응이 느리고 부자연스럽게 느껴집니다. 그래서 200ms가 이 상황에서 균형 잡힌 적정값이라는 것이 저자의 결론입니다. 같은 논리로 warm window(쿨다운)는 300ms — 한 트리거에서 다음 트리거로 이동하는 동작을 충분히 커버할 만큼 길지만, 1초쯤 지난 뒤의 호버는 다시 기다리게 할 만큼 짧은 값 — 로 설정했고, close delay는 0ms로 두었습니다. 트리거에서 벗어나는 행동은 명확한 의도이기 때문에 기다릴 이유가 없다는 것입니다.</p>
<h3>판단력과 감각(Judgement &amp; Taste)</h3>
<p>저자는 AI에게 툴팁을 만들어달라고 하면 &quot;동작하는&quot; 툴팁은 만들어주지만, 그 결과물이 정말 괜찮은지 판단하는 것은 결국 인간의 몫이라고 짚습니다. 동작하는 툴팁과 다듬어진 툴팁을 가르는 것은 이런 디테일이며, 이는 동작하는 제품과 다듬어진 제품을 가르는 것과 같은 종류의 차이입니다. AI는 사람이 방향을 제시할 때만 다듬어진 결과물을 만들 수 있고, 그 방향을 제시하려면 수년간의 경험과 실수, 연습에서 나온 판단력과 감각이 필요합니다.</p>
<p>다만 다른 엔지니어나 디자이너의 감각을 담은 &quot;skill&quot;을 활용해 자신만의 감각을 키워나가는 것도 방법입니다. 색상, 접근성, 폼, 애니메이션, 타이포그래피 등 다양한 영역에 대한 skill을 만들거나 활용해 꽤 괜찮은 결과물을 뽑아낼 수는 있지만, 그렇다고 그게 곧바로 프로덕션에 쓸 수 있다는 뜻은 아닙니다. 결국 그 결과물이 자신의 기준과 감각에 부합하는지 판단하고 출시를 결정하는 것은 여전히 사람의 역할입니다.</p>
<h3>Claude Skill로 코드베이스 점검하기</h3>
<p>저자는 이 문제를 해결하기 위해 만든 Claude skill을 공개했습니다. 이 skill을 그대로 복사해서 실행하거나 참고해 비슷한 skill을 만들면 자신의 코드베이스를 점검할 수 있습니다. 코드베이스마다 툴팁을 만드는 라이브러리가 다르고 커스텀 구현 방식도 다르지만, 이 skill은 그런 차이와 무관하게 동작합니다.</p>
<p><code>.claude/skills/tooltip/SKILL.md</code>:</p>
<pre><code>---
name: tooltip
description: Tooltips need a delay so they don't open up on unintentional mouse travel
---
# Tooltip Timing

A click is always intentional whereas a hover is not intentional. The cursor travels across the page to get wherever it has to, and it passes over elements on the way, so a tooltip cannot tell from the hover whether the user wants to open it. The 200ms is how it finds out.

.tooltip {
  transition-delay: 200ms;
}

## The three numbers and states

| Value       | Number | Why                                                                  |
| ----------- | ------ | --------------------------------------------------------------------- |
| Open delay  | 200ms  | Below 150ms a cursor that is only passing over a trigger still opens it. Above 250ms an intentional hover feels broken. |
| Warm window | 300ms  | Long enough to cover the move from one trigger to the next one. Short enough that a hover a second later waits again. |
| Close delay | 0ms    | Leaving a trigger should be clear. So there is nothing to wait for.   |

## How it should behave

hover -&gt; wait 200ms -&gt; tooltip opens (page is now warm)
leave -&gt; tooltip closes -&gt; 300ms cooldown</code></pre>
<h3>정리</h3>
<ul>
<li>호버 기반 툴팁은 딜레이가 반드시 필요합니다. 딜레이가 없으면 커서가 지나가기만 해도 의도치 않게 툴팁이 열립니다. 200ms 정도(150ms~250ms 사이)가 실수로 지나가는 것과 의도적인 호버를 구분하는 적정 기준입니다.</li>
<li>하지만 인접한 여러 트리거를 연속으로 탐색할 때는 매번 딜레이를 기다리게 하면 UX가 오히려 나빠집니다. 이를 해결하려면 &quot;warm/cold&quot; 상태 개념을 도입해, 툴팁이 닫힌 뒤 일정 시간(예: 300ms) 동안은 다음 트리거가 즉시 열리도록 해야 합니다.</li>
<li>구현 핵심은 <code>isWarm</code> 상태를 ref로 관리해 불필요한 리렌더링을 피하고, <code>markOpened</code>/<code>markClosed</code>로 쿨다운 타이머를 취소·재시작하는 provider 패턴입니다. 여기에 CSS의 <code>data-instant</code> 속성으로 애니메이션을 건너뛰는 처리까지 더하면 완성됩니다.</li>
<li>close delay는 0ms로 두는 것이 자연스럽습니다. 트리거에서 벗어나는 행동은 이미 의도가 명확하기 때문입니다.</li>
<li>이런 디테일은 AI에게 &quot;툴팁을 만들어달라&quot;고 요청해서는 자동으로 얻어지지 않으며, 개발자가 직접 판단하고 다듬어야 하는 영역입니다. 저자는 이 패턴을 Claude skill로 문서화해 코드베이스 점검에 재사용할 수 있도록 공개했습니다.</li>
