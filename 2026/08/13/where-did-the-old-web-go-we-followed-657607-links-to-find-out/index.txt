15:T324b,<p>웹의 링크는 영원할 것 같지만, 실제로는 끊임없이 사라지고 있습니다. 마케도니아의 URL 단축 서비스 0.mk 팀은 2009년부터 2014년까지 만들어진 65만 개가 넘는 링크의 데이터베이스 백업을 우연히 발견했고, 2026년 8월 이 링크들을 하나하나 다시 방문해봤습니다. 그 결과를 정리한 이 아티클은 &quot;옛날 웹은 대체 어디로 사라졌는가&quot;라는 질문에 구체적인 숫자로 답합니다.</p>
<h3>조사 배경</h3>
<p>0.mk는 2009년, 세 명이 부업 삼아 시작한 프로젝트였습니다. 일주일에 몇 시간씩 짬을 내서 운영하다가 2014년 무렵 서비스를 종료했는데, 17년이 지난 뒤 팀원 중 한 명이 디스크에 남아있던 옛 데이터베이스 백업을 찾아냈습니다. 여기엔 2009~2014년 사이 생성된 657,958개의 링크와 각 링크의 클릭 수가 고스란히 남아 있었죠.</p>
<p>이 중 657,607개를 2015년 이전 링크로 복원한 뒤, 2026년 8월 모든 목적지 URL을 크롤러로 재방문했습니다. 다만 이 데이터는 웹 전체에 대한 통계가 아니라, 당시 마케도니아 온라인 커뮤니티가 공유했던 지역 뉴스, 개인 블로그, 사진 호스팅, 포럼, 그리고 당대 주요 플랫폼들의 기록이라는 점을 짚어둘 필요가 있습니다.</p>
<h3>76.7%가 사라졌다</h3>
<p>크롤링 대상은 2014년 12월까지 생성된 링크 657,607건 전체입니다. 이 중 목적지가 손상되었거나, 내부 주소이거나, 인증이 필요하거나, 정책상 접근이 차단된 2,429건을 제외하고 나면 655,178건의 크롤링 가능한 히스토리 링크가 남습니다. 결과는 다음과 같습니다.</p>
<ul>
<li><strong>51.24%</strong> — 연결 자체가 불가능 (DNS 오류, 타임아웃, TLS 오류)</li>
<li><strong>25.44%</strong> — HTTP 에러 (4xx / 5xx)</li>
<li><strong>23.32%</strong> — 정상 로딩 (2xx / 3xx 응답)</li>
</ul>
<p>즉 76.7%는 더 이상 페이지를 불러오지 못했습니다. 그런데 이 23.3%라는 수치조차 실제 생존율을 과대평가한 것일 수 있습니다. 로그인 페이지, 광고로 도배된 파킹 도메인, &quot;이 콘텐츠는 더 이상 제공되지 않습니다&quot;라는 안내 문구도 모두 &quot;로딩됨&quot;으로 카운트되기 때문입니다. 페이지가 뜬다고 해서 원래 콘텐츠가 그 자리에 있다는 뜻은 아니라는 겁니다.</p>
<h3>링크 레코드 수 vs 고유 URL 수</h3>
<p>657,607개의 링크 레코드가 있지만, 실제 고유 URL 수는 494,781개입니다. 서로 다른 단축 링크가 정확히 같은 목적지를 가리키는 경우가 162,826건이나 있었기 때문입니다. 목적지를 한 번씩만 세면 494,781개의 고유 URL이 남고, 이 중 492,620개가 크롤링 가능했습니다. 이 고유 URL 기준으로는 <strong>21.3%</strong>만 로딩되었습니다.</p>
<p>중복 목적지를 제거해도 결과는 크게 달라지지 않습니다. 여전히 78.7%가 로딩되지 않았죠. 고유 URL 레벨에서는 두 번째 네트워크로 재시도한 뒤에도 <strong>55.0%</strong>가 네트워크 계층에서 실패했고, <strong>23.7%</strong>가 HTTP 에러를 반환했습니다. 가장 흔한 HTTP 응답은 404로, 76,403개의 고유 URL에서 나타났습니다. 또 다른 29,663개는 403이나 429를 반환했는데, 이 경우는 크롤러 접속 자체가 차단된 것일 수 있어 &quot;사라졌다&quot;기보다 &quot;로딩되지 않았다&quot;고 보는 게 더 정확합니다.</p>
<p>도메인 레벨에서도 같은 패턴이 반복됩니다. 크롤링 가능한 133,605개 호스트네임 중 단 하나의 URL이라도 로딩된 곳은 34,827개뿐이었고, 나머지 98,778개는 단 하나도 로딩되지 않았습니다.</p>
<h3>연도별로 보면</h3>
<p>연도별 &quot;로딩 안 됨&quot; 비율(전체 크롤링 기준)은 다음과 같습니다.</p>

<p>2011년의 유독 높은 수치는 특이 사례 때문입니다. 어떤 계정 하나가 pelaphptutorials.com이라는 사이트로 향하는 링크를 83,398개나 만들었는데, URL 기준으로 보면 2011년 목적지의 92.5%가 로딩되지 않는 것으로 나타나지만, 이 호스트를 한 번만 세면 61.7%로 2010년·2012년과 거의 같아집니다.</p>
<p>이 배치를 제외하면 2011년 레코드 수는 103,053건에서 19,655건으로 줄어들고, 2012년은 23,148건입니다. 즉 연간 총량 그래프만 보고 2012년에 사용량이 갑자기 붕괴했다고 해석하면 안 됩니다. 게다가 2013년과 2014년 레코드는 각각 97.8%, 99.9%가 복원된 계정 정보와 연결되지 않은 익명 데이터인데, 이들 호스트네임의 4분의 3은 로딩되는 URL이 하나도 없습니다. 링크 생성량 자체는 사용자 증가 곡선을 대변하지 않는다는 뜻이죠.</p>
<p>전반적으로 살아남은 것들은 대부분 거대 플랫폼입니다. YouTube, Wikipedia, 구글 계열 서비스는 여전히 살아있는 반면, 개인 블로그, 포럼, 지역 뉴스 사이트, 사진 호스팅 서비스는 대부분 사라진 목록에 속해 있었습니다. 중앙화된 웹은 작은 웹보다 확실히 더 잘 버텨냈습니다.</p>
<h3>2010년대 인터넷 유적지 탐방</h3>
<p>데이터베이스는 2010년대 인터넷 박물관 같은 모습을 하고 있습니다. 각 서비스로 향하는 링크 수와 생존 여부는 다음과 같습니다.</p>
<ul>
<li><strong>Facebook 사진 CDN (fbcdn.net)</strong> — 835개 링크, 하나도 로딩되지 않음</li>
<li><strong>Google Code</strong> — 803개 링크, 지금은 다수의 URL을 자체 아카이브로 리다이렉트</li>
<li><strong>PureVolume</strong> — 796개 링크, 예전 서비스는 사라졌지만 도메인은 응답함</li>
<li><strong>Rapidshare</strong> — 139개 링크, 하나도 로딩되지 않음</li>
<li><strong>Megaupload</strong> — 71개 링크, 하나도 로딩되지 않음</li>

<p>사람들이 Facebook 사진을 CDN 직링크로 공유했던 관행 때문에, 835건의 레코드 뒤에 있는 789개의 고유 fbcdn.net URL은 단 하나도 로딩되지 않았습니다. 반면 PureVolume은 653개 고유 URL 중 633개가 지금도 페이지를 반환하고, Google Code는 754개 중 628개가 로딩되거나 리다이렉트됩니다. 원래 서비스는 사라졌지만 도메인은 여전히 응답하고 있는 셈이죠. 즉, HTTP 응답이 온다고 해서 콘텐츠가 보존되어 있다는 뜻은 아닙니다.</p>
<h3>마케도니아 웹의 흔적</h3>
<p>0.mk는 마케도니아 최초의 URL 단축 서비스였던 만큼, 이 데이터는 이제는 부분적으로 사라진 마케도니아 국가 단위 웹의 기록이기도 합니다. 2011년 문을 닫은 A1 텔레비전, 그리고 2017년 폐간된 신문사 Utrinski Vesnik, Dnevnik, Vest로 향하는 링크가 남아있습니다. 수백 개의 지역 뉴스 링크가 이제는 인터넷 아카이브를 제외하고는 어디에서도 읽을 수 없는 상태입니다. 단축 링크는 그것이 가리켰던 언론사보다 오래 살아남았습니다.</p>
<h3>보석 같은 링크들</h3>
<p>17년 치 남의 북마크 더미 속에는 흥미로운 기록도 숨어 있었습니다.</p>
<ul>
<li>사상 첫 번째 단축 링크(2009년 7월 14일 오전 3시 52분)는 거창한 선언문이나 런칭 포스트가 아니라, 누군가의 워드프레스 블로그에 걸린 CSS 스타일시트였습니다. 클릭 수는 평생 딱 두 번.</li>
<li>서비스 이틀째, 누군가 localhost를 단축했습니다. 0.mk/localhost는 http://127.0.0.1/을 가리켰고, 두 번 클릭될 때마다 방문자를 각자 자신의 컴퓨터로 돌려보냈습니다. 가장 짧은 URL이 가장 외로운 목적지를 가리킨 사례입니다.</li>
<li>가장 짧은 링크는 가장 긴 도메인을 가리킵니다. 0.mk/1은 17년간 10,415번 클릭되며 thelongestlistofthelongeststuffatthelongestdomainnameatlonglast.com이라는 2000년대의 기묘한 사이트를 가리켜 왔는데, 이 사이트 역시 지금은 사라졌습니다. 4글자가 63글자를 가리키는 관계가 17년째 이어진 셈입니다.</li>
<li>지금까지 단축된 가장 긴 URL은 38,753자로, 쿼리 스트링에 TRYING_THE_MAXIMUM_URL이라는 문구가 반복되는 2012년 CodePen 링크였습니다. 누군가 시스템의 한계를 테스트하고 있었던 것이고, 서비스는 그 테스트를 통과했으며 그 기록은 지금도 남아 있습니다.</li>
<li>4,478개 링크는 bit.ly, TinyURL, goo.gl 같은 다른 URL 단축 서비스를 가리킵니다. 단축 링크가 또 다른 단축 링크를 가리키는, 이중으로 취약한 구조죠. 구글이 2025년 goo.gl 서비스를 종료하면서, 이 링크들은 이제 &quot;중간이 끊어진 체인&quot;이 되었습니다. 0.mk 쪽 절반은 여전히 작동하지만, 그 끝에 있던 goo.gl은 더 이상 해석되지 않습니다. 링크 부패의 제곱인 셈입니다.</li>
<li>그리고 불멸의 링크 하나: 2009년 7월 15일 만들어진 0.mk/7은 google.com을 가리킵니다. 95,999번 클릭되었고, 17년과 한 번의 서비스 부활을 거친 지금도 여전히 그 자리를 지키고 있습니다.</li>
</ul>
<h3>0.mk는 왜 돌아왔나</h3>
<p>2014년 당시 0.mk의 수익은 호스팅 비용과 운영에 필요한 작업량을 감당하지 못했습니다. 스팸은 끊임없이 밀려들었고, 이를 걸러내려면 더 많은 엔지니어링이 필요했으며, 남용 신고는 사람이 일일이 검토해야 했습니다. 결국 원년 팀은 서비스를 접었습니다.</p>
<p>17년이 지난 지금, AI가 이 방정식을 바꿔놓았습니다. 예전에는 감당할 수 없었던 개발, 스팸 탐지, 남용 신고 검토, 고객 지원, 모니터링 작업의 상당 부분을 이제는 AI가 처리합니다. 덕분에 0.mk를 다시 살리는 일이 현실적으로 가능해졌고, 복원된 링크들은 이제 300개가 넘는 도시의 엣지 머신에서 서비스되고 있습니다.</p>
<h3>검증 방법</h3>
<p>2015년 1월 1일 이전 날짜로 복원된 모든 링크를 테스트 대상으로 삼았습니다. 크롤러는 최대 5회의 리다이렉트를 따라갔고, 연결 실패로 판정된 결과는 두 번째 네트워크에서 재시도했습니다. HTTP 2xx 및 3xx 응답은 &quot;로딩됨&quot;으로 카운트했고, HTTP 에러는 별도로 집계했으며, 로컬 주소나 안전하지 않은 주소는 애초에 접속하지 않았습니다.</p>
<h3>정리</h3>
<ul>
<li>2009~2014년 생성된 65만여 개 링크를 2026년 재크롤링한 결과, 76.7%가 더 이상 페이지를 로딩하지 못했으며, &quot;로딩됨&quot;으로 분류된 23.3%조차 로그인 벽이나 파킹 도메인을 포함하고 있어 실제 콘텐츠 생존율은 이보다 낮습니다.</li>
<li>중복 링크를 제거한 고유 URL 494,781개 기준으로는 로딩 성공률이 21.3%까지 떨어지며, 도메인 133,605개 중 74%는 로딩되는 URL이 단 하나도 없었습니다.</li>
<li>YouTube, Wikipedia, Google 같은 대형 플랫폼은 대체로 살아남았지만, 개인 블로그·포럼·지역 뉴스·사진 호스팅 같은 &quot;작은 웹&quot;은 거의 사라졌습니다. 이는 웹 아카이빙과 콘텐츠 이관에서 중앙화 서비스 대 소규모 사이트의 생존력 격차를 그대로 보여줍니다.</li>
<li>도메인이 응답한다고 해서 원래 콘텐츠가 남아있는 것은 아니라는 점(PureVolume, Google Code 사례), 그리고 단축 링크가 원본 뉴스 매체보다 오래 살아남는 역설적 상황(마케도니아 신문 폐간 사례)은 URL 영속성과 콘텐츠 보존이 서로 다른 문제임을 보여줍니다.</li>
<li>프론트엔드/웹 개발자 입장에서는 외부 리소스에 대한 하드링크(CDN 직링크, 타 서비스 단축 URL 체이닝 등)가 장기적으로 얼마나 취약한지, 그리고 아카이빙·리다이렉트 전략을 설계할 때 &quot;HTTP 응답 성공&quot;과 &quot;콘텐츠 보존&quot;을 구분해야 한다는 실무적 교훈을 얻을 수 있습니다.</li>
