13:T27fe,<h2>MCP, 드디어 제대로 고쳐진 걸까?</h2>
<p>2025년 한 해 동안 모두가 MCP(Model Context Protocol)를 자기 제품에 통합하려고 안달이었지만, 저는 줄곧 MCP에 대해 부정적인 입장이었습니다. 지나치게 부풀려진, 비대한 스펙이라 문제를 해결하는 만큼 새로운 문제를 만들어낸다고 생각했고, 실제로 일상 워크플로우에서도 잘 쓰지 않았습니다. 오히려 Codex처럼 MCP를 스펙대로 &quot;제대로&quot; 구현한 도구를 쓸 때마다 리소스 낭비가 심해서 더 짜증이 났습니다. 그런데 최근 Anthropic이 다섯 번째 MCP 스펙을 내놓으면서 이 프로토콜의 핵심 구조를 완전히 바꿔버렸습니다. Simon Willison은 이를 두고 &quot;stateless MCP가 다시 내 관심을 사로잡았다&quot;고 표현했는데요, 이번 글에서는 MCP가 그동안 왜 문제였는지, 그리고 이번 개편이 무엇을 바꿨는지 살펴보겠습니다.</p>
<h3>MCP가 왜 그렇게 별로였나</h3>
<p>MCP의 근본적인 문제는 클라이언트와 서버가 <strong>양방향(bidirectional) 상태 유지(stateful) 연결</strong>을 맺어야 한다는 구조에 있었습니다. 실제로 그 도구를 호출하지 않더라도, MCP 서버가 하나 설정되어 있으면 에이전트가 실행되는 동안 그 서버와의 연결이 계속 살아있어야 했습니다.</p>
<p>예를 들어 Cloud Code에 MCP 5개를 설정해두고, 그중 하나도 쓰지 않는 작업을 실행하더라도 그 실행 세션은 5개의 상태 유지 연결을 외부 서비스와 계속 붙잡고 있는 셈입니다. 이게 왜 문제인지는 Codex를 쓰다 보면 바로 체감할 수 있습니다. Codex에서 새 스레드를 열 때마다 Xcode build MCP 같은 서버들을 초기화하느라 첫 메시지가 막혀버리는 현상이 있었습니다. (최근에는 메시지를 보낸 뒤에 초기화하도록 바뀌면서 조금 나아졌지만요.)</p>
<p>더 심각한 건 서브 에이전트(sub-agent)가 생성될 때입니다. Codex에서 하나의 에이전트 실행이 서브 에이전트 5개를 스폰하면, 각 서브 에이전트마다 컴퓨터 사용(computer use) 관련 MCP 서버 5개 이상을 상태 유지 연결로 붙잡아야 합니다. 즉 하나의 프롬프트를 위해 로컬 머신에 30개의 상태 유지 연결이 생기는 겁니다. 서버 쪽에서도 30개의 상태 유지 프로세스가 떠 있고, 클라이언트 쪽에서도 30번 바인딩이 됩니다. macOS를 쓰는 사람이라면 <code>sysctld</code>가 CPU를 잡아먹는 걸 본 적이 있을 텐데, 이게 바로 그 원인입니다. macOS가 프로세스를 감시하는 <code>sysctld</code>는 로컬 머신에서 서버가 30개씩 뜨는 걸 당연히 의심스러운 활동으로 보게 됩니다.</p>
<p>이런 오버헤드 때문에 실제로 많은 MCP 서버들이 클라우드에 호스팅되지 못하고 로컬로만 돌아가는 경우가 많았습니다. 99%의 시간 동안 사용되지 않는 서비스를 위해 클라우드 인프라를 유지하는 비용이 그만한 가치가 없었기 때문입니다.</p>
<h3>새 스펙의 핵심: Stateless Core</h3>
<p>이번에 나온 다섯 번째 MCP 스펙 릴리스(버전명은 <code>2026-06-28</code>)의 핵심은 MCP가 <strong>stateless core</strong>로 전환됐다는 점입니다. Anthropic의 설명에 따르면 MCP는 양방향 상태 유지 프로토콜에서 <strong>요청-응답(request-response) 모델</strong>로 옮겨갔습니다. 이 덕분에 서버를 서버리스(serverless)나 엣지(edge) 인프라에 배포할 수 있게 됐고, MCP 서버를 만들고 채택 규모가 커질 때 스케일링하는 경험이 훨씬 단순해졌습니다.</p>
<p>이제 각 에이전트는 그냥 임의의 엔드포인트를 호출해서 JSON을 받아오고, 그걸 바탕으로 다음에 뭘 할지 결정하면 됩니다. 연결을 계속 바인딩해둘 필요가 없어진 거죠. 사실 MCP는 애초에 에이전트에게 &quot;내가 할 수 있는 것&quot;을 알려주고, 그걸 호출하는 데 필요한 정보를 주는 역할만 하면 충분했는데, 이번 개편으로 그 본질에 맞게 동작하게 된 셈입니다. 호스팅 방식도 훨씬 자유로워졌습니다. 로컬에서는 단순한 HTTP API로, 클라우드에서는 간단한 키 하나로 구분하는 방식으로도 얼마든지 구현할 수 있습니다.</p>
<p>이번 스펙에는 이 외에도 apps와 tasks를 통한 확장 기능 표준화, 인증(auth) 강화 같은 개선도 포함됐습니다. 공식 MCP 사이트에는 이 변화를 시각화해서 보여주는 도구도 올라와 있는데요, 예전에는 클라이언트가 항상 같은 서버 인스턴스에 연결되도록 보장하는 &quot;지능형 로드밸런서(intelligent load balancer)&quot;가 필요했습니다. 요청이 어느 서버로 라우팅됐는지 계속 추적하고, 같은 클라이언트의 후속 요청이 항상 그 서버로 돌아가게 만들어야 했죠. Stateless 모델에서는 이 모든 복잡성이 사라집니다. Anthropic은 이 stateless 전환이 개발자들이 가장 많이 요청한 기능 중 하나였다고 밝혔는데, 실제로 낡은 웹 스펙에서 가져온 핸드셰이크 과정을 없앤 건 확실히 반가운 변화입니다.</p>
<h3>MCP는 왜 다시 주목받는가 — Skills와의 관계</h3>
<p>MCP는 2024년 11월 Anthropic이 처음 발표한 프로토콜로, 2025년 내내 큰 관심을 받았습니다. 하지만 곧 Anthropic이 만든 또 다른 개념인 <strong>Skills</strong>에 인기를 빼앗겼습니다. 화려한 스펙과 프로토콜이 결국 마크다운 파일 하나로 대체된 셈인데, 요즘 여러 영역에서 이런 패턴이 반복되고 있습니다. 터미널과 <code>curl</code> 접근 권한을 가진 에이전트 하네스가 MCP가 하던 일의 대부분을 더 유연하게 처리할 수 있다는 게 명확해지면서 Skills가 우위를 점했습니다.</p>
<p>그런데 Simon Willison은 이번 stateless 전환으로 다시 MCP 쪽으로 관심이 옮겨가고 있다고 말합니다. 에이전트에게 셸 환경과 인터넷 접근 권한을 주는 방식은 위험 부담이 크고, 그런 환경을 효과적으로 다루려면 강력한 모델이 필요합니다. 반면 MCP 도구는 감사(audit)하고 통제하기가 훨씬 쉽고, 충분히 단순해서 노트북에서 돌아가는 작은 모델도 무리 없이 다룰 수 있습니다.</p>
<h3>Simon Willison이 본 Before/After</h3>
<p>Simon은 이번 주에만 stateless MCP 서버를 3개 직접 만들어봤다고 밝히며, 새 스펙이 클라이언트와 서버 양쪽 구현 복잡도를 크게 줄였다고 설명합니다. 그는 기존 방식을 &quot;legacy MCP&quot;라고 부르는데, legacy MCP는 다음과 같이 동작했습니다.</p>
<ul>
<li><strong>HTTP 요청 1</strong>: 세션을 초기화하고 세션 ID를 발급받음</li>
<li><strong>HTTP 요청 2</strong>: 실제 도구를 호출</li>
</ul>
<p>문제는 도구 호출 요청이 들어올 때마다 이 세션 ID와 매칭해서 원래 연결됐던 서버로 정확히 라우팅해야 한다는 점이었습니다. 이는 곧 상태를 계속 유지하는 &quot;sticky routing&quot;이 필수였다는 뜻입니다.</p>
<p>새로운 stateless 버전은 <strong>단 하나의 HTTP 요청</strong>만으로 동작합니다. 애초에 이렇게 동작했어야 하는 방식이죠. 서버 쪽에서 세션 ID를 추적하거나 동일 세션을 항상 같은 백엔드 머신으로 라우팅해야 한다는 부담이 없어졌기 때문에, 스케일 가능한 웹앱을 만들기에도 훨씬 적합해졌습니다.</p>
<p>Simon은 이런 변화를 살펴보기 위해 Codex와 함께 <strong>MCP Explorer</strong>라는 도구도 만들었습니다. 이는 stateless Python CLI로, 설치할 필요 없이 <code>uvx</code>로 바로 실행해볼 수 있고, <code>agentic mermaid.dev</code> 데모 MCP를 대상으로 동작을 확인해볼 수 있습니다.</p>
<h3>남는 불만: 이름</h3>
<p>기술적으로는 반길 만한 변화지만, 스펙 버전명은 여전히 아쉽습니다. <code>2026-06-28</code>처럼 날짜를 그대로 버전명에 박아넣는 방식은, Anthropic이 Claude Sonnet 3.5의 여러 버전을 날짜로만 구분해서 혼란을 줬던 것과 똑같은 실수를 반복하는 것처럼 보입니다. MCP라는 브랜드 자체도 그동안 부정적인 인식이 워낙 쌓였기 때문에, 차라리 &quot;MCP 2&quot;처럼 완전히 새로운 이름을 붙였다면 이번 변화의 의미가 더 명확하게 전달됐을 거라는 아쉬움이 남습니다.</p>
<h3>정리</h3>
<ul>
<li>MCP의 가장 큰 문제는 클라이언트-서버 간 <strong>상태 유지(stateful) 연결</strong>을 실제 사용 여부와 상관없이 계속 붙잡아야 했다는 점이었습니다. 서브 에이전트가 늘어날수록 연결 수가 배로 늘어나 로컬 머신 리소스를 심하게 잡아먹었습니다(예: Codex에서 서브 에이전트 5개 → 상태 유지 연결 30개).</li>
<li>Anthropic의 다섯 번째 MCP 스펙(<code>2026-06-28</code>)은 프로토콜을 <strong>요청-응답(request-response) 기반 stateless core</strong>로 전환했습니다. 이제 MCP 서버는 서버리스/엣지 인프라에도 자유롭게 배포할 수 있고, 로드밸런서에서 sticky routing을 유지할 필요가 없어졌습니다.</li>
<li>기존(legacy) MCP는 세션 초기화 + 도구 호출로 최소 2번의 HTTP 요청과 세션 ID 기반 라우팅이 필요했지만, 새 stateless MCP는 단일 HTTP 요청으로 끝납니다.</li>
<li>MCP는 2024년 11월 등장 후 한동안 Skills(마크다운 기반 접근)에 인기를 내줬지만, 감사·통제가 쉽고 작은 모델도 다룰 수 있다는 장점 덕분에 stateless 전환을 계기로 다시 주목받고 있습니다.</li>
<li>실무적으로는 MCP 서버를 직접 만들거나 운영하고 있다면, 이번 stateless 스펙으로 전환해 인프라 복잡도와 리소스 낭비를 크게 줄일 수 있는지 검토해볼 만합니다.</li>
