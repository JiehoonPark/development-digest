LLM 코딩 품질을 높이는 나만의 agent.md 만들기

My agent.md to improve LLM-assisted code quality

📅 2026-08-23📰 Hacker News (Top)
ai

LLM을 활용한 코딩 보조 도구들이 빠르게 발전하고 있지만, 실제로 프로덕션 수준의 코드 품질을 뽑아내려면 단순히 도구를 쓰는 것만으로는 부족합니다. Fabien Sanglard가 자신의 LLM 코딩 경험을 시간 순으로 돌아보며, 반복되는 코드 스타일 피드백을 어떻게 agent.md 파일 하나로 해결했는지 정리한 글을 소개합니다.

2025년 중반: 컴파일도 안 되던 시절

저자가 LLM으로 코딩 속도를 높여보려 처음 시도한 건 2025년 중반이었습니다. 당시 작업하던 프로젝트는 Rust로 작성한 mDNS 구현체인 libadbmdns였는데, 결과는 실망스러웠습니다. LLM이 짜준 코드는 컴파일조차 되지 않았습니다.

2026년 1월: 성능은 좋아졌지만 코드 품질은 여전히 엉망

2026년 1월, 저자는 다시 한번 LLM을 시도했습니다. 이번엔 확실히 나아졌습니다. LLM은 복잡한 인덱스 기반 바이너리 힙(indexed-binary heap) 클래스를 작성해냈을 뿐 아니라, Windows IOCP 구현 때문에 발생한 polling 크레이트의 난해한 버그까지 정확히 짚어냈습니다.

문제는 코드 품질이었습니다. 결과물은 주석도 없고 구조도 없는 전형적인 스파게티 코드였습니다. 재미있는 결과이긴 했지만, 속도로 얻은 이득을 코드를 프로덕션 수준으로 정리하는 데 다 써버려야 한다면 실용적이라 할 수 없었습니다.

2026년 3월: 에이전틱 IDE와 반복 작업의 피로

2026년 3월, 저자는 Antigravity나 VS Code의 Claude Code 플러그인 같은 에이전틱 IDE를 시도했습니다. 이제는 "스테이징된" 코드를 놓고 "이터레이션"하는 것이 가능해졌습니다. 마치 인내심 넘치는 신입 컴퓨터공학 전공생의 코드를 리뷰하는 것 같았다고 합니다. "매직 넘버 쓰지 마라", "여기엔 짧은 설명 주석을 달아라", "함수 이름을 짧게 써라" 같은 피드백을 계속 주게 되었습니다.

코드 품질은 눈에 띄게 좋아졌고, 직접 손으로 짠 코드에 근접한 수준까지 올라왔습니다. 하지만 문제는 지루함이었습니다. 새로운 세션을 시작할 때마다 같은 지적을 계속 반복해야 했습니다.

agent.md: 반복을 없애는 방법

코딩 세션이 시작되면, 코딩 하네스는 agent.md라는 파일을 로드해서 프롬프트에 주입합니다. 이 파일이 바로 코딩 스타일 선호도를 세밀하게 튜닝하기에 최적의 위치입니다. 같은 제안을 계속 반복하고 있다는 걸 깨달을 때마다, 저자는 그 내용을 agent.md에 추가했습니다.

원문 저자는 자신의 agent.md 예시를 시작점으로 공유하고 있으며, 프로젝트 루트에 이 파일을 두는 것만으로 충분하다고 설명합니다. 만약 gemini.md나 claude.md처럼 도구별로 다른 파일명을 요구하는 환경이라면, 해당 파일들을 agent.md에 심볼릭 링크로 연결해두면 어디서든 동일하게 동작하도록 만들 수 있습니다.

다만 이 "트릭"이 생성되는 코드 품질을 크게 개선해준 건 맞지만, 코드를 읽지 않아도 되게 해주는 마법 같은 해결책은 아니라고 저자는 강조합니다. LLM은 여전히 끊임없이 할루시네이션을 일으키기 때문에 신뢰할 수 없고, 검증과 반복 작업은 여전히 많이 필요합니다. 다만 이제는 코드 스타일이 아니라 아키텍처와 설계에 집중할 수 있게 되었다는 점이 달라졌습니다.

컨텍스트 희석(Context Dilution) 문제

LLM을 다루다 보면 "컨텍스트 희석(context dilution)" 혹은 "어텐션 희석(attention dilution)"이라 불리는 성가신 현상을 만나게 됩니다. 이는 "Lost in the Middle" 논문에서 다뤄진 내용으로, 컨텍스트가 길어질수록 모델이 컨텍스트 중간에 위치한 지시사항에는 점점 덜 주의를 기울이고, 대신 맨 앞과 맨 뒤에 있는 내용에 더 집중하게 되는 현상을 말합니다. 이 현상이 왜 발생하는지에 대한 명확한 원인은 이 글이 작성되는 시점까지도 잘 밝혀지지 않았습니다.

agent.md 스스로 업데이트하기

agent.md에 새 규칙을 추가하고 싶을 때마다 에디터를 열 필요는 없습니다. 저자가 지금 쓰는 방법은 에이전트에게 직접 agent.md를 업데이트해달라고 요청하는 것입니다. 이렇게 하면 세션 중에 반복적으로 지적하던 스타일 피드백을 그 자리에서 바로 규칙으로 기록할 수 있어, 다음 세션부터는 같은 지적을 반복할 필요가 없어집니다.

정리

  • LLM 코딩 도구는 2025년 중반의 "컴파일도 안 되는" 수준에서 2026년 초에는 복잡한 알고리즘 작성과 난해한 버그 탐지까지 가능한 수준으로 빠르게 발전했지만, 코드 품질(주석, 구조, 네이밍)은 별개의 문제로 남아 있었습니다.
  • 에이전틱 IDE(Antigravity, Claude Code 플러그인 등)를 통해 코드를 반복적으로 검토·수정하는 워크플로우가 가능해졌지만, 매 세션 같은 스타일 피드백을 반복해야 하는 비효율이 있었습니다.
  • 프로젝트 루트에 agent.md를 두면 코딩 하네스가 세션 시작 시 이를 프롬프트에 자동으로 주입하므로, 반복되는 코드 스타일 규칙(매직 넘버 금지, 주석 작성, 짧은 함수명 등)을 한 번만 정리해두면 계속 재사용할 수 있습니다. claude.md/gemini.md는 심볼릭 링크로 연결하면 도구에 관계없이 동일하게 작동합니다.
  • 이 방법은 코드 스타일 문제는 해결해주지만 할루시네이션 문제까지 없애주지는 않으므로, 개발자는 여전히 코드를 검증해야 하며 대신 스타일이 아닌 아키텍처와 설계에 리뷰 역량을 집중할 수 있게 됩니다.
  • "Lost in the Middle" 논문에서 지적된 컨텍스트 희석 현상, 즉 컨텍스트가 길어질수록 중간에 있는 지시사항이 무시되기 쉬운 문제를 염두에 두고, 새로운 규칙이 생기면 에이전트에게 직접 agent.md를 갱신하도록 요청하는 습관을 들이는 것이 실무에 유용합니다.
💡
LLM 코딩 도구를 매일 쓰는 프론트엔드 개발자라면, agent.md 같은 설정 파일로 반복적인 코드 리뷰 피드백을 줄이고 검증 시간을 아키텍처 설계에 재투자할 수 있는 실무 팁을 얻을 수 있습니다.
