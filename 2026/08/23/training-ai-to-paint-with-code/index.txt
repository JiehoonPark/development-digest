13:T2fb6,<p>AI로 이미지를 만들 때 우리가 개입할 수 있는 유일한 지점은 프롬프트뿐입니다. 결과물을 직접 수정할 수는 없고, 뭔가 바꾸려면 다시 모델로 돌아가 프롬프트를 고쳐야 하죠. 이 답답함에서 시작된 프로젝트가 있습니다. 필자와 친구 Cameron은 강화학습(RL)을 이용해 &quot;코드를 작성해서 그림을 그리는&quot; 언어 모델을 학습시켰습니다. 결과물이 코드이기 때문에 얼마든지 편집이 가능하고, 프롬프트로 되돌아가지 않고도 훨씬 세밀하게 결과물을 조정할 수 있습니다.</p>
<p>이 프로젝트가 던지는 더 근본적인 질문은 &quot;창작·디자인 과제에 어떻게 RL을 적용할 것인가&quot;입니다. RL은 보상이 검증 가능할 때 잘 작동합니다. 수학 문제는 맞거나 틀리고, 게임은 이기거나 집니다. 하지만 미적 완성도는 이도 저도 아닙니다. 결국 문제의 핵심은 보상 함수를 어떻게 설계하고, 심판(judge) 모델에게 어떤 기준을 적용시킬 것인가로 옮겨갑니다. 기준이 너무 엄격하면 모델이 한 가지 정답으로 수렴해버리고, 너무 느슨하면 방향성 없이 표류합니다.</p>
<h3>4단계 학습 루프</h3>
<p>이 시스템은 학습 중 수천 번 반복되는 4단계 루프로 구성됩니다.</p>
<p>모델은 &quot;복숭아빛 히비스커스를 수채화로 그려줘&quot; 같은 프롬프트를 받아 완전한 p5.brush 자바스크립트 스케치를 작성합니다. 이 스케치는 샌드박스 처리된 Puppeteer 환경에서 렌더링되어 PNG로 만들어집니다. 이 PNG는 사람이 직접 평가해둔 풀(pool)에서 무작위로 뽑은 두 개의 레퍼런스 그림과 비교되고, 별도의 심판 모델이 어느 쪽이 더 나은 수채화인지 판정합니다. 이 판정이 보상 신호로 변환되고, GRPO가 모델을 업데이트한 뒤 루프가 다시 반복됩니다.</p>
<p>이 과정에서 정말 중요한 결정들은 &quot;무엇을 평가할 것인가&quot;, &quot;어떻게 판정할 것인가&quot;, &quot;레퍼런스 풀에는 무엇을 담을 것인가&quot;, &quot;시스템 프롬프트를 어떻게 쓸 것인가&quot;에 있었습니다. 아래에서 각각을 살펴보겠습니다.</p>
<h3>첫 번째 루브릭의 실패</h3>
<p>처음 만든 루브릭에는 9개의 개별 신호가 있었습니다. 컴파일 여부를 확인하는 게이트, 코드가 네이티브 p5가 아니라 실제로 p5.brush를 사용했는지 확인하는 체크, 약 3,000 토큰을 목표로 하는 코드 길이 램프, 사람의 선호도를 학습한 모델인 HPSv3, GPT-5.4와 Gemini로 구성된 위원회가 판정하는 프롬프트 충실도, 그리고 인지 가능성·미학·기술력·깊이감을 평가하는 4개의 품질 심판까지, 총 9가지였습니다.</p>
<p>하지만 모델은 보상 0.65 부근에서 정체됐고 거기서 벗어나지 못했습니다. 모든 롤아웃이 똑같이 생긴, 다섯 장의 둥근 꽃잎을 가진 납작한 클립아트풍 꽃만 그려냈습니다. 보상 값은 계속 올라가는데 실제 실력은 전혀 나아지지 않는 이상한 상황이었죠.</p>
<p>문제의 원인은 각 서브 보상을 개별적으로 뜯어보고서야 드러났습니다. 4개의 품질 심판과 프롬프트 충실도 신호는 서로 0.85~0.95의 상관관계를 보였습니다. 사실상 같은 것을 다섯 번 측정하고 있었던 셈입니다. 전체 보상의 약 3분의 1을 차지하던 코드 길이 신호는 30스텝 만에 포화 상태에 도달해 그 이후로는 아무런 그래디언트도 만들어내지 못했습니다. 실제로 유의미한 분산을 보인 유일한 신호였던 HPSv3는 가중치가 겨우 0.10에 불과했습니다. 결국 루브릭 전체가 모델에게 같은 말을 여러 번 반복해서 들려주고 있었던 겁니다.</p>
<h3>절대 점수에서 상대 비교로</h3>
<p>첫 번째 해결책은 절대 점수 방식을 쌍대비교(pairwise) 판정으로 바꾸는 것이었습니다. 원래 루브릭은 심판에게 각 롤아웃을 0점에서 10점 사이로 채점하라고 요구했는데, 점수들이 0점 근처로 압축되어 돌아왔습니다. 반면 쌍대비교는 전혀 다른 질문을 던집니다. 심판에게 롤아웃 결과물 하나와 풀에서 뽑은 레퍼런스 두 개를 함께 보여주고 &quot;이 중 어느 것이 더 나은 히비스커스 수채화인가?&quot;라는 단 하나의 질문만 던지는 것이죠. 보상은 이 비교에서 이긴 비율로 계산됩니다. 이렇게 하니 점수의 다이나믹 레인지가 훨씬 넓어졌습니다. 심판 모델은 추상적인 척도로 점수를 매기는 것보다 상대적인 질문을 더 안정적으로 처리했습니다.</p>
<h3>사람이 직접 평가한 레퍼런스 풀 구축</h3>
<p>두 번째로 필요했던 것은 사람이 직접 평가한 레퍼런스 풀이었습니다. 1,664장의 이미지를 하나씩 보면서 love, okay, nope 세 등급으로 분류했고, 이 중 love 등급 117장이 비교용 풀의 씨앗이 되었습니다. 이 시점부터는 모든 롤아웃이 필자가 직접 &quot;좋다&quot;고 판단한 것들과 비교되며 평가받게 됩니다. 여기서 더 나아가지는 못했지만, 다음 단계로는 이 평가 데이터 자체로 작은 리워드 모델을 학습시키는 방법(제대로 된 RLHF)이 있었을 겁니다. 그러면 매번 풀과 직접 비교하지 않고도 모델의 &quot;좋음&quot;에 대한 감각을 적용할 수 있었을 테니까요.</p>
<h3>새 루브릭과 그 결과</h3>
<p>새 루브릭은 9개였던 신호를 4개로 압축했습니다: 컴파일 및 brush 사용 여부를 확인하는 이진 게이트(0.05), 이진 길이 체크(0.05), HPSv3(0.30), 그리고 레퍼런스 풀 대상 쌍대비교 판정(0.60)입니다.</p>
<p>같은 베이스 모델, 같은 학습 데이터로 다시 돌렸더니 결과는 확연히 달랐습니다. 이전 실행에서 도달했던 정체 지점에 3배 빠르게 도달했고, 그 지점을 넘어서 계속 올라갔으며, 코드 길이는 13,500 토큰에서 2,000 토큰 미만으로 압축됐습니다. 모델은 좋은 구도를 만드는 데 굳이 장황한 코드가 필요하지 않다는 것을 스스로 학습한 겁니다.</p>
<p>레퍼런스 풀은 최종적으로 581장의 그림으로 구성됐습니다. 1,664장의 생성물을 손으로 평가해 117장을 love 등급, 266장을 okay 등급으로 분류했고, 나머지 198장은 손으로 평가한 예시가 부족한 색상 영역의 비교 세트를 넓히기 위해 별도의 생성 실행에서 보충한 것입니다.</p>
<p>풀 안의 이미지는 전부 모델이 생성한 것입니다. p5.brush 자체가 예술가들이 쓰는 니치한 도구라 사람이 직접 그린 예시를 충분히 구하기 어려웠기 때문입니다. 생성 작업은 두 가지 파이프라인으로 진행됐습니다. 하나는 AutoResearch로, Opus 4.6과 GPT-5.4, Gemini 3.1 Pro가 VLM 심판이 매기는 점수와 피드백을 받으며 참조 사진에 맞춰 반복 개선하는 방식입니다. 다른 하나는 Gemini 3.1 Pro로 돌린 대량 배치 생성입니다. 두 파이프라인 모두 GEPA를 통해 진화시킨 시스템 프롬프트를 사용했는데, 이는 다음 섹션에서 다룰 내용입니다.</p>
<h3>시스템 프롬프트: 문서화보다 제약이 낫다</h3>
<p>시스템 프롬프트 역시 별도의 작업이 필요했습니다. 초기 버전에는 400줄짜리 p5.brush API 레퍼런스가 포함되어 있었는데, 모델은 그럴듯하고 형식이 잘 갖춰진 코드를 자신 있게 뽑아냈지만 정작 존재하지 않는 API를 지어내는 경우가 많았습니다.</p>
<p>이 문제는 GEPA라는 프롬프트 최적화 라이브러리로 해결했습니다. GEPA는 점수 함수를 기준으로 프롬프트를 진화시키는 도구인데, 취향 기준을 앵커로 삼은 7-shot 심판을 대상으로 200회 반복 최적화를 돌렸습니다. 그 결과 수렴한 프롬프트는 여덟 개의 브러시 메서드로만 이루어진 엄격한 허용 목록(allowlist)이었고, API 문서도 예시 코드도 전혀 없었습니다. 400줄짜리 레퍼런스를 완전히 걷어낸 이 버전에서, 처음으로 세 번 생성 중 세 번 모두 알아볼 수 있는 히비스커스 형태가 나왔습니다.</p>
<p>이 결과는 일반화할 수 있는 교훈으로 이어집니다. 시스템 프롬프트에 긴 레퍼런스 문서를 넣으면 모델이 API를 환각(hallucination)하게 되는 반면, 짧고 명확한 허용 목록이 원래의 스펙 문서보다 결과물을 더 잘 제약한다는 것입니다.</p>
<h3>창작 과제를 위한 RL이라는 설계 문제</h3>
<p>강화학습에는 검증 가능한 보상이 필요합니다. 수학 문제는 맞거나 틀리고, 게임은 이기거나 집니다. 하지만 미적 선호는 어느 쪽도 아닙니다. 주관적인 작업에 RL을 적용하려면 결국 보상을 손수 설계해야 하고, 그 보상이 일반화될 수 있도록 신중하게 만들어야 합니다. 너무 구체적으로 만들면 모델은 그저 평가해둔 예시를 베끼는 법만 배우고, 너무 느슨하게 만들면 특별히 배우는 것 없이 끝나버립니다. 창작 과제를 위한 RL은 결국 &quot;취향이 사용자의 선호로 일반화될 수 있는 구조를 만드는&quot; 설계 문제입니다.</p>
<p>필자는 이것이 이미지를 만드는 더 나은 방법이라고 생각하지 않습니다. 사실 훨씬 느립니다. 하지만 이 프로젝트를 시작한 이유는 AI로 이미지를 만들 때 참여할 수 있는 유일한 방법이 프롬프트뿐이라는 사실에 답답함을 느꼈기 때문입니다. 이 프로젝트를 통해 프롬프트와 모델, 그리고 결과물(artefact) 전반에 걸쳐 관심과 노력을 쏟을 수 있게 되었습니다. 프로젝트는 계속 진행 중이며, 지금까지 발견한 문제들을 보완하기 위한 마지막 학습 실행이 하나 더 남아 있습니다. 전체 기술 보고서는 6월 26일에 공개될 예정입니다.</p>
<h3>정리</h3>
<ul>
<li>AI 이미지 생성의 한계는 &quot;프롬프트로만 개입 가능하다&quot;는 점에서 출발합니다. 이 프로젝트는 모델이 p5.brush 자바스크립트 코드를 직접 작성하게 함으로써, 결과물을 코드 레벨에서 편집 가능한 형태로 바꿨습니다.</li>
<li>미적 품질처럼 검증 불가능한 목표에 RL을 적용하려면 보상 함수 설계 자체가 핵심 난제가 됩니다. 서로 상관관계가 높은 신호를 여러 개 섞으면(0.85~0.95 상관), 실제로는 같은 것을 반복 측정하며 학습 정체(0.65 보상에서 플래토)를 유발합니다.</li>
<li>절대 점수(0~10점) 대신 레퍼런스 풀과의 쌍대비교로 보상을 설계하면 심판 모델의 판정 신뢰도와 다이나믹 레인지가 크게 개선됩니다. 이 변화만으로 학습 속도가 3배 빨라지고 코드 길이가 13,500 토큰에서 2,000 토큰 미만으로 줄었습니다.</li>
<li>사람이 직접 평가한 레퍼런스 풀(1,664장 중 love 117장, okay 266장 + 보충 198장)을 비교 기준으로 사용하는 것이 좋은 결과물의 &quot;정의&quot;를 학습 과정에 주입하는 실질적 방법이었습니다.</li>
<li>시스템 프롬프트에서는 상세한 API 문서보다 8개짜리 엄격한 허용 목록이 API 환각을 줄이고 실제 결과물의 정확도를 높였습니다. 이는 GEPA로 200회 반복 최적화를 거쳐 도출한 결론입니다.</li>
</ul>
