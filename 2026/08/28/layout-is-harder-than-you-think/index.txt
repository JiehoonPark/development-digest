13:T2ebe,<h2>레이아웃 시스템, 생각보다 훨씬 어렵다</h2>
<p>게임 엔진 오딘(Odin)으로 프로젝트를 진행하면서 직접 레이아웃 시스템을 만들었습니다. 결과물은 깔끔하게 정렬된 박스들, 그럴듯한 카드 UI, 심지어 애니메이션이 붙은 카드 덱까지 만들어낼 정도로 꽤 만족스러운데요. 이번 글에서는 이 레이아웃 시스템을 어떻게 설계했는지, 그리고 그 과정에서 마주친 즉시 모드(immediate mode) UI 특유의 문제들을 어떻게 풀었는지 정리해보겠습니다.</p>
<h3>리테인드 모드 vs 즉시 모드</h3>
<p>레이아웃 시스템이라고 하면 대부분 DOM을 떠올릴 겁니다. DOM에서는 화면에 보이는 모든 엘리먼트가 실제로 존재하는 노드입니다. <code>div</code>를 만들어서 <code>body</code>에 붙이면 그게 그대로 화면에 남아있고, 여기에 <code>onClick</code> 같은 이벤트 리스너를 걸어서 호버, 포커스, 블러 같은 상태 변화에 반응할 수 있습니다. 이런 방식을 <strong>리테인드 모드(retained mode)</strong>라고 부릅니다. UI 트리 전체가 메모리에 계속 유지되고, 변화가 필요할 때마다 그 일부를 수정해서 화면을 갱신하는 구조입니다.</p>
<p>이번에 만든 것은 이와 반대되는 <strong>즉시 모드(immediate mode)</strong> UI입니다. 예전에 만들었던 게임 Mordoria는 리테인드 모드 UI로 만들었는데, 그때는 상태를 관리하기 위해 이벤트 버스 같은 걸 잔뜩 도입해야 했고 그게 상당히 골치 아팠습니다. 이번에는 이런 복잡함 없이 갈 수 있을 것 같습니다.</p>
<p>즉시 모드의 핵심 아이디어는 매 프레임마다 게임 UI 전체를 새로 그려낸다는 겁니다. 어차피 한 시점에 존재하는 UI 요소는 그렇게 많지 않습니다. 하이라이트된 타워 하나, 체력바가 표시되는 적 하나, 증가하는 골드 수치, 타워 스탯 창, 혹은 맵 위에 동시에 놓인 카드 여러 장 정도인데 많아야 50~100개 수준입니다. 이 정도라면 매 프레임 다시 만들어내는 데 드는 비용은 사실상 무시할 만합니다. 진짜 어려운 부분은 이 요소들의 위치와 크기를 계산하는 수학적인 로직 쪽입니다.</p>
<h3>Clay 알고리즘에서 배운 것</h3>
<p>레이아웃 시스템을 만들기 전에 &quot;How Clay's layout algorithm works&quot;라는 영상을 보고 상당 부분을 참고했습니다. 관심 있다면 원본 영상을 직접 보는 걸 추천하지만, 간단히 요약하면 이렇습니다.</p>
<p>필요한 기능은 사실 몇 개 안 됩니다.</p>
<ul>
<li>박스를 만들고 그 안의 요소들을 가로로 정렬하기</li>
<li>같은 방식으로 세로로 정렬하기</li>
<li>박스 안에서 div를 정중앙에 배치하기(센터링, 다들 알다시피 세상에서 제일 어려운 문제죠)</li>
</ul>
<p>이걸 구현하기 위해 세운 규칙은, 리프 노드(leaf node)는 크기를 결정하는 방식이 딱 세 가지뿐이라는 겁니다.</p>
<ul>
<li><strong>고정 크기</strong>: &quot;이건 50x50 크기의 정사각형이다&quot;</li>
<li><strong>텍스트</strong>: 화면에 그냥 텍스트가 있고, 그 텍스트의 크기가 곧 요소의 크기</li>
<li><strong>스프라이트</strong>: 정해진 크기를 가진 스프라이트가 있고, 그게 요소의 크기</li>
</ul>
<p>이 세 가지 기본 단위만 있으면 나머지 시스템 전체를 쌓아 올릴 수 있습니다.</p>
<h3>크기 계산: Post-order 순회</h3>
<p>레이아웃 시스템의 동작 방식을 간단히 그려보면 이렇습니다. 박스 하나를 만들고 그 안에 세 개의 아이템을 넣는다고 합시다. 이 시점에서는 이 아이템들이 어디에 위치할지 전혀 모릅니다. 다만 각자 고정된 크기를 가지고 있다는 것만 알 뿐입니다. 최종적으로 원하는 건 이 세 박스가 가운데 정렬되어, 어떤 건 가장자리에 가깝게, 어떤 건 좀 덜 가깝게, 어떤 건 가장 멀게 배치되는 겁니다.</p>
<p>이걸 구현하려면 UI 트리를 <strong>post-order 순회</strong>로 내려가야 합니다. 즉 가장 아래 리프 노드까지 내려가서 자식들의 크기부터 계산합니다. 자식들은 이미 정해진 크기를 갖고 있으니 계산이 쉽습니다. 문제는 자동 레이아웃되는 박스들인데, 이 박스의 크기는 결국 자식들의 크기에 달려 있습니다. 자식 크기를 이미 알고 있으니, 필요한 건 각 방향의 패딩 크기와 자식들 사이의 간격(gap)뿐입니다. 이 둘을 더하면 너비가 나옵니다. 생각보다 어렵지 않습니다.</p>
<p>높이도 비슷합니다. 패딩에 가장 큰 자식 요소의 높이를 더하면 됩니다(가로 정렬 기준). 세로 정렬의 경우는 반대로, 가장 큰 자식의 너비가 박스의 너비가 되고, 자식들의 높이 합에 gap과 패딩을 더한 값이 박스의 높이가 됩니다. 이게 이 알고리즘에서 크기 계산 부분의 핵심입니다. 다른 세부 사항들도 있지만, 사이즈를 구하는 부분 자체는 생각보다 만만했습니다.</p>
<h3>위치 계산: 사이즈를 알면 자연스럽게 풀린다</h3>
<p>크기를 다 구하고 나면 위치를 계산할 수 있습니다. 당연한 얘기죠. 박스 안에 세 개의 요소가 있고 각각의 크기를 안다면, 첫 번째 요소를 배치한 다음 &quot;패딩 + 첫 번째 자식의 너비 + gap&quot;만큼 떨어진 지점이 두 번째 요소의 시작점이 되고, 다시 그 지점에 &quot;너비 + gap&quot;을 더하면 세 번째 요소의 시작점이 나옵니다. 이런 식으로 위치를 쉽게 배치할 수 있습니다.</p>
<p>정렬(alignment)을 적용할 때는 오프축(off-axis, 정렬 방향과 반대되는 축)을 계산해야 하는데, 이것도 어렵지 않습니다. 부모의 높이에서 자식의 높이를 뺀 다음 2로 나누면 센터링에 필요한 오프셋이 나옵니다. 이 로직이 실제 코드로는 조금 더 길어지긴 하지만(정렬 옵션까지 처리해야 하니까요), 직접 이 코드를 짜고 나니 &quot;내가 여기서 뭘 하고 있는지 정확히 안다&quot;는 느낌이 들어서 만족스러웠습니다.</p>
<p>이번이 즉시 모드 UI를 직접 만들어본 첫 경험이었는데, 왜 이 방식에 장점이 있다고들 하는지 이해가 됐습니다.</p>
<h3>마우스 처리: 닭이 먼저냐 달걀이 먼저냐</h3>
<p>즉시 모드 UI의 큰 트레이드오프 중 하나는 마우스 처리 방식입니다. 간단한 예를 들어보겠습니다.</p>
<p>레이아웃을 계산하려면 먼저 모든 아이템의 크기를 계산하고, 그다음 각 아이템의 위치를 계산해야 합니다. 그런데 마우스가 특정 위치에 있을 때 어떤 박스가 확대되어야 한다고 합시다. 아직 크기와 위치를 계산하지 않은 상태에서 마우스가 그 박스 안에 있는지 어떻게 알 수 있을까요?</p>
<p>여기서 닭과 달걀 문제가 생깁니다. 마우스가 화면의 어떤 위치에 있다는 건 압니다. 그런데 이 요소가 확대되어야 하는지는 요소의 위치를 알아야 판단할 수 있고, 요소의 위치는 전체를 렌더링해봐야 알 수 있습니다. 근데 전체를 렌더링하고 나면 이미 그 시점엔 마우스 위치를 반영할 기회가 지나간 것처럼 보입니다. 그럼 레이아웃을 두 번 계산해야 하는 걸까요? 아닙니다. 그렇게 순진하게 생각하면 완전히 틀린 겁니다.</p>
<p>해결 방법은 이렇습니다. 레이아웃의 루트(root)를 저장해둡니다. 매 프레임 시작 시점에 먼저 마우스 정보(XY 좌표, 버튼이 눌렸는지 여부)를 가져옵니다. 그리고 <strong>이전 프레임의 루트</strong>를 기준으로 마우스 위치를 계산합니다. 만약 이전 루트가 없다면 그냥 넘어갑니다. 그 다음 트리를 내려가면서(descend), 리프 노드까지 도달해서 &quot;마우스가 내 렌더링된 사각형 안에 있는가?&quot;를 체크합니다. 이 시점에 held, entered, exited, hovered, dragging 같은 모든 상태 계산을 한 곳에서 처리할 수 있습니다.</p>
<p>이 마우스 라이브러리 전체는 디버깅용 구문, 리셋 로직, 마우스-사각형 충돌 판정 코드를 다 포함해도 200줄이 채 안 됩니다. 이해하기도 쉽습니다.</p>
<p>정리하면, 첫 프레임에서는 아무 정보도 없으니 마우스 관련 처리를 할 수 없습니다. 하지만 그다음 프레임부터는 이전 프레임에서 계산된 위치 정보가 있으므로, 그것을 기준으로 마우스를 테스트하고, 렌더링이 끝난 뒤 &quot;마우스가 나한테 있었나? 있었으면 확장을 시작해야지&quot;라고 판단합니다. 이렇게 하면 렌더링 과정 안에서 모든 요소가 마우스의 위치와 자신의 상태를 자연스럽게 알게 되는 효과를 얻을 수 있습니다.</p>
<p>이게 즉시 모드의 큰 장점입니다. 리테인드 모드에서는 마우스가 들어왔을 때 실행되는 핸들러 함수들을 계속 유지해야 하고, &quot;지금 호버 중이다&quot;라는 상태를 어딘가에 저장해뒀다가 다른 함수가 실행되어 &quot;이제 호버 아니다&quot;라고 알려줄 때까지 기다려야 하는, 상당히 헷갈리는 상태 관리가 필요합니다. 반면 즉시 모드에서는 UI를 구성하는 바로 그 순간에 &quot;지금 호버되고 있나? 그렇다면 2배 크기로 그려야지&quot;라고 바로 판단해버리면 끝입니다. 애니메이션을 섞는 것도 마찬가지로 어렵지 않은데, &quot;현재 순간의 내 상태가 뭔지&quot;만 정하고 그 상태를 기반으로 UI를 만든다는 아이디어만 잡으면 나머지는 술술 풀립니다.</p>
<p>즉시 모드 UI가 이렇게까지 마음에 들 줄은 몰랐습니다. 다만 여기까지 만들고 나서도 완전히 만족스럽지는 않았기에, UI 컴포넌트를 좀 더 쉽게 만들 수 있도록 작은 헬퍼 도구를 추가로 만들게 됩니다.</p>
<h3>정리</h3>
<ul>
<li><strong>즉시 모드 vs 리테인드 모드</strong>: DOM 같은 리테인드 모드는 UI 트리를 메모리에 계속 유지하며 부분 수정으로 갱신하는 방식이고, 즉시 모드는 매 프레임 UI 전체를 새로 그리는 방식입니다. 게임 UI처럼 화면에 존재하는 요소 수가 50~100개 수준으로 제한적이라면 즉시 모드의 재생성 비용은 무시할 만합니다.</li>
<li><strong>레이아웃 계산의 핵심은 크기 → 위치 순서</strong>: 리프 노드는 고정 크기, 텍스트, 스프라이트 세 가지 방식으로만 크기가 결정됩니다. Post-order 순회로 자식부터 크기를 구하고, 패딩과 gap을 더해 부모 크기를 역산한 뒤, 이 크기를 기반으로 각 요소의 위치를 순차적으로 배치합니다.</li>
<li><strong>마우스 처리는 이전 프레임 정보를 활용해 해결</strong>: 현재 프레임에서 위치를 모르는 상태로 마우스 판정을 할 수 없다는 딜레마는, 직전 프레임에 저장해둔 레이아웃 루트를 기준으로 히트 테스트를 하는 방식으로 풀립니다. 이 방식은 200줄 미만의 코드로 hover, held, entered, exited, dragging 상태를 모두 처리할 수 있습니다.</li>
<li><strong>상태 관리가 극적으로 단순해짐</strong>: 리테인드 모드처럼 이벤트 핸들러와 상태 플래그를 여기저기 흩어놓을 필요 없이, &quot;지금 이 순간의 상태가 무엇인가&quot;만 판단해서 그 자리에서 바로 UI를 그리면 되므로 애니메이션과 상호작용 로직이 훨씬 직관적입니다.</li>
