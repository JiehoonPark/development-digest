CSS 애니메이션이 JavaScript보다 빠른 진짜 이유

CSS vs. JavaScript

📅 2026-10-14📰 Josh W. Comeau
frontend

애니메이션 성능 이야기가 나오면 항상 등장하는 질문이 있습니다. "JavaScript로 만든 애니메이션이 CSS보다 느린가?" "항상 CSS transition을 써야 하는가, 아니면 JavaScript 애니메이션 라이브러리를 써도 괜찮은가?" 하는 질문인데요. 이 질문에는 생각보다 많은 뉘앙스가 숨어 있고, 흔히 알려진 통념도 정확하지는 않습니다. 이 글에서는 CSS와 JavaScript 애니메이션의 실제 차이를 코드와 함께 직접 파헤쳐 보겠습니다.

CSS 키프레임 vs JavaScript 루프

공을 좌우로 튕기는 간단한 애니메이션을 만든다고 해봅시다. CSS 키프레임으로는 이렇게 작성할 수 있습니다.

@keyframes bounce {
  to {
    transform: translateX(calc(var(--bounce-magnitude) * -1));
  }
}

.ball {
  --bounce-magnitude: 200px;
  animation: bounce 1000ms infinite alternate;
}

여기서는 transform 속성을 사용했는데, 이 방식이 가장 부드러운 움직임을 만들어내기 때문입니다. 참고로 컨테이너 크기가 동적으로 바뀌는 경우라면 --bounce-magnitude 값을 JS에서 계산해 적용해야 할 수도 있습니다.

같은 애니메이션을 JavaScript로도 구현할 수 있습니다. GSAP나 Motion 같은 라이브러리를 쓰기 전에, 순수 JavaScript 버전부터 살펴보겠습니다.

const startTime = performance.now();
const ball = document.querySelector('.ball');

function animate() {
  const elapsedTime = performance.now() - startTime;
  // ✂️ 경과 시간을 기반으로 x 값을 계산
  ball.style.transform = `translateX(${x}px)`;
  window.requestAnimationFrame(animate);
}

이 코드는 requestAnimationFrame을 이용해 animate 함수를 매 프레임(대부분의 디스플레이 기준 초당 60회)마다 실행합니다. x 값을 계산하는 핵심 로직은 다소 복잡하고 주제와 크게 관련이 없어 생략했습니다.

자, 두 방식 중 어느 쪽이 더 부드럽게 동작할까요? 아마 대부분 CSS 버전이 더 성능이 좋을 거라고 직관적으로 느낄 겁니다. 이 직감은 맞지만, 그 이유는 우리가 흔히 생각하는 것과는 다릅니다.

흔히 JS 버전이 느린 이유를 "매 프레임마다 x 값을 계산하는 추가 작업이 들어가서" 또는 "JavaScript와 DOM 사이를 오가는 데 비용이 든다"고 생각하기 쉽습니다. 하지만 현대 브라우저 엔진은 이 정도 작업은 식은 죽 먹기로 처리합니다. 저사양 기기에서도 이런 연산은 1밀리초도 채 안 되는 시간에 끝나며, 프레임레이트에 영향을 줄 정도의 비용이 아닙니다.

진짜 차이는 따로 있습니다. JavaScript 애니메이션은 애플리케이션의 다른 모든 작업과 함께 메인 스레드에서 실행됩니다. 반면 CSS transition과 키프레임 애니메이션은 별도의 스레드에서 실행되기 때문에, JavaScript에서 무슨 일이 벌어지든 영향을 받지 않습니다.

이를 직접 확인할 수 있는 시뮬레이션을 생각해보면, 재생 버튼을 누르고 몇 초마다 메인 스레드를 의도적으로 블로킹시키는 상황을 가정해볼 수 있습니다. 이때 CSS 키프레임으로 만든 애니메이션은 아무 영향 없이 매끄럽게 유지되지만, JavaScript 루프 기반 애니메이션은 메인 스레드가 막히는 순간 뚝뚝 끊기는 모습을 보입니다.

현대 웹 애플리케이션에서는 메인 스레드가 정말 많은 일을 처리합니다. React 같은 프레임워크는 애플리케이션 상태와 DOM을 동기화하기 위해 끊임없이 업데이트를 수행하고, fetch 요청을 보낼 때마다(추가 데이터를 불러오거나 기존 데이터를 갱신할 때) 응답 데이터를 파싱하는 작업도 메인 스레드에서 일어납니다.

그러니 UI가 업데이트되기 직전에 로딩 스피너가 잠깐 멈칫하는 걸 본 적이 있다면, 바로 이게 원인입니다. JavaScript 기반 애니메이션은 애플리케이션의 나머지 작업들과 처리 능력을 놓고 경쟁해야 하는 셈입니다.

애니메이션 라이브러리 비교하기

앞선 예제에서는 requestAnimationFrame 루프로 매 프레임마다 UI를 직접 갱신하는, 상당히 로우레벨한 방식을 사용했습니다. 실제 현업에서는 더 높은 수준의 추상화를 제공하는 JavaScript 라이브러리를 사용하는 경우가 많습니다.

대표적인 두 라이브러리, Motion(구 Framer Motion)과 GSAP을 비교해보겠습니다. 둘 다 JavaScript 기반이니 메인 스레드에서 실행되는 한계를 똑같이 공유할 거라 예상할 수 있는데요, 메인 스레드가 바쁜 상황에서도 Motion은 신기하게도 애니메이션을 매끄럽게 유지합니다.

비밀은 Motion이 내부적으로 Web Animations API(WAAPI)를 사용한다는 데 있습니다. WAAPI는 CSS 키프레임 애니메이션과 동일한 저수준 애니메이션 엔진에 연결되는 JavaScript 인터페이스입니다. 그래서 Motion은 자신의 애니메이션을 별도의 스레드에서 실행할 수 있고, 대부분의 다른 JavaScript 애니메이션 라이브러리가 가진 근본적인 약점을 피해 갑니다.

공정하게 말하면, GSAP은 매우 강력한 라이브러리이고 WAAPI와는 호환되지 않을 법한 고급 기능들을 다수 포함하고 있습니다. 즉 GSAP이 잘못된 선택을 한 게 아니라, Motion과는 다른 트레이드오프를 택한 것뿐입니다.

상황에 맞는 도구 선택하기

필자는 가능하면 항상 네이티브 CSS 애니메이션/transition을 먼저 사용하려고 합니다. CSS만으로 해결할 수 없는 상황에 부딪히면, 일반적인 JS 라이브러리가 가진 단점 없이 문제를 해결해주는 Motion 같은 라이브러리를 활용합니다.

사실 요즘 CSS는 워낙 강력해져서, 애니메이션 라이브러리까지 끌어와야 할 상황 자체가 많지 않습니다. View Transitions, linear() 이징 함수, Animation Timeline 같은 새로운 API 덕분에 JavaScript 없이도 다양한 효과를 구현할 수 있게 되었습니다.

정리

  • CSS 키프레임/transition 애니메이션과 순수 JavaScript(requestAnimationFrame) 애니메이션의 성능 차이는 계산 비용이나 JS-DOM 간 오버헤드 때문이 아니라, 실행되는 스레드가 다르기 때문입니다. CSS 애니메이션은 별도 스레드에서, JS 애니메이션은 메인 스레드에서 돌아갑니다.
  • React의 DOM 업데이트, fetch 응답 파싱 등으로 메인 스레드가 바빠지면 JavaScript 기반 애니메이션은 끊기지만, CSS 기반 애니메이션은 영향을 받지 않습니다.
  • 같은 JavaScript 라이브러리라도 결과가 다를 수 있습니다. Motion은 내부적으로 Web Animations API를 사용해 CSS와 동일한 저수준 엔진·별도 스레드에서 동작하므로 메인 스레드 블로킹에도 끊기지 않습니다. 반면 GSAP은 더 강력한 기능을 제공하는 대신 이런 이점을 포기하는 트레이드오프를 선택했습니다.
  • 실무 원칙은 단순합니다. 가능하면 네이티브 CSS 애니메이션/transition을 우선 사용하고, CSS로 해결이 안 되는 경우에만 WAAPI 기반의 Motion 같은 라이브러리를 고려하세요. View Transitions, linear(), Animation Timeline 등 최신 CSS API 덕분에 JavaScript 라이브러리가 꼭 필요한 경우는 점점 줄어들고 있습니다.
💡
애니메이션 라이브러리를 고를 때 '전부 JavaScript니까 성능이 비슷하겠지'라는 잘못된 전제를 깨고, 내부 구현 방식(WAAPI 사용 여부)에 따라 실제 체감 성능이 크게 달라질 수 있음을 이해하는 것이 중요합니다.
