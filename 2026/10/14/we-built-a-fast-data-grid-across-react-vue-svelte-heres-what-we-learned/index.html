We built a fast data grid across React, Vue & Svelte – here's what we learned

📅 2026-10-14📰 Echo JS
frontendtypescript

SVAR 팀은 데이터 그리드, Gantt 차트, 캘린더 같은 기능이 묵직한 UI 컴포넌트를 만듭니다. 이런 컴포넌트들의 공통점은 하나, 대용량 데이터가 쏟아져도 빠르고 반응성 있게 동작해야 한다는 겁니다. 게다가 SVAR는 같은 컴포넌트를 React, Svelte, Vue 세 프레임워크로 동시에 출시하기 때문에, 하나의 컴포넌트를 세 번씩 고성능으로 구현해야 했습니다. 흔한 프레임워크 비교 글이 한 프레임워크는 깊이 알고 나머지 둘은 문서만 훑어본 사람이 쓰는 것과 달리, 이번 글은 세 프레임워크 모두에서 실제로 성능을 쥐어짜 본 경험을 바탕으로 합니다.

결론부터 말하면 꽤 의외였습니다. 빠른 데이터 그리드를 만들 때 비용이 큰 부분은 거의 대부분 프레임워크와 무관했고, 프레임워크마다 진짜로 다른 지점은 흔히들 벌이는 "프레임워크 전쟁"이 암시하는 것보다 훨씬 좁았습니다. 그래서 이 글은 의도적으로 승자를 가리지 않습니다.

프레임워크와 무관한 성능 문제

데이터 그리드는 이런 비교에 딱 맞는 테스트 케이스입니다. 누구나 한 번쯤 만들어 보거나 써 본 컴포넌트이고, 구조는 단순하지만 데이터량만큼은 어떤 UI 컴포넌트보다 무겁습니다. 1,000행은 평범한 화요일 수준이고 10,000행도 드물지 않으니, 처음부터 이 규모를 염두에 두고 설계해야 합니다.

실제로 SVAR React DataGrid는 20만 행, 2만 열이라는 말도 안 되는 규모를 부드럽게 렌더링하는 데모를 제공합니다.

하지만 10,000행을 그대로 DOM에 렌더링하면 React든 Vue든 Svelte든 똑같이 죽습니다(최신 하드웨어가 워낙 빠르니 '죽는다'기보다는 심하게 느려지는 쪽에 가깝겠지만요). 세 프레임워크 모두 결국 브라우저에게 수십만 개의 DOM 노드를 생성하고 레이아웃을 계산하라고 요청하게 되고, 병목은 브라우저 자체가 됩니다. 이 지점에서 프레임워크 차이는 거의 의미가 없어집니다. 이 실패 지점이 바로 비용 구조의 꼭대기를 보여줍니다.

  • HTML을 만들어내는 작업이 어떤 프레임워크에서든 가장 느립니다.
  • JavaScript 연산은 저렴하지만, 컴포넌트 규모가 커지면 더 이상 공짜가 아닙니다.
  • 프레임워크 오버헤드(가상 DOM이냐 컴파일된 DOM 조작이냐)는 앞의 두 가지에 비하면 오차 범위 수준입니다.

이 순서를 이해하고 나면, 아래에서 설명할 구체적인 기법들은 대부분 당연한 선택으로 보일 겁니다.

SVAR DataGrid의 공통 아키텍처

SVAR 그리드는 React, Vue, Svelte 각각에서 '그 프레임워크 네이티브처럼' 동작하도록 설계되어 있습니다.

엔진과 통합 레이어

프레임워크 독립성은 설계할 가치가 충분합니다. 그리드는 프레임워크에 독립적인 코어(데이터 구조, 설정 정규화, 레이아웃 계산 등)와 프레임워크별 얇은 통합 레이어로 나뉩니다.

힘든 작업은 모두 코어에서 일어납니다. 통합 레이어는 코어의 상태를 각 프레임워크의 반응형 원시 요소로 변환해주는 역할만 합니다. 이 분리 덕분에 React, Vue, Svelte 버전을 동시에 유지보수하는 일이 현실적으로 가능해집니다.

세 프레임워크를 동시에 지원할 필요가 없더라도 이 아이디어는 유용합니다. 단일 React 앱 안에서도 무거운 로직을 컴포넌트 밖으로 빼두면 테스트하기 쉽고, 프로파일링하기 쉽고, 렌더 사이클에서 발생하는 우발적 문제에서 자유로워집니다.

가상화는 기본값

모든 데이터를 그대로 렌더링하는 건 선택지가 아니므로, (다른 SVAR 컴포넌트들처럼) 그리드는 렌더링 가상화를 사용합니다. 컨테이너 크기를 측정하고 화면에 보이는 행과 열만 렌더링하는 방식입니다.

동시에 전체 데이터셋이 다 렌더링된 것처럼 보이고 동작하도록 숨겨진 placeholder를 그려둡니다. 스크롤이 발생하면 데이터 스토어에 새로 보이는 영역을 요청하고, 이를 일반적인 React, Svelte, Vue 컴포넌트로 렌더링합니다.

세 프레임워크 어느 것도 이 작업을 위한 전용 기능을 제공하지 않습니다. 원시 요소도, 내장 헬퍼도 없습니다. 가상화는 순수한 DOM 엔지니어링이고, 전적으로 개발자의 몫입니다. 프레임워크가 하는 일은 그저 선택된 15개 행을 다시 렌더링하는 것뿐이고, 이 정도는 셋 다 잘 해냅니다.

가상화는 데이터를 렌더링하기도 전에 첫 번째 문제를 만듭니다. 어떤 행이 보이는지 알려면 컨테이너 크기가 필요한데, 크기를 얻으려면 뭔가를 먼저 렌더링해야 합니다. 일종의 '닭이 먼저냐 달걀이 먼저냐' 문제입니다.

모든 프레임워크에 공통으로 통하는 패턴은 이렇습니다: 스타일만 적용된 빈 컨테이너를 먼저 렌더링하고, ResizeObserver를 붙인 다음, 0이 아닌 첫 크기 값이 들어올 때까지 실제 데이터 렌더링을 미루는 것입니다. 0은 정당한 중간 상태입니다. 컨테이너에 높이를 부여하는 CSS가 아직 로딩 중일 수 있기 때문입니다.

// React, but the same logic ports to Svelte and Vue as is
const [size, setSize] = useState({ height: 0 });
useEffect(() => { const element = viewportRef.current; if (!element) return;
const observer = new ResizeObserver( ([entry]) => setSize({ height: entry.contentRect.height }) ); observer.observe(element);
return () => observer.disconnect();}, []);

if (!size.height) return null;
return render();

React에는 다른 두 프레임워크엔 없는 무기가 하나 있습니다. 바로 useLayoutEffect입니다. 이 훅은 DOM이 생성된 직후, 브라우저가 화면을 그리기 전에 실행되므로, 컨테이너를 측정하고 상태를 업데이트해서 사용자가 보는 첫 프레임에 이미 보정된 결과를 띄울 수 있습니다.

// react only
const [size, setSize] = useState({ height: 0 });
useLayoutEffect(() => { const element = viewportRef.current; setSize({ height: element.offsetHeight });});

if (!size.height) return null;
return render();

사람들은 useLayoutEffect를 발등 찍는 훅이라고 놀리길 좋아하고, 대체로 맞는 말이기도 합니다. 하지만 가상화 컴포넌트의 초기 측정은 이 훅이 제값을 하는 몇 안 되는 사례입니다.

다만 솔직히 말하면, 실무에서는 결국 ResizeObserver 방식으로 되돌아가는 경우가 많습니다. 외부 스타일시트, 폰트, 이미지가 아직 로드되지 않은 상태라면 useLayoutEffect 콜백 안에서도 레이아웃이 준비되어 있지 않은 경우가 흔하기 때문입니다. 결국 observer는 어차피 필요하고, useLayoutEffect는 이를 대체하는 게 아니라 그 위에 얹는 '첫 프레임 최적화' 정도로 봐야 합니다.

Svelte와 Vue에는 useLayoutEffect에 대응하는 개념이 없습니다. Svelte의 $effect.pre는 DOM 업데이트 전에 실행되어 측정하기엔 너무 이릅니다. onMount와 tick()은 DOM이 존재한 이후에 실행되지만, 거기서 만든 변경사항은 다음 프레임에 그려지므로 그냥 ResizeObserver만 쓰는 것과 차이가 없습니다.

Vue도 비슷합니다. onBeforeUpdate는 너무 이르고, onUpdated는 DOM을 볼 수는 있지만 거기서의 변경은 다음 렌더링 프레임에 반영됩니다. 이건 React의 진짜 우위이긴 하지만, 상당히 좁은 범위의 우위입니다. 다른 두 프레임워크의 설계도 나름의 타당성이 있고, 애초에 React가 이 훅을 갖게 된 것도 React 자체의 렌더 사이클 방식 때문입니다.

SSR에 관한 짧은 이야기

가상화와 서버 사이드 렌더링은 본질적으로 충돌합니다. 서버는 사용자의 뷰포트에 어떤 행이 들어올지 알 수 없으니, 올바른 슬라이스를 렌더링할 방법이 없습니다. 하지만 경험상 이 문제는 생각보다 크지 않습니다.

SSR이 존재하는 주된 이유는 더 빠른 첫 페인트와 SEO인데, 첫 페인트는 가상화가 이미 자체적인 방식으로 해결하고 있고, SEO는 어차피 10만 행 중 15행만 렌더링하는 컴포넌트에서는 애초에 기대할 수 없는 영역입니다.

순수 React나 Vue를 쓸 때는 이 충돌을 체감할 일이 거의 없습니다. 하지만 Next.js나 Nuxt를 쓰면 하이드레이션 불일치 에러가 줄줄이 쏟아지는 형태로 충돌을 만나게 됩니다. 해결책은 생각보다 단순합니다. 그리드를 클라이언트 전용 컴포넌트로 지정하면 에러가 사라집니다. 받아들이고 넘어가면 그만인 트레이드오프입니다.

내부 로직: 메모이제이션과 파생 상태

본격적으로 들어가기 전에 짚고 넘어갈 부분이 있습니다. SVAR 컴포넌트는 폭넓은 사용자를 대상으로 하기 때문에, 모든 React 버전에서 동작해야 한다는 조건이 있습니다. 그래서 여전히 코드에 손으로 메모이제이션 지시자를 넣고 있습니다. 만약 최신 코드베이스에서 React Compiler를 쓸 수 있는 운 좋은 상황이라면, 컴파일러가 수동 배치보다 훨씬 잘 처리해줄 겁니다. 그런 경우라면 아래의 useMemo 관련 내용은 무시해도 됩니다 — 유효한 기법이긴 하지만 React Compiler가 도입되면 쓸모없어지는 기법이니까요.

React의 원래 성능 전략은 "HTML 렌더링이 느리고 JavaScript는 빠르니, 컴포넌트 코드를 다시 실행하는 건 문제없다"는 것이었습니다. 단순한 버튼이라면 완벽하게 통하는 전략입니다.

하지만 데이터 그리드는 렌더링 전에 데이터와 설정을 정규화하고, 레이아웃을 계산하고, 열 geometry를 풀어야 합니다. SVAR의 Gantt 컴포넌트는 이보다 더 많은 계산을 합니다. 이 정도 규모에서는 매 렌더마다 모든 걸 다시 계산하는 게 더 이상 괜찮지 않습니다.

useMemo와 useCallback이 React의 표준 답이고, 복잡한 컴포넌트에서는 최고의 친구가 되어줍니다.

// React
const normalizedHeaders = useMemo(() => normalize(columns), [columns]);
const columnCount = normalizedHeaders.length;

Svelte는 같은 아이디어를 $derived로 표현합니다.

// Svelte
const normalizedHeaders = $derived(normalize(columns));
const columnCount = $derived(normalizedHeaders.length);

Vue는 computed를 씁니다.

// Vue
const normalizedHeaders = computed(() => normalize(columns));
const columnCount = computed(() => normalizedHeaders.value.length);

내부의 반응성 메커니즘은 완전히 다르지만, 사용법은 거의 차이가 없습니다. 셋 다 "입력값이 바뀔 때까지 이 값을 보존한다"는 동일하고 저렴한 계약을 제공합니다.

실제로 그리드의 가상화 계산 로직(보이는 행 범위, 좌/우/중앙 열 분할, 전체 스크롤 높이)을 포팅할 때, useMemo, $derived.by, computed 사이를 거의 한 줄씩 그대로 옮기는 수준으로 이동했습니다. $x, x.value, 그냥 값을 쓰는 식의 문법만 조금씩 달라질 뿐, 로직은 그대로 이식됩니다. 한 프레임워크를 안다면 나머지 둘도 이미 이해하고 있는 셈입니다.

이 비슷함 속에 진짜 차이가 하나 숨어 있습니다. React는 의존성 배열을 직접 작성해야 합니다. 그리드의 renderRows 메모에는 8개의 의존성이 나열되어 있는데, 하나라도 빠뜨리면 디버깅하기 지긋지긋한 오래된(stale) 그리드가 만들어집니다. Svelte와 Vue는 의존성을 자동으로 추적합니다.

React, Vue, Svelte의 기본 동작이 만드는 차이

프레임워크의 기본 동작 방식 이야기를 좀 더 해보면, 컴포넌트 코드가 '언제' 실행되는지에 구조적인 차이가 있고, 이게 모든 걸 좌우합니다. Svelte와 Vue는 컴포넌트의 setup 코드를 한 번만 실행합니다. React는 렌더링마다 함수 본문 전체를 다시 실행합니다.

Svelte나 Vue에서는 "데이터 스토어를 만든다"가 그냥 평범한 한 줄짜리 문장입니다. React에서 같은 의도를 구현하려면 여러 관용구를 동원해야 합니다. 스토어를 위한 useMemo(() => new DataStore(...), []), 이벤트 버스 연결을 위한 null 체크가 딸린 useRef, 그리고 effect는 페인트 이후에 실행되어 첫 프레임에는 늦기 때문에 useEffect 바깥에 두는 동기적인 첫 렌더 초기화 호출까지. 하나의 개념에 네 가지 관용구가 필요한 셈입니다.

하지만 이 모델에는 반대급부도 있습니다. Svelte와 Vue는 setup 코드를 한 번만 실행하기 때문에, 반응성은 명시적으로 선택해서 넣는 대상이 되고, 그 결과 우발적인 재계산은 설계상 거의 발생하지 않습니다. 대신 위험은 다른 곳으로 옮겨갑니다. 애초에 어떤 값을 반응형으로 만드는 걸 깜빡해서, 조용히 절대 업데이트되지 않는 무언가를 출시해버릴 수 있다는 것이죠. 실무에서는 자동 의존성 추적과 린트 도구가 이런 경우 대부분을 잡아줍니다.

그러니 이건 우열의 문제가 아니라 트레이드오프의 문제입니다. React의 모델은 기본값이 더 위험하지만 완전히 명시적이라 무슨 일이 일어나는지 항상 볼 수 있습니다. Svelte와 Vue의 모델은 기본값이 더 안전하지만, 가끔씩 예상 못한 곳에서 허를 찌릅니다.

그렇다고 모든 걸 useMemo로 감싸라는 뜻은 아닙니다. 대부분의 계산은 신경 쓸 필요도 없을 만큼 저렴합니다. 코드를 읽거나, 더 좋게는 프로파일링을 통해 무거운 부분을 찾아내고, 그 부분만 렌더링 사이에 보존하세요. 그게 메모이제이션의 전부입니다.

참고: 하나의 스토어, 세 개의 어댑터

SVAR 컴포넌트에서는 메모이제이션만으로 충분하지 않아서, 프레임워크에 독립적인 반응형 스토어를 하나 두고 이를 각 프레임워크의 원시 요소에 맞게 적용합니다.

Svelte는 $store 자동 구독이 있는 실제 svelte/store writable을 통해 스토어를 소비합니다. Vue는 작은 subscribe() 헬퍼를 통해 ref를 받습니다.

React는 훅을 받습니다. useStore(api, 'name')는 useState와 useEffect 안의 구독을 결합해서 만들어졌습니다. React에는 한 가지 장치가 더 필요했는데, 배열이 제자리에서(in place) 변경될 때 참조 동등성으로는 변화를 감지할 수 없기 때문에, 의존성으로 사용할 변경 카운터를 반환하는 useStoreWithCounter 훅을 추가로 만들어야 했습니다.

단일 프레임워크만 타겟으로 한다면 이런 장치는 필요 없습니다. React와 Vue 모두 성숙한 외부 스토어 생태계를 갖추고 있고, Svelte 5의 .svelte.js state 모듈도 정말 괜찮은 네이티브 옵션입니다. 다만 SVAR는 하나의 스토어가 세 호스트를 모두 서빙해야 했기 때문에 이런 선택지를 쓸 수 없었을 뿐입니다.

정리

SVAR가 React, Vue, Svelte로 같은 데이터 그리드를 세 번 만들며 얻은 결론은, 흔히 떠올리는 "프레임워크 전쟁"의 구도와는 꽤 달랐습니다.

  • 성능 병목의 대부분은 프레임워크가 아니라 브라우저의 DOM 렌더링/레이아웃 비용에서 나옵니다. HTML 생성이 가장 비싸고, JS 연산은 그보다 저렴하며, 가상 DOM이냐 컴파일 방식이냐 하는 프레임워크 차이는 오차 범위에 가깝습니다.
  • 대용량 데이터를 다루려면 결국 가상화가 필수이며, 세 프레임워크 모두 가상화를 위한 전용 기능을 제공하지 않습니다. 가상화는 순수하게 개발자가 직접 구현해야 하는 DOM 엔지니어링 영역입니다.
  • 초기 컨테이너 크기 측정에서 React의 useLayoutEffect는 실질적인 우위지만 좁은 범위의 우위이며, 실무에서는 결국 ResizeObserver와 함께 써야 합니다.
  • useMemo/$derived/computed는 문법만 다를 뿐 거의 동일한 계약을 제공하며, 로직은 거의 그대로 포팅됩니다. 다만 React는 의존성 배열을 수동으로 관리해야 하는 반면 Svelte와 Vue는 자동 추적을 제공합니다.
  • React는 컴포넌트 함수를 매 렌더마다 재실행하는 모델이라 기본적으로 위험하지만 명시적이고, Svelte·Vue는 setup을 한 번만 실행해 기본적으로 안전하지만 반응성을 깜빡 빠뜨리는 실수가 숨어들 수 있습니다. 어느 쪽이 우월한 게 아니라 트레이드오프입니다.

프론트엔드 개발자 입장에서 핵심 실무 포인트는, 복잡하고 무거운 컴포넌트를 만들 때 "어떤 프레임워크가 더 빠른가"에 매몰되기보다 데이터 구조·레이아웃 계산 같은 무거운 로직을 프레임워크 바깥(프레임워크 독립적인 코어)으로 분리하고, 가상화와 메모이제이션 같은 기본기를 프레임워크 특성에 맞게 적용하는 쪽이 훨씬 더 큰 성능 차이를 만든다는 점입니다.
