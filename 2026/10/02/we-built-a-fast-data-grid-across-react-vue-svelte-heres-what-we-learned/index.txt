15:T48b9,<p>SVAR는 데이터 그리드, 간트 차트, 캘린더처럼 기능이 많고 복잡한 UI 컴포넌트를 만드는 회사입니다. 이런 컴포넌트들의 공통점은 단 하나, 바로 성능인데요. 대량의 데이터가 쏟아져 들어와도 빠르고 반응성 있게 동작해야 합니다. 그런데 SVAR는 같은 컴포넌트를 React, Vue, Svelte 세 가지 프레임워크 버전으로 동시에 출시하고 있습니다. 덕분에 &quot;프레임워크 비교&quot;라는 주제에 대해 꽤 독특한 위치에 서 있는데요. 보통 이런 비교 글은 한 프레임워크를 깊이 아는 사람이 나머지 둘은 문서만 훑어보고 쓰는 경우가 많지만, SVAR는 실제로 세 프레임워크 모두에서 똑같이 &quot;고성능&quot;을 만들어내야 했던 입장입니다.</p>
<p>이 글은 SVAR가 세 프레임워크에서 동일한 데이터 그리드 컴포넌트를 만들면서 무엇을 배웠는지 정리한 내용입니다. 결론부터 말하면 다소 의외인데요, 빠른 데이터 그리드를 만드는 데 드는 비용의 대부분은 프레임워크와 거의 무관했고, 프레임워크 간에 실제로 차이가 나는 지점은 흔히 벌어지는 &quot;프레임워크 전쟁&quot;에서 말하는 것보다 훨씬 좁았습니다. 그래서 이 글은 의도적으로 승자를 가리지 않습니다.</p>
<h3>프레임워크와 무관한 성능 문제</h3>
<p>데이터 그리드는 이런 비교를 하기에 좋은 테스트 케이스입니다. 누구나 한 번쯤 만들어봤거나 써봤을 만큼 구조는 단순하지만, 동시에 다른 컴포넌트들과 달리 데이터양이 어마어마합니다. 1,000행은 흔한 수준이고 10,000행도 드물지 않아서, 처음부터 이를 염두에 두고 설계해야 합니다.</p>
<p>실제로 SVAR React DataGrid가 20만 행, 2만 열을 렌더링하는 데모를 보면, 터무니없이 큰 숫자인데도 그리드가 매끄럽게 처리하는 것을 확인할 수 있습니다.</p>
<p>반면 10,000행을 그대로 DOM에 렌더링하면 React, Vue, Svelte 모두 똑같은 방식으로 죽습니다. 요즘 하드웨어가 워낙 빠르다 보니 &quot;죽는다&quot;기보다는 심하게 느려지는 정도겠지만, 결국 수십만 개의 DOM 노드를 만들고 레이아웃을 계산하라고 브라우저에 요청하게 되고, 병목은 브라우저 쪽에서 발생합니다. 프레임워크가 거의 상관없어지는 지점입니다. 이 실패 지점이 바로 비용 구조의 꼭대기를 보여줍니다.</p>
<ul>
<li>HTML을 만들어내는 작업은 어떤 프레임워크를 쓰든 가장 느립니다.</li>
<li>JavaScript 연산은 저렴하지만, 컴포넌트 규모가 커지면 더 이상 공짜가 아닙니다.</li>
<li>프레임워크 오버헤드(가상 DOM 대 컴파일된 DOM 조작)는 앞의 두 가지에 비하면 오차 범위 수준입니다.</li>
</ul>
<p>이 순서를 한번 받아들이고 나면, 아래 설명할 구체적인 기법들은 대부분 자연스럽게 이해가 됩니다.</p>
<h3>SVAR DataGrid의 공통 아키텍처</h3>
<p>여기서는 SVAR가 React, Vue, Svelte 각각에서 &quot;프레임워크 네이티브&quot;하게 느껴지도록 그리드를 어떻게 설계했는지 다룹니다.</p>
<h4>엔진과 통합 레이어</h4>
<p>프레임워크 독립성은 설계할 가치가 있는 목표입니다. SVAR의 그리드는 프레임워크에 독립적인 코어(데이터 구조, 설정 정규화, 레이아웃 계산 등)와, 프레임워크별로 얇게 붙는 통합 레이어로 나뉩니다.</p>
<p>어려운 작업은 전부 코어에서 일어납니다. 통합 레이어는 코어의 상태를 각 프레임워크의 반응형(reactive) 프리미티브로 번역해주는 역할만 합니다. 이렇게 분리했기 때문에 React, Vue, Svelte 세 버전을 동시에 유지보수하는 일이 현실적으로 가능해집니다.</p>
<p>꼭 세 프레임워크를 동시에 지원해야만 이 아이디어가 유용한 건 아닙니다. 단일 React 앱 안에서도 무거운 로직을 컴포넌트 밖에 두면 테스트하기 쉽고, 프로파일링하기 쉽고, 렌더 사이클에서 발생하는 우발적인 문제로부터 안전해집니다.</p>
<h4>가상화는 기본값</h4>
<p>모든 데이터를 렌더링하는 건 애초에 선택지가 아니므로, 그리드는 (대부분의 SVAR 컴포넌트가 그렇듯) 렌더링 가상화를 사용합니다. 컨테이너 크기를 측정해서 화면에 실제로 보이는 행과 열만 렌더링하는 방식입니다.</p>
<p>동시에 숨겨진 플레이스홀더를 그려서 마치 전체 데이터셋이 다 렌더링된 것처럼 보이고 동작하게 만듭니다. 스크롤이 일어나면 데이터 스토어에 새로 보여야 할 구간을 요청하고, 그걸 React든 Svelte든 Vue든 평범한 컴포넌트로 렌더링합니다.</p>
<p>세 프레임워크 중 어느 것도 이 작업을 위한 특별한 기능을 제공하지 않습니다. 전용 프리미티브도, 내장 헬퍼도 없습니다. 가상화는 순수한 DOM 엔지니어링의 영역이고, 전적으로 개발자의 몫입니다. 프레임워크가 하는 일은 그저 여러분이 보여주기로 결정한 15개 행을 다시 렌더링하는 것뿐이고, 그 부분은 셋 다 잘 해냅니다.</p>
<p>하지만 가상화는 데이터가 렌더링되기도 전에 첫 번째 문제를 만듭니다. 어떤 행이 보이는지 알려면 컨테이너의 크기가 필요하고, 크기를 얻으려면 일단 뭔가를 렌더링해야 합니다. 일종의 닭과 달걀 문제인 셈입니다.</p>
<p>어느 프레임워크에서나 통하는 패턴은 이렇습니다. 먼저 스타일만 입힌 빈 컨테이너를 렌더링하고, ResizeObserver를 붙인 다음, 0이 아닌 첫 번째 크기 값이 들어올 때까지 실제 데이터 렌더링을 미루는 것입니다. 0이라는 값도 정당한 중간 상태로 취급해야 하는데, 컨테이너에 높이를 부여하는 CSS가 아직 로딩 중일 수 있기 때문입니다.</p>
<pre><code class="language-js">// React, but the same logic ports to Svelte and Vue as is
const [size, setSize] = useState({ height: 0 });
useEffect(() =&gt; {
  const element = viewportRef.current;
  if (!element) return;

  const observer = new ResizeObserver(
    ([entry]) =&gt; setSize({ height: entry.contentRect.height })
  );
  observer.observe(element);

  return () =&gt; observer.disconnect();
}, []);

if (!size.height) return null;
return render();</code></pre>
<p>여기서 React만 가진 무기가 하나 있는데, 바로 <code>useLayoutEffect</code>입니다. 이 훅은 DOM이 만들어진 뒤, 브라우저가 화면을 그리기 전에 실행되기 때문에 컨테이너를 측정하고 상태를 갱신한 결과가 사용자가 보는 첫 프레임에 바로 반영될 수 있습니다.</p>
<pre><code class="language-js">// react only
const [size, setSize] = useState({ height: 0 });
useLayoutEffect(() =&gt; {
  const element = viewportRef.current;
  setSize({ height: element.offsetHeight });
});

if (!size.height) return null;
return render();</code></pre>
<p>사람들은 <code>useLayoutEffect</code>를 보통 &quot;발등 찍는 훅&quot;이라고 놀리곤 하는데, 대체로 맞는 말입니다. 하지만 가상화를 위한 초기 측정이야말로 이 훅이 제값을 하는 몇 안 되는 사례입니다.</p>
<p>다만 솔직히 말하면, 실제로는 결국 ResizeObserver 방식으로 되돌아가게 됩니다. 레이아웃이 <code>useLayoutEffect</code> 콜백 시점에 아직 준비되지 않은 경우가 많은데, 외부 스타일시트나 폰트, 이미지가 아직 로드되지 않아서 크기가 확정되지 않았기 때문입니다. 그래서 어차피 observer는 필요하고, <code>useLayoutEffect</code>는 이를 대체하는 게 아니라 그 위에 &quot;첫 프레임 최적화&quot;를 얹어주는 역할에 가깝습니다.</p>
<p>Svelte와 Vue에는 <code>useLayoutEffect</code>에 대응하는 개념이 없습니다. Svelte의 <code>$effect.pre</code>는 DOM이 업데이트되기 전에 실행되어서 측정하기엔 너무 이릅니다. <code>onMount</code>와 <code>tick()</code>은 DOM이 존재한 뒤에 실행되지만, 거기서 만든 변경은 다음 프레임에 그려지기 때문에 그냥 ResizeObserver를 쓰는 것과 별 차이가 없습니다.</p>
<p>Vue도 같은 식으로 나뉩니다. <code>onBeforeUpdate</code>는 너무 이르고, <code>onUpdated</code>는 DOM은 볼 수 있지만 그 안에서 만든 변경사항은 다음 렌더링 프레임에 반영됩니다. 여기서는 React가 실제로 우위를 갖는데, 다만 적용 범위가 좁은 우위입니다. 다른 프레임워크들의 설계도 나름의 타당성이 있고, React가 이 훅을 갖게 된 것도 어느 정도는 React 자체의 렌더 사이클 구조 때문입니다.</p>
<h4>SSR에 대한 이야기</h4>
<p>가상화와 서버 사이드 렌더링은 정의상 서로 충돌합니다. 서버는 사용자의 뷰포트에 어떤 행이 들어올지 전혀 알 수 없으므로, 올바른 구간을 렌더링할 수 없습니다. 그런데 실제로는 생각보다 큰 문제가 아닙니다.</p>
<p>SSR이 존재하는 주된 이유는 더 빠른 첫 페인트와 SEO인데, 첫 페인트는 가상화 자체가 나름의 방식으로 이미 해결해주고, SEO는 애초에 10만 행 중 15행만 렌더링하는 컴포넌트에서 작동할 리가 없습니다.</p>
<p>순수 React나 Vue를 쓸 때는 이 충돌을 전혀 눈치채지 못합니다. 하지만 Next.js나 Nuxt를 쓰면 보통 하이드레이션 불일치(hydration mismatch) 에러가 연쇄적으로 터지는 형태로 드러납니다. 해결책은 생각보다 싱겁습니다. 그리드를 클라이언트 전용 컴포넌트로 표시하면 에러가 사라집니다. 받아들이고 넘어가야 하는 트레이드오프인 셈입니다.</p>
<h4>내부 로직: 메모이제이션과 파생 상태</h4>
<p>본격적으로 들어가기 전에 짚어둘 점이 있습니다. SVAR 컴포넌트는 폭넓은 사용자를 대상으로 만들기 때문에 모든 종류의 React 환경에서 동작해야 하고, 그래서 메모이제이션 지시문을 여전히 코드에 수동으로 배치하고 있습니다. 만약 최신 코드베이스를 다루고 있어서 React Compiler를 쓸 수 있다면, 컴파일러가 이 작업을 대신, 아마도 수동 배치보다 훨씬 잘 해줄 겁니다. 그렇다면 아래에서 <code>useMemo</code>와 관련된 내용은 무시해도 됩니다. 유효한 기법이긴 하지만 React Compiler가 도입되면 의미가 사라지는 기법이기 때문입니다.</p>
<p>React의 원래 성능 전략은 &quot;HTML 렌더링은 느리고 JavaScript는 빠르니, 컴포넌트 코드를 다시 실행하는 건 괜찮다&quot;는 것이었습니다. 단순한 버튼 하나라면 완벽하게 맞는 말입니다.</p>
<p>하지만 데이터 그리드는 렌더링하기 전에 데이터와 설정을 정규화하고, 레이아웃을 계산하고, 컬럼의 기하학적 구조를 풀어내야 하며, SVAR의 간트 컴포넌트는 그보다도 더 많은 계산을 합니다. 이 정도 규모에서는 렌더링마다 모든 걸 다시 실행하는 게 더 이상 괜찮지 않습니다.</p>
<p><code>useMemo</code>와 <code>useCallback</code>이 React의 표준 해법이고, 복잡한 컴포넌트에서는 가장 든든한 친구가 됩니다.</p>
<pre><code class="language-js">// React
const normalizedHeaders = useMemo(() =&gt; normalize(columns), [columns]);
const columnCount = normalizedHeaders.length;</code></pre>
<p>Svelte는 <code>$derived</code>로 같은 개념을 표현합니다.</p>
<pre><code class="language-js">// Svelte
const normalizedHeaders = $derived(normalize(columns));
const columnCount = $derived(normalizedHeaders.length);</code></pre>
<p>Vue는 <code>computed</code>를 씁니다.</p>
<pre><code class="language-js">// Vue
const normalizedHeaders = computed(() =&gt; normalize(columns));
const columnCount = computed(() =&gt; normalizedHeaders.value.length);</code></pre>
<p>내부의 반응성 메커니즘은 완전히 다르게 작동하지만, 사용하는 방식은 거의 똑같습니다. 셋 다 &quot;입력값이 바뀔 때까지 이 값을 보존한다&quot;는 저렴한 계약을 똑같이 제공합니다.</p>
<p>실제로 그리드의 가상화 계산 로직(보이는 행 범위, 좌/우/중앙 컬럼 분할, 전체 스크롤 높이)을 포팅했을 때, <code>useMemo</code>, <code>$derived.by</code>, <code>computed</code> 사이를 거의 한 줄 단위로 번역하는 수준이었습니다. 문법만 <code>$x</code>, <code>x.value</code>, 일반 값 사이를 오가고, 로직 자체는 그대로 옮겨졌습니다. 한 프레임워크를 알면 나머지 둘도 이미 이해하고 있는 셈입니다.</p>
<p>이 유사함 속에 진짜 차이가 하나 숨어 있는데, 바로 의존성 배열입니다. React는 의존성 배열을 직접 작성해야 합니다. 그리드의 <code>renderRows</code> 메모에는 8개의 의존성이 나열되어 있고, 하나라도 빠뜨리면 디버깅하기 끔찍한 &quot;낡은&quot; 그리드가 됩니다. Svelte와 Vue는 의존성을 자동으로 추적합니다.</p>
<h4>React, Vue, Svelte의 기본 동작이 만드는 차이</h4>
<p>프레임워크의 기본적인 작동 방식을 이야기하자면, 컴포넌트 코드가 언제 실행되는지에 구조적인 차이가 있고, 이게 모든 것에 영향을 미칩니다. Svelte와 Vue는 컴포넌트의 설정(setup) 코드를 한 번만 실행합니다. React는 렌더링할 때마다 함수 본문 전체를 다시 실행합니다.</p>
<p>Svelte나 Vue에서는 &quot;데이터 스토어를 만든다&quot;는 게 그냥 평범한 한 줄의 문장입니다. React에서는 같은 의도를 구현하는 데 여러 관용구가 필요합니다. 스토어를 위한 <code>useMemo(() =&gt; new DataStore(...), [])</code>, 이벤트 버스 연결을 위한 null 체크가 딸린 <code>useRef</code>, 그리고 첫 렌더링에서 동기적으로 실행되어야 하는 초기화 호출(이펙트는 페인트 이후에 실행되므로 첫 프레임에는 너무 늦습니다)까지. 개념은 하나인데 관용구는 네 개입니다.</p>
<p>하지만 이 모델에는 이면도 있습니다. Svelte와 Vue는 설정 코드를 딱 한 번만 실행하기 때문에, 반응성은 명시적으로 &quot;가입&quot;해야 하는 것이 되고, 그 결과 의도치 않은 재계산이 설계상 거의 발생하지 않습니다. 대신 위험은 다른 곳으로 옮겨갑니다. 애초에 어떤 값을 반응형으로 만드는 걸 깜빡해서, 조용히 절대 업데이트되지 않는 값을 그대로 배포해버릴 수 있다는 것입니다. 실무에서는 자동 의존성 추적과 린트 도구가 이런 경우의 대부분을 잡아줍니다.</p>
<p>그러니 이건 우열이 아니라 트레이드오프입니다. React의 모델은 기본적으로 위험 부담이 더 크지만 완전히 명시적이라서 무슨 일이 일어나는지 항상 눈으로 볼 수 있습니다. Svelte와 Vue의 모델은 기본적으로 더 안전하지만, 가끔 예상치 못한 순간에 놀라게 됩니다.</p>
<p>그렇다고 모든 걸 <code>useMemo</code>로 감싸라는 뜻은 아닙니다. 대부분의 계산은 신경 쓸 만큼 비싸지 않습니다. 코드를 읽거나, 더 좋게는 프로파일링을 해서 무거운 덩어리를 찾아내고, 그 부분만 렌더링 사이에 보존하면 됩니다. 그게 이 작업의 전부입니다.</p>
<h4>사이드 노트: 하나의 스토어, 세 개의 어댑터</h4>
<p>SVAR 컴포넌트에서는 메모이제이션만으로는 충분하지 않았기 때문에, 프레임워크에 독립적인 반응형 스토어를 하나 두고 이를 각 프레임워크의 프리미티브에 맞게 어댑터로 연결했습니다.</p>
<p>Svelte는 실제 <code>svelte/store</code>의 writable을 <code>$store</code> 자동 구독 방식으로 소비합니다. Vue는 작은 <code>subscribe()</code> 헬퍼를 통해 ref를 받습니다.</p>
<p>React는 훅 형태로, <code>useStore(api, 'name')</code>을 <code>useState</code>와 <code>useEffect</code> 안의 구독으로 구현했습니다. React에는 장치가 하나 더 필요했는데, 변경 카운터를 반환하는 <code>useStoreWithCounter</code> 훅입니다. 배열이 제자리에서(in place) 변경될 때는 참조 동등성(reference equality)만으로는 변화를 감지할 수 없기 때문에, 의존성 값으로 쓸 카운터가 따로 필요했습니다.</p>
<p>만약 단일 프레임워크만 타겟으로 한다면 이런 장치는 전혀 필요 없습니다. React와 Vue는 둘 다 성숙한 외부 스토어 생태계를 갖고 있고, Svelte 5의 <code>.svelte.js</code> 상태 모듈도 꽤 괜찮은 네이티브 옵션입니다. 다만 SVAR의 경우 하나의 스토어가 세 개의 호스트를 동시에 섬겨야 했기 때문에 이런 선택지를 쓸 수 없었을 뿐입니다.</p>
<h3>정리</h3>
<p>SVAR가 React, Vue, Svelte에서 같은 데이터 그리드를 세 번 고성능으로 구현하며 얻은 결론은 생각보다 담백합니다.</p>
<ul>
<li>데이터 그리드 같은 무거운 컴포넌트의 성능 병목은 대부분 프레임워크 선택이 아니라 &quot;얼마나 많은 DOM을 만드는가&quot;에서 결정됩니다. HTML 생성 &gt; JS 연산 &gt; 프레임워크 오버헤드 순으로 비용이 큽니다.</li>
<li>가상화는 세 프레임워크 어디서도 기본 제공되지 않는, 순수하게 개발자가 직접 구현해야 하는 영역입니다. 초기 크기 측정 문제는 &quot;빈 컨테이너 렌더링 → ResizeObserver 부착 → 0이 아닌 크기 대기&quot;라는 패턴으로 공통 해결할 수 있습니다.</li>
<li><code>useLayoutEffect</code>는 React만 가진 실질적이지만 좁은 우위입니다. Svelte의 <code>$effect.pre</code>/<code>onMount</code>나 Vue의 <code>onBeforeUpdate</code>/<code>onUpdated</code>는 타이밍상 같은 역할을 하지 못하지만, 실무에서는 어차피 ResizeObserver로 폴백하게 되므로 이 우위의 체감 효과는 제한적입니다.</li>
<li><code>useMemo</code>/<code>useCallback</code>, <code>$derived</code>, <code>computed</code>는 문법만 다를 뿐 로직은 거의 그대로 포팅되는 동일한 개념입니다.</li>
