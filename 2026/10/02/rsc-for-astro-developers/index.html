📅 2026-10-02📰 Dan Abramov (overreacted)
frontend

RSC for Astro Developers

Astro와 React Server Components(RSC)는 겉보기엔 완전히 다른 생태계처럼 보이지만, 핵심 멘탈 모델은 놀랍도록 비슷합니다. Dan Abramov는 이 글에서 Astro를 이미 알고 있는 개발자를 대상으로, Astro의 개념을 다리 삼아 RSC를 설명합니다. Astro의 구조를 안다면 RSC 멘탈 모델의 80%는 이미 갖춘 셈이라는 것이 이 글의 핵심 주장인데요, 동시에 두 모델이 어디서 갈라지는지, 그리고 그 차이가 왜 중요한지도 짚어줍니다.

Astro의 두 가지 세계: Astro Components와 Client Islands

Astro에는 근본적으로 두 종류의 컴포넌트가 있습니다.

Astro Components는 .astro 확장자를 가진 파일로, 서버 또는 빌드 타임에서만 실행됩니다. 즉 이 코드는 클라이언트로 절대 전송되지 않습니다. 그래서 파일 시스템을 읽거나 내부 서비스를 호출하거나 데이터베이스에 접근하는 등, 클라이언트 코드가 할 수 없는 일들을 할 수 있습니다. 대신 네이티브 HTML 기능이나 직접 작성한 <script> 외에는 인터랙티브한 동작을 할 수 없습니다. Astro Components는 다른 Astro Components나 Client Islands를 렌더링할 수 있습니다.

Client Islands는 React, Vue 등으로 작성된 일반적인 프론트엔드 컴포넌트입니다. 인터랙티브한 부분을 추가하기 편한 지점이 바로 여기죠. Client Islands는 해당 프레임워크 고유의 방식으로 같은 프레임워크의 다른 컴포넌트를 렌더링할 수 있습니다(React 컴포넌트가 다른 React 컴포넌트를 렌더링하는 것처럼요). 하지만 Client Island에서 Astro Component를 렌더링할 수는 없습니다. 이미 그 시점엔 Astro의 실행이 끝났기 때문에 말이 안 되는 거죠.

다음은 PostPreview.astro라는 Astro Component가 LikeButton Island를 렌더링하는 예시입니다.

---
import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';
const { slug } = Astro.props;
const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
---
<article>
<h1>{title}</h1>
<LikeButton client:load />
</article>
import { useState } from 'react';
export function LikeButton() {
const [liked, setLiked] = useState(false);
return (
<button onClick={() => setLiked(!liked)}>
{liked ? '❤️' : '🤍'} Like
</button>
);
}

여기서 중요한 포인트는, Astro Components와 Client Islands가 본질적으로 서로 다른 "세계"에 살고 있고, 데이터는 오직 아래 방향으로만 흐른다는 점입니다. 모든 전처리는 Astro Components에서 일어나고, 인터랙티브한 부분은 Client Islands에 "넘겨주는" 구조입니다.

React Server Components로 같은 걸 작성한다면

RSC에서는 같은 개념이 Server Components와 Client Components로 불립니다. 위의 Astro Component를 RSC로 작성하면 이렇게 됩니다.

import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';
async function PostPreview({ slug }) {
const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
return (
<article>
<h1>{title}</h1>
<LikeButton />
</article>
);
}
'use client';
import { useState } from 'react';
export function LikeButton() {
const [liked, setLiked] = useState(false);
return (
<button onClick={() => setLiked(!liked)}>
{liked ? '❤️' : '🤍'} Like
</button>
);
}

두 접근 방식 뒤에 깔린 멘탈 모델은 거의 같습니다. Astro를 안다면 React Server Components의 멘탈 모델 80%는 이미 갖고 있는 셈입니다. (설령 RSC가 별로라고 생각하더라도 Astro는 배워볼 가치가 있습니다.)

문법적 차이점

몇 가지 눈에 띄는 차이가 있습니다.

  • Astro Components와 달리 React Server Components는 그냥 일반 JavaScript 함수입니다. "싱글 파일" 형태가 아니고요, props도 Astro.props가 아니라 함수 인자로 들어오며, 별도의 "템플릿" 영역도 없습니다.
  • Astro에서는 .astro 파일로 작성함으로써 Astro Components와 Client Islands를 구분합니다. Client Island를 import하는 순간 더 이상 .astro 파일 안에 있지 않게 되고, 그렇게 Astro 세계를 "벗어나는" 셈이죠. RSC에서는 이 역할을 'use client' 디렉티브가 맡습니다. 'use client'는 서버 세계가 "끝나는" 지점을 표시하는, 두 세계 사이의 문입니다.
  • Astro에는 client:load 같은 디렉티브가 있어서 Island를 정적 HTML로 다룰지, 클라이언트에서 하이드레이션할지 선택할 수 있습니다. RSC는 이런 구분을 사용자 코드에 노출하지 않습니다. React 입장에서 보면, 어떤 컴포넌트가 인터랙티브하게 작성됐다면 그 인터랙티비티를 없애는 건 애초에 잘못된 일입니다. 만약 정말로 인터랙티비티가 필요 없다면 그냥 'use client'를 지우면 되고, 그러면 서버 세계에서 import될 때 자연히 서버 전용으로 남습니다.

"Astro 부분"도 결국은 "그냥 React"다

마지막 포인트가 꽤 흥미롭습니다. Astro에서는 .astro 파일과 Client Islands라는 서로 다른 문법이 두 세계를 명확하고 뚜렷하게 구분해줍니다. 같은 컴포넌트가 맥락에 따라 Astro Component도 됐다가 Client Island도 됐다가 할 수는 없습니다. 둘은 문법부터 다른, 완전히 별개의 존재니까요.

하지만 RSC에서는 "Astro에 해당하는 부분"도 결국 "그냥 React"입니다. 그래서 클라이언트 전용 기능이나 서버 전용 기능을 전혀 쓰지 않는 컴포넌트가 있다면, 그 컴포넌트는 양쪽 역할을 모두 할 수 있습니다.

자체적으로 파싱을 수행하는 <Markdown /> 컴포넌트를 생각해봅시다. 이 컴포넌트는 클라이언트 기능(State 등)도, 서버 기능(DB 읽기 등)도 쓰지 않으므로 양쪽 세계 어디서든 import할 수 있습니다. 서버 세계에서 import하면 "Astro Component"처럼 동작하고, 클라이언트 세계에서 import하면 "Client Island"처럼 동작합니다. 이건 새로운 개념이 아니라 그냥 함수를 import하는 방식이 원래 그런 것뿐입니다.

RSC에서는 서버 세계에서 import된 것은 서버 세계에서 실행되고, 클라이언트 세계에서 import된 것은 클라이언트 세계에서 실행되며, 양쪽 세계 모두에서 지원되지 않는 것(클라이언트에서 DB 접근, 서버에서 useState 등)은 빌드 에러를 일으킵니다. 그러면 어쩔 수 없이 'use client'로 "문을 내야" 하는 거죠.

저주이자 축복

이 구조는 저주이면서 동시에 축복입니다.

저주인 이유는, RSC를 능숙하게 다루는 법을 배우는 게 상당히 직관적이지 않기 때문입니다. "지금 내가 어느 세계에 있는지" 계속 신경 쓰게 됩니다. 사실 이건 중요하지 않고, 항상 로컬하게만 추론하면 된다는 사실을 받아들이기까지 연습이 필요합니다. DB 같은 서버 기능이 필요한 파일에서는 그걸 쓰고, State 같은 클라이언트 기능이 필요한 파일에서는 그걸 쓰고, 뭔가 잘못되면 빌드 타임 검증이 에러를 내주는 데 의존하면 됩니다. 그다음엔 모듈 스택 트레이스를 보고 "island를 위한 새로운 문"을 어디에 낼지 결정하면 됩니다.

하지만 바로 이 점이 축복이기도 합니다. 양쪽 모두에서 React를 그대로 쓰기 때문에, RSC 모델은 Astro를 쓰면서 마주칠 수 있는 몇 가지 한계를 해결해줍니다.

1) 정적/동적 경계를 미리 결정할 필요가 없다. Astro Components를 잔뜩 작성했다가, 나중에 그 UI를 Client Islands로 옮겨야 한다는 걸(문법을 바꿔가며) 깨닫거나, 동적 UI에서도 같은 UI를 써야 해서 아예 코드를 중복 작성해야 하는 상황이 생길 수 있습니다. RSC에서는 공통 부분을 추출해서 양쪽에서 import하면 됩니다. "이 부분은 주로 동적일 거야" 혹은 "이 부분은 주로 정적일 거야"를 UI 조각마다 미리 생각할 필요가 줄어듭니다. 'use client'를 넣고 빼거나 import 체인 위아래로 옮기는 게 큰 마찰 없이 가능하기 때문이죠. 어디에 "문을 낼지"는 결정해야 하지만, 앞뒤로 "변환"할 필요는 없습니다.

2) 중첩이 자연스럽게 합성된다. Astro에서는 Client Island 안에 Astro Components를 중첩할 수 있지만, 그 안에 또 다른 Client Islands가 있다면 프레임워크(예: React) 입장에서는 서로 별개의 루트로 취급됩니다. 그래서 React나 Vue의 context가 Astro island들 사이를 넘나들 수 없고, 인터랙티브한 동작을 중첩시키는 게 클라이언트 앱처럼 자연스럽게 합성되지 않습니다. RSC에서는 이게 문제가 되지 않습니다. 전체 UI가 내부적으로 하나의 React 트리이기 때문입니다. 클라이언트 context provider가 서버 서브트리 위에 있고, 그 아래 어디에서든 여러 클라이언트 컴포넌트가 그 context를 읽을 수 있습니다. RSC는 프랙탈 island입니다.

3) 페이지 전체 리로드 없는 내비게이션. Astro Components는 결국 HTML만 만들어낼 수 있습니다. 그래서 Astro 사이트에서 링크를 클릭하면 브라우저가 페이지를 완전히 새로 로드해야 합니다. 이게 받아들일 만한 UX라면 괜찮고, View Transitions와 수동 로직으로 개선할 수도 있지만, 근본적으로는 페이지의 HTML 자체가 교체됩니다. 내비게이션 chrome의 상태(React state든 입력창·스크롤 위치 같은 DOM 상태든)를 항상 유지하는 SPA 같은 내비게이션을 원한다면 RSC가 그 공백을 채워줍니다. RSC는 React 트리를 위한 JSON에 가까운 포맷을 사용하는데, 이는 첫 페인트를 위해 HTML로 바뀔 수도 있지만, 내비게이션 시에는 JSON 형태로 다시 가져올 수도 있습니다. 즉 RSC는 MPA 멘탈 모델로 생각하면서도 SPA처럼 느껴지는 경험을 제공합니다.

4) 서버 파트를 제자리에서 새로고침할 수 있다. Astro와 달리 RSC의 서버 파트는 즉석에서 리프레시가 가능합니다. (제 블로그처럼 빌드 시에만 RSC를 돌리는 게 아니라) 실제로 서버를 운영한다면, RSC를 이용해 언제든 화면을 "새로고침"해서 이미 존재하는 클라이언트 사이드 stateful 트리로 새로운 서버 props를 흘려보낼 수 있습니다. 예를 들어 어떤 Astro Component가 상호작용에 반응해서 새로고침되어야 한다면, 전체 페이지 리프레시를 하거나 로직을 Client Island로 옮기거나 둘 중 하나를 선택해야 합니다. RSC에서는 그냥 서버에 새로운 JSX를 요청해서 기존 트리에 병합하면 됩니다.

근본적인 출력 포맷의 차이

Astro의 근본적인 출력 포맷은 HTML입니다. 프론트엔드 프레임워크는 근본적으로 HTML 자체를 조작하는 게 아니라 HTML로 초기화될 수 있는 stateful한 DOM을 조작하기 때문에, Astro는 "일회성 핸드오프" 모델을 따릅니다. 이 덕분에 배우기는 비교적 쉽지만, 서버 기능은 "첫 렌더링"(HTML로의 변환)에 필요한 것으로 제한되고, 인터랙티브한 부분은 대부분 알아서 처리해야 합니다. 인터랙티브한 요소를 점점 더 늘려갈수록 Astro 모델의 한계에 부딪히게 되고, 결국 더 많은 로직을 SPA 같지만 고립된 Islands로 옮기게 될 수 있습니다.

반면 RSC의 근본적인 출력 포맷은 React 트리입니다(HTML로 변환될 수도 있지만, JSON으로 (다시) fetch될 수도 있습니다). RSC는 양쪽 세계 모두에서 React를 쓰고 두 세계 사이에 시각적 구분이 없기 때문에 익히기가 더 까다롭습니다. 대신 일단 경계를 옮기는 요령을 터득하고 나면 그 경계가 매우 유연해져서, 뭔가가 예상보다 더 정적이거나 더 동적이 되었을 때 코드를 "Astro 쪽으로" 혹은 "다시 Islands로" 옮겨야 하는 문제를 해결해줍니다. 또한 UI가 읽기 전용이든 뮤테이션에 반응해서 다시 가져와야 하든, "데이터를 UI로 매핑한다"는 같은 멘탈 모델을 그대로 유지할 수 있습니다. 서버 파트는 트리 깊숙이까지 파고들어 클라이언트 파트와 인터리브됩니다.

그리고 양쪽 다 React이기 때문에, 모든 React 기능이 처음부터 끝까지 통합되어 있습니다. 예를 들어 클라이언트의 선언적 로딩 상태인 <Suspense>는 서버에서 오는 비동기 데이터뿐 아니라, 클라이언트가 로드하는 JS와 CSS, 적절한 타임아웃을 가진 폰트와 이미지까지 기다릴 줄 알고, View Transitions까지 트리거할 수 있습니다. React에서는 모든 기능이 서버와 클라이언트 조각들을 자유롭게 중첩·합성·제자리 리프레시할 수 있도록 설계되어 있습니다. 결국 하나의 트리인 거죠. 단점이라면, RSC를 받아들인다는 건 곧 React 전체를 받아들인다는 뜻이라는 점입니다. RSC는 풀스택 React입니다.

Astro는 프레임워크, RSC는 빌딩 블록

마지막으로 짚어둘 점은, Astro는 프레임워크지만 RSC 자체는 더 로우레벨이라는 겁니다. 프레임워크를 위한 빌딩 블록, 혹은 프레임워크가 구현할 수 있는 하나의 표준에 가깝습니다. 현재 공식적으로 지원되는 RSC 구현체는 Next.js App Router(프레임워크)와 Parcel RSC(프레임워크는 아님) 두 가지입니다.

저자는 개인적으로 RSC의 개발자 경험이 아직 다소 거칠다고 느끼지만, 그래도 배워볼 가치가 있다고 말합니다. 흥미로운 아이디어들이 담겨 있기 때문이죠. 그리고 Astro를 한 번도 써본 적이 없다면 꼭 써보라고 권합니다. RSC가 어렵게 느껴진다면 Astro가 같은 아이디어에 대한 더 완만한 진입로가 되어줄 수 있고, 반대로 클라이언트 사이드 React만 써봤다면 Astro가 미처 깨닫지 못했던 문제들을 해결해줄 수도 있습니다.

정리

  • Astro의 Astro Components/Client Islands 구조와 RSC의 Server Components/Client Components 구조는 멘탈 모델이 거의 동일합니다. 서버 전용 세계와 클라이언트 세계가 나뉘어 있고 데이터는 아래로만 흐른다는 점이 핵심입니다.
  • 가장 큰 차이는 "경계를 표시하는 방식"입니다. Astro는 .astro 파일이라는 문법으로 세계를 나누지만, RSC는 'use client' 디렉티브로 같은 React 함수 안에서 문을 냅니다. 그래서 서버/클라이언트 어느 쪽에도 특화되지 않은 컴포넌트는 RSC에서 양쪽 역할을 모두 할 수 있습니다.
  • 이 유연성 덕분에 RSC는 Astro의 몇 가지 한계를 해결합니다: 정적/동적 여부를 미리 결정할 필요가 없고, context가 island 경계를 넘어 전파되며(프랙탈 island), SPA 같은 내비게이션이 가능하고, 서버 파트를 제자리에서 리프레시할 수 있습니다.
  • 근본적으로 Astro의 출력은 HTML(일회성 핸드오프)이고 RSC의 출력은 React 트리(HTML로도, JSON으로도 변환 가능)입니다. 이 차이가 Suspense, View Transitions 같은 React 기능이 서버-클라이언트 전체에 걸쳐 통합되는 이유입니다.
  • RSC는 배우기 어렵지만 일단 익히면 경계를 유연하게 옮길 수 있다는 장점이 있고, Astro는 프레임워크인 반면 RSC는 Next.js App Router나 Parcel RSC 같은 구현체를 통해 쓰이는 로우레벨 표준이라는 위치 차이도 기억해둘 만합니다.
