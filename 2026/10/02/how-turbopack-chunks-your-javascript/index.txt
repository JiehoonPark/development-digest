14:T466b,<p>Next.js 15.3부터 적용된 Turbopack의 청킹(chunking) 전략은 &quot;어떤 코드를 어떤 파일로 묶을 것인가&quot;라는, 번들러라면 피할 수 없는 트레이드오프를 다룹니다. Vercel의 Turbopack 팀에서 인턴으로 근무한 Sam Poder가 이 트레이드오프의 구조를 정리하고, Next.js 16.3에서 추가된 새로운 청킹 제어 기능들을 소개한 글을 바탕으로 정리해봤습니다.</p>
<h3>청크란 무엇인가</h3>
<p>Next.js 페이지의 네트워크 탭을 열어보면 <code>36wnellv-yn9q.js</code> 같은 알 수 없는 이름의 JS 파일들이 잔뜩 로드되는 걸 볼 수 있습니다. 이걸 압축 해제해보면 대략 이런 모습입니다.</p>

<p>이게 바로 &quot;청크(chunk)&quot;입니다. Turbopack은 Next.js 앱을 위해 내 코드, 의존하는 패키지들, 그리고 이들을 엮는 런타임을 수십 개의 청크로 쪼개서 만들어냅니다. 그리고 &quot;청킹&quot;이란 어떤 코드를 어떤 청크에 넣을지 결정하는 과정을 말합니다. 이 결정 방식에는 여러 선택지가 있고, 각각 서로 다른 장단점을 가지고 있습니다.</p>
<h3>세 가지 극단적인 전략과 그 한계</h3>
<p>가장 단순한 방법부터 살펴보겠습니다. <strong>앱의 모든 JavaScript를 하나의 청크에 담는 방식</strong>입니다.</p>
<p>실제로 355개의 모듈을 1개의 청크(1.09MB, <code>app.js</code>)로 합치면, 이 청크는 모든 페이지에서 로드됩니다. 모든 페이지가 같은 청크를 공유하니 첫 로드 이후의 모든 로드는 캐시 히트가 됩니다. 내비게이션은 빨라지겠죠.</p>
<p>하지만 트레이드오프가 바로 보입니다. JavaScript가 거의 없는 페이지를 열어도 다른 모든 페이지의 JavaScript까지 함께 받아야 합니다. 사이트가 커질수록 모든 페이지 로드가 점점 무거워지는 구조라 장기적으로는 지속 불가능합니다.</p>
<p>그래서 <strong>페이지당 하나의 청크</strong>로 바꿔볼 수 있습니다. 같은 355개 모듈을 8개의 청크로 쪼개는 방식인데, 이렇게 하면 청크가 가벼워지고 코드를 과도하게 전송하는 일도 없어집니다. 완벽해 보이지만, 캐싱을 잃게 됩니다. 모든 페이지에 쓰이는 <code>&lt;Footer /&gt;</code>가 있다면 그 코드가 모든 페이지의 청크 안에 각각 들어가 버립니다. 방문자가 네 개의 페이지를 열면 같은 footer 코드를 네 번 내려받는 셈입니다.</p>
<p>그렇다면 더 세분화해서 <strong>모듈 하나당 청크 하나</strong>로 만들면 어떨까요? 355개의 모듈이 355개의 독립된 청크(총 1.09MB)가 되면, 아무것도 과도하게 전송되지 않고 공유되는 모듈은 한 번만 다운로드됩니다. 문제는 작은 JavaScript 파일에 대한 네트워크 요청이 수백 건이 된다는 점입니다. 각 요청은 오버헤드를 수반하고, 이게 수백 개 쌓이면 사이트 속도가 느려집니다. HTTP/2가 요청 비용을 줄여주긴 했지만 여전히 요청 하나하나에 비용이 듭니다. 또한 gzip 같은 압축 알고리즘은 단일 파일 내에서만 반복 패턴을 찾을 수 있기 때문에 작은 파일이 많을수록 압축 효율도 떨어집니다. 압축 딕셔너리가 이를 어느 정도 완화하긴 하지만 근본적인 해결책은 아닙니다.</p>
<h3>요청 수 대 다운로드 크기, 그리고 청크 그룹</h3>
<p>결국 우리가 원하는 건 <strong>가장 작은 다운로드 크기와 가장 적은 요청 수</strong>를 동시에 달성하는 것인데, 이 두 목표는 서로 충돌합니다. 청크가 적고 크면 요청 수는 줄지만, 크기가 커질수록 페이지 간 재사용성은 떨어집니다.</p>
<p>Turbopack의 해법은 <strong>작은 청크들을 더 큰 청크로 병합하되, 어떤 것을 언제 병합해야 실제로 이득인지 판단하는 것</strong>입니다. 이를 위해 &quot;청크 그룹(chunk group)&quot;이라는 개념이 필요합니다. 청크 그룹은 함께 로드되는 청크들의 집합입니다. 예를 들어 <code>/home</code>에서 쓰이는 모든 청크는 하나의 그룹을, <code>/blog</code>에서 쓰이는 청크들은 또 다른 그룹을 이룹니다.</p>
<p>청크 그룹은 과도한 전송 문제를 해결해줍니다. Turbopack은 같은 그룹 안에 있는 청크끼리만 병합하는데, 같은 그룹의 청크들은 어차피 항상 함께 로드되므로 병합해도 원래 받던 것보다 더 많이 받는 일은 생기지 않습니다.</p>
<h3>병합이 언제 이득인가: 비용-편익 계산</h3>
<p>관건은 요청 수를 늘리지 않으면서 캐시 히트율을 최적화하는 방법입니다. 이를 분석하기 위해 두 가지 방문 패턴을 생각해볼 수 있습니다. 하나는 페이지 하나만 보고 떠나는 경우, 다른 하나는 한 페이지를 보고 다른 페이지로 이동하는 경우입니다. (세 페이지 이상 세션도 같은 논리로 확장됩니다.)</p>
<p><code>&lt;Footer /&gt;</code>의 청크를 A, <code>&lt;VideoPlayer /&gt;</code>의 청크를 B라고 해봅시다. A는 모든 페이지에서 쓰이고 B는 홈페이지에서만 쓰입니다. 둘 다 홈페이지 청크 그룹에 속하므로 병합 후보입니다.</p>
<p>방문자가 홈페이지만 보고 떠난다면 병합은 항상 이득입니다. 어차피 둘 다 필요했던 코드이므로, 요청이 두 번에서 한 번으로 줄어드는 순수 이득만 남습니다.</p>
<p>하지만 두 번째 페이지로 이동한다면 얘기가 달라집니다. 홈페이지에서 법률 고지 페이지로 이동하는 경우를 생각해보죠. 법률 고지 페이지는 A는 필요하지만 B는 필요 없습니다. A와 B가 하나의 파일로 합쳐져 있었기 때문에 그 병합 파일은 여기서는 쓸모가 없고, 브라우저는 A를 다시 단독으로 다운로드해야 합니다. 결국 방문자는 A를 두 번 받은 셈입니다.</p>
<p><strong>병합이 두 페이지 세션 전체에서 이득을 보려면, 두 페이지 모두 A와 B를 동시에 필요로 해야 합니다.</strong> 그래야만 병합된 파일이 재사용되고 요청을 실제로 절약할 수 있습니다.</p>
<p>가능한 내비게이션 시나리오를 정리하면 아래와 같습니다. 각 행은 2페이지 세션에서 &quot;첫 페이지가 필요로 하는 것 → 두 번째 페이지가 필요로 하는 것&quot;이며, 숫자는 A와 B를 병합했을 때 요청 수와 다운로드 코드량이 어떻게 변하는지를 (병합하지 않았을 때와 비교해서) 나타냅니다.</p>
<div class="table-wrapper"><table><thead><tr><th>내비게이션</th><th>요청 수 변화</th><th>다운로드 코드량 변화</th></tr></thead><tbody><tr><td>A → A</td><td>0</td><td>0</td></tr><tr><td>A → B</td><td>0</td><td>0</td></tr><tr><td>B → B</td><td>0</td><td>0</td></tr><tr><td>A → A + B</td><td>0</td><td>+ A</td></tr><tr><td>B → A + B</td><td>0</td><td>+ B</td></tr><tr><td>A + B → A</td><td>0</td><td>+ A</td></tr><tr><td>A + B → B</td><td>0</td><td>+ B</td></tr><tr><td>A + B → A + B</td><td>−1</td><td>0</td></tr></tbody></table></div>
<p>A와 B를 병합할지 고려할 때 Turbopack은 &quot;A만 쓰는 청크 그룹&quot;, &quot;B만 쓰는 청크 그룹&quot;, &quot;A+B를 둘 다 쓰는 청크 그룹&quot;의 개수를 세고, 각 시나리오가 발생할 확률로 병합의 비용/이득에 가중치를 매깁니다. 마지막으로 1페이지 방문과 2페이지 이상 방문의 확률도 가중합니다. Turbopack은 기본적으로 전체 세션의 2/3가 단일 페이지 방문, 1/3이 2페이지 이상 방문이라고 가정합니다.</p>
<h3>세 가지 청킹 전략, 실측 비교</h3>

<h3>Next.js 16.3의 새로운 청킹 기능</h3>
<p>청킹의 효율을 제한하는 두 가지 요소가 있습니다. 첫째, 병합 여부는 빌드 타임에 결정되기 때문에 실제로 브라우저가 무엇을 이미 캐시하고 있는지 반영할 수 없습니다. 둘째, 알고리즘은 사람들이 사이트를 어떻게 돌아다니는지 추측에 의존할 수밖에 없고, 그래서 단일 페이지 방문에 2/3라는 가중치를 임의로 부여하고 있습니다. 이번 여름 Turbopack 팀 인턴십에서는 이 두 문제, 그리고 애초에 청크에 담기는 코드량 자체를 줄이는 작업을 진행했습니다.</p>
<h4>더 똑똑한 청크 페칭</h4>
<p>병합의 비용은 방문자가 A를 쓰는 페이지를 로드한 뒤 A+B를 쓰는 페이지로 이동할 때 A를 중복으로 다운로드하게 된다는 점이었습니다. 번들러는 빌드 타임에 브라우저가 무엇을 캐시하고 있는지 알 수 없지만, 런타임은 알 수 있습니다.</p>
<p>Next.js 16.3 이상에서 <code>next.config.js</code>의 <code>experimental.turbopackChunking.generateComponentChunks</code>를 활성화하면, Turbopack은 병합된 청크와 함께 병합 이전의(un-merged) 버전도 함께 생성합니다. 각 병합 청크가 어떤 항목들로 구성되어 있는지, 그리고 그중 어떤 것이 이미 로드되었는지를 추적해서, 요청 시점에 병합된 청크를 쓸지 아니면 부족한 부분만 가져올지 더 저렴한 쪽을 선택할 수 있습니다. 역방향도 마찬가지로 동작합니다. 방문자가 이미 병합된 A+B를 로드했다면, A를 단독으로 다시 로드하는 걸 건너뛸 수 있습니다.</p>
<p>이렇게 하면 소프트 내비게이션 시 불필요한 코드를 덜 받으면서도, 병합의 이점은 그대로 누릴 수 있습니다. (관련 데모 앱: <code>component-chunks-demo-off.labs.vercel.dev</code> vs <code>component-chunks-demo-on.labs.vercel.dev</code>)</p>
<p>또한 <code>only-if-cached</code> 디렉티브를 실험적으로 도입해서, 방문자가 사이트에 들어올 때 무엇을 캐시하고 있는지 확인하는 방법도 시도 중입니다. 이게 적용되면 사이트를 떠났다가 나중에 다시 방문하는 사람들에게도 같은 최적화를 확장할 수 있습니다.</p>
<h4>분석 데이터 기반 청킹</h4>
<p>청킹 알고리즘은 사이트에 대해 여러 가정을 전제로 합니다. 예를 들어 2/3이라는 가중치는 추측값입니다. 많은 사이트에 대체로 합리적인 기본값이지만, 특정 사이트에 꼭 맞는 값은 아닐 수 있습니다. 만약 자신의 사이트에서 사람들이 실제로 어떻게 이동하는지 안다면, 이를 직접 설정할 수 있습니다.</p>
<p><code>next.config.js</code>의 <code>experimental.turbopackChunking</code> 아래에 다음 옵션들을 설정할 수 있습니다.</p>
<ul>
<li><strong><code>firstPageLoadPriority</code></strong>: 단일 페이지 방문과 2페이지 이상 방문 사이의 가중치를 조정합니다. 0~1 사이 값이며, 높을수록 초기 로드 속도를 우선시하는 대신 내비게이션 성능을 희생할 수 있습니다. 이탈률(bounce rate)을 초깃값으로 쓰는 게 합리적입니다. 기본값은 0.67입니다.</li>
<li><strong><code>priorityRoutes</code></strong>: 로드 속도가 가장 중요한 페이지 목록입니다. 해당 라우트에서는 더 적극적으로 청크를 병합합니다.</li>
<li><strong><code>clusters</code></strong>: 함께 자주 방문되는 라우트들의 그룹으로, 정규식 배열로 정의합니다. 클러스터 내부에서는 겹치는 청크를 더 적극적으로 병합합니다. 단, 클러스터 안에 A만 쓰거나 B만 쓰는 페이지와 A와 B를 모두 쓰는 페이지가 섞여 있다면 병합을 덜 합니다.</li>
</ul>
<h4>더 작고 더 적은 청크</h4>
<p>위 내용이 코드를 어떻게 묶을지에 관한 것이라면, 이번 기능들은 애초에 전송되는 코드 자체를 줄이는 데 초점이 맞춰져 있습니다.</p>
<ul>
<li><strong>CJS 모듈 트리쉐이킹</strong>: 기존에는 ESM 모듈에만 트리쉐이킹이 지원되어 CJS 모듈의 사용하지 않는 import/export까지 클라이언트로 전송되고 있었습니다. <code>experimental.turbopackCjsTreeShaking</code>으로 활성화할 수 있으며, 향후 버전에서는 기본값이 될 예정입니다. 더불어 ESM 모듈을 분석·트리쉐이킹할 수 있는 범위도 넓혔고, 특히 동적 import 안의 배럴 파일(barrel file) 지원이 개선되었습니다.</li>
<li><strong>공유 Turbopack 런타임</strong>: 기존에 페이지별로 생성되던 런타임 청크를 하나의 공유 런타임 청크로 대체합니다. <code>experimental.turbopackSharedRuntime</code>으로 활성화할 수 있으며, 첫 로드 이후의 모든 내비게이션에서 블로킹 요청 하나와 약 10KB의 클라이언트 JavaScript를 절약합니다. 이 역시 추후 기본값이 될 예정입니다.</li>
<li><strong>더 가벼운 기본 런타임</strong>: 런타임이 기본적으로 WebAssembly와 Web Worker 관련 코드를 더 이상 포함하지 않습니다. 해당 모듈을 실제로 사용하는 경우에만 로딩 코드를 그때그때 삽입합니다.</li>
</ul>
<p>이 기능들은 모두 Next.js 16.3 이상에서 사용해볼 수 있습니다.</p>
<h3>정리</h3>
<ul>
<li>청킹은 &quot;다운로드 크기 최소화&quot;와 &quot;요청 수 최소화&quot;라는 서로 상충하는 두 목표 사이의 균형점을 찾는 문제입니다. 하나의 거대한 청크는 캐시 히트율은 높지만 과도한 전송을, 모듈 단위의 극세분화는 전송량은 최소화하지만 과도한 요청 수를 만듭니다.</li>
<li>Turbopack은 &quot;청크 그룹&quot; 단위로만 병합을 수행해 과도한 전송을 막고, 단일 페이지 방문과 다중 페이지 내비게이션의 확률(기본 2:1)을 가중치로 삼아 병합이 실제로 이득인지 비용-편익을 계산합니다.</li>
<li>실측 결과 Turbopack 기본 설정은 병합 없음 대비 요청 수를 절반 이상 줄이면서 코드량도 비슷하거나 더 적었고, 그룹 전체를 하나로 합치는 전략은 초기 로드에는 유리하지만 내비게이션이 늘어날수록 중복 다운로드가 늘어 불리해졌습니다.</li>
<li>Next.js 16.3에서는 <code>generateComponentChunks</code>로 런타임에서 병합/비병합 청크 중 더 저렴한 쪽을 선택하게 하고, <code>firstPageLoadPriority</code>/<code>priorityRoutes</code>/<code>clusters</code>로 사이트별 실제 방문 패턴을 반영할 수 있으며, CJS 트리쉐이킹·공유 런타임·경량 기본 런타임으로 애초에 전송되는 코드량 자체를 줄일 수 있습니다.</li>
<li>자신의 서비스가 단일 페이지 위주인지, 특정 라우트 간 이동이 잦은지에 따라 이 옵션들을 조정하면 기본값보다 더 나은 성능을 끌어낼 수 있습니다. 특히 랜딩 페이지 중심 사이트라면 <code>firstPageLoadPriority</code>를, 특정 플로우(예: 결제, 온보딩)가 중요한 서비스라면 <code>priorityRoutes</code>나 <code>clusters</code>를 검토해볼 만합니다.</li>
