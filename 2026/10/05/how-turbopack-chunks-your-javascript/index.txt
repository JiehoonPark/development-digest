<p>&quot;청킹(chunking)&quot;이란 어떤 코드(모듈)를 어떤 청크에 담을지 결정하는 과정입니다. 접근 방식에 따라 트레이드오프가 크게 달라지는데, 극단적인 세 가지 전략부터 살펴보겠습니다.</p>
<p><strong>1. 전체를 하나의 청크로</strong> — 앱이 사용하는 모든 JavaScript를 하나의 <code>app.js</code>에 담는 방식입니다. 예시 사이트 기준 355개 모듈이 1개 청크(1.09MB)로 뭉쳐집니다. 모든 페이지가 같은 청크를 공유하므로 첫 로드 이후에는 항상 캐시 히트가 발생해 네비게이션이 빨라집니다. 다만 JavaScript가 거의 필요 없는 페이지를 열어도 사이트 전체 코드를 받아야 한다는 치명적 단점이 있습니다. 사이트가 커질수록 모든 페이지 로드가 점점 무거워지는 구조라 장기적으로 쓸 수 없습니다.</p>
<p><strong>2. 페이지당 하나의 청크</strong> — 355개 모듈을 8개 청크(1.20MB)로 쪼개는 방식입니다. 청크가 가벼워지고 불필요한 코드를 더 이상 과도하게 보내지 않지만, 캐싱 이점을 잃습니다. 모든 페이지가 쓰는 <code>&lt;Footer /&gt;</code> 같은 공통 코드가 각 페이지 청크마다 중복으로 들어가기 때문에, 방문자가 페이지 4개를 열면 같은 Footer 코드를 4번 내려받게 됩니다.</p>
<p><strong>3. 모듈당 하나의 청크</strong> — 그럼 아예 모듈 하나당 청크 하나씩 만들면 어떨까요? 355개 모듈이 355개의 개별 청크(1.09MB)가 되어, 어떤 코드도 과도하게 전송되지 않고 공유 모듈은 딱 한 번만 다운로드됩니다. 문제는 작은 JavaScript 파일 수백 개를 요청해야 한다는 점입니다. 각 요청에는 오버헤드가 따르고, 수백 개가 쌓이면 사이트가 느려집니다. HTTP/2가 요청 비용을 낮췄다고는 해도 여전히 오버헤드는 존재하고, gzip 같은 압축 알고리즘도 작은 파일이 많으면 파일 하나 안에서만 반복 패턴을 찾을 수 있어 성능이 떨어집니다. 압축 사전(compression dictionary)이 도움이 되긴 하지만 근본적인 해결책은 아닙니다.</p>
<h3>요청 수냐 코드량이냐</h3>
<p>결국 남는 과제는 &quot;가능한 한 적은 다운로드 용량&quot;과 &quot;가능한 한 적은 요청 수&quot;를 동시에 만족시키는 것인데, 이 둘은 서로 충돌합니다. 청크 수를 줄이면 요청은 줄지만 재사용성이 떨어지고, 청크를 잘게 쪼개면 재사용성은 높아지지만 요청이 늘어납니다.</p>
<p>Turbopack의 해법은 작은 청크들을 더 큰 청크로 병합하되, <strong>어떤 청크를 언제 병합하는 것이 실제로 이득인지</strong>를 판단하는 것입니다. 이를 위해 &quot;청크 그룹(chunk group)&quot;이라는 개념이 필요합니다. 청크 그룹이란 함께 로드되는 청크들의 집합입니다. 예를 들어 <code>/home</code>이 쓰는 모든 청크는 하나의 그룹, <code>/blog</code>가 쓰는 청크들은 또 다른 그룹을 이룹니다. 한 청크가 두 그룹에 모두 속할 수도 있는데, 이런 경우 다른 청크와 병합하려면 같은 그룹 안에서만 안전합니다.</p>
<p>청크 그룹은 &quot;과도한 전송&quot; 문제를 해결해줍니다. Turbopack은 같은 그룹에 속한 청크끼리만 병합하는데, 한 그룹의 청크들은 어차피 항상 함께 로드되므로 병합한다고 해서 페이지가 원래 받지 않던 코드를 추가로 받게 되는 일은 없습니다.</p>
<h3>병합이 이득인지 판단하는 법</h3>
<p>문제는 &quot;요청 수를 줄이면서도 캐시 히트율을 어떻게 최적화할 것인가&quot;입니다. 이를 알아보기 위해 두 가지 방문 패턴을 생각해봅니다. 하나는 페이지 하나만 보고 떠나는 경우, 다른 하나는 페이지를 본 뒤 다른 페이지로 이동하는 경우입니다. (세 페이지 이상 방문하는 세션도 같은 방식으로 분석할 수 있습니다.)</p>
<p><code>&lt;Footer /&gt;</code>의 청크를 A, <code>&lt;VideoPlayer /&gt;</code>의 청크를 B라고 해봅시다. A는 모든 페이지에서 쓰이고, B는 홈페이지에서만 쓰입니다. 둘 다 홈페이지의 청크 그룹에 속하므로 병합 후보가 됩니다.</p>
<p>방문자가 홈페이지만 보고 떠난다면 병합은 항상 이득입니다. 어차피 둘 다 필요했던 코드이니 요청이 2개에서 1개로 줄어듭니다.</p>
<p>두 번째 페이지로 이동하는 경우엔 그 페이지가 A와 B를 둘 다 필요로 하는지가 관건입니다. 예를 들어 홈페이지에서 법적 고지 페이지로 이동했다고 하면, 법적 고지 페이지는 A만 필요하고 B는 필요 없습니다. A와 B가 하나의 파일로 합쳐진 상태라면 그 합쳐진 파일은 이 페이지에서 쓸모가 없으니, 브라우저는 A를 단독으로 다시 받아야 합니다. 결과적으로 방문자는 A를 두 번 다운로드하게 됩니다.</p>
<p>병합이 네비게이션 전체에 걸쳐 이득을 보려면 두 페이지 모두 A와 B를 함께 필요로 해야 합니다. 그래야 합쳐진 파일이 재사용되고 요청 하나를 절약하게 됩니다.</p>
<p>가능한 2페이지 세션 시나리오를 정리하면 다음과 같습니다(첫 페이지가 필요로 하는 것 → 두 번째 페이지가 필요로 하는 것). A와 B를 병합했을 때 전체 요청 수와 다운로드 코드량이 어떻게 바뀌는지 나타냅니다.</p>

<p>A와 B의 병합 여부를 판단할 때는 A만 쓰는 청크 그룹, B만 쓰는 청크 그룹, A+B를 함께 쓰는 청크 그룹의 수를 각각 계산하고, 각 시나리오의 발생 확률로 병합의 비용/이득에 가중치를 매깁니다. 마지막으로 단일 페이지 방문과 2페이지 이상 방문의 비율도 확률로 가중합니다. Turbopack은 세션의 2/3가 단일 페이지 방문, 1/3이 2페이지 이상 방문이라고 추정합니다.</p>

<p>이 분석을 검증하기 위해 nextjs.org를 대상으로 세 가지 Turbopack 청킹 설정(병합 없음 / 기본값 / 그룹당 하나로 전부 병합)에서 동일한 네비게이션 시퀀스를 수행하고, 요청 수와 클라이언트 측 JavaScript 다운로드량을 측정했습니다.</p>

<p>청킹이 저울질의 영역이라는 걸 숫자로 확인할 수 있습니다. nextjs.org에서 Turbopack 기본값은 병합 없음 대비 요청 수를 절반 이하로 줄이면서도 다운로드 코드량은 오히려 소폭 줄였습니다. 최대 병합(그룹당 1청크)은 요청 수를 더 줄였지만 전체 코드량은 10% 더 많이 받아야 했습니다. 다만 네비게이션 횟수가 더 적었다면 최대 병합 쪽이 더 유리했을 겁니다. 그룹 전체를 하나의 큰 청크로 합치는 전략은 초기 페이지 로드에서는 이득이지만, 장기적인 탐색 과정에서는 비용이 더 컸습니다.</p>
<h3>Next.js 16.3의 새 청킹 기능</h3>
<p>청킹의 효율을 가로막는 한계는 두 가지입니다. 첫째, 병합은 빌드 타임에 결정되기 때문에 실제 방문자가 브라우저에 이미 무엇을 캐시해뒀는지 알 수 없습니다. 둘째, 알고리즘은 방문자가 사이트를 어떻게 돌아다닐지 추측에 의존해야 하는데, 그래서 단일 페이지 방문에 2/3라는 가중치를 쓰는 겁니다. 이번 인턴십에서는 이 두 가지 한계를 개선하는 작업과, 애초에 청크에 담기는 코드량 자체를 줄이는 작업을 함께 진행했습니다.</p>
<h4>더 똑똑한 청크 페칭</h4>
<p>앞서 본 표에서처럼, 병합된 청크가 로드된 뒤 방문자가 A만 필요한 페이지에서 A+B만 필요한 페이지로 이동하면 A를 두 번 다운로드하는 비용이 발생합니다. 번들러는 빌드 타임에 브라우저가 무엇을 이미 갖고 있는지 알 수 없지만, 런타임은 알 수 있습니다.</p>
<p>Next.js 16.3 이상에서 <code>next.config.js</code>에 <code>experimental.turbopackChunking.generateComponentChunks</code>를 활성화하면, Turbopack은 병합된 청크와 함께 병합되지 않은 버전도 함께 생성합니다. 각 병합 청크를 구성하는 개별 항목과 그중 이미 로드된 항목을 추적하기 때문에, 요청 시점에 &quot;병합된 청크&quot;와 &quot;빠진 부분만 따로&quot; 중 더 저렴한 쪽을 선택할 수 있습니다. 반대의 경우도 마찬가지입니다. 방문자가 이미 병합된 A+B를 로드한 상태라면 A를 단독으로 다시 로드하는 걸 건너뛸 수 있습니다. 결과적으로 소프트 네비게이션(soft navigation)에서 불필요한 코드를 덜 로드하면서도 병합의 이점은 그대로 누릴 수 있습니다.</p>
<p>또한 방문자가 사이트를 떠났다가 나중에 다시 방문할 때도 같은 이점을 적용하기 위해 <code>only-if-cached</code> 지시자를 활용하는 실험도 진행 중입니다. 이를 통해 방문자가 도착했을 때 무엇이 캐시되어 있는지 확인할 수 있게 됩니다.</p>
<h4>애널리틱스 기반 청킹</h4>
<p>청킹 알고리즘에는 사이트에 대한 여러 가정이 깔려 있습니다. 예를 들어 2/3이라는 가중치는 어디까지나 추정치입니다. 많은 사이트에 걸쳐서는 합리적인 기본값이지만, 특정 사이트에 꼭 맞는 값은 아닙니다. 만약 자신의 사이트에서 사람들이 실제로 어떻게 이동하는지 알고 있다면, 이를 직접 설정할 수 있습니다. <code>next.config.js</code>의 <code>experimental.turbopackChunking</code> 아래에 다음 옵션을 설정할 수 있습니다.</p>
<ul>
<li><strong><code>firstPageLoadPriority</code></strong>: 단일 페이지 방문과 2페이지 이상 방문 사이의 가중치를 조정합니다. 0~1 사이 값으로, 값이 클수록 네비게이션 비용을 감수하고서라도 초기 로드 속도를 우선시합니다. 사이트의 바운스율(bounce rate)이 합리적인 출발점이 될 수 있습니다. 기본값은 0.67입니다.</li>
<li><strong><code>priorityRoutes</code></strong>: 로드 속도가 특히 중요한 페이지 목록입니다. 이 경로에서는 청크를 더 적극적으로 병합합니다.</li>
<li><strong><code>clusters</code></strong>: 정규식 배열로 정의된, 함께 자주 방문되는 경로들의 그룹입니다. 클러스터 내부에서는 겹치는 청크를 더 적극적으로 병합합니다. 단, 클러스터 안에 A만 쓰는 페이지나 B만 쓰는 페이지가 A+B를 함께 쓰는 페이지와 섞여 있으면 병합을 덜 하게 됩니다.</li>
</ul>
<h4>더 작고 더 적은 청크</h4>
<p>지금까지는 코드를 &quot;어떻게 묶을지&quot;에 관한 이야기였다면, 마지막은 애초에 &quot;얼마나 적게 보낼지&quot;에 관한 기능들입니다.</p>
<ul>
<li><strong>CJS 모듈 트리쉐이킹</strong>: 기존에는 ESM 모듈에만 트리쉐이킹을 지원해서, CJS 모듈 안의 쓰지 않는 import/export도 그대로 클라이언트에 전송되고 있었습니다. <code>experimental.turbopackCjsTreeShaking</code>으로 활성화할 수 있으며, 향후 Next.js 버전에서는 기본으로 켜질 예정입니다. 더불어 분석·트리쉐이킹 가능한 ESM 모듈의 범위도 넓혔는데, 동적 import 안의 배럴 파일(barrel file) 지원 개선도 포함됩니다.</li>
<li><strong>공유 Turbopack 런타임</strong>: 페이지마다 따로 있던 런타임 청크를 하나의 공유 런타임 청크로 대체합니다. <code>experimental.turbopackSharedRuntime</code>으로 활성화할 수 있으며, 첫 로드 이후의 모든 네비게이션에서 블로킹 요청 하나와 약 10KB의 클라이언트 측 JavaScript를 절약합니다. 이 기능도 추후 기본으로 켜질 예정입니다.</li>
<li><strong>더 가벼운 기본 런타임</strong>: 런타임이 기본적으로 WebAssembly와 Web Worker 코드를 포함하지 않도록 바뀌었습니다. 대신 해당 모듈을 실제로 사용하는 경우를 감지해서 그때 로딩 코드를 삽입합니다.</li>
</ul>
<p>이 기능들은 Next.js 16.3 이상에서 사용해볼 수 있습니다.</p>
<h3>정리</h3>
<ul>
<li>청킹은 &quot;요청 수를 줄이는 것&quot;과 &quot;다운로드 코드량을 줄이는 것&quot;이 서로 충돌하는 트레이드오프 문제입니다. 하나의 청크로 합치면 캐시 재사용률은 높지만 과도한 전송이 발생하고, 모듈 단위로 쪼개면 전송량은 최소화되지만 요청 수가 폭증합니다.</li>
<li>Turbopack은 &quot;청크 그룹&quot; 단위로만 병합을 허용해 과도한 전송을 막고, 방문 시나리오(단일 페이지 vs 다중 페이지 네비게이션)별 확률 가중치로 병합 이득을 계산합니다. 실측 결과 기본 설정은 병합 없음 대비 요청 수를 절반 이하로 줄이면서 코드량도 비슷하거나 더 적었지만, 최대 병합은 요청은 더 줄여도 코드량이 10% 늘었습니다.</li>
<li>Next.js 16.3부터는 <code>generateComponentChunks</code>로 런타임에 이미 캐시된 조각만 골라 받을 수 있고, <code>firstPageLoadPriority</code>/<code>priorityRoutes</code>/<code>clusters</code> 설정으로 실제 사이트의 방문 패턴에 맞춰 청킹 전략을 튜닝할 수 있습니다.</li>
<li>CJS 트리쉐이킹, 공유 런타임, 가벼운 기본 런타임 등은 청크 구성 전략과 별개로 전송되는 코드 자체의 절대량을 줄여주는 보완 기능입니다.</li>
<li>실무에서는 <code>next.config.js</code>에 이 experimental 옵션들을 켜보고, 자사 사이트의 실제 바운스율과 네비게이션 패턴을 반영해 <code>firstPageLoadPriority</code>나 <code>clusters</code>를 튜닝하면 기본값보다 더 나은 성능을 끌어낼 수 있습니다.</li>
