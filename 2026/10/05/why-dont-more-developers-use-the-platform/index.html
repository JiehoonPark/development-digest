왜 더 많은 개발자들은 "플랫폼을 쓰지" 않을까

Why don't more developers “use the platform”?

📅 2026-10-05📰 Hacker News (Top)
frontend

웹 표준, 성능, 접근성을 옹호하는 사람들은 오랫동안 "플랫폼을 써라(use the platform)"고 외쳐왔습니다. 저 역시 그런 옹호자 중 한 명이었고요. 그런데 이 말이 그렇게나 당연하다면, 왜 아직도 이렇게 많은 사람들을 설득해야 할까요? 이 글에서는 일부러 반대편 입장에 서서, 플랫폼 회의론자 개발자들이 어디서 오는지를 이해해보려 합니다.

"플랫폼을 써라"는 왜 이렇게 당연해 보이는가

논리는 단순합니다. 브라우저가 알아서 해줄 수 있는 걸 왜 굳이 JavaScript로 직접 만드나요? 직접 만든 결과물은 브라우저가 기본으로 제공하는 것보다 성능도, 사용성도 떨어질 가능성이 큽니다. 이 주장 자체는 반박하기 어렵습니다. 그런데도 왜 이렇게 많은 개발자가 직접 만드는 쪽을 택할까요.

역사적 관성과 습관의 문제

가장 뻔한 이유는 역사적인 배경입니다. 오랫동안 브라우저는 생태계를 뒤쫓아가는 입장이었습니다. jQuery 같은 라이브러리들은 브라우저가 동등한 API를 구현할 때까지의 공백을 메웠고, 설령 API가 나와도 IE6 같은 느림보가 퇴장할 때까지 기다려야 실제로 쓸 수 있었습니다. 오늘날 대부분의 브라우저는 에버그린이지만(Safari는 논란의 여지가 있지만, 그래도 1년에 7번 정도 업데이트되니 나쁘지 않습니다), 2020년대 이전까지 웹 개발자들은 상당히 울퉁불퉁한 웹 환경에서 일해야 했습니다. 그런 환경에서는 직접 만드는 게 합리적인 선택이었죠.

또 다른 이유는 익숙함입니다. React 컴포넌트를 npm에서 찾는 데 익숙해지면, 문제가 뭐든 간에 일단 npm부터 뒤지게 됩니다. npm에서 "sticky positioning"을 검색해봐도 "그냥 CSS position: sticky 쓰세요, 이 양반아"라고 말해주는 패키지는 없으니까요.

React 생태계가 만든 역할 분담

견고한 표준이 있어도, npm 라이브러리는 프레임워크의 편의성과 그 아래의 플랫폼 사이의 유용한 간극을 메워주곤 했습니다. 흥미로운 점은, 많은 React 개발자들이 JSX와 React의 관용구에만 머무르려 하고 날것의 DOM API는 "찝찝하다"고 느끼면서도, 내부적으로 날것의 DOM 조작을 하는 저수준 라이브러리는 아무렇지 않게 쓴다는 겁니다. 예를 들어 가상 리스트(virtual list) 라이브러리는 순수한 성능을 위해 날것의 DOM API를 적극 활용하면서, 초보 React 개발자도 쉽게 이해할 수 있는 고수준 프리미티브를 겉으로 노출합니다. 결국 React 컴포넌트 생태계는 자연스러운 역할 분담을 만들어냈습니다. 전문성이 있는 사람들이 낯선 플랫폼 API를 익숙한 형태로 포장해주는 식으로요.

문서화의 차이

이 현상은 문서화에서도 영향을 받았습니다. npm 패키지들은 공들여 작성한 README나, 예제·튜토리얼·스크린샷이 가득한 웹사이트를 갖춘 경우가 많습니다. 반면 MDN이 웹 문서의 표준 출처로 자리 잡기 전까지(그리고 Google의 좀 더 미래지향적인 보조 채널인 web.dev가 나오기 전까지), 웹 플랫폼 문서는 블로그, StackOverflow, CSS Tricks 같은 사이트에 흩어져 있었습니다. 그리고 이런 사이트들 상당수가 그냥 jQuery나 GreenSock 같은 유명 라이브러리를 쓰라고 안내했습니다! 실제로 Dragula 사이트와 MDN의 Drag and Drop 페이지를 비교해보면, 지금도 전자가 더 매력적으로 보일 정도입니다.

서드파티 vs 플랫폼, 그 이상의 문제

하지만 단순히 서드파티 라이브러리 대 플랫폼 API의 문제라면, "플랫폼을 써라"에 대한 반감을 완전히 설명할 수 없습니다. 게으른 개발자들(동어반복이긴 하지만)은 해결책이 npm에서 왔든, 브라우저에서 왔든, 누군가의 GitHub Gist에서 복사해온 것이든 신경 쓰지 않습니다. 그냥 문제를 풀고 넘어가고 싶을 뿐이죠. 제가 정말 짚고 싶은 건 "플랫폼 반대" 정서의 또 다른 근원입니다.

직접 만드는 게 더 재밌다는 사실

어떤 유형의 개발자에게는 직접 만드는 것 자체가 더 재밌습니다. 그리고 결과물도 오히려 이해하기 쉬울 때가 많습니다. 특히 웹 플랫폼에 대한 백과사전적 지식이 없다면요. 뭔가를 한번 만들고 나면 일종의 이케아 효과(IKEA effect)도 생깁니다. 자기가 손수 만든 코드를 계속 유지보수하고 만지작거리고 싶어지는 거죠.

모달 다이얼로그를 만든다고 생각해봅시다. 시각적으로는 어떻게 동작해야 하는지 대략 알고 있죠. 화면에 콘텐츠가 뜨고, 배경은 일부 가려진 채 여전히 보이고, 바깥을 클릭하면 닫힐 수도 있고요. 그래서 position: absolute와 z-index로 위치를 잡아봅니다. 아, 그런데 배경이 여전히 스크롤되네요. body의 overflow를 꺼야 합니다. 그리고 접근성을 좀 안다면, Esc 키로 닫히게 해야 하고, 포커스 트랩(focus trap)을 만들어야 하고, 다이얼로그를 연 요소로 포커스를 되돌려야 한다는 걸 깨닫게 됩니다...

많은 개발자에게 이건 악몽처럼 들립니다(그리고 절반만 동작하는 걸 만드는 지름길이기도 하고요). 하지만 많은 개발자에게는 이게 재밌는 일입니다! 이걸 만들면서 얼마나 많이 배우는지 생각해보세요. 애니메이션, 테마, 선택적 "닫기" 버튼 같은 걸 추가하며 자기만의 스타일을 입힐 수도 있고요. 어느새 npm에 올릴 준비가 된 라이브러리 하나를 완성하게 됩니다. 그냥 <dialog>를 가져다 쓰고 끝내는 것보다 훨씬 재밌는 일이죠. 그렇게 끝내버리면 얼마나 허탈한가요!

<dialog> 같은 API가 나오기 전까지, 많은 사람들에게는 이런 방식이 웹 플랫폼을 배우는 과정이었습니다. 지금 "플랫폼을 써라"를 옹호하는 사람들 중 상당수가 과거에는 폴리필, 심(shim), 라이브러리의 저자였습니다. 저도 그중 한 명입니다! 저는 PouchDB 작업을 하며 IndexedDB, WebSQL 등 브라우저 스토리지 API용 툴링을 몇 년간 만들었고, 그 과정에서 자신감을 얻어 결국 W3C 표준 회의에 참석하고, IndexedDB 스펙 자체에 이슈와 풀 리퀘스트까지 올리게 됐습니다. 플랫폼에 빈틈이 있고 그걸 메워야 한다는 강제적인 동기가 없었다면, 그 정도 전문성에 이를 만한 관심이나 동기를 찾지 못했을 겁니다.

때로는 단순한 무지일 뿐

물론 직접 만드는 게 항상 좋은 것만은 아닙니다. 때로는 순전히 무지에서 비롯되기도 합니다. 웹 플랫폼에서 CSS로 더 잘 풀 수 있는 문제를 JavaScript로 해결하는 사례가 그렇게 많았던 이유 중 하나는, 많은 개발자가 CSS가 실제로 어떻게 동작하는지 깊이 이해하는 데 시간을 들이지 않았기 때문이라고 생각합니다.

물론 공평하게 말하면 CSS는 역사적으로 이해하기 어려웠습니다. 사이트 이름이 "CSS Tricks"인 데는 이유가 있죠. clear fix, float, min-width: 0 트릭 같은 것들은 전혀 직관적이지 않습니다. CSS의 내부 알고리즘을 이해하려 애쓰기보다는, 원하는 명령형 로직을 상상한 뒤 JavaScript로 표현하는 게 훨씬 쉬울 때가 많습니다. 게다가 오랫동안 CSS는 line clamping, textarea 리사이징, 스크롤바 숨기기 같은 흔한 패턴을 표현할 직관적인 방법이 없었습니다. 그러니 개발자들이 이미 알고 있는 도구로 직접 만든 건 당연한 일이었습니다.

웹에만 국한된 이야기가 아니다

저는 이 "플랫폼 회피" 현상이 웹에만 국한된다고 생각하지 않습니다. 완전히 이해하지 못한 플랫폼 위에서 일하는 모든 개발자에게 적용될 수 있습니다. 예를 들어 제가 일하는 회사에서는 다양한 분석 데이터를 저장하는 데 ClickHouse를 씁니다. 한번은 동료와 대용량 JSON 데이터를 컬럼에 저장하는 방식을 두고 의견이 갈렸습니다. 동료는 저장 전에 압축하는 시스템을 만들었고, 저는 데이터를 별도의 키-값 스토어에 넣고 ClickHouse에는 키만 넣자고 했습니다. 결과적으로 둘 다 틀렸습니다! ClickHouse는 데이터를 자동으로 압축하고, 컬럼형 데이터 저장소이기 때문에 그냥 ClickHouse에 맡기면 행(row) 전체에 걸쳐 오히려 더 나은 압축률을 얻을 수 있었습니다. 그리고 별도의 키-값 스토어는 컬럼형 SELECT가 이미 해주는 일을 어설프게 흉내 낸 것에 불과했고요.

저는 ClickHouse 문서를 꼼꼼히 읽고 직접 벤치마크를 작성해 가설을 검증한 뒤에야 이 사실을 깨달았습니다. 결국 우리가 플랫폼이 기본으로 제공하는 것보다 더 느리고 더 번거로운 걸 만들었다는 사실에 충격을 받았죠. JavaScript와 웹 플랫폼의 사례와 평행선을 이룬다는 걸 무시하기 어려웠습니다.

iOS나 Android 개발자든, 게임 엔진 위에서 작업하는 개발자든, 어떤 플랫폼 계층 위에서 일하는 개발자든 비슷한 경험이 있을 거라고 확신합니다. 노련한 시니어 엔지니어의 전형적인 이미지가 주니어의 복잡하게 꼬인 코드 더미를 단 한 줄로 바꿔버리는 사람인 데는 이유가 있습니다. 많이 알수록 시스템 전체가 어떻게 end-to-end로 동작하는지에 대한 지식을 활용해, 가능한 가장 작은 기여로 문제를 해결할 수 있고(그 결과 장기적인 유지보수 부담도 줄어듭니다).

AI 코딩은 이 현상을 어떻게 바꿀까

이 글 내내 AI 얘기를 꺼내지 않으려고 애썼습니다(지난 1년 동안 그 얘기는 지겹도록 했으니까요). 하지만 AI 코딩이 이 현상에 어떤 영향을 미칠지 궁금하지 않을 수 없습니다. 저는 낙관적인 전망과 비관적인 전망을 둘 다 가지고 있습니다.

낙관적인 전망: LLM은 작업 중인 플랫폼에 대해 백과사전적인 지식을 갖고 있기 때문에, 사용자가 모호한 영어로 요청한 경험을 구현하는 데 정확히 맞는 플랫폼 API를 고를 수 있습니다. 이 해법은 사용자 코드보다 더 빠르고 정확할 가능성이 높으므로, 철저한 테스트와 벤치마킹을 거친 에이전트는 이 방식을 선호하게 될 겁니다. 게다가 개발자가 직접 코드를 작성하지 않으니 "이케아 효과"도 사라집니다.

비관적인 전망: LLM은 코드를 중복 작성하는 걸 좋아하는 경향이 있습니다. 예를 들어 이미 존재하는 헬퍼 함수를 무시하고 똑같은 걸 또 만드는 식으로요. 이 때문에 플랫폼 관용구를 따르지 않는 커스텀 코드의 양이 폭증할 수 있습니다. 개발자들은 에이전트에게 충분히 테스트하거나 여러 대안을 시도해보라고 지시하지 않고 첫 초안을 그냥 커밋해버릴 것입니다. 그리고 에피사이클을 계속 덧붙이는 게 항상 가능하기 때문에, 애초에 존재할 필요도 없었던 과도하게 설계된 해법을 에이전트가 끝없이 개선해나갈 수도 있습니다.

제가 실제로 AI 코딩을 쓰면서 이 두 현상을 모두 목격했습니다. 모델과 코딩 도구가 발전할수록 낙관적인 결과 쪽으로 기울 거라 믿고 싶지만, 확신할 수는 없습니다.

정리

  • "플랫폼을 써라"는 성능과 사용성 측면에서 당연한 논리처럼 보이지만, 실제로는 역사적 관성(과거의 울퉁불퉁한 브라우저 환경), npm 중심의 습관, React 생태계의 역할 분담, 그리고 npm 패키지의 풍부한 문서화 같은 여러 요인이 겹쳐 "직접 만들기"를 더 매력적으로 만들어왔습니다.
  • 더 근본적인 이유는 재미와 학습입니다. 모달 다이얼로그를 처음부터 만들어보는 과정은 번거롭지만 동시에 많은 걸 배우게 해주고, 이렇게 만든 코드에는 일종의 애착(이케아 효과)이 생깁니다. 저자 본인도 PouchDB/IndexedDB 작업을 통해 이런 과정을 거쳐 W3C 표준 작업에까지 참여하게 됐습니다.
  • 하지만 직접 만드는 것이 항상 좋은 건 아닙니다. CSS나 ClickHouse 사례처럼, 플랫폼을 깊이 이해하지 않은 채 직접 구현하면 오히려 더 느리고 복잡한 결과물을 만들게 될 수 있습니다. 이는 웹에 국한되지 않고 모든 플랫폼 위에서 일하는 개발자에게 공통적으로 나타나는 현상입니다.
  • AI 코딩 시대에는 LLM의 백과사전적 지식이 "플랫폼 활용"을 촉진할 수도 있지만, 반대로 코드 중복과 검증 없는 커밋 습관이 플랫폼 비관용적 코드를 양산할 위험도 있습니다. 실무에서는 에이전트가 제안한 해법이 플랫폼 네이티브 API를 충분히 활용했는지, 그리고 실제로 벤치마크를 거쳤는지 검증하는 습관이 중요해질 것입니다.
