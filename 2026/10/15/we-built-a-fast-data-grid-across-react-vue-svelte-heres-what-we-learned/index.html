We built a fast data grid across React, Vue & Svelte – here's what we learned

📅 2026-10-15📰 Echo JS
frontend

SVAR는 데이터 그리드, Gantt 차트, 캘린더처럼 기능이 많고 복잡한 UI 컴포넌트를 만드는 팀입니다. 이들 컴포넌트는 공통적으로 "성능"이 생명인데요, 데이터셋이 아무리 커져도 빠르고 반응성 있게 동작해야 하기 때문입니다. 더 흥미로운 점은 이 팀이 같은 컴포넌트를 React, Svelte, Vue 세 가지 프레임워크로 동시에 만들어 배포한다는 것입니다. 보통의 프레임워크 비교 글이 한 프레임워크에 정통한 사람이 나머지 두 개는 문서만 훑어보고 쓰는 것과 달리, 이들은 세 프레임워크 모두에서 똑같이 고성능 컴포넌트를 만들어내야 했습니다. 다소 무모하지만 그만큼 통찰력 있는 경험이었다고 합니다.

이 글은 SVAR가 세 프레임워크에서 동일한 데이터 그리드 컴포넌트를 어떻게 구현했고, 성능을 끌어올리기 위해 무엇을 했는지를 공유합니다. 결론부터 말하자면, 빠른 데이터 그리드를 만들 때 비용이 많이 드는 부분은 거의 전적으로 프레임워크와 무관했고, 프레임워크마다 진짜로 차이가 나는 지점은 흔히 벌어지는 '프레임워크 전쟁'이 암시하는 것보다 훨씬 좁았습니다. 그래서 이 글은 의도적으로 승자를 가리지 않습니다.

프레임워크와 무관한 성능 문제

데이터 그리드는 이런 비교에 안성맞춤인 테스트 케이스입니다. 누구나 한 번쯤 만들어보거나 써본 적이 있고, UI 도구 중에서 게으른 엔지니어링을 가장 빨리 응징하는 컴포넌트이기도 합니다. 구조적으로는 단순하지만 동시에 다른 컴포넌트에서는 보기 드물 정도로 데이터 양이 많습니다. 1,000행은 평범한 수준이고 10,000행도 드물지 않으니, 처음부터 이를 염두에 두고 설계해야 합니다.

참고로 SVAR React DataGrid가 20만 행, 2만 열을 렌더링하는 데모를 보면 엄청난 수치인데도 그리드가 매끄럽게 처리하는 것을 확인할 수 있습니다.

반면 10,000개 행을 그냥 직접 렌더링하면 어떤 프레임워크든 똑같이 죽어버립니다(요즘 하드웨어가 워낙 빠르니 완전히 죽기보다는 심하게 느려지는 정도겠지만요). React, Vue, Svelte 모두 결국 브라우저에게 수십만 개의 DOM 노드를 만들고 배치하라고 요청하게 되고, 이 시점에서는 브라우저 자체가 병목이 되어 프레임워크의 차이가 거의 의미 없어집니다. 이 실패 지점이 곧 비용 서열의 최상단을 보여줍니다.

  • HTML을 생성하는 것은 어떤 프레임워크에서든 가장 느린 작업입니다.
  • JavaScript 연산은 저렴하지만, 컴포넌트 규모에서는 더 이상 공짜가 아닙니다.
  • 프레임워크 오버헤드(가상 DOM 대 컴파일된 DOM 조작)는 앞의 두 가지에 비하면 오차 범위 수준입니다.

이 순서를 이해하고 나면, 아래 소개할 구체적인 기법들이 대부분 자연스럽게 납득됩니다.

SVAR DataGrid의 공통 아키텍처

여기서는 React, Vue, Svelte 각각에서 프레임워크 네이티브처럼 동작하도록 데이터 그리드를 어떻게 설계했는지 다룹니다.

엔진과 통합 레이어

프레임워크 독립성은 설계할 가치가 충분합니다. SVAR의 그리드는 프레임워크에 종속되지 않는 코어(데이터 구조, 설정 정규화, 레이아웃 계산 등)와 프레임워크별로 얇게 붙는 통합 레이어로 나뉩니다.

어려운 작업은 모두 코어에서 이루어집니다. 통합 레이어는 코어의 상태를 각 프레임워크의 반응형 primitive로 변환해주는 역할만 하는데, 이 분리 덕분에 React, Vue, Svelte 세 버전을 동시에 유지보수하는 것이 현실적으로 가능해집니다.

꼭 세 프레임워크에 배포할 필요는 없습니다. React 앱 하나만 만들더라도 무거운 로직을 컴포넌트 밖에 두면 테스트하기 쉽고, 프로파일링하기 쉽고, 렌더 사이클에서 발생하는 예기치 못한 사고로부터도 자유로워집니다.

가상화는 기본값이다

모든 데이터를 렌더링하는 것은 선택지가 아니므로, 이 그리드는 (다른 SVAR 컴포넌트들처럼) 렌더링 가상화를 사용합니다. 컨테이너의 크기를 측정하고 화면에 보이는 행과 열만 렌더링하는 방식입니다.

동시에 전체 데이터셋이 렌더링된 것처럼 보이고 동작하도록 숨겨진 플레이스홀더를 그려둡니다. 스크롤이 발생하면 데이터 스토어에 새로 보여야 할 구간을 요청하고, 이를 React, Svelte, Vue의 일반적인 컴포넌트로 렌더링합니다.

세 프레임워크 중 어느 것도 이 작업을 위한 특별한 수단을 제공하지 않습니다. primitive도, 내장 헬퍼도 없습니다. 가상화는 순수한 DOM 엔지니어링이고, 이는 개발자의 몫입니다. 프레임워크의 역할은 개발자가 보여주기로 결정한 15개 행을 다시 렌더링하는 것뿐이고, 이 부분은 세 프레임워크 모두 잘 해냅니다.

하지만 가상화는 데이터를 렌더링하기도 전에 첫 번째 문제를 만듭니다. 어떤 행이 보이는지 알려면 컨테이너의 크기가 필요하고, 크기를 얻으려면 무언가를 렌더링해야 합니다. 이른바 닭과 달걀 문제입니다.

모든 프레임워크에서 통하는 패턴은 이렇습니다. 먼저 스타일이 적용된 빈 컨테이너를 렌더링하고, ResizeObserver를 붙인 다음, 첫 번째 0이 아닌 크기 값이 들어올 때까지 실제 데이터 렌더링을 미루는 것입니다. 컨테이너에 높이를 부여하는 CSS가 아직 로딩 중일 수 있기 때문에, 0은 충분히 정상적인 중간 상태입니다.

// React, but the same logic ports to Svelte and Vue as is
const [size, setSize] = useState({ height: 0 });
useEffect(() => {
  const element = viewportRef.current;
  if (!element) return;

  const observer = new ResizeObserver(
    ([entry]) => setSize({ height: entry.contentRect.height })
  );
  observer.observe(element);

  return () => observer.disconnect();
}, []);

if (!size.height) return null;
return render();

여기서 React만이 가진 무기가 하나 있는데, 바로 useLayoutEffect입니다. 이 훅은 DOM이 만들어진 후, 브라우저가 화면을 그리기 전에 실행되므로 컨테이너를 측정하고 상태를 업데이트한 뒤, 사용자가 처음 보는 프레임에 바로 보정된 결과를 반영할 수 있습니다.

// react only
const [size, setSize] = useState({ height: 0 });
useLayoutEffect(() => {
  const element = viewportRef.current;
  setSize({ height: element.offsetHeight });
});

if (!size.height) return null;
return render();

사람들은 useLayoutEffect를 발등을 찍기 쉬운 위험한 훅이라고 놀리곤 하는데, 대체로는 맞는 말입니다. 하지만 가상화된 컴포넌트의 초기 측정이야말로 이 훅이 제값을 하는 몇 안 되는 경우 중 하나입니다.

다만 솔직히 말하면, 실제로는 결국 ResizeObserver 방식으로 되돌아갑니다. useLayoutEffect 콜백 안에서도 레이아웃이 아직 준비되지 않은 경우가 많기 때문인데, 외부 스타일시트나 폰트, 이미지가 아직 로드되지 않아 크기가 확정되지 않았을 수 있기 때문입니다. 그래서 어차피 옵저버는 필요하고, useLayoutEffect는 이를 대체하는 수단이라기보다는 첫 프레임을 조금 더 빠르게 만드는 최적화 장치에 가깝습니다.

Svelte와 Vue에는 useLayoutEffect에 대응하는 개념이 없습니다. Svelte의 $effect.pre는 DOM이 업데이트되기 전에 실행되어 측정하기에는 너무 이르고, onMount와 tick()은 DOM이 존재한 후 실행되지만 거기서 가한 변경은 다음 프레임에 그려지므로 그냥 ResizeObserver를 쓰는 것과 별 차이가 없습니다.

Vue도 비슷하게 나뉩니다. onBeforeUpdate는 너무 이르고, onUpdated는 DOM을 볼 수 있지만 그 안에서의 변경은 다음 렌더링 프레임에 반영됩니다. 그러니 React의 실질적인 우위라고 할 수 있지만, 그 폭은 좁습니다. 다른 프레임워크들의 설계도 나름의 이유가 있으며, React가 이 훅을 갖게 된 것도 어느 정도는 자신의 렌더 사이클 방식 때문입니다.

SSR에 관한 짧은 이야기

가상화와 서버 사이드 렌더링은 정의상 충돌합니다. 서버는 사용자의 뷰포트에 어떤 행이 들어올지 알 수 없으므로, 올바른 구간을 렌더링할 수 없습니다. 하지만 실무에서 이 충돌이 체감되는 비용은 생각보다 크지 않습니다.

SSR은 주로 더 빠른 첫 페인트를 위해 존재하는데, 이는 가상화가 이미 나름의 방식으로 해결하고 있는 문제이고, SEO를 위해서도 쓰이지만 애초에 100,000행 중 15개만 렌더링하는 컴포넌트로는 SEO가 작동할 수 없습니다.

순수한 React나 Vue를 쓴다면 이 충돌을 체감할 일이 없습니다. 하지만 Next.js나 Nuxt를 쓰면 보통 하이드레이션 불일치 에러가 줄줄이 발생하는 형태로 드러납니다. 해결책은 놀랍도록 단순한데, 그리드를 클라이언트 전용 컴포넌트로 표시하면 에러가 사라집니다. 받아들이고 넘어가야 하는 트레이드오프인 셈입니다.

내부 로직: 메모이제이션과 파생 상태

이 부분을 설명하기 전에 한 가지 짚고 넘어갈 점이 있습니다. SVAR 컴포넌트는 폭넓은 사용자층을 위해 만들어지기 때문에, 모든 버전의 React에서 동작해야 합니다. 그래서 여전히 코드에 메모이제이션 지시어를 손으로 직접 넣고 있습니다. 만약 현대적인 코드베이스에서 React Compiler를 활성화할 수 있는 환경이라면, 컴파일러가 이 작업을 직접, 아마도 수작업보다 훨씬 더 잘 처리해 줄 것입니다. 그런 경우라면 아래의 useMemo 관련 내용은 무시해도 됩니다. 이는 유효한 기법이지만 React Compiler가 도입되면 사라질 기법이기 때문입니다.

React의 원래 성능 전략은 "HTML 렌더링은 느리고 JavaScript는 빠르니, 컴포넌트 코드를 다시 실행해도 괜찮다"는 것이었습니다. 단순한 버튼이라면 이 전략은 완벽하게 통합니다.

하지만 데이터 그리드는 렌더링하기 전에 데이터와 설정을 정규화하고, 레이아웃을 계산하고, 열의 기하학적 구조를 해석해야 합니다. Gantt 컴포넌트는 더 많은 계산을 필요로 합니다. 이 정도 규모에서는 렌더링할 때마다 모든 것을 다시 계산하는 것이 더 이상 괜찮지 않습니다.

useMemo와 useCallback이 React의 표준적인 해법이고, 복잡한 컴포넌트라면 가장 든든한 친구가 됩니다.

// React
const normalizedHeaders = useMemo(() => normalize(columns), [columns]);
const columnCount = normalizedHeaders.length;

Svelte는 같은 개념을 $derived로 표현합니다.

// Svelte
const normalizedHeaders = $derived(normalize(columns));
const columnCount = $derived(normalizedHeaders.length);

Vue는 computed를 씁니다.

// Vue
const normalizedHeaders = computed(() => normalize(columns));
const columnCount = computed(() => normalizedHeaders.value.length);

내부적으로 돌아가는 반응성 메커니즘은 완전히 다르지만, 사용법은 거의 다르지 않습니다. 세 프레임워크 모두 "입력값이 바뀔 때까지는 이 값을 보존한다"는 똑같이 저렴한 계약을 제공합니다.

실제로 그리드의 가상화 계산 로직(보이는 행 범위, 좌/우/중앙 열 분할, 전체 스크롤 높이)을 포팅할 때 useMemo, $derived.by, computed 사이를 거의 한 줄 한 줄 그대로 옮기는 수준이었습니다. 문법은 $x, x.value, 일반 값 사이를 오가지만 로직 자체는 그대로 포팅됩니다. 한 프레임워크를 알면 이 영역에서는 이미 나머지 두 개도 이해하는 셈입니다.

다만 이 유사함 속에 진짜 차이가 하나 숨어 있습니다. React는 의존성 배열을 직접 작성해야 합니다. 그리드의 renderRows 메모는 8개의 의존성을 나열하고 있는데, 하나라도 빠뜨리면 디버깅하기 끔찍한 상태가 된 그리드를 만나게 됩니다. Svelte와 Vue는 의존성을 자동으로 추적합니다.

React, Vue, Svelte의 기본 동작 방식이 만드는 차이

프레임워크의 기본 동작 방식을 이야기하자면, 컴포넌트 코드가 언제 실행되는지에 구조적인 차이가 있고, 이것이 모든 것을 좌우합니다. Svelte와 Vue는 컴포넌트의 설정(setup) 코드를 한 번만 실행합니다. React는 렌더링할 때마다 함수 본문 전체를 다시 실행합니다.

Svelte나 Vue에서 "데이터 스토어를 생성한다"는 그냥 평범한 한 줄의 문장입니다. React에서 같은 의도를 구현하려면 여러 관용구가 뒤섞입니다. 스토어를 위한 useMemo(() => new DataStore(...), []), 이벤트 버스 연결을 위한 null 체크가 딸린 useRef, 그리고 effect는 페인트 이후에 실행되어 첫 프레임에는 너무 늦기 때문에 useEffect 바깥에 두는 동기적인 첫 렌더 초기화 호출까지, 하나의 개념이 네 가지 관용구로 흩어집니다.

하지만 이 모델에는 반대급부도 있습니다. Svelte와 Vue는 컴포넌트의 설정 코드를 한 번만 실행하기 때문에, 반응성은 명시적으로 선택해서 적용하는 대상입니다. 즉 의도치 않은 재계산이 설계상 거의 발생하지 않습니다. 대신 위험은 다른 곳으로 옮겨가는데, 애초에 어떤 값을 반응형으로 만드는 것을 깜빡하면 조용히 절대 업데이트되지 않는 무언가를 그대로 배포해버릴 수 있습니다. 실무에서는 자동 의존성 추적과 린트 도구가 이런 경우 대부분을 잡아냅니다.

그러니 이건 우열의 문제가 아니라 트레이드오프의 문제입니다. React의 모델은 기본값이 더 위험하지만 완전히 명시적이라서 지금 무슨 일이 벌어지고 있는지 항상 볼 수 있습니다. Svelte와 Vue의 모델은 기본값이 더 안전하지만 가끔씩 예상치 못한 방식으로 발목을 잡습니다.

이 말이 모든 것을 useMemo로 감싸라는 뜻은 아닙니다. 대부분의 계산은 신경 쓸 필요가 없을 만큼 저렴합니다. 코드를 읽거나, 더 좋게는 프로파일링을 해서 무거운 부분을 찾아내고, 그 부분만 렌더링 사이에 보존하면 됩니다. 그게 이 작업의 전부입니다.

참고: 하나의 스토어, 세 개의 어댑터

SVAR 컴포넌트에서는 메모이제이션만으로는 충분하지 않았기 때문에, 프레임워크와 무관한 단일 반응형 스토어를 운영하고 이를 각 프레임워크의 primitive에 맞게 어댑터로 연결합니다.

Svelte는 $store 자동 구독이 적용된 진짜 svelte/store의 writable을 통해 이 스토어를 소비합니다. Vue는 작은 subscribe() 헬퍼를 통해 ref를 받습니다.

React는 훅을 받습니다. useStore(api, 'name')은 useState와 useEffect 안의 구독으로 구현되어 있습니다. React는 한 가지 추가 장치가 더 필요했는데, 바로 변경 카운터를 반환하는 useStoreWithCounter 훅입니다. 배열이 제자리에서(in place) 변경될 때는 참조 동등성 비교로는 변화를 감지할 수 없기 때문에, 이 카운터를 의존성으로 활용합니다.

단일 프레임워크만을 대상으로 한다면 이런 장치는 필요 없습니다. React와 Vue 모두 성숙한 외부 스토어 생태계를 갖고 있고, Svelte 5의 .svelte.js 상태 모듈은 정말로 훌륭한 네이티브 옵션입니다. 다만 SVAR의 경우 하나의 스토어가 세 개의 호스트를 모두 서비스해야 했기 때문에 이런 선택지를 쓸 수 없었습니다.

정리

SVAR 팀이 React, Vue, Svelte 세 프레임워크로 동일한 고성능 데이터 그리드를 만들며 얻은 결론은 명확합니다. 성능의 병목은 거의 항상 프레임워크 자체가 아니라, HTML을 얼마나 적게 그리느냐와 무거운 계산을 얼마나 잘 캐싱하느냐에 달려 있다는 것입니다.

  • 비용의 서열은 'HTML 생성 > JS 연산 > 프레임워크 오버헤드' 순이며, 이 순서를 이해하면 대부분의 최적화 기법이 자연스럽게 따라옵니다.
  • 가상화는 세 프레임워크 모두 전혀 지원해주지 않는 순수 DOM 엔지니어링 영역이며, 초기 크기 측정을 위한 ResizeObserver 패턴은 공통으로 필요합니다. 단, React의 useLayoutEffect는 첫 프레임 품질을 살짝 끌어올리는 좁지만 실질적인 우위입니다.
  • useMemo/$derived/computed는 문법만 다를 뿐 거의 동일한 계약을 제공하며, 로직을 거의 그대로 포팅할 수 있습니다. 차이는 React만 의존성 배열을 수동으로 관리해야 한다는 점입니다.
  • React는 렌더마다 함수 전체를 재실행하는 모델이라 명시적이지만 관용구가 늘어나고, Svelte/Vue는 설정 코드를 한 번만 실행하는 모델이라 기본적으로 안전하지만 반응성을 깜빡 빠뜨리는 위험이 있습니다.
