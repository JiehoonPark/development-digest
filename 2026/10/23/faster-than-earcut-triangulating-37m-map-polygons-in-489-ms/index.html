Faster than earcut: triangulating 3.7M map polygons in 489 ms

📅 2026-10-23📰 Hacker News (Top)
frontend

지도 렌더링 엔진에서 가장 많이 반복되는 작업 중 하나가 폴리곤을 삼각형으로 쪼개는 삼각분할(triangulation)입니다. GPU는 삼각형만 채울 수 있기 때문에, 건물·공원·주차장처럼 지도의 대부분을 차지하는 폴리곤은 렌더링 전에 반드시 삼각형들로 잘게 나눠야 합니다. 이 글은 지도 엔진 Globus의 개발팀이 자사의 삼각분할기를 earstrip이라는 작은 라이브러리로 공개하면서, 기존에 쓰던 constrained Delaunay 삼각분할기를 ear clipping(귀 자르기) 알고리즘으로 교체하고 단계별로 최적화해 나간 과정을 기록한 것입니다.

earstrip은 ISC 라이선스(널리 쓰이는 earcut과 동일한 라이선스)로 공개됐고, C++ 헤더 파일 하나와 npm에 올라간 WebAssembly 빌드로 구성되어 있습니다. API는 earcut과 동일한 인자를 받습니다. 성능은 C++ 환경에서 earcut.hpp보다 14% 빠르고, 브라우저에서는 earcut.js보다 1.4~2.1배 빠릅니다. 이 글은 그 결과에 도달하기까지의 과정을 다룹니다.

왜 Delaunay에서 Ear Clipping으로

바르샤바 시내 중심가 Śródmieście의 몇 개 블록을 예로 들면, 이 구역에는 331개의 폴리곤과 5,151개의 정점이 있고, 삼각분할을 마치면 4,514개의 삼각형이 됩니다. 이 팀이 제공하는 바르샤바 주변 마조프셰 주(Masovian Voivodeship) 전체 오프라인 지도의 줌 레벨 13에는 무려 374만 425개의 폴리곤이 있습니다. M4 Pro 한 코어 기준으로, 기존 엔진의 constrained Delaunay 삼각분할기는 이 전체를 처리하는 데 2.93초가 걸립니다. 이번 10월, 이 팀은 이를 ear clipping으로 교체했고, 이 글을 쓰기 위해 아이디어 하나당 커밋 하나씩 ear clipper를 다시 만들면서 374만 개 폴리곤에 대해 매 커밋마다 시간을 측정했습니다. 그래서 아래 각 섹션은 구체적인 수치로 끝납니다.

Delaunay 삼각분할이란

점 집합의 삼각분할이 Delaunay 조건을 만족한다는 것은, 어떤 삼각형이든 그 세 꼭짓점을 지나는 외접원 안에 다른 점이 들어있지 않다는 뜻입니다. 변을 공유하는 두 삼각형만 봐도 이 규칙이 어떻게 작동하는지 알 수 있습니다. 점 D가 A, B, C를 지나는 점선 원 바깥에 있는 동안은 공유 변이 AC로 유지됩니다. D를 원 안으로 밀어 넣으면 변은 BD로 뒤집히고, 다시 바깥으로 빼면 원래대로 돌아옵니다. 이 뒤집기(flip)는 국소적인 교정이며, 어떤 변도 뒤집히고 싶어 하지 않는 삼각분할이 바로 Delaunay 삼각분할입니다. 같은 점 집합을 삼각분할하는 여러 방법 중, Delaunay 삼각분할은 가장 작은 각을 최대로 만드는 방법입니다.

"Constrained(제약된)"라는 말은 원 규칙이 변을 뒤집으려 하더라도, 폴리곤 자신의 변은 삼각분할의 변으로 반드시 유지되어야 한다는 뜻입니다. 이 엔진의 삼각분할기는 정점을 하나씩 삽입합니다. 새로운 점마다 지금까지 만들어진 삼각형들을 가로질러 걸어가며 그 점이 속한 삼각형을 찾아 분할하고, 원 규칙이 다시 성립할 때까지 새 점 주변의 변들을 뒤집습니다. 이후 폴리곤의 변들을 강제로 끼워 넣고, 마지막에는 폴리곤 안쪽에 있으면서 구멍 바깥에 있는 삼각형만 남깁니다.

하지만 잘 생긴(well-shaped) 삼각형은 그 위에서 어떤 값을 보간하거나 시뮬레이션을 돌릴 때만 중요합니다. 단순히 색을 채우는 작업이라면 상관없습니다. GPU는 바늘처럼 가느다란 삼각형이든 통통한 삼각형이든 똑같이 정확하게 채웁니다. 그런데 Delaunay 알고리즘은 그다지 자를 필요도 없는 폴리곤에 많은 시간을 씁니다. 마조프셰 지역 폴리곤의 거의 절반인 180만 개가 정점 4개 이하입니다. 삼각형은 아예 자를 필요가 없고, 볼록 사각형은 삼각형 두 개면 끝인데도, Delaunay 코드는 이들 각각을 처음부터 다시 삼각분할하느라 419ms를 씁니다.

Ear(귀) 자르기의 원리

폴리곤의 귀(ear)란 한 번의 직선 절단으로 잘라낼 수 있는 모서리입니다. 연속된 세 정점 a, b, c를 생각해보면, b에서의 모서리가 볼록(convex)이고 폴리곤의 다른 부분이 삼각형 abc 안으로 파고들지 않는다면, 그 삼각형이 바로 귀입니다. 이걸 잘라내면 정점이 하나 줄어든 폴리곤이 남습니다. 1975년 Gary Meisters는 4개 이상의 정점을 가진 모든 단순 폴리곤에는 서로 겹치지 않는 귀가 적어도 2개 존재한다는 것을 증명했습니다. 따라서 항상 자를 수 있는 귀가 남아 있고, 정점이 n개인 폴리곤은 n − 2개의 삼각형으로 쪼개집니다.

알고리즘이 필요로 하는 것은 "이 모서리가 귀인가?"라는 테스트 하나뿐입니다. 가장 단순한 버전은 해당 모서리와 경계선의 다른 모든 정점을 비교합니다. cross는 모든 기하학 코드베이스에 등장하는 2×2 행렬식으로, 반시계 방향 경계선에서 c가 a에서 b로 가는 선의 왼쪽에 있으면 양수가 되며, 이는 곧 볼록한 모서리를 의미합니다.

static double cross(double ax, double ay, double bx, double by, double cx, double cy){ return (bx - ax) * (cy - ay) - (by - ay) * (cx - ax);}
bool isEar(uint32_t v) const{ const Node &b = _nodes[v]; const Node &a = _nodes[b.prev], &c = _nodes[b.next]; if (cross(a, b, c) <= 0) return false; for (uint32_t w = c.next; w != b.prev; w = _nodes[w].next) { const Node &p = _nodes[w]; if (cross(a.x, a.y, b.x, b.y, p.x, p.y) < 0 || cross(b.x, b.y, c.x, c.y, p.x, p.y) < 0 || cross(c.x, c.y, a.x, a.y, p.x, p.y) < 0) continue; if (!samePos(p, a) && !samePos(p, b) && !samePos(p, c)) return false; } return true;}

삼각형 변 위에 놓인 점도 내부에 있는 것으로 간주합니다. 귀가 나머지 경계선과 맞닿아 있다면, 그걸 잘라낸 폴리곤이 스스로와 맞닿게 되기 때문입니다. 유일한 예외는 점이 정확히 a, b, c 중 하나와 같은 위치에 있는 경우로, 이는 외곽선이 한 정점에서 자기 자신과 만나는 경우에 흔히 생깁니다. 구멍이 있는 폴리곤에서 이런 경우가 자주 발생합니다.

구멍(Holes) 처리하기

Ear clipping은 닫힌 경계선 하나에 대해서만 동작하는데, 마조프셰 지역 폴리곤 중 11,345개는 구멍(마당, 숲 속 공터 등)을 가지고 있습니다. 이를 처리하는 방법은 각 구멍을 잘라서 열고, 구멍의 한 정점에서 외곽 경계선의 한 정점으로 이어지는 "다리(bridge)"로 꿰매는 것입니다. 이 다리는 양 방향으로 한 번씩 걸어갑니다. 그러면 경계선은 바깥쪽을 돌다가 다리를 건너 구멍을 반대 방향으로 돈 다음 다시 돌아옵니다. 다리의 두 사본 사이에는 면적이 없으므로 폴리곤은 그대로지만, 이제 하나의 링(ring)이 됩니다.

다리는 어떤 것과도 교차하면 안 됩니다. David Eberly의 ear clipping 설명에는 안전한 다리를 찾는 깔끔한 방법이 나옵니다. 구멍에서 가장 오른쪽 정점 m을 잡고 오른쪽으로 광선을 쏩니다. 광선이 처음 맞닥뜨리는 변의 끝점 중 더 오른쪽에 있는 점을 P라 합니다. 삼각형 m, I, P(I는 교차점) 안에 경계선 정점이 하나도 없다면 다리 m–P는 안전합니다. 삼각형 안에 있는 정점이 여럿이면, Eberly의 방법은 그중 광선과 각도가 가장 가까운 것을 선택합니다. 구멍은 가장 오른쪽 것부터 다리를 놓기 때문에, 더 왼쪽에 있는 구멍은 이미 경계선의 일부가 된 다른 구멍에 다리를 놓을 수 있습니다.

지도 데이터는 여기에 두 가지 특수한 경우를 더합니다. 좌표가 타일 격자 위의 정수이기 때문에 격자선을 따라가는 광선이 정점을 정확히 관통하는 경우가 흔한데, 교차 테스트는 이런 정점을 그냥 지나쳐버립니다. 실제로 첫 번째 구현에서 바로 이 경우를 잘못 처리했습니다. 또한 지도 제작자들은 종종 외벽에 한 점에서 맞닿는 마당을 그리는데, 이런 구멍은 다리가 필요 없이 두 링이 공유 정점에서 그대로 이어집니다.

순진한 구현 (-1,812 ms)

구멍까지 처리한 첫 완성 버전은 경계선을 돌면서 위의 isEar로 모서리를 테스트하고, 귀를 찾을 때마다 잘라서 세 개의 인덱스로 삼각형을 기록합니다. 마조프셰 전체 폴리곤에 대해 1.12초가 걸리며, 이는 Delaunay보다 2.6배 빠른 수치입니다.

크기별로 보면, 순진한 ear clipping은 가장 큰 폴리곤 구간을 제외한 모든 구간에서 Delaunay보다 빠릅니다. 정점 257개 이상인 가장 큰 폴리곤 1,123개는 ear clipping으로 199ms, Delaunay로는 90ms가 걸립니다. 이런 큰 폴리곤에서는 귀 테스트 한 번이 수백 개 정점을 훑어야 하고, 폴리곤 하나에 수백 번의 테스트가 필요하므로 비용이 크기의 제곱에 비례해 커집니다. 이후 최적화는 전부 이 귀 테스트를 더 싸게 만들고, 덜 자주 실행되게 만드는 데 집중됩니다.

오목점만 검사하기 (-237 ms)

볼록한 모서리가 귀가 되지 못하게 막을 수 있는 정점이 어떤 것인지 생각해보면, 삼각형 안에 있는 정점 중 모서리에 가장 가까운 것을 봤을 때, 그 정점의 두 변은 삼각형의 변들과 교차할 수 없으므로 둘 다 모서리로부터 멀어지는 방향으로 뻗어 나가고, 폴리곤은 그 정점을 모서리 쪽에서 감싸게 됩니다. 즉 이 정점은 반사(reflex) 정점, 즉 오목점(dent)입니다. 따라서 삼각형 안에 무언가 있다면 그 안에는 반드시 오목점도 있으므로, 테스트는 오목점만 살펴보면 됩니다.

엔진은 오목점 목록을 관리합니다. 오목점은 이웃을 잘라서 자신이 볼록으로 바뀔 때 목록에서 빠지고, 볼록한 모서리는 절대 오목점으로 바뀌지 않으므로 이 목록은 줄어들기만 합니다. 테스트는 다음과 같이 바뀝니다.

bool isEar(uint32_t v) const{ const Node &b = _nodes[v]; if (b.reflex) return false; const Node &a = _nodes[b.prev], &c = _nodes[b.next]; for (uint32_t i = 0; i < _live; ++i) { const Item &p = _items[i]; if (p.node == b.prev || p.node == b.next) continue; if (cross(a.x, a.y, b.x, b.y, p.x, p.y) < 0 || cross(b.x, b.y, c.x, c.y, p.x, p.y) < 0 || cross(c.x, c.y, a.x, a.y, p.x, p.y) < 0) continue; if ((p.x != a.x || p.y != a.y) && (p.x != b.x || p.y != b.y) && (p.x != c.x || p.y != c.y)) return false; } return true;}

2,810만 번의 귀 테스트가 이제 3억 5,300만 개가 아니라 1억 8,500만 개의 점만 들여다보게 되고, 전체 소요 시간은 882ms로 줄어듭니다. 기대보다는 적게 줄었는데, 건물 외곽선에는 오목점이 생각보다 많기 때문입니다. 앞서 나온 아치형 건물 예시는 정점 27개 중 15개가 오목점입니다. 그리고 가장 작은 폴리곤들은 오히려 34ms에서 54ms로 느려졌는데, 삼각형이나 사각형 정도는 오목점과 나머지를 분류하는 비용이 원래 테스트보다 더 비싸기 때문입니다.

볼록 폴리곤 건너뛰기 (-2 ms)

오목점이 없는 폴리곤은 볼록 폴리곤이고, 볼록 폴리곤의 모든 모서리는 귀이므로 테스트 없이 바로 자를 수 있습니다. 이걸 판별하는 데는 주의가 필요합니다. "모든 모서리가 좌회전한다"는 조건만으로는 충분하지 않은데, 별 모양 폴리곤은 다섯 개 모서리 모두에서 좌회전하지만 중심을 두 번 돌기 때문에 볼록이 아닙니다(오각형은 5개 중 5개가 좌회전, x 방향 전환은 2회로 볼록인 반면, 별은 좌회전은 5개 중 5개지만 x 방향 전환이 4회로 볼록이 아닙니다).

엔진은 조건을 하나 더 추가합니다. 볼록한 링을 따라 걸으면 변들은 아래쪽에서는 오른쪽으로, 위쪽에서는 왼쪽으로 진행하므로, x 방향이 바뀌는 횟수는 정확히 두 번, 즉 가장 왼쪽과 가장 오른쪽 지점에서만 바뀝니다. 오각형은 이 조건을 통과하고, 별은 표시된 모서리들에서 네 번 방향이 바뀌어 일반적인 귀 테스트로 넘어갑니다. 이 두 카운트는 오목점을 표시하는 동일한 루프에서 함께 계산되므로 추가 비용이 거의 없습니다. 삼각형과 사각형은 이 루프보다 앞서 별도의 단축 경로를 거칩니다.

이 단축 경로는 2,810만 번의 귀 테스트 중 440만 번을 제거하지만, 이것들은 애초에 가장 저렴한 테스트들이었습니다(오목점이 없는 링은 스캔할 것이 없으므로). 그래서 전체 시간에는 거의 영향을 주지 않아 880ms에 머물지만, 정점 4개 이하의 폴리곤들은 오목점 분류로 잃었던 비용 일부를 되찾아 54ms에서 48ms로 줄어듭니다. 이 최적화는 다음 단계, 즉 볼록 링을 하나의 스트립으로 만드는 단계에서 더 중요해집니다.

스트립 쓰기 (-118 ms)

지금까지는 삼각형 하나당 인덱스 3개가 필요했습니다. 그런데 GPU는 삼각형 스트립(triangle strip)도 그릴 수 있는데, 여기서는 새로운 인덱스 하나가 자신과 앞선 두 인덱스로 이루어진 삼각형을 추가합니다. 볼록한 링은 지그재그로 가로지르면 하나의 스트립이 됩니다.

Ear clipper도 스트립을 쓸 수 있습니다. 귀를 하나 자르면 그 양쪽 이웃 모서리가 더 날카로워져 다음 귀의 유력한 후보가 되고, 그중 하나를 자르면 스트립은 인덱스 하나만큼 늘어납니다. 엔진은 이 이웃들을 먼저 시도하고, 귀가 남아있는 동안 양쪽 끝을 번갈아 가며 이어갑니다. 코드에서 잘린 정점의 이웃은 a와 b로 표현됩니다.

while (true) { if (sideA) { const uint32_t z = n[a].prev; _strips.push_back(n[z].index); unlink(a); a = z; } else { const uint32_t z = n[b].next; _strips.push_back(n[z].index); unlink(b); b = z; } count--; sideA = !sideA; if (count < 3 || !isEar(sideA ? a : b)) break;}
