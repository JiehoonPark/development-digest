13:T1d6b,<p>JPEG XL(.jxl) 이미지 포맷이 드디어 Chrome에 정식으로 안착했습니다. Chrome 155부터 디코딩을 지원하게 된 이번 변화는 단순한 포맷 추가를 넘어, 메모리 안전 언어인 Rust로 이미지 디코더를 새로 작성하면서 보안과 성능을 동시에 잡으려 한 흥미로운 시도이기도 합니다. Chrome 팀이 공개한 이번 발표를 바탕으로, JPEG XL 도입 배경과 기술적 구현, 그리고 이 과정에서 얻은 교훈을 정리해봤습니다.</p>
<h3>JPEG XL, 왜 지금 Chrome에 들어왔나</h3>
<p>JPEG XL은 웹 개발자와 사진가의 요구를 겨냥해 설계된 차세대 이미지 포맷입니다. 기존 JPEG 대비 30~50% 더 나은 압축률을 제공하면서도, 무손실 압축, HDR(High Dynamic Range) 내장 지원, JPEG를 손실 없이 트랜스코딩하는 기능까지 갖추고 있습니다.</p>
<p>Chrome 팀은 AVIF와 JPEG XL 둘 다 상황에 맞게 테스트해볼 것을 권장합니다. 다만 JPEG XL은 특히 다음과 같은 상황에서 강점을 보일 것으로 예상합니다.</p>
<ul>
<li>고충실도(high-fidelity) 압축이나 무손실 압축이 필요한 경우</li>
<li>사진 이미지를 다룰 때</li>
<li>점진적(progressive) 디코딩을 세밀하게 제어하고 싶은 경우</li>
</ul>
<p>즉 AVIF와 JPEG XL이 서로를 완전히 대체하는 관계라기보다는, 각자 유리한 사용 사례가 다른 상호 보완적 포맷으로 보는 편이 맞습니다.</p>
<h3>안전 최우선: Rust로 새로 작성한 디코더 jxl-rs</h3>
<p>이미지 디코더는 현대 웹 브라우저에서 가장 민감하고 많이 공격당하는 영역 중 하나입니다. 네트워크에서 바로 받아온, 신뢰할 수 없는 복잡한 바이너리 구조를 렌더링 프로세스 내부에서 직접 파싱하기 때문입니다. 실제로 C++처럼 메모리 안전성을 보장하지 않는 언어로 작성된 디코더들은 역사적으로 범위를 벗어난 읽기(out-of-bounds read), 힙 오버플로, use-after-free 같은 취약점에 반복적으로 노출되어 왔습니다.</p>
<p>Chrome의 보안 모델은 샌드박싱과 심층 방어(defense in depth), 그리고 &quot;둘의 규칙(rule of two)&quot;에 기반을 두고 있습니다. 하지만 샌드박싱은 어디까지나 2차 방어선일 뿐입니다. 근본적으로 보안 위험을 소스 단계에서 제거하기 위해 Chrome 팀은 <strong>jxl-rs</strong>라는, 순수 Rust로 작성된 JPEG XL 디코더를 새로 구현해 통합했습니다.</p>
<h3>안전성을 포기하지 않으면서 속도까지 잡기</h3>
<p>메모리 안전성은 물론 중요하지만, 기존의 안전하지 않은 최고 성능 구현체와 맞먹는 속도를 내지 못한다면 채택의 명분이 약해집니다. Chrome 팀은 &quot;성능 손실이 거의 없는 안전한 디코더&quot;와 &quot;성능은 뛰어나지만 안전하지 않은 디코더&quot; 사이의 선택이라면, 전자가 훨씬 자명한 선택지라고 강조합니다.</p>
<p>현대 코덱의 성능에서 핵심적인 부분은 기기의 SIMD 하드웨어를 얼마나 완전히 활용하느냐에 달려 있습니다. 이를 안전하게 구현하기 위해 Rust의 <code>target_feature_11</code> 기능을 안정화(stabilize)하는 작업이 선행되어야 했습니다. 이 기능 덕분에 <code>unsafe</code> 코드 없이도 SIMD 명령어를 사용할 수 있게 되었습니다.</p>
<p>다음 단계는 SIMD 추상화 레이어인 <code>jxl_simd</code>를 만드는 것이었습니다. 이는 원래 libjxl(JPEG XL의 C++ 레퍼런스 구현체)을 위해 개발된 C++ 라이브러리 Highway에서 영감을 받은 설계입니다. <code>target_feature_11</code>과 <code>jxl_simd</code>가 결합되면서, SIMD 기반 성능 최적화를 포기하지 않으면서도 <code>unsafe</code> 연산을 극소수의, 철저하게 검증된 지점으로 한정한 크로스플랫폼 라이브러리를 작성할 수 있었습니다.</p>
<p>jxl-rs의 성능 최적화는 libjxl의 최적화 기법을 그대로 계승합니다. 예를 들어 리전(region) 경계를 넘나드는 처리 단계를 위한 범용 처리 파이프라인을 두어, 데이터 복사를 최소화함으로써 하드웨어 성능을 최대로 끌어내는 방식입니다. Chrome 팀은 이러한 Rust 재구현체의 성능을 다양한 하드웨어 플랫폼에서 지속적으로 추적하기 위해 [jxl-rs 성능 대시보드](https://developer.chrome.com/blog/jpeg-xl-in-chrome)를 운영하고 있습니다.</p>
<p>검증 측면에서도 퍼징(fuzzing)과 AI 기반 코드 리뷰 등 최신 기법들을 총동원했는데, 그 결과 구현 전체 역사를 통틀어 단 한 건의 메모리 안전성 버그도 발견되지 않았다고 밝혔습니다. 이는 Rust가 메모리 안전성 측면에서 가져다주는 이점을 다시 한번 입증하는 사례로 평가됩니다.</p>
<h3>개발자 피드백과 Interop 프로젝트</h3>
<p>Chrome 팀은 버그 리포트, 설문조사, Developer Signals 프로젝트, Interop 프로젝트 등 다양한 채널을 통해 웹 개발자들의 피드백을 수집해왔습니다. JPEG XL을 Chrome에 도입하기로 한 결정 역시 이러한 채널을 통해 꾸준히 접수된 개발자들의 요청에 근거한 것입니다. 특히 Interop 프로세스에서 JPEG XL은 2026년을 포함해 이전부터 계속 인기 있는 제안 항목으로 꼽혀왔습니다.</p>
<p>브라우저 간 상호운용성을 담보하기 위해 Chrome 팀은 Interop 2026 JPEG XL 조사에 참여해, JPEG XL의 모든 기능에 대한 테스트 커버리지가 각 브라우저에 존재하는지, 그리고 Chrome이 해당 테스트들을 실제로 통과하는지 확인했습니다.</p>
<h3>정리</h3>
<ul>
<li>Chrome 155부터 JPEG XL(.jxl) 디코딩을 공식 지원합니다. JPEG 대비 30~50% 향상된 압축률, 무손실 압축, HDR 지원, JPEG 무손실 트랜스코딩이 핵심 특징입니다.</li>
<li>AVIF와 JPEG XL은 상호 대체재라기보다 보완 관계에 가깝습니다. 고충실도/무손실 압축, 사진 이미지, 점진적 디코딩이 중요한 경우 JPEG XL을 우선 검토해볼 만합니다.</li>
<li>이번 도입에서 가장 눈여겨볼 부분은 순수 Rust로 작성된 신규 디코더 <strong>jxl-rs</strong>입니다. 이미지 디코더라는 고위험 공격 표면을 소스 단계에서부터 안전하게 만들기 위한 선택이었습니다.</li>
<li><code>target_feature_11</code> 안정화와 <code>jxl_simd</code> 추상화 레이어를 통해 <code>unsafe</code> 코드 없이도 SIMD 최적화를 적용했고, libjxl의 성능 기법을 계승해 기존 C++ 구현체 수준의 속도를 확보했습니다.</li>
<li>퍼징과 AI 코드 리뷰를 거쳤음에도 구현 역사 전체에서 메모리 안전성 버그가 한 건도 발견되지 않아, Rust 채택의 효과를 실증적으로 보여준 사례가 되었습니다.</li>
<li>이번 결정은 Interop 프로젝트 등을 통해 누적된 개발자 피드백에 기반한 것으로, 표준화 과정에서 개발자 의견이 실제 브라우저 기능 도입으로 이어진 좋은 예시이기도 합니다.</li>
</ul>
