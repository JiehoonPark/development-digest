How Turbopack chunks your JavaScript

📅 2026-10-08📰 Next.js Blog
frontendtypescript

Next.js 앱을 빌드하면 네트워크 탭에 36wnellv-yn9q.js 같은 알 수 없는 이름의 JS 파일들이 잔뜩 나타납니다. 이 파일들이 바로 "청크(chunk)"인데, Turbopack이 어떤 기준으로 코드를 이렇게 쪼개는지, 그리고 Next.js 16.3에서 이 과정이 어떻게 더 똑똑해졌는지 Turbopack 팀 인턴 Sam Poder가 설명한 글을 정리합니다.

청크란 무엇인가

빌드된 JS 파일을 비압축해서 열어보면 이런 구조를 볼 수 있습니다.

(globalThis.TURBOPACK || (globalThis.TURBOPACK = [])).push([
  "object" == typeof document ? document.currentScript : void 0,
  7284,
  (e) => {
    "use strict";
    function r() {
      for (var e, r, o = 0, t = "", l = arguments.length; o < l; o++) {
        // ...
      }
      return t;
    }
    e.s(["clsx", 0, r, "default", 0, r]);
  },
  395264,
  (e) => {
    "use strict";
    var r = e.i(7284);
    let o = function () {
      // ...
    };
  },
]);
//# debugId=e60a5ad0-3ac6-bb3a-e12b-6130e99fb7a6

Next.js 앱 하나를 빌드하면 Turbopack은 이런 청크를 수십 개 생성합니다. 각 청크에는 내 코드, 의존하는 패키지, 그리고 이 모든 걸 엮어주는 런타임이 들어갑니다. "청킹(chunking)"이란 결국 어떤 코드를 어떤 청크에 담을지 결정하는 과정이고, 이 결정에는 다양한 방식과 트레이드오프가 존재합니다.

세 가지 극단적인 전략과 각각의 문제

가장 단순한 방법부터 살펴보겠습니다.

방법 1: 모든 코드를 하나의 청크에 담기

355개 모듈을 app.js 하나(1.09 MB)에 몰아넣고 모든 페이지에서 로드하는 방식입니다. 이러면 모든 페이지가 같은 청크를 공유하므로 첫 로드 이후에는 항상 캐시 히트입니다. 페이지 이동은 빨라지죠.

하지만 트레이드오프가 바로 보입니다. JS가 거의 필요 없는 페이지조차 다른 모든 페이지의 코드를 함께 내려받아야 합니다. 사이트가 커질수록 모든 페이지의 초기 로드가 점점 무거워집니다. 장기적으로 지속 가능한 방식이 아닙니다.

방법 2: 페이지당 하나의 청크

그럼 반대로 페이지별로 청크를 쪼개면 어떨까요? 같은 355개 모듈을 8개 청크(1.20 MB)로 나누되, 페이지 간 공유되는 코드는 필요한 모든 청크에 중복으로 포함됩니다. 이러면 과도한 코드 전송 문제는 없지만, 캐싱 효과를 잃습니다. 모든 페이지에 들어가는 <Footer />가 있다면, 방문자가 페이지 4개를 열 때마다 같은 Footer 코드를 네 번 내려받게 됩니다.

방법 3: 모듈당 하나의 청크

그래서 더 세밀하게, 모듈마다 독립된 청크를 만들면 어떨까 생각해볼 수 있습니다. 355개 모듈을 355개의 별도 청크(1.09 MB)로 나누면 과도한 전송은 전혀 없고, 공유 모듈도 딱 한 번만 다운로드됩니다.

문제는 작은 JS 파일 수백 개에 대해 네트워크 요청 수백 번이 발생한다는 점입니다. 각 요청에는 오버헤드가 따르고, 수백 개가 쌓이면 사이트 속도가 느려집니다. HTTP/2 덕분에 요청 비용이 줄었다고는 해도 여전히 공짜가 아니고, gzip 같은 압축 알고리즘도 파일 하나 안에서만 반복 패턴을 찾을 수 있기 때문에 작은 파일이 많을수록 압축 효율이 떨어집니다. 압축 사전(compression dictionary)이 도움이 되긴 하지만 이 문제를 근본적으로 해결하지는 못합니다.

적은 요청 수 vs 적은 코드량, 둘 중 하나는 포기해야 할까

결국 우리가 원하는 건 "가능한 한 적은 다운로드 용량"과 "가능한 한 적은 요청 수" 둘 다인데, 이 두 목표는 서로 충돌합니다. 청크를 크고 적게 만들면 요청은 줄지만 페이지 간 재사용성이 떨어지고, 반대로 잘게 쪼개면 재사용성은 높아지지만 요청이 늘어납니다.

Turbopack의 해법은 작은 청크들을 더 큰 청크로 병합하는 것입니다. 어려운 부분은 "어떤 청크를, 언제 병합하는 게 실제로 이득인지" 판단하는 것이죠.

이를 위해 "청크 그룹(chunk group)"이라는 개념을 도입합니다. 청크 그룹이란 함께 로드되는 청크들의 묶음입니다. 예를 들어 /home에서 쓰는 모든 청크는 한 그룹, /blog에서 쓰는 청크는 또 다른 그룹을 이룹니다. 어떤 청크는 두 그룹 모두에 속할 수도 있는데, 이런 경우 이웃 청크와 병합하는 건 같은 그룹 안에서만 안전합니다.

청크 그룹 개념은 과도한 전송 문제를 해결해줍니다. Turbopack은 같은 그룹에 속한 청크끼리만 병합하는데, 한 그룹의 청크들은 어차피 항상 함께 로드되므로 병합해도 페이지가 원래 받던 것 이상을 받게 되지는 않습니다.

캐시 히트율과 요청 수, 균형점 계산하기

그렇다면 요청 수를 늘리지 않으면서도 캐시 히트율을 최적화하려면 어떻게 해야 할까요? 방문자의 행동을 두 가지로 나눠 생각해봅니다. 하나는 페이지 하나만 보고 떠나는 경우, 다른 하나는 한 페이지를 보고 다른 페이지로 이동하는 경우입니다(세 페이지 이상의 세션도 같은 논리로 확장됩니다).

<Footer />의 청크(A)와 <VideoPlayer />의 청크(B)를 병합할지 말지 예로 들어보겠습니다. A는 모든 페이지에서 쓰이고 B는 홈페이지에서만 쓰입니다. 둘 다 홈페이지의 청크 그룹에 속하므로 병합 후보입니다.

방문자가 홈페이지를 보고 떠난다면 병합은 항상 이득입니다. 어차피 둘 다 필요했으니 요청 2번이 1번으로 줄어드는 것뿐이죠.

하지만 두 번째 페이지로 이동한다면 얘기가 달라집니다. 홈페이지에서 법적 고지 페이지로 넘어간다고 해봅시다. 법적 고지 페이지는 A만 필요하고 B는 필요 없습니다. A와 B가 하나의 파일로 병합되어 있으니 이 병합 파일은 여기서 쓸모가 없고, 브라우저는 A를 다시 단독으로 내려받아야 합니다. 결국 방문자는 A를 두 번 다운로드하게 됩니다.

즉 병합이 내비게이션 전반에서 이득을 보려면 두 페이지 모두 A와 B를 전부 필요로 해야 합니다. 그래야 병합된 파일이 재사용되고 요청을 아낄 수 있습니다.

가능한 2페이지 세션 시나리오를 정리하면 다음과 같습니다 (각 행은 "첫 페이지가 필요로 하는 것 → 두 번째 페이지가 필요로 하는 것", 수치는 A와 B를 병합했을 때 요청 수와 다운로드 코드량의 변화입니다).

A와 B의 병합 여부를 검토할 때는, A만 쓰는 청크 그룹, B만 쓰는 청크 그룹, A+B 둘 다 쓰는 청크 그룹의 개수를 계산하고 각 시나리오가 일어날 확률로 비용/이득에 가중치를 매깁니다. 마지막으로 1페이지 방문과 2페이지 방문의 확률도 가중치로 반영하는데, 전체 세션의 2/3는 1페이지 방문, 1/3은 2페이지 이상 방문으로 추정합니다.

결과를 보면 청킹은 역시 균형의 문제입니다. nextjs.org에서는 Turbopack 기본값이 병합 없는 경우 대비 요청 수를 절반 이하로 줄이면서도 코드량은 오히려 살짝 적었습니다. 최대 병합 전략은 요청 수를 더 줄였지만 전체 코드량은 10% 더 늘었습니다. 다만 내비게이션을 더 적게 했다면 최대 병합 전략이 더 유리했을 겁니다. 그룹 내 모든 청크를 하나의 큰 청크로 합치는 방식은 초기 페이지 로드에는 이득이지만 장기적으로는 비용이 더 컸습니다.

Next.js 16.3의 새로운 청킹 기능

기존 방식에는 두 가지 한계가 있었습니다. 첫째, 병합은 빌드 타임에 결정되기 때문에 실제 브라우저가 무엇을 캐시해두었는지에 반응할 수 없습니다. 둘째, 알고리즘은 사람들이 사이트를 어떻게 돌아다니는지 추측에 의존해야 하는데, 1페이지 방문에 2/3라는 가중치를 매기는 것도 결국 추정치입니다. Turbopack 팀 인턴십 기간 동안 저자는 이 두 문제, 그리고 애초에 청크에 담기는 코드량 자체를 줄이는 작업까지 진행했습니다.

더 똑똑한 청크 페칭

위 표가 보여준 병합의 대가는, A를 쓰는 페이지에 이어 A+B를 쓰는 페이지를 방문하면 A를 두 번 내려받게 된다는 점이었습니다. 번들러는 빌드 타임에 브라우저가 무엇을 이미 가지고 있는지 알 수 없으니 이 문제를 피할 수 없지만, 런타임은 알 수 있습니다.

Next.js 16.3 이상에서 next.config.js에 experimental.turbopackChunking.generateComponentChunks를 켜면, Turbopack은 병합된 청크와 함께 병합되지 않은 버전도 같이 생성합니다. 각 병합 청크를 구성하는 항목들과 그중 이미 로드된 항목을 추적해서, 요청 시점에 "병합된 청크 전체"와 "빠진 부분만" 중 더 저렴한 쪽을 선택할 수 있습니다.

반대 방향도 동작합니다. 방문자가 이미 병합된 A+B를 로드했다면, A를 단독으로 다시 로드할 필요 없이 그대로 넘어갑니다. 결과적으로 소프트 내비게이션에서 불필요한 코드 로드가 줄어들고, 병합의 이점은 유지하면서 내비게이션 비용은 피할 수 있게 됩니다. (글 원문에는 이 차이를 보여주는 데모 앱 링크가 포함되어 있습니다.)

또한 only-if-cached directive를 활용해 방문자가 사이트에 도착했을 때 이미 캐시해둔 것을 확인하는 방식도 실험 중입니다. 이게 적용되면 사이트를 떠났다가 나중에 다시 돌아오는 방문자에게도 동일한 이점을 확장할 수 있습니다.

분석 데이터 기반 청킹

청킹 알고리즘에는 여러 가정이 들어갑니다. 예를 들어 "1페이지 방문 2/3"이라는 가중치는 추정치일 뿐, 많은 사이트에 대체로 맞는 기본값이지 특정 사이트에 꼭 맞는 값은 아닙니다. 만약 자기 사이트 사용자들의 실제 이동 패턴을 안다면, 이제 그 정보를 Turbopack에 직접 알려줄 수 있습니다. next.config.js의 experimental.turbopackChunking 아래에 다음 옵션들을 설정하면 됩니다.

  • firstPageLoadPriority: 1페이지 방문과 2페이지 방문 사이의 가중치를 조정합니다. 0~1 사이 값이 높을수록 내비게이션 비용을 감수하더라도 초기 로드 속도를 우선합니다. 이탈률(bounce rate)을 기준값으로 쓰면 적절하며, 기본값은 0.67입니다.
  • priorityRoutes: 로드 속도가 특히 중요한 페이지 목록입니다. 해당 라우트에서는 청크를 더 적극적으로 병합합니다.
  • clusters: 정규식 배열로 정의하는, 함께 자주 방문되는 라우트 묶음입니다. 클러스터 내부에서는 겹치는 청크를 더 쉽게 병합하지만, 클러스터 안에 A만 쓰는 페이지나 B만 쓰는 페이지와 A+B를 모두 쓰는 페이지가 섞여 있으면 병합을 덜 적극적으로 합니다.

청크 자체를 더 작고 적게 만들기

지금까지는 코드를 "어떻게 그룹 짓느냐"의 문제였다면, 마지막 개선은 애초에 "얼마나 적게 담느냐"의 문제입니다. 다음 기능들이 여기 해당합니다.

  • CJS 모듈 트리 셰이킹: 기존에는 ESM 모듈에만 트리 셰이킹을 지원해서, CJS 모듈의 미사용 import/export가 그대로 클라이언트로 전송되고 있었습니다. experimental.turbopackCjsTreeShaking으로 활성화할 수 있으며, 향후 Next.js 버전에서는 기본으로 켜질 예정입니다. 더불어 ESM 모듈에서 분석·트리 셰이킹 가능한 범위도 확장했고, 동적 import 안의 배럴 파일(barrel file) 지원도 개선했습니다.
  • 공유 Turbopack 런타임: 페이지별로 따로 두던 런타임 청크를 하나의 공유 런타임으로 대체합니다. experimental.turbopackSharedRuntime으로 활성화하며, 첫 로드 이후의 모든 내비게이션에서 블로킹 요청 1개와 클라이언트 JS 약 10KB를 절약합니다. 이 기능 역시 추후 기본값이 될 예정입니다.
  • 더 가벼운 기본 런타임: 런타임이 더 이상 WebAssembly와 Web Worker 관련 코드를 기본으로 포함하지 않습니다. 실제로 해당 모듈을 사용할 때만 로딩 코드를 삽입합니다.

이 기능들은 Next.js 16.3 이상에서 사용할 수 있으며, 청킹(CSS 청킹 포함)의 트레이드오프와 제약에 대해 더 깊이 알고 싶다면 Tobias의 최근 발표를 참고하면 됩니다.

정리

  • 청킹에는 "코드를 하나로 뭉치기", "페이지별로 쪼개기", "모듈별로 쪼개기"라는 세 극단이 있지만 각각 과도한 전송, 캐시 무효화, 과도한 요청 수라는 문제를 안고 있습니다.
  • Turbopack은 "청크 그룹" 단위로만 병합을 수행해 과도한 전송을 막고, 1페이지/2페이지 방문 확률을 가중치로 삼아 병합 이득과 비용을 계산합니다.
  • nextjs.org 실측에서 Turbopack 기본 설정은 병합 없음 대비 요청 수를 거의 1/3로 줄이면서도 다운로드 코드량은 오히려 적었고, 완전 병합은 요청 수는 더 줄였지만 코드량은 10% 늘어났습니다. 즉 최적 전략은 사이트의 내비게이션 패턴에 따라 달라집니다.
  • Next.js 16.3부터는 generateComponentChunks로 런타임에 캐시 상태를 보고 병합/비병합 청크 중 더 저렴한 쪽을 선택할 수 있고, firstPageLoadPriority·priorityRoutes·clusters 설정으로 실제 사용자 행동 데이터를 청킹 알고리즘에 반영할 수 있습니다.
  • CJS 트리 셰이킹, 공유 런타임, 가벼운 기본 런타임 같은 기능으로 청크 자체의 용량도 줄어들었습니다. 실무에서는 next.config.js에서 이 실험적 플래그들을 켜보고 사이트별 트래픽 패턴에 맞게 튜닝해볼 만합니다.
