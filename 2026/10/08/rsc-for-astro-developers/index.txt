13:T40a7,<h2>Astro 개발자를 위한 RSC 입문기</h2>
<p>React Server Components(RSC)는 처음 접하면 낯설고 불친절하게 느껴지기 쉽습니다. 그런데 흥미롭게도 Astro를 사용해본 적이 있다면 이미 RSC의 핵심 멘탈 모델을 80%는 알고 있는 셈입니다. 이 글은 Dan Abramov가 Astro의 구조를 출발점 삼아 RSC의 개념을 설명한 내용을 정리한 것입니다.</p>
<h3>Astro의 두 가지 구성 요소</h3>
<p>Astro에는 근본적으로 두 가지 요소가 있습니다.</p>
<p><strong>Astro Components</strong>는 <code>.astro</code> 확장자를 가진 파일로, 서버 또는 빌드 시점에서만 실행됩니다. 즉 이 코드는 절대 클라이언트로 전송되지 않습니다. 그래서 파일 시스템을 읽거나, 내부 서비스를 호출하거나, 데이터베이스에 직접 접근하는 등 클라이언트 코드로는 할 수 없는 일을 할 수 있습니다. 대신 HTML 자체가 기본 제공하는 기능이나 직접 작성한 <code>&lt;script&gt;</code> 외에는 인터랙티브한 동작을 할 수 없습니다. Astro Component는 다른 Astro Component나 Client Island를 렌더링할 수 있습니다.</p>
<p><strong>Client Islands</strong>는 React, Vue 등으로 작성된 일반적인 프론트엔드 컴포넌트입니다. 인터랙티브한 부분을 담당하는 자리죠. Client Island는 같은 프레임워크의 메커니즘을 이용해 또 다른 Client Island를 렌더링할 수 있습니다. 하지만 거꾸로 Client Island에서 Astro Component를 렌더링하는 것은 불가능합니다. 그 시점에는 이미 Astro의 처리가 끝난 뒤이기 때문에 말이 안 되는 것이죠.</p>
<p>다음은 <code>LikeButton</code> Island를 렌더링하는 <code>PostPreview.astro</code> 예시입니다.</p>
<pre><code class="language-astro">---
import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';
const { slug } = Astro.props;
const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
---
&lt;article&gt;
&lt;h1&gt;{title}&lt;/h1&gt;
&lt;LikeButton client:load /&gt;
&lt;/article&gt;</code></pre>
<pre><code class="language-jsx">import { useState } from 'react';
export function LikeButton() {
const [liked, setLiked] = useState(false);
return (
&lt;button onClick={() =&gt; setLiked(!liked)}&gt;
{liked ? '❤️' : '🤍'} Like
&lt;/button&gt;
);
}</code></pre>
<p>여기서 주목할 점은 Astro Component와 Client Island가 본질적으로 서로 다른 &quot;세계&quot;에 살고 있고, 데이터는 오직 위에서 아래로만 흐른다는 것입니다. 모든 전처리는 Astro Component에서 일어나고, 인터랙티브한 부분은 Client Island에 &quot;넘겨주는&quot; 구조입니다.</p>
<h3>RSC로 같은 구조 표현하기</h3>
<p>RSC에서는 이 두 가지가 각각 Server Component와 Client Component로 불립니다. 위 Astro Component를 React Server Component로 작성하면 다음과 같습니다.</p>
<pre><code class="language-jsx">import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';
async function PostPreview({ slug }) {
const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
return (
&lt;article&gt;
&lt;h1&gt;{title}&lt;/h1&gt;
&lt;LikeButton /&gt;
&lt;/article&gt;
);
}</code></pre>
<pre><code class="language-jsx">'use client';
import { useState } from 'react';
export function LikeButton() {
const [liked, setLiked] = useState(false);
return (
&lt;button onClick={() =&gt; setLiked(!liked)}&gt;
{liked ? '❤️' : '🤍'} Like
&lt;/button&gt;
);
}</code></pre>
<p>두 모델 뒤에 있는 사고방식은 놀라울 정도로 비슷합니다. Astro를 알고 있다면 RSC의 멘탈 모델을 이미 대부분 이해하고 있는 셈입니다. (설령 RSC가 별로라고 생각하더라도 Astro는 배울 가치가 있습니다.)</p>
<h3>문법적 차이점</h3>
<p>몇 가지 눈에 띄는 차이가 있습니다.</p>
<p>Astro Component와 달리 React Server Component는 평범한 JavaScript 함수입니다. &quot;단일 파일&quot; 구조가 아니라서, props는 <code>Astro.props</code> 대신 함수 인자로 전달받고, 별도의 &quot;템플릿&quot; 영역도 없습니다.</p>
<p>Astro에서는 <code>.astro</code> 파일로 작성함으로써 Astro Component와 Client Island의 경계를 구분합니다. Client Island를 import하는 순간 더 이상 <code>.astro</code> 파일 안에 있지 않으므로 Astro 세계를 &quot;벗어나는&quot; 것이죠. RSC에서는 같은 역할을 <code>'use client'</code> 지시어가 수행합니다. 이 지시어는 서버 세계가 &quot;끝나는&quot; 지점을 표시하는, 두 세계 사이의 문과 같습니다.</p>
<p>Astro에는 <code>client:load</code> 같은 지시어가 있어서 Island를 정적 HTML로 취급할지, 클라이언트에서 하이드레이션할지를 선택할 수 있습니다. RSC는 이런 구분을 사용자 코드에 노출하지 않습니다. React 입장에서는 어떤 컴포넌트가 인터랙티브하도록 작성됐다면 그 인터랙티브함을 임의로 제거하는 것 자체가 잘못된 일입니다. 만약 정말로 인터랙티브함이 필요 없다면 그냥 <code>'use client'</code>를 지우면 됩니다. 그러면 서버 세계에서 import되는 순간 자동으로 서버 전용으로 남게 됩니다.</p>
<h3>핵심 차이: 경계가 고정되어 있는가, 유동적인가</h3>
<p>여기서부터가 흥미로운 지점입니다. Astro에서는 <code>.astro</code> 파일과 Client Island라는 서로 다른 문법이 두 세계 사이에 뚜렷하고 명확한 시각적 경계를 만듭니다. 같은 컴포넌트가 맥락에 따라 Astro Component도 됐다가 Client Island도 되는 일은 없습니다. 둘은 애초에 문법 자체가 다른, 별개의 존재이기 때문입니다.</p>
<p>하지만 RSC에서는 &quot;Astro에 해당하는 부분&quot;조차 &quot;그냥 React&quot;입니다. 그래서 클라이언트 전용 기능도, 서버 전용 기능도 쓰지 않는 컴포넌트가 있다면 그 컴포넌트는 양쪽 역할을 모두 할 수 있습니다.</p>
<p>예를 들어 자체적으로 파싱을 수행하는 <code>&lt;Markdown /&gt;</code> 컴포넌트를 생각해봅시다. State 같은 클라이언트 기능도, DB 조회 같은 서버 기능도 쓰지 않으니 어느 쪽에서든 import할 수 있습니다. 서버 세계에서 import하면 &quot;Astro Component&quot;처럼 동작하고, 클라이언트 세계에서 import하면 &quot;Client Island&quot;처럼 동작합니다. 이건 새로운 개념이 아니라 단순히 함수를 import하는 방식 그 자체일 뿐입니다.</p>
<p>RSC에서는 서버 세계에서 import된 것은 서버 세계에서 실행되고, 클라이언트 세계에서 import된 것은 클라이언트 세계에서 실행됩니다. 그리고 어느 쪽에서도 지원되지 않는 것(예: 클라이언트에서의 DB 접근, 서버에서의 <code>useState</code>)은 빌드 에러를 발생시켜서 <code>'use client'</code>로 &quot;문을 새로 뚫도록&quot; 강제합니다.</p>
<h3>축복이자 저주</h3>
<p>이 유동성은 축복이자 저주입니다.</p>
<p>저주인 이유는 RSC를 다루는 법을 배우기가 직관적이지 않기 때문입니다. &quot;지금 내가 어느 세계에 있는지&quot;를 계속 신경 쓰게 됩니다. 사실 이건 중요하지 않고 항상 지역적으로(locally) 추론할 수 있다는 것을 받아들이기까지 연습이 필요합니다. DB 같은 서버 기능이 필요한 파일에서는 그걸 쓰고, State 같은 클라이언트 기능이 필요한 파일에서는 그걸 쓰면서, 뭔가 잘못되면 빌드 타임 검증이 에러를 내준다는 것에 의존하면 됩니다. 그다음 모듈 스택 트레이스를 보고 &quot;섬&quot;을 어디에 새로 만들지 결정하면 되는 것이죠.</p>
<p>저주이지만 동시에 축복이기도 합니다. 양쪽 모두에서 React를 그대로 활용함으로써, RSC 모델은 Astro에서 마주칠 수 있는 몇 가지 한계를 해결합니다.</p>
<ul>
<li><strong>경계를 옮기기 쉬움</strong>: Astro Component 여러 개를 작성했다가 나중에 그 UI를 Client Island로 옮겨야 하거나(그 과정에서 문법을 바꿔야 하거나), 동적인 UI에서도 필요해서 아예 중복 작성해야 하는 상황이 생길 수 있습니다. RSC에서는 공통 부분을 추출해서 양쪽에서 import하면 됩니다. &quot;이 부분은 대부분 동적일 것이다&quot;, &quot;이 부분은 대부분 정적일 것이다&quot;를 UI 조각마다 미리 다 생각해둘 필요가 줄어듭니다. <code>'use client'</code>를 추가하거나 제거하고, import 체인 위아래로 옮기는 데 마찰이 거의 없기 때문입니다. &quot;문을 어디에 뚫을지&quot;는 결정해야 하지만, 앞뒤로 &quot;변환&quot;하는 과정은 필요 없습니다.</li>
</ul>
<ul>
<li><strong>컨텍스트의 자연스러운 전파</strong>: Astro에서는 Client Island 안에 Astro Component를 중첩할 수 있지만, 그 안에 또 Client Island가 있다면 프레임워크(예: React) 입장에서는 별개의 루트로 취급됩니다. 그래서 React나 Vue의 context가 Astro Island 사이를 넘나들 수 없어서, 인터랙티브한 동작의 중첩이 클라이언트 앱만큼 자연스럽게 합성되지 않습니다. RSC에서는 이 문제가 없습니다. 전체 UI가 내부적으로 하나의 React 트리이기 때문입니다. 서버 서브트리 위에 클라이언트 context provider를 두고, 그 아래 어디서든 여러 클라이언트 컴포넌트가 그 context를 읽을 수 있습니다. RSC는 &quot;프랙탈 아일랜드&quot;입니다.</li>
</ul>
<ul>
<li><strong>SPA 같은 내비게이션</strong>: Astro Component는 결국 HTML만 생성할 수 있습니다. 그래서 Astro 사이트에서 링크를 클릭하면 브라우저가 페이지를 완전히 새로고침해야 합니다. 이 정도 UX로 충분하다면 문제없지만, View Transitions 같은 수동 로직으로 개선하더라도 근본적으로는 페이지의 HTML이 통째로 교체됩니다. nav 영역의 상태(React 상태든, 입력값·스크롤 위치 같은 DOM 상태든)를 항상 유지하는 SPA 같은 내비게이션을 원한다면 RSC가 이 간극을 메워줍니다. RSC는 React 트리를 JSON과 유사한 포맷으로 다루는데, 이는 최초 페인트를 위해 HTML로 변환될 수도 있고, 내비게이션 시에는 JSON으로 다시 가져올 수도 있습니다. 즉 RSC는 MPA 방식으로 사고하면서도 SPA처럼 느껴지게 해줍니다.</li>
</ul>
<ul>
<li><strong>서버 부분의 제자리 갱신</strong>: Astro와 달리 RSC의 서버 부분은 그 자리에서 다시 새로 고칠 수 있습니다. 블로그 빌드 시에만 RSC를 쓰는 게 아니라 실제로 서버를 운영한다면, RSC는 언제든 화면을 &quot;새로고침&quot;해서 이미 존재하는 상태 기반 클라이언트 트리 안으로 최신 서버 props를 흘려보낼 수 있습니다. 예를 들어 어떤 Astro Component가 상호작용에 반응해서 새로고침되어야 한다면, 전체 페이지를 새로고침하거나 로직을 Client Island로 옮기는 것 중 하나를 선택해야 합니다. RSC에서는 그냥 서버에 새 JSX를 요청해서 기존 트리에 병합하면 됩니다.</li>
</ul>
<h3>근본적인 출력 형식의 차이</h3>
<p>Astro의 근본적인 출력 형식은 HTML입니다. 프론트엔드 프레임워크는 HTML 자체를 조작하는 게 아니라 HTML로 초기화될 수 있는 상태 기반 DOM을 다루기 때문에, Astro는 &quot;일회성 핸드오프&quot; 모델을 따릅니다. 이는 배우기는 비교적 쉽지만, 서버 기능을 &quot;최초 렌더링&quot;(HTML로의 변환)에 필요한 수준으로 제한하고, 인터랙티브한 부분은 대부분 개발자 스스로 처리하게 만듭니다. 인터랙티브한 요소를 점점 늘리다 보면 Astro 모델의 한계에 부딪혀, 더 많은 로직을 SPA 같지만 고립된 Island로 옮기게 될 수도 있습니다.</p>
<p>RSC의 근본적인 출력 형식은 React 트리입니다. 이 트리는 HTML로 변환될 수도 있지만, JSON으로 (다시) 가져올 수도 있습니다. RSC는 양쪽 모두에서 React를 사용하고 두 세계 사이에 시각적 구분이 없기 때문에 다루는 법을 배우기가 더 까다롭습니다. 그 대신 일단 경계를 옮기는 감을 잡고 나면 그 경계가 매우 유동적이 되어서, 뭔가 예상보다 더 정적이거나 동적이 됐을 때 코드를 &quot;Astro 안으로&quot; 옮기거나 &quot;다시 Island로&quot; 되돌려야 하는 문제를 해결해줍니다. 또한 UI가 읽기 전용이든, 뮤테이션에 반응해 다시 가져와야 하든, &quot;데이터를 UI에 매핑한다&quot;는 동일한 멘탈 모델을 유지할 수 있습니다. 서버 부분이 트리 깊숙이까지 파고들어 클라이언트 부분과 서로 엮여 들어갑니다.</p>
<p>그리고 양쪽 모두 React이기 때문에 모든 React 기능이 처음부터 끝까지 통합됩니다. 예를 들어 클라이언트의 <code>&lt;Suspense&gt;</code> 선언적 로딩 상태는 서버에서 오는 비동기 데이터, 클라이언트가 로드하는 JS와 CSS, 적절한 타임아웃이 설정된 폰트와 이미지를 모두 &quot;인지&quot;하고 기다릴 수 있으며, 심지어 View Transitions까지 트리거할 수 있습니다. React에서는 모든 기능이 서버와 클라이언트 조각이 임의로 중첩되고, 합성되고, 제자리에서 갱신될 수 있도록 설계되어 있습니다. 결국 하나의 트리인 것이죠. 단점은 RSC를 받아들인다는 것이 곧 React를 전적으로 받아들인다는 뜻이라는 점입니다. RSC는 풀스택 React입니다.</p>
<h3>Astro와 RSC의 위치</h3>
<p>마지막으로 짚어둘 점은, Astro는 프레임워크이지만 RSC 자체는 더 낮은 레벨이라는 것입니다. RSC는 프레임워크를 위한 빌딩 블록, 혹은 프레임워크가 구현할 수 있는 하나의 표준에 가깝습니다. 현재 공식적으로 지원되는 RSC 구현체는 Next.js App Router(프레임워크)와 Parcel RSC(프레임워크가 아님) 두 가지입니다.</p>
<p>개인적인 생각으로는, RSC의 개발자 경험은 아직 다소 거친 편입니다. 하지만 그럼에도 배워볼 가치는 있다고 봅니다. 흥미로운 아이디어들을 품고 있기 때문입니다.</p>
<p>그리고 아직 Astro를 써본 적이 없다면 한 번 시도해보는 것도 좋습니다. RSC가 어렵게 느껴진다면 Astro가 같은 개념으로 들어가는 더 완만한 입구가 되어줄 수 있습니다. 반대로 클라이언트 사이드 React만 써봤다면, Astro는 미처 깨닫지 못했던 문제들을 해결해줄지도 모릅니다.</p>
<h3>정리</h3>
<ul>
<li>Astro의 Astro Component/Client Island 구조와 RSC의 Server Component/Client Component 구조는 멘탈 모델이 거의 동일합니다. Astro를 알면 RSC 학습이 훨씬 수월해집니다.</li>
<li>Astro는 <code>.astro</code> 파일이라는 문법 자체로 서버·클라이언트 세계를 명확히 분리하지만, RSC는 <code>'use client'</code> 지시어 하나로 경계를 표시할 뿐 본질적으로는 둘 다 &quot;그냥 React&quot;입니다. 그래서 같은 컴포넌트가 맥락에 따라 서버에서도, 클라이언트에서도 쓰일 수 있습니다.</li>
<li>이런 유동성 때문에 RSC는 배우기 어렵지만(&quot;내가 지금 어느 세계에 있는지&quot; 계속 신경 써야 함), 동시에 경계를 자유롭게 옮길 수 있고, context가 서버·클라이언트 트리를 넘나들며, SPA 같은 내비게이션과 서버 부분의 제자리 갱신이 가능하다는 강력한 이점을 제공합니다.</li>
<li>Astro의 출력 형식은 HTML(일회성 핸드오프)이고, RSC의 출력 형식은 React 트리(HTML로도, JSON으로도 변환 가능)입니다. 이 차이가 Suspense, View Transitions 등 React 기능이 서버·클라이언트 경계를 넘어 통합되는 이유입니다.</li>
<li>RSC를 받아들인다는 것은 React 생태계 전체를 받아들인다는 뜻입니다. RSC는 프레임워크가 아니라 Next.js App Router나 Parcel RSC 같은 프레임워크가 구현하는 저수준 표준입니다.</li>
