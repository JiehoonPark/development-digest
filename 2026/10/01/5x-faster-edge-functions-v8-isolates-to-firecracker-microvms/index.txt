14:T3899,<p>Netlify는 매일 약 10억 건의 Edge Function을 실행합니다. Sunweb의 개인화 페이지부터 Loto-Québec의 쿠키 기반 트래픽 라우팅까지, 수십만 개 사이트가 개인화·라우팅·인증 등 다양한 용도로 이 기능을 쓰고 있는데요. 이 모든 요청은 고객의 트래픽 규모에 맞춰 확장되는 완전한 JavaScript 런타임 위에서 동작합니다.</p>
<p>문제는 지연 시간입니다. 초당 수만, 많게는 수십만 건의 엣지 함수를 처리하려면 요청을 받고, 올바르게 라우팅하고, 컴퓨팅 자원을 할당하고, 플랫폼 코드와 고객 코드를 부팅하는 과정이 전부 밀리초 단위에서 끝나야 합니다. 지난 몇 달간 Netlify 팀은 Unikraft 팀과 긴밀히 협업해 Edge Functions의 기반 인프라를 통째로 다시 만들었습니다. 기존에는 요청이 외부에 호스팅된 실행 서비스로 나갔다 돌아왔지만, 이제는 자체 엣지 네트워크 안의 MicroVM에서 직접 실행됩니다. 그 결과 중앙값 기준으로 약 5배 빨라졌고, 보안과 안정성도 함께 개선됐습니다. 물론 URL import, npm 패키지, Node 내장 모듈, netlify.toml 설정, 로컬 개발 등 기존 사용 방식은 전혀 바뀌지 않았습니다. 이 글에서는 새 아키텍처가 어떻게 동작하는지, 그리고 대규모 트래픽을 낮은 오버헤드로 처리하는 컴퓨트 플랫폼을 만들며 얻은 교훈을 정리합니다.</p>
<h3>숫자로 보는 성과</h3>
<p>엣지 함수는 사이트 앞단에서 매칭되는 모든 요청에 대해 실행됩니다. 이 함수가 걸리는 시간은 고스란히 고객이 기다리는 시간이기 때문에, 밀리초 단위 차이가 다른 어떤 시스템보다도 민감하게 작용합니다.</p>
<p>컴퓨트 노드로 라우팅 → MicroVM 진입 → 함수 실행 → 응답 헤더 생성까지 이어지는 '웜 인보케이션(warm invocation)'의 비용은 다음과 같이 개선됐습니다.</p>
<ul>
<li>중앙값(p50) 기준 ~5–6ms (기존 인프라의 25–40ms 대비 대폭 단축)</li>
<li>p99 인보케이션 47.4% 개선</li>
<li>99.998% 가용성</li>
<li>엣지 함수 로그 전달 속도 5배 향상</li>
</ul>
<p>콜드 인보케이션도 언급할 만합니다. 특정 리전에 처음 들어온 요청이라 컴퓨트 노드가 관련 이미지를 미리 가지고 있지 않은 경우인데, 전체 요청의 약 1.2%에서 발생하며 평균 9ms 정도가 소요됩니다.</p>
<h3>요청 처리 흐름</h3>
<p>하나의 요청이 들어와서 응답이 나가기까지의 경로를 순서대로 따라가 보겠습니다. 요청은 엣지 노드에 도착해 스펙(specification)으로 변환되고, 컴퓨트 노드로 라우팅된 뒤, 이미 존재하거나(웜) 새로 생성해야 하는(콜드) MicroVM으로 전달됩니다.</p>
<h4>엣지 노드 도착</h4>
<p>모든 요청은 클라이언트와 가장 가까운 Netlify 엣지 노드에 도착합니다. 이 노드는 TLS 연결을 종료하고, 요청 경로를 해당 배포의 Edge Functions 라우트와 대조합니다.</p>
<p>매칭되는 라우트가 없으면 요청은 평소처럼 캐시를 거쳐 오리진으로 흘러갑니다. 매칭이 되면, 바로 이 지점이 예전에는 요청이 네트워크를 벗어나던 구간이었습니다. 기존 인프라에서는 요청이 인터넷을 거쳐 나가 엣지 함수를 실행하고 다시 돌아와야 했지만, 새 컴퓨트 플랫폼에서는 요청이 자사 네트워크 내부의 컴퓨트 노드로 바로 전달됩니다.</p>
<h4>엣지 노드가 스펙을 작성한다</h4>
<p>요청이 어디로든 가기 전에, 엣지 노드는 함수를 실행할 머신에 대한 스펙을 먼저 작성합니다. 이 스펙에는 런타임, 플랫폼 이미지, 엣지 함수 이미지라는 세 가지 이미지 이름이 명시되고, CPU·메모리·커넥션 제한도 함께 설정됩니다.</p>
<p>이 스펙은 모든 요청과 함께 이동합니다. 스펙의 해시값과 사이트별 정보를 조합해 서비스 ID를 생성하는데, 덕분에 서로 다른 코드나 환경변수를 가진 두 배포는 각각 다른 서비스로 취급되어 절대 같은 MicroVM을 공유하지 않습니다.</p>
<p>이 격리는 발생해서는 안 되는 장애 상황에서 특히 중요합니다. 잠재적으로 손상된 배포가 있더라도 별도의 MicroVM에서 실행되기 때문에, 런타임을 탈출하더라도 다른 고객이나 컴퓨트 계층 자체를 오염시킬 수 없습니다. V8 isolate는 이름과 달리 이 수준의 격리를 제공하지 못한다는 점도 짚어둘 만합니다.</p>
<h4>엣지 함수를 실행할 컴퓨트 노드 선택</h4>
<p>컴퓨트 노드가 머신 스펙과 서비스 ID가 담긴 요청을 받으면, 먼저 해당 ID의 서비스가 이미 존재하는지 확인합니다. 존재하면 그 서비스로 요청을 넘겨 MicroVM으로 보냅니다. 서비스는 같은 사이트의 Edge Functions에 여러 MicroVM을 연결할 수 있게 해주고, MicroVM을 언제 스케일 인/아웃할지도 설정할 수 있게 해줍니다. 예를 들어 하나의 MicroVM이 처리할 수 있는 요청 수를 제한해 두고 그 수를 넘기면 종료시키는 식으로, MicroVM이 무한정 떠 있는 상황을 방지합니다. 동일한 파라미터를 이용해 기존 MicroVM이 종료되기 전에 미리 새 MicroVM을 띄워둘 시점도 판단합니다.</p>
<p>해당 사이트의 서비스가 컴퓨트 노드에 아직 없다면 새로 생성하고, 머신 스펙에 명시된 이미지들이 디스크에 있는지 확인합니다. 없는 이미지가 있으면 엣지 노드에서 가져와 디스크에 기록합니다. 이 방식 덕분에 해당 리전에서 실제로 트래픽을 받고 있는 엣지 함수 이미지만 가져오면 됩니다.</p>
<p>각 리전에는 컴퓨트 노드 그룹이 있고, 엣지 노드는 랑데부 해싱(rendezvous hashing)으로 서비스가 실행될 노드를 선택합니다. 같은 서비스는 항상 같은 노드로 가게 되는데, 이것이 MicroVM을 웜 상태로 유지하고 코드를 디스크와 캐시에 남겨두는 핵심 메커니즘입니다. 이런 고정성(stickiness)이 일종의 캐싱 전략인 셈인데요, 만약 요청을 스웜 전체에 골고루 분산시킨다면 오히려 콜드 스타트가 더 많이 발생하게 됩니다.</p>
<p>다만 특정 함수의 모든 요청을 같은 컴퓨트 노드로 보내는 것이 빠른 경로이기는 해도, 바로 이 지점에서 핫스팟이 생길 수 있다는 점도 유의해야 합니다. 한 리전 트래픽의 큰 비중을 차지하는 서비스가 단일 노드에 고정되면, 같은 노드의 다른 서비스들을 희생시키며 노드를 포화시키게 됩니다.</p>
<p>이를 완화하기 위해 특정 임계값을 넘으면 고정성을 완화해 서비스를 여러 노드로 분산시킵니다. 이렇게 하면 한 고객의 갑작스러운 트래픽 스파이크를 흡수하면서도, 같은 노드로 해싱된 다른 서비스에 영향을 주지 않을 수 있습니다.</p>
<p>노드가 최종 선택되면 해당 함수의 코드를 끌어옵니다. 이전에 그 함수를 서빙한 적 있는 노드라면 이미 코드를 갖고 있고, 처음 보는 노드라면 한 번만 가져와 캐싱하므로 그 비용은 최초 요청 한 번만 부담하면 됩니다.</p>
<h4>MicroVM 기동</h4>
<p>각 함수는 자신만의 Firecracker MicroVM 안에서 실행됩니다. 이 MicroVM은 1밀리초 이내에 생성되고 p99 기준 약 2ms 안에 시작되는데, 완전한 운영체제가 아니라 경량화된 Linux 환경만 띄우기 때문입니다. 엣지 함수의 파일들은 압축되지 않은 EROFS 이미지로 마운트된 뒤 메모리 맵핑되므로, VM은 번들 전체를 로드하지 않고 실제로 사용하는 부분만 읽습니다.</p>
<p>MicroVM이 부팅되고 JavaScript 서버가 포트를 리스닝하기 시작하면, 그 시점의 MicroVM 스냅샷을 찍어둡니다. 엣지 함수가 호출되지 않는 동안에는 이를 실행하던 MicroVM이 유휴 상태로 남아있는 대신 0으로 스케일 다운됩니다. 다음에 다시 호출되면 이 스냅샷에서 새 MicroVM을 기동합니다. 스냅샷 역시 메모리 맵핑되어 있어서, VM은 스냅샷 전체를 메모리로 다시 읽어들일 때까지 기다리지 않고도 실행을 시작할 수 있습니다.</p>
<p>VM의 전체 생명주기 — 부팅, 스냅샷, 복원, 스케일 투 제로 — 는 Unikraft 제품이 담당하는 영역입니다. Netlify는 마이그레이션 전 과정에서 Unikraft 팀과 긴밀히 협업하며 이 기능이 자사의 요청 규모와 트래픽 패턴에서도 안정적으로 동작하도록 검증했습니다.</p>
<h4>실행과 응답 처리</h4>
<p>이 프로젝트를 수년간 운영해 오면서 성능 최적화와 디버깅 역량을 높이기 위한 여러 교훈을 쌓아왔습니다. 대규모 운영 중에는 가상 스위치의 포트 고갈부터 DNS 문제까지 온갖 이슈를 겪었는데요(놀랍게도 DNS 문제가 아닌 경우도 있었다고 합니다).</p>
<p>이번 아키텍처에서는 컴퓨트 노드가 로컬 DNS 리졸버를 운영하도록 했습니다. 수집하는 메트릭도 확장해서 부팅 시간, 첫 포트가 열리기까지 걸린 시간, 사용자 코드 시작 시간 등을 기록하고 있습니다. 또한 컴퓨트 노드를 신속하게 재라우팅하거나 폐기할 수 있도록 여러 단계의 서킷 브레이커도 마련해 두었습니다.</p>
<p>여기까지가 전체 경로이고, 웜 인스턴스 기준으로 약 6ms가 추가됩니다. 이 과정 중 어느 것도 Netlify 네트워크를 벗어나지 않으며, 요청 전체 사이클을 자사가 직접 통제합니다. 위에서 설명한 모든 과정이 요청 도착과 응답 반환 사이에서 일어납니다.</p>
<h3>복원력 있는 컴퓨트 인프라 설계</h3>
<p>이런 시스템을 구축할 때는 두 가지를 동시에 최적화해야 합니다. 최종 사용자 경험과 롤아웃 복원력입니다. 변경 사항을 빠르게 배포할 수 있어야 하는 동시에, 그만큼 빠르게 롤백할 수 있는 능력도 갖춰야 합니다.</p>
<p>컴퓨트 노드는 Unikraft가 배포한 베이스 이미지를 기반으로, 필요한 패키지 세트를 설치해서 구성됩니다. 이 노드들은 몇 가지 이유로 엣지 노드와 별도로 빌드됩니다. 엣지 노드를 가볍고 빠르게 유지할 수 있고, 컴퓨트 노드에는 다른 인스턴스 타입을 사용할 수 있으며, 두 노드를 독립적으로 스케일링할 수 있기 때문입니다.</p>
<p>컨트롤 플레인은 어떤 컴퓨트 노드가 존재하고 그 중 어느 것이 정상인지를 추적하며, 엣지 노드들은 이 목록을 주기적으로 폴링합니다. 배포 역시 이 컨트롤 플레인이 주도하는데, 새 플릿이 기존 플릿과 함께 기동되어 규모를 맞춘 뒤, 정상 상태가 확인되어야만 트래픽을 넘겨받습니다.</p>
<p>이 컴퓨트 인프라를 구축하는 과정 전반에서 Unikraft 팀과의 긴밀한 협업이 필수적이었습니다. 마이그레이션 내내 정확성 테스트, 대량 요청 처리, Netlify 플랫폼 전용 기능 구축 등을 함께 진행했습니다.</p>
<h3>지금 가능해진 것들</h3>
<p>이번 재구축은 단순한 속도 개선 이상의 의미를 갖습니다. 앞으로 계속 쌓아 올릴 수 있는, 그리고 더 많은 통제권을 가진 기반을 마련한 것인데요. 가장 좋은 점은 이미 지금 이 순간 프로덕션 트래픽을 처리하고 있다는 사실입니다. 가격은 동일하고, 마이그레이션 단계도 없으며, 어떤 프로젝트에서도 바꿀 게 없습니다.</p>
<p>컴퓨트를 직접 운영한다는 것은 Edge Functions의 한계를 스스로 끌어올릴 수 있다는 뜻이기도 합니다. 이번 재구축으로 다음 세 가지가 실현 가능해졌습니다.</p>
<ul>
<li><strong>npm 패키지 지원의 정식 출시</strong>: npm 패키지는 현재 베타로 엣지 함수에서 동작하지만, 네이티브 바이너리나 런타임 중 파일 import 관련 제약이 있습니다. 실제 파일시스템을 가진 진짜 VM 환경에서는 이런 제약의 대부분이 사라집니다.</li>
<li><strong>연산 한도 재검토의 여지</strong>: 요청당 CPU 50ms, 메모리 512MB, 압축 코드 20MB라는 기존 문서화된 제한은 isolate 기반 실행 모델에서 비롯된 것이었습니다.</li>
<li><strong>자사 네트워크 내부에서의 컴퓨트</strong>: 인터넷을 거쳐 제3자에게 도달하는 대신 네트워크 경로 자체를 통제할 수 있어야 가능했던 기능들을, 이제 직접 구축할 수 있게 됐습니다.</li>
</ul>
<p>Netlify는 이전에는 손댈 수 없었던 한계와 미흡한 부분들을 지금 작업 중이라고 밝히며, 앞으로의 변화를 예고하고 있습니다.</p>
<h3>정리</h3>
<ul>
<li>Netlify는 Edge Functions의 실행 환경을 외부 호스팅 서비스에서 자체 엣지 네트워크 안의 Firecracker MicroVM으로 전면 교체했습니다. Unikraft와의 협업을 통해 완성된 이번 작업으로 웜 인보케이션 지연 시간이 25–40ms에서 5–6ms로, 중앙값 기준 약 5배 개선됐습니다.</li>
<li>핵심은 요청마다 작성되는 '머신 스펙'과 이를 바탕으로 한 서비스 ID 해시입니다. 서로 다른 배포는 절대 같은 MicroVM을 공유하지 않아 V8 isolate보다 강한 격리를 제공합니다.</li>
<li>랑데부 해싱으로 같은 서비스를 같은 컴퓨트 노드에 고정시켜 캐시 적중률과 웜 상태를 유지하되, 트래픽이 몰리면 고정성을 완화해 핫스팟을 방지하는 균형 잡힌 설계를 적용했습니다.</li>
<li>MicroVM은 1ms 이내 생성, p99 기준 2ms 부팅을 달성했으며, EROFS 이미지의 메모리 맵핑과 스냅샷 복원 기법으로 콜드 스타트 비용을 최소화했습니다.</li>
<li>이번 인프라 전환은 개발자가 코드나 설정을 전혀 바꾸지 않아도 적용되며, 동시에 npm 패키지 정식 지원, 연산 한도 재검토, 네트워크 경로 직접 제어 등 기존에는 불가능했던 기능 확장의 토대를 마련했습니다.</li>
