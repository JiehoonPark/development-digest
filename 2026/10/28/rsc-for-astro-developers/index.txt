13:T3e75,<h2>Astro 개발자를 위한 RSC 이해하기</h2>
<p>React Server Components(RSC)는 처음 접하면 낯설고 어렵게 느껴집니다. 그런데 사실 Astro를 써본 적이 있다면 이미 RSC의 핵심 멘탈 모델을 80% 정도는 알고 있는 셈입니다. Dan Abramov는 자신의 블로그 글에서 Astro의 컴포넌트/아일랜드 구조와 RSC의 서버/클라이언트 컴포넌트 구조가 얼마나 닮아 있는지, 그리고 둘이 어디서 갈라지는지를 코드와 함께 설명합니다. 이 글에서는 그 내용을 정리해봅니다.</p>
<h3>Astro의 두 가지 세계</h3>
<p>Astro에는 근본적으로 두 종류의 컴포넌트가 존재합니다.</p>
<p><strong>Astro Components</strong>는 <code>.astro</code> 확장자를 가지며, 서버에서 또는 빌드 시점에만 실행됩니다. 즉 이 코드는 클라이언트로 절대 전송되지 않습니다. 그래서 파일시스템을 읽거나, 내부 서비스를 호출하거나, 데이터베이스에 접근하는 등 클라이언트 코드는 할 수 없는 일을 할 수 있습니다. 대신 HTML 네이티브 기능이나 직접 작성한 <code>&lt;script&gt;</code> 외에는 인터랙티브한 동작을 할 수 없습니다. Astro Components는 다른 Astro Components나 Client Islands를 렌더링할 수 있습니다.</p>
<p><strong>Client Islands</strong>는 React, Vue 등으로 작성된 컴포넌트입니다. 우리가 익히 아는 프론트엔드 코드이고, 인터랙티브한 부분을 붙이기 편한 자리입니다. Client Islands는 같은 프레임워크의 메커니즘으로 또 다른 같은 프레임워크의 컴포넌트를 렌더링할 수 있습니다. 하지만 Client Island에서 Astro Component를 렌더링할 수는 없습니다—그 시점에는 이미 Astro의 실행이 끝났기 때문에 말이 되지 않습니다.</p>
<p>다음은 <code>PostPreview.astro</code>라는 Astro Component가 <code>LikeButton</code>이라는 Island를 렌더링하는 예시입니다.</p>
<pre><code class="language-astro">---
import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';
const { slug } = Astro.props;
const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
---
&lt;article&gt;
&lt;h1&gt;{title}&lt;/h1&gt;
&lt;LikeButton client:load /&gt;
&lt;/article&gt;</code></pre>
<pre><code class="language-jsx">import { useState } from 'react';
export function LikeButton() {
const [liked, setLiked] = useState(false);
return (
&lt;button onClick={() =&gt; setLiked(!liked)}&gt;
{liked ? '❤️' : '🤍'} Like
&lt;/button&gt;
);
}</code></pre>
<p>여기서 주목할 점은 Astro Components와 Client Islands가 사실상 완전히 분리된 두 &quot;세계&quot;에 살고 있고, 데이터는 오직 위에서 아래로만 흐른다는 것입니다. Astro Components는 모든 전처리가 일어나는 곳이고, 인터랙티브한 부분은 Client Islands에 &quot;넘겨주는&quot; 구조입니다.</p>
<h3>RSC로 같은 걸 표현하면</h3>
<p>이제 React Server Components를 살펴보겠습니다. RSC에서는 같은 두 가지가 각각 Server Components와 Client Components로 불립니다. 위의 Astro Component를 RSC로 작성하면 이렇게 됩니다.</p>
<pre><code class="language-jsx">import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';
async function PostPreview({ slug }) {
const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
return (
&lt;article&gt;
&lt;h1&gt;{title}&lt;/h1&gt;
&lt;LikeButton /&gt;
&lt;/article&gt;
);
}</code></pre>
<pre><code class="language-jsx">'use client';
import { useState } from 'react';
export function LikeButton() {
const [liked, setLiked] = useState(false);
return (
&lt;button onClick={() =&gt; setLiked(!liked)}&gt;
{liked ? '❤️' : '🤍'} Like
&lt;/button&gt;
);
}</code></pre>
<p>두 접근의 멘탈 모델은 놀랍도록 비슷합니다. Astro를 안다면 이미 RSC 멘탈 모델의 대부분을 갖춘 것입니다. (설령 RSC가 별로라고 생각하더라도 Astro는 배워둘 가치가 있습니다.)</p>
<h3>문법적 차이</h3>
<p>몇 가지 눈에 띄는 차이가 있습니다.</p>
<p>Astro Components와 달리 React Server Components는 평범한 JavaScript 함수입니다. &quot;싱글 파일&quot; 구조가 아니고, props는 <code>Astro.props</code>가 아니라 함수 인자로 전달되며, 별도의 &quot;템플릿&quot; 영역도 없습니다.</p>
<p>Astro에서는 <code>.astro</code> 파일로 작성함으로써 Astro Components와 Client Islands의 경계를 나눕니다. Client Island를 import하는 순간 더 이상 <code>.astro</code> 파일 안이 아니므로 Astro 세계를 &quot;벗어나는&quot; 것입니다. RSC에서는 같은 목적을 <code>'use client'</code> 지시어로 달성합니다. <code>'use client'</code>는 서버 세계가 &quot;끝나는&quot; 지점을 표시하는, 두 세계 사이의 문 같은 역할을 합니다.</p>
<p>Astro에는 <code>client:load</code>처럼 Island를 정적 HTML로 둘지 클라이언트에서 하이드레이션할지 선택하는 지시어가 있습니다. RSC는 이런 구분을 사용자 코드에 노출하지 않습니다. React 입장에서는 애초에 인터랙티브하게 작성된 컴포넌트에서 인터랙티브함을 제거하는 건 잘못된 접근이기 때문입니다. 정말로 인터랙티브함이 필요 없다면 그냥 <code>'use client'</code>를 지우면 되고, 그러면 서버 세계에서 import할 때 자동으로 서버 전용으로 남게 됩니다.</p>
<h3>핵심 차이: &quot;Astro&quot; 부분도 그냥 React다</h3>
<p>마지막 지점이 흥미롭습니다. Astro에서는 <code>.astro</code> 파일과 Client Islands라는 서로 다른 문법이 두 세계 사이에 뚜렷하고 명확한 시각적 구분을 만듭니다. 같은 컴포넌트가 맥락에 따라 Astro Component도 됐다가 Client Island도 될 수는 없습니다—둘은 서로 다른 문법을 가진 별개의 존재입니다.</p>
<p>하지만 RSC에서는 &quot;Astro&quot;에 해당하는 부분도 그냥 React입니다. 그래서 클라이언트 전용이든 서버 전용이든 특정 기능을 쓰지 않는 컴포넌트라면, 어느 역할이든 수행할 수 있습니다.</p>
<p>자체적으로 파싱을 수행하는 <code>&lt;Markdown /&gt;</code> 컴포넌트를 생각해봅시다. State 같은 클라이언트 기능도, DB 읽기 같은 서버 기능도 쓰지 않으므로 어느 쪽에서든 import할 수 있습니다. 서버 세계에서 import하면 &quot;Astro Component&quot;처럼 동작하고, 클라이언트 세계에서 import하면 &quot;Client Island&quot;처럼 동작합니다. 이건 새로운 개념이 아니라 그냥 함수 import가 원래 작동하는 방식일 뿐입니다.</p>
<p>RSC에서는 서버 세계에서 import된 것은 서버 세계에서 실행되고, 클라이언트 세계에서 import된 것은 클라이언트 세계에서 실행됩니다. 그리고 양쪽 모두에서 지원되지 않는 것(예: 클라이언트에서의 DB 접근, 서버에서의 <code>useState</code>)은 빌드 에러를 일으켜 <code>'use client'</code>로 &quot;문을 새로 뚫도록&quot; 강제합니다.</p>
<h3>저주이자 축복</h3>
<p>이 특성은 저주이기도 하고 축복이기도 합니다.</p>
<p>저주인 이유는 RSC를 다루는 법을 배우기가 상당히 직관적이지 않기 때문입니다. &quot;내가 지금 어느 세계에 있는지&quot;를 계속 신경 쓰게 됩니다. 사실 그건 중요하지 않다는 걸 받아들이는 데는 연습이 필요합니다—왜냐하면 항상 로컬하게 추론할 수 있기 때문입니다. DB 같은 서버 기능이 필요한 파일에서는 그걸 쓰고, State 같은 클라이언트 기능이 필요한 파일에서는 그걸 쓰면 됩니다. 뭔가 잘못되면 빌드 타임 검증이 에러를 내줄 테니, 모듈 스택 트레이스를 보고 어디에 새로 &quot;문을 뚫을지&quot; 결정하면 됩니다.</p>
<p>저주이지만 동시에 축복이기도 한 이유는, 양쪽 모두에서 React를 그대로 쓰는 RSC 모델이 Astro가 가진 몇 가지 한계를 해결해주기 때문입니다.</p>
<ul>
<li><strong>공유 로직의 재사용</strong>: Astro Components로 한참 작업하다가 나중에 그 UI를 Client Islands로 옮기거나(문법을 바꿔가며), 혹은 동적인 UI도 그걸 필요로 해서 중복 작성해야 하는 상황이 생길 수 있습니다. RSC에서는 공유되는 부분을 추출해서 양쪽에서 import하면 됩니다. &quot;이 부분은 대체로 정적일 거야&quot; &quot;이 부분은 대체로 동적일 거야&quot; 하고 미리 다 예측할 필요가 적어집니다. <code>'use client'</code>를 넣고 빼거나 import 체인 위아래로 옮기는 게 큰 마찰 없이 가능하기 때문입니다. 어디서 &quot;문을 뚫을지&quot;는 결정해야 하지만, 앞뒤로 &quot;변환&quot;할 필요는 없습니다.</li>
</ul>
<ul>
<li><strong>컨텍스트 전달</strong>: Astro에서는 Client Islands 안에 Astro Components를 중첩할 수 있지만, 그 안에 또 다른 Client Islands가 들어가면 프레임워크(예: React) 입장에서는 별개의 루트로 인식됩니다. 그래서 React나 Vue의 context를 Astro 아일랜드 사이에서 전달할 수 없고, 인터랙티브한 동작을 중첩시키는 게 클라이언트 앱만큼 자연스럽게 합성되지 않습니다. RSC에서는 전체 UI가 내부적으로 하나의 React 트리이므로 이 문제가 없습니다. 어떤 Server 서브트리 위에 Client context provider를 두고, 그 아래 어디서든 여러 Client 컴포넌트가 그 context를 읽을 수 있습니다. RSC는 프랙탈 아일랜드입니다.</li>
</ul>
<ul>
<li><strong>네비게이션</strong>: Astro Components는 결국 HTML만 만들어냅니다. 그래서 Astro 사이트에서 링크를 클릭하면 브라우저가 페이지를 완전히 새로고침해야 합니다. 이게 충분한 UX라면 문제없고, View Transitions와 수동 로직으로 개선할 수도 있지만 근본적으로는 페이지 HTML이 교체됩니다. nav chrome의 상태(React state든 입력값·스크롤 위치 같은 DOM 상태든)를 항상 유지하는 SPA 같은 네비게이션을 원한다면 RSC가 이 간극을 메워줍니다. RSC는 React 트리를 JSON과 유사한 포맷으로 다루는데, 이는 최초 페인트 시 HTML로 변환될 수도 있고 네비게이션 시 JSON으로 다시 페칭될 수도 있습니다. 즉 RSC는 MPA 멘탈 모델로 생각하면서도 SPA처럼 느껴지게 해줍니다.</li>
</ul>
<ul>
<li><strong>제자리 새로고침</strong>: Astro와 달리 RSC UI의 서버 부분은 그 자리에서 다시 새로고침할 수 있습니다. 실제로 서버를 운영한다면(필자의 블로그처럼 빌드 시점에만 RSC를 돌리는 게 아니라), RSC는 언제든 화면을 &quot;새로고침&quot;해서 새 서버 props가 이미 존재하는 클라이언트 측 상태 트리에 흘러들어가게 할 수 있습니다. 예를 들어 어떤 Astro Component가 인터랙션에 반응해 새로고침되어야 한다면, 페이지 전체를 새로고침하거나 로직을 Client Island로 옮기는 것 중 하나를 선택해야 합니다. RSC에서는 그냥 서버에 새 JSX를 요청해서 트리에 병합시키면 됩니다.</li>
</ul>
<h3>근본적인 출력 포맷의 차이</h3>
<p>Astro의 근본적인 출력 포맷은 HTML입니다. 프론트엔드 프레임워크는 원래 HTML 자체를 다루는 게 아니라 HTML로 초기화될 수 있는 상태를 가진 DOM을 다루기 때문에, Astro는 &quot;일회성 핸드오프&quot; 모델을 따릅니다. 이는 배우기는 비교적 쉽지만, 서버 기능을 &quot;최초 렌더링&quot;(HTML로 변환되는 시점)에 필요한 것으로 제한하고, 인터랙티브한 부분은 대체로 개발자가 알아서 처리하도록 남겨둡니다. 더 많은 것을 인터랙티브하게 만들수록 Astro 모델의 한계에 부딪히게 되고, 결국 더 많은 로직을 SPA 같지만 고립된 Islands로 옮기게 될 수 있습니다.</p>
<p>RSC의 근본적인 출력 포맷은 React 트리입니다(HTML로 변환될 수도 있지만, JSON으로 (재)페칭될 수도 있습니다). RSC는 양쪽 모두에서 React를 쓰고 두 세계 사이에 시각적 구분이 없기 때문에 다루는 법을 배우기가 더 어렵습니다. 하지만 일단 경계를 옮기는 요령을 터득하면 그 경계는 매우 유연해져서, 뭔가가 예상보다 더 정적이거나 동적으로 밝혀질 때마다 코드를 &quot;Astro 안으로&quot; 혹은 &quot;다시 Islands로&quot; 옮겨야 하는 문제를 해결해줍니다. UI가 읽기 전용이든 뮤테이션에 반응해 다시 가져와야 하든 &quot;데이터를 UI로 매핑한다&quot;는 동일한 멘탈 모델을 그대로 유지할 수 있습니다. Server 부분은 트리 깊숙이까지 뻗어나가며 Client 부분과 서로 얽혀 들어갑니다.</p>
<p>그리고 양쪽 모두 React이기 때문에 모든 React 기능이 처음부터 끝까지 통합됩니다. 예를 들어 클라이언트의 <code>&lt;Suspense&gt;</code> 선언적 로딩 상태는 (서버로부터의) 비동기 데이터, (클라이언트가 로드하는) JS와 CSS, 적절한 타임아웃을 둔 폰트와 이미지를 기다릴 줄 알고, 심지어 View Transitions도 트리거할 수 있습니다. React에서는 모든 기능이 Server와 Client 조각이 임의로 중첩·합성·제자리 새로고침 가능하도록 설계되어 있습니다. 하나의 트리인 것이죠. 단점은 RSC를 받아들인다는 것이 곧 React를 받아들인다는 뜻이라는 점입니다. RSC는 풀스택 React입니다.</p>
<p>마지막으로 짚어둘 점은, Astro는 프레임워크지만 RSC 자체는 더 낮은 레벨이라는 것입니다. RSC는 프레임워크를 위한 빌딩 블록, 혹은 프레임워크가 구현할 수 있는 표준에 가깝습니다. 현재 공식적으로 지원되는 RSC 구현체는 Next.js App Router(프레임워크)와 Parcel RSC(프레임워크가 아님) 두 가지입니다.</p>
<h3>정리</h3>
<ul>
<li>Astro Components/Client Islands와 RSC의 Server Components/Client Components는 멘탈 모델이 거의 동일합니다. Astro를 안다면 RSC도 금방 익숙해질 수 있습니다.</li>
<li>가장 큰 차이는 &quot;경계를 긋는 방식&quot;입니다. Astro는 <code>.astro</code> 파일이라는 문법으로 두 세계를 뚜렷하게 나누지만, RSC는 <code>'use client'</code> 지시어 하나로 같은 React 함수들 사이에 문을 뚫는 방식입니다. 서버/클라이언트 기능을 쓰지 않는 컴포넌트는 RSC에서 양쪽 어디서든 동작할 수 있습니다.</li>
<li>이 유연함 덕분에 RSC는 Astro의 몇 가지 한계—공유 로직 재사용의 번거로움, Islands 간 context 전달 불가, 풀페이지 새로고침 없는 네비게이션, 서버 부분의 제자리 리프레시—를 해결합니다. 단, 그 대가로 학습 곡선이 더 가파릅니다.</li>
<li>Astro의 출력은 궁극적으로 HTML이고, RSC의 출력은 React 트리(HTML로도, JSON으로도 변환 가능)입니다. 이 차이가 SPA 같은 네비게이션, Suspense와의 통합 등 RSC가 가진 특유의 장점으로 이어집니다.</li>
<li>RSC는 프레임워크가 아니라 Next.js App Router나 Parcel RSC 같은 프레임워크가 구현하는 저수준 표준입니다. RSC를 받아들인다는 건 곧 React를 풀스택으로 받아들인다는 뜻입니다.</li>
<li>Astro를 안 써봤다면 RSC를 배우기 전에 시도해볼 만합니다. 더 완만한 진입로가 되어줄 수 있습니다. 반대로 클라이언트 React만 써봤다면 Astro가 미처 몰랐던 문제들을 해결해줄 수도 있습니다.</li>
