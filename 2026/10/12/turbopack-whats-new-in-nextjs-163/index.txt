18:T3320,<h2>Next.js 16.3 Turbopack 업데이트: 메모리 90% 절감과 빌드 캐시</h2>
<p>Next.js 16.3 프리뷰가 정식 릴리스를 앞두고 있습니다. Instant Navigation 기능과 AI 관련 개선 사항을 다룬 이전 포스트에 이어, 이번에는 Turbopack 번들러에 적용된 변경 사항을 살펴보겠습니다. 이번 버전은 CPU와 메모리 사용량을 줄이고, 빌드 시간을 단축하며, 런타임 경험을 개선하는 데 초점을 맞췄습니다. 핵심 변경 사항은 다음과 같습니다.</p>
<ul>
<li>개발 서버 메모리 사용량 최대 90% 절감</li>
<li>빌드 속도를 높이는 영구 파일 시스템 캐시</li>
<li>실험적 Rust 기반 React Compiler 지원</li>
<li><code>import.meta.glob</code> API 지원</li>
<li>더 빨라진 HMR과 개발 서버 시작 속도</li>
</ul>
<h3>개발 모드 메모리 사용량 절감</h3>
<p>Turbopack의 핵심 설계 철학은 증분 컴파일입니다. 이전 작업 결과를 캐싱해 변경되지 않은 파일은 재컴파일하지 않죠. 덕분에 대규모 Next.js 애플리케이션을 개발할 때 컴파일 시간은 라우트 전체 크기가 아니라 변경된 부분의 크기에 비례하게 됩니다.</p>
<p>이 설계를 구현하는 과정에서 팀은 의도적인 트레이드오프를 선택했습니다. CPU 사용량을 줄이는 대신 더 많은 결과를 메모리에 캐싱하는 방식이었는데요. 문제는 Turbopack이 처음 출시된 이후 메모리가 항상 부족한 자원이었다는 점입니다. 코딩 에이전트, IDE, 타입체커, 린터가 개발 중에 동시에 돌아가면서 각각 상당한 메모리를 소비하기 때문입니다. 지난 3개월간 Turbopack 팀은 시스템 메모리 압박에 대한 자체 기여도를 줄이는 데 집중해왔고, 16.3으로 업그레이드하면 장시간 개발 세션에서 메모리 사용량이 눈에 띄게 줄어드는 것을 바로 확인할 수 있습니다.</p>
<p><strong>50개 라우트 컴파일 후 메모리 사용량</strong></p>
<div class="table-wrapper"><table><thead><tr><th>프로젝트</th><th>Before</th><th>After</th><th>개선율</th></tr></thead><tbody><tr><td>vercel.com (dashboard)</td><td>21.5 GB</td><td>2 GB</td><td>약 90% 감소</td></tr><tr><td>nextjs.org</td><td>4,600 MB</td><td>840 MB</td><td>약 82% 감소</td></tr></tbody></table></div>
<p>이러한 개선의 상당 부분은 데이터 구조를 압축하고 불필요하게 오래 데이터를 보관하지 않도록 하는 등 자잘한 최적화들이 쌓여 만들어졌습니다. 하지만 가장 큰 효과는 메모리 내 캐시 상당 부분을 제거(evict)할 수 있게 된 새로운 기능에서 나왔습니다. Next.js 16.1에서 처음 도입된 파일 시스템 영속화 기능을 활용해, Turbopack이 캐시된 결과를 메모리에서 제거할 수 있게 된 것이죠. 이로써 메모리 캐시가 방문한 모든 라우트를 계속 붙잡고 있지 않게 되면서, 개발 세션 중 메모리가 무한정 늘어나는 현상을 막을 수 있습니다.</p>
<p>메모리 제거(eviction) 기능은 개발 파일 시스템 캐시가 활성화되어 있어야 동작합니다. 16.3에서는 두 옵션 모두 기본값으로 켜져 있습니다. 캐시나 개발 성능을 디버깅할 때는 실험적 설정값인 <code>turbopackMemoryEviction</code>으로 비활성화할 수 있습니다.</p>
<pre><code class="language-js">const nextConfig = {
  experimental: {
    turbopackMemoryEviction: false, // disables memory eviction, default value is 'auto'
  },
};</code></pre>
<p>모든 애플리케이션에 동일하게 적용되는 단일 감소율은 없습니다. 실제 결과는 라우트 그래프의 크기, 개발 세션 중 얼마나 많은 부분을 건드렸는지, 세션이 얼마나 오래 지속됐는지에 따라 달라집니다.</p>
<h3>빌드를 위한 파일 시스템 캐시</h3>
<p>Turbopack 메모리 캐시를 디스크에 영속화하는 기능은 16.1 릴리스 이후 <code>next dev</code> 세션의 속도를 높여왔습니다. Vercel 자체 사이트에서 수개월간 프로덕션 환경으로 검증한 끝에, 이제 동일한 영속 캐시가 <code>next build</code>에도 기본으로 적용됩니다.</p>
<p><strong><code>next build</code>의 Turbopack 컴파일 시간</strong></p>
<div class="table-wrapper"><table><thead><tr><th>프로젝트</th><th>Cold</th><th>Cached</th><th>개선율</th></tr></thead><tbody><tr><td>nextjs.org</td><td>21s</td><td>9.2s</td><td>약 2.3배 빠름</td></tr><tr><td>vercel.com/home</td><td>66s</td><td>46s</td><td>약 1.4배 빠름</td></tr><tr><td>vercel.com/geist</td><td>30s</td><td>5.5s</td><td>약 5.5배 빠름</td></tr></tbody></table></div>
<p>영구 디스크 캐시 덕분에 빌드는 이전에 계산된 작업 결과를 재활용해 정적 자산 컴파일 시간을 줄일 수 있습니다. Turbopack은 빌드 시작 시 캐시를 확인하고, 새로운 변경 사항을 컴파일하기 전에 디스크에서 캐시 항목을 먼저 읽어옵니다.</p>
<p>캐시는 <code>.next/cache</code>에 저장되므로, CI 빌드에서 속도 향상을 보려면 실행 사이사이에 이 디렉터리가 복원되어야 합니다. 옵트아웃 방법과 전체 옵션은 <code>turbopackFileSystemCacheForBuild</code> 레퍼런스 문서를 참고하세요.</p>
<h3>실험적 Rust React Compiler</h3>
<p>Next.js는 16.0 첫 릴리스부터 React Compiler를 안정적으로 지원해왔습니다. 하지만 지금까지 React Compiler는 Babel 변환 방식으로만 제공됐는데요, 대규모 애플리케이션에서는 JS 실행 리소스를 기다리느라 빌드가 느려지는 현상이 관찰됐습니다. 최근 React 팀이 컴파일러의 네이티브 Rust 포트를 공개했고, Turbopack 팀은 이를 빠르게 통합했습니다.</p>
<p>v0 같은 대형 React 앱을 대상으로 한 초기 테스트에서 20~50%의 컴파일 속도 향상이 확인되어, 더 많은 채택을 이끌어내기 위해 실험적 기능으로 네이티브 컴파일러 통합을 공개합니다.</p>
<p>Rust React Compiler를 테스트해보려면 컴파일러를 활성화하고 실험적 플래그 <code>turbopackRustReactCompiler</code>로 네이티브 버전을 사용하면 됩니다.</p>
<pre><code class="language-js">const nextConfig = {
  // enable the compiler
  reactCompiler: true,
  experimental: {
    // use the Rust version, instead of the OG Babel one
    turbopackRustReactCompiler: true,
  },
};</code></pre>
<p>옵트인 기능 등 React Compiler를 설정하는 다양한 방법은 공식 문서에서 자세히 확인할 수 있습니다.</p>
<h3>import.meta.glob</h3>
<p>Turbopack이 이제 Vite와 호환되는 <code>import.meta.glob</code> API를 지원합니다.</p>
<pre><code class="language-js">const posts = import.meta.glob('./posts/*.mdx');</code></pre>
<p>이 API는 파일명을 하드코딩하지 않고도 패턴에 매칭되는 모든 모듈을 임포트할 수 있습니다. 결과는 매칭된 파일 경로를 키로 하는 객체로 반환되며, 기본적으로 각 값은 모듈을 로드하는 비동기 함수입니다.</p>
<pre><code class="language-js">for (const path in posts) {
  const post = await posts[path]();
}</code></pre>
<p><code>eager: true</code> 옵션을 쓰면 매칭된 모듈을 즉시 임포트할 수 있습니다.</p>
<pre><code class="language-js">const posts = import.meta.glob('./posts/*.mdx', {
  eager: true,
});</code></pre>
<p>이 구현체는 named import, 다중 패턴, 제외 패턴(negative pattern), 커스텀 검색 경로, 로더용 쿼리 스트링, 생성된 TypeScript 타입까지 지원합니다.</p>
<p>이 기능은 Turbopack의 파일 워처를 기반으로 동작합니다. 매칭 대상 파일이 추가되거나 삭제되면 개발 모드에서 재컴파일이 트리거되므로, 사이트는 항상 최신 상태를 반영합니다. 이 API는 상품 설명이나 블로그 포스트처럼 유사한 문서 집합을 가져올 때 특히 유용하며, 더 넓은 JS 생태계 전반에서 라이브러리 개발자들에게도 도움이 될 것으로 기대합니다.</p>
<p><code>import.meta.glob</code>은 Turbopack 전용 기능이며, <code>--webpack</code> 옵션으로 빌드한 Next.js 앱에서는 동작하지 않습니다. 사용 가능한 모든 옵션은 <code>import.meta.glob</code> 레퍼런스 문서에서 확인할 수 있습니다.</p>
<h3>HMR 개선</h3>
<p>Vercel 내부의 대규모 Next.js 앱에서 Turbopack 성능을 분석한 결과, 모든 Turbopack 사용자에게 도움이 될 만한 여러 성능 개선 포인트를 발견했습니다. 대부분은 HMR 구독(subscription)을 더 효율적으로 만드는 데 집중됐는데요. 그중 특히 중요한 변경은 페이지에 로드되는 청크를 추적하는 방식을 단순화한 것입니다. 여러 개의 구독을 하나로 통합함으로써, 복잡한 앱에서 개발 서버 콜드 스타트 시간을 15% 이상 줄일 수 있었습니다.</p>
<p>이는 HMR 리소스 조사의 시작일 뿐이며, 앞으로 출시될 Next.js 버전에서 메모리와 콜드 스타트 관련 개선을 더 많이 선보일 예정입니다.</p>
<h3>런타임 크기 축소</h3>
<p>Turbopack은 모듈을 해석하고 새로운 청크를 동적으로 가져오는 데 필요한 런타임 코드를 모든 라우트에 함께 전달합니다. 여기에는 WebAssembly, 워커, 최상위 레벨 비동기 모듈을 로드하는 코드도 포함돼 있는데요. 하지만 모든 Next.js 애플리케이션이 이런 기능을 쓰는 것은 아닙니다. 이제 Turbopack은 실제로 필요한 경우에만 해당 기능 코드를 전달하고, 그렇지 않은 경우에는 불필요한 런타임 코드를 전송하지 않습니다.</p>
<h3>로컬 PostCSS 설정</h3>
<p>모노레포에서는 패키지마다 서로 다른 PostCSS 변환이 필요할 수 있습니다. 실험적 옵션인 <code>turbopackLocalPostcssConfig</code>를 사용하면, Turbopack이 프로젝트 루트 설정으로 폴백하기 전에 각 CSS 파일에서 가장 가까운 설정을 먼저 찾아 적용하도록 할 수 있습니다.</p>
<pre><code class="language-ts">// next.config.ts
const nextConfig = {
  experimental: {
    turbopackLocalPostcssConfig: true,
  },
};</code></pre>
<p>이를 통해 패키지 단위 CSS는 로컬 설정을 사용하면서, 애플리케이션 CSS는 계속 루트 설정을 따르도록 할 수 있습니다.</p>
<h3>호환성 및 안정성 개선</h3>
<p>Next.js 16.3은 16.2 패치 라인의 모든 수정 사항을 포함하며, 모듈 해석, 트레이싱, HMR 영역에서 다음과 같은 개선 사항을 추가로 담고 있습니다.</p>
<ul>
<li>Windows에서 <code>import.meta.url</code>의 올바른 파일 URL 처리</li>
<li>청크 가져오기 실패 시 재시도</li>
<li><code>createRequire(new URL(..., import.meta.url))</code>에 대한 지원 강화</li>
<li><code>worker_threads</code> URL 해석 수정</li>
<li><code>module-sync</code> export condition 지원</li>
<li>webpack 로더 충돌 시 더 나은 에러 메시지</li>
<li>Safari에서의 CSS HMR 버그 수정</li>
</ul>
<h3>정리</h3>
<p>Next.js 16.3의 Turbopack 업데이트는 &quot;더 빠르게&quot;보다 &quot;더 가볍고 안정적으로&quot;에 방점이 찍혀 있습니다. 핵심을 정리하면 다음과 같습니다.</p>
<ul>
<li><strong>메모리 관리의 질적 변화</strong>: 파일 시스템 캐시를 활용한 메모리 제거(eviction) 기능으로 장시간 개발 세션에서 메모리 사용량을 최대 90%까지 줄였습니다. <code>turbopackMemoryEviction</code>과 파일 시스템 캐시 모두 기본 활성화 상태입니다.</li>
<li><strong>빌드 캐시의 범위 확장</strong>: 기존에 <code>next dev</code>에만 적용되던 영구 디스크 캐시가 이제 <code>next build</code>에도 기본 적용되어, 프로젝트에 따라 최대 5.5배의 컴파일 속도 향상을 기대할 수 있습니다. CI에서 효과를 보려면 <code>.next/cache</code> 디렉터리 캐싱이 필수입니다.</li>
<li><strong>Rust 기반 React Compiler</strong>: 기존 Babel 변환 대비 20~50%의 컴파일 속도 향상이 확인됐으며, <code>turbopackRustReactCompiler</code> 플래그로 실험적으로 사용할 수 있습니다.</li>
<li><strong>개발 경험 개선</strong>: Vite 호환 <code>import.meta.glob</code> API, HMR 콜드 스타트 15% 이상 단축, 필요한 기능만 포함하는 축소된 런타임, 모노레포를 위한 로컬 PostCSS 설정 등 실무에 바로 체감되는 변화들이 포함됐습니다.</li>
</ul>
