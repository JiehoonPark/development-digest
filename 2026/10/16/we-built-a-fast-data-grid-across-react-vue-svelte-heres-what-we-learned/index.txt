19:T4772,<p>SVAR는 데이터 그리드, 간트 차트, 캘린더처럼 기능이 많고 무거운 UI 컴포넌트를 만드는 팀입니다. 이 컴포넌트들은 공통적으로 대용량 데이터를 다뤄야 하기 때문에 성능이 생명인데요, 특이하게도 이 팀은 같은 컴포넌트를 React, Vue, Svelte 세 프레임워크로 각각 만들어 배포합니다. 보통 프레임워크 비교 글은 한 프레임워크에 익숙한 사람이 나머지 두 개는 문서만 훑어보고 쓰는 경우가 많은데, 이 팀은 세 프레임워크 모두에서 실제로 고성능 컴포넌트를 세 번 만들어봐야 했던 셈입니다. 이 글은 그 과정에서 얻은 인사이트를 정리한 것으로, 데이터 그리드를 세 프레임워크에 걸쳐 어떻게 빠르게 만들었는지를 다룹니다.</p>
<p>결론부터 말하면 다소 의외인데요, 빠른 데이터 그리드를 만들 때 비용이 많이 드는 부분은 거의 전적으로 프레임워크와 무관했고, 프레임워크마다 진짜 차이가 나는 지점은 흔히 떠도는 &quot;프레임워크 전쟁&quot; 수준의 차이보다 훨씬 좁았습니다. 그래서 이 글은 의도적으로 승자를 가리지 않습니다.</p>
<h3>프레임워크와 무관한 성능 문제</h3>
<p>데이터 그리드는 이런 비교에 좋은 테스트 케이스입니다. 누구나 한 번쯤 만들어보거나 써봤을 만큼 구조는 단순하지만, 동시에 다른 컴포넌트들과 달리 데이터 양이 압도적으로 많습니다. 1,000개 행은 평범한 수준이고 10,000개 행도 드물지 않아서, 처음부터 이를 염두에 두고 설계해야 합니다.</p>
<p>(참고로 SVAR React DataGrid가 20만 행, 2만 열을 렌더링하는 데모가 있는데, 터무니없는 숫자처럼 보이지만 실제로 부드럽게 동작합니다.)</p>
<p>10,000개 행을 그대로 DOM에 렌더링하면 React, Vue, Svelte 할 것 없이 모두 똑같이 무너집니다. 세 프레임워크 모두 결국 브라우저에게 수십만 개의 DOM 노드를 만들고 레이아웃을 계산하라고 요청하게 되고, 그 순간 병목은 브라우저가 됩니다. 프레임워크 자체는 거의 의미가 없어지는 거죠. 이 실패 지점은 비용의 우선순위를 명확히 보여줍니다.</p>
<ul>
<li>HTML을 생성하는 것이 어떤 프레임워크에서든 가장 느린 작업입니다.</li>
<li>JavaScript 연산은 저렴하지만, 컴포넌트 규모가 커지면 더 이상 공짜가 아닙니다.</li>
<li>프레임워크 오버헤드(가상 DOM 대 컴파일된 DOM 조작)는 앞의 두 가지에 비하면 반올림 오차 수준입니다.</li>
</ul>
<p>이 순서를 이해하고 나면, 아래에서 설명할 구체적인 기법들은 대부분 당연한 선택처럼 보입니다.</p>
<h3>SVAR DataGrid의 공통 아키텍처</h3>
<h4>엔진과 통합 레이어</h4>
<p>프레임워크 독립성은 설계할 가치가 충분합니다. SVAR 그리드는 프레임워크에 종속되지 않는 코어(데이터 구조, 설정 정규화, 레이아웃 계산 등)와 프레임워크별 얇은 통합 레이어로 나뉩니다.</p>
<p>어려운 작업은 모두 코어에서 처리됩니다. 통합 레이어는 코어의 상태를 각 프레임워크의 리액티브 프리미티브로 변환하는 역할만 하는데, 이 분리 구조 덕분에 React, Vue, Svelte 세 버전을 동시에 유지보수하는 것이 현실적으로 가능해졌습니다.</p>
<p>세 프레임워크를 동시에 지원해야만 이 아이디어가 유용한 건 아닙니다. React 앱 하나만 만들더라도 무거운 로직을 컴포넌트 밖으로 빼두면 테스트하기 쉽고, 프로파일링하기 쉬우며, 렌더 사이클에서 발생하는 우발적인 문제로부터 자유로워집니다.</p>
<h4>가상화는 기본값이다</h4>
<p>모든 데이터를 그대로 렌더링하는 건 애초에 선택지가 아니므로, 이 그리드(그리고 대부분의 SVAR 컴포넌트)는 렌더링 가상화를 기본으로 사용합니다. 컨테이너의 크기를 측정해서 화면에 보이는 행과 열만 렌더링하는 방식입니다.</p>
<p>동시에 전체 데이터셋이 렌더링된 것처럼 보이고 동작하도록 숨겨진 플레이스홀더를 그려둡니다. 스크롤이 발생하면 데이터 스토어에 새로 보여야 할 구간을 요청하고, 이를 일반적인 React/Svelte/Vue 컴포넌트로 렌더링합니다.</p>
<p>세 프레임워크 모두 이 작업에 특화된 기능을 제공하지 않습니다. 전용 프리미티브도, 내장 헬퍼도 없습니다. 가상화는 순수한 DOM 엔지니어링의 영역이고, 전적으로 개발자의 몫입니다. 프레임워크가 하는 일은 그저 &quot;화면에 보여주기로 한 15개 행을 다시 렌더링하는 것&quot;뿐이고, 이 부분은 세 프레임워크 모두 무난하게 잘 해냅니다.</p>
<p>그런데 가상화는 데이터를 렌더링하기도 전에 첫 번째 문제를 만듭니다. 어떤 행이 보이는지 알려면 컨테이너의 크기가 필요한데, 크기를 알려면 뭔가를 렌더링해야 합니다. 일종의 닭과 달걀 문제인 셈입니다.</p>
<p>이를 해결하는, 세 프레임워크 모두에 통하는 패턴은 다음과 같습니다. 먼저 스타일만 적용된 빈 컨테이너를 렌더링하고, ResizeObserver를 붙인 뒤, 0이 아닌 첫 번째 크기 값이 들어올 때까지 실제 데이터 렌더링을 미루는 것입니다. 0은 정당한 중간 상태인데, 컨테이너에 높이를 부여하는 CSS가 아직 로딩 중일 수 있기 때문입니다.</p>
<pre><code class="language-js">// React, but the same logic ports to Svelte and Vue as is
const [size, setSize] = useState({ height: 0 });
useEffect(() =&gt; {
  const element = viewportRef.current;
  if (!element) return;

  const observer = new ResizeObserver(
    ([entry]) =&gt; setSize({ height: entry.contentRect.height })
  );
  observer.observe(element);

  return () =&gt; observer.disconnect();
}, []);

if (!size.height) return null;
return render();</code></pre>
<p>여기서 React만 가진 무기가 하나 있는데, 바로 <code>useLayoutEffect</code>입니다. 이 훅은 DOM이 만들어진 뒤, 브라우저가 화면을 그리기 전에 실행되기 때문에, 컨테이너를 측정하고 상태를 업데이트한 결과가 사용자가 보는 바로 첫 프레임에 반영될 수 있습니다.</p>
<pre><code class="language-js">// react only
const [size, setSize] = useState({ height: 0 });
useLayoutEffect(() =&gt; {
  const element = viewportRef.current;
  setSize({ height: element.offsetHeight });
});

if (!size.height) return null;
return render();</code></pre>
<p>사람들은 흔히 <code>useLayoutEffect</code>를 위험한 도구라고 놀리는데, 대체로 맞는 말입니다. 하지만 가상화 초기 측정은 이 훅이 진가를 발휘하는 몇 안 되는 사례 중 하나입니다.</p>
<p>다만 솔직하게 말하면, 실제로는 결국 ResizeObserver 방식으로 되돌아가는 경우가 많습니다. 외부 스타일시트, 폰트, 이미지가 아직 로드되지 않아서 크기가 영향을 받기 때문에, <code>useLayoutEffect</code> 콜백 시점에도 레이아웃이 준비되지 않은 경우가 흔하거든요. 그래서 어차피 observer는 필요하고, <code>useLayoutEffect</code>는 이를 대체하는 게 아니라 그 위에 얹는 &quot;첫 프레임 최적화&quot; 정도의 역할을 하게 됩니다.</p>
<p>Svelte와 Vue에는 <code>useLayoutEffect</code>에 대응하는 개념이 없습니다. Svelte의 <code>$effect.pre</code>는 DOM이 업데이트되기 전에 실행되어 측정하기엔 너무 이르고, <code>onMount</code>와 <code>tick()</code>은 DOM이 존재한 뒤 실행되지만 그 안에서 만든 변경사항은 다음 프레임에 그려져서 일반 ResizeObserver 대비 얻는 게 없습니다.</p>
<p>Vue도 같은 구조입니다. <code>onBeforeUpdate</code>는 너무 이르고, <code>onUpdated</code>는 DOM을 볼 수 있지만 그 안의 변경사항은 다음 렌더링 프레임에 반영됩니다. 이 지점은 React의 진짜 장점이지만, 그 범위는 좁습니다. 다른 두 프레임워크의 설계도 나름의 근거가 있고, 애초에 React가 이 훅을 갖게 된 것도 React 자체의 렌더 사이클 구조 때문입니다.</p>
<h4>SSR에 대한 짧은 이야기</h4>
<p>가상화와 서버사이드 렌더링(SSR)은 태생적으로 충돌합니다. 서버는 사용자의 뷰포트에 어떤 행이 들어올지 알 수 없으므로, 올바른 구간을 렌더링할 방법이 없습니다. 하지만 실제로 겪어보면 이게 생각만큼 큰 문제는 아닙니다.</p>
<p>SSR을 쓰는 이유는 대개 첫 페인트 속도 개선과 SEO인데, 첫 페인트는 가상화가 이미 나름의 방식으로 해결하고 있고, SEO는 애초에 10만 개 행 중 15개만 렌더링하는 컴포넌트에서는 작동할 수 없는 목표입니다.</p>
<p>순수 React나 Vue를 쓴다면 이 충돌을 체감할 일이 거의 없습니다. 하지만 Next.js나 Nuxt를 쓴다면 보통 hydration mismatch 에러가 줄줄이 발생하는 형태로 느끼게 됩니다. 해법은 생각보다 단순합니다. 그리드를 클라이언트 전용 컴포넌트로 지정하면 에러가 사라집니다. 받아들이고 넘어가야 할 트레이드오프인 셈입니다.</p>
<h4>내부 로직: 메모이제이션과 파생 상태</h4>
<p>본론에 들어가기 전에 짚을 점이 있습니다. SVAR 컴포넌트는 폭넓은 사용자층을 대상으로 하기 때문에 모든 버전의 React와 호환되어야 하고, 그래서 메모이제이션 지시문을 코드에 직접 손으로 배치합니다. 만약 최신 코드베이스에서 React Compiler를 사용할 수 있는 환경이라면, 컴파일러가 이 작업을 수동 배치보다 훨씬 잘 처리해줄 겁니다. 그런 경우라면 아래 <code>useMemo</code> 관련 내용은 무시해도 됩니다. 유효한 기법이긴 하지만 React Compiler가 도입되면 불필요해지는 기법이니까요.</p>
<p>React의 원래 성능 전제는 &quot;HTML 렌더링은 느리고 JavaScript는 빠르니, 컴포넌트 코드를 매번 다시 실행해도 괜찮다&quot;는 것이었습니다. 단순한 버튼이라면 이 전제가 완벽하게 통합니다.</p>
<p>하지만 데이터 그리드는 렌더링하기 전에 데이터와 설정을 정규화하고, 레이아웃을 계산하고, 컬럼 지오메트리를 해석해야 합니다. 간트 컴포넌트는 더 많은 연산을 합니다. 이 정도 규모에서는 렌더링마다 모든 걸 다시 계산하는 게 더 이상 괜찮지 않습니다.</p>
<p><code>useMemo</code>와 <code>useCallback</code>이 React의 표준 해법이고, 복잡한 컴포넌트에서는 가장 중요한 도구입니다.</p>
<pre><code class="language-js">// React
const normalizedHeaders = useMemo(() =&gt; normalize(columns), [columns]);
const columnCount = normalizedHeaders.length;</code></pre>
<p>Svelte는 같은 아이디어를 <code>$derived</code>로 표현합니다.</p>
<pre><code class="language-js">// Svelte
const normalizedHeaders = $derived(normalize(columns));
const columnCount = $derived(normalizedHeaders.length);</code></pre>
<p>Vue는 <code>computed</code>를 씁니다.</p>
<pre><code class="language-js">// Vue
const normalizedHeaders = computed(() =&gt; normalize(columns));
const columnCount = computed(() =&gt; normalizedHeaders.value.length);</code></pre>
<p>내부에서 돌아가는 리액티비티 메커니즘은 완전히 다르지만, 사용법은 거의 다르지 않습니다. 세 프레임워크 모두 &quot;입력값이 바뀌기 전까지는 이 값을 보존한다&quot;는 동일하고 저렴한 계약을 제공합니다.</p>
<p>실제로 그리드의 가상화 연산(보이는 행 범위, 좌/우/중앙 컬럼 분할, 전체 스크롤 높이)을 포팅할 때, <code>useMemo</code>에서 <code>$derived.by</code>, <code>computed</code>로 거의 한 줄 단위로 그대로 옮겨졌습니다. <code>$x</code>, <code>x.value</code>, 일반 값 같은 문법만 바뀔 뿐 로직은 그대로 포팅됩니다. 한 프레임워크를 안다면 이미 나머지 둘도 이해하고 있는 셈입니다.</p>
<p>이런 유사함 속에서도 진짜 차이가 하나 숨어있습니다. React는 의존성 배열을 직접 손으로 작성해야 합니다. 그리드의 <code>renderRows</code> 메모는 여덟 개의 의존성을 나열하는데, 하나라도 빠뜨리면 디버깅하기 지독히 어려운 &quot;오래된 상태의 그리드&quot;가 만들어집니다. Svelte와 Vue는 의존성을 자동으로 추적합니다.</p>
<h4>React, Vue, Svelte의 기본 동작 방식이 만드는 차이</h4>
<p>프레임워크의 기본 동작 방식 이야기를 하자면, 컴포넌트 코드가 &quot;언제&quot; 실행되는지에 구조적인 차이가 있고, 이 차이가 거의 모든 것을 좌우합니다. Svelte와 Vue는 컴포넌트의 setup 코드를 단 한 번만 실행합니다. React는 렌더링할 때마다 함수 본문 전체를 다시 실행합니다.</p>
<p>Svelte나 Vue에서는 &quot;데이터 스토어를 생성한다&quot;가 그냥 평범한 한 줄짜리 구문입니다. React에서 같은 의도를 구현하려면 여러 관용구를 조합해야 합니다. 스토어를 위한 <code>useMemo(() =&gt; new DataStore(...), [])</code>, 이벤트 버스 연결을 위한 null 체크가 딸린 <code>useRef</code>, 그리고 effect는 페인트 이후에 실행되어 첫 프레임에는 너무 늦기 때문에 <code>useEffect</code> 바깥에 둬야 하는 동기적인 첫 렌더 초기화 호출까지. 하나의 개념을 위해 네 가지 관용구가 필요한 셈입니다.</p>
<p>하지만 이 모델에도 이면이 있습니다. Svelte와 Vue는 setup 코드를 한 번만 실행하기 때문에, 리액티비티는 명시적으로 opt-in해야 하는 것이 되고, 그 결과 의도치 않은 재계산이 설계상 거의 발생하지 않습니다. 대신 위험은 다른 곳으로 옮겨갑니다. 애초에 어떤 값을 리액티브하게 만드는 걸 깜빡해서, 조용히 업데이트되지 않는 뭔가를 그대로 배포해버릴 수 있다는 점이죠. 실무에서는 자동 의존성 추적과 린트 도구가 이런 사례 대부분을 잡아줍니다.</p>
<p>그러니 이건 우열의 문제가 아니라 트레이드오프의 문제입니다. React 모델은 기본적으로 더 위험하지만 완전히 명시적이어서 무슨 일이 일어나는지 항상 볼 수 있습니다. Svelte와 Vue는 기본적으로 더 안전하지만, 가끔씩 예상치 못한 방식으로 놀라게 만듭니다.</p>
<p>그렇다고 모든 걸 <code>useMemo</code>로 감싸라는 뜻은 아닙니다. 대부분의 연산은 신경 쓸 필요가 없을 만큼 저렴합니다. 코드를 읽거나, 더 좋게는 프로파일링을 통해 무거운 부분을 찾아내고, 그 부분만 렌더링 사이에 보존하세요. 그게 전부입니다.</p>
<h4>참고: 하나의 스토어, 세 개의 어댑터</h4>
<p>SVAR 컴포넌트에서는 메모이제이션만으로는 충분하지 않았기 때문에, 프레임워크와 무관한 단일 리액티브 스토어를 운영하고 이를 각 프레임워크의 프리미티브에 맞게 어댑팅합니다.</p>
<p>Svelte는 <code>$store</code> 자동 구독 기능이 있는 진짜 <code>svelte/store</code> writable을 통해 이 스토어를 소비합니다. Vue는 작은 <code>subscribe()</code> 헬퍼를 통해 ref를 받습니다.</p>
<p>React는 훅을 받는데, <code>useStore(api, 'name')</code>은 <code>useState</code>와 <code>useEffect</code> 안의 구독으로 구성됩니다. React는 추가 장치가 하나 더 필요했는데, 바로 <code>useStoreWithCounter</code> 훅입니다. 배열이 제자리에서(in place) 변경되면 참조 동등성 비교로는 변화를 감지할 수 없기 때문에, 변경 카운터를 의존성으로 쓸 수 있도록 반환해주는 훅입니다.</p>
<p>하나의 프레임워크만 타겟팅한다면 이런 장치는 전혀 필요 없습니다. React와 Vue 모두 성숙한 외부 스토어 생태계를 갖추고 있고, Svelte 5의 <code>.svelte.js</code> 상태 모듈은 정말 괜찮은 네이티브 옵션입니다. 다만 하나의 스토어가 세 프레임워크를 모두 섬겨야 했던 SVAR의 상황에서는 선택할 수 없는 옵션이었을 뿐입니다.</p>
<h3>정리</h3>
<p>SVAR 팀이 React, Vue, Svelte 세 프레임워크로 동일한 데이터 그리드를 만들며 얻은 결론은 명확합니다.</p>
<ul>
<li><strong>비용 구조는 프레임워크와 무관하다.</strong> HTML 생성이 가장 비싸고, JS 연산은 규모가 커지면 더 이상 공짜가 아니며, 가상 DOM 대 컴파일 방식의 차이는 그에 비하면 오차 수준입니다.</li>
<li><strong>가상화는 세 프레임워크 어디서도 기본 제공되지 않는다.</strong> 보이는 범위만 렌더링하고 나머지는 플레이스홀더로 채우는 건 순수 DOM 엔지니어링의 영역이며, 초기 크기 측정을 위해 빈 컨테이너 렌더링 → ResizeObserver 연결 → 첫 유효 크기 대기라는 패턴이 세 프레임워크 모두에 통합니다.</li>
<li><strong>React만의 좁은 장점이 있다.</strong> <code>useLayoutEffect</code>는 첫 프레임 측정에서 Svelte/Vue에 없는 이점을 주지만, 실제로는 폰트·스타일시트 로딩 문제로 ResizeObserver와 함께 써야 하는 보조 수단에 가깝습니다.</li>
<li><strong>메모이제이션 문법은 다르지만 개념은 동일하다.</strong> <code>useMemo</code>/<code>computed</code>/<code>$derived</code>는 거의 1:1로 포팅 가능하며, 유일한 실질적 차이는 React가 의존성 배열을 수동으로 관리해야 한다는 점입니다.</li>
<li><strong>기본 실행 모델의 차이가 개발 경험을 가른다.</strong> React는 매 렌더마다 함수 전체를 재실행해 위험하지만 명시적이고, Svelte/Vue는 setup을 한 번만 실</li>
