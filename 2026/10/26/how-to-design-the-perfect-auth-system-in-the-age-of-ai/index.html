How To Design The Perfect Auth System In The Age of AI

📅 2026-10-26📰 React Conf🎬 Video
frontendai

권한(permission) 시스템은 애플리케이션에서 가장 중요한 부분 중 하나입니다. 여기서 실수를 하면 앱 전체를 망가뜨릴 수 있는 치명적인 버그로 이어지기 때문인데요. Web Dev Simplified의 Kyle은 수년간 다양한 권한 시스템을 설계해왔고, 관련 강의까지 만든 경험을 바탕으로 이번 영상에서 권한 시스템을 바라보는 고수준 시스템 설계 관점을 정리합니다. 직접 코드를 짜든 AI에게 구현을 맡기든 상관없이 통하는 이야기인데, 설계를 제대로 해두면 사람이 코딩할 때 시간을 아낄 뿐 아니라 AI로 구현할 때도 토큰과 시간을 크게 절약할 수 있다는 것이 핵심 포인트입니다.

이 글에서 다룰 것들

권한 시스템을 설계할 때 고려해야 할 축은 크게 세 가지입니다.

첫째, 어떤 종류의 권한 시스템을 쓸 것인지, 그리고 코드 안에서 그것을 어떻게 구조화할 것인지입니다. 둘째, 권한 데이터를 어디에 저장할 것인지입니다. 코드 안에 하드코딩할 수도 있고(가장 흔한 방식), 데이터베이스에 저장할 수도 있고, JSON 같은 별도 파일 포맷으로 관리할 수도 있으며, 이들을 조합하는 방식도 있습니다. 각각의 장단점을 따져봐야 합니다. 셋째, AI 시대에 특화된 고려사항입니다. 코드를 생성할 때 토큰을 얼마나 아낄 수 있는지, 사람이 변경사항을 피로감 없이 리뷰할 수 있는지, AI가 빠르고 정확하게 작업할 수 있는지를 따져봐야 합니다. 이 외에도 권한이 정적(static)인지 동적(dynamic)인지, 권한 매트릭스를 편집할 UI가 필요한지 같은 부가적인 고려사항들도 있습니다.

애드혹 권한 시스템: 나쁜 예시로 배우기

이를 설명하기 위해 먼저 평범하거나 다소 부실한 권한 시스템의 실제 예시를 살펴봅니다. 데모로 사용하는 앱은 칸반 스타일의 보드 여러 개로 구성되어 있고, 사용자들은 소속 부서나 특정 보드 초대 여부에 따라 접근 권한을 얻습니다.

  • 디자인 부서 소속인 마야는 웹 디자인 보드에 속해 있지만, 부서 소속이 아님에도 모바일 앱 보드에 초대받아 접근할 수 있습니다.
  • 엔지니어링 소속의 프로덕트 매니저는 작업 삭제 등 일반 사용자가 할 수 없는 작업들을 수행할 수 있습니다.
  • 읽기 전용 사용자와 일반 사용자도 존재하며, 일반 멤버는 삭제 권한이 없는 등 상대적으로 적은 권한을 가집니다.

이 앱 안에는 역할(role), 그룹(디자이너, 엔지니어 등), 사용자 초대 권한, 보드 내 작업에 대한 세부 권한 등 꽤 복잡한 권한 로직이 기본 권한 시스템 위에 쌓여 있습니다. 그리고 만약 여러분이 AI로 이런 앱을 만들었다면, 십중팔구 이와 비슷한 구조의 권한 시스템을 얻게 될 가능성이 큽니다. Kyle은 이 앱에서 권한을 체크하는 거의 모든 지점을 표시해두었는데, 이는 "권한이 코드 어디에 있고 어떻게 작성되어 있는지"가 권한 시스템에서 가장 중요한 두 가지 요소이기 때문입니다.

이 시스템은 나름의 조직화는 되어 있지만 충분하지 않다는 의미에서 애드혹(ad hoc) 권한 시스템이라 부를 수 있습니다. 권한 체크 코드는 다음과 같이 앱 전체에 흩어져 있습니다.

  • API: 당연히 API 내부에 권한 체크가 존재합니다.
  • 프론트엔드: UI 전반에 걸쳐 권한 관련 체크가 산재해 있습니다.
  • Auth 폴더: 누가 무엇에 접근할 수 있는지 확인하고 권한 정보를 가져오는, 다소 중앙화된 영역이지만 전부는 아닙니다.
  • 보드 공유(Board sharing) 섹션: 역할별 권한을 체크합니다.
  • 보드 데이터(Board data) 섹션: 마찬가지로 역할 기반 권한을 체크합니다.
  • 뮤테이션(Mutation) 섹션: 데이터를 변경하는 로직에서 직접 역할을 체크합니다.

즉 UI는 한 세트의 권한 로직을, 백엔드는 또 다른 세트의 권한 로직을 사용하고 있는 셈입니다. 지금은 둘이 동기화되어 있지만 언제든 어긋날 수 있습니다. 예를 들어 "이제 매니저뿐 아니라 더 많은 사람이 태그를 생성할 수 있다"는 규칙을 한쪽에서는 반영하고 다른 쪽에서는 깜빡한다면, UI와 백엔드 사이에 불일치가 생기고 이는 곧 버그와 사용자 불만으로 이어집니다.

서비스 레이어는 있지만 여전히 부족한 이유

전체 구조로 돌아가 보면, 이 앱은 필요한 곳에 그때그때 권한 체크를 박아 넣는 애드혹 방식을 쓰고 있습니다. 어느 정도 서비스 레이어는 존재합니다. 모든 뮤테이션이 일어나는 레이어가 있어서, API와 프론트엔드가 할 일(todo) 목록을 업데이트할 때 같은 함수를 사용하긴 합니다. 적어도 일부 로직에 대한 중앙화된 지점은 있는 셈이지만, 정작 UI를 렌더링하는 코드는 실제 작업을 수행하는 백엔드 코드와는 전혀 다른 코드를 사용하고 있어서 둘 사이에 일관성이 없습니다.

데이터베이스 통합(database integration)도 전혀 없습니다. 모든 권한이 애드혹하게 처리되다 보니 자연스럽게 데이터베이스 단에 반영되지 않습니다. 여기서 데이터베이스 통합이란, 예를 들어 "사용자는 특정 항목만 접근할 수 있다"는 권한 규칙을 작성했을 때 그것이 데이터베이스 레벨에서 강제되어 항상 올바른 데이터만 받아오도록 하는 것을 말합니다. 이게 안 되어 있으면 개발자가 매번 올바른 쿼리를 작성하고 올바른 위치에 사용했는지 직접 챙겨야 합니다.

또한 단일 진실 공급원(single source of truth)도 없습니다. 권한 로직이 앱 곳곳에 흩어져 있기 때문입니다. 결론적으로 서비스 레이어 방식은 어느 정도 맞는 방향이지만, 나머지 두 축(스토리지 방식, 단일 소스)은 완전히 실패하고 있고, 더 나은 모델들은 전혀 활용되지 못하고 있습니다.

AI 관점에서 바라본 애드혹 시스템의 실패

스토리지 방식을 보면 모든 권한이 코드 안에 들어있는데, 이 자체는 충분히 합리적인 선택입니다. 하지만 AI 활용 관점에서 보면 이 시스템은 여러 항목에서 낙제점을 받습니다.

  • 토큰 효율성과 속도: 권한이 앱 전체에 흩어져 있다 보니, AI가 무엇을 바꿔야 할지 파악하려면 애플리케이션 전체를 읽어야 합니다. 이는 느릴 뿐 아니라 토큰도 많이 소모합니다.
  • 오류 발생 가능성: 모든 곳을 다 읽어야 하기 때문에, 권한 체크 지점을 단 한 곳이라도 놓치면 바로 버그로 이어집니다.
  • 리뷰의 어려움: 권한 로직이 사방에 흩어져 있으니, 변경사항이 생길 때마다 풀 리퀘스트 전체를 읽으면서 권한 관련 지점이 모두 제대로 반영되었는지, 빠뜨린 곳은 없는지 일일이 확인해야 합니다.

종합하면, 이 애드혹 권한 시스템은 거의 모든 카테고리에서 실패하고 있다고 볼 수 있습니다.

대안: RBAC(역할 기반 접근 제어)

가장 쉽게 넘어갈 수 있는 대안이 바로 RBAC(Role-Based Access Control, 역할 기반 접근 제어)입니다. 이는 애드혹 시스템의 많은 문제를 해결해줍니다.

예시로 보여준 (다른 프로젝트지만 비슷한 권한 구조를 가진) RBAC 시스템에서는, permissions 폴더 안에 RBAC 하나만 존재하고, 코드에서는 오직 can 함수 하나만 호출하면 됩니다. 이 can 함수는 사용자의 역할(role)과 체크하고자 하는 권한(permission)을 인자로 받아, 해당 사용자가 그 작업을 수행할 수 있는지 여부에 따라 true/false를 반환합니다.

즉, 앱 어디에서든 권한 체크가 필요할 때 전부 can(user, permission) 형태로 동일하게 호출하게 되므로 매우 단순해집니다. 권한을 업데이트하고 싶을 때도 수정할 곳이 한 군데뿐이고, 권한을 호출하는 모든 코드가 앱 전역에서 동일한 함수를 사용하게 됩니다.

내부적으로는 각 역할(role)에 대해 접근 가능한 권한 목록을 할당하는 방식으로 동작합니다. "역할 기반" 접근 제어라는 이름이 여기서 나옵니다. 이 방식은 복잡한 권한 구조가 없는 단순한 프로젝트에 특히 훌륭한 선택지입니다.

RBAC의 한계

하지만 "이 사용자를 프로젝트에 초대할 수 있다", "이 사용자는 자신이 만든 문서만 수정할 수 있다"처럼 좀 더 복잡한 권한 규칙이 추가되기 시작하면 RBAC는 한계를 드러냅니다.

실제로 데모 앱에는 이런 엣지 케이스들을 따로 처리하는 별도 섹션이 존재합니다. 예를 들어 "이 사용자가 특정 프로젝트를 읽을 수 있는가?"라는 질문 하나에도 다음과 같은 여러 조건이 얽혀 있습니다.

  • 해당 프로젝트에 초대되었는가?
  • 해당 프로젝트가 자신의 부서 소속 프로젝트인가?
  • 관리자(admin)라서 원래부터 모든 것을 읽을 수 있는가?

이처럼 단 하나의 권한 체크 뒤에도 생각보다 많은 로직이 숨어 있습니다. 지금 수준에서는 아직 관리할 만하지만, 애플리케이션에 엣지 케이스가 계속 늘어날수록 이를 다루는 작업은 점점 더 까다로워집니다.

또한 이 앱에는 서비스 레이어도 존재하는데, AI가 이 부분은 스스로 꽤 잘 구현해냈습니다. 다만 이 서비스 레이어 내부에 다양한 can 체크 로직들이 포함되어 있다는 점은 여전히 주목할 부분입니다.

정리

  • 권한 시스템 설계에서 가장 중요한 것은 권한 로직이 어디에 있고, 어떻게 작성되어 있는지를 명확히 하는 것입니다.
  • 권한 체크 코드가 API, 프론트엔드, auth 폴더, 보드 관련 섹션, 뮤테이션 로직 등 애플리케이션 전역에 흩어진 애드혹 방식은 UI와 백엔드 간 불일치, 버그, 사용자 불만을 야기하기 쉽습니다.
  • 애드혹 시스템은 데이터베이스 레벨 강제(DB integration)도 없고 단일 진실 공급원(single source of truth)도 없어서, 사람이 유지보수하기도 힘들고 AI가 다루기에도 비효율적입니다. 토큰 소모가 크고, 속도가 느리며, 오류 발생 가능성이 높고, 리뷰도 고통스러워집니다.
  • 이에 대한 개선책으로 제시된 것이 RBAC(역할 기반 접근 제어)입니다. 모든 권한 체크를 can(user, permission) 같은 단일 함수로 통일하면, 수정 지점이 하나로 모이고 앱 전체에서 일관된 로직을 사용하게 되어 단순 프로젝트에는 매우 효과적입니다.
  • 다만 "자신이 만든 문서만 수정 가능" 같은 소유권·관계 기반의 복잡한 권한 규칙이 늘어나면 RBAC만으로는 한계가 드러나며, 이런 엣지 케이스를 처리할 별도의 설계가 필요해집니다.

실무적으로는, 지금 작업 중인 프로젝트가 단순한 역할 구조라면 RBAC로 충분하지만, 소유권 기반 권한이나 동적인 조건이 늘어나는 시점이라면 더 정교한 모델(예: 속성 기반 접근 제어 등)로의 전환을 미리 염두에 두는 것이 좋습니다. 그리고 AI로 코드를 생성하는 워크플로우를 쓰고 있다면, 권한 로직을 한곳에 모아두는 것 자체가 토큰 비용 절감과 리뷰 효율성 측면에서 분명한 이득이 된다는 점을 기억해둘 만합니다.
