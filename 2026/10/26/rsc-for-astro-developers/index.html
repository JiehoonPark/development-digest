Astro 개발자를 위한 RSC 이해하기

RSC for Astro Developers

📅 2026-10-26📰 Dan Abramov (overreacted)
frontend

Astro 개발자를 위한 RSC 이해하기

React Server Components(RSC)는 배우기 꽤 까다로운 개념으로 알려져 있는데요, 사실 Astro를 이미 써본 개발자라면 그 멘탈 모델의 상당 부분을 이미 알고 있는 셈입니다. Dan Abramov는 이 글에서 Astro의 핵심 개념을 RSC로 1:1 대응시켜가며, 두 모델이 얼마나 닮아 있는지, 그리고 어디서 갈라지는지를 설명합니다.

Astro의 두 가지 세계

Astro에는 두 가지 종류의 컴포넌트가 있습니다.

Astro Components는 .astro 확장자를 가지며 서버 또는 빌드 시점에만 실행됩니다. 즉 코드가 클라이언트로 전송되지 않습니다. 그래서 파일 시스템을 읽거나, 내부 서비스를 호출하거나, 데이터베이스를 조회하는 등 클라이언트 코드로는 할 수 없는 일을 할 수 있습니다. 대신 HTML이 기본 제공하는 기능이나 직접 작성한 <script> 외에는 인터랙티브한 동작을 할 수 없습니다. Astro Component는 다른 Astro Component나 Client Island를 렌더링할 수 있습니다.

Client Islands는 React, Vue 등으로 작성된 컴포넌트입니다. 일반적인 프런트엔드 코드가 들어가는 곳이고, 인터랙티브한 부분을 넣기에 적합합니다. Client Island는 같은 프레임워크의 방식대로 다른 컴포넌트를 렌더링할 수 있습니다. 하지만 Client Island에서 Astro Component를 렌더링할 수는 없습니다—이미 Astro의 실행이 끝난 시점이기 때문에 말이 안 되는 거죠.

다음은 PostPreview.astro라는 Astro Component가 LikeButton Island를 렌더링하는 예시입니다.

---
import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';
const { slug } = Astro.props;
const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
---
<article>
<h1>{title}</h1>
<LikeButton client:load />
</article>
import { useState } from 'react';
export function LikeButton() {
const [liked, setLiked] = useState(false);
return (
<button onClick={() => setLiked(!liked)}>
{liked ? '❤️' : '🤍'} Like
</button>
);
}

여기서 주목할 점은 Astro Component와 Client Island가 완전히 분리된 두 "세계"에 살고 있고, 데이터는 오직 위에서 아래로만 흐른다는 것입니다. Astro Component에서 모든 전처리가 일어나고, 인터랙티브한 부분은 Client Island에 "넘겨주는" 구조입니다.

RSC로 똑같이 그려보기

RSC에서는 같은 두 가지 개념이 Server Components와 Client Components라고 불립니다. 위의 Astro Component를 React Server Component로 작성하면 이렇게 됩니다.

import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';
async function PostPreview({ slug }) {
const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
return (
<article>
<h1>{title}</h1>
<LikeButton />
</article>
);
}
'use client';
import { useState } from 'react';
export function LikeButton() {
const [liked, setLiked] = useState(false);
return (
<button onClick={() => setLiked(!liked)}>
{liked ? '❤️' : '🤍'} Like
</button>
);
}

두 모델의 멘탈 모델은 놀랍도록 비슷합니다. Astro를 안다면 이미 RSC 멘탈 모델의 80%를 갖춘 셈입니다. (RSC가 별로라고 생각하더라도, Astro는 배워볼 가치가 있습니다.)

몇 가지 문법적 차이를 짚어보면 다음과 같습니다.

  • Astro Component와 달리 React Server Component는 평범한 JavaScript 함수입니다. "단일 파일" 형태가 아니고요, props는 Astro.props가 아니라 함수 인자로 전달되며, 별도의 "템플릿" 영역도 없습니다.
  • Astro에서는 .astro 파일로 작성함으로써 Astro Component와 Client Island의 경계를 만듭니다. Client Island를 import하는 순간 더 이상 .astro 파일 안이 아니게 되고, 그렇게 Astro 세계를 "벗어나게" 됩니다. RSC에서는 같은 역할을 'use client' 디렉티브가 합니다. 이 디렉티브는 서버 세계가 "끝나는" 지점, 즉 두 세계 사이의 문을 표시합니다.
  • Astro에는 client:load처럼 Island를 정적 HTML로 둘지 클라이언트에서 하이드레이션할지를 결정하는 디렉티브가 있습니다. RSC는 이런 구분을 사용자 코드에 노출하지 않습니다. React 입장에서 애초에 인터랙티브하도록 작성된 컴포넌트에서 인터랙티비티를 제거하는 것은 말이 안 되는 일이니까요. 만약 정말로 인터랙티비티가 필요 없다면 그냥 'use client'를 지우면 됩니다. 그러면 서버 세계에서 import하는 순간 자동으로 서버 전용으로 유지됩니다.

경계가 흐릿해진다는 것의 의미

마지막 포인트가 흥미로운 지점입니다. Astro에서는 문법 자체(.astro 파일 vs Client Island)가 두 세계 사이에 뚜렷하고 명확한 시각적 구분을 만듭니다. 같은 컴포넌트가 맥락에 따라 Astro Component도 됐다가 Client Island도 될 수는 없습니다—둘은 애초에 문법이 다른 별개의 존재입니다.

하지만 RSC에서는 "Astro에 해당하는 부분"도 그냥 React입니다. 그래서 클라이언트 전용 기능도, 서버 전용 기능도 쓰지 않는 컴포넌트라면 양쪽 역할을 다 할 수 있습니다.

예를 들어 자체적으로 파싱을 수행하는 <Markdown /> 컴포넌트를 생각해보죠. State 같은 클라이언트 기능도, DB 조회 같은 서버 기능도 쓰지 않으니 어느 쪽에서든 import될 수 있습니다. 서버 세계에서 import하면 "Astro Component"처럼 동작하고, 클라이언트 세계에서 import하면 "Client Island"처럼 동작합니다. 이건 새로운 개념이 아니라, 그냥 함수를 import하는 방식이 원래 그렇다는 것뿐입니다.

RSC에서는 서버 세계에서 import된 것은 서버 세계에서 실행되고, 클라이언트 세계에서 import된 것은 클라이언트 세계에서 실행됩니다. 그리고 어느 쪽에서도 지원되지 않는 것(예: 클라이언트에서의 DB 접근, 서버에서의 useState)은 빌드 에러를 일으켜 'use client'로 "문을 내도록" 강제합니다.

이는 축복이면서 동시에 저주입니다.

저주인 이유는 RSC를 익히는 과정 자체가 직관적이지 않기 때문입니다. 계속 "내가 지금 어느 세계에 있는지" 신경 쓰게 됩니다. 사실 그건 중요하지 않다는 것—즉 항상 로컬하게 추론할 수 있다는 것을 받아들이기까지는 연습이 필요합니다. DB 같은 서버 기능이 필요한 파일에서는 그걸 쓰고, State 같은 클라이언트 기능이 필요한 파일에서는 그걸 쓰면 됩니다. 뭔가 잘못되면 빌드 타임 검증이 에러를 내줄 테니, 그 모듈 스택 트레이스를 보고 어디에 새로운 "문"을 낼지 결정하면 됩니다.

저주이자 동시에 축복인 이유는, 양쪽 모두에서 React를 그대로 쓰는 이 모델이 Astro가 가진 몇 가지 한계를 해결해주기 때문입니다.

  • UI를 왔다 갔다 옮길 필요가 없다. Astro Component로 한참 작성하다가 나중에 그 UI를 Client Island로 옮겨야 한다는 걸 깨닫는 경우(문법을 손봐야 하죠), 혹은 동적 UI가 같은 걸 필요로 해서 아예 중복 작성해야 하는 경우가 생길 수 있습니다. RSC에서는 공유되는 부분을 추출해서 양쪽에서 import하면 됩니다. "이 부분은 대체로 정적일 거야" 혹은 "이 부분은 대체로 동적일 거야"를 미리 치밀하게 따질 필요가 줄어듭니다. 'use client'를 붙이거나 떼는 것, import 체인에서 위아래로 옮기는 것 모두 마찰 없이 가능하기 때문입니다. "문을 어디에 낼지"는 결정해야 하지만, 앞뒤로 "변환"할 필요는 없습니다.
  • 중첩된 인터랙티브 영역이 자연스럽게 합성된다. Astro에서는 Client Island 안에 Astro Component를 중첩할 수 있지만, 그 안에 또 Client Island가 있다면 프레임워크(예: React) 입장에서는 별개의 루트로 취급됩니다. 그래서 React나 Vue의 context가 Astro Island 사이를 넘나들 수 없고, 인터랙티브한 동작의 중첩이 클라이언트 앱만큼 자연스럽게 합성되지 않습니다. RSC에서는 이게 문제가 되지 않습니다—UI 전체가 내부적으로 하나의 React 트리이기 때문입니다. Server 서브트리 위에 Client context provider를 두고, 그 아래 어디서든 여러 Client 컴포넌트가 그 context를 읽을 수 있습니다. RSC는 프랙탈 구조의 island입니다.
  • SPA 같은 내비게이션이 가능하다. Astro Component는 결국 HTML만 만들어낼 수 있습니다. 그래서 Astro 사이트에서 링크를 클릭하면 브라우저가 페이지를 완전히 새로고침해야 합니다. 이 정도 UX가 용도에 맞는다면 괜찮고, View Transitions 같은 수동 로직으로 개선할 수도 있지만, 근본적으로는 페이지의 HTML이 교체되는 구조입니다. 만약 React 상태든 입력값·스크롤 위치 같은 DOM 상태든 네비게이션 바의 상태를 항상 유지하는 SPA 같은 내비게이션을 원한다면, RSC가 그 공백을 메워줍니다. RSC는 React 트리를 JSON과 유사한 포맷으로 다루는데, 최초 페인트에는 이걸 HTML로 바꾸지만 내비게이션 시에는 JSON으로 다시 가져옵니다. 즉 RSC는 MPA 멘탈 모델로 생각하면서도 SPA처럼 느껴지게 해줍니다.
  • 서버 부분을 그 자리에서 새로고침할 수 있다. Astro와 달리 RSC의 서버 영역은 제자리에서 리프레시가 가능합니다. (제 블로그처럼 빌드 시점에만 RSC를 돌리는 게 아니라) 실제로 서버를 운영한다면, RSC는 언제든 화면을 "새로고침"해서 이미 존재하는 상태 기반 클라이언트 트리 안으로 새로운 서버 props를 흘려보낼 수 있습니다. 예를 들어 어떤 Astro Component가 상호작용에 반응해서 새로고침되어야 한다면, 전체 페이지를 새로고침하거나 로직을 Client Island로 옮기는 것 중 하나를 선택해야 합니다. RSC에서는 그냥 서버로부터 새 JSX를 받아와 트리에 병합하면 됩니다.

근본적인 출력 형식의 차이

Astro의 근본적인 출력 형식은 HTML입니다. 프런트엔드 프레임워크는 원래 HTML 자체가 아니라 HTML로 초기화할 수 있는 상태 기반 DOM을 다루기 때문에, Astro는 "일회성 핸드오프" 모델을 따릅니다. 이 덕분에 배우기는 상대적으로 쉽지만, 서버 기능은 "첫 렌더링"(HTML로의 변환)에 필요한 만큼으로 제한되고, 인터랙티브한 부분은 대체로 개발자 스스로 처리해야 합니다. 더 많은 부분을 인터랙티브하게 만들수록 Astro 모델의 한계를 느끼게 되고, 결국 더 많은 로직을 SPA 같지만 고립된 Island로 옮기게 될 수 있습니다.

RSC의 근본적인 출력 형식은 React 트리입니다(HTML로 변환될 수도 있지만, JSON으로 (재)요청될 수도 있습니다). RSC는 양쪽 모두에서 React를 쓰고 두 세계 사이에 시각적 구분이 없기 때문에 다루는 법을 익히기가 더 까다롭습니다. 대신 일단 경계를 옮기는 감을 잡고 나면 그 경계가 매우 유연해지고, "생각보다 더 정적이거나 더 동적으로 밝혀진" 코드를 "Astro 쪽으로" 혹은 "다시 Island로" 옮겨야 하는 문제 자체가 사라집니다. UI가 읽기 전용이든, 변이(mutation)에 반응해 다시 가져와야 하든 "데이터를 UI로 매핑한다"는 동일한 멘탈 모델을 유지할 수 있습니다. 서버 영역이 트리 더 깊숙이까지 파고들면서 클라이언트 영역과 서로 뒤섞여 있습니다.

그리고 양쪽 모두 React이기 때문에 모든 React 기능이 처음부터 끝까지 통합되어 있습니다. 예를 들어 클라이언트의 선언적 로딩 상태인 <Suspense>는 서버에서 오는 비동기 데이터, 클라이언트가 로드하는 JS와 CSS, 적절한 타임아웃을 가진 폰트와 이미지를 모두 기다릴 줄 알고, 심지어 View Transitions까지 트리거할 수 있습니다. React의 모든 기능은 서버와 클라이언트 조각이 임의로 중첩되고 합성되고 제자리에서 새로고침될 수 있도록 설계되어 있습니다. 하나의 트리인 거죠. 단점이라면 RSC를 받아들인다는 것은 곧 React를 통째로 받아들인다는 뜻이라는 점입니다. RSC는 풀스택 React입니다.

마지막으로 짚어둘 점은, Astro는 프레임워크지만 RSC 자체는 더 낮은 레벨이라는 것입니다. RSC는 프레임워크의 구성 요소, 혹은 프레임워크가 구현할 수 있는 하나의 표준이라고 보는 게 맞습니다. 현재 공식적으로 지원되는 RSC 구현체는 Next.js App Router(프레임워크)와 Parcel RSC(프레임워크 아님) 두 가지입니다.

개인적으로는 RSC의 개발자 경험이 아직은 다소 거칠다고 생각하지만, 그럼에도 배워볼 가치가 있다고 봅니다. 흥미로운 아이디어들이 담겨 있기 때문입니다.

그리고 Astro를 한 번도 써본 적이 없다면 한 번 써보기를 권합니다. RSC가 어렵게 느껴진다면 Astro가 같은 아이디어에 더 완만하게 접근하는 길이 되어줄 수 있습니다. 반대로 클라이언트 사이드 React만 써봤다면, Astro가 미처 깨닫지 못했던 문제들을 해결해줄지도 모릅니다.

정리

  • Astro의 Astro Component/Client Island 구조와 RSC의 Server Component/Client Component 구조는 멘탈 모델 자체가 거의 동일합니다. 데이터는 서버 쪽에서 클라이언트 쪽으로 흐르고, 서버 전용 기능과 클라이언트 전용 기능은 서로 섞일 수 없다는 원칙도 같습니다.
  • 가장 큰 차이는 "경계를 만드는 방식"입니다. Astro는 .astro 파일이라는 문법으로 세계를 명확히 가르는 반면, RSC는 'use client' 디렉티브 하나로 문을 내는 방식이라 같은 컴포넌트가 맥락에 따라 서버에서도 클라이언트에서도 동작할 수 있습니다.
  • 이 유연함 덕분에 RSC는 Astro가 가진 한계—UI를 Island로 옮기며 중복 작성해야 하는 문제, Island 간 context 공유 불가, 풀 페이지 리로드, 서버 부분의 제자리 새로고침 불가—를 해결합니다. 대신 "내가 지금 어느 세계에 있는지"를 항상 신경 써야 하는 학습 곡선을 감수해야 합니다.
  • Astro는 최종적으로 HTML을 출력하는 프레임워크이고, RSC는 React 트리(JSON으로도 직렬화 가능)를 출력하는 더 낮은 레벨의 표준입니다. 이 차이로 인해 RSC는 Suspense, View Transitions 등 React 기능 전체가 서버·클라이언트에 걸쳐 끊김 없이 통합됩니다.
  • RSC를 받아들인다는 것은 React 생태계 전체를 받아들인다는 뜻입니다. 현재 공식 구현체는 Next.js App Router와 Parcel RSC입니다.
💡
Astro와 RSC 둘 다 서버/클라이언트 경계를 다루는 최신 렌더링 패러다임이기 때문에, 두 모델의 공통점과 차이를 이해하면 RSC 특유의 낯선 멘탈 모델을 훨씬 빠르게 체득할 수 있고, 어떤 프로젝트에 어떤 모델이 적합한지 판단하는 데도 도움이 됩니다.
