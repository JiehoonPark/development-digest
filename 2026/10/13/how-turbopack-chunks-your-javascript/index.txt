<h3>청킹이란 무엇인가</h3>
<p>&quot;청킹&quot;은 어떤 코드를 어떤 청크에 넣을지 결정하는 과정입니다. 방법은 다양하고, 각각 트레이드오프가 있습니다. 가장 단순한 접근부터 살펴보겠습니다.</p>
<p><strong>1. 전체를 하나의 청크로</strong></p>
<p>앱이 사용하는 모든 JavaScript를 단 하나의 청크(355개 모듈, 1.09MB)에 넣는 방식입니다. 모든 페이지가 같은 청크를 공유하므로, 첫 로드 이후의 모든 방문은 캐시 히트가 됩니다. 내비게이션은 빨라지겠죠.</p>
<p>하지만 트레이드오프가 분명합니다. JS를 거의 쓰지 않는 페이지도 다른 모든 페이지의 JS를 함께 받아야 합니다. 사이트가 커질수록 모든 페이지 로드가 점점 무거워지는 구조라, 장기적으로는 지속 가능하지 않습니다.</p>
<p><strong>2. 페이지당 하나의 청크</strong></p>
<p>같은 355개 모듈을 8개 청크로 나누되, 페이지 간 공유되는 코드는 필요한 모든 청크에 중복으로 들어갑니다 (8개 청크, 총 1.20MB). 이렇게 하면 청크가 슬림하게 유지되고 불필요한 코드를 내려받을 일도 없습니다.</p>
<p>문제는 캐싱을 잃는다는 겁니다. 모든 페이지가 <code>&lt;Footer /&gt;</code>를 쓴다면, 그 코드는 모든 페이지의 청크 안에 각각 들어갑니다. 방문자가 페이지 4개를 열면 동일한 푸터 코드를 4번 다운로드하는 셈입니다.</p>
<p><strong>3. 모듈당 하나의 청크</strong></p>
<p>더 세밀하게, 모듈마다 자신만의 청크를 갖게 하면 어떨까요? 355개 모듈이 355개의 개별 청크(총 1.09MB)로 쪼개지고, 각 모듈은 딱 한 번만 다운로드됩니다. 이론상으로는 불필요한 코드도, 중복 다운로드도 없는 완벽한 그림입니다.</p>
<p>하지만 작은 문제가 하나 있는데, 수백 개의 작은 JS 파일에 대해 수백 번의 네트워크 요청이 발생한다는 겁니다. 각 요청에는 오버헤드가 따르고, 이게 수백 개 쌓이면 사이트가 느려집니다. HTTP/2 덕분에 요청 비용이 줄긴 했지만 여전히 공짜는 아닙니다. 게다가 gzip 같은 압축 알고리즘은 하나의 파일 안에서만 반복 패턴을 찾을 수 있기 때문에, 파일이 작게 쪼개질수록 압축 효율도 떨어집니다. 압축 사전(compression dictionary)이 도움이 되긴 하지만 근본적인 해결책은 아닙니다.</p>
<h3>요청 수냐, 코드량이냐</h3>
<p>결국 남는 과제는 이겁니다. 다운로드 크기는 최소로, 요청 수도 최소로 만들고 싶은데, 이 두 목표는 서로 충돌합니다. 청크가 적고 클수록 요청 수는 줄지만, 커질수록 페이지 간 재사용성은 떨어집니다.</p>
<p>Turbopack의 해법은 작은 청크들을 더 큰 청크로 병합하는 것입니다. 어려운 부분은 어떤 청크를 언제 병합해야 실제로 이득인지 판단하는 일입니다.</p>
<p>이를 위해 <strong>청크 그룹(chunk group)</strong>이라는 개념이 필요합니다. 청크 그룹은 함께 로드되는 청크들의 집합입니다. 예를 들어 <code>/home</code>에서 사용하는 모든 청크는 하나의 그룹을, <code>/blog</code>에서 사용하는 청크들은 또 다른 그룹을 형성합니다. <code>/home</code> 그룹은 3개 청크를, <code>/blog</code> 그룹은 2개 청크를 로드하며, 한 청크가 양쪽 그룹에 모두 속할 수도 있습니다. 이 경우 그 청크를 이웃 청크와 병합하는 것은 두 그룹 모두에서 안전할 때만 가능합니다.</p>
<p>청크 그룹은 '불필요한 코드 과다 전송' 문제를 해결해줍니다. Turbopack은 같은 그룹 안의 청크끼리만 병합하는데, 어차피 한 그룹의 청크들은 항상 함께 로드되므로, 병합해도 원래 다운로드하던 것 이상을 추가하지 않습니다.</p>
<h3>병합이 이득이 되는 조건</h3>
<p>그렇다면 요청 폭주 없이 캐시 히트를 최대화하려면 어떻게 해야 할까요? 이를 파악하기 위해 두 가지 방문 패턴을 생각해봅니다. 페이지 하나를 보고 떠나는 경우, 그리고 페이지를 본 뒤 다른 페이지로 이동하는 경우입니다. (이 분석은 3개 이상 페이지를 방문하는 세션으로도 자연스럽게 확장됩니다.)</p>
<p><code>&lt;Footer /&gt;</code>의 청크를 A, <code>&lt;VideoPlayer /&gt;</code>의 청크를 B라고 합시다. A는 모든 페이지에서 쓰이고, B는 홈페이지에서만 쓰입니다. 둘 다 홈페이지의 청크 그룹에 속하므로 병합 후보입니다.</p>
<p>방문자가 홈페이지만 보고 떠난다면 병합은 언제나 이득입니다. 어차피 둘 다 필요했던 코드이므로, 요청이 2번에서 1번으로 줄어드니까요.</p>
<p>두 번째 페이지로 넘어가는 경우는 그 페이지가 A, B 둘 다 필요한지, 아니면 하나만 필요한지에 따라 달라집니다. 예를 들어 홈페이지에서 법률 페이지로 이동한다면, 법률 페이지는 A만 필요하고 B는 필요 없습니다. A와 B가 병합되어 하나의 파일이 되어버렸으므로, 이 병합 파일은 법률 페이지에서 쓸모가 없고 브라우저는 A를 따로 다시 다운로드해야 합니다. 결과적으로 방문자는 A를 두 번 받게 됩니다.</p>
<p>즉 내비게이션에 걸쳐 병합이 이득을 보려면, 두 페이지 모두 A와 B를 함께 필요로 해야 합니다. 그래야 병합된 파일이 재사용되어 요청 하나를 절약할 수 있습니다.</p>
<p>가능한 2페이지 세션 시나리오를 정리하면 다음과 같습니다. 각 행은 &quot;첫 페이지가 필요로 하는 것 → 두 번째 페이지가 필요로 하는 것&quot; 형태이며, 숫자는 A와 B를 병합했을 때 분리된 경우와 비교해 요청 수와 다운로드 코드량이 어떻게 바뀌는지를 나타냅니다.</p>

<p>청크 A와 B의 병합 여부를 결정할 때, Turbopack은 A만 쓰는 청크 그룹, B만 쓰는 청크 그룹, A+B를 함께 쓰는 청크 그룹의 개수를 계산하고, 각 시나리오의 발생 확률에 따라 병합의 비용 혹은 이득에 가중치를 매깁니다. 마지막으로 1페이지 방문과 2페이지 방문 케이스에도 확률 가중치를 적용하는데, 단일 페이지 세션을 2/3, 2페이지 이상 세션을 1/3로 추정합니다.</p>
<h3>세 가지 청킹 전략 실측 비교</h3>
<p>지금까지 설명한 전략들을 실제로 비교해보기 위해, nextjs.org에 세 가지 Turbopack 청킹 설정(&quot;병합 없음&quot;, &quot;Turbopack 기본값&quot;, &quot;그룹당 하나의 청크로 모두 병합&quot;)을 적용하고 동일한 내비게이션 시퀀스를 실행하며 요청 수와 클라이언트 측 JavaScript 다운로드량을 측정했습니다.</p>

<p>결과를 보면 청킹은 결국 균형의 문제라는 게 명확해집니다. nextjs.org에서는 기본 설정이 &quot;병합 없음&quot; 대비 요청 수를 절반 이하로 줄이면서도 코드량은 오히려 살짝 줄였습니다. 최대 병합은 요청 수를 더 줄였지만 전체 코드량이 10% 더 늘어났습니다. 다만 내비게이션 횟수가 더 적었다면 최대 병합 쪽이 더 유리했을 겁니다. 그룹 내 모든 청크를 하나의 거대한 청크로 합치는 방식은 최초 페이지 로드에서는 이득이지만, 장기적인 세션에서는 비용이 큽니다.</p>
<h3>Next.js 16.3에서 추가된 청킹 기능</h3>
<p>청킹의 효과를 제한하는 두 가지 요인이 있습니다. 첫째, 병합은 누군가 방문하기 전인 빌드 타임에 결정되므로 브라우저가 이미 무엇을 캐시해뒀는지 반영할 수 없습니다. 둘째, 알고리즘은 사람들이 사이트를 어떻게 돌아다니는지를 추측에 의존해야 하는데, 그래서 단일 페이지 방문에 2/3라는 가중치를 쓰는 것입니다. 이번 여름 Turbopack 팀 인턴십 기간 동안, 저는 이 두 가지 문제와 더불어 애초에 청크에 들어가는 코드량 자체를 줄이는 작업을 진행했습니다.</p>
<h4>더 똑똑한 청크 페칭</h4>
<p>앞서 본 표는 병합의 비용을 보여줍니다. 방문자가 A를 포함한 페이지를 로드한 뒤 A+B가 필요한 페이지로 이동하면, 병합된 상태에서는 A를 또 다운로드하게 됩니다. 번들러는 빌드 타임에 브라우저가 무엇을 갖고 있는지 알 수 없기 때문에 이를 피할 수 없지만, 런타임은 알 수 있습니다.</p>
<p>Next.js 16.3 이상에서 <code>next.config.js</code>의 <code>experimental.turbopackChunking.generateComponentChunks</code>를 활성화하면, Turbopack은 병합된 청크와 함께 병합되지 않은 버전도 함께 생성합니다. 각 병합 청크를 구성하는 요소들과 그중 이미 로드된 것이 무엇인지 추적해서, 요청 시점에 더 저렴한 쪽—병합된 청크 전체인지, 아니면 빠진 조각들만인지—을 선택할 수 있습니다.</p>
<p>반대 경우도 가능합니다. 방문자가 이미 병합된 A+B를 로드했다면, A만 따로 다시 로드하는 것을 생략할 수 있습니다.</p>
<p>결과적으로 소프트 내비게이션에서는 불필요한 코드를 덜 받으면서도 병합의 이점을 그대로 누릴 수 있습니다. (<code>generateComponentChunks: false</code>와 <code>true</code> 비교 데모 앱이 원문에 제공되어 있습니다.)</p>
<p>또한 <code>only-if-cached</code> 디렉티브를 활용해 방문자가 도착했을 때 이미 무엇을 캐시했는지 확인하는 방법도 실험 중입니다. 이렇게 되면 사이트를 떠났다가 나중에 다시 방문하는 사람들에게도 같은 개선 효과를 확장할 수 있습니다.</p>
<h4>분석 데이터 기반 청킹</h4>
<p>Turbopack의 청킹 알고리즘은 여러 가정에 의존합니다. 예를 들어 앞서 언급한 2/3 가중치는 어디까지나 추정치입니다. 많은 사이트에 적용 가능한 합리적인 기본값이지만, 특정 사이트에 꼭 맞는 값은 아닐 수 있습니다. 만약 여러분의 사이트에서 사람들이 실제로 어떻게 이동하는지 안다면, 이를 직접 알려줄 수 있습니다.</p>
<p><code>next.config.js</code>의 <code>experimental.turbopackChunking</code> 아래에 다음 옵션들을 설정할 수 있습니다.</p>
<ul>
<li><strong><code>firstPageLoadPriority</code></strong>: 단일 페이지 케이스와 2페이지 케이스 사이의 가중치를 조정합니다. 값(0~1)이 높을수록 내비게이션 비용을 감수하더라도 최초 로드 속도를 우선시합니다. 이탈률(bounce rate)이 적절한 초기값이 될 수 있으며, 기본값은 0.67입니다.</li>
<li><strong><code>priorityRoutes</code></strong>: 로드 속도가 특히 중요한 페이지 목록입니다. 해당 라우트에서는 청크를 더 적극적으로 병합합니다.</li>
<li><strong><code>clusters</code></strong>: 정규식 배열로 정의되는, 자주 함께 방문되는 라우트 그룹입니다. 클러스터 내부에서는 겹치는 청크를 더 기꺼이 병합합니다. 단, 클러스터 안에 A만 쓰는 페이지나 B만 쓰는 페이지와 A+B를 모두 쓰는 페이지가 섞여 있다면, 병합을 덜 하게 됩니다.</li>
</ul>
<h4>더 작고 더 적은 청크</h4>
<p>위의 내용이 코드를 어떻게 묶을지에 관한 것이었다면, 마지막으로 소개할 기능들은 애초에 내려보내는 코드량 자체를 줄이는 데 초점을 맞춥니다. 다음 기능들을 작업했습니다.</p>
<ul>
<li><strong>CJS 모듈 트리 셰이킹</strong>: 기존에는 ESM에서만 지원되어서, CJS 모듈의 사용하지 않는 import/export가 그대로 클라이언트에 전송되고 있었습니다. <code>experimental.turbopackCjsTreeShaking</code>으로 활성화할 수 있으며, 향후 버전에서는 기본값으로 켜질 예정입니다. 이와 함께 분석·트리 셰이킹 가능한 ESM 모듈의 범위도 넓혔는데, 동적 import 안의 배럴 파일(barrel file) 지원 개선도 포함됩니다.</li>
<li><strong>공유 Turbopack 런타임</strong>: 페이지별로 따로 있던 런타임 청크를 하나의 공유 런타임 청크로 대체합니다. <code>experimental.turbopackSharedRuntime</code>으로 활성화할 수 있고, 첫 로드 이후의 모든 내비게이션에서 블로킹 요청 하나와 약 10KB의 클라이언트 측 JavaScript를 절약합니다. 이 역시 추후 기본값으로 전환될 예정입니다.</li>
<li><strong>더 가벼워진 기본 런타임</strong>: 런타임이 더 이상 WebAssembly와 Web Worker 관련 코드를 기본으로 포함하지 않습니다. 해당 모듈을 실제로 사용할 때만 감지해서 로딩 코드를 삽입합니다.</li>
</ul>
<p>이 모든 신기능은 Next.js 16.3 이상에서 사용해볼 수 있습니다.</p>
<h3>정리</h3>
<ul>
<li>Turbopack의 청킹은 &quot;요청 수를 줄일 것인가, 코드 다운로드량을 줄일 것인가&quot;라는 상반된 목표 사이의 균형 잡기입니다. 전체를 한 청크로 묶으면 캐싱은 완벽하지만 불필요한 코드가 너무 많이 전송되고, 모듈 하나당 청크 하나로 쪼개면 전송량은 최소지만 요청 수가 폭발합니다.</li>
<li>Turbopack은 <strong>청크 그룹</strong> 단위로만 병합을 수행해 불필요한 코드 전송을 막고, 두 청크가 동시에 필요한 내비게이션 확률을 추정해 병합이 실제로 이득인지 계산합니다. 단일 페이지 방문은 2/3, 2페이지 이상 세션은 1/3로 가중치를 둡니다.</li>
<li>nextjs.org 실측 결과, Turbopack 기본 설정은 &quot;병합 없음&quot;보다 요청 수를 절반 이하로 줄이면서 코드량도 약간 줄였지만, 모든 청크를 하나로 합치는 전략은 요청 수는 더 줄여도 전체 전송량이 10% 늘어나는 트레이드오프를 보였습니다.</li>
<li>Next.js 16.3에서는 <code>generateComponentChunks</code>(런타임에 캐시 상태를 보고 병합/분리 청크 중 유리한 쪽을 선택), <code>firstPageLoadPriority</code>/<code>priorityRoutes</code>/<code>clusters</code>(사이트별 실제 방문 패턴 반영), CJS 트리 셰이킹, 공유 런타임, 경량 기본 런타임 등을 실험적으로 제공합니다.</li>
<li>실무에서는 사이트의 실제 방문 패턴(이탈률, 자주 함께 방문되는 페이지 묶음 등)을 파악해 <code>experimental.turbopackChunking</code> 옵션으로 튜닝하면, 기본값보다 더 나은 로딩 성능을 끌어낼 수 있습니다.</li>
