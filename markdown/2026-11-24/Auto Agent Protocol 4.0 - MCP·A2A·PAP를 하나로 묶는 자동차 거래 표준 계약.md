## 핵심 개념

> [!abstract]
> Auto Agent Protocol(AAP) 4.0은 자동차 대리점 발견, 재고 검색, 차량 정보·가격 검증, 리드 제출 같은 자동차 거래 업무를 MCP, A2A, PAP(Personal Agent Protocol) 세 인터페이스 위에서 동일한 계약으로 제공하는 오픈 스펙입니다. 다섯 개 핵심 스킬과 중고차 보상 판매·신용 신청이라는 두 개 선택 스킬을 정의하며, 디스커버리 문서(agent-card.json, poppy.json, llms.txt)를 통해 에이전트가 딜러의 실제 역량을 확인할 수 있게 합니다. 4.0에서는 PAP 1.0 도입, 스네이크 케이스 네이밍 통일, 리베이트 필드 추가 등 주요 변경이 이뤄졌습니다.

## 아티클

# Auto Agent Protocol 4.0 - MCP·A2A·PAP를 하나로 묶는 자동차 거래 표준 계약

최근 AI 에이전트가 쇼핑, 상담, 거래 같은 실제 업무를 대신 처리하는 사례가 늘면서, 에이전트와 서비스 간 통신 프로토콜(MCP, A2A, PAP 등)도 빠르게 발전하고 있습니다. 문제는 이 프로토콜들이 각자 다른 방식으로 발전하다 보니, 같은 비즈니스 로직을 서비스마다 세 번씩 구현해야 하는 상황이 생긴다는 점입니다. Auto Agent Protocol(AAP)은 이 문제를 자동차 딜러 도메인에 한정해서 풀어낸 오픈 스펙으로, MCP·A2A·PAP(Personal Agent Protocol) 세 인터페이스 위에서 동일한 자동차 거래 계약을 제공합니다.

## AAP가 해결하려는 문제

AAP는 에이전트가 자동차 대리점을 발견하고, 실제 재고를 검색하고, 차량 사실관계와 리베이트가 반영된 가격을 검증하고, 고객이 승인한 문의를 전송할 수 있게 해주는 자동차 전용 계약입니다. 여기에 더해 딜러는 중고차 보상 판매(trade-in) 견적과 신용 신청(credit application) 기능도 선택적으로 제공할 수 있습니다.

핵심 아이디어는 "하나의 자동차 계약, 세 개의 인터페이스"입니다. MCP, A2A, PAP는 각자 다른 통신 방식을 쓰지만, AAP는 이 세 인터페이스 모두에서 동일한 의미의 페이로드를 네이티브로 지원합니다.

| 인터페이스 | 네이티브 동작 방식 | 자동차 계약 내용 |
|---|---|---|
| MCP | Streamable HTTP 도구; 2026-07-28 및 2025-11-25 버전 호환 | 타입이 지정된 인자, 완전한 스키마, 구조화된 결과 |
| A2A 1.0 | 필수 AAP 확장이 포함된 SendMessage | `DataPart.data`에 동일한 페이로드 |
| PAP 1.0 | 위임된 Poppy-Session JWT와 모든 요청의 `Poppy-Version: 1.0` 헤더, 네이티브 OpenAPI | 동일한 요청/응답 바디 |

완전한 AAP 4.0 딜러 배포는 자신이 구현한 스킬 하위 집합을 이 세 인터페이스 모두를 통해 제공합니다. 반면 구매자 측 클라이언트는 자신이 선택한 바인딩 하나만 구현하면 됩니다. 중요한 점은 AAP가 딜러 측에 언어 모델이나 새로운 CRM 도입을 요구하지 않는다는 것입니다. 단, MCP 엔드포인트는 실제로 동작해야 하며, 자동 생성되는 `mcp.json` 카탈로그는 도구 목록을 설명하는 문서일 뿐 서버 자체가 아니라는 점은 유의해야 합니다.

## 디스커버리는 대리점 도메인에서 시작된다

AAP는 에이전트가 딜러를 발견하는 방식도 표준화합니다. 딜러 도메인 아래 세 개의 잘 알려진(well-known) 리소스를 두고, 각각이 서로 다른 관점에서 동일한 대리점과 그 실제 역량을 설명합니다.

| 딜러 도메인 리소스 | 알려주는 정보 |
|---|---|
| `/.well-known/agent-card.json` | A2A 엔드포인트, 선택된 AAP 계약, 스킬, 검색 역량, MCP/PAP 링크 |
| `/.well-known/poppy.json` | PAP 1.0 신원 정보, 선택적 issuer, 네이티브 API, 다른 디스커버리 문서로 연결되는 AAP 확장 엔트리 |
| `/llms.txt` | 정확한 서비스 URL, 접근 요구사항, 문서, 재고 링크 |

서비스 자체는 다른 제공자의 인프라에서 돌아갈 수도 있지만, 모든 진입점은 동일한 대리점과 동일한 실제 역량을 가리켜야 합니다. 디스커버리는 호환되는 에이전트가 서비스를 찾도록 도와줄 뿐, 모든 어시스턴트가 그 서비스를 반드시 선택하도록 보장하지는 않습니다. 실제 배포 전에는 Agent Card, Poppy 문서, 딜러 `llms.txt` 템플릿(현재는 가상의 딜러 정보로 채워져 있음)에서 신원, URL, 역량 정보를 자신의 것으로 교체해야 합니다.

## 다섯 가지 핵심 스킬과 두 가지 선택 스킬

AAP는 자동차 구매 여정을 다섯 개의 핵심 스킬과 두 개의 선택 스킬로 정의합니다.

- **핵심 스킬**: 딜러 정보(Dealer information), 패싯(Facets), 검색(Search), 차량 상세(Vehicle detail), 리드 제출(Lead submission)
- **선택 스킬**: 중고차 보상 판매 견적(`trade_in_submit`), 신용 신청(`credit_application_submit`)

설계상 중요한 원칙 몇 가지가 있습니다. 쇼핑객의 연락처 정보 없이도 브라우징이 가능해야 하고, 리드(고객 문의)는 명시적 동의, 허용된 채널, 멱등성 키(idempotency key)가 있을 때만 제출됩니다. 또한 "문의가 접수됐다"와 "상담 예약이 확정됐다"는 서로 다른 결과로 명확히 구분합니다. 딜러는 선택 스킬을 실제로 구현했을 때만 지원한다고 선언해야 하며, 선언한 이상 모든 바인딩(MCP/A2A/PAP)에서 동일한 역량을 제공해야 합니다.

## AAP 4.0에서 달라진 점

이번 메이저 릴리스의 변경사항은 꽤 폭넓습니다.

**PAP 1.0 도입**: 위임된 Poppy-Session JWT를 사용하는 모든 요청은 `Poppy-Version: 1.0` 헤더를 함께 보내야 합니다. 버전이 누락되거나 호환되지 않으면 HTTP 400 `version_unsupported`가 반환됩니다. 확장(extension)은 버전별 리스트로 관리되고, 선택적인 `tasks.endpoint` 하나가 기존에 분리되어 있던 태스크 링크들을 대체합니다. Companies는 ES256과 PS384 서명 알고리즘을 받아들이며, Session은 client, SID, User ID 조합으로 조회됩니다.

**스네이크 케이스 통일**: 스킬 ID와 메시지 타입에서 점(dot)이 사라지고 언더스코어로 통일됐습니다. 예를 들어 `lead.submit` → `lead_submit`, `lead.submit.request` → `lead_submit_request`, `aap.error` → `aap_error`로 변경됐습니다. 단, `aap_lead_submit` 같은 MCP 도구 이름 자체는 그대로 유지됩니다.

**리베이트(rebates) 필드 추가**: 신차는 이제 `rebates[]` 배열을 가질 수 있습니다. 무조건적 리베이트(unconditional rebate)는 이미 가격에 반영되어 있고, 조건부 리베이트(conditional rebate)는 가능한 추가 절약분으로 별도 표시됩니다.

**선택 스킬 `trade_in_submit`**: 리드와 동일한 고객 데이터를 담는 동의 기반 중고차 보상 판매 제출 기능입니다. 응답에는 금액 또는 범위 형태의 견적, 추정치(estimate), 또는 제안(offer)이 포함될 수 있습니다.

**선택 스킬 `credit_application_submit`**: 각 신청자의 신용 동의가 포함된 단일 신청서, 소프트/하드 조회 구분, 절대 그대로 반환되지 않는(never echoed) 민감 정보 처리를 포함합니다. 딜러는 이를 반드시 API로 구현해야 하며, ADF/XML이나 이메일을 통한 구현은 허용되지 않습니다.

**유지되는 기존 동작**: 다섯 개 핵심 스킬, 통화, 주행거리 단위, 가격 책정, 장비 증빙, 리드 동의, MCP, A2A 1.0, 브리지 버전 1의 의미는 그대로 유지됩니다. `lead_submit`은 여전히 중고차 보상 판매 정보를 함께 받을 수 있지만, 견적을 반환하지는 않습니다.

이번 릴리스는 메이저 버전이라 PAP 클라이언트 마이그레이션이 필수입니다. 과거 버전인 고정된 AAP 3.2는 기존에 발행된 PAP 0.3을 그대로 유지하며, 해당 엔드포인트와 아티팩트는 변경되지 않습니다. 딜러는 마이그레이션 기간 동안 `supported_versions`에서 이 문서를 링크해 둘 수 있습니다.

## 자동차 도메인 세부 규칙: 가격과 동의

AAP는 차량 종류와 관계없이 공통으로 적용되는 가격 표시 규칙을 정의합니다. 알려진 가격에는 딜러 의무 수수료와 무조건적 리베이트가 반영되어 있어야 하며, 정부가 요구하는 소비자 부담금만 예외적으로 제외됩니다. 선택적인 수수료 항목화(fee itemization)는 기존 총액을 설명하기 위한 것이며, 조건부 리베이트는 이 총액에서 절대 차감되지 않습니다. 알려지지 않은 장비나 가격은 알려지지 않은 상태 그대로 둡니다.

중고차 보상 판매 견적과 신용 신청 제출은 어디까지나 선택 스킬이며, 결제, 체크아웃, 예약, 구속력 있는 구매 견적은 AAP의 범위 밖입니다.

## 패키지와 개발 환경

AAP는 npm 패키지로 스키마, 타입, 검증 도구를 제공합니다.

```
npm install @autoagentprotocol/schemas@4.0.0 @autoagentprotocol/types@4.0.0 @autoagentprotocol/validator@4.0.0
```

주요 아티팩트는 다음과 같습니다.

| 아티팩트 | 위치 |
|---|---|
| JSON Schema 2020-12 | `spec/v4.0/schemas/` |
| 타입 및 와이어 예시 | `spec/v4.0/examples/` |
| MCP 도구 카탈로그 | `/v4.0/mcp.json` |
| A2A JSON-RPC OpenAPI | `/v4.0/openapi-jsonrpc.yaml` |
| PAP OpenAPI | `/v4.0/openapi-poppy.yaml` |
| 불변 릴리스 레지스트리 | `releases.json` |

빌드 및 검증은 Node.js 22 이상과 `package.json`에 고정된 pnpm 10 버전을 사용합니다. Corepack이나 최신 pnpm 런처는 이 버전을 자동으로 선택하며, CI 워크플로도 동일한 버전을 사용합니다.

```
pnpm install --frozen-lockfile
pnpm validate
pnpm test:contract
pnpm typecheck
pnpm build
```

공식 MCP·A2A 클라이언트는 실제 HTTP 계약 픽스처로 테스트를 수행하고, PAP 검증은 디스커버리, 신원, 세션 스키마, 자동 생성된 OpenAPI를 다룹니다. 다만 이런 검증은 스펙 자체의 유효성을 확인하는 것이고, 실제 프로덕션 배포에서는 실제 인증, 재고, 동의, CRM 동작을 별도로 검증해야 합니다.

## 저장소 구조

| 경로 | 용도 |
|---|---|
| `spec/latest/`, `docs/` | 편집 가능한 계약 및 문서 |
| `docs/img/` | 재생성 가능한 SVG 다이어그램 (`pnpm generate:images`) |
| `spec/v*/`, `versioned_docs/` | 불변 릴리스 스냅샷 |
| `releases/v*/` | 생성된 아티팩트, 출처 정보, 무결성 검증 자료 |
| `packages/` | 스키마, 타입, 검증기 패키지 |
| `src/` | 웹사이트 및 인터랙티브 설명 |
| `tools/` | 생성기, 검증, 릴리스 체크 도구 |

`/latest` 경로의 머신 아티팩트는 안정 레지스트리를 따르지만, `/docs/latest`는 편집 가능한 문서로서 아직 출시되지 않은 미래 버전을 설명할 수도 있습니다. 실제 통합 작업을 할 때는 반드시 공식적으로 공지된 버전을 고정해서 사용해야 합니다.

스펙, 스키마, 코드는 Apache-2.0 라이선스를, 문서 산문은 CC BY 4.0 라이선스를 따릅니다.

## 정리

AAP 4.0은 자동차 딜러 도메인이라는 명확한 경계 안에서, MCP·A2A·PAP 세 프로토콜 위에 동일한 의미의 계약을 올려놓는 접근을 보여줍니다. 핵심은 다음과 같습니다.

- 에이전트 생태계가 MCP, A2A, PAP 등으로 파편화되는 상황에서, 특정 도메인(여기서는 자동차 딜러)에 한정해 공통 스킬·데이터 모델을 정의하고 이를 세 인터페이스 모두에서 네이티브로 제공하는 전략이 유효할 수 있습니다.
- 디스커버리(`agent-card.json`, `poppy.json`, `llms.txt`)를 표준화해, 에이전트가 어떤 서비스가 어떤 역량을 제공하는지 신뢰성 있게 확인할 수 있게 한 점이 눈에 띕니다.
- 가격·동의·리베이트 같은 도메인 특화 규칙(무조건/조건부 리베이트 구분, 소비자 부담금 처리 등)을 스펙 레벨에서 엄격하게 못박아, 구현체마다 해석이 갈리는 문제를 줄이려 한 점도 참고할 만합니다.
- 4.0에서의 스네이크 케이스 통일이나 PAP 버전 협상 같은 변경은, 여러 프로토콜을 동시에 지원하는 스펙을 메이저 업그레이드할 때 생기는 실무적 고민(마이그레이션 경로, 하위 호환 문서 유지)을 보여주는 사례입니다.

자동차 업계가 아니더라도, 여러 에이전트 프로토콜을 동시에 지원해야 하는 서비스를 설계한다면 AAP의 "하나의 계약, 여러 바인딩" 구조와 디스커버리 설계 방식은 참고할 가치가 있습니다.
