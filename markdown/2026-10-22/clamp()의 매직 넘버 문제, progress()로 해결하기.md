## 핵심 개념

> [!abstract]
> CSS clamp()로 유체 타이포그래피를 만들 때 중간값과 구간 설정이 매직 넘버가 되어 스케일 간 타이밍이 어긋나는 문제를 progress() 함수로 해결하는 방법을 다룹니다. progress()는 0~1 사이 단위 없는 값을 반환해 예측 가능한 최소/최대 범위를 만들 수 있고, pow()와 결합하면 지수적인 타입 스케일도 쉽게 구현할 수 있습니다. 아직 progress()의 브라우저 지원이 걱정된다면 tan(atan2()) 트릭으로 동일한 효과를 오늘 당장 적용할 수 있습니다.

## 아티클

# clamp()의 매직 넘버 문제, progress()로 해결하기

CSS에서 반응형 폰트 크기를 만들 때 `clamp()`를 많이 씁니다. 그런데 `clamp()`를 쓰다 보면 항상 중간값이 골치 아픕니다. 거기에 어떤 뷰포트 너비 값을 넣어야 할지 감이 안 오고, 줌 대응을 위해 플러스마이너스 연산까지 끼워 넣다 보면 숫자가 점점 복잡해집니다. 게다가 시작점이나 끝점 숫자를 한 번 바꾸면 이전과 비교해서 변화 구간이 어긋나버리고, 다시 바꾸면 또 어긋나고... 결국 의미를 알 수 없는 매직 넘버들이 쌓이면서 코드가 엉망이 되기 쉽습니다.

이 문제를 깔끔하게 풀어주는 게 바로 `progress()` 함수입니다. 문법이 좀 낯설고 길어 보이긴 하지만, 실제로 써보면 훨씬 다루기 쉽습니다. 마침 최근 `progress()`가 Baseline Newly Available 상태가 되어 모든 주요 브라우저 엔진에 들어갔습니다. 아직 바로 쓰기 부담스럽다면, 동일한 동작을 하면서도 폭넓은 브라우저 지원을 받는 대체 기법도 함께 살펴보겠습니다.

## clamp()의 문제 상황

`clamp()`로 폰트 크기 스케일을 여러 개 설정하다 보면, 어떤 요소는 특정 구간에서 크기가 변하고 어떤 요소는 변하지 않다가, 또 다른 구간에서 갑자기 변하기 시작하는 등 서로 다른 타이밍에 어긋나게 움직이는 현상이 생깁니다. 특히 타입 스케일 전체를 조화롭게 맞추려고 할 때 이런 문제가 두드러집니다. 이런 이유 때문에 Utopia 같은 도구를 써서 제대로 작동하는 유체(fluid) 타입 스케일을 만드는 경우가 많습니다.

반면 `progress()`를 쓰면 모든 요소가 정확히 같은 비율로 함께 커지고 작아지게 만들 수 있습니다.

## progress() 함수의 동작 원리

기본 개념을 살펴보겠습니다. 뷰포트 너비를 기준으로 500px와 1000px 사이를 측정하는 커스텀 프로퍼티를 다음과 같이 만들 수 있습니다.

핵심은 `progress()`가 항상 0과 1 사이의 **단위 없는(unitless)** 값을 반환한다는 점입니다. CSS에서 단위 없는 값을 주는 기능이 흔치 않다는 점에서 꽤 흥미로운 특성입니다.

동작 방식은 이렇습니다.

- 뷰포트가 1000px보다 크면 → 값은 1
- 뷰포트가 1000px 아래로 내려가기 시작하면 → 진행률(progress)이 계산되기 시작
- 뷰포트가 500px에 도달하면 → 값은 0

이렇게 얻은 0~1 사이의 단위 없는 값에 원하는 숫자를 곱하고 더해서 실제 폰트 크기를 만들어낼 수 있습니다. 예를 들어 `fluid * 16px + 48px` 같은 식으로 계산하면:

- 뷰포트가 500px보다 작을 때: 폰트 크기는 48px 고정
- 뷰포트가 500px~1000px 사이: fluid 값(0~1)에 따라 48px에서 서서히 증가
- 뷰포트가 1000px 이상: `1 * 16px + 48px = 64px`로 고정

즉 최소값과 최대값을 수학적으로 정확히 예측할 수 있으면서도, `clamp()`를 쓸 때와 마찬가지로 범위 설정이 쉽습니다.

## 가독성 문제와 해결 — 커스텀 프로퍼티로 분리하기

`progress()`의 가장 큰 단점은 코드를 읽기 어렵다는 점입니다. 실제로 직접 써보면서 가장 힘들었던 부분도 수식을 눈으로 보고 무슨 의미인지 파악하는 일이었습니다.

이를 해결하는 가장 간단한 방법은 최소/최대 폰트 크기를 별도의 커스텀 프로퍼티로 빼두는 것입니다. 그러면 실제 값을 조정할 때는 복잡한 수식이 있는 영역을 건드릴 필요 없이, 분리된 커스텀 프로퍼티만 수정하면 됩니다. 동작 방식은 이전과 완전히 동일하게 유지됩니다.

같은 방식으로 `vmin`, `vmax` 기준값도 유체 타입 스케일용 커스텀 프로퍼티로 분리해두면 가독성이 한층 좋아집니다. 코드의 어느 부분이 "값"이고 어느 부분이 "로직"인지 명확히 구분되기 때문에, 복잡한 수학 계산을 신경 쓰지 않고도 원하는 값만 바꿔서 결과를 조정할 수 있습니다.

픽셀 단위로 쓴 뷰포트 기준값(500px, 1000px 등)은 그대로 둬도 문제없습니다. 어차피 뷰포트 위치를 측정하는 용도이기 때문에, 줌을 하더라도 픽셀 자체의 크기가 함께 변하므로 괜찮습니다. 다만 실제 폰트 크기 계산에는 `rem` 단위를 쓰는 걸 권장합니다. 폰트 크기에 픽셀을 쓰면 사용자가 브라우저 설정으로 기본 폰트 크기를 키워도 반영되지 않는 접근성 문제가 생기기 때문입니다. 뷰포트 단위만 써서 폰트 크기를 고정해버리는 것보다는, `rem` 기반 계산을 유지하는 편이 줌 동작과도 자연스럽게 맞아떨어집니다.

## 타입 스케일 전체에 적용하기 — pow() 함수 활용

특정 크기 몇 개만 설정하는 경우라면 위 방법으로 충분하지만, Utopia 같은 도구에서 제공하는 것처럼 전체 타입 스케일을 한 번에 관리하고 싶을 때도 있습니다. 모든 폰트 크기가 동시에 같은 비율로 커지고 작아지게 만들고 싶은 경우인데, 이런 상황에서도 `progress()`는 꽤 쉽게 적용됩니다.

Utopia 같은 생성기는 훌륭한 도구이지만, `progress()`와 `pow()`를 직접 CSS에 적용하면 나중에 값을 커스터마이징하기가 훨씬 쉬워진다는 장점이 있습니다.

설정 방식은 다음과 같습니다.

- 기본 폰트 크기(base)는 앞서 다룬 방식과 동일하게 설정
- 작은 화면용 타입 스케일과 큰 화면용 타입 스케일 값을 각각 지정 (Utopia에서 설정할 때와 같은 개념)
- 타입 스케일 자체도 앞서 만든 `progress()` 기반 fluid 값을 따라 함께 변화하도록 설정
- `pow()` 함수로 기본 크기에 타입 스케일 값을 거듭제곱하여 각 단계별 폰트 크기를 산출

타입 스케일이 뷰포트 크기에 따라 함께 커지도록 만드는 이유는, 작은 화면에서는 폰트 크기 단계 간 차이가 크지 않다가 화면이 커질수록 큰 폰트들이 기하급수적으로 더 커지는, 이른바 "하키스틱" 형태의 지수 스케일을 구현하기 위해서입니다. 선형 스케일이 아니라 지수 스케일을 쓰는 게 타이포그래피에서는 더 자연스럽기 때문에, `pow()`가 이 역할을 담당합니다.

`pow()` 함수의 브라우저 지원도 걱정할 필요 없습니다. 이미 4~5년 전부터 모든 브라우저에 들어가 있는 기능으로, Baseline Widely Available 상태가 된 지 오래입니다.

정리하면: 기본값(base)에 타입 스케일을 곱하고, 다른 단계들은 거듭제곱으로 계산해서 하키스틱 형태로 스케일링하는 방식입니다.

## 가독성을 한 번 더 개선하기

여기서도 여전히 가독성 문제가 남습니다. 타입 스케일 설정 시 첫 번째 숫자(작은 화면용 스케일)는 직관적이지만, 두 번째 숫자(큰 화면용 스케일)는 원하는 결과를 얻기 위해 역산한 값이라 꽤 임의적으로 보일 수 있습니다.

해결책은 간단합니다. 그 수학 계산 자체를 CSS 안에서 직접 하도록 넘겨버리면 됩니다. 즉, 작은 화면용 스케일 값과 큰 화면용 스케일 값을 각각 그대로 설정해두고, 앞서 폰트 크기를 계산할 때 썼던 것과 동일한 방식으로 수식을 CSS 내부에서 처리하면 됩니다.

이렇게 하면 원하는 두 개의 타입 스케일 값만 명확하게 지정해두고, 필요할 때 그 값들만 조정하면 됩니다. 예를 들어 작은 화면에서는 폰트 크기를 살짝 더 키우고 큰 화면에서는 훨씬 더 공격적으로 커지도록 바꾸는 것도, 반대로 전체적으로 덜 공격적인 스케일로 바꾸는 것도 숫자 두 개만 조정하면 바로 반영됩니다. 코드 가독성도 좋아지고, 필요하다면 섹션을 재배치하거나 주석을 추가해서 더 명확하게 정리할 수도 있습니다.

## 브라우저 지원이 부족할 때의 대안 — tan(atan2()) 트릭

`progress()`가 최근에야 Baseline Newly Available이 된 만큼, 아직 바로 도입하기 꺼려질 수 있습니다. 하지만 지금 당장 써도 괜찮습니다.

`progress()`가 내부적으로 하는 계산은 사실 단순합니다. 예를 들어 500px~1000px 구간이라면 다음과 같은 수식입니다.

```
(100vw - 500px) / (1000px - 500px)
```

이 계산 자체는 `calc()` 안에서 똑같이 할 수 있을 것 같지만, 한 가지 걸림돌이 있습니다. 길이(length) 값끼리 나눗셈을 해서 단위 없는 값을 얻는 "타입 연산(typed arithmetic)"이 CSS에 도입되어 있는데, Chrome과 Safari는 지원하지만 Firefox는 아직 지원하지 않습니다.

하지만 이게 걸림돌이 되지는 않습니다. `tan()`과 `atan2()`가 있기 때문입니다. 특히 `tan(atan2())` 조합을 쓰면 `progress()`와 동일한 계산을 단위 없는 값으로 뽑아낼 수 있는데, 이 트릭은 이미 CSS 고수들 사이에서 오랫동안 다양한 용도로 활용되어 온 방법입니다. 이를 활용하면 Firefox를 포함한 폭넓은 브라우저 환경에서도 `progress()`와 동일한 동작을 오늘 당장 구현할 수 있습니다.

## 정리

- `clamp()`로 유체 타이포그래피를 구현할 때 겪는 가장 큰 문제는 중간값과 구간 설정이 매직 넘버화되어, 값을 하나 바꿀 때마다 전체 스케일 타이밍이 어긋나는 것입니다.
- `progress()`는 두 값 사이의 진행 정도를 0~1 사이의 단위 없는 값으로 반환해주는 함수로, 이 값에 원하는 배수와 베이스값을 곱하고 더해서 최소/최대가 명확한 유체 스케일을 만들 수 있습니다.
- 가독성을 높이려면 뷰포트 기준값, 최소/최대 폰트 크기, 타입 스케일 값 등을 모두 별도 커스텀 프로퍼티로 분리해두고, 복잡한 수식 영역은 건드리지 않은 채 값만 조정하는 구조를 만드는 게 핵심입니다.
- 전체 타입 스케일을 한 번에 관리하려면 `pow()` 함수로 기본 폰트 크기를 거듭제곱해 지수적(하키스틱) 스케일을 만들 수 있고, `pow()`는 이미 모든 브라우저에서 수년간 안정적으로 지원되고 있습니다.
- `progress()`가 아직 Baseline Newly Available 단계라 부담스럽다면, `tan(atan2())` 트릭으로 동일한 수식을 더 넓은 브라우저 지원 범위에서 오늘 바로 구현할 수 있습니다.
- 폰트 크기 자체는 접근성을 위해 `rem` 단위를 유지하고, 뷰포트 기준값만 `px`로 둬도 줌 동작에 문제가 없습니다.
