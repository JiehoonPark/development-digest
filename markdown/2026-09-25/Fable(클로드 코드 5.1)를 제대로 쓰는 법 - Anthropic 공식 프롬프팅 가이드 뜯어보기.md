## 핵심 개념

> [!abstract]
> Theo가 Anthropic의 Claude Fable 5.1 공식 프롬프팅 가이드를 리뷰하며 한 달간 직접 사용한 경험을 정리합니다. Fable이 Astra보다 결과 품질 편차가 적어 선호한다는 점, 구독 한도 구조의 비효율성, 노력 수준(effort level) 설정 전략, 그리고 프롬프트 한 줄로 모델의 진행 상황 업데이트 행동을 바꿀 수 있다는 점을 다룹니다.

## 아티클

# Fable(클로드 코드 5.1)를 제대로 쓰는 법 - Anthropic 공식 프롬프팅 가이드 뜯어보기

Theo는 최근 자신을 "Anthropic 팬보이"라고 부른 Sam Altman의 발언에 응수하며, 왜 자신이 하루하루 작업에 Astra(OpenAI 계열 모델)보다 Fable(Claude Code)을 더 선호하는지 다시 짚어봅니다. 이번 글의 핵심은 단순 비교가 아니라, Anthropic이 공식으로 배포한 "Claude Fable 5.1 프롬프팅 가이드"를 읽고 나서 얻은 인사이트를 정리하는 것인데요. 지난 한 달간 이 모델로 어마어마한 양의 코드를 뽑아내면서 계정을 여러 번 태워먹은 경험을 바탕으로, 에이전트 커맨드 설정 개선법부터 모델이 더 나은 결과를 내도록 유도하는 방법까지 실무에 바로 쓸 수 있는 내용들을 추려봤습니다.

## Fable과 Astra, 품질의 노이즈 차이

이전 비교 영상에서 Theo는 두 모델의 출력 품질이 태스크에 따라 얼마나 들쭉날쭉한지 그래프로 표현한 적이 있습니다. Astra는 어떤 지점에서는 Fable보다 훨씬 좋은 결과를 내지만, 다른 지점에서는 훨씬 나쁜 결과를 내는 식으로 편차가 큽니다. 반면 Fable은 여전히 실수를 하긴 하지만 그 편차, 즉 "노이즈"가 훨씬 적다는 게 핵심입니다.

이 안정성은 단순히 신뢰도 문제를 넘어 실질적인 이점으로 이어집니다. 모델이 한 번의 실행에서 더 오래, 더 많은 작업을 할 수 있고, "끝나면 비디오 결과물을 가지고 돌아와"라는 지시를 실제로 수행해낼 수 있습니다. 대신 가끔 나오는 품질 저하가 상대적으로 더 뼈아프게 느껴지기 때문에, 이런 저하를 줄이는 방법을 찾는 게 매우 가치 있는 일이라는 겁니다.

## 구독 요금제의 현실: API 가격은 답이 아니다

Anthropic 가이드의 첫 섹션은 "모든 노력 수준(effort level)을 고려하라"는 내용인데, Theo는 이 조언이 구독자 입장에서는 다소 비현실적이라고 지적합니다. 구독자는 주간 한도의 50%만 Fable에 쓸 수 있고, 나머지 50%는 사실상 Opus 4에 배정되는데, Opus 4는 별로 좋은 모델이 아니기 때문입니다.

- API 정가로 Fable을 쓰는 건 Theo 생각에 돈값을 못 한다고 봅니다.
- Astra도 크게 나은 건 아닌데, 루프에 빠져서 오히려 사용량을 과도하게 태우는 경우가 있기 때문입니다.
- 중간값(median) 태스크 기준으로는 Fable이 더 비싸지만, 극단적인 경우엔 Astra가 훨씬 비효율적으로 사용량을 소모합니다.
- 다행히 Opus용 5.1(혹은 5.2) 버전이 곧 나올 예정이라, 스파이크성 소모가 줄어들 것으로 기대하고 있습니다.

Theo는 대부분 주가 끝날 때쯤이면 Opus 쪽에 배정된 나머지 50% 한도를 거의 다 써버린다고 언급하며, 이런 배경을 깔고 "노력 수준" 이야기를 봐야 한다고 강조합니다.

## 노력 수준(Effort Level) 설정: High가 기본값

Anthropic 가이드는 High에서 시작해서 자체 평가(eval)를 통해 다른 수준들을 테스트해보라고 권장합니다. 하지만 Claude Code 환경에서 이 정도로 정교하게 평가하는 사람은 거의 없다고 Theo는 말합니다. 알고 있는 답이 나와야 하는 태스크를 여러 노력 수준으로 돌려보며 감을 잡는 것도 방법이지만, 토큰을 너무 많이 태우기 때문에 그냥 "감"으로 판단하는 걸 추천합니다.

Theo 본인의 경험상:
- **Low/Medium**: 실패 확률이 높아서 거의 안 씀. 낮은 수준에서 실패하고 다시 Medium이나 High로 재시도하면 결국 토큰을 더 쓰게 됨
- **High**: 기본값으로 사용
- **X-High**: 정말 깊고 철저한 작업에 가끔 사용
- **Max**: 한도를 일부러 태우려는 게 아니면 거의 안 씀

중요한 점은, High를 단순한 태스크에 써도 모델이 불필요하게 추론을 낭비하지 않는다는 겁니다. Theo가 직접 시연한 예시에서, "안녕, 오늘 어때?"라는 간단한 인사에 Max reasoning을 걸어도 모델은 짧게 답했습니다. 다만 이 태스크 크기에 따른 조절 능력은 Astra가 더 뛰어나다고 인정합니다.

실제로 Theo가 만든 벤치마크(SkateBench)에서 Astra는 Low에서 Max로 올려도 토큰 사용량 차이가 130~180개 정도로 미미했던 반면, Gemini 1.5 Pro는 같은 태스크에 1,000개 이상의 추론 토큰을 썼습니다. 즉 Astra는 태스크 크기에 맞춰 추론 윈도우를 더 영리하게 조절하는 편이지만, Fable도 충분히 잘 조절해서 그냥 High에 두고 쓰기에 무리가 없다는 게 결론입니다.

Low나 Medium은 모델이 일찍 멈추길 원하거나, 특정 작업이 "래빗홀"에 빠질 걸 알고 있어서 깊이 파고드는 걸 막고 싶을 때만 쓰는 게 좋다고 조언합니다.

## 진행 상황 업데이트 요청하기: 프롬프트만으로 행동을 바꾼다

이번 가이드에서 Theo가 가장 흥미롭게 본 부분은 "사용자에게 보이는 진행 상황 업데이트를 요청하라(Ask for user-facing progress updates)"는 항목입니다. 이게 이번 영상을 만들게 된 계기이기도 합니다.

며칠 전 Julius가 Theo에게 왜 자신이 쓰는 T3 Code 버전에서는 Fable이 작업 경과를 보여주지 않냐고 물었는데, 답은 간단했습니다. "요청하지 않으면 보여주지 않기 때문"입니다. 실제로 요청하자 모델이 업데이트를 보여주기 시작했습니다.

Opus와 Fable 5는 원래 도구 호출을 할 때마다 "이걸 찾았으니 이제 저걸 하겠다" 식으로 이유와 업데이트를 계속 알려주는 경향이 있었고, 결과적으로 상당히 시끄러운(noisy) 출력이 나왔습니다. Anthropic은 5.1에서 이 부분을 의도적으로 줄였습니다. 긴 도구 호출 턴 동안 사용자 대상 업데이트를 훨씬 적게 작성하도록 만든 겁니다.

Theo도 이 변화를 직접 체감했습니다. Fable이 150번 가까이 도구 호출을 하는 동안 아무 업데이트 없이 조용히 작업만 하는 경우가 많았다고 하는데, 본인은 오히려 그 방식을 선호합니다. `command+shift+O`로 새 스레드를 열고, 원하는 작업을 지시한 뒤, 다른 스레드로 넘어가서 일하다가 끝나면 돌아와 확인하는 식의 워크플로우이기 때문에 중간 과정에 관심이 없다는 겁니다.

하지만 업데이트를 원하는 사람들을 위한 해법은 간단합니다. **그냥 요청하면 됩니다.** 시스템 프롬프트에 다음과 같은 지침을 추가하면 됩니다.

- 작업을 시작하기 전에 무엇을 할지 한 줄로 먼저 말할 것
- 작업 중간중간 짧은 업데이트를 제공해 사용자가 진행 상황을 따라갈 수 있게 할 것
- 마지막에는 그 자체로 완결된 짧은 요약으로 마무리할 것 — 무엇을 찾았고, 무엇을 했고, 다음은 무엇인지
- 마지막 메시지만 보는 독자도 전체 그림을 파악할 수 있도록 할 것

Theo는 이렇게 프롬프트만으로 모델의 심층적인 행동 방식을 바꿀 수 있다는 사실 자체가 놀랍다고 말합니다. 모델이 그만큼 똑똑하고 잘 학습되어 있다는 방증이라는 거죠. 덧붙여, 만약 만들고 있는 앱이나 제품이 도구 출력(tool output)을 UI에서 닫아버리는 구조라면, 모델에게 그 사실을 알려줘야 한다고 조언합니다. 그렇지 않으면 모델이 UI가 알아서 보여줄 거라 기대하고 아무것도 출력하지 않을 수 있기 때문입니다. Theo는 이 문제를 언급하며 자신이 만드는 T3 Code에도 이 부분을 반영해야겠다고 덧붙였습니다. 현재 T3 Code는 도구 호출 결과가 거의 쓸모없다는 이유로 화면에 보여주지 않고 있는데, 이 지침을 참고해 개선할 여지가 있다는 겁니다.

영상 후반부에는 API 히스토리를 편집할 때 생기는 변경 사항에 대한 콜아웃도 이어지지만, 이 부분은 다음 내용으로 넘어가는 지점에서 트랜스크립트가 끊깁니다.

---

중간에 Sentry의 스폰서십 소개도 등장합니다. 에이전트로 코드를 만들고, 에이전트를 사용자에게 서빙하는 시대에 버그를 잡는 게 점점 어려워지고 있다는 문제의식과 함께, Sentry MCP를 통해 에이전트도 동일한 버그 추적 데이터를 활용할 수 있다는 점을 소개합니다. Theo는 T3 Code에서 직접 트레이스를 수집한 데모를 보여주며, 요청 전체 비용뿐 아니라 요청 내 각 청크(chunk)별 비용까지 타임라인 뷰로 세세하게 분석할 수 있다는 점, 그리고 타임라인이 익숙하지 않은 사람을 위한 채팅 뷰(에이전트와 사용자 간 대화 트랜스크립트, 토큰 수, 에러 횟수, 비용 등을 함께 보여주는 뷰)가 특히 커스텀 툴이나 MCP를 디버깅할 때 유용하다고 강조합니다.

## 정리

- **Fable(Claude Code)이 Astra보다 결과 품질의 편차(노이즈)가 적다**는 점이 Theo가 Fable을 선호하는 핵심 이유입니다. 덕분에 모델이 더 오래, 더 안정적으로 작업을 이어갈 수 있습니다.
- **구독 요금제 기준으로 한도의 절반은 Fable, 나머지 절반은 상대적으로 약한 Opus 4에 배정**되는 구조이므로, API 정가 사용은 비효율적이라는 게 Theo의 판단입니다. Opus용 5.1/5.2 출시로 개선을 기대하고 있습니다.
- **노력 수준(effort level)은 기본적으로 High를 쓰고, 정말 깊은 작업에만 X-High를 사용**하는 것이 실용적입니다. Low/Medium은 실패 시 재시도 비용이 더 크기 때문에 잘 쓰지 않습니다. 다만 Astra가 태스크 크기에 따른 토큰 조절은 더 정교합니다.
- **"사용자 대상 진행 상황 업데이트를 요청하라"는 프롬프트 한 줄로 모델의 행동을 크게 바꿀 수 있습니다.** Fable 5.1은 기본적으로 업데이트를 적게 남기도록 조정됐지만, 필요하면 시스템 프롬프트에 명시적으로 요청하면 됩니다.
- 도구 출력을 UI에서 숨기는 제품을 만든다면, 모델에게 그 사실을 알려줘야 원하는 출력을 얻을 수 있습니다. 이는 프롬프트 설계 시 자주 놓치는 디테일입니다.
