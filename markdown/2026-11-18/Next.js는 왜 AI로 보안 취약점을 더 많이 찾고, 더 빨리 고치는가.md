## 핵심 개념

> [!abstract]
> Next.js의 보안 권고 건수가 2024년 6건에서 2026년 51건으로 급증했지만, 이는 프레임워크가 취약해져서가 아니라 AI 덕분에 오래된 코드의 엣지 케이스 버그를 찾는 비용이 낮아졌기 때문입니다. Vercel은 버그 바운티, 내부 보안 봇, Trail of Bits 감사로 기존 버그를 선제적으로 찾아내고, 모든 PR에 적대적 보안 리뷰 봇을 돌려 새 코드의 버그를 차단하며, Adapters와 메모리 안전 코덱 도입으로 구조적 리스크를 줄이고 있습니다. 동시에 next dev/build의 취약점 경고와 next upgrade --agent 명령으로 사용자가 안전한 버전을 쉽게 유지하도록 돕고 있습니다.

## 아티클

최근 몇 년간 Next.js 릴리스 노트를 유심히 봐온 개발자라면 보안 권고(security advisory) 건수가 눈에 띄게 늘어난 걸 알아챘을 겁니다. 2024년에는 6건, 2025년에는 14건이었던 권고가 2026년 현재까지 벌써 51건에 달합니다. 숫자만 보면 "Next.js가 점점 불안정해지는 거 아니냐"는 걱정이 들 수 있지만, Vercel은 오히려 지금이 역대 가장 안전한 시점이라고 말합니다. 이 글에서는 왜 권고 건수가 늘었는지, AI를 활용해 새 코드의 버그를 어떻게 막고 있는지, 그리고 사용자들이 항상 안전한 버전을 유지할 수 있도록 어떤 도구를 제공하는지 정리합니다.

## 왜 취약점이 늘어났을까

답은 단순합니다. AI 덕분에 취약점을 찾기가 훨씬 쉬워졌기 때문입니다.

보안 리포트를 받는 체계가 잘 갖춰진 인기 오픈소스 프로젝트라면, LLM의 능력이 점점 강력해지고 널리 보급되는 지금 시기에 권고 건수가 늘어나는 건 자연스러운 현상입니다.

그렇다면 왜 해마다 꾸준히 늘어나는 걸까요? 이유 중 하나는, 모든 프레임워크에는 발견되지 않았거나 악용하기엔 너무 비효율적이라고 여겨졌던 엣지 케이스 버그들이 쌓여 있다는 점입니다. AI가 등장하면서 이런 버그를 찾고 악용하는 비용이 크게 낮아졌고, 그 결과 예전엔 무시해도 됐던 엣지 케이스가 이제는 반드시 고쳐야 할 리스크로 바뀌었습니다.

실제로 올해 발견된 51건의 취약점 중 70%는 1년 이상 된 코드에서 나왔고, 43%는 3년 이상 된 코드에서 발견됐습니다.

- 1년 미만 코드: 30%
- 1~3년 코드: 27%
- 3년 이상 코드: 43%

이런 패턴은 Next.js만의 문제가 아니라 업계 전반의 성숙한 프레임워크와 프로그래밍 언어에서 동일하게 나타나고 있습니다.

더불어 이 현상은 Next.js가 의존하는 업스트림 라이브러리에서도 똑같이 벌어지고 있습니다. Next.js는 사이트 속도를 최대한 끌어올리기 위해 이미지 최적화 같은 기능을 기본 제공하는데, 다른 많은 프레임워크는 이 부분을 개발자에게 맡깁니다. 올해 발견된 취약점 상당수는 Next.js 자체 코드가 아니라, Next.js가 의존하는 이미지 처리 라이브러리에서 나온 것이었습니다.

이런 변화에 대응하기 위해 Vercel은 보안 프로그램을 더 선제적으로 운영하기 시작했고, 그 첫걸음은 기존 버그가 실제 공격으로 악용되기 전에 고칠 수 있는 체계와 인센티브를 마련하는 것이었습니다.

## 공격자보다 먼저 오래된 버그 찾기

Next.js의 오래된 코드에 쌓여 있던 미발견 버그 더미를 어떻게 처리하고 있는지 살펴보겠습니다.

### 버그 바운티 프로그램

1차 방어선은 새로운 취약점을 발견한 연구자에게 보상을 지급하는 버그 바운티 프로그램입니다. 이 프로그램의 목적은 누군가 버그를 직접 악용하는 것보다 비공개로 신고하는 쪽이 경제적으로 더 이득이 되도록 만드는 데 있습니다. 실제로 효과가 있어서, 최근 몇 년간 공개된 보안 권고 상당수는 바운티 리포트에서 출발했습니다.

### 보안 봇 개발

AI는 공격자가 기존 버그를 찾기 쉽게 만든 동시에, Vercel에게도 같은 이점을 줬습니다. Vercel은 Eve를 활용해 취약점을 찾고, 들어오는 리포트를 분류(triage)하고, 재현 환경을 구축하고, 심각도를 검증하고, 수정 사항이 충분한지 분석하는 내부 봇을 개발했습니다. 이 봇 덕분에 팀은 이전보다 훨씬 많은 양의 인바운드 리포트를 더 빠르게 처리할 수 있게 됐습니다.

### Trail of Bits 감사

독립 보안 기업인 Trail of Bits에 Next.js 수동 보안 감사를 의뢰했습니다. 이들은 다른 경로로는 발견하지 못했던 이슈들을 찾아냈고, 이는 기존 코드베이스를 보강하는 노력에서 중요한 한 축이 됐습니다.

이렇게 여러 경로에서 쏟아지는 수정 사항을 사용자가 예측 가능한 일정에 맞춰 적용할 수 있도록, Vercel은 새로운 보안 릴리스 프로그램을 만들었습니다. 이제 보안 릴리스는 대략 한 달에 한 번씩 사전 공지와 함께 배포되며, 덕분에 개발자는 업그레이드 일정을 미리 계획할 수 있고 호스팅 제공업체들도 세부 내용이 공개되기 전에 보호 조치를 마련할 수 있습니다.

Vercel은 이렇게 잠재된 버그 재고를 소진해 나가면서, 연간 권고 건수의 추세가 점차 바뀔 것으로 기대하고 있습니다.

## 새 코드에서 보안 버그 막기

Vercel의 모든 팀이 그렇듯 Next.js 팀도 AI를 활용해 그 어느 때보다 빠르게 새 기능을 출시하고 있습니다. 이 과정에서 새로운 버그가 프레임워크에 섞여 들어가지 않도록 몇 가지 조치를 취하고 있습니다.

### 적대적 리뷰 봇

먼저 Vercel Agent 팀과 협력해 새로운 Security Review 기능이 Next.js에 잘 작동하도록 함께 작업했습니다. 이제 Vercel Agent는 Next.js의 모든 풀 리퀘스트에서 실행되며, Next.js 전용 커스텀 보안 가이드라인을 기준으로 실제로 해킹을 시도합니다.

보안 리뷰는 GitHub push 이벤트로 트리거됩니다. PR이 아무리 작아도, 프레임워크의 어떤 부분을 건드리든 상관없이 에이전트는 공격자의 시선으로 변경 사항을 들여다보고 실제로 악용을 시도합니다. 실제로 이미 코드 리뷰를 통과하고 CI도 초록불이었던, 거의 머지 직전이었던 PR에서 이슈를 잡아낸 사례도 있습니다. 이는 새로운 취약점이 배포되는 것을 사전에 막은 셈입니다.

기존 버그 더미를 정리하는 작업과 합쳐지면, 시간이 지날수록 취약점 건수 자체가 줄어드는 효과를 기대할 수 있습니다.

### 서비스 경계 강화

지금까지 수집한 취약점 데이터를 활용해, 보안 리스크에 특히 취약한 프레임워크의 일부 구조를 재설계하고 있습니다.

Next.js는 원래 Node.js 위에서 돌아가는 단순한 셀프 호스팅 도구로 시작했지만, 지난 10년간 프록시 라우팅 레이어, CDN, 다양한 JavaScript 런타임 등 최신 클라우드 제공업체가 제공하는 프리미티브들과 함께 동작하는 종합적인 풀스택 프레임워크로 성장했습니다.

이런 레이어들 사이의 불일치는 보안 우회(bypass)의 원인이 될 수 있습니다. 그래서 Adapters라는 체계를 통해 이 경계를 명확히 정식화하고 있는데, 이는 호스팅 제공업체에게 Next.js 앱이 정확히 어떻게 서비스되어야 하는지를 알려주는 잘 정의된 계약입니다. Adapters가 성숙하고 더 널리 채택될수록, 이런 유형의 버그는 완전히 사라질 것으로 보고 있습니다.

### 취약한 의존성 교체

올해 패치한 취약점 중 가장 심각한 이슈 상당수는 Next.js 자체 코드가 아니라 의존 라이브러리에서 나왔습니다. 서드파티 의존성에서 많은 가치를 얻고 있지만, 이들이 항상 Next.js의 정확한 요구사항이나 위협 모델에 맞춰 설계된 것은 아닙니다.

이미지 최적화 같은 기능은 폭넓은 기능성과 호환성을 목표로 하는 라이브러리에 의존하는데, 이런 코드 경로는 신뢰할 수 없는 사용자 입력을 다룰 가능성이 높으면서도 코드 규모가 커서 검증하기 어렵습니다. 요구사항과 위협 모델의 불일치는 결국 원하는 수준보다 약한 보안 보장으로 이어질 수 있습니다.

이미지 최적화의 경우, 커뮤니티에서는 이미 메모리 안전(memory-safe) 대체 코덱들을 만들어 왔습니다. 이 중 일부는 비슷한 보안 과제를 안고 있는 웹 브라우저에서도 이미 사용되고 있습니다. AI를 활용해 통합 프로토타입을 빠르게 만들고 샌드박싱 레이어를 반복 개선함으로써, 예전보다 훨씬 빠르게 이런 최신 코덱을 도입할 수 있었습니다. 관련 진행 상황은 추후 더 자세히 공유할 예정입니다.

## 사용자의 앱을 안전하게 유지하기

프레임워크 자체가 점점 안전해지더라도, 실제 프로덕션 앱이 안전한 버전을 쓰고 있지 않으면 소용이 없습니다. 이를 위해 Vercel은 최신 버전 유지를 돕는 몇 가지 도구를 만들었습니다.

Next.js 16.4부터 `next dev`와 `next build`는 현재 실행 중인 버전이 알려진 취약점의 영향을 받는지 알려줍니다. 개발 모드에서는 Next.js DevTools에 Vulnerability Insight가 표시되며, 코딩 에이전트에 바로 복사해 넣을 수 있는 프롬프트도 함께 제공됩니다.

업그레이드 과정 전체를 맡기고 싶다면 다음 명령을 실행하면 됩니다.

```
npx next@canary upgrade --agent
```

이 명령은 현재 버전을 보안 권고와 대조해 가장 최신의 안전한 릴리스를 골라줍니다. 이때 패치가 있는 가장 오래된 메이저 버전 범위 안에서 선택하기 때문에, 단순히 패치를 적용하려고 메이저 업그레이드까지 떠안을 필요는 없습니다. 이후 관련 마이그레이션 가이드와 함께 코딩 에이전트에 작업을 넘기면, 에이전트가 변경 사항을 적용하고 앱이 정상 동작하는지 검증까지 수행합니다.

## 정리

- 2024년 6건, 2025년 14건, 2026년(현재까지) 51건으로 Next.js 보안 권고 건수가 꾸준히 늘고 있는데, 이는 Next.js가 덜 안전해졌다기보다 AI로 인해 기존 코드의 엣지 케이스 버그를 찾는 비용이 급격히 낮아졌기 때문입니다. 올해 발견된 취약점의 70%는 1년 이상, 43%는 3년 이상 된 코드에서 나왔습니다.
- 이미지 최적화처럼 Next.js가 의존하는 서드파티 라이브러리도 취약점의 주요 출처로 떠올랐습니다.
- 기존 버그 발굴을 위해 버그 바운티 프로그램, Eve 기반 내부 보안 봇, Trail of Bits 수동 감사를 병행하고, 매달 예고된 일정으로 보안 릴리스를 내보내는 체계를 갖췄습니다.
- 새 코드의 버그를 막기 위해 모든 PR에서 공격자 관점으로 동작하는 Vercel Agent Security Review를 돌리고, Adapters로 호스팅 환경 간 경계를 명확히 하며, 메모리 안전 코덱 등으로 취약한 의존성을 교체하는 작업을 진행 중입니다.
- 개발자 쪽에서는 `next dev`/`next build`의 취약점 경고, DevTools의 Vulnerability Insight, `npx next@canary upgrade --agent` 명령으로 안전한 버전 유지를 훨씬 쉽게 만들어 줍니다.

실무적으로는 Next.js 프로젝트를 운영 중이라면 16.4 이상으로 올려 보안 경고 기능을 활성화하고, `upgrade --agent` 명령을 정기적인 업데이트 루틴에 포함시키는 것이 좋습니다. 또한 보안 권고 건수 증가를 프레임워크의 품질 저하로 오해하기보다, AI 시대에 성숙한 오픈소스 프로젝트가 겪는 공통적인 흐름으로 이해하고 대응 체계를 갖춘 프로젝트인지를 판단 기준으로 삼는 게 더 합리적입니다.
