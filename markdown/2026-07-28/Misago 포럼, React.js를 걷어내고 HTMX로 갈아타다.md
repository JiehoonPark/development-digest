## 핵심 개념

> [!abstract]
> 오픈소스 포럼 소프트웨어 Misago는 Django 템플릿과 React.js 컴포넌트를 이중 구현하면서 커스터마이징 혼란, 번역 중복, JS 번들 비대화 같은 문제를 겪어왔습니다. 개발자는 완전한 SPA나 Next.js/Remix 도입 대신, 페이지 일부만 서버 렌더링 HTML로 교체하는 HTMX를 채택하기로 했습니다. 실제로 Account settings 페이지와 스레드 목록을 HTMX 기반으로 재작성한 결과 misago.js 번들이 615KB에서 530KB(gzip 124KB→99KB)로 줄어드는 성과를 확인했습니다.

## 아티클

# Misago 포럼 소프트웨어, React.js를 걷어내고 HTMX로 갈아타다

오픈소스 포럼 소프트웨어 Misago의 개발자가 자신의 프로젝트에서 React.js를 걷어내고 HTMX로 전환하기로 한 결정을 공유했습니다. SPA 아키텍처가 낳은 이중 구현 문제, 번들 크기 문제를 실제 수치와 함께 짚어보고, 왜 최신 프레임워크(Next.js, Remix) 대신 HTMX라는 오래된 아이디어를 다시 꺼내 들었는지 설명하는 내용인데요. 포럼처럼 "부분적으로만 인터랙티브한" 페이지를 만들 때 React가 정말 최선의 선택인지 고민하는 개발자라면 참고할 만합니다.

## 현재 구조와 문제점

Misago가 지금까지 페이지를 렌더링하는 방식은 이렇습니다.

1. `https://misago-project.org`에 접속하면 Django 뷰가 스레드 목록에 필요한 데이터를 모읍니다.
2. Django 뷰는 스레드 목록이 담긴 완전한 HTML을 템플릿으로 렌더링합니다. 이때 같은 데이터를 담은 JSON도 함께 페이지에 심어둡니다. 하지만 폼이 비활성화되어 있어 이 시점엔 아무 인터랙션도 되지 않습니다.
3. JavaScript가 다운로드됩니다.
4. JavaScript가 실행되면서 페이지 body에 박혀 있던 JSON을 읽어, Django 템플릿이 그려놓은 HTML 대부분을 React.js 컴포넌트가 렌더링한 HTML로 갈아치웁니다. 그제서야 버튼이 활성화되고 타임스탬프 표기도 바뀝니다.

문제는 이 과정에서 발생합니다.

- **같은 페이지를 두 번 구현**해야 합니다. Django 템플릿 버전과 React.js 컴포넌트 버전이 따로 존재합니다.
- HTML을 커스터마이징하려는 사람들이 혼란을 겪습니다. Django 템플릿을 고쳐서 확인해보면 잠깐 화면에 반영됐다가, React.js가 그 HTML을 다시 덮어써버리는 걸 뒤늦게 알게 됩니다.
- 로그인 사용자와 게스트 모두 접근 가능한 뷰는 전부 Django 뷰+템플릿, React.js 라우트+컴포넌트로 이중 구현해야 합니다. 여기에 데이터를 가져오기 위한 API와 JSON 시리얼라이저까지 필요합니다.
- React.js 앱에 데이터를 미리 구워 넣기 위한 JSON 시리얼라이제이션이 응답 생성 속도를 늦춥니다.
- 번역 메시지의 상당수가 `django.po`와 `djangojs.po` 양쪽에 중복 존재합니다. JavaScript 번역 파일은 초기 다운로드 크기도 늘립니다.
- JavaScript 양이 많아지면서 특히 오래되고 느린 모바일 기기에서 성능이 떨어집니다.
- 플러그인 개발자가 페이지에 커스텀 HTML을 주입하려면 Django 템플릿과 React.js 컴포넌트를 둘 다 구현해야 하고, 이를 위해 `misago-docker`에 JavaScript 빌드 스텝까지 넣어야 합니다. 플러그인 개발자는 양쪽 스택을 모두 알아야 하는 부담을 지게 됩니다.

## 검토했던 대안들

이 문제를 해결하기 위해 두 가지 방향을 고려했습니다.

1. Django 뷰와 템플릿을 아예 버리고, 검색엔진 봇을 달래기 위한 최소한의 버전만 남긴 뒤 API 구현과 React.js 앱에 집중하는 방향.
2. Django를 API 전용으로 축소하고, Next.js나 Remix.run처럼 서버사이드 렌더링을 지원하는 JavaScript 프레임워크를 쓰는 방향.

하지만 관점을 바꿔보면, 세상에는 여전히 서버에서 최대한 렌더링을 끝내고 클라이언트에서는 필요한 부분에만 약간의 JavaScript로 인터랙티브함을 더하는 방식의 포럼 소프트웨어가 많이 존재하고, 사람들은 이 방식에 충분히 만족하고 있습니다. 그리고 이 방식에는 위에서 나열한 문제들이 애초에 존재하지 않습니다.

포럼 소프트웨어에는 인터랙션이 꽤 많지만, 사실 이 인터랙션들은 페이지의 특정 부분에만 국한되어 있습니다. 모더레이션 액션, 스레드 구독, 답글 작성, 최근 알림 확인, 투표 참여 같은 것들인데요. 이 모든 기능은 React.js 없이도 구현 가능하며, 실제로 "전체 페이지 리로드는 무조건 피해야 한다"는 통념이 자리잡기 전 수년간 그렇게 구현되어 왔습니다.

## HTMX란 무엇인가

HTMX는 HTML의 일부를 "다이나믹 아일랜드"로 지정해서, 사용자 인터랙션이 일어날 때 서버가 렌더링한 새 HTML로 그 부분만 교체할 수 있게 해주는 작은 라이브러리입니다.

예를 들어 실제 스레드 목록은 이런 아일랜드 중 하나(꽤 큰 아일랜드)가 될 수 있습니다. Django 템플릿에 HTMX 몇 줄만 넣으면, 스레드 목록에서 카테고리를 변경할 때 선택된 카테고리의 새 스레드 목록 HTML만 Django에서 가져오고, 페이지의 나머지 부분(예를 들어 이미 로드된 네비바의 검색 결과)은 그대로 유지할 수 있습니다. 백엔드 코드는 요청이 HTMX에서 온 경우 전체 페이지 대신 해당 아일랜드의 HTML만 반환하도록 살짝 고치면 되고, 별도의 JSON 시리얼라이제이션이나 전용 JavaScript, React.js 코드는 필요 없습니다.

한마디로 HTMX는 20년 전 jQuery로 하던 `$.get("url", "#outlet")` 방식을 선언적으로 다시 구현한 것에 가깝습니다. Rails의 Turbolinks와도 비슷한 개념이죠. 개발자 본인도 "이걸 지금 와서 다시 쓰게 될 줄은 몰랐다"고 표현할 정도인데, 무한 스크롤이 싫거나 구조를 단순하게 유지하고 싶은 포럼 소프트웨어라면 이 방식이 답이라는 결론에 이르렀습니다.

관련 논의는 GitHub 이슈 #1674에서 확인할 수 있습니다.

## 관리자 패널은 그대로 둔다

한 가지 특기할 점은, 관리자 패널(admin panel)은 SPA로 옮기지 않기로 했다는 겁니다. 현재 재사용 가능한 Django 뷰들이 작업의 90%를 처리해주고 있고, 관리자 패널에 새 페이지를 추가하려면 적절한 베이스 뷰를 골라 빈칸을 채우고, 폼 한두 개를 정의한 뒤 아주 기본적인 템플릿만 작성하면 됩니다. 나머지는 자동으로 처리되는 이 구조가 마음에 든다는 이유입니다.

## 마이그레이션 계획과 과도기

React.js를 걷어내고 HTMX로 옮기는 작업은 결코 작지 않은 노력이 필요하지만, 여러 개의 작은 단계로 나눠 진행할 수 있습니다. 예를 들어 한 릴리스에서는 네비바를, 다음 릴리스에서는 스레드 목록을, 그다음엔 스레드 페이지를, 또 그다음엔 사용자 프로필을 HTMX로 옮기는 식입니다. 다만 플러그인, 권한 시스템, 새 파서 작업이 먼저 마무리되어야 하기 때문에 HTMX 마이그레이션은 2024년 하반기로 미뤄질 예정입니다. 이 시기에 맞춰 최신 Bootstrap으로도 옮기고 싶다는 계획도 밝혔는데, Bootstrap 팀이 준비 중인 변화들이 상당히 흥미롭다는 이유입니다.

과도기에는 일부 영역이 React.js도, HTMX도 적용되지 않은 상태, 즉 사실상 "멀티페이지 애플리케이션"이 되는 구간이 생길 수밖에 없다는 점도 미리 짚었습니다. 예를 들어 사용자 옵션 페이지에서 링크를 클릭하거나 폼을 제출하면 전체 페이지가 다시 로드되는 식입니다. 다만 전체 페이지 리로드가 도저히 용납되지 않는 부분, 예를 들어 게시글 좋아요나 투표 같은 기능에는 임시 AJAX(혹은 바로 HTMX)를 적용할 계획입니다.

## 실제 진행 상황과 번들 크기 변화

전환 전, Misago 0.39 기준 JavaScript 번들 크기는 다음과 같았습니다.

- `vendor.js`: 679KB (gzip 214KB)
- `misago.js`: 615KB (gzip 124KB)
- `django-i18n.js`: 102KB (gzip 25.4KB)

여기에 지연 로딩되는 항목도 있습니다.

- `hljs.js`: 144KB (gzip 49KB)
- `zxcvbn.js`: 820KB (gzip 430KB)

이 수치들을 기준선으로 삼아 React.js(그리고 다른 JS 의존성들)를 제거하면서 변화를 추적하겠다고 밝혔습니다.

실제로 "Forum options" 페이지가 "Account settings" 페이지로 교체되었는데, 이 새 페이지는 전부 Django 뷰로 구현되었고 일부 페이지에서 동적 업데이트를 위해 HTMX를 사용합니다. 이 변경만으로 `misago.js`가 578KB(gzip 107KB)로 줄어, 기존 대비 37KB(gzip 17KB) 감소했습니다.

이어서 스레드 목록도 거의 처음부터 다시 작성해 React.js 대신 Django 뷰와 HTMX로 구현했습니다. 그 결과 `misago.js`는 530KB(gzip 99KB)로 줄어, 48KB(gzip 8KB) 추가 감소를 기록했습니다.

## 정리

- Misago는 스레드 목록 페이지를 Django 템플릿과 React.js 컴포넌트로 이중 구현해왔고, 이 때문에 커스터마이징 혼란, 번역 파일 중복, JSON 시리얼라이제이션 오버헤드, JS 번들 비대화, 플러그인 개발 부담 등 여러 문제가 누적되어 왔습니다.
- 완전한 SPA 전환이나 Next.js/Remix 같은 SSR 프레임워크 도입 대신, 인터랙션이 페이지의 특정 영역에만 국한된다는 포럼 소프트웨어의 특성을 살려 HTMX를 채택했습니다. HTMX는 필요한 부분(아일랜드)만 서버에서 새 HTML로 받아 교체하는 방식으로, 별도의 API/JSON 레이어 없이 Django 뷰만으로 인터랙티브함을 구현할 수 있게 해줍니다.
- 관리자 패널은 재사용 가능한 Django 뷰 구조가 이미 효율적으로 작동하고 있어 SPA로 옮기지 않기로 했습니다.
- 마이그레이션은 네비바, 스레드 목록, 스레드 페이지, 사용자 프로필 순으로 릴리스별로 점진적으로 진행되며, 과도기에는 일부 영역이 전체 페이지 리로드 방식(MPA)으로 동작하는 구간이 있을 수 있습니다.
- 실제로 Account settings 페이지 교체와 스레드 목록 재작성만으로 `misago.js`가 615KB → 530KB(gzip 124KB → 99KB)로 줄었으며, 이는 React.js를 걷어내는 작업이 실질적인 번들 크기 개선으로 이어지고 있음을 보여줍니다.
