## 핵심 개념

> [!abstract]
> GitHub Actions가 워크플로우 lockfile 기능을 공식 지원하면서, 보안을 위해 긴 SHA 값으로 action을 고정하던 기존 관행 대신 사람이 읽기 쉬운 태그와 별도의 lockfile을 조합하는 방식이 가능해졌습니다. gh-actions-lock CLI 확장으로 워크플로우를 잠그고, Renovate/Dependabot으로 자동 갱신하며, CI에서 gh actions-lock --verify와 zizmor로 검증하는 전체 흐름을 소개합니다.

## 아티클

# GitHub Actions 워크플로우, 이제 Lockfile로 잠그세요

GitHub Actions의 보안 모범 사례는 원래 "태그 대신 전체 SHA로 고정(pin)하라"였습니다. GitHub Actions는 Git에서 가져오는 방식이기 때문에, 태그는 언제든 다른 커밋을 가리키도록 바뀔 수 있는 가변(mutable) 참조이고, 공격자가 한때 안전했던 태그를 악성 코드로 바꿔치기하는 공급망 공격(supply-chain attack)에 취약했기 때문입니다. 그래서 다들 이런 식으로 긴 SHA 값을 워크플로우에 박아 넣어왔습니다.

```yaml
name: Lint
on: [push, pull_request, workflow_dispatch]
permissions: {}
env:
  FORCE_COLOR: 1
  RUFF_OUTPUT_FORMAT: github
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: j178/prek-action@44924fe9ef4a6f88253c4b6b1bf11c689d3ce53d # v3.1.0
```

문제는 이런 SHA 고정 방식이 가독성을 크게 해친다는 점이었습니다. `@v7.0.1` 같은 사람이 읽을 수 있는 태그 대신 저 긴 해시 값이 코드에 그대로 노출되니, 어떤 버전을 쓰고 있는지 한눈에 파악하기 어려웠습니다. 이제 GitHub Actions가 워크플로우 lockfile 기능을 공식 지원하면서, 가독성과 보안을 동시에 챙길 수 있게 됐습니다. npm의 `package-lock.json`처럼, 사람이 읽는 워크플로우 파일은 태그를 쓰고, 실제 고정된 커밋 정보는 별도의 lockfile에서 관리하는 방식입니다.

## 설치하기

먼저 `gh` CLI에 `gh-actions-lock` 확장을 설치합니다.

```bash
$ gh extension install github/gh-actions-lock
✓ Installed extension github/gh-actions-lock
```

## 잠그기

저장소 루트에서 다음 명령을 실행하면 끝입니다.

```bash
$ gh actions-lock
✓ All 1 workflows valid
```

이 명령을 실행하면 워크플로우 파일의 SHA 고정이 다시 사람이 읽기 쉬운 `vX.Y.Z` 태그로 바뀝니다.

```diff
diff --git a/.github/workflows/lint.yml b/.github/workflows/lint.yml
index 946971c..3503607 100644
--- a/.github/workflows/lint.yml
+++ b/.github/workflows/lint.yml
@@ -13,7 +13,7 @@ jobs:
     runs-on: ubuntu-latest
     steps:
-      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
+      - uses: actions/checkout@v7.0.1
         with:
           persist-credentials: false
-      - uses: j178/prek-action@44924fe9ef4a6f88253c4b6b1bf11c689d3ce53d # v3.1.0
+      - uses: j178/prek-action@v3.1.0
```

그리고 실제 보안을 담당하는 lockfile이 `.github/workflows/actions.lock` 경로에 생성됩니다.

```yaml
# This file is machine-generated by `gh actions-lock`.
# Do not edit by hand; run `gh actions-lock` to update.
# Docs: https://gh.io/actions-lockfile
version: 'v0.0.3'
workflows:
  '.github/workflows/lint.yml':
    - 'actions/checkout@v7.0.1'
    - 'j178/prek-action@v3.1.0'
dependencies:
  'actions/checkout@v7.0.1':
    ref: 'v7.0.1'
    commit: 'sha1-3d3c42e5aac5ba805825da76410c181273ba90b1'
    owner_id: 44036562
    repo_id: 197814629
  'j178/prek-action@v3.1.0':
    ref: 'v3.1.0'
    commit: 'sha1-44924fe9ef4a6f88253c4b6b1bf11c689d3ce53d'
    owner_id: 10510431
    repo_id: 1052387486
```

워크플로우 파일과 새로 생성된 lockfile을 함께 커밋하면 됩니다.

## Renovate와 Dependabot도 이미 지원

다행히 Renovate와 Dependabot 모두 이미 lockfile을 지원합니다. 평소처럼 주기적인 의존성 업데이트를 돌리면 lockfile도 함께 갱신됩니다. 다만 쿨다운(cooldown) 설정을 활용하는 것을 잊지 말아야 합니다.

## CI에서 검증하기

GitHub은 lockfile이 최신 상태인지, 손상되지 않았는지를 CI에서 검증할 것을 권장합니다. 공식적으로는 `verify-lockfile.yml`이라는 워크플로우 파일을 그대로 복사해 쓰는 방법을 제안하는데, 원문 작성자는 이를 기존 lint 워크플로우 안에 별도 job으로 추가해, 독립적으로 그리고 병렬로 실행되도록 구성했습니다.

```yaml
name: Lint
on: [push, pull_request, workflow_dispatch]
permissions: {}
env:
  FORCE_COLOR: 1
  RUFF_OUTPUT_FORMAT: github
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7.0.1
        with:
          persist-credentials: false
      - uses: j178/prek-action@v3.1.0

  # Fails when .github/workflows/actions.lock is out of sync with the
  # workflows or a locked pin no longer verifies upstream.
  lockfile:
    runs-on: ubuntu-slim
    env:
      GH_TOKEN: ${{ github.token }}
    steps:
      - uses: actions/checkout@v7.0.1
        with:
          persist-credentials: false
      - run: gh extension install github/gh-actions-lock --pin v0.4.1
      - run: gh actions-lock --verify
```

여기서 몇 가지 눈여겨볼 점이 있습니다. 가벼운 `ubuntu-slim` 러너를 사용했고, `gh-actions-lock` 확장은 `v0.4.1`로 핀 고정을 해뒀습니다. 이 핀은 언젠가 직접 업데이트하거나 자동화할 방법을 찾아야 하는데, 이는 추후 과제로 남겨뒀습니다.

주의할 점은, 워크플로우의 action 구성을 수정했다면 반드시 `gh actions-lock`을 다시 실행해 재잠금(relock)해야 한다는 것입니다. 예시에서처럼 `lint.yml`에 job을 추가하는 정도는 이미 `actions/checkout`을 잠그고 있어 실제로는 변경 사항이 없지만, `verify-lockfile.yml` 같은 새 파일을 만들었다면 반드시 재잠금이 필요합니다. 만약 깜빡하더라도 CI가 알려줍니다.

## zizmor와 함께 쓰기

zizmor는 GitHub Actions를 위한 보안 린터로, 강력하게 권장되는 도구입니다. 아직 안 쓰고 있다면 꼭 도입해보길 권합니다.

v1.32.0 이전 버전의 zizmor는 action을 해시로 고정하라고 안내했는데, v1.32.0부터 처음으로 lockfile을 지원하기 시작했습니다. 원문 작성자는 prek에서 zizmor를 사용하고 있어, `.pre-commit-config.yaml`에 zizmor를 추가/업데이트했습니다.

```yaml
  - repo: https://github.com/zizmorcore/zizmor-pre-commit
    rev: v1.32.0
    hooks:
      - id: zizmor
```

## 정리

- **문제의 본질**: 기존에는 공급망 공격을 막기 위해 가변 태그 대신 긴 SHA 값으로 action을 고정해야 했는데, 이는 가독성을 심각하게 해치는 방식이었습니다.
- **해결책**: GitHub Actions의 신규 lockfile 기능과 `gh-actions-lock` CLI 확장을 쓰면, 워크플로우 파일은 `@v7.0.1`처럼 사람이 읽기 쉬운 태그를 유지하면서도, 실제 고정은 `.github/workflows/actions.lock` 파일이 커밋 해시 기준으로 담당합니다.
- **적용 절차**: `gh extension install github/gh-actions-lock` → `gh actions-lock` 실행 → 워크플로우와 lockfile 커밋, 이 세 단계면 충분합니다.
- **자동화 생태계**: Renovate와 Dependabot이 이미 lockfile 갱신을 지원하므로 기존 의존성 자동 업데이트 파이프라인에 자연스럽게 녹아듭니다.
- **CI 검증 필수**: `gh actions-lock --verify`를 CI job으로 추가해 lockfile이 최신 상태인지, 손상되지 않았는지 지속적으로 확인해야 하며, zizmor v1.32.0 이상을 함께 사용하면 보안 린팅까지 커버할 수 있습니다.

CI/CD 파이프라인을 운영하는 프론트엔드 개발자라면, 지금 쓰고 있는 워크플로우가 SHA 고정으로 지저분해져 있는지, 혹은 반대로 가변 태그를 그대로 쓰고 있어 공급망 공격에 노출돼 있는지 점검해볼 좋은 계기가 될 것 같습니다.
