## 핵심 개념

> [!abstract]
> us-vs-them은 에이전틱 코딩/에이전틱 에디팅 환경에서 텍스트의 각 줄이 사람에 의해 작성되었는지 AI 에이전트에 의해 생성되었는지를 Git 버전 히스토리 기반 diff로 추적하는 CLI 도구이자 라이브러리입니다. 별도 마크업 없이 플레인 텍스트를 그대로 지원하며, 줄 단위가 아닌 '의미적으로 응집된 범위' 단위로 저자성을 판별해 0.00(완전 에이전트 작성)~1.00(완전 사람 작성) 점수로 출력합니다. 바이브코딩 프로젝트에서 사람이 소유권을 주장하고 싶은 코드 영역이나, 자동 생성 문서 중 직접 수정한 부분을 다음 에이전트 세션에서 보호하려는 용도로 만들어졌습니다.

## 아티클

## 에이전틱 코딩 시대, "이 줄은 누가 썼는가"라는 질문

AI 에이전트가 코드베이스를 직접 수정하는 에이전틱 코딩·에이전틱 에디팅이 일상이 되면서, 새로운 종류의 문제가 생겨났습니다. 바로 **provenance(출처 추적)** 문제입니다. 사람이 직접 쓰거나 손댄 텍스트와, 다른 에이전트가 마구 생성한 "슬롭(slop)" 텍스트를 구분할 방법이 필요해진 것이죠. `us-vs-them`은 이 문제를 diff 기반으로 풀어내는 라이브러리이자 CLI 도구입니다.

## 왜 이런 도구가 필요한가

에이전트가 반복적으로 코드를 편집하는 워크플로우에서는, 사람이 직접 작성하거나 수정한 텍스트는 거의 신성불가침에 가깝게 다뤄져야 합니다. 에이전트가 이 부분을 건드리려면 아주 확실한 이유가 있어야 하죠. 반대로 다른 에이전트가 만들어낸 코드는 언제든 갈아엎어도 무방한 대상입니다.

저장소 저자가 든 대표적인 사례는 두 가지입니다.

- **거의 전부 바이브코딩으로 만든 앱**에서, 특정 부분만큼은 자신의 아이디어와 소유권을 확실히 주장하고 싶은 경우. 다음 세션에서 다른 에이전트가 이 부분을 밀어버리는 걸 막아야 합니다.
- **처음엔 자동 생성됐던 README.md**에서, 도입부 문단만 직접 다시 썼다면 에이전트가 그 아래 부분은 자유롭게 재작성하거나 추가해도 되지만, 도입부만큼은 손대기 전에 재차 고민해야 하는 경우.

## 동작 원리: 텍스트에 마크업 없이도 출처를 추적한다

이 도구를 설계할 때 핵심 제약 조건은 **텍스트에 별도의 마크업을 요구하지 않는다**는 점입니다. 어디에나 존재하는 플레인 텍스트(마크다운)를 있는 그대로 지원해야 한다는 원칙이죠.

그래서 활용할 수 있는 유일한 단서는, 텍스트의 각 새 버전이 식별 가능한 저자(사람이든 에이전트든) 아래서 만들어진다는 사실뿐입니다. Git 저장소는 이미 이런 버전 히스토리 그 자체입니다 — 파일의 모든 리비전이 순서대로 기록되어 있고, 각 변경을 만든 저자 정보도 함께 남아 있으니까요.

평가 결과로 출력되는 것은 일련의 **범위(range)** 집합입니다. 기계가 생성한 텍스트라는 "바다(sea)" 안에 사람이 작성한 텍스트가 "섬(island)"처럼 존재하는 형태로 표현되죠. 기술적으로는 단순한 diff 알고리즘을 기반으로 하지만, 알고리즘을 설계하는 데 있어 이 "섬과 바다" 은유가 핵심 가이드라인이 됩니다. 개별 줄 단위로만 저자를 추적하는 게 아니라, **의미적으로 응집된 텍스트 덩어리** 단위로 추적하는 게 목표이기 때문입니다.

그래서 알고리즘은 다음과 같은 동작을 함께 고려합니다.

- 텍스트 조각을 합치는(joining) 동작
- 텍스트 조각을 분리하는(splitting apart) 동작
- 저자성이 희석되는(dilution of authorship) 동작

그리고 이 모든 동작이 결국 결과가 "완전한 바다" 혹은 "완전한 섬"으로 수렴해버리지 않도록 균형을 잡는 것도 중요한 설계 목표입니다.

## 사용법

CLI 도구로 쓰려면 로컬 설치를 위해 `bbin`이 필요합니다.

```
make install
```

Git 저장소 안 어디서든 다음과 같이 실행할 수 있습니다.

```
us-vs-them --ours dan@eighttrigrams.net README.md
```

실행 결과는 이런 식으로 출력됩니다.

```
1-3 0.00
4 1.00
5-7 0.00
8-20 0.46
21-164 0.00
```

여기서 숫자는 각 줄 범위가 얼마나 사람에 의해 작성되었는지를 나타내는 점수입니다.

- **1.0**: 완전히 사람이 작성한 범위
- **0.46**: 원래는 사람이 작성했지만 이후 에이전트가 어느 정도 수정을 가한 범위
- **0.00**: 완전히 에이전트가 작성한 범위

파라미터는 두 가지입니다.

- `--ours`: 여기 명시된 사람이 "우리"(human)이고, 나머지는 전부 에이전트로 간주됩니다.
- `--theirs`: 여기 명시된 저자가 "그들"(agent)이고, 나머지는 전부 사람으로 간주됩니다.

둘 중 목록이 더 짧은 쪽을 지정하면 됩니다. `--ours`와 `--theirs`를 동시에 넘기는 것은 허용되지 않습니다.

## 정리

`us-vs-them`은 에이전틱 코딩/에이전틱 에디팅 환경에서 "이 줄은 사람이 썼는가, 에이전트가 썼는가"를 Git의 버전 히스토리만으로 판별하는 diff 기반 도구입니다. 별도의 마크업 없이 플레인 텍스트(마크다운 등)를 그대로 지원한다는 점, 그리고 줄 단위가 아니라 "의미적으로 응집된 범위" 단위로 저자성을 추적한다는 점이 핵심 설계 철학입니다.

- 사람이 작성/수정한 코드는 보호받아야 할 영역, 에이전트가 생성한 코드는 자유롭게 갈아엎어도 되는 영역이라는 구분이 필요하다는 문제의식에서 출발했습니다.
- 결과는 줄 범위별로 0.00(완전 에이전트 작성)부터 1.00(완전 사람 작성) 사이의 점수로 표현되며, 중간값은 사람이 쓴 텍스트가 이후 에이전트에 의해 부분 수정되었음을 뜻합니다.
- `--ours`/`--theirs` 옵션으로 사람과 에이전트 저자 목록 중 더 짧은 쪽만 지정하면 되고, Git 저장소 안이라면 별도 설정 없이 바로 사용할 수 있습니다.
- 바이브코딩으로 만든 프로젝트에서 특정 코드 영역의 소유권을 지키거나, 자동 생성된 문서 중 직접 수정한 부분을 다음 에이전트 세션에서 보호하려는 실무 시나리오에 바로 적용할 수 있습니다.

AI 에이전트가 반복적으로 코드를 건드리는 워크플로우가 표준이 되어가는 지금, "내가 쓴 코드"와 "에이전트가 쓴 코드"를 구분하고 보호 정책을 적용하는 이런 provenance 도구는 프론트엔드 개발자를 포함한 모든 코드 작성자에게 실질적인 안전장치가 될 수 있습니다.
