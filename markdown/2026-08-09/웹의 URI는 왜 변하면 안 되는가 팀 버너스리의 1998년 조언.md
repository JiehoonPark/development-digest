## 핵심 개념

> [!abstract]
> 웹의 창시자 팀 버너스리가 1998년에 쓴 이 글은 URI(URL)가 깨지는 것이 기술적 필연이 아니라 조직의 관리 부실이라고 지적합니다. cgi-bin이나 파일 경로처럼 구현 메커니즘을 노출하는 URI, 주제 분류나 담당자 이름이 들어간 URI가 왜 위험한지 실제 NSF 사이트 사례를 들어 설명하고, URI 설계의 핵심 원칙으로 '정보를 최대한 빼는 것'을 제시합니다. URN이 URI 관리 문제의 만능 해결책이 아니라는 점과, 도메인 분리(cgi., secure. 등)도 같은 위험을 안고 있다는 점도 함께 다룹니다.

## 아티클

# 웹의 URI는 왜 변하면 안 되는가: 팀 버너스리의 1998년 조언이 여전히 유효한 이유

웹 아키텍처의 원년 멤버이자 HTTP의 창시자인 팀 버너스리가 1998년에 쓴 "Cool URIs Don't Change"는 지금까지도 웹 개발자들 사이에서 인용되는 글입니다. URI(URL)를 어떻게 설계해야 수십 년 후에도 깨지지 않는지, 그리고 사람들이 URI를 함부로 바꾸는 흔한 변명들이 왜 성립하지 않는지를 다룹니다. 원문은 20여 년 전에 쓰였지만, URL 구조를 설계하는 모든 웹/프론트엔드 개발자에게 여전히 실무적인 지침을 줍니다.

## URI가 깨질 이유는 이론적으로 없다

버너스리는 단호하게 말합니다. 도메인 소유자가 파산하지 않는 한, 그리고 그 도메인 아래의 URI 공간은 완전히 소유자의 통제 아래 있기 때문에, 이론적으로 URI가 바뀔 이유는 전혀 없습니다. 문서가 웹에서 사라져야 하는 거의 유일한 정당한 이유는 회사가 도산하거나 서버를 더 이상 운영할 여력이 없어졌을 때뿐입니다. 그런데도 현실에는 죽은 링크(dangling link)가 넘쳐납니다. 대부분은 단순한 무계획, 즉 사전에 충분히 생각하지 않은 결과입니다.

## 흔한 변명들, 그리고 그것들이 통하지 않는 이유

글은 사람들이 URI를 바꾸는 이유로 흔히 대는 변명들을 하나씩 반박합니다.

**"재설계 때문에 옛날 URI를 유지할 수 없다"** — 그건 URI를 처음부터 잘못 설계했기 때문입니다. 다음 재설계 이후에도 계속 작동할 수 있도록 URI를 지금부터 설계해야 합니다.

**"기밀 정보라서 삭제해야 했다"** — 이건 공감할 수 있는 사유입니다. W3C도 아카이브를 공개하기 전에 기밀 자료를 걸러내야 했던 시기가 있었습니다. 해결책은 사전 준비입니다. 모든 문서에 배포 허용 범위, 생성일, 이상적으로는 만료일까지 메타데이터로 남겨두는 것입니다.

**"서버 구조상 URI가 파일 시스템 경로와 묶여 있다"** — 이건 가장 궁색한 변명 중 하나입니다. Apache 같은 서버는 URI와 실제 파일 위치 사이의 관계를 유연하게 제어할 수 있는 기능을 충분히 제공합니다. URI 공간을 완벽하게 정돈된 추상 공간으로 먼저 설계하고, 그 다음에 실제 구현 방식에 매핑하고, 서버에 그 매핑 규칙을 알려주면 됩니다.

**"관리자가 바뀌었다"** — 그렇다면 애초에 왜 URI에 특정 담당자의 이름(예: John의 개인 디렉터리)이 들어가 있었을까요?

**"cgi-bin 같은 경로는 서버 구현 방식이 바뀌면 어쩔 수 없다"** — 이는 서버를 어떻게 돌리는지의 메커니즘을 URI에 그대로 노출시킨 것이 문제입니다. 메커니즘을 바꾸면(콘텐츠는 그대로인데도) URI가 통째로 바뀌어 버립니다. 실제 사례로 미국 국립과학재단(NSF)의 URI를 비교합니다.

```
http://www.nsf.gov/cgi-bin/pubsys/browser/odbrowse.pl
http://www.nsf.gov/cgi-bin/getpub?nsf9814
```

이런 URI들은 "cgi-bin", "oldbrowse", ".pl" 같은 요소가 현재 서버 구현 방식을 그대로 드러내고 있어 몇 년 안에 사라질 가능성이 큽니다. 반면 실제 문서로 연결되는 URI는 훨씬 견고합니다.

```
http://www.nsf.gov/pubs/1998/nsf9814/nsf9814.htm
```

"pubs/1998"이라는 헤더는 미래의 아카이브 서비스에게 "이건 1998년의 문서 분류 체계였다"는 좋은 힌트를 줍니다. 2098년에 문서 번호 체계가 달라져도 이 URI는 여전히 유효할 수 있고, 관리 주체가 이 URI 때문에 부끄러워할 일도 없습니다.

## URN이 만능 해결책이라는 오해

일부 사람들은 URN(Uniform Resource Name) 같은 영속적 네임스페이스 연구가 진행 중이니, HTTP URI 관리에는 느슨해도 된다고 생각합니다. 버너스리는 이 생각을 강하게 반박합니다.

대부분의 URN 스킴은 권한 있는 기관 ID 뒤에 날짜와 문자열, 혹은 그냥 문자열이 붙는 형태로, 사실 HTTP URI와 매우 비슷합니다. 즉, 조직이 영속적인 URN을 만들 능력이 있다고 믿는다면, 지금 당장 그것을 HTTP URI에 적용해서 증명하면 됩니다. HTTP 자체에는 URI를 불안정하게 만드는 요소가 전혀 없습니다. 문제는 언제나 조직의 관리 체계입니다. 문서 URN을 현재 파일명에 매핑하는 데이터베이스를 만들고, 웹 서버가 그것을 이용해 실제 파일을 가져오게 하면 됩니다.

## 진짜 어려운 문제: 도구와 인프라의 부재

여기서 버너스리는 실무적으로 공감할 수 있는 진짜 어려움도 인정합니다. 영속적인 URI를 순식간에 조회해서 파일을 반환하는 웹 서버, URI를 체크섬처럼 파일 안에 저장해두고 데이터베이스와 실제 상태를 지속적으로 맞추는 시스템, 문서의 여러 버전과 번역본 간의 관계를 저장하는 기능, 파일 손상을 막기 위한 독립적인 체크섬 기록 등은 대부분의 웹 서버가 기본 제공하지 않습니다. 새 문서를 만들 때 에디터가 URI를 알려주는 게 아니라 오히려 URI를 물어봐야 하는 상황인 것입니다.

W3C는 이 문제를 해결하기 위해 Jigsaw 서버의 편집 기능인 Jigedit를 사용해 버전을 추적하고, 문서 생성 스크립트를 실험하고 있다고 밝힙니다. 도구, 서버, 클라이언트를 만드는 사람들에게 이 부분에 주목하라고 당부합니다.

버너스리는 심지어 이 글이 실려 있는 W3C 페이지들조차 이 원칙을 완벽히 지키지 못한다고 인정하며, "내가 말하는 대로 하되, 내가 하는 대로는 하지 말라"고 자조적으로 덧붙입니다.

## 링크가 깨지면 신뢰가 깨진다

URI를 바꾸면 누가 그 URI로 링크를 걸어놨는지 완전히 알 방법이 없습니다. 일반 웹페이지에서 링크했을 수도 있고, 북마크했을 수도 있고, 친구에게 쓴 편지 여백에 손으로 적어놨을 수도 있습니다. 누군가 링크를 따라갔다가 깨진 것을 발견하면, 그 사람은 서버 소유자에 대한 신뢰를 잃습니다. 목표를 달성하지 못했다는 감정적·실무적 좌절도 겪습니다. 죽은 링크에 대한 불만은 흔하고, 그 피해는 결국 문서를 사라지게 만든 관리자의 평판으로 돌아갑니다.

웹마스터의 의무는 2년, 20년, 200년 후에도 지켜낼 수 있는 URI를 할당하는 것입니다. 이는 충분한 사고와 조직력, 그리고 의지를 요구합니다.

## URI 설계 원칙: 정보를 최대한 빼라

URI는 그 안에 "변하는 정보"가 들어 있을 때 깨집니다. 그래서 어떻게 설계하느냐가 핵심입니다. 설계의 핵심은 대체로 정보를 URI에서 최대한 빼는 것입니다.

**생성일(발행일)은 남겨도 좋은 정보**입니다. 이는 절대 바뀌지 않으며, 새 시스템으로 만든 요청과 옛 시스템으로 만든 요청을 구분하는 데도 유용합니다. 그래서 URI는 날짜로 시작하는 것이 좋은 경우가 많습니다.

예외는 조직 전체 혹은 큰 부분을 대표하는 "최신" 페이지입니다.

```
http://www.pathfinder.com/money/moneydaily/latest/
```

이건 Money 매거진의 "오늘의 머니 데일리" 칼럼입니다. 이 URI에 날짜가 필요 없는 이유는, 이 URI의 영속성이 매거진 자체보다 오래갈 필요가 없기 때문입니다. Money가 폐간되면 "오늘의 머니"라는 개념 자체가 사라집니다. 특정 회차의 콘텐츠에 링크하려면 아카이브에 저장된 개별 URI를 써야 합니다.

```
http://www.pathfinder.com/money/moneydaily/1998/981212.moneyonline.html
```

이 URI는 pathfinder.com 안에서 "money"라는 이름이 앞으로도 계속 같은 의미로 쓰인다는 가정을 전제로 하며, "98"이 중복되고 ".html"이 불필요하게 들어가 있긴 하지만 전반적으로 견고한 URI입니다. W3C 자체의 더 나은 예시로는 다음과 같은 URI가 있습니다.

```
http://www.w3.org/1998/12/01/chairs
```

W3C 의장단 회의록을 나타내는 URI로, 날짜만으로 충분히 식별 가능합니다.

## 날짜 이후에는 아무것도 넣지 마라

생성일을 제외하면, URI에 이름을 넣는 순간 무언가는 문제를 일으킵니다. 특히 위험한 것이 **주제(topic) 분류**입니다. 문서를 업무 분류 체계에 따라 정리하다 보면 그 분류명이 URI에 자연스럽게 들어가게 되는데, 이 분류 체계는 반드시 바뀝니다. 영역의 이름도 바뀝니다. W3C는 실제로 "MarkUp"을 "Markup"으로, 다시 "HTML"로 바꾼 적이 있습니다. 또한 이런 분류는 보통 평평한(flat) 이름 공간이라서, 100년 후에 그 이름을 재사용하고 싶지 않을 것이라 확신할 수 없습니다. W3C도 "History"와 "Stylesheets" 같은 이름을 짧은 역사 속에서도 재사용하고 싶었던 적이 있습니다.

주제 기반 분류는 중기적으로는 매력적인 조직 방식이지만 장기적으로는 심각한 결함이 있습니다. 사람과 사람 사이의 주제 관계는 나무(tree)가 아니라 그물(web) 구조를 이루기 때문에, 같은 웹에 동의하는 사람들끼리도 서로 다른 트리 표현을 선택할 수 있습니다. URI에 주제명을 넣는다는 건 곧 특정 분류 체계에 스스로를 묶어버리는 것이고, 나중에 다른 분류를 선호하게 되면 그 URI는 깨질 위험을 안게 됩니다.

주제 영역을 URI에 넣게 되는 또 다른 이유는 조직 구조상 URI 공간의 하위 부분에 대한 책임이 위임되기 때문입니다. 이는 URI를 조직 구조에 묶는 것이며, 앞쪽(왼쪽)에 날짜가 있어 보호될 때만 대체로 안전합니다. 예를 들어 `1998/pics`는 "1998년 당시 우리가 pics라고 부른 것"을 의미할 수 있어, 나중에 조직 구조가 바뀌어도 별 문제가 없습니다.

## 도메인명과 서버 분리도 마찬가지 문제

이 원칙은 URI의 경로 부분뿐 아니라 **서버 이름(도메인)**에도 똑같이 적용됩니다. 여러 종류의 콘텐츠에 별도의 서버를 두면, 그 구분을 나중에 바꾸는 건 수많은 링크를 파괴하지 않고서는 불가능합니다. "cgi.pathfinder.com", "secure", "lists.w3.org" 같은 도메인명은 전형적으로 "지금 우리가 어떤 소프트웨어를 쓰고 있는지"를 그대로 노출한 사례입니다. 이런 도메인 분리는 서버 관리를 편하게 하려고 만들어진 것일 뿐입니다. 회사 내 부서, 문서 상태, 접근 권한, 보안 등급 등 무엇을 나타내든, 여러 도메인명을 서로 다른 문서 유형에 매핑하기 전에 매우 신중해야 합니다. 리다이렉션과 프록시를 이용하면 여러 웹 서버를 하나의 겉보기 서버 안에 숨길 수 있다는 점을 기억해야 합니다.

도메인명 자체도 마찬가지입니다. 회사 이름이 "soap"가 아닌데 제품군을 완전히 바꿔버린 후에도 여전히 "soap.com"으로 불리고 싶은지 미리 생각해봐야 합니다.

## 실무적 구현: 파일 확장자 문제

파일 기반 웹 서버에서 URI 안에 파일 확장자(.html, .png 등)를 넣지 않는 방법도 소개합니다. Apache의 콘텐츠 협상(content negotiation) 기능을 이용하면, 파일 자체는 확장자(예: mydog.png)를 유지한 채로, 웹 리소스는 확장자 없이 참조할 수 있습니다. Apache가 해당 디렉터리에서 그 이름을 가진 모든 확장자 파일을 확인하고, GIF와 PNG처럼 여러 형식 중 최적의 파일을 선택해서 제공할 수도 있습니다. 이때 서로 다른 타입의 파일들을 굳이 다른 디렉터리에 나눠 담을 필요도 없습니다.

## 정리

- **URI가 깨지는 것은 기술적 필연이 아니라 조직의 관리 부실입니다.** 도메인 소유자가 존속하는 한, URI 공간은 완전히 통제 가능하며, 재설계·서버 교체·담당자 변경 같은 이유는 URI를 바꿔야 할 정당한 사유가 되지 못합니다.
- **URI 설계의 핵심 원칙은 "정보를 빼는 것"입니다.** 생성일 정도는 남겨도 안전하지만, 주제 분류명·담당자 이름·구현 메커니즘(cgi-bin, .pl 등)처럼 시간이 지나면 바뀔 수밖에 없는 정보는 URI에서 배제해야 합니다.
- **URN이 URI 관리의 대안이 될 수 없습니다.** URN도 결국 조직의 관리 체계에 의존하며, 영속적인 URN을 만들 능력이 있다면 지금 그 능력을 HTTP URI 설계에 바로 적용하면 됩니다.
- **도메인 분리도 URI 경로와 똑같은 위험을 안고 있습니다.** 현재 사용 중인 인프라나 조직 구조를 그대로 드러내는 서브도메인(cgi., secure. 등)은 나중에 구조가 바뀌면 대규모 링크 붕괴를 일으킵니다.
- **링크가 깨지면 사용자는 목표를 달성하지 못하고, 그 책임은 결국 관리자의 신뢰도로 돌아갑니다.** 웹마스터의 의무는 2년, 20년, 200년 후에도 유효한 URI를 설계하는 것이며, 이는 도구와 인프라(URI-파일 매핑 데이터베이스, 버전 관리 등)의 사전 준비가 뒷받침되어야 가능합니다.
