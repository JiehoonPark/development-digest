## 핵심 개념

> [!abstract]
> 저자는 AliExpress 홈페이지를 열면 블루투스 멀티포인트 헤드폰이 폰 오디오로 전환되지 않는 문제를 발견하고, AudioContext 생성자를 후킹해 원인을 추적했다. 그 결과 collina.js와 fireyejs.js라는 난독화된 Alibaba 스크립트가 게인 0인 오실레이터-분석기 오디오 그래프를 destination에 연결해 소리 없이 실시간 오디오 처리를 유지하고 있었으며, 이는 캔버스·WebGL·하드웨어·인터랙션 데이터까지 수집하는 광범위한 브라우저 핑거프린팅의 일부였다. 저자는 uBlock Origin 필터 두 줄로 해당 스크립트를 차단해 문제를 해결했다.

## 아티클

블루투스 헤드폰의 멀티포인트 기능은 PC와 스마트폰에 동시에 연결해두고, PC에서 소리가 나오지 않을 때 자동으로 폰 오디오를 재생해주는 편리한 기능입니다. 그런데 이 글의 저자는 AliExpress 홈페이지를 Firefox나 Chrome에서 열었을 때만 이 기능이 먹통이 되는 이상한 현상을 발견했습니다. 탭을 뮤트해도, Windows 볼륨을 뮤트해도 소용없고 화면에는 재생 중인 영상이나 오디오 요소도 전혀 보이지 않는 상황에서, 저자는 원인을 추적해 AliExpress가 WebAudio API를 이용해 은밀한 브라우저 핑거프린팅을 수행하고 있다는 사실을 밝혀냈습니다.

## 현상: AliExpress 탭만 열면 폰 오디오가 끊긴다

평소 저자는 폰으로 음악을 들으면서 PC에서 알림음이나 유튜브 소리가 날 때만 그쪽으로 오디오가 넘어가는 방식으로 멀티포인트 헤드폰을 사용해왔습니다. 이 조합은 안정적으로 작동했지만, Firefox나 Chrome에서 AliExpress 홈페이지를 열면 얼마 지나지 않아 폰에서 재생 중이던 음악이 멈춰버렸습니다. AliExpress 탭을 닫으면 즉시 정상으로 돌아왔고요.

주목할 점은 탭 뮤트, 브라우저 전체 뮤트, Windows 시스템 뮤트 어느 것도 효과가 없었다는 겁니다. 페이지 안에 눈에 보이는 영상이나 음악도 전혀 없었습니다.

## 숨겨진 미디어를 찾아서

가장 먼저 의심한 건 자동재생 상품 영상이나 광고였습니다. 저자는 다음 항목들을 하나씩 확인했습니다.

- `<audio>`, `<video>` 요소
- `HTMLMediaElement.play()` 호출
- Media Session API의 활성 메타데이터
- 미디어 관련 네트워크 요청
- 미디어를 포함한 임베디드 iframe

하지만 어떤 것도 걸리지 않았습니다. `<audio>`나 `<video>` 요소는 존재하지 않았고, 미디어 재생 호출도 없었으며 `navigator.mediaSession.playbackState`는 계속 `none`을 유지했습니다.

단서는 하나 있었습니다. 문제가 즉시 발생하지 않고 페이지가 몇 초간 idle 상태로 있다가 나타난다는 점이었습니다. 저자는 페이지를 로드하기 전에 계측 코드를 심어두고, 일반적인 미디어 요소 대신 Web Audio API 자체를 감시하기로 했습니다.

핵심 아이디어는 `AudioContext` 생성자를 래핑해서 페이지가 오디오 처리 컨텍스트를 만들 때마다 기록하는 것이었습니다.

```javascript
const OriginalAudioContext = window.AudioContext;
window.AudioContext = class extends OriginalAudioContext {
    constructor(...args) {
        super(...args);
        console.log("AudioContext created", {
            state: this.state,
            stack: new Error().stack
        });
    }
};
```

여기에 더해 `AudioNode.prototype.connect()`도 래핑해서 무언가가 컨텍스트의 오디오 출력(destination)에 연결되는지도 확인했습니다.

그리고 마침내 원인을 찾았습니다. 숨겨진 `AudioContext`가 무려 두 개나 있었던 겁니다.

## 두 개의 숨겨진 AudioContext

AliExpress 홈페이지를 idle 상태로 캡처하는 동안, 페이지는 두 개의 `AudioContext` 객체를 생성했습니다. 둘 다 `running` 상태로 진입했고, 둘 다 노드를 `AudioContext.destination`에 연결했습니다.

동시에 다음 조건은 여전히 유지되고 있었습니다.

- `<audio>` / `<video>` 요소 0개
- 미디어 `play()` 호출 0회
- 활성 Media Session 없음
- 실제로 들리는 소리 없음

생성자 호출 스택은 다음 두 스크립트를 가리켰습니다.

- `https://assets.aliexpress-media.com/g/AWSC/uab/1.140.0/collina.js`
- `https://assets.aliexpress-media.com/g/AWSC/fireyejs/1.231.67/fireyejs.js`

첫 번째 컨텍스트는 `collina.js`가, 두 번째는 `fireyejs.js`가 생성했습니다. 두 스크립트 모두 `AWSC` 디렉토리 아래 위치하며, Alibaba의 브라우저 보안 및 어뷰징 방지 도구의 일부로 보입니다. 스크립트는 극도로 난독화되어 있지만, 남아 있는 이름과 연산 패턴만으로도 AI를 활용해 오디오 코드가 무엇을 하는지 추론할 수 있었다고 합니다.

## 오디오 그래프의 정체

두 스크립트가 만드는 WebAudio 그래프는 대략 이런 구조입니다.

```
Sawtooth oscillator
    -> AnalyserNode
    -> ScriptProcessorNode
    -> GainNode (게인 0)
    -> AudioContext.destination
```

톱니파(sawtooth) 오실레이터가 알려진 파형을 생성하면, 분석 노드(AnalyserNode)가 이 신호가 브라우저의 오디오 구현부를 거친 뒤의 결과를 측정하고, 스크립트는 여기서 주파수 데이터를 읽어들입니다.

게인 노드는 값이 0으로 설정되어 있어 사용자에게는 아무 소리도 들리지 않습니다. 하지만 그래프는 여전히 시스템 오디오 출력(destination)에 연결되어 있습니다. destination에 연결되어 있다는 사실 자체가 브라우저로 하여금 최종 볼륨이 0이더라도 이 그래프를 실제로 능동 처리(process)하게 만듭니다.

이는 자동재생 영상과는 완전히 다른 메커니즘입니다. 브라우저의 일반적인 탭 뮤트 기능이 멈춰 세울 미디어 요소 자체가 존재하지 않기 때문입니다. 페이지 입장에서는 실시간 오디오 처리를 계속 수행하고 있는 셈이죠.

저자의 환경에서는 이것만으로도 Firefox나 Windows가 블루투스 오디오 경로를 계속 활성 상태로 유지하기에 충분했고, 그 결과 멀티포인트 헤드폰이 폰 쪽으로 깔끔하게 전환되지 못했던 겁니다.

## 이건 사실상 핑거프린팅이다

WebAudio 테스트는 이 스크립트들이 수행하는 유일한 측정이 아니었습니다. 번들 코드를 조사한 결과, 다음 항목들을 조회하거나 측정하는 코드가 발견되었습니다.

- 캔버스 렌더링과 `toDataURL()`
- WebGL 렌더러 정보, 확장 기능, 셰이더 정밀도
- 오디오 오실레이터 및 분석 출력값
- 화면·뷰포트 크기
- 디바이스 픽셀 비율
- 하드웨어 코어 수(hardware concurrency)와 디바이스 메모리
- 설치된 브라우저 플러그인
- 지원되는 오디오/비디오 포맷
- WebRTC 동작
- 브라우저 성능 타이밍
- 마우스, 터치, 포커스, 스크롤 이벤트
- 디바이스 모션 및 방향
- 브라우저 자동화(automation)와 관련된 속성들

이 결과를 직렬화하고 암호화한 뒤 Alibaba 텔레메트리 서버로 `fetch()`나 `sendBeacon()`을 통해 전송하는 코드도 함께 발견되었습니다. 사실상 상당히 포괄적인 브라우저·디바이스 핑거프린트라고 할 수 있습니다.

오디오 핑거프린팅이 작동하는 원리는, 브라우저 버전, OS, 오디오 라이브러리, 하드웨어의 미세한 차이가 동일한 생성 신호에 대해 조금씩 다른 결과를 만들어낸다는 데 있습니다. 이것만으로 기기를 고유하게 식별하기는 어렵지만, 캔버스·WebGL·하드웨어·타이밍·인터랙션 데이터와 결합되면 훨씬 강력한 식별 수단이 됩니다.

저자는 이렇게 수집된 데이터가 서버 쪽에서 정확히 어떻게 쓰이는지는 확인할 수 없었다고 밝힙니다. 영구적인 디바이스 식별자로 쓰일 수도 있고, 사기·봇 탐지 점수를 매기는 여러 입력값 중 하나일 수도 있습니다.

## AliExpress가 이런 걸 하는 이유

AliExpress 입장에서는 정상 구매자와 자동화된 의심스러운 클라이언트를 구분하고 사용자의 쇼핑 행태를 추적할 이유가 충분합니다. 계정 탈취, 가짜 계정, 스크래핑, 자동 구매, 결제 사기, 리뷰 조작, 쿠폰이나 신규 고객 프로모션 악용 같은 문제를 다뤄야 하고, 대부분의 대형 사업자와 마찬가지로 방대한 사용자 행동 데이터를 마케팅에 활용하고 싶어하기도 합니다.

쿠키는 이런 목적에 그다지 신뢰할 만한 수단이 아닙니다. 삭제되거나 복제되거나 교체될 수 있기 때문이죠. 반면 여러 독립적인 브라우저 측정값을 조합한 핑거프린트는 일관되게 조작하기가 훨씬 어렵습니다.

인터랙션 데이터는 해당 브라우저가 사람이 조작하는 것인지 자동화 프로그램인지 판별하는 데도 도움이 됩니다. AliExpress 입장에서는 이를 통해 사기를 줄이고, 신뢰할 수 있는 고객에게는 페이지마다 CAPTCHA를 띄우지 않고 통과시킬 수 있다는 이점이 있습니다. 물론 AliExpress가 AI로 생성한 CAPTCHA를 안 쓰는 것도 아니지만요.

저자는 개인적으로 쇼핑 홈페이지가 자신의 그래픽, 오디오, WebRTC, 하드웨어, 모션 API 등을 은밀하게 조작해가며 행동을 추적하는 것을 원치 않는다고 말합니다. 특히 그것이 음악 재생을 방해하는 성가신 부작용까지 낳는다면 더욱 그렇고요. 사실 AliExpress가 음악을 막지만 않았어도 이 문제를 조사할 일도 없었을 거라고 덧붙입니다.

## uBlock Origin으로 차단하기

저자는 앞서 발견한 두 스크립트 계열을 차단해봤습니다. 두 요청을 모두 차단한 상태에서 AliExpress 홈페이지는 정상적으로 렌더링되었고, 통제된 재캡처 과정에서 `AudioContext` 객체도, destination 연결도 전혀 나타나지 않았습니다.

Firefox에서는 Raymond Hill이 만든 공식 uBlock Origin 확장을 사용했습니다. 스크립트를 차단하려면 uBlock 대시보드를 열고 "My filters"를 선택한 뒤 다음 규칙을 추가하면 됩니다.

```
! AliExpress AWSC fingerprinting scripts
||assets.aliexpress-media.com/g/AWSC/uab/*/collina.js$script,domain=aliexpress.com
||assets.aliexpress-media.com/g/AWSC/fireyejs/*/fireyejs.js$script,domain=aliexpress.com
```

"Apply changes"를 클릭하고 기존에 열려 있던 AliExpress 탭을 모두 닫은 뒤 다시 접속하면 됩니다. 스크립트를 차단한다고 해서 이미 생성된 AudioContext가 자동으로 종료되지는 않기 때문에, 기존 탭을 반드시 닫아줘야 합니다.

이 규칙들은 의도적으로 매우 좁은 범위로 작성되어 있습니다. 관찰된 두 스크립트 계열만, 그것도 AliExpress 도메인에서 요청될 때만 차단합니다. 저자는 이 규칙이 언젠가 작동하지 않게 될 수도 있다고 말하며, 그때 가서 다시 대응하겠다는 입장입니다.

이 스크립트들이 사기 방지 시스템과 연관되어 있는 것으로 보이는 만큼, 차단할 경우 로그인이나 결제 과정에서 추가 CAPTCHA나 문제가 발생할 수 있습니다. 지금까지는 홈페이지와 일반적인 상품 탐색은 문제없이 작동했지만, 만약 AliExpress가 정당한 로그인이나 결제를 거부한다면 저자는 이 규칙을 임시로 비활성화할 계획이라고 밝혔습니다.

## 저자가 이를 차단하기로 한 이유

사기 방지라는 목적 자체는 이해할 만하지만, 이 구현 방식에는 실질적인 문제가 있다고 저자는 지적합니다.

이 스크립트는 민감한 행동(로그인, 결제 등)을 하기도 전인 일반 쇼핑 홈페이지 단계에서부터 광범위한 기기·행동 데이터를 수집합니다. 구현 자체가 의도적으로 분석하기 어렵게 만들어져 있고, 페이지가 실시간 오디오 처리 그래프를 가동했다는 사실을 사용자에게 알려주는 시각적 표시도 전혀 없습니다.

무엇보다 이 스크립트는 실제 하드웨어에 부작용을 일으켰습니다. 눈에 보이지 않는 핑거프린팅 테스트가 블루투스 멀티포인트 전환을 방해할 수 있었고, 브라우저의 뮤트 기능은 아무 역할도 하지 못했습니다.

숨겨진 분석/보안 기능이 오디오 경로를 강하게 점유해서 외부 하드웨어의 동작 방식까지 바꿔놓을 수 있다면, 이를 차단하는 것은 합리적인 트레이드오프로 보인다고 저자는 결론짓습니다. 또한 AliExpress가 이렇게 수집한 핑거프린트를 얼마나 오래 보관하는지, 다른 Alibaba 계열 서비스에서도 함께 사용하는지도 클라이언트 코드만으로는 확인할 방법이 없다는 점을 지적합니다. 광범위한 핑거프린트성 측정값이 수집되고 전송된다는 사실은 클라이언트 코드로 증명되지만, 서버 측 보관 기간과 신원 연결 여부는 브라우저에서 확인할 수 없는 영역이기 때문입니다.

## 정리

- AliExpress 홈페이지는 `collina.js`, `fireyejs.js`라는 심하게 난독화된 스크립트를 통해 두 개의 숨겨진 `AudioContext`를 생성하고, 톱니파 오실레이터→AnalyserNode→ScriptProcessorNode→게인 0인 GainNode→destination으로 이어지는 오디오 그래프를 구동한다.
- 이 그래프는 게인이 0이라 소리는 나지 않지만 destination에 연결되어 있기 때문에 브라우저가 실제로 오디오 처리를 계속 수행하며, 이로 인해 저자의 환경에서는 블루투스 멀티포인트 헤드폰이 PC 쪽 오디오 경로를 점유한 채 놓아주지 않는 부작용이 발생했다. 탭이나 시스템 뮤트로는 해결되지 않는데, 정지시킬 미디어 요소 자체가 존재하지 않기 때문이다.
- 같은 스크립트 번들에는 캔버스, WebGL, 하드웨어 정보, 인터랙션 이벤트, 자동화 탐지 속성 등을 수집하는 코드가 함께 들어 있어, 오디오 테스트는 훨씬 큰 규모의 브라우저 핑거프린팅 시스템의 일부로 보인다.
- uBlock Origin에 도메인 한정 필터 두 줄을 추가하면 해당 스크립트의 로드 자체를 막아 문제를 해결할 수 있지만, 이 스크립트들이 부정 거래 방지 로직과 연결되어 있을 가능성이 높은 만큼 로그인·결제 시 예기치 못한 CAPTCHA가 나타날 수 있다는 점은 감안해야 한다.
- 프론트엔드 개발자 입장에서 이 사례는 `AudioContext`, `<audio>`/`<video>` 요소, Media Session API처럼 서로 다른 오디오 관련 API가 브라우저와 OS의 오디오 경로 제어에 각각 다르게 관여할 수 있음을, 그리고 겉으로 드러나지 않는 API 사용이 실제 하드웨어 동작에까지 영향을 줄 수 있음을 보여주는 흥미로운 디버깅 사례이기도 하다.
