## 핵심 개념

> [!abstract]
> 한 개발자가 상용 SaaS 제품 marketyour.games를 C 언어와 CGI, SQLite만으로 구축한 경험을 공유합니다. OpenBSD의 BCHS 스택(OpenBSD, C, httpd, SQLite)을 사용해 프레임워크, 템플릿 엔진, 컨테이너, 별도 DB 서버 없이 결제·이메일·인증 기능을 갖춘 제품을 만들었고, 빌드 의존성은 libcurl과 libsodium 단 두 개뿐입니다. 2004년에 표준화된 뒤 변하지 않은 CGI 명세와 현대 커널의 프로세스 포킹 최적화 덕분에, CGI를 버린 2000년대 초반의 이유들이 더 이상 유효하지 않다고 주장합니다.

## 아티클

1994년, 동적인 웹사이트를 만들고 싶다면 C 프로그램을 작성해 `cgi-bin` 디렉터리에 넣고 Apache가 요청마다 프로세스를 포크하도록 두는 게 일반적이었습니다. 그로부터 32년이 지난 지금, 한 개발자가 본질적으로 동일한 기술로 상용 웹 제품을 출시했습니다. 이 글은 C와 CGI로 실제 프로덕트를 만들어본 경험과, 2004년에 "죽었다"고 평가받던 CGI가 2026년에도 여전히 유효한 선택지인 이유를 다룹니다.

## marketyour.games: 겉보기엔 평범한 모던 웹 제품

marketyour.games는 사용자 계정, 콘텐츠 크리에이터를 위한 검색 대시보드, 콘텐츠를 정리하는 폴더 기능, Stripe 결제, Postmark를 통한 트랜잭션 이메일까지 갖춘 제품입니다. 프로그레시브 인핸스먼트 원칙을 따르며 자바스크립트 없이도 동작합니다. 기능 목록만 보면 더없이 모던한 SaaS지만, 이를 "만든 방식"과 "서빙하는 방식"만큼은 2026년 기준으로 전혀 모던하지 않습니다. 바로 C로 작성하고 CGI로 서빙했기 때문입니다.

저자의 주장은 명확합니다. CGI가 쇠퇴한 것은 2004년 기준으로는 타당했지만, 2026년 기준으로는 그 근거가 더 이상 성립하지 않는다는 것입니다.

## BCHS 스택: 프레임워크 없는 웹 애플리케이션

이 프로젝트가 채택한 스택은 **BCHS**(OpenBSD, C, httpd, SQLite)입니다. 하나의 바이너리, SQLite 파일 하나, 세 개의 의존성만으로 전체 애플리케이션이 돌아가며, 그 구조는 머릿속에 통째로 담길 만큼 단순합니다.

- 프레임워크가 없습니다. CGI 환경 변수를 읽고 응답을 작성하는 C 프로그램을 직접 짭니다.
- 템플릿 언어가 없습니다. HTML을 C 코드에서 직접 출력합니다.
- 별도의 데이터베이스 서버가 없습니다. SQLite의 C API로 데이터베이스 파일을 바로 엽니다.
- 컨테이너가 없습니다. 정적으로 링크된 바이너리를 빌드해 폴더에 넣으면 끝입니다.

요청이 들어올 때마다 새 프로세스가 스폰됩니다. 배포는 파일 하나를 교체하는 것으로 끝나며, 서버 재시작도 다운타임도 없습니다. 새 요청은 자연스럽게 새 바이너리를 집어 듭니다.

OpenBSD는 기본값 자체가 안전하게 설계되어 있고, `pledge`와 `unveil` 같은 도구로 C 프로그램을 실질적으로 샌드박싱할 수 있게 해줍니다. httpd는 기본적으로 chroot 환경에서 서비스를 돌리기 때문에, CGI 바이너리는 파일시스템의 아주 좁은 영역에만 접근할 수 있도록 격리됩니다.

추가로 의존하는 라이브러리는 세 개이며, 이 중 실제 빌드 의존성은 libcurl과 libsodium 두 개뿐입니다. 둘 다 프로젝트 안에 벤더링되어 빌드 과정에 포함됩니다. 그 결과 움직이는 부품이 거의 없는 빌드 시스템이 만들어졌습니다. 클린 빌드는 몇 초면 끝나고, 재빌드는 0.5초 이내로 완료됩니다.

정적 자산 역시 전통적인 방식 대신, httpd의 모든 트래픽을 CGI 바이너리로 라우팅하는 방식을 택했습니다. 모든 에셋이 실행 파일 안에 컴파일되어 메모리에서 바로 서빙됩니다.

## CGI는 배울 게 거의 없는 인터페이스다

CGI는 익혀야 할 프레임워크가 아닙니다. CGI 1.1 명세는 2004년에 발표된 뒤로 단 한 번도 바뀌지 않았습니다. 내재화해야 할 API도 없습니다. 인터페이스 전체가 몇 가지 기본적인 HTTP 개념으로 구성되어 있을 뿐입니다. HTTP를 이해하고 있다면 이미 CGI를 이해하고 있는 셈입니다. 언어와 플랫폼에 종속되지 않기 때문에, 한 번 배운 지식은 영구적으로 유효합니다.

일반적인 모던 웹 애플리케이션은 nginx 같은 웹 서버를 앞단에 두고, Ruby·Python·Go·Rust 같은 다른 언어로 작성된 애플리케이션 서버로 리버스 프록시를 거칩니다. 저자는 이 구조가 늘 어딘가 이상하다고 느꼈다고 말합니다. 사실상 웹 서버가 두 대 존재하는데, 그중 하나는 비즈니스 로직까지 떠맡고 있다는 것입니다.

반면 CGI는 비즈니스 로직을 직접 호출하는 단일 웹 서버만 존재합니다. 누가 무엇을 담당하는지가 명확합니다. 디버깅도 단순해집니다. 애플리케이션은 셸에서 직접 실행할 수 있는 평범한 프로그램이기 때문에, 요청을 파이프로 흘려보내고 stderr를 지켜보고 gdb로 한 줄씩 스텝 실행할 수 있습니다.

어떤 면에서 CGI는 서버리스 아키텍처와 닮아 있습니다. 슈퍼바이저가 요청마다 코드를 호출하고 환경 변수 묶음을 넘겨준 뒤 결과를 수거하는 구조죠. 다만 벤더도 없고, 그에 따른 예상치 못한 청구서도 없는 서버리스입니다.

## 자율 에이전트 시대의 최소 공급망

최근 자율 에이전트의 부상과 매주 발생하는 패키지 저장소 공격 소식을 보면, 의존성이 적다는 것이 상당히 안심되는 요소로 다가온다고 저자는 말합니다. 대부분의 모던 기술 스택은 패키지 매니저와 그에 딸린 생태계를 제공합니다. 편리하긴 하지만 의존성 그래프가 순식간에 불어납니다. 직접 의존성 한두 개가 수백 개의 간접 의존성을 끌어들이고, 그 각각은 한 번도 들어본 적 없는 누군가가 관리하며, 게시 권한은 2015년부터 재사용해온 비밀번호로 보호되고 있을지도 모릅니다.

이 프로젝트의 공급망은 C 컴파일러 하나와 라이브러리 세 개가 전부입니다. 이를 손상시키려면 libcurl을 뚫어야 하는데, 이는 전 세계 인터넷이 지켜보는 프로젝트이지, 주간 다운로드 11회에 2019년에 떠난 관리자가 소유한 패키지가 아닙니다.

## 미니멀한 툴링: Vim 하나면 충분하다

저자는 자칭 미니멀리스트로, 플러그인 없는 순정 Vim을 사용합니다. LSP도, 자동완성도, 코드 포매터도, AI도 쓰지 않습니다. 복잡한 기술 스택은 복잡한 툴링을 요구합니다. 추상화 계층을 헤쳐나가려면 언어 서버가 필요해지기 때문입니다. 하지만 이 스택은 평범한 에디터만으로 충분할 만큼 단순합니다. 애플리케이션 전체가 C 파일들과 Makefile 하나로 이루어진 디렉터리에 불과합니다. 파일을 열고 읽으면, 그게 무슨 일을 하는지 바로 알 수 있습니다.

그러면서도 더 깊은 도구가 필요할 때는 멀리 갈 필요가 없습니다. 새니타이저, valgrind, gdb, ctags, cscope 같은 (다소 연로하지만) 수십 년간 다듬어진 성숙한 도구들이 C 컴파일이 가능한 어떤 시스템에서든 패키지 설치 한 번으로 준비됩니다. 이런 성숙함은 도구 자체를 넘어 에디터 통합에도 이어집니다. Vim은 ctags, cscope를 기본 지원하고, 그래픽 gdb 프런트엔드(`:h Termdebug`)까지 내장하고 있습니다.

프런트엔드 전체를 C로 작성하는 것에 처음엔 망설임이 있었지만, 생각만큼 고통스럽지 않았다고 합니다. C만 사용한다는 것은 에디터가 어설프게 감지해야 할 두 번째 언어가 없다는 뜻이고, 하이라이팅이 깨지는 혼합 문법도, 두 언어를 협업시키기 위한 플러그인 묘기도 필요 없다는 뜻입니다. 그저 C만 쓰는 것은 오히려 신선한 경험이었으며, "예쁘지는 않지만 Tailwind도 예쁘지는 않다"는 것이 저자의 코멘트입니다.

## SQLite, 운영 부담 없는 데이터베이스

저자는 늘 웹 애플리케이션에 Postgres를 기본으로 사용해왔습니다. 훌륭한 데이터베이스지만 운영 부담이 따릅니다. 돌봐야 할 서버 프로세스가 있고, 자주 나오는 릴리스를 계속 업그레이드해야 합니다.

SQLite에는 그런 부담이 없습니다. 프로세스도, 설정도, 의존성도 없습니다. 애플리케이션이 데이터베이스 파일을 직접 엽니다. 운영 부담이 최소한으로 줄어듭니다.

## CGI의 빈틈: 직접 채워야 하는 유틸리티

CGI는 웹 서버와 애플리케이션 사이의 인터페이스일 뿐, 프레임워크나 라이브러리가 아닙니다. 그래서 기본으로 제공되는 것이 거의 없습니다. 다음과 같은 기능들을 위한 유틸리티를 직접 작성해야 합니다 (원문에서는 구체적인 목록을 길게 나열하지 않았지만, 요청 파싱, 세션 관리 등 CGI가 처리해주지 않는 기본 작업들을 의미합니다).

저자는 `cgi.h`라는 단일 헤더 파일로 이를 직접 구현했지만, 이것이 정답인지는 확신하지 못한다고 말합니다. kcgi 같은 라이브러리도 존재하지만, 이를 채택하는 순간 그 라이브러리의 API와 보안 모델을 고스란히 받아들여야 합니다. 저자는 stb 라이브러리들처럼 개발자들이 가져다 쓸 수 있는 공유 유틸리티 모음이 나왔으면 좋겠다고 제안하며, 어쩌면 자신이 작성한 `cgi.h`를 그 시작점으로 공개할 수도 있다고 덧붙입니다.

## CGI는 오래됐지만 잊힌 건 아니다

2000년대 초반 CGI를 버린 이유들 대부분은 오늘날 더 이상 유효하지 않습니다. 프로세스 포킹은 과거만큼 비싸지 않으며, 현대 커널은 이를 상당히 최적화해두었습니다. 만약 포킹 비용이 실제로 문제가 된다면, FastCGI로의 업그레이드도 그리 어렵지 않은 선택지입니다.

C로 모던 웹 애플리케이션을 작성하는 것은 충분히 실현 가능합니다. marketyour.games는 단일 바이너리로 돌아가는 상용 제품이며, 2004년에 공식 표준화된 서빙 모델을 그대로 사용하고 있습니다. 저자는 이것이 지금까지 출시해본 그 어떤 프로젝트보다도 움직이는 부품이 적다며, 앞으로도 이 스택을 다시 선택할 것이라고 글을 맺습니다.

## 정리

이 글은 "오래된 기술 = 폐기된 기술"이라는 통념에 반기를 듭니다. CGI가 쇠퇴한 2000년대 초반의 이유(프로세스 포킹 비용 등)는 현대 하드웨어와 커널 환경에서 더는 설득력이 없고, 오히려 단순함과 적은 의존성이 자율 에이전트·공급망 공격 시대에 강점으로 재평가될 수 있다는 것이 핵심 메시지입니다.

- **BCHS 스택**(OpenBSD + C + httpd + SQLite)으로 프레임워크, 템플릿 엔진, 별도 DB 서버, 컨테이너 없이도 결제·이메일·인증을 갖춘 상용 웹 제품을 만들 수 있습니다.
- CGI는 2004년 이후 변하지 않은 안정적인 인터페이스이며, HTTP만 이해하면 추가로 배울 게 거의 없습니다.
- 단일 웹 서버가 비즈니스 로직을 직접 호출하는 구조는 리버스 프록시 + 애플리케이션 서버 구조보다 책임 경계가 명확하고 디버깅이 쉽습니다.
- 적은 의존성(libcurl, libsodium 등 단 두 개의 빌드 의존성)은 npm 생태계식 거대한 의존성 그래프 대비 공급망 공격 표면을 획기적으로 줄여줍니다.
- SQLite, Vim(플러그인 없는), gdb/valgrind 같은 성숙한 C 생태계 도구만으로 LSP나 복잡한 빌드 체인 없이도 생산적으로 개발할 수 있습니다.

프런트엔드 개발자 입장에서 이 글이 당장 스택 교체를 권하는 글은 아닙니다. 다만 프레임워크와 의존성이 끝없이 쌓여가는 현재의 개발 방식에 대해, "정말 이만큼의 복잡도가 필요한가"를 다시 묻게 만드는 사례로 읽을 가치가 있습니다.
