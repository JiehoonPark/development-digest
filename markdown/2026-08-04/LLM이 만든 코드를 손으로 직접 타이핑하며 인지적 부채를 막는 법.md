## 핵심 개념

> [!abstract]
> 한 개발자가 코딩 어시스턴트를 활용하되 코드에 대한 이해를 잃지 않기 위해 택한 방법을 소개합니다. LLM이 생성한 코드를 파일에 바로 반영하지 않고 채팅창에만 띄운 뒤, 이를 직접 손으로 타이핑해 코드베이스에 옮기는 것입니다. 속도는 완전 위임 대비 느리지만(약 2배 vs 10배), 코드에 대한 깊은 이해와 코드베이스의 공간 지도를 얻을 수 있다는 것이 핵심 주장입니다.

## 아티클

코딩 어시스턴트가 일상적인 개발 워크플로우에 깊숙이 들어온 지금, 많은 개발자들이 "AI가 짠 코드를 얼마나 이해하고 있는가"라는 질문 앞에서 찜찜함을 느낍니다. 이 글은 그 찜찜함에 대한 한 개발자의 개인적인 해법을 다룹니다. LLM의 속도는 취하되 이해는 포기하지 않기 위해, 그는 조금은 우스꽝스러워 보이는 방법을 택했습니다. AI가 생성한 코드를 채팅창에만 띄워두고, 그것을 자기 손으로 직접 타이핑해서 코드베이스에 옮기는 것입니다.

## 문제의식: AI에게 맡기면 편한데, 왜 찜찜한가

글쓴이는 지난 4월에 코딩 어시스턴트에 대해 회의적인 입장을 밝힌 적이 있지만, 여전히 개인 프로젝트에서 이를 사용하고 있다고 고백합니다. 다만 기능 전체를 LLM에게 통째로 맡기는 "원샷" 방식은 만족감보다는 불만족과 방향 상실감을 남긴다고 말합니다. 반면 지루한 반복 작업을 빨리감기 하듯 넘기는 용도로는 꽤 만족스럽다고 하죠.

문제는 코딩 어시스턴트를 프로젝트 안에서 자유롭게 풀어놓으면 엄청난 양의 "인지적 부채(cognitive debt)"가 쌓인다는 점입니다. Django 문서를 뒤져가며 웹사이트에 태깅 기능을 붙이는 작업이 지루하게 느껴질 수는 있지만, 그렇다고 해서 그 해결책이 어떻게 작동하는지조차 통째로 기계에게 위임하고 싶지는 않다는 겁니다. 문제가 지루하다는 것과, 그 해법을 이해하고 싶지 않다는 것은 전혀 다른 이야기라는 거죠.

## PR 리뷰라는 대안이 즐겁지 않은 이유

물론 LLM이 만든 코드를 한 줄 한 줄 리뷰하는 방법도 있습니다. 글쓴이는 이를 "저주받은 2026년"의 개발자들에게 기대되는 표준적인 방식이라고 표현합니다. 로봇이 PR을 올리고, 인간이 그걸 리뷰하는 용감한 신세계라는 거죠.

하지만 그는 이 방식이 즐겁지 않다고 단언합니다. 과도하게 방어적이고, 주석은 부실하며, 미묘하게 틀린 코드 수백 줄을 검토하는 일은 재미가 없다는 겁니다. 회사 업무라면 마지못해서라도 하겠지만—동시에 그 회사를 최대한 빨리 전 직장으로 만들 계획을 세우면서—개인 프로젝트에서는 절대 하고 싶지 않다고 말합니다. 개인 프로젝트는 무엇보다 재미있어야 하고, 그 재미는 결과물이 아니라 과정에서 나오기 때문입니다.

## 해법: 채팅창에서만 코드를 보고, 손으로 직접 타이핑하기

그래서 글쓴이가 찾은 답은 지루한 작업은 LLM에게 맡기되, 자기 작업물과 사고 과정에 대한 통제권은 넘기지 않는 방법입니다. 방식은 단순합니다. 코딩 어시스턴트에게 채팅창에서 코드를 생성하게 한 다음, 그 수정 사항을 자신이 직접 손으로 타이핑해서 반영하는 것입니다.

그는 자신의 모든 개인 프로젝트의 agents 파일에 다음과 같은 지침을 넣어둔다고 밝힙니다.

> I want to understand every line of code that goes into this project. Never create, edit, move, rename, or delete project files unless I explicitly ask you to do so. Instead, show me every proposed edit in the chat so I can type it in manually.
>
> Do not run commands that modify project files, install dependencies, or change repository state unless I explicitly request that action. Instead, show me those commands in the chat so I can run them manually.
>
> I'm an experienced developer. Do not explain syntax, APIs, programming concepts, or implementation details unless explicitly asked.

즉 파일을 직접 건드리지 말고 제안만 채팅으로 보여줄 것, 커맨드도 직접 실행하지 말고 보여줄 것, 그리고 숙련된 개발자이니 불필요한 설명은 생략할 것을 명시적으로 요구하는 것입니다.

## 속도는 조금 포기하고, 이해는 훨씬 깊어진다

이런 방식으로 작업하면 LLM을 전혀 안 쓰는 것보다는 빠르지만, 기계에게 생각을 완전히 맡기는 사람들보다는 느립니다. 글쓴이는 흔히 말하는 "10배 생산성"이 아니라 대략 "2배" 정도의 속도라고 추정합니다. 하지만 그 대가로 자기 코드에 대한 훨씬 깊은 이해를 얻는다고 말합니다.

LLM이 생성한 코드를 한 줄씩 직접 에디터에 타이핑하면서, 그는 그 코드가 어떻게 동작하고 기존 코드베이스와 어떻게 맞물리는지에 대한 멘탈 모델을 쌓아갑니다. API나 알고리즘이 이해가 안 되면 멈춰서 찾아보거나 LLM에게 설명을 요청하면 됩니다.

직접 타이핑한다는 행위 자체가 속도를 늦추기 때문에, LLM의 환각(hallucination)이나 잘못된 설계 판단을 알아챌 확률도 높아집니다. 타이핑하는 과정에서 코드를 정리하고, 재구성하고, 리팩토링하고, 주석을 달고, 자신의 취향에 맞게 다듬는 것도 자연스럽게 이루어집니다.

## 코드베이스의 공간 지도를 그린다는 것

무엇보다 중요한 효과는 코드베이스의 "공간 지도(spatial map)"를 그릴 수 있다는 점입니다. 어떤 기능이 코드베이스의 어디에 있는지 정확히 알게 되고, 뭔가를 수정해야 할 때 어디를 고쳐야 하는지 바로 알 수 있습니다. 이는 프로젝트 내에서 더 빠르게 작업하도록 도와줄 뿐 아니라, 나중에 LLM에게 더 정확한 프롬프트와 지시를 내리는 데도 도움이 됩니다.

글쓴이는 이 경험을 십 대 시절 코딩을 배우던 때와 비교합니다. 당시 숙련된 프로그래머들은 절대 코드를 복사-붙여넣기 하지 말라고 조언했습니다. 책으로 배울 때는 모든 예제를 직접 컴퓨터에 옮겨 적어 실행이 되는지 확인하라고 했고, 블로그 글이나 포럼 답변으로 배울 때는 코드를 직접 타이핑해 자신의 코드베이스에 맞게 고쳐보라고 했습니다. LLM이 생성한 코드를 손으로 옮겨 적는 지금의 워크플로우는, 그때의 학습 과정과 본질적으로 똑같다는 것이 글쓴이의 결론입니다.

## 정리

- LLM에게 기능 전체를 맡기는 원샷 방식은 만족감보다 불만족과 방향 상실감을 남기고, 자유롭게 풀어두면 막대한 인지적 부채가 쌓인다. AI가 만든 PR을 한 줄씩 리뷰하는 방식도 즐겁지 않기는 마찬가지다.
- 글쓴이의 해법은 agents 파일에 "파일을 직접 수정하지 말고 제안만 채팅에 보여줄 것, 커맨드도 직접 실행하지 말 것"을 명시해, LLM이 제안한 코드를 채팅에서만 확인하고 이를 자신이 직접 손으로 타이핑해 코드베이스에 반영하는 것이다.
- 이 방식은 완전 위임 대비 속도는 느리지만(10배가 아니라 대략 2배 수준), 코드에 대한 깊은 이해와 환각·설계 오류 탐지 능력, 그리고 코드베이스 전체의 공간 지도를 얻는다는 이점이 있다.
- 이는 과거 "예제 코드를 복사하지 말고 직접 타이핑하며 배우라"던 학습 조언과 본질적으로 같은 원리이며, 글쓴이는 생산성보다 이해를 우선시하는 이 워크플로우를 몇 달째 유지하고 있다.
- 글쓴이는 소프트웨어 업계 전체가 조만간 갚아야 할 거대한 인지적 부채를 지고 있다고 우려하며, 최소한 자신이 내놓는 소프트웨어만큼은 완전히 이해하고 있어야 한다는 것이 전문가로서의 책임이라고 강조한다.
