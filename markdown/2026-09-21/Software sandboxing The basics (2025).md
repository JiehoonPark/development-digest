## 아티클

소프트웨어 샌드박싱은 알고 보면 아직 지도가 제대로 그려지지 않은 영역입니다. 좋은 샌드박스를 구현하는 데 필요한 조각들은 여기저기 흩어져 있고, 이 분야를 먼저 탐험한 사람들도 아직 신참 개발자들을 안전하게 안내할 만한 통합된 지도를 완성하지 못했습니다. 이 글은 Emilua(Lua 기반 액터 모델 런타임)의 샌드박싱 기능을 만들면서 저자가 직접 겪은 경험을 정리한 것으로, 오해를 막기 위해 같은 내용을 여러 번 반복해서 설명하는 스타일을 택하고 있습니다. 참고로 일부 Lua 예제 코드는 아직 정식 릴리스되지 않은 Emilua 0.11(개발 브랜치의 최신 커밋)이 필요합니다.

## 샌드박싱이란 무엇인가

먼저 용어부터 정리하고 시작하겠습니다. 2009년 Hack In The Box Malaysia에서 Julien Tinnes와 Chris Evans가 제시한 정의를 출발점으로 삼습니다.

프로세스의 권한을 제한할 수 있는 능력으로서,
- 프로그래밍적으로(programmatically)
- 시스템 관리자 권한 없이(without administrative authority)
- 임의적(discretionary) 권한 축소

이 세 가지 조건을 하나씩 짚어보겠습니다. 다만 원 발표자들의 2009년 관점(특히 "슈퍼유저 API를 써도 되는가")과 지금의 저자의 견해는 조금 다르기 때문에, 2025년 기준으로 더 나은 실무 방향을 제시하는 쪽으로 설명을 풀어갑니다.

### 프로그래밍적 권한 축소

OS는 일반 사용자와 개발자에게 서로 다른 인터페이스를 제공합니다. 시스템 관리자는 전통적으로 파일시스템 권한을 이용해 서비스(UNIX 데몬)를 격리합니다. 만약 서드파티 프로그램이 이런 권한을 자유롭게 바꿀 수 있다면 관리자가 세워둔 정책은 무력화되고 말 것입니다.

게다가 서드파티 프로그램은 저마다 독자적인 가상 세계를 추상화하고 있어서, 대부분의 경우 UNIX 파일시스템 권한이 그 가상 세계에 필요한 보안 정책과 잘 맞지 않습니다. 예를 들어 트위터 피드를 누가 볼 수 있는지, Identi.ca에서 누가 메시지를 보낼 수 있는지를 UNIX 권한 모드로 정의하지는 않겠죠. 파일시스템 권한은 관리자가 가진 여러 접근 제어 수단 중 하나일 뿐이지만, 여기서 다루는 논리는 다른 수단에도 똑같이 적용됩니다.

그럼에도 프로세스는 결국 OS 위에서 돌아가고, 커널이 노출하는 자원(예: 파일)과 상호작용할 수밖에 없습니다. 개발자에게 중요한 건 바로 이 인터페이스입니다. Firefox 같은 웹 브라우저는 DRM 플러그인을 실행하는데, 이런 서드파티 플러그인이 Firefox가 접근할 수 있는 모든 파일(보통 사용자 HOME 디렉터리 전체)에 접근하지 못하게 막는 게 바람직합니다. `setuidgid` 같은 전통적인 도구는 여기서 도움이 되지 않으며, 관리자가 사용하는 인터페이스로서의 쓰임도 제한적입니다. `setuidgid`나 유사 도구는 애초에 개발자가 프로그래밍적으로 사용하도록 설계된 인터페이스가 아니기 때문입니다.

이런 프로그래밍적 권한 축소에는 전통적인 UNIX 인터페이스가 잘 맞지 않고, 이 문제가 실제로 중요한 OS들은 전통 UNIX를 넘어서는 확장 인터페이스를 제공합니다. FreeBSD의 Capsicum, Linux의 Seccomp가 그 예입니다.

### 루트 권한 없이 권한 축소하기

샌드박싱에 적합한 인터페이스가 없던 시절, 개발자들은 슈퍼유저만 사용할 수 있는 메커니즘을 편법으로 활용해서라도 샌드박스를 만들어냈습니다. 이 부류에서 가장 상징적인 기법이 chroot jail을 구성하는 suid 헬퍼 바이너리입니다.

이런 접근의 명백한 문제는 모든 프로그램이 이를 사용할 수 없다는 점입니다. 임의의 프로그램이 suid 바이너리를 설치할 수 있게 허용하면 모든 보안 장치가 무의미해집니다. suid 바이너리는 곧 시스템 전체에 대한 완전한 관리자 권한으로 일시적으로 상승하는 것과 같습니다. 권한은 오직 줄어들기만 해야 하며 절대 늘어나서는 안 됩니다(최소 권한 원칙).

여기서 함께 짚어야 할 또 다른 문제는, 커널 공격 표면을 지수적으로 늘리는 API 설계를 피해야 한다는 점입니다. Docker의 인기와 함께 Linux 네임스페이스가 서비스를 저렴하게 격리하는 메커니즘으로 널리 알려졌습니다. 하지만 중첩된 사용자 네임스페이스 안에서는 프로세스가 (그 네임스페이스 내에서) 슈퍼유저로 실행되고, 원래는 슈퍼유저만 접근할 수 있던 커널 코드 경로가 이제 모든 사용자에게 열립니다. 그런데 커널 코드는 10년 넘게 이런 전제 없이 작성되어 왔습니다. 이 설계 결정은 과거에도 보안 문제를 일으켰고, 앞으로도 반복될 가능성이 높습니다. Andy Lutomirski는 이렇게 지적합니다.

> CLONE_NEWUSER를 이용해 임의의 네트워크 네임스페이스에 대한 CAP_NET_ADMIN을 획득하고, 이를 통해 네트워크 설정 API에 접근할 수 있게 되는 것을 저는 엄청난 위험으로 봅니다. 예를 들어 비권한 사용자가 iptables를 프로그래밍할 수 있게 되는데, 여기서 권한 상승 취약점이 안 나온다면 제 손에 장을 지지겠습니다.
> — Andy Lutomirski

신뢰할 수 있는 컨테이너화 도구(예: Docker)로 이 인터페이스를 제한하는 한 사용자 네임스페이스를 허용하는 것은 괜찮습니다. 하지만 소프트웨어 샌드박싱 용도로는 Linux 네임스페이스가 형편없는 인터페이스입니다. Linux의 Landlock 같은 최신 샌드박싱 인터페이스는 사용자 네임스페이스에서 겪은 참사가 되풀이되지 않도록 커널 공격 표면을 지수적으로 늘리지 않게 신중하게 설계되었습니다. 게다가 Linux에서 네임스페이스를 제한하는 새로운 방법들이 지금도 계속 개발되고 있어서, 장기적으로 이를 범용 샌드박싱 메커니즘으로 삼는 건 좋은 선택이 아닙니다.

실제로 Emilua의 초기 몇 년간의 샌드박싱 연구는 전적으로 Linux 네임스페이스에 집중되어 있었습니다. 하지만 많은 좌절 끝에 방향을 다른 해법으로 옮기게 되었습니다. 지금도 Emilua는 Linux 네임스페이스를 지원하지만, 이제 그 용도는 컨테이너화 도구를 만드는 것으로 한정되어 있습니다. Emilua에서 제대로 된 샌드박싱을 하려면 Linux 네임스페이스가 아닌 다른 메커니즘을 써야 합니다.

### 임의적 권한 축소

실제로 샌드박스는 다음과 같이 정의되기도 합니다.

> 잠재적으로 악성일 수 있는 소프트웨어가 […] 권한을 부여받지 않은 시스템 자원에 접근하지 못하도록 막는, 제한되고 통제된 실행 환경.
> — Committee on National Security Systems (CNSS) Glossary 2022

어떤 코드를 "샌드박스화되었다"고 부르기 위해 필요한 특성이 무엇인지에 대한 합의는 사실상 존재하지 않으며, 정의들은 대체로 느슨합니다. 이런 정의들은 지금까지 논의한 속성들을 요구하지 않습니다. 그래서 아예 다른 용어를 쓰는 편이 유용할 수 있습니다. J. Tinnes는 "임의적 권한 축소(discretionary privilege dropping)"라는 표현을 제안했고, 이 글에서 다루는 것도 바로 이 유형의 샌드박싱입니다.

임의적 권한 축소는 시스템 관리 정책을 대체하지 않습니다. 오히려 서로 보완하는 관계이며 함께 도입되어야 합니다.

## 실전 샌드박싱: 프로세스

이제 용어 정리는 끝났습니다. 우리에게 샌드박스란 곧 임의적 권한 축소를 의미합니다. 그렇다면 샌드박스화되지 않은 프로그램을 실제 OS 위에서 어떻게 샌드박스화된 프로그램으로 바꿀 수 있을까요? 오늘날 주류 OS에서 권한 경계는 모두 프로세스 단위에 놓여 있습니다. 각 프로세스에는 자격 증명(credential)이 연결되어 있고, 커널은 프로세스가 앰비언트 권한(ambient authority)으로 새 자원을 획득할 수 있는지 판단할 때 바로 이 자격 증명을 확인합니다.

Linux는 특이하게도 자격 증명을 스레드 단위로 관리합니다. 하지만 스레드 단위 설계는 근본적으로 성립할 수 없습니다. 그래서 glibc는 커널이 이 부분을 허술하게 처리하더라도 스레드 간에 자격 증명을 동기화하는 추가 작업을 수행합니다. GNOME 개발자들은 스레드 레벨에서도 문제없이 동작할 거라 생각했지만 CVE-2023-43641로 그 생각이 틀렸음이 증명되었습니다.

Adam Langley는 이론적으로는 스레드 레벨에서도 동작 가능한 메커니즘을 설명한 적이 있지만, 실제로는 비용이 너무 커서 실용화되기 어렵다고 봅니다.

> 그래서 저희가 하는 방식은 이렇습니다: 신뢰할 수 없는 스레드마다 같은 프로세스 안에서 실행되는 신뢰된 헬퍼 스레드를 하나씩 둡니다. 이건 신뢰된 코드 입장에서는 상당히 적대적인 환경입니다. 왜냐하면 CPU 레지스터만 믿을 수 있고, 메모리는 전부 적대적이라고 가정해야 하기 때문입니다. C 코드는 필요할 때 스택에 값을 저장하고 인자를 스택으로 넘기기도 하므로, 신뢰된 스레드의 코드는 전부 어셈블리로 신중하게 작성해야 합니다.
>
> 신뢰된 스레드는 소켓 페어를 통해 신뢰할 수 없는 스레드로부터 시스템 콜 요청을 받아 그 번호를 검증한 뒤 대신 실행해줍니다. CPU 레지스터만 사용하도록 제한하고, mmap이나 mprotect 같은 방식으로 신뢰할 수 없는 코드가 VM을 안전하지 않게 조작하지 못하게 막으면 탈출을 막을 수 있습니다.
> — https://www.imperialviolet.org/2009/08/26/seccomp.html

다른 설계가 이론적으로 가능한지는 여기서 논하지 않겠습니다. 지금 우리가 가진 건 프로세스뿐입니다. 프로그램을 별도의 프로세스들로 나눠 격리(compartmentalise)하고 나면, 다음 단계로 넘어갈 수 있습니다.

- 각 구획(프로세스)에 서로 다른 권한을 부여하기
- 구획 간 통신 처리하기

FreeBSD Capsicum 연구자들은 이미 10년도 더 전에 샌드박스를 만드는 데 필요한 정확한 사고 모델을 갖고 있었습니다.

> 구획화된 애플리케이션 개발은 필연적으로 분산 애플리케이션 개발입니다. 소프트웨어 컴포넌트들이 서로 다른 프로세스에서 실행되며 메시지 전달을 통해 통신하기 때문입니다.
> — Capsicum: practical capabilities for UNIX, Robert N. M. Watson, Jonathan Anderson, Ben Laurie, Kris Kennaway

권한을 축소하는 구체적인 방법은 플랫폼마다 다르므로 일단 이 부분은 넘어가고 나중에 다시 다루겠습니다. 먼저 분산 애플리케이션 개발이라는 문제 자체에 집중해보겠습니다.

## 액터 모델과 능력 기반 보안

액터 모델은 분산 시스템 개발에서 가장 잘 알려진 패턴 중 하나입니다. Erlang이 대표적인 사용 사례이지만, Erlang이 액터 모델에 관심을 가진 이유는 고가용성과 장애 허용(fault tolerance) 때문입니다. 그래도 고가용성이나 장애 허용에 관심이 없더라도 널리 쓰이는 이 모델을 살펴볼 가치는 있습니다.

액터 모델을 설명하는 많은 자료가 곧바로 수학의 세계로 넘어가곤 하는데(그 자체는 괜찮습니다), 문제는 추상화의 세계에 빠져 컴퓨터 자체를 완전히 잊어버리는 경우가 많다는 점입니다(이건 문제입니다). 그러니 여기서는 우리가 관심 있는 핵심만 요약하겠습니다.

- 액터는 자신의 내부 상태를 관리할 수 있다.
- 액터는 다른 액터를 생성(spawn)할 수 있다.
- 액터는 다른 액터에게 메시지를 보낼 수 있다.
- 액터는 메시지 안에 다른 액터의 주소를 포함시킬 수 있다.

이 액터 모델을 프로그래밍 언어나 프레임워크의 구체적인 설계로 요약하면 다음과 같습니다.

- 액터를 생성하는 함수가 있고, 이 함수는 새 액터의 주소를 반환한다.
- 액터의 주소는 메시지를 보내는 데 사용할 수 있다.
- 액터의 주소는 그 자체로 메시지가 되거나, 더 큰 메시지의 일부가 될 수 있다.
- 메시지를 수신하는 함수가 있어서, 호출한 액터에게 큐잉된 메시지를 읽는다.
- 현재 액터의 주소를 조회할 수 있다.
- 액터끼리는 메모리를 공유하지 않는다.
- 액터는 자기 자신과 병렬로 실행되지 않는다. 어떤 액터가 스레드 A에서 실행 중이라면 동시에 스레드 B에서 실행될 수 없다. 다만 (work-stealing 방식의 스레드 작업 스케줄러처럼) 한 스레드에서 다른 스레드로 옮겨 다니는 건 괜찮다. 이는 Boost.Asio가 strand라고 부르는 것과 같은 속성이다.

Emilua에서는 이 설계가 다음 3개 함수로 구체화됩니다.

```
spawn_vm(module) -> actor
actor.send(msg)
inbox.receive() -> msg
```

이 3개 함수만 익히면 액터 모델로 코드를 짤 수 있습니다. 몇 가지 예시를 살펴보겠습니다.

**액터 생성하기**

```lua
-- `module1.lua` will be the entry-point
-- for the execution of `new_actor1`
local new_actor1 = spawn_vm{
    module = 'module1' }

local new_actor2 = spawn_vm{
    module = 'module2' }
```

**메시지 보내기**

```lua
new_actor1:send(1)
new_actor1:send('ping')
new_actor1:send{ arg1 = 1, arg2 = 2 }
```

**메시지 받기**

```lua
local inbox = require 'inbox'

while true do
    local msg = inbox:receive()
    handle(msg)
end
```

**주소를 담아 메시지 보내기**

```lua
new_actor1:send{ arg1
```

(원문은 이 마지막 예제 코드가 잘린 채로 끝납니다. 이 글에서 다룬 내용을 토대로 이후 글에서는 각 플랫폼별 권한 축소 메커니즘과, 이 액터 기반 구조 위에서 실제로 권한을 어떻게 부여하고 통신을 어떻게 처리할지가 이어서 다뤄질 것으로 보입니다.)

## 정리

- 샌드박싱을 논할 때 유용한 출발점은 Tinnes/Evans의 정의, 즉 "프로그래밍적으로, 관리자 권한 없이, 임의적으로 프로세스 권한을 제한하는 능력"입니다. 이 글은 이 중에서도 "임의적 권한 축소(discretionary privilege dropping)"에 초점을 맞춥니다.
- `setuidgid`나 suid 헬퍼 바이너리를 이용한 chroot jail 같은 전통적 기법은 슈퍼유저 권한을 임시로 필요로 하기 때문에 최소 권한 원칙에 위배되며, 모든 프로그램이 쓸 수 있는 방식이 아닙니다.
- Docker가 대중화시킨 Linux 사용자 네임스페이스는 네임스페이스 안에서 프로세스를 슈퍼유저로 만들어버려서, 원래 슈퍼유저 전용이던 커널 코드 경로를 일반 사용자에게 열어줍니다. Andy Lutomirski가 지적했듯 이는 실제 권한 상승 취약점으로 이어질 위험이 큰 설계이며, 신뢰된 컨테이너화 도구에만 제한적으로 허용해야 합니다. FreeBSD의 Capsicum, Linux의 Seccomp/Landlock 같은 인터페이스가 이런 문제를 피하도록 설계된 대안입니다.
- 오늘날 모든 주류 OS에서 권한 경계는 프로세스 단위입니다. Linux가 자격 증명을 스레드 단위로 취급하는 예외적인 설계를 갖고 있지만, glibc가 이를 동기화해주지 않으면 문제가 생기며(CVE-2023-43641), Adam Langley가 제시한 스레드 레벨 트릭도 실용적이지 않습니다. 결국 프로세스를 단위로 애플리케이션을 구획화하고, 각 구획에 권한을 부여한 뒤 메시지 전달로 통신시키는 것이 현실적인 접근입니다.
- 이런 프로세스 기반 구획화는 액터 모델과 자연스럽게 맞물립니다. Emilua는 `spawn_vm`, `send`, `receive` 세 함수만으로 액터 모델을 구현하며, 이는 Capsicum 연구자들이 오래전부터 강조해온 "구획화된 애플리케이션 개발은 곧 분산 애플리케이션 개발"이라는 관점과 일치합니다.

프론트엔드 개발자에게는 다소 낯선 시스템 프로그래밍 영역이지만, Electron 앱에서 서드파티 플러그인을 격리하거나, 브라우저 확장 프로그램·WebAssembly 샌드박스를 설계할 때 등장하는 권한 모델·프로세스 격리·메시지 기반 통신의 기본 원리를 이해하는 데 유용한 배경 지식이 됩니다.
