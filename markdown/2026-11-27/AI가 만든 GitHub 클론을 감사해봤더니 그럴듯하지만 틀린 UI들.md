## 핵심 개념

> [!abstract]
> AI 에이전트가 대부분의 코드를 작성한 개발 도구 Forge를 디자인 감사한 경험을 다룬 글입니다. PR 카운트가 30에서 멈추고, 모든 PR이 '0개 파일 변경'으로 표시되고, 모든 버튼이 주황색으로 렌더링되는 등 겉보기엔 멀쩡하지만 실제로는 틀린 UI 문제들을 발견했습니다. 이를 4개의 작은 PR로 수정하고, 다섯 번째 PR로 각 버그 유형을 CI에서 실패하는 체크와 브라우저 스윕 스크립트로 전환해 재발을 막았습니다.

## 아티클

AI 에이전트가 코드 대부분을 작성하고 PR을 올리는 개발 도구, Forge를 운영하면서 겪은 이야기입니다. Forge는 깃 호스팅, CI 러너, 배포 플랫폼을 하나로 합친 서비스로, Cloudflare 위에서 돌아갑니다. 백엔드는 테스트가 있어서 에이전트가 틀리면 바로 드러나지만, 프론트엔드는 다릅니다. 에이전트는 렌더링도 되고 타입체크도 통과하고 스크린샷으로 봐도 그럴듯한 페이지를 만들어내지만, 그 안의 숫자가 실제 데이터와 맞는지는 아무도 확인하지 않은 채로 넘어갈 수 있습니다. 그래서 이번에는 에이전트에게 "까다로운 디자인 리뷰어처럼" Forge를 감사하도록 시켜봤습니다.

## 왜 감사가 필요했나

감사는 실제 운영 중인 사이트를 대상으로, 로그인 상태와 비로그인 상태 모두, 1440px와 모바일 너비에서 진행하도록 지시했습니다. 수정하기 쉬운 순서가 아니라 심각도 순으로 문제를 정리해달라고 요청했습니다.

## 발견된 문제들: 그럴듯하지만 틀린 것들

목록 맨 위를 차지한 건 전부 "UI가 거짓말을 하고 있다"는 종류의 문제였습니다.

- Closed와 Merged 카운트가 30에서 멈춰 있었습니다. swyx/forge 저장소에는 실제로 229개의 머지된 PR이 있는데, 목록은 상태별로 페이지를 한 번만 가져온 뒤 그 페이지에 있는 개수만 세고 있었습니다.
- 모든 PR 행에 "+0 -0 across 0 files"라고 표시됐습니다. 목록 API가 애초에 diff 통계를 반환하지 않는데, UI는 그냥 0을 찍어냈던 겁니다. 그럴듯한 0은 아무도 의심하지 않습니다.
- 저장소 탭이 8개를 넘어가면 오른쪽 끝이 잘려서 스크롤바도 힌트도 없이 사라졌습니다. 트랙패드로 스와이프하지 않으면 Branches나 Settings 탭에 접근할 수 없었습니다.
- 상태 표시가 거의 보이지 않았습니다. PR 헤더에는 10px 대문자 모노폰트로 "OPEN"이 찍혀 있었고, 목록에서는 12px의 연한 텍스트가 연한 배경 위에 있었습니다.
- 브랜치 이름이 강제로 대문자로 표시됐습니다(CLAUDE/PROJECT-THREAD-888AAN 식으로). 브랜치 참조는 대소문자를 구분하기 때문에 이는 잘못된 정보였습니다.

그 다음은 겹침 버그들이었습니다. 떠다니는 "Contents" 박스가 기본적으로 README와 PR 사이드바 위에 열렸고, 마크다운 블록마다 박스를 하나씩 쌓아서 PR 본문에 댓글 다섯 개가 달리면 박스가 여섯 개가 되는 식이었습니다. 잘린 라벨에는 툴팁이 없었고, 전체 UI가 다른 PR, 커밋, 실행 결과로 연결되는 링크로 이뤄진 제품임에도 호버 미리보기가 어디에도 없었습니다.

## 수정: 작은 PR 네 개

각각 프론트엔드 전용이고 독립적으로 머지 가능하도록 나눴습니다. 네 개 모두 main에 머지되어 다음 릴리스에 포함됩니다.

**PR 274, 읽을 수 있는 상태와 정확한 숫자.** 카운트는 API의 pagination.total에서 가져오고, 30개를 넘으면 "Show more (N more)" 버튼이 뜹니다. 가짜 "+0 -0" 줄은 삭제했습니다. open, draft, merged, closed, queued 상태를 아이콘과 13px 라벨로 표시하는 공통 상태 pill 하나로 통일했습니다. PR 번호는 볼드체 모노 칩으로 바뀌었고, 브랜치 이름은 대소문자를 그대로 유지합니다.

**PR 275, 한눈에 보이는 저장소 내비게이션.** 탭에 열린 PR과 이슈 개수를 표시합니다. 한 번도 사용하지 않은 섹션(이슈가 없거나, publication이 없는 경우)은 이유를 설명하는 툴팁과 함께 흐릿한 아이콘으로 접힙니다. 탭은 사용 빈도순으로 정렬되고, 공간이 부족하면 잘리는 대신 줄바꿈되거나 가장자리 페이드와 함께 스크롤됩니다.

**PR 276, 겹침 제거.** Contents 박스는 제목이 4개 이상인 문서에서만 표시됩니다. "Contents · 33" 형태의 접힌 pill로 시작하고, 페이지당 하나만 표시됩니다.

**PR 277, 호버 미리보기와 에이전트용 훅.** PR, 이슈, 커밋, 실행, 사용자 링크에 마우스를 올리거나 포커스를 주면 해당 항목의 상태, 핵심 필드, API 객체로 연결되는 JSON 링크가 담긴 카드가 뜹니다.

이 마지막 PR이 가장 마음에 드는 부분입니다. 미리보기 대상마다 data-forge-kind, data-forge-ref, data-forge-api 속성을 붙였습니다. 사람에게 호버 카드를 보여주는 동일한 마크업이 에이전트에게는 안정적이고 기계가 읽을 수 있는 페이지 지도 역할을 합니다. Forge를 탐색하는 에이전트는 바이라인에서 "#270"을 스크래핑할 필요 없이 pull:swyx/forge#270을 읽고 바로 해당 객체를 가져올 수 있습니다. 개발자 도구의 주요 사용자가 결국 에이전트가 될 거라면, DOM 자체도 API가 되어야 한다는 생각입니다.

## 가장 마음에 들었던 버그: 모든 버튼이 주황색이었다

감사 이후 로그인 페이지가 온통 똑같은 주황색 버튼으로 도배돼 있고, 삭제 버튼이 메인 액션처럼 보인다는 걸 알게 됐습니다.

원인은 지극히 평범해 보이는 한 줄이었습니다.

```
className={`forge-button forge-button--${variant}`}
```

Tailwind v3는 @layer components 안의 규칙 중 클래스 이름이 소스 코드에 문자 그대로 등장하는 것만 유지합니다. forge-button--secondary는 소스에 문자 그대로 나타나지 않으니 Tailwind가 이걸 제거해버렸고, --danger와 모든 사이즈 variant도 마찬가지로 사라졌습니다. 그 결과 사이트 전체에서 variant="secondary"인 버튼이 전부 primary 색상으로 렌더링됐습니다. 브라우저에서 직접 확인해보니, 수정 전 secondary 버튼의 실제 배경색은 #c96b43(primary 색)이었고, 수정 후(PR 299)에는 #e7ddc8이 됐습니다.

이건 에이전트가 만들기 쉽고 리뷰어가 놓치기 쉬운 전형적인 버그입니다. 코드는 올바르게 읽힙니다. 타입도 정확합니다. 테스트가 있다면 클래스 문자열이 맞는지 확인할 텐데, 실제로 맞습니다. 틀린 건 오직 빌드된 CSS뿐입니다.

## 설계된 막다른 길

로그인 페이지와 관련된 두 번째 PR(300)은 뭔가 잘못됐을 때 벌어지는 일을 다뤘습니다. 14개 페이지가 로드에 실패하면 빨간색 "Error: Not found" 한 줄만 보여줬습니다. /explore는 사용자 이름으로 해석되어 "User not found"라고 표시됐습니다. 그리고 어떤 라우트와도 매칭되지 않는 URL은 완전히 빈 페이지를 렌더링했는데, 앱에 catch-all 라우트가 없었기 때문입니다.

이제는 실패 유형을 분류하는 ForgeErrorState 하나로 통일했습니다. Not found는 무엇이 없는지 명시합니다("저장소를 찾을 수 없습니다"). Sign in required와 No access는 적절한 다음 행동을 제안합니다. Offline과 Unexpected는 "Try again" 버튼과 함께 서버 메시지를 세부 정보로 남겨둡니다. 비로그인 방문자는 같은 URL로 되돌아가는 로그인 버튼을 받는데, 비공개 저장소는 비로그인 사용자에게 404로 보이기 때문입니다. 매칭되지 않는 URL은 이제 진짜 404 페이지를 보여줍니다.

작업하는 김에 로그인 흐름도 다시 손봤습니다(PR 301). 이 기기에서 마지막에 사용한 방법을 "이 기기에서 마지막 사용"이라는 라벨과 함께 맨 위에 보여줍니다. 기록이 없으면 패스키가 먼저 뜹니다. 비밀번호나 OAuth로 로그인한 뒤에는 패스키 생성을 한 번 제안합니다. 방법 ID와 시간은 로컬에 저장하고, 계정에 관한 다른 정보는 저장하지 않습니다.

## 다음엔 아예 되돌아갈 수 없게 만들기

버그를 하나씩 고치는 방식은 에이전트가 다음 수천 줄을 쓰게 될 상황에서는 확장되지 않습니다. 그래서 마지막 단계로 각 버그 유형을 CI에서 실패하는 체크로 바꾸는 가드레일 PR을 만들었습니다.

- @layer components 안의 모든 클래스는 소스에 문자 그대로 등장해야 함 (주황 버튼 버그)
- 템플릿 문자열로 만들어진 @layer components 클래스 이름 금지
- 빈 "Error: {...}" 한 줄이나 회색 "not found" 조기 반환 금지, 페이지는 반드시 ForgeErrorState를 써야 함
- `*` catch-all 라우트가 반드시 존재해야 함
- 로그인을 처리하는 모든 코드 경로는 반드시 방법을 기록하고 패스키를 제안해야 함 (새 OAuth 제공자가 이 과정을 조용히 빠뜨릴 수 없도록)

정적 체크로는 모든 걸 잡을 수 없기 때문에 브라우저 스윕인 `npm run ui:sweep`도 추가했습니다. 주요 라우트를 390px와 1280px에서, 로그인 상태와 비로그인 상태 모두로 열어보고 다음을 찾아냅니다.

- 잡히지 않은 에러와 빈 페이지
- 가로 스크롤 (원인이 된 엘리먼트까지 명시)
- 빈 "Error:" 한 줄
- primary 색상으로 렌더링되는 secondary 버튼
- 접근성 이름이 없는 컨트롤

프로덕션을 대상으로 돌렸을 때는 32개 페이지 뷰에서 12개 문제를 찾았습니다. 모든 수정을 머지한 로컬 환경에서는 38개 페이지 뷰에서 0개였습니다. 이 과정에서 아무도 보고하지 않았던 문제 두 개도 잡아냈습니다. 모바일에서 swyx/forge의 README가 인라인 코드가 줄바꿈되지 않아서 551px 너비로 튀어나왔던 것, 그리고 408~433px 구간에서 상단 바가 넘쳤던 것입니다.

## 여전히 남은 문제: 구조적인 부분

이번 감사는 "망가진" 부분을 고쳤습니다. 두 번째 작업인 리디자인 제안에서는 "제대로 기능하지 못하는" 부분을 살펴봤는데, 이 목록이 더 깁니다.

PR 페이지는 "이거 머지해도 될까?"라는 질문에 답하지 못합니다. 체크 항목이 하나도 없는데도 "Ready to merge"라고 뜨고, 페이지 어디에도 해당 커밋의 CI 실행으로 연결되는 링크가 없습니다. 미리보기 배포 패널은 대화 내용 맨 아래, 가장 하단에 있습니다. 제안은 상단에 상태 박스 하나를 두는 방식입니다. 머지 가능 여부, 체크 항목별 한 줄씩, 썸네일이 있는 미리보기, 머지 버튼까지. GitHub의 머지 박스와 Vercel의 미리보기 댓글을 한곳에 합친 셈인데, 여기에 더해 어떤 에이전트가 어떤 스레드에서 이 PR을 열었는지 보여주는 출처 표시 행도 추가합니다. 이 마지막 부분이 Forge가 GitHub 대비 가진 강점인데, 지금은 이걸 둘 곳이 없습니다.

앱에는 페이지 너비가 네 가지, 저장소 헤더 스타일이 두 가지나 있습니다. packages/web/src/pages 안에서 25개 페이지는 max-w-5xl을, 22개는 max-w-6xl을, 4개는 max-w-7xl을 쓰고, 880px와 1540px짜리 예외도 있습니다. 페이지를 이동할 때마다 헤더가 튑니다. 해법은 왼쪽 사이드바를 가진 셸 하나로 통일하는 것입니다.

홈 화면은 받은함이 아니라 프로필입니다. /dashboard는 큰 아트 카드와 저장소 카드 여섯 개가 있는 화면으로 리다이렉트되는데, 정작 오늘 내가 푸시한 저장소는 거기에 없습니다. 개발 도구를 열 때 궁금한 건 "나에게 필요한 게 뭔가"입니다. 내 PR에서 실패한 CI, 내가 머지할 수 있는 초록 불 PR, 리뷰 요청 같은 것들이요.

실행이 실패했을 때, 그 실패 내용은 페이지에서 가장 마지막에 보이는 정보입니다. 릴리스 영수증, 빌드 콘솔, 러너 설정, "해당 없음"이라고 표시된 네 개의 단계 아래, 진행 라인의 세 번째 단계 밑에 10px짜리 회색 모노폰트로 놓여 있습니다.

테마가 라벨에까지 새어 들어갔습니다. 39개 파일에서 헤딩 위에 테마가 들어간 짧은 머리말을 붙이고 있습니다. "Joining bench", "Change gauge", "Threshold ledger", "Bounded intervention" 같은 식으로요. 워크숍 테마는 랜딩 페이지에서는 진짜 브랜드 자산이지만, 앱 내부에서는 모든 화면에 번역 과정을 하나 더 추가할 뿐입니다.

밀도도 문제입니다. 1440px에서 PR 목록은 96px짜리 카드와 12px 간격으로 화면당 다섯 개의 PR만 보여줍니다. 개발 도구라면 이보다 세 배는 더 보여줘야 합니다.

## AI가 만든 UI에서 배운 것

에이전트는 "진실"이 아니라 "그럴듯함"을 최적화합니다. "+0 -0 across 0 files"가 완벽한 예시입니다. 포맷도 깔끔하고 위치도 적절하지만, 모든 행에서 틀렸습니다. 스크린샷이 아니라 실제 데이터를 기준으로 감사해야 합니다.

진짜 중요한 버그는 레이어 사이에 숨어 있습니다. 주황 버튼 버그는 올바른 TSX가 잘못된 CSS를 만들어낸 경우였습니다. 30개로 멈춘 카운트는 올바른 컴포넌트가 잘못된 페이지네이션 가정 위에 얹힌 경우였습니다. 한 레이어의 단위 테스트는 이런 걸 잡아내지 못하지만, 브라우저는 잡아냅니다.

손으로 고친 버그는 반드시 체크로 전환해야 합니다. 에이전트는 다음 수천 줄을 계속 쓸 테니, 잊어버릴 교훈 대신 실패하는 테스트를 남겨두는 게 맞습니다.

문제는 애초에 미적인 부분이 아니었습니다. Forge는 감각이 있는 제품입니다. 부족했던 건 페이지마다 "이 화면은 무엇을 위한 것이고, 그 역할을 제대로 하고 있는가"를 물어보는 사람이었습니다. 그리고 그 질문도 에이전트에게 시킬 수 있다는 걸 이번에 확인했습니다.

## 정리

- 에이전트가 만든 프론트엔드는 렌더링되고 타입체크를 통과해도 실제 데이터와 맞지 않는 "그럴듯한 거짓"을 담을 수 있습니다. 스크린샷이 아니라 실제 데이터를 기준으로 감사해야 합니다.
- 가장 위험한 버그는 레이어 경계에서 생깁니다. 올바른 TSX가 Tailwind의 purge 규칙 때문에 잘못된 CSS로 빌드되거나, 올바른 컴포넌트가 잘못된 API 가정 위에 얹히는 식입니다. 단위 테스트로는 못 잡고 실제 브라우저 검증이 필요합니다.
- 발견한 버그는 전부 CI에서 실패하는 체크로 전환해야 재발을 막을 수 있습니다. Forge는 정적 린트 규칙과 함께 `npm run ui:sweep` 같은 브라우저 스윕 스크립트를 만들어, 호버 버그·접근성 이름 누락·가로 스크롤 등을 자동으로 탐지합니다.
- 에이전트의 출력을 사람 눈으로만 리뷰하는 건 한계가 있습니다. 에이전트에게 "까다로운 리뷰어" 역할을 맡겨 심각도순으로 감사하게 하는 방식이 실제로 효과가 있었습니다.
- UI의 호버 타겟에 data 속성(data-forge-kind, data-forge-ref, data-forge-api 등)을 붙이는 것만으로 같은 마크업이 사람에게는 미리보기를, 에이전트에게는 기계가 읽을 수 있는 API 지도를 제공할 수 있습니다. 에이전트가 주요 사용자가 될 도구라면 DOM 설계 자체를 API 설계처럼 접근해야 합니다.
