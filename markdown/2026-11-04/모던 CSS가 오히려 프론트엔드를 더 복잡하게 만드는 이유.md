## 핵심 개념

> [!abstract]
> ResizeObserver를 컨테이너 쿼리로, JavaScript 로직을 :has() 선택자로 대체하면 코드의 diff는 줄어들지만 시스템 전체의 복잡성은 오히려 늘어날 수 있다. 이 글은 CSS와 JavaScript가 하나의 행동을 동시에 제어할 때, container-type이 블록 포매팅 컨텍스트를 의도치 않게 생성할 때, 짧은 선택자가 예상보다 넓게 매치될 때 발생하는 세 가지 실제 버그 시나리오를 다룬다. 핵심 주장은 '지역적 단순함'과 '시스템 복잡성'을 구분해야 한다는 것이다.

## 아티클

# 모던 CSS가 오히려 프론트엔드를 더 복잡하게 만드는 이유

ResizeObserver를 컨테이너 쿼리로, 복잡한 자바스크립트 로직을 `:has()` 선택자 몇 줄로 바꾸고 PR을 올리면 diff는 온통 초록색이고 빨간줄 일색입니다. 리뷰어들은 점심시간 전에 승인 도장을 찍어주죠. 그런데 일주일 뒤, 대시보드의 카드 하나가 사라지고, 태블릿에서 제목이 이유 없이 커지고, 댓글 영역의 여백이 미묘하게 틀어집니다. 방금 작성한 몇 줄의 코드 자체에는 버그가 없습니다. 문제는 그 몇 줄의 CSS가 "함께" 몰고 들어온 부작용들입니다.

이 글은 "CSS 기능 하나가 코드 한 조각을 단순하게 만들면서도, 그것이 기존 코드(CSS든 JavaScript든)와 어떻게 얽히는지 이해하지 못하면 애플리케이션 전체를 더 이해하기 어렵게 만들 수 있다"는 주장을 다룹니다. 모던 CSS가 나쁘다는 이야기가 아닙니다. 로직이 CSS와 JavaScript로 나뉠 때 무슨 일이 벌어지는지, 그리고 무엇을 트리거했는지 명확히 보이지 않는 조건부 스타일을 어떻게 디버깅할 것인지에 대한 고민입니다.

## 지역적 단순함 vs 시스템적 복잡성

새로운 CSS 기능이 공유 아파트에 입주하는 새 세입자라고 생각해보면 이해가 쉽습니다. 조용하고 깔끔한 세입자라 해도 결국 기존 거주자들과 부엌을 함께 씁니다. 여기서 CSS의 룸메이트는 JavaScript, 컴포넌트의 레이아웃, CSS 캐스케이드, 브라우저의 렌더링 엔진입니다. 아파트의 안정성은 새 세입자 개인보다 이들이 서로 얼마나 잘 지내느냐에 달려 있습니다.

이렇게 보면 측정해야 할 두 가지가 분리됩니다.

- **지역적 단순함(Local simplicity)**: 파일 하나가 얼마나 적은 코드를 필요로 하는가
- **시스템 복잡성(System complexity)**: 애플리케이션을 안전하게 변경하기 전에 이해해야 하는 상호작용의 개수

PR의 diff는 이 중 첫 번째만 보여줍니다.

이 주제는 저자 혼자만의 고민이 아닙니다. 2026년 4월 Igor Roztropiński가 "Modern Frontend Complexity: essential or accidental?"이라는 에세이에서 "브라우저가 최근 몇 년간 발전한 것을 감안하면, 처음부터 다시 시작해 훨씬 단순한 접근법을 찾을 수 있지 않을까?"라는 질문을 던졌고, 이는 r/programming에서 80개 이상의 댓글을 끌어모았습니다. 반응은 양쪽으로 갈립니다. 한쪽(Kwantuum)은 "이런 글들은 다 '더 적게 할 수 있다'고 말하지만 실제로는 더 적게 하지 않는다. 그냥 덜 할 뿐이다"라며 비판적입니다. 반대쪽(kayinfire)은 "프론트엔드 프레임워크가 그 가치보다 더 많은 우발적 복잡성을 끌어들이는 경우가 수두룩하다"며 "CSS가 최근 몇 년간 상호작용성 면에서 얼마나 엄청나게 발전했는지는 말할 필요도 없는데, 다들 JS 말고는 신경쓰지 않는 게 참 안타깝다"고 반박합니다.

저자는 두 입장 모두 일리가 있다고 봅니다. CSS는 분명 발전했지만, 종이 위의 "더 적은" CSS가 실무에서 자동으로 "더 적은" 복잡성을 뜻하지는 않습니다. 네이티브 기능이 복잡성을 줄이는 것은, 그것이 실제로 기존에 있던 것을 "완전히" 대체하고 그와 상호작용하는 다른 모든 것의 평온한 상태를 깨뜨리지 않을 때뿐입니다.

이 글은 아파트의 룸메이트들을 한 번에 하나씩 소개하는 방식으로 이 문제를 풀어갑니다.

## 시나리오 1: 두 명의 주인을 가진 행동

첫 번째 룸메이트는 JavaScript입니다. 문제는 옛 세입자가 완전히 이사를 나가지 않을 때 시작됩니다.

충분한 공간이 있을 때 2열 레이아웃으로 전환되는 카드가 있다고 해봅시다. 원래 버전은 ResizeObserver로 클래스를 토글합니다.

```js
const card = document.querySelector('.card');
new ResizeObserver(([entry]) => {
  card.classList.toggle('card--wide', entry.contentRect.width > 480);
}).observe(card);
```

```css
.card--wide .card__body {
  display: grid;
  grid-template-columns: 160px 1fr;
}
.card--wide .card__title {
  font-size: 1.5rem;
}
```

CSS 컨테이너 쿼리를 쓰면 스크립트가 전혀 필요 없고 선택자도 동시에 단순해집니다.

```css
.card {
  container-type: inline-size;
}
@container (width > 480px) {
  .card__body {
    display: grid;
    grid-template-columns: 160px 1fr;
  }
}
```

아름답죠. 하지만 마이그레이션은 한 번의 깔끔한 작업으로 끝나지 않는 경우가 대부분입니다. PR은 `@container` 규칙을 추가하고 `.card--wide .card__body` 규칙을 제거합니다. 하지만 옵저버는 다른 파일에 등록돼 있어 살아남고, `.card--wide .card__title` 규칙도 아무도 그 클래스를 검색해보지 않아 살아남습니다. 두 구현이 모두 480px에서 일치하기 때문에 당장은 아무것도 깨진 것처럼 보이지 않습니다.

그러다 디자이너가 브레이크포인트를 600px로 옮겨달라고 요청하고, 개발자는 자신이 알고 있는 유일한 지점인 `@container` 규칙만 수정합니다. 그 결과 480px에서 600px 사이에서 카드는 단일 컬럼 본문에 와이드 레이아웃 제목을 가진 상태가 됩니다. 아무도 이런 상태를 의도적으로 작성하지 않았습니다. 이걸 찾으려면 레이아웃에 두 개의 주인이 있다는 사실을 알고 둘 다 읽어봐야 합니다.

같은 함정이 다른 형태로도 나타납니다.

- JavaScript가 `.is-active` 클래스를 토글하는 동시에 `:has()`가 DOM에서 똑같은 상태를 유도
- JavaScript 애니메이션과 CSS 트랜지션이 하나의 인터랙션에 동시에 반응
- 옛 미디어 쿼리 규칙이 새 컨테이너 쿼리 규칙과 나란히 남아, 컴포넌트가 한쪽에서는 뷰포트에, 다른 쪽에서는 자신의 컨테이너에 반응

CSS와 JavaScript는 하나의 컴포넌트를 행복하게 공유할 수 있지만, 그 컴포넌트의 "행동(behavior)"은 공유할 수 없습니다. 조용히 주도권 다툼을 벌이게 두기보다는 먼저 확인해야 합니다. 관련된 모든 당사자를 파악하고 역할을 분리하세요.

**CSS가 소유해야 할 것**: 크기나 DOM 구조로부터 자연스럽게 따라오는 표현 — 특정 너비에서의 레이아웃, 유효하지 않은 필드를 포함한 폼의 외관

**JavaScript가 소유해야 할 것**: 애플리케이션 상태와 비동기 작업 — 요청이 대기 중인지 여부, 서버가 반환한 값, 스타일시트 바깥의 코드가 읽어야 하는 모든 것

그리고 마이그레이션이 끝났다면 마무리까지 지어야 합니다. 옵저버, 클래스, 그 클래스를 언급하는 모든 선택자를 삭제하세요. 그렇지 않으면 절대 이사 나가지 않는 세입자를 떠안게 됩니다.

## 시나리오 2: 방을 재배치하는 룸메이트

2023년 저자는 블록 포매팅 컨텍스트(block formatting context)가 float 문제를 어떻게 해결하는지에 대해 쓴 적이 있습니다. 그때는 블록 포매팅 컨텍스트를 만드는 것이 의도적인 선택이었습니다. 하지만 지금은 의도치 않게 만들 수 있습니다.

`container-type: inline-size`를 선언할 때 우리는 "자식 요소들이 내 너비를 쿼리할 수 있게 해달라"고 말하는 것뿐이라 생각하지만, 브라우저는 훨씬 더 많은 것을 듣습니다. 이게 두 번째 룸메이트, 즉 컴포넌트 "주변의" 레이아웃입니다. 선반 하나만 달라고 한 새 세입자가 거실 전체 가구 배치를 바꿔버린 셈이죠.

MDN의 `container-type` 레퍼런스에 따르면 이 값은 "요소에 style containment와 inline-size containment를 적용"합니다. 그리고 MDN의 블록 포매팅 컨텍스트 가이드는 "쿼리 컨테이너(container-type이 normal이 아닌 요소)"를 블록 포매팅 컨텍스트를 생성하는 CSS 스타일 중 하나로 꼽습니다. 새 블록 포매팅 컨텍스트를 형성하는 요소는 MDN의 표현을 빌리면:

- 내부 float를 포함(contain)하고
- 외부 float를 배제(exclude)하며
- 마진 병합(margin collapsing)을 억제합니다

즉 선언 하나가 쿼리와 전혀 관계없는 세 가지 레이아웃 동작을 바꾸고, inline-size containment에서 비롯된 네 번째 동작까지 더해집니다. 저자는 "before"와 "after" 쌍이 오직 이 선언 하나로만 다른 데모를 만들어 확인했습니다.

**마진 병합이 멈춘다**: `margin-bottom: 16px`인 문단이 카드 위에 있고, 카드의 제목은 `margin-top: 24px`입니다. 변경 전에는 제목의 마진이 카드 상단을 통과해 병합(collapse)되어 문단의 마진과 합쳐지며 24px 간격만 남았습니다. 변경 후에는 마진이 카드 내부에 갇힙니다. 두 마진이 이제 합산되어 40px가 되고, 카드는 30px에서 54px 높이로 늘어납니다.

**float이 카드를 밀어낸다**: 카드가 float된 이미지를 따르는 상황에서, 변경 전에는 카드 박스가 float 뒤를 지나가며 텍스트가 이미지를 감쌌습니다. 변경 후에는 카드 전체가 float 옆에 놓이며, 이미지 너비(120px)만큼 더 안쪽에서 시작하고 그만큼 좁아집니다.

**콘텐츠 크기 기반 카드가 사라진다**: 이게 카드를 아예 사라지게 만드는 원인입니다. Inline-size containment는 요소가 콘텐츠로부터 너비를 가져오지 못하게 막습니다. MDN의 설명은 간결합니다. "맥락적이거나 명시적인 크기를 얻을 수 없다면, size containment를 가진 요소는 붕괴(collapse)한다."

데모에서 태그 크기의 카드 세 개가 flex row에 있었고, 각각 약 74px, 96px, 114px였습니다. 여기에 `container-type: inline-size`를 추가하면 셋 다 0px가 됩니다. 저자는 카드가 `inline-block`일 때, float됐을 때, `width: fit-content` 박스일 때, `align-items: flex-start`를 가진 컬럼 flex 컨테이너의 자식일 때, auto grid 트랙의 아이템일 때도 동일하게 0px 결과를 확인했습니다. 일반 블록 레벨 카드만 너비를 부모로부터 가져오기 때문에 전체 너비를 유지합니다.

고립된 상태에서 카드는 부모를 채우는 블록입니다. 하지만 실제로는 flex 아이템이거나, float을 따르거나, 자신이 흡수하던 마진을 가진 문단 아래 놓여 있습니다.

`container-type`을 요소에 추가하기 전에 다음 세 가지를 확인하세요.

1. **이 요소의 너비는 어디서 오는가?** 답이 "자신의 콘텐츠"라면 맥락에서 너비를 부여하거나(예: `flex: 1`과 `width: 100%`), 이미 너비를 가진 래퍼 요소로 `container-type`을 옮기세요.
2. **첫 번째나 마지막 자식이 마진을 가지고 있는가?** 그 마진들이 요소를 통과해 병합되고 있을 수 있습니다.
3. **이 요소는 실제로 어디서 사용되는가?** 고립된 상태뿐 아니라 이 컴포넌트를 호스팅하는 모든 실제 레이아웃 안에서 테스트하세요.

이 질문들에 답하면 룸메이트가 몰래 가구 배치를 바꿔버리는 상황을 막을 수 있습니다.

## 시나리오 3: 시끄러운 룸메이트

세 번째 룸메이트는 CSS 캐스케이드입니다. 공유 아파트마다 마지막 발언권이 누구에게 있는지에 대한 규칙이 있는데, 새 세입자가 예상보다 훨씬 큰 발언권을 가지고 들어올 수 있습니다.

`:has()` 선택자와 네이티브 중첩(nesting)은 짧은 선택자를 쓸 수 있게 해주지만, 짧은 선택자는 보이는 것보다 더 많은 것과 매치되고 더 높은 우선순위를 가질 수 있습니다.

히어로 이미지를 가진 카드 컴포넌트에서 문단 마진을 제거하고 싶다고 해봅시다. 다음과 같이 작성하면 의도대로 동작할 것처럼 보입니다.

```html
<article class="card">
  <p>Body text of the card.</p>
  <p>A second paragraph.</p>
  <div class="comment">
    <img src="avatar.png" alt="">
    <p>Nice post.</p>
  </div>
</article>
```

```css
.card:has(img) p {
  margin: 0;
}
/* Elsewhere, the comment component's own rule */
.comment p {
  margin-block: 8px;
}
```

이 카드에는 히어로 이미지가 없습니다. 그런데도 카드 안의 모든 문단이 마진을 잃습니다.

`.card:has(img) p` 선택자는 "히어로 이미지가 있는 카드의 직계 문단"을 의도했지만, 실제로는 카드 안 "어디에든" `img`가 있기만 하면(댓글 안의 아바타 이미지라도) 매치되고, 카드 내부의 "모든" 하위 `p` 요소에 적용됩니다. `.comment p`보다 특이도(specificity)가 높거나 소스 순서상 나중에 오면 댓글의 마진 규칙까지 덮어써 버립니다.

## 정리

이 글은 모던 CSS 기능(컨테이너 쿼리, `:has()`, 네이티브 중첩 등)이 본질적으로 나쁘다고 주장하지 않습니다. 핵심은 **지역적 단순함(diff가 줄어드는 것)과 시스템 복잡성(전체를 이해하는 데 필요한 상호작용의 수)을 구분해야 한다**는 것입니다.

- **행동의 소유권을 명확히 하라**: CSS는 크기·DOM 구조에서 따라오는 표현을, JavaScript는 애플리케이션 상태와 비동기 작업을 맡아야 합니다. 마이그레이션 시 옛 구현(옵저버, 클래스, 관련 선택자)을 완전히 제거하지 않으면 두 로직이 동시에 컴포넌트를 제어하는 상태가 됩니다.
- **`container-type: inline-size`는 단순한 쿼리 선언이 아니다**: 블록 포매팅 컨텍스트를 생성해 마진 병합 억제, float 포함/배제, 콘텐츠 기반 크기 붕괴라는 부수 효과를 동반합니다. 적용 전에 요소의 너비 출처, 자식의 마진, 실제 사용 맥락을 점검해야 합니다.
- **짧은 선택자는 생각보다 넓게 매치된다**: `:has()`를 활용한 선택자는 의도한 범위보다 넓은 DOM 트리에 매치되어 다른 컴포넌트의 스타일 규칙을 예상치 못하게 덮어쓸 수 있습니다.

실무에서는 새로운 CSS 기능을 도입할 때 "이 기능이 무엇을 대체하는가"뿐 아니라 "이 기능이 어떤 기존 동작·레이아웃·캐스케이드 규칙과 상호작용하는가"까지 함께 검토하는 습관이 필요합니다. diff가 짧아졌다고 복잡성이 줄어든 것은 아니며, 마이그레이션은 새 코드를 추가하는 것만큼이나 옛 코드를 완전히 제거하는 작업까지 포함해야 끝난 것입니다.
