## 핵심 개념

> [!abstract]
> Kevin Powell은 프론트엔드에서 가장 저평가된 스킬이 프롬프트 작성이 아니라 AI가 만든 코드의 문제를 빠르게 식별하고 고치는 능력이라고 말합니다. CSS Demystified 강의의 실전 예제를 통해 고정 width/height, 불필요한 width: 100%, box-sizing 오해, margin과 padding의 혼용, margin collapsing 문제 등 흔히 발생하는 CSS 레이아웃 버그를 하나씩 진단하고 고치는 과정을 보여줍니다. 결론은 AI를 잘 쓰기 위해서라도 CSS 자체에 대한 근본적인 이해가 필요하다는 것입니다.

## 아티클

프론트엔드 개발에 AI 도구가 깊숙이 들어오면서, 정작 실력을 가르는 지점은 "프롬프트를 얼마나 잘 쓰는가"가 아니라는 이야기가 나오고 있습니다. CSS 전문가이자 유튜버인 Kevin Powell은 자신의 채널에서, AI가 만들어낸 코드에서 문제가 생겼을 때 이를 얼마나 빠르게 식별하고 고치는지가 지금 가장 저평가된 프론트엔드 역량이라고 말합니다. 이 글에서는 그가 실제 CSS Demystified 강의의 챌린지 예제를 활용해 보여준 디버깅 과정을 정리해봅니다.

## 왜 "문제 해결 능력"이 핵심인가

AI가 코드를 짤 때 매번 틀리는 건 아닙니다. 하지만 가끔씩, 그것도 예상치 못한 순간에 문제가 생기기 마련이고, 이때 개발자는 두 부류로 나뉩니다.

- 1분 안에 문제를 짚어내고 빠르게 고치는 개발자
- 30분 동안 AI에게 재차 프롬프트를 넣으며 "뭐가 문제인지" 알아내려 애쓰는 개발자

특히 CSS는 겉보기엔 문법 오류가 없어도 레이아웃이 미묘하게 어긋나는 경우가 많아서, AI가 생성한 CSS에서 이런 문제가 자주 발견된다고 합니다. 마크업 자체는 딱히 문제가 없어 보이는데도 레이아웃에서 뭔가 이상하다면, 그 즉시 "레드 플래그"를 감지할 수 있는 눈이 필요하다는 것이 핵심 주장입니다.

## 실전 예제: 카드 레이아웃 디버깅

예제로 사용된 카드 컴포넌트는 다음과 같은 증상을 보입니다.

- 텍스트가 카드 상단에 너무 붙어 있음
- 콘텐츠 오버플로우 발생
- 그 외 자잘한 여백 문제들

이런 문제들을 하나씩 짚어가며 고치는 과정을 살펴보겠습니다.

### 1. 고정 width/height 대신 제약(constraint) 사용하기

요즘 LLM은 예전만큼 고정 크기값을 잘 넣지 않는다고 합니다. 하지만 여전히 피해야 할 습관 중 하나로 꼽힙니다. 크기를 지정해야 한다면 고정값이 아니라 제약을 주는 방식이 바람직합니다.

- width가 필요하면 `width` 대신 `max-width`를 사용해서, 그보다 작아질 수 있는 여지를 남겨둡니다.
- height가 필요하면 `height` 대신 `min-height`를 사용합니다.

사실 대부분의 경우 `height`는 아예 필요 없는 선언입니다. 높이를 지정하지 않으면 브라우저가 콘텐츠 양에 맞춰 자연스럽게 늘고 줄어드는 `auto` 동작이 훨씬 잘 작동합니다. 다만 이런 무의미한 height 선언은 보통 LLM이 아니라 사람이 습관적으로 넣는 경우가 많다고 짚었습니다.

### 2. width: 100%이 진짜 범인

오버플로우의 실제 원인을 찾아보니 `width: 100%`가 문제였습니다. 이 선언을 지우자 레이아웃이 바로 정상화되었습니다. 이런 종류의 "쓸모없는 선언"은 실제로 LLM이 자주 만들어내는 패턴이라고 합니다.

### 3. box-sizing: border-box는 만능이 아니다

여기서 "박스 사이징을 border-box로 안 줘서 그런 거 아니냐"는 반론이 나올 법한데, 이는 정확한 진단이 아닙니다. 실제로 `box-sizing: border-box`를 추가해보면 레이아웃이 조금 나아지긴 하지만 완전히 해결되지는 않습니다. 이유는 간단합니다. margin은 border-box 계산에 포함되지 않기 때문입니다. 즉 `box-sizing: border-box` + `width: 100%` + `margin`의 조합이라면 margin만큼 여전히 넘칠 수밖에 없습니다.

결국 해결책은 `width` 선언 자체를 지우는 것이었습니다. height와 마찬가지로 width도 `auto`로 두면 대부분 잘 작동하기 때문에, 굳이 명시적으로 선언할 필요가 없었습니다.

### 4. margin 대신 padding으로

레이아웃을 거의 다 잡았지만 여전히 남은 문제는 margin이었습니다. 어떤 요소 안에 내부 콘텐츠가 있을 때, 바깥쪽에 margin을 주는 방식은 대체로 좋은 선택이 아닙니다. 특정 요소 하나만 신경 쓰다 보면 "이 주변에 여백이 필요하다"는 생각에 습관적으로 margin을 넣게 되는데, 이게 문제를 만드는 패턴 중 하나입니다.

이 예제에서는 카드 바깥쪽에 걸려 있던 margin을 완전히 제거하고, 대신 카드 자체에 `padding: 24px`를 주는 방식으로 바꿨습니다. 배경이나 카드 안쪽에 여백이 더 필요할 때는 margin이 아니라 padding으로 해결하는 것이 기본 전략입니다.

### 5. 마진 병합(collapsing margin)과 잔여 여백 문제

margin을 정리하고 나서도 여전히 이상한 여백이 남아 있었습니다. 원인은 두 가지였습니다.

첫째, 타이틀에 걸려 있던 `margin-top`이 실제로는 아무 역할도 하지 않으면서 불필요한 여백만 만들고 있었습니다. 이를 제거하고, 아예 `margin-top: 0`으로 명시했습니다. (물론 CSS 리셋을 적용해서 모든 요소의 margin을 0으로 초기화하는 방법이 더 표준적인 접근이라는 언급도 있었습니다.)

둘째, 콘텐츠 하단의 이상한 여백은 사실 콘텐츠 자체가 아니라 그 안의 `<p>` 태그에서 비롯된 것이었습니다. 이 경우 `p` 요소에 `margin: 0`을 주는 방식으로 해결할 수 있고, 대신 부모 요소에 `display: grid`와 `gap`을 적용해 요소 간 간격을 margin 대신 gap으로 관리하는 전략을 제안했습니다. 이 방식이 유일한 정답은 아니며, margin을 다루는 전략은 여러 가지가 있을 수 있다고 덧붙였습니다.

## 결국 필요한 건 CSS에 대한 이해

이 모든 디버깅 과정은 Kevin Powell의 CSS Demystified 강의 중 "Making Sense of Layouts" 모듈에 포함된 챌린지였습니다. 이 모듈에서는 margin을 다루는 다양한 전략, grid로 구조를 잡는 방법, flexbox와 grid를 상황에 맞게 선택하는 법 등을 다룹니다. 현재는 "Writing Resilient CSS"라는 새 모듈도 준비 중인데, 확장 가능하고 유지보수하기 좋은 CSS를 작성하는 데 초점을 맞춘다고 합니다.

강의의 궁극적인 목표는 CSS를 더 잘 이해하는 것입니다. 직접 CSS를 작성하든, LLM이나 다른 AI 도구를 활용해 프론트엔드 코드를 생성하든 상관없이, CSS를 제대로 이해하고 있으면 가끔 발생하는 문제를 빠르고 정확하게 짚어내고 고칠 수 있다는 것이 핵심 메시지입니다.

## 정리

- AI 시대의 프론트엔드 개발에서 가장 저평가된 역량은 프롬프트 작성 실력이 아니라, AI가 만든 코드의 문제를 빠르게 식별하고 고치는 능력입니다.
- CSS 레이아웃 문제를 빠르게 진단하려면 몇 가지 체크리스트가 유용합니다: 고정 width/height 대신 max-width/min-height 같은 제약 사용, 불필요한 width: 100% 의심하기, box-sizing: border-box가 margin 문제까지 해결해주지 않는다는 점 인지하기, 요소 바깥 margin보다 padding을 우선 고려하기, margin collapsing과 자식 요소(p 등)의 기본 margin이 의외의 여백을 만들 수 있다는 점 기억하기.
- margin 문제를 grid + gap 조합으로 대체하는 것도 하나의 실전 전략으로 소개되었지만, 유일한 정답은 아니며 상황에 따라 다양한 접근이 가능합니다.
- 결국 AI 도구를 잘 쓰기 위해서라도 CSS 자체에 대한 깊은 이해가 필요하며, 이것이 코드를 직접 짜는 것보다 오히려 더 중요한 역량이 되고 있습니다.
