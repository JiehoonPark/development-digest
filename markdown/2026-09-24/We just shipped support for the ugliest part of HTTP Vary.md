## 핵심 개념

> [!abstract]
> HTTP 표준 헤더 중 하나인 Vary는 "아직 개선하지 못한, HTTP에서 가장 지저분한 부분"이라는 말을 들을 정도로 악명이 높습니다. 중개 서버(intermediary) 간 상호운용성이 형편없다는 평가까지 받는 헤더인데요. 하지만 지저분하다고 해서 쓸모없다는 뜻은 아닙니다. Cloudflare는 최근 모든 플랜에서 Cache Rules를 통해 Vary 헤더를 제어할 수 있는 기능을 출시했습니다. 이 글에서는 Vary가 왜 다루기 까다로운 헤더인지, 그리고 Cloudflare가 이 문제를 어떻게 풀었는지 정리해봅니다.

## 아티클

HTTP 표준 헤더 중 하나인 `Vary`는 "아직 개선하지 못한, HTTP에서 가장 지저분한 부분"이라는 말을 들을 정도로 악명이 높습니다. 중개 서버(intermediary) 간 상호운용성이 형편없다는 평가까지 받는 헤더인데요. 하지만 지저분하다고 해서 쓸모없다는 뜻은 아닙니다. Cloudflare는 최근 모든 플랜에서 Cache Rules를 통해 `Vary` 헤더를 제어할 수 있는 기능을 출시했습니다. 이 글에서는 `Vary`가 왜 다루기 까다로운 헤더인지, 그리고 Cloudflare가 이 문제를 어떻게 풀었는지 정리해봅니다.

## Vary가 하는 일

하나의 URL이 두 개 이상의 정당한 응답을 가질 수 있는 경우가 있습니다. 예를 들어 서버가 브라우저에 따라 다른 이미지 포맷을 내려주는 경우가 대표적입니다. 캐시가 `Vary`를 무시하면 잘못된 응답을 그대로 서빙할 위험이 있고, 반대로 요청 헤더의 원시 값(raw value)을 전부 다른 것으로 취급하면 비슷비슷한 요청 몇 개가 순식간에 재사용 불가능한 캐시 엔트리 수천 개로 흩어져 버립니다. `Vary`는 캐시에게 "어떤 요청 필드가 응답에 영향을 줄 수 있는지"는 알려주지만, "그 차이가 실제로 의미 있는 차이인지"는 알려주지 않습니다.

`Vary`는 오리진 서버가 캐시(Cloudflare 같은 중개 서버)에게 어떤 요청 필드가 응답에 영향을 줄 수 있는지 알려주는 표준 HTTP 응답 헤더입니다. 사이트들은 같은 URL에서 언어, 이미지 포맷, 압축 방식, 지역별 콘텐츠 등을 다르게 내려주기 위해 `Vary`를 사용합니다.

브라우저가 웹페이지를 요청하는 상황을 예로 들어보겠습니다.

```
GET /catalog HTTP/1.1
Host: example.com
Accept: text/html
```

오리진은 HTML을 반환하면서, 응답에 영향을 줄 수 있는 필드로 `Accept`를 지정합니다.

```
HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: public, max-age=3600
Vary: Accept
```

API 클라이언트가 같은 URL을 다른 선호값으로 요청할 수도 있습니다.

```
GET /catalog HTTP/1.1
Host: example.com
Accept: application/json
```

이번엔 JSON이 올바른 응답입니다. `Vary: Accept`는 캐시에게 "URL만으로는 응답을 선택하기에 충분치 않으며, 요청의 `Accept` 값도 함께 고려해야 한다"고 알려줍니다.

`Vary`가 없다면 먼저 캐시에 들어간 응답이 두 클라이언트 모두에게 서빙될 수 있습니다. HTML이 먼저 들어가면 API 클라이언트는 마크업을 받아 JSON 파서가 실패하고, JSON이 먼저 들어가면 웹페이지를 기대한 브라우저가 API 응답을 받게 됩니다.

`Vary`는 캐시가 요청자에게 잘못된 응답을 서빙하는 것을 막아주지만, 대신 더 어려운 질문을 남깁니다. 서로 다른 헤더 값을 가진 두 요청이 정말로 다른 응답을 필요로 하는가 하는 질문입니다.

## 올바른 캐싱이 무용지물이 되는 순간

`Vary`는 어떤 요청 필드가 응답에 영향을 줄 수 있는지는 알려주지만, 그 응답이 실제로 무엇을 나타내는지는 알려주지 않습니다. 영어, 프랑스어, 독일어 세 언어만 지원하는 오리진을 예로 들어보겠습니다. 한 클라이언트는 다음처럼 요청할 수 있습니다.

```
Accept-Language: en-US, fr;q=0.8
```

다른 클라이언트는 이렇게 요청할 수 있습니다.

```
Accept-Language: fr;q=0.8, en-GB
```

두 요청 모두 실제로는 영어를 선호합니다. 오리진은 두 요청 모두 동일한 영어 응답으로 매핑할 수 있습니다. 하지만 원시 값을 비교하는 캐시는 이 둘이 동등하다고 안전하게 가정할 수 없습니다. 순서도 다르고 언어 태그도 다르기 때문입니다(오리진은 이 차이를 구분하지 않는데도 말이죠). 결국 캐시는 응답 본문이 완전히 동일한 바이트인데도 이 둘을 별개의 변형(variant)으로 저장하게 됩니다.

이것이 바로 `Vary`의 근본적인 문제입니다. 애플리케이션은 방대한 요청 값 집합으로부터 작고 한정된 응답 집합을 만들어내는 경우가 많습니다. 오리진은 수천 가지 언어 선호가 결국 지원하는 세 언어로 수렴한다는 것을 알지만, 캐시는 보통 그 사실을 모릅니다.

이 문제는 응답이 여러 필드에 대해 달라질 때 더 커집니다. 한 필드에서 열 개의 값이 존재하면 열 개의 변형이 생기지만, 세 필드에 걸쳐 각각 열 개의 값이 존재하면 1,000가지 조합이 생길 수 있습니다. 실제 헤더의 카디널리티(값의 다양성)는 이보다 훨씬 클 수 있습니다. `User-Agent` 값은 매우 다양하고, 쿠키는 방문자별로 고유할 수 있으며, 선호도 헤더는 순서, 포맷(공백과 탭도 중요합니다!), 품질 값(quality value)에 따라 얼마든지 달라질 수 있습니다.

결과적으로 완벽하게 정확하지만 거의 영구적으로 콜드(재사용되지 않는 엔트리)한 캐시가 만들어집니다. 동일한 응답들이 트래픽이 너무 적어 핫 상태를 유지하지 못하는 여러 엔트리로 흩어지게 됩니다. 이런 엔트리들은 캐시 용량을 소모하고 서로를 밀어내며(evict) 캐시 적중률을 낮추고, 더 많은 요청을 오리진으로 되돌려 보냅니다. 축출(eviction)은 콜드 엔트리를 제거할 수는 있어도, 단지 응답이 동일하다는 이유만으로 여러 엔트리를 병합해주지는 않습니다.

Cloudflare가 인기 사이트 약 5만 곳에서 1억 2천만 건 이상의 응답을 분석한 결과, 약 3,000개 사이트가 네 개 이상의 필드에 대해 `Vary`를 사용하고 있었고, 일부는 10개, 23개, 심지어 47개 필드에 걸쳐 변형을 만들고 있었습니다.

물론 카디널리티가 높은 변형이 의도적인 경우도 있습니다. CDN이나 리버스 프록시가 지리적 지역 같은 값을 주입해 콘텐츠를 예측 가능한 방식으로 분할하는 경우가 그렇습니다. 가능한 값이 통제되어 있고 모든 구성 요소가 그 의미에 동의한다면 이런 방식은 잘 작동합니다. 하지만 이런 제약이 없다면 캐시는 다시는 재사용되지 못할 변형들로 쪼개져 버립니다.

이것이 바로 Cloudflare가 `Vary` 지원을 설계하면서 풀어야 했던 문제입니다. 올바른 응답을 서빙하는 데 필요한 만큼의 변형은 유지하면서, 요청 간의 우발적인 차이가 캐시 효율을 망가뜨리지 않도록 해야 했습니다.

## Cache Rules로 Vary 다루기

Cloudflare 고객들은 이미 `Vary`와 유사한 콘텐츠 협상(negotiation)을 처리할 여러 방법을 갖고 있었습니다. 캐시를 우회하고 오리진에 맡기거나, 커스텀 캐시 키나 다른 룰로 오리진의 협상 로직을 재현하거나, Worker를 사용하거나, 이미지 전용의 Vary for images 같은 기능을 쓸 수 있었습니다. 이런 옵션들은 여전히 유용하지만, 캐싱 자체를 포기하거나, 애플리케이션 로직을 중복 구현해야 하거나, 추가 코드를 작성해야 하거나, 좁은 사용 사례만 다룬다는 한계가 있었습니다.

Cache Rules의 `Vary` 지원은 이 결정을 두 단계로 나눠서 이 공백을 메꿉니다.

- 오리진은 `Vary`를 통해 응답에 영향을 줄 수 있는 요청 헤더를 지정합니다.
- Cache Rule은 각 헤더의 값을 Cloudflare가 어떻게 처리할지 결정합니다.

Cache Rule이 있다고 해서 모든 응답이 강제로 변형되는 것은 아닙니다. 오리진이 `Vary`를 반환하지 않으면 Cloudflare는 평소처럼 응답을 캐싱합니다(다만 룰이 오리진에 요청을 전달하기 전에 `Accept`나 `Accept-Language`를 재작성할 수는 있습니다). 오리진이 `Vary`를 반환하면 Cloudflare는 그 헤더에 설정된 액션을 사용합니다. 개별 설정이 없는 헤더는 룰의 기본 액션을 따릅니다.

사용 가능한 액션은 세 가지입니다.

| 액션 | Cloudflare가 하는 일 | 적합한 경우 |
|---|---|---|
| **normalize** | 캐시된 변형을 선택하기 전에 요청 헤더를 정규화해, 동등한 요청들이 같은 캐시 응답을 공유하도록 돕습니다. `Accept`, `Accept-Language`, `Accept-Encoding`에는 헤더별 규칙을 적용하고, 그 외 헤더는 선택적 공백을 제거하고 반복된 헤더 라인을 원래 순서대로 합치되 대소문자와 내부 공백은 보존합니다. | 다수의 요청 값이 소수의 응답 집합으로 수렴하는 협상 헤더에 적용할 기본 시작점으로 권장됩니다. |
| **passthrough** | 요청 헤더의 원시 바이트(대소문자, 공백, 순서, 중복 값 포함)를 그대로 캐시 매칭에 사용합니다. 헤더가 여러 줄에 걸쳐 있으면 순서대로 콤마로 합쳐 매칭에 사용하며, 실제로 나가는 헤더 라인 자체는 바꾸지 않습니다. `Respect Strong ETags`가 꺼져 있으면 Cloudflare가 `Accept-Encoding`은 여전히 재작성할 수 있습니다. | 값의 범위는 통제되어 있지만 정확한 값이 응답을 바꾸는 헤더에 사용합니다. |
| **bypass** | 오리진이 해당 헤더를 `Vary`로 지정하면 응답 자체를 저장하지 않습니다. 기존 캐시 엔트리는 자동으로 제거되지 않으므로, 필요하면 직접 퍼지(purge)해야 합니다. | `Cookie`나 `User-Agent`처럼 개인화되어 있거나 카디널리티가 높거나 예측 불가능한 헤더에 사용합니다. |

Cloudflare는 기본값으로 **normalize**를 권장합니다. 개인화되어 있거나 범위가 무한한 값을 갖는 개별 헤더에는 **bypass**를, 정확한 값이 응답을 바꾸는 경우에는 **passthrough**를 사용하면 됩니다.

예를 들어 오리진이 동등하게 취급하는 값이라도, `passthrough`는 대소문자·공백·순서·중복 값의 차이를 그대로 보존합니다. `Vary: X-View`에 `passthrough`를 적용하면 다음 세 값은 각각 별도의 캐시 키를 만듭니다.

```
X-View: compact,full
X-View: Compact,full
X-View: compact, full
```

이렇듯 사소한 변형만으로도 재사용 가능한 응답이 캐시 안에서 수많은 일회성 변형으로 쪼개질 수 있습니다.

어떤 액션을 설정하든 `Vary: *`는 항상 캐시를 우회합니다. 이는 요청의 어떤 측면이든, 심지어 HTTP 메시지 밖의 정보(예: 클라이언트 IP 주소)까지도 응답 선택에 영향을 줄 수 있다는 뜻이기 때문에, Cloudflare는 오리진에 다시 문의하지 않고서는 이후 요청에 응답을 재사용할 수 없습니다.

## 캐시를 통과하는 요청의 흐름

앞서 나온 `/catalog` 요청 하나가 Cloudflare를 어떻게 통과하는지 따라가 보겠습니다.

첫 요청에서는 Cloudflare가 해당 리소스에 대해 저장해둔 `Vary` 데이터가 없으므로 캐시 조회는 미스가 납니다. 매칭되는 Cache Rule은 Cloudflare가 오리진에 연결하기 전에 설정된 필드를 정규화할 수 있는데, 이는 응답에 `Vary`가 포함될지 아직 알 수 없는 시점에도 일어납니다. Cache Rule은 허용되는 정규화 방식을 정의할 뿐이고, 실제로 그 필드가 캐시된 변형의 일부가 될지는 이후 응답이 결정합니다.

이 순서가 중요합니다. 만약 Cloudflare가 여러 원시 값을 하나의 정규화된 캐시 키 아래로 묶으면서도 오리진에는 여전히 원시 값을 그대로 전달한다면, 오리진이 서로 다른 응답을 만들어낼 수 있는데 캐시는 나중에 이 응답들을 같은 것으로 취급하게 됩니다. 정규화된 값을 오리진에도 전달함으로써 오리진의 선택과 캐시 매칭을 일치시키는 것입니다.

오리진이 다음과 같이 응답한다고 해보겠습니다.

```
Vary: Accept, Accept-Language
```

Cloudflare는 이 헤더 이름들을 기록하고 응답을 캐시된 변형으로 저장합니다. Cache Rule에 따라 처리된 헤더 값들이 같은 리소스에 대한 다른 변형들과 이 변형을 구분해줍니다.

`/catalog`에 대한 또 다른 요청이 들어오면, Cloudflare는 리소스의 기본 캐시 키(대개 URL과 그 외 설정된 키 필드)에서 시작합니다. 그런 다음 저장해둔 `Vary` 필드를 읽고, 새 요청의 해당 헤더에 Cache Rule을 적용해 일치하는 캐시된 변형을 찾습니다.

예를 들어 이 헤더들이 다음처럼 정규화된다고 해보겠습니다.

```
Accept: text/html
Accept-Language: en,fr
```

Cloudflare는 이 값들을 이용해 일치하는 캐시 변형을 바로 조회합니다. 저장된 변형들을 하나하나 순회하며 비교하지 않습니다.

일치하는 변형이 있고 신선(fresh)하면 캐시 히트가 됩니다. 그렇지 않다면 Cloudflare는 요청을 오리진으로 보내고, 결과 응답을 또 다른 변형으로 저장할 수 있습니다.

오리진 응답이 이 순환을 마무리합니다. `Vary`에 지정된 각 헤더에 대해, Cloudflare는 해당 헤더에 설정된 액션(설정이 없으면 룰의 기본 액션)을 사용합니다.

- `Vary`가 없으면 Cloudflare는 정상적으로 캐싱합니다.
- 지정된 모든 헤더가 normalize나 passthrough로 처리되면 Cloudflare는 응답을 캐시된 변형으로 저장할 수 있습니다.
- 지정된 필드 중 하나라도 bypass로 처리되면 Cloudflare는 응답을 저장하지 않습니다.
- 응답에 `Vary: *`가 있으면 Cloudflare는 저장하지 않습니다.

여기서 오리진에게 중요한 책임이 생깁니다. 요청 필드에 따라 달라질 수 있는 모든 캐시 가능 응답은 오류 응답이나 폴백 응답을 포함해 일관되게 적절한 `Vary` 헤더를 반환해야 합니다. 만약 어떤 응답 하나가 이를 빠뜨리면, Cloudflare는 변형을 격리하는 데 필요한 정보 없이 그 응답을 캐싱해버릴 수 있습니다.

퍼지(purge) 대상이 캐시된 리소스라면, 해당 리소스의 모든 `Vary` 변형이 함께 퍼지됩니다. 커스텀 캐시 키에 대한 기존 퍼지 요구사항도 그대로 적용됩니다.

`Vary` 설정을 바꾼다고 해서 기존 콘텐츠가 자동으로 퍼지되지는 않습니다. 새로운 정책은 다른 캐시 키를 만들어낼 수 있으므로, 요청은 새 키로 미스가 나고 다시 채워지는 반면, 기존 엔트리는 만료되거나 직접 퍼지될 때까지 그대로 남아있습니다.

## 정규화로 동등한 요청 묶기

앞서 살펴본 영어·프랑스어 요청 예시를 다시 떠올려 보겠습니다.

```
Accept-Language: en-US, fr;q=0.8
Accept-Language: fr;q=0.8, en-GB
```

두 요청 모두 실제로는 영어를 선호합니다. `passthrough`를 사용하면 순서와 언어 태그의 차이 때문에 이 둘을 서로 다른 변형으로 취급하지만, `normalize`를 사용하면 `Accept-Language`에 적용되는 헤더별 규칙에 따라 두 요청을 오리진이 실제로 지원하는 응답 집합에 맞춰 동일한 캐시 변형으로 수렴시킬 수 있습니다. 오리진이 지원하는 언어가 영어, 프랑스어, 독일어뿐이라면, 표기나 순서가 제각각인 수많은 `Accept-Language` 값들이 세 개의 캐시 변형으로 정리되는 셈입니다.

## 정리

- `Vary`는 캐시에게 "어떤 요청 필드가 응답에 영향을 줄 수 있는지"만 알려줄 뿐, "그 차이가 실제로 의미 있는지"는 알려주지 않습니다. 이 때문에 원시 헤더 값을 그대로 비교하면 동일한 응답이 수많은 별개 변형으로 쪼개져 캐시 적중률이 떨어지는 문제가 생깁니다.
- Cloudflare 분석에 따르면 약 5만 개 사이트 중 3,000개 사이트가 네 개 이상의 필드에 대해 `Vary`를 사용했고, 일부는 최대 47개 필드에 걸쳐 변형을 만들고 있어 카디널리티 폭증 문제가 실제로 광범위하다는 것을 보여줍니다.
- Cloudflare는 Cache Rules를 통해 `Vary`가 지정한 각 헤더에 대해 normalize(협상 헤더 정규화, 기본 권장), passthrough(정확한 값 보존), bypass(개인화·고카디널리티 헤더 제외) 세 가지 액션을 선택할 수 있게 했습니다. 오리진은 "무엇이 달라질 수 있는지"를 선언하고, 개발자는 "그 변형이 캐시 입장에서 얼마나 의미 있는지"를 결정하는 구조입니다.
- `Vary: *`는 어떤 액션을 설정하든 항상 캐시를 우회하며, 오리진은 캐시 가능한 모든 응답(오류·폴백 포함)에서 `Vary` 헤더를 일관되
