## 핵심 개념

> [!abstract]
> Theo는 T3 Code 앱에서 노트북이 과열될 정도로 GPU 프로세스가 20%까지 치솟는 문제를 발견하고, GPT-5.6과 Fable에게 원인 분석과 수정을 맡겼습니다. 에이전트는 그럴듯한 진단과 함께 1만 줄 넘는 리팩터링 PR을 만들었지만 실제 성능은 전혀 개선되지 않았고, 결국 크롬 작업 관리자로 탭을 격리하며 직접 디버깅해야 했습니다. 브라우저 내장 성능 도구조차 CSS/GPU 레이어 문제 앞에서는 무용지물이었다는 점이 핵심 교훈입니다.

## 아티클

# 왜 T3 Code는 GPU를 20%나 잡아먹었을까? AI 에이전트가 풀지 못한 웹 성능 버그의 정체

Theo가 최근 T3 Code 프로젝트에서 겪은 실제 디버깅 경험을 공유했습니다. GPT-5.6, Fable 같은 강력한 코딩 에이전트를 총동원했지만, 결국 문제의 원인은 에이전트 스스로 찾지 못했고, 개발자가 직접 브라우저 도구를 파고들어야 풀렸던 사례입니다. 이 글에서는 그 과정에서 드러난 "에이전트가 이해하지 못하는 성능 문제"의 실체와, AI 도구가 오히려 문제를 더 키웠던 상황을 정리합니다.

## 문제의 발단: 노트북이 뜨거워졌다

Theo는 최근 며칠간 T3 Code로 굉장히 많은 작업을 처리했습니다. Fable 사용량을 마감 전에 최대한 뽑아내려는 목적도 있었고, 컨퍼런스 일정 사이 잠깐 생긴 자유 시간에 여러 프로젝트(T3 Code, LakeBed 등)에 걸쳐 수십 개의 PR을 동시에 굴리고 있었습니다.

집 데스크에서 모니터를 연결해 작업할 때는 별문제가 없었는데, Moonlight로 데스크톱 게임을 노트북에 스트리밍하면서(120fps, 10기가비트 네트워크) 동시에 노트북에서 에이전틱 코딩을 돌리자 키보드가 뜨거워지기 시작했습니다. Moonlight와 Sunshine 설정을 아무리 손봐도 발열이 잡히지 않았고, 다음 날 아침에도 컴퓨터는 여전히 뜨거운 상태였습니다.

## 범인은 브라우저였다

Fable과 GPT-5.6을 이용해 문제를 추적한 결과, 원인은 브라우저 프로세스였습니다. Theo는 평소 T3 Code를 브라우저를 통해 다른 머신을 제어하는 방식으로 사용하는데, 보통 T3 Code 성능 이슈는 자체 JavaScript 백엔드(웹소켓 서버)가 아니라 Claude Code, Codex 같은 하네스가 메모리를 비효율적으로 쓰는 데서 발생했습니다. 하지만 이번엔 그 하네스들이 전부 네트워크상의 다른 머신에서 돌고 있었기 때문에 자신의 컴퓨터에 이 정도 부하를 줄 이유가 없었습니다.

여기서 중요한 힌트가 하나 나옵니다. **브라우저 내장 성능 도구가 전혀 도움이 되지 않았다**는 점입니다. 크롬 DevTools 등의 성능 도구는 JavaScript가 불필요하게 실행되거나, 로드 시간이 느리거나, 리소스가 제대로 안 들어오는 문제를 잡는 데 최적화되어 있습니다. 하지만 문제가 CSS 레이어로 넘어가면 이런 도구들의 유용성이 급격히 떨어집니다. T3 Code의 브라우저 도구를 아무리 들여다봐도 이 정도로 성능이 나쁠 이유를 찾을 수 없었고, 실제 탭 조작이나 내비게이션은 여전히 쾌적했습니다. 그런데도 GPU 프로세스는 계속 갈려나가고 있었습니다.

문제는 크롬 작업 관리자가 탭별로 분리되지 않는다는 점이었습니다. 브라우저 전체의 리소스만 보여주기 때문에 어느 탭이 문제인지 특정할 수 없었습니다. 그래서 Theo는 평소 안 쓰는 크롬 브라우저를 켜서 T3 Code 탭 하나만 열어두고 검증했습니다. 실제로 구글닷컴 같은 다른 페이지로 이동하면 GPU 프로세스 사용률이 18% 이상에서(큰 모니터에서는 40% 이상) 3% 수준으로 뚝 떨어졌습니다. T3 Code 탭 자체가 문제라는 게 명확해진 순간입니다.

## 에이전트에게 맡겼더니 벌어진 일

문제를 확인한 뒤 Theo는 평소 방식대로 Codex에게 아주 모호한 설명만 던지고 뭘 해내는지 지켜봤습니다. Codex는 다음과 같이 그럴듯한 진단을 내놓았습니다.

> T3 Code의 웹 UI는 지속적인 CPU 부하와 노트북 발열을 유발할 수 있다. 실시간 크롬 프로파일링 결과 웹소켓 기반의 메인 스레드 스톨(stall)이 발견되었고, 소스 분석 결과 여러 개의 곱셈적(multiplicative) 경로들이 활성 에이전트 스트림을 지속적인 디코딩, 히스토리 스캔, 상태 재작성, 퍼시스턴스, 시간 계산, 하이라이팅으로 전환시킬 수 있다.

그럴듯해 보였기 때문에 Theo는 늘 하던 대로 에이전트에게 "만들고 테스트하고 고쳐보라"고 지시했습니다. 에이전트는 자신 있게 문제를 해결했다고 보고했고, 네트워크 레이어와 React 상태 업데이트 트리거 방식을 중심으로 1만 줄이 넘는 대규모 리팩터링 PR을 만들어냈습니다.

결과는 완전한 실패였습니다. 실제 사용해보니 자신의 머신에서 체감 성능은 전혀 개선되지 않았습니다. 1만 줄짜리 코드 변경이 통째로 무의미했던 셈입니다. 여기서 Theo는 "이건 힘든 여정이 되겠구나"를 직감하고, 직접 크롬을 열어 문제를 분리해나가는 수작업 디버깅에 들어갔습니다.

## 작업 관리자로 GPU 프로세스를 추적하다

크롬 작업 관리자로 레이어별 문제 지점을 좁혀나가던 중, 브라우저 섹션에서 GPU 프로세스가 비정상적으로 많은 리소스를 쓰고 있다는 걸 발견했습니다. 심지어 해당 탭 자체는 1~4% 수준의 사용률만 보이는데, 브라우저 전체는 낮은 해상도에서도 GPU를 최대 20%까지 끌어다 쓰고 있었습니다.

Theo는 AI가 등장하기 훨씬 전부터 이런 디버깅을 해온 경력이 있었기에, 높은 프레임레이트(120fps, 5K 디스플레이)에서 트리거되는 요소들이 의심스럽다는 직감이 있었습니다. 그래서 에이전트에게 코드베이스 전체를 뒤져서 렌더링이나 업데이트를 트리거하면서 GPU 부하를 조금이라도 유발할 수 있는 모든 지점을 찾아달라고 요청했습니다.

이 과정에서 크롬 프로파일링 결과를 Gemini AI 요약 기능에 넣어봤지만, 이 역시 별 도움이 되지 않았습니다. 스크립팅, 스타일, 레이아웃, 프레임워크 관련 시간이 모두 아주 적은 비중으로 나온다는 식의 결과만 나왔고, 실제 문제와는 거리가 멀었습니다.

(원문 트랜스크립트는 이 지점에서 끊겨 있으며, Theo가 예고한 "결국 원인은 내장 Tailwind 클래스 하나였다"는 최종 결론과 구체적인 수정 내용은 이후 영상 분량에서 다뤄질 것으로 보입니다.)

## 정리

- **AI 코딩 에이전트는 "그럴듯한 진단"과 "실제로 맞는 진단"을 구분하지 못했습니다.** Codex는 웹소켓 스톨, 상태 재작성 등 정교해 보이는 원인을 제시하고 1만 줄 넘는 리팩터링까지 해냈지만, 실제 성능 문제와는 무관했습니다.
- **브라우저 내장 성능 도구는 CSS/GPU 레이어 문제에 취약합니다.** DevTools는 JavaScript 실행이나 리소스 로딩 문제를 잡는 데는 강하지만, 렌더링이 CSS 레이어로 오프로드된 이후의 문제는 잘 드러내지 못했습니다.
- **탭별 GPU/CPU 사용량을 확인하려면 브라우저를 격리해야 했습니다.** 크롬 작업 관리자는 탭 단위로 분리되지 않기 때문에, 문제 탭만 남긴 별도 브라우저 인스턴스를 띄워 검증하는 수작업이 필요했습니다.
- **경력에서 나온 직감이 결정적이었습니다.** 고주사율 디스플레이(120fps, 5K)에서 GPU 부하가 튀는 패턴은 AI 이전 시대부터 성능 디버깅을 해온 경험이 있었기에 의심할 수 있었던 지점입니다.
- **실무 시사점**: 에이전트에게 성능 최적화를 맡길 때는 "동작했다"는 보고를 곧이곧대로 믿지 말고, 실제 사용자 환경(고해상도 디스플레이, 고주사율)에서 작업 관리자나 GPU 프로파일러로 직접 검증하는 과정이 여전히 필요합니다.
