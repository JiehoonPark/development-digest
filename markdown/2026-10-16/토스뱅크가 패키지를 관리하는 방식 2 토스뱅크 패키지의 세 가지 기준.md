## 핵심 개념

> [!abstract]
> 토스뱅크 기술그룹은 여러 서비스가 공유하는 패키지에서 발생하던 호환성 확인 부담과 디버깅 어려움을 해결하기 위해 세 가지 기준을 세웠습니다. 호스트가 지원하는 환경에서 안정적으로 동작할 것, 배포 후에도 원본 문법과 모듈 구조가 유지될 것, 사용처에서 원본 코드를 쉽게 확인할 수 있을 것이 그것입니다. 이를 위해 문법 변환과 최종 번들링은 호스트에 맡기고, 패키지는 TypeScript를 JavaScript로 변환하는 역할만 담당하도록 책임을 나눴습니다.

## 아티클

토스뱅크에서는 여러 서비스가 공통으로 사용하는 패키지를 운영하면서, 패키지를 사용하는 쪽(호스트)이 매번 브라우저 지원 범위와 API 호환성을 직접 확인해야 하는 문제를 겪었습니다. 패키지의 원본 소스 코드를 확인하기 어려운 점도 걸림돌이었는데요. 이 글에서는 토스뱅크 기술그룹이 이 문제를 풀기 위해 세운 세 가지 패키지 기준과, 그 기준을 지키기 위해 선택한 접근 방식을 소개합니다.

## 왜 기준이 필요했나

패키지를 사용하는 각 서비스는 저마다 지원해야 하는 브라우저와 런타임이 다릅니다. 그래서 호스트 쪽에서는 패키지가 어떤 문법까지 쓰는지, 패키지 개발 중 사용한 API가 실제 서비스 환경에서도 동작하는지를 따로 확인해야 했습니다. 게다가 패키지의 원본 코드를 들여다보기 어려워서, 문제가 생겨도 원인을 추적하기 힘들었습니다.

토스뱅크 기술그룹은 이 문제를 해결하기 위해 패키지가 반드시 갖춰야 할 기준 세 가지를 정하고, 각 기준을 충족하는 데 필요한 조건을 분석한 뒤 그에 맞는 빌드 도구와 설정을 선택했습니다.

## 기준 1. 호스트가 지원하는 실행 환경에서 안정적으로 동작해야 한다

토스뱅크의 각 서비스는 자신의 지원 범위에 맞춰 패키지를 항상 트랜스파일합니다. 그렇다면 패키지에서 최신 문법을 자유롭게 써도 호스트 런타임에서 문제없이 동작한다고 보장할 수 있을까요? 실제로는 두 가지를 따로 확인해야 합니다.

**문법**은 호스트의 트랜스파일러가 해당 변환을 지원해야 하고, **API**는 실행 환경이 직접 제공하거나 폴리필로 채워줘야 합니다.

문법 변환에는 도구 자체의 한계가 있습니다. 예를 들어 rolldown의 문법 변환 관련 이슈에서는, 당시 oxc가 ES2025의 일부 정규식 문법을 구형 환경용으로 변환하지 못한다는 점이 지적된 적이 있습니다. 즉, 최종 호스트가 아무리 낮은 target을 지정해도 도구가 지원하지 않는 변환까지는 수행되지 않습니다.

폴리필에도 한계가 있습니다. 예를 들어 `Proxy`는 이를 지원하지 않는 엔진에서 폴리필만으로는 전체 동작을 구현할 수 없습니다. 폴리필 라이브러리를 추가한다고 해서 모든 API를 쓸 수 있게 되는 건 아니라는 뜻입니다.

결국 문법은 호스트의 변환 도구가 실제로 처리할 수 있는지, API는 대상 브라우저 혹은 호스트의 폴리필이 제공할 수 있는지를 각각 따져봐야 합니다. 트랜스파일링 자체는 호스트에 맡기더라도, 호환성 문제는 패키지 개발 단계에서 미리 점검해야 합니다. 이를 위해 토스뱅크는 호스트의 API 지원 범위를 타입 검사에 반영했습니다. 다만 TypeScript 설정만으로 호환성을 전부 보장할 수는 없기 때문에, 실제 API 지원 여부와 필요한 문법 변환 가능 여부는 별도로 확인해야 합니다.

## 기준 2. 배포 후에도 원본 코드의 의도가 유지되어야 한다

호스트는 각자의 실행 환경에 맞춰 패키지 코드를 변환하고 번들링합니다. 토스뱅크는 이 작업을 호스트에 맡기고, 패키지 빌드 단계에서는 원본의 문법과 모듈 구조를 최대한 그대로 유지하기로 했습니다.

### 문법 변환은 호스트에 맡긴다

패키지를 사용하는 서비스마다 지원 브라우저와 런타임이 다르기 때문에, 같은 패키지 코드라도 호스트에 따라 필요한 문법 변환이 달라질 수 있습니다.

예를 들어 `user?.name`을 Optional Chaining을 지원하지 않는 환경에 맞춰 변환하면 다음처럼 바뀝니다.

```js
const name = user === null || user === void 0 ? void 0 : user.name;
```

이 상태로 패키지를 배포하면, Optional Chaining을 지원하는 호스트까지 변환된 코드를 그대로 받게 됩니다. 문법에 따라서는 호환성을 위한 추가 함수까지 포함되기도 합니다. 즉 패키지 쪽에서 미리 문법을 낮춰버리면 호스트에 불필요한 코드가 섞여 들어가고, 원본과 결과물의 차이도 점점 커집니다.

그래서 토스뱅크는 패키지의 JavaScript 문법을 원본 그대로 유지하고, 실행 환경에 맞춘 문법 변환은 호스트가 자신의 지원 범위에 맞춰 직접 적용하도록 역할을 나눴습니다.

### 모듈 구조도 유지해서 전달한다

패키지를 빌드할 때 미리 번들링해버리면, 원본에서 나눠 둔 파일 경계가 달라질 수 있습니다. 프레임워크가 파일 단위로 코드를 처리하는 경우에는 이 경계 변화가 실제 동작에까지 영향을 줍니다.

대표적인 예가 Next.js App Router입니다. 여기서는 `'use client'`를 선언한 파일이 클라이언트 코드의 경계가 됩니다. `'use client'`가 선언된 `Counter.tsx`와 선언이 없는 `formatPrice.ts`가 분리돼 있다면, Server Component에서도 `formatPrice`를 가져와 호출할 수 있습니다. 하지만 두 파일을 하나로 번들링하면서 전체에 `'use client'`를 적용해버리면, `formatPrice`도 클라이언트 코드로 취급돼 더 이상 같은 방식으로 호출할 수 없게 됩니다.

번들링 과정에서도 이런 경계를 유지하는 것 자체는 가능하지만, 패키지 빌드에서 파일별 지시문의 적용 범위까지 고려하고 이를 위한 설정을 별도로 관리해야 합니다.

그래서 토스뱅크는 원본의 모듈 구조를 그대로 유지한 채 배포하기로 했습니다. 패키지 빌드 단계에서는 TypeScript를 JavaScript로 변환하는 것까지만 담당하고, 파일별 지시문과 모듈 경계를 해석하는 일, 그리고 최종 번들링은 호스트에 맡겼습니다.

## 기준 3. 사용처에서 쉽게 디버깅할 수 있어야 한다

패키지가 예상과 다르게 동작할 때, 사용하는 서비스 쪽에서도 원인을 스스로 파악할 수 있어야 합니다. 함수가 어떤 조건에서 오류를 던지는지, 옵션을 생략했을 때 어떻게 동작하는지 같은 세부 사항은 타입 선언과 문서만으로는 파악하기 어려운 경우가 많습니다.

이럴 때 가장 빠른 방법은 원본 코드를 직접 확인하는 것입니다. 그래서 토스뱅크는 에디터에서 패키지의 원본 코드를 바로 열어볼 수 있도록 **declaration sourcemap**을 지원하기로 했습니다.

declaration sourcemap은 `.d.ts`의 각 타입 선언을 원본 소스 코드의 해당 위치와 연결해 주는 파일입니다. 이 sourcemap 파일과 원본 소스 파일을 설치된 패키지에 함께 포함시키면, 사용하는 쪽에서도 IDE에서 클릭 한 번으로 `.d.ts` 선언 대신 실제 구현 코드를 바로 확인할 수 있습니다.

## 정리

토스뱅크 기술그룹은 패키지를 만드는 쪽과 사용하는 쪽의 역할을 명확히 나누기 위해 세 가지 기준을 세웠습니다.

- **안정성**: 패키지가 쓰는 문법과 API는 호스트의 트랜스파일러와 폴리필이 실제로 처리할 수 있는지 사전에 확인해야 합니다. 트랜스파일링 자체는 호스트에 맡기더라도, 호환성 검증은 패키지 개발 단계에서 미리 해야 합니다.
- **예측 가능성**: 패키지 빌드에서는 문법과 모듈 구조를 원본 그대로 유지하고, 실행 환경에 맞춘 문법 변환과 최종 번들링은 호스트가 담당하도록 했습니다. 이렇게 하면 `'use client'` 같은 파일 단위 지시문의 경계도 깨지지 않고, 호스트에 불필요한 변환 코드가 섞여 들어가는 것도 막을 수 있습니다.
- **디버깅 편의성**: declaration sourcemap과 원본 소스 파일을 함께 배포해, 사용하는 쪽에서 타입 선언이 아닌 실제 구현 코드를 바로 확인할 수 있게 했습니다.

이 세 가지 기준 덕분에 토스뱅크는 빌드 도구와 설정을 고를 때마다 "어떤 변환이 필요하고 어떤 파일을 제공해야 하는가"를 일관된 잣대로 판단할 수 있게 됐습니다. 여러 서비스가 패키지를 공유하는 조직이라면, 트랜스파일링과 번들링의 책임을 패키지와 호스트 중 어느 쪽에 둘지 명확히 정하는 것만으로도 호환성 문제와 디버깅 비용을 크게 줄일 수 있다는 점이 이 사례의 핵심입니다.
