## 핵심 개념

> [!abstract]
> macOS Sequoia 이후 반복적으로 뜨는 '로컬 네트워크에서 기기 찾기 허용' 팝업은 Chromium 브라우저의 임시 경로 복사, 버전별 설치 경로, 잘못된 귀속 등으로 인해 권한 결정이 제대로 기억되지 않아 발생합니다. dontallow는 Accessibility API로 이 팝업을 감지해 자동으로 '허용 안 함'을 눌러주는 경량 Swift 에이전트로, 필요한 앱은 일시정지나 허용 목록으로 예외 처리할 수 있습니다. MDM 환경에서는 PPPC 프로파일로 Accessibility 권한을 사전 부여해 조직 전체에 배포할 수도 있습니다.

## 아티클

macOS Sequoia부터 등장한 "로컬 네트워크에서 기기를 찾도록 허용하시겠습니까?" 팝업은 한 번 설정하면 기억되어야 정상이지만, 실제로는 같은 앱에서 매번 다시 뜨는 경우가 많습니다. 이 문제를 겪던 개발자가 아예 이 팝업을 자동으로 "허용 안 함"으로 처리해주는 작은 macOS 에이전트 `dontallow`를 만들어 Hacker News에 공개했는데요, 왜 이런 현상이 생기는지와 함께 그 구조를 살펴보겠습니다.

## 왜 로컬 네트워크 팝업이 계속 뜨는가

macOS는 앱이 처음 로컬 네트워크에 접근할 때 이 권한 팝업을 띄우고, 사용자의 선택을 기억해야 합니다. 하지만 다음과 같은 이유로 그 "기억"이 제대로 작동하지 않는 경우가 흔합니다.

- **Chromium 계열 브라우저(Chrome, Brave, Edge, Island, Arc)**는 실행할 때마다 앱 번들 자체를 임시 폴더의 랜덤 경로로 복사합니다. 코드 서명을 그대로 유지하면서 인플레이스 업데이트를 지원하기 위한 방식인데, macOS는 로컬 네트워크 권한 결정을 이 랜덤 경로에 연동시킵니다. 결과적으로 다음 실행 시에는 완전히 새로운 앱으로 인식되어 다시 팝업이 뜨고, 개인정보 보호 설정에는 더 이상 아무것도 가리키지 않는 중복된 "Google Chrome.app" 항목이 계속 쌓입니다.
- **버전별 설치 경로를 쓰는 앱**(`.../versions/1.2.3/` 형태)도 업데이트할 때마다 새로운 항목이 생깁니다.
- **잘못된 귀속(misattribution)** 문제도 있습니다. macOS가 "책임자"로 판단한 앱에 팝업을 고정시키다 보니, 실제로는 실행 중이지도 않은 앱에 대해 팝업이 뜨기도 합니다.

물론 이 권한이 실제로 필요한 경우도 있습니다. 브라우저나 미디어 플레이어의 Chromecast/AirPlay 탐색, 게임의 LAN 멀티플레이어, 프린터·스캐너 유틸리티 등이 대표적입니다. 이런 기능을 쓴다면 해당 순간에만 허용하면 되고, 앱의 경로가 안정적이기만 하면 그 선택은 계속 유지됩니다. 반대로 그 기능을 전혀 쓰지 않는다면 애초에 물어볼 필요도 없는 셈입니다.

문제는 이 목록을 정리할 공식적인 방법이 없다는 점입니다. MDM으로 권한을 미리 거부하도록 설정할 수도 없고, `tccutil reset`도 이 항목을 건드리지 못합니다. 그래서 나온 해결책이 사용자 대신 매번 "아니오"를 눌러주는 작은 에이전트, `dontallow`입니다.

## 설치와 기본 동작

설치는 Homebrew 또는 직접 빌드 두 가지 방법을 지원합니다.

```
brew install johncassil/tap/dontallow # or: make && make install
dontallow install
```

`dontallow install`을 실행하면 사용자별 launchd 에이전트를 생성하고 바로 시작한 뒤, 시스템 설정의 개인정보 보호 및 보안 > 손쉬운 사용 화면을 자동으로 열어줍니다. 만약 macOS가 자동으로 권한 요청 창을 띄우지 않으면, 추가해야 할 정확한 경로를 터미널에 출력해줍니다. 여기서 "손쉬운 사용(Accessibility)" 권한이 필요한 이유는, 이 권한이 있어야 에이전트가 팝업의 버튼을 실제로 누를 수 있기 때문입니다. 설치 과정은 권한이 부여될 때까지 대기한 뒤 에이전트가 정상 작동 중임을 확인해줍니다. 권한이 빠져 있으면 `dontallow status` 명령으로 언제든 다시 안내를 받을 수 있습니다.

## 사용 가능한 명령어

| 명령 | 동작 |
|---|---|
| `dontallow status` | 에이전트 상태, 일시정지 상태, 허용 목록, 최근 닫힌 팝업 내역 표시 |
| `dontallow pause [1h]` | 일정 시간 동안 팝업을 건드리지 않음 (30m, 2h, 1d, forever) |
| `dontallow resume` | 다시 자동으로 닫기 시작 |
| `dontallow rules` | 시스템의 로컬 네트워크 규칙 저장소를 해석해, 각 개인정보 보호 항목이 실제로 무엇인지(고아 항목 포함) 보여줌 |
| `dontallow uninstall` | 에이전트 중지 및 제거 |
| `dontallow run --dry-run` | 포그라운드에서 동작을 로그로만 남기고 실제 클릭은 하지 않음 |

팝업을 닫을 때마다 해당 앱 이름과 일시정지 명령어를 알려주는 알림이 뜨기 때문에, 끄는 방법을 따로 외워둘 필요는 없습니다. 알림 자체가 거슬린다면 시스템 설정에서 음소거할 수 있습니다.

## 실제로 권한이 필요한 앱을 다룰 때

앱이 정말로 로컬 네트워크 접근이 필요한 상황이라면 세 가지 방법 중 하나를 선택하면 됩니다.

1. `dontallow pause 10m`으로 잠시 멈춘 뒤, 앱을 실행해 직접 "허용"을 클릭합니다.
2. `~/.config/dontallow/allowlist` 파일에 앱 이름을 한 줄씩 추가합니다(대소문자 구분 없는 부분 일치). 목록에 포함된 앱의 팝업은 아예 건드리지 않습니다.
3. 시스템 설정 > 개인정보 보호 및 보안 > 로컬 네트워크에서 직접 토글을 켭니다. 참고로 `dontallow`가 닫은 팝업은 "거부"로 기록되므로, 여기서 언제든 되돌릴 수 있습니다.

또한 `~/.config/dontallow/grace`에 초 단위 값을 설정하면, 에이전트가 자동으로 버튼을 누르기 전에 사용자가 직접 클릭할 수 있는 유예 시간을 둘 수 있습니다(기본값 0.25초).

## 동작 원리

이 팝업은 시스템 프로세스인 `UserNotificationCenter`가 소유한 창입니다. `dontallow`는 이 프로세스의 창 생성 이벤트에 대해 Accessibility 옵저버를 등록하고, 이벤트가 발생할 때까지 대기합니다. 창이 뜨면 다이얼로그 텍스트를 읽어 그것이 정말 로컬 네트워크 관련 팝업인지(다른 종류의 팝업이 아닌지) 확인하고, 일시정지 상태와 허용 목록을 체크한 뒤 Accessibility API로 "허용 안 함" 버튼에 대해 press 액션을 수행합니다. 만약 이 press 액션이 거부되면, 버튼 위치를 좌표로 계산해 합성 클릭(synthetic click)으로 대체합니다.

중요한 점은 이 도구가 시스템 파일을 절대 수정하지 않고, 어떤 보호 기능도 비활성화하지 않으며, 한 번도 "허용"을 선택하지 않는다는 점입니다. 오직 "허용 안 함"만 누릅니다.

## 관리형 Mac(기업 환경)에서의 적용

로컬 네트워크 권한은 MDM으로 미리 설정할 수 없지만, Accessibility 권한은 가능합니다. 조직 단위로 배포하려면 바이너리를 한 번 빌드하고 Developer ID로 서명한 뒤, 해당 코드 요구사항(code requirement)에 Accessibility 권한을 부여하는 PPPC(Privacy Preferences Policy Control) 프로파일과 함께 배포하면 됩니다. 이후 각 사용자별로 `dontallow install`만 실행하면 되고, 수동으로 시스템 설정을 건드릴 필요가 없습니다.

## 업그레이드 이후 주의사항

Accessibility 권한 부여는 바이너리의 코드 서명에 연동되는데, `brew upgrade`를 포함한 모든 새 빌드는 새로운 서명을 만들어냅니다. 업그레이드 후에는 `dontallow status`로 상태를 확인하고, 권한이 빠졌다고 나오면 Accessibility 설정에서 기존 `dontallow` 항목을 지운 뒤 출력된 경로로 다시 추가해야 합니다. 그러면 에이전트가 10초 이내에 자동으로 다시 연결됩니다. 향후 Developer ID로 서명된 릴리스가 나오면 이 수동 단계는 사라질 예정입니다.

## 테스트와 호환성

`make test`로 실행하는 단위 테스트는 다이얼로그 텍스트 파싱, 기간·일시정지 파싱, 허용 목록 매칭, launchd plist 생성, 그리고 픽스처 아카이브를 대상으로 한 로컬 네트워크 규칙 디코더 등 순수 로직을 검증합니다. 순정 `swiftc`만으로 빌드되며 Xcode나 SwiftPM이 필요 없습니다. 실제 팝업에 실제로 버튼을 누르는 엔드투엔드 테스트는 Accessibility 권한이 부여된 실제 Mac에서만 확인할 수 있고, 수동 테스트 절차는 `Tests/INTEGRATION.md`에 정리되어 있습니다.

호환성 측면에서는 Apple Command Line Tools만으로 빌드 가능하며(Xcode 불필요), Apple Silicon과 Intel 모두에서 Homebrew가 네이티브로 컴파일합니다. 빌드는 macOS 13 이상에서 가능하지만, 팝업 자체는 macOS 15 Sequoia 이상에서만 존재합니다. 현재까지는 Intel, macOS 26.6 환경에서 테스트되었고, 다른 버전에서의 사용 후기도 환영한다고 밝히고 있습니다. 다만 아직은 영어 로케일 macOS만 지원합니다. 매칭 로직이 다이얼로그 텍스트와 "Don't Allow" 버튼 제목에 의존하기 때문인데, 현지화된 문자열 지원은 계획 중입니다. 라이선스는 MIT입니다.

## 정리

- macOS의 로컬 네트워크 접근 팝업은 Chromium 계열 브라우저의 임시 경로 복사, 버전별 설치 경로, 잘못된 귀속 등의 이유로 "기억"이 제대로 작동하지 않아 반복적으로 등장하는 경우가 많습니다.
- `dontallow`는 Accessibility API를 이용해 이 팝업을 감지하고 자동으로 "허용 안 함"을 눌러주는 경량 Swift 에이전트로, 유휴 시 CPU 사용량이 0이고 재부팅 후에도 유지됩니다.
- 정말 로컬 네트워크 접근이 필요한 앱(Chromecast, AirPlay, LAN 멀티플레이어 등)은 일시정지, 허용 목록, 시스템 설정 토글 세 가지 방법으로 예외 처리할 수 있습니다.
- MDM으로 로컬 네트워크 권한 자체는 사전 설정할 수 없지만, Developer ID 서명과 PPPC 프로파일을 활용하면 조직 단위로 Accessibility 권한을 미리 부여해 수동 설정 단계를 없앨 수 있습니다.
- 바이너리를 업데이트할 때마다 코드 서명이 바뀌어 Accessibility 권한을 다시 등록해야 하는 번거로움이 있으며, 이는 향후 Developer ID 서명 릴리스로 해결될 예정입니다.
