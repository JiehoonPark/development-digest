## 아티클

SVAR 팀은 데이터 그리드, 간트 차트, 캘린더처럼 기능이 많고 무거운 UI 컴포넌트를 만듭니다. 이런 컴포넌트들의 공통점은 하나인데요, 대량의 데이터가 들어와도 빠르고 반응성을 유지해야 한다는 점입니다. 여기에 더해 SVAR는 동일한 컴포넌트를 React, Svelte, Vue 세 프레임워크로 각각 출시하기 때문에, 프레임워크 비교에 대해 꽤 특이한 위치에 서 있습니다. 보통 프레임워크 비교글은 한 프레임워크를 깊이 아는 사람이 나머지 둘은 문서만 훑어보고 쓰는 경우가 많은데, SVAR는 세 프레임워크 모두에서 똑같이 고성능 컴포넌트를 만들어야 했습니다. 조금 무모한 일이지만, 그만큼 배운 것도 많았다고 합니다. 이 글은 그 경험을 공유하면서 "어떤 프레임워크가 더 빠른가"라는 질문에 의도적으로 답하지 않습니다. 놀랍게도 빠른 데이터 그리드를 만드는 데 드는 비용 대부분은 프레임워크와 무관했고, 프레임워크 간 진짜 차이는 흔히 벌어지는 '프레임워크 전쟁'이 암시하는 것보다 훨씬 좁았기 때문입니다.

## 프레임워크를 가리지 않는 성능 문제

데이터 그리드는 이런 비교에 아주 적합한 테스트 케이스입니다. 누구나 한 번쯤 만들어보거나 써본 적이 있고, UI 요소 중에서도 게으른 설계를 가장 빨리 응징하는 컴포넌트이기 때문입니다. 구조 자체는 단순하지만 대부분의 컴포넌트와 달리 데이터량이 압도적입니다. 1,000행은 평범한 수준이고 10,000행도 드물지 않으니, 처음부터 이를 염두에 두고 설계해야 합니다.

실제로 SVAR React DataGrid는 20만 행, 2만 열을 렌더링하는 데모를 제공하는데, 터무니없이 큰 숫자지만 그리드는 이를 부드럽게 처리합니다.

반면 1만 행을 그대로(가상화 없이) 렌더링하면 어떤 프레임워크든 똑같이 무너집니다. 요즘 하드웨어가 워낙 빠르다 보니 완전히 죽기보다는 심하게 느려지는 정도겠지만, 결국 React든 Vue든 Svelte든 브라우저에게 수십만 개의 DOM 노드를 만들고 레이아웃하라고 요청하게 되고, 병목은 브라우저 쪽에서 생깁니다. 이 지점에서는 프레임워크가 거의 의미가 없어집니다. 이 실패 지점은 비용의 서열을 보여줍니다.

1. HTML을 생성(DOM 구성)하는 작업이 어떤 프레임워크에서든 가장 느립니다.
2. JavaScript 연산은 저렴하지만, 컴포넌트 규모가 커지면 더 이상 공짜가 아닙니다.
3. 프레임워크 오버헤드(virtual DOM이냐 컴파일된 DOM 조작이냐)는 앞의 두 가지에 비하면 반올림 오차 수준입니다.

이 서열을 이해하고 나면, 이어서 설명할 구체적인 기법들은 대부분 자명해집니다.

## SVAR DataGrid의 공통 아키텍처

### 엔진과 통합 레이어

프레임워크 독립성은 설계할 만한 가치가 있습니다. SVAR의 그리드는 프레임워크에 무관한 코어(데이터 구조, 설정 정규화, 레이아웃 계산 등)와 프레임워크별로 얇게 붙는 통합 레이어로 나뉩니다.

어려운 작업은 모두 코어에 있습니다. 통합 레이어는 코어의 상태를 각 프레임워크의 반응형 primitive로 번역해줄 뿐이고, 이 분리 덕분에 React, Vue, Svelte 세 버전을 동시에 유지보수하는 일이 현실적으로 가능해졌습니다.

꼭 세 프레임워크를 동시에 지원해야만 이 아이디어가 유용한 건 아닙니다. 단일 React 앱 안에서도 무거운 로직을 컴포넌트 밖에 두면 테스트하기 쉽고, 프로파일링하기 쉽고, 렌더 사이클에서 생기는 우발적 사고로부터 안전해집니다.

### 가상화는 기본값

모든 행을 렌더링하는 건 애초에 선택지가 아니므로, SVAR의 그리드(다른 컴포넌트들도 대부분 마찬가지)는 렌더링 가상화를 사용합니다. 컨테이너 크기를 측정해서 화면에 들어오는 행과 열만 렌더링합니다.

동시에 숨겨진 플레이스홀더를 그려서 전체 데이터셋이 렌더링된 것처럼 보이고 작동하게 만듭니다. 스크롤이 일어나면 데이터 스토어에 새로 보여야 할 구간을 요청하고, 그 구간을 일반적인 React, Svelte, Vue 컴포넌트로 렌더링합니다.

세 프레임워크 모두 이 작업을 위한 특별한 도구를 제공하지 않습니다. primitive도, 내장 헬퍼도 없습니다. 가상화는 순수하게 DOM 엔지니어링의 영역이고, 개발자가 직접 구현해야 할 몫입니다. 프레임워크의 역할은 개발자가 "보여주기로 결정한" 15개 행을 다시 렌더링하는 것뿐이고, 이 부분은 세 프레임워크 모두 무난하게 잘 해냅니다.

문제는 데이터가 렌더링되기도 전에 생깁니다. 어떤 행이 보이는지 알려면 컨테이너 크기가 필요한데, 크기를 얻으려면 일단 뭔가를 렌더링해야 합니다. 일종의 닭과 달걀 문제입니다.

어디서나 통하는 패턴은 이렇습니다. 먼저 스타일이 적용된 빈 컨테이너를 렌더링하고, ResizeObserver를 붙인 다음, 0이 아닌 첫 크기 값이 들어올 때까지 실제 데이터 렌더링을 보류합니다. 0은 정당한 중간 상태인데, 컨테이너 높이를 결정하는 CSS가 아직 로딩 중일 수도 있기 때문입니다.

```
// React, but the same logic ports to Svelte and Vue as is
const [size, setSize] = useState({ height: 0 });
useEffect(() => {
  const element = viewportRef.current;
  if (!element) return;

  const observer = new ResizeObserver(
    ([entry]) => setSize({ height: entry.contentRect.height })
  );
  observer.observe(element);

  return () => observer.disconnect();
}, []);

if (!size.height) return null;
return render();
```

여기서 React만 가진 무기가 하나 있는데, 바로 useLayoutEffect입니다. DOM이 구성된 직후, 브라우저가 화면을 그리기(paint) 전에 실행되기 때문에 컨테이너를 측정하고 상태를 업데이트한 결과를 사용자가 보는 바로 첫 프레임에 반영할 수 있습니다.

```
// react only
const [size, setSize] = useState({ height: 0 });
useLayoutEffect(() => {
  const element = viewportRef.current;
  setSize({ height: element.offsetHeight });
});

if (!size.height) return null;
return render();
```

useLayoutEffect는 흔히 '풋건(footgun)'이라고 조롱받고 대체로 그 평가가 맞지만, 가상화의 초기 측정만큼은 이 훅이 제값을 하는 드문 사례입니다.

다만 솔직히 말하면, 실무에서는 결국 ResizeObserver 경로로 폴백하게 됩니다. useLayoutEffect 콜백 시점에 레이아웃이 아직 준비되지 않은 경우가 빈번한데, 외부 스타일시트나 폰트, 이미지가 아직 로드되지 않아서 크기가 결정되지 않은 상태이기 때문입니다. 그래서 어차피 옵저버는 필요하고, useLayoutEffect는 대체재가 아니라 그 위에 얹는 '첫 프레임 최적화' 정도의 역할을 합니다.
