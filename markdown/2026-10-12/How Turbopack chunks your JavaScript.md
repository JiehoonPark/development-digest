## 아티클

Next.js 앱의 네트워크 탭을 열어보면 `36wnellv-yn9q.js` 같은 알 수 없는 이름의 JavaScript 파일들이 잔뜩 보입니다. 이것들이 바로 "청크(chunk)"인데요, Turbopack은 여러분의 코드, 의존하는 패키지들, 그리고 이 모든 걸 연결하는 런타임을 수십 개의 청크로 나눠 생성합니다. 이 글은 Turbopack 팀에서 인턴으로 일한 Sam Poder가 "청킹(chunking)"이 정확히 무엇이고, 어떤 트레이드오프를 가지며, Next.js 16.3에서 어떻게 더 똑똑해졌는지를 설명합니다.

실제로 로드되는 청크 파일을 압축 해제해보면 다음과 같은 형태를 띱니다.

"청킹"은 어떤 코드를 어떤 청크에 담을지 결정하는 과정입니다. 이 결정 방식에는 여러 가지가 있고, 각각 트레이드오프가 다릅니다.

## 세 가지 극단적인 접근법

가장 단순한 방식부터 살펴보겠습니다. 앱이 사용하는 모든 JavaScript를 하나의 청크에 담는 방식입니다.

**모든 걸 하나로: 355개 모듈을 1개 청크에**(1.09 MB, `app.js`)

이 청크는 모든 페이지에서 로드됩니다. 모든 페이지가 같은 청크를 공유하기 때문에 첫 로드 이후의 모든 로드는 캐시 히트가 됩니다. 내비게이션은 빠르겠죠.

하지만 트레이드오프도 금방 눈에 띕니다. JavaScript가 거의 필요 없는 페이지를 열어도 다른 모든 페이지의 JavaScript까지 함께 받아야 합니다. 사이트가 커질수록 모든 페이지 로드가 점점 더 무거워지죠. 장기적으로는 지속 불가능한 방식입니다.

그럼 페이지당 하나의 청크로 바꿔보면 어떨까요? 청크를 가볍게 유지하고 코드를 과도하게 보내는 일도 없을 것 같습니다.

**페이지당 1개 청크**: 같은 355개 모듈을 8개 청크로 나누되, 페이지 간 공유되는 코드는 필요한 모든 청크에 중복 포함(8개 청크, 1.20 MB — `/docs`, `/learn`, `/blog`, `/showcase`, `/team`, `/governance`, `/telemetry`)

문제는 캐싱을 잃는다는 겁니다. 모든 페이지가 `<Footer />`를 사용한다면, 그 코드는 모든 페이지의 청크 안에 중복으로 들어갑니다. 방문자가 네 개 페이지를 열면 같은 Footer 코드를 네 번 다운로드하는 셈이죠.

그래서 더 세밀한 방식이 필요합니다. 모든 모듈이 각자의 청크를 갖는다면 어떨까요? 코드가 과도하게 전송되는 일도 없고, 페이지 간 공유되는 모듈도 단 한 번만 다운로드될 겁니다.

**모듈당 1개 청크**: 355개의 개별 청크, 각각 한 번씩 전송되고 각각 별도의 네트워크 요청(355개 청크, 1.09 MB)

좋습니다. 다만 작은 문제가 하나 있는데, 이렇게 되면 작은 JavaScript 파일에 대해 수백 개의 네트워크 요청이 발생합니다. 요청 하나하나마다 오버헤드가 붙고, 수백 개가 쌓이면 사이트가 느려집니다. HTTP/2 덕분에 요청 비용이 줄긴 했지만 여전히 요청마다 오버헤드는 존재합니다. gzip 같은 압축 알고리즘도 파일이 작게 쪼개지면 성능이 떨어지는데, 압축 패턴을 단일 파일 내에서만 찾을 수 있기 때문입니다. 압축 사전(compression dictionary)이 도움이 되긴 하지만 이 문제를 근본적으로 해결하지는 못합니다.

## 요청 수냐, 코드 크기냐

결국 남는 과제는 이렇습니다. 다운로드 크기는 최소화하고 요청 수도 최소화하고 싶은데, 이 두 목표는 서로 충돌합니다. 청크가 적고 클수록 요청 수는 줄지만, 커질수록 페이지 간 재사용성은 떨어집니다.

Turbopack의 해법은 작은 청크들을 더 큰 청크로 병합하는 것입니다. 어려운 부분은 어떤 청크를 병합할지, 그리고 그 병합이 정말로 이득인지 판단하는 것인데요.

이를 위해 **청크 그룹(chunk group)**이라는 개념이 필요합니다. 청크 그룹은 함께 로드되는 청크들의 모음입니다. 예를 들어 `/home`에서 쓰이는 모든 청크는 하나의 청크 그룹에, `/blog`에서 쓰이는 청크들은 또 다른 그룹에 속합니다.

**두 개의 청크 그룹**: `/home` 그룹은 3개 청크를 로드하고, `/blog` 그룹은 2개 청크를 로드합니다. 한 청크가 두 그룹 모두에 속해 있다면, 이웃 청크와의 병합은 같은 그룹 내에서만 안전합니다.

청크 그룹은 코드 과잉 전송 문제를 해결해줍니다. Turbopack은 같은 그룹 내의 청크들만 병합하는데, 한 그룹 안의 청크들은 어차피 항상 함께 로드되므로 병합해도 페이지가 원래 받던 것 이상을 받게 되지는 않습니다.

그럼 브라우저에 요청을 과도하게 쏟아붓지 않으면서 캐시 히트율은 어떻게 최적화할까요?

## 병합이 이득인지 판단하기

이를 분석하기 위해 두 가지 방문 패턴을 상상해봅시다. 하나는 페이지 하나를 방문하고 떠나는 경우, 다른 하나는 페이지를 방문한 뒤 다른 페이지로 이동하는 경우입니다. (세 페이지 이상 방문하는 세션도 같은 논리로 확장됩니다.)

`<Footer />`의 청크를 A, `<VideoPlayer />`의 청크를 B라고 부르겠습니다. A는 모든 페이지에서 쓰이고, B는 홈페이지에서만 쓰입니다. 둘 다 홈페이지의 청크 그룹에 속하므로 병합 후보입니다.

방문자가 홈페이지를 로드하고 떠난다면, 병합은 항상 이득입니다. 어차피 둘 다 필요했던 코드인데, 요청이 2개에서 1개로 줄어드니까요.

두 번째 페이지로 이동하는 경우라면 그 페이지가 A와 B 둘 다 필요한지, 하나만 필요한지에 달려 있습니다. 예를 들어 홈페이지에서 법적 고지 페이지로 이동한다고 합시다. 법적 고지 페이지는 A는 필요하지만 B는 필요 없습니다. A와 B가 하나의 파일로 병합되어 있다면 그 병합 파일은 이 페이지에서 쓸모가 없으니, 브라우저는 A를 단독으로 다시 다운로드합니다. 결과적으로 방문자는 A를 두 번 다운로드한 셈이 됩니다.

병합이 내비게이션 전체에 걸쳐 이득을 보려면, 두 페이지 모두 A와 B를 전부 필요로 해야 합니다. 그래야 병합된 파일이 재사용되어 요청 하나를 절약할 수 있습니다.

가능한 모든 2페이지 세션 시나리오를 정리하면 다음과 같습니다. 각 행은 "첫 페이지가 필요로 하는 것 → 두 번째 페이지가 필요로 하는 것" 형태이며, 수치는 A와 B를 병합했을 때 세션 전체의 요청 수와 다운로드 코드량이 어떻게 변하는지(병합하지 않은 경우 대비)를 나타냅니다.

| 내비게이션 | 요청 수 변화 | 다운로드 코드량 변화 |
|---|---|---|
| A → A | 0 | 0 |
| A → B | 0 | 0 |
| B → B | 0 | 0 |
| A → A + B | 0 | + A |
| B → A + B | 0 | + B |
| A + B → A | 0 | + A |
| A + B → B | 0 | + B |
| A + B → A + B | −1 | 0 |

청크 A와 B의 병합을 고려할 때는, A만 쓰는 청크 그룹의 수, B만 쓰는 청크 그룹의 수, A+B를 모두 쓰는 청크 그룹의 수를 계산하고, 각 시나리오의 발생 확률로 병합의 비용/이득에 가중치를 매깁니다. 마지막으로 한 페이지만 방문하는 경우와 두 페이지 이상 방문하는 경우에도 각각의 확률로 가중치를 부여합니다. Turbopack은 세션의 2/3가 단일 페이지 방문이고 1/3이 두 페이지 이상이라고 추정합니다.

## Next.js 16.3에서 추가된 청킹 기능들

청킹의 효과를 제한하는 두 가지 요인이 있습니다. 첫째, 병합은 빌드 시점에 결정되기 때문에 방문자가 실제로 무엇을 캐시하고 있는지 반영할 수 없습니다. 둘째, 알고리즘은 사람들이 사이트를 어떻게 돌아다니는지 추측에 의존할 수밖에 없는데, 단일 페이지 방문에 2/3 가중치를 두는 것도 이 때문입니다. Sam Poder는 이번 여름 Turbopack 팀 인턴십 동안 이 두 가지 문제를 개선하는 작업과, 애초에 청크에 담기는 코드 자체를 줄이는 작업을 진행했습니다.

### 더 똑똑한 청크 페칭

앞서 살펴본 표에서 병합의 비용을 확인했습니다. 방문자가 A가 포함된 페이지를 로드한 뒤 A+B가 필요한 페이지로 이동하면, 병합 때문에 A를 두 번 다운로드하게 됩니다. 번들러는 빌드 시점에 브라우저가 무엇을 이미 가지고 있는지 알 수 없기 때문에 이를 피할 수 없지만, 런타임은 알 수 있습니다.

Next.js 16.3 이상에서 `next.config.js`에 `experimental.turbopackChunking.generateComponentChunks`를 활성화하면, Turbopack은 병합된 청크와 함께 병합되지 않은 버전도 함께 생성합니다. 각 병합 청크가 어떤 구성 요소들로 이루어져 있는지, 그리고 그중 이미 로드된 것이 무엇인지 추적해서, 요청 시점에 병합된 청크와 빠진 조각들만 가져오는 것 중 더 저렴한 쪽을 선택합니다.

반대 방향도 동작합니다. 방문자가 이미 병합된 A+B를 로드했다면, A를 단독으로 다시 로드하는 일을 건너뛸 수 있습니다.

이렇게 하면 소프트 내비게이션 시 불필요한 코드를 덜 로드하게 되어, 내비게이션 비용 없이 병합의 이점만 얻을 수 있습니다. 데모 앱(`component-chunks-demo-off.labs.vercel.dev`와 `component-chunks-demo-on.labs.vercel.dev`)에서 `generateComponentChunks`를 켰을 때와 껐을 때의 차이를 직접 확인할 수 있습니다.

또한 Turbopack 팀은 `only-if-cached` 디렉티브도 실험 중인데, 이는 방문자가 도착했을 때 이미 캐시하고 있는 것이 무엇인지 확인할 수 있게 해줍니다. 이를 통해 사이트를 떠났다가 나중에 다시 돌아오는 방문자에게도 같은 개선 효과를 확장할 수 있습니다.

### 분석 데이터 기반 청킹

청킹 알고리즘에는 사이트에 대한 여러 가정이 들어갑니다. 예를 들어 앞서 말한 2/3 가중치는 추측값입니다. 여러 사이트에 걸쳐서는 합리적인 기본값이지만, 특정 사이트에 반드시 맞는 값은 아닙니다. 실제 사용자들이 사이트를 어떻게 돌아다니는지 안다면, 그 정보를 Turbopack에 알려줄 수 있습니다.

`next.config.js`의 `experimental.turbopackChunking` 아래에 다음 설정들을 추가할 수 있습니다.

- **firstPageLoadPriority**: 단일 페이지 케이스와 두 페이지 케이스 사이의 가중치를 조정합니다. 0에서 1 사이의 값으로, 값이 클수록 내비게이션 비용을 감수하더라도 최초 로드 속도를 우선시합니다. 이탈률(bounce rate)을 초깃값으로 쓰는 것이 합리적이며, 기본값은 0.67입니다.
- **priorityRoutes**: 로드 속도가 가장 중요한 페이지 목록입니다. 이 경로들에 대해서는 더 적극적으로 청크를 병합합니다.
- **clusters**: 함께 자주 방문되는 경로들의 그룹으로, 각각 정규식 배열로 정의합니다. 클러스터 내부에서는 겹치는 청크를 더 적극적으로 병합합니다. 다만 한 클러스터 안에 A만 쓰거나 B만 쓰는 페이지와 둘 다 쓰는 페이지가 섞여 있다면 병합을 덜 적극적으로 합니다.

### 더 작고 더 적은 청크

지금까지는 코드를 어떻게 묶을지에 관한 내용이었습니다. 마지막으로 소개할 기능들은 애초에 전송되는 코드량 자체를 줄이는 데 초점을 맞춥니다.

- **CJS 모듈 트리 셰이킹**: 기존에는 ESM 모듈에만 트리 셰이킹을 지원했기 때문에, CJS 모듈 안의 사용되지 않는 import/export도 클라이언트로 전송되고 있었습니다. `experimental.turbopackCjsTreeShaking`으로 활성화할 수 있으며, 향후 Next.js 버전에서 기본값으로 켜질 예정입니다. 또한 분석 및 트리 셰이킹이 가능한 ESM 모듈의 범위도 확장했는데, 여기에는 동적 import 내 배럴 파일(barrel file) 지원 개선도 포함됩니다.
- **공유 Turbopack 런타임**: 이제 페이지별 런타임 대신 하나의 런타임 청크가 사용됩니다. `experimental.turbopackSharedRuntime`으로 활성화할 수 있으며, 첫 로드 이후의 모든 내비게이션에서 블로킹 요청 하나와 약 10KB의 클라이언트 측 JavaScript를 절약합니다. 이 역시 추후 기본값으로 켜질 예정입니다.
- **더 가벼운 기본 런타임**: 런타임은 더 이상 기본적으로 WebAssembly와 Web Worker 관련 코드를 포함하지 않습니다. 해당 모듈을 사용하는 경우를 감지해서 그때 로딩 코드를 삽입하는 방식으로 바뀌었습니다.

이 새로운 기능들은 Next.js 16.3 이상에서 사용해볼 수 있습니다. 청킹(CSS 청킹 포함)에 대한 트레이드오프와 제약을 더 깊이 알고 싶다면 Tobias의 최근 발표를 참고할 만합니다.

## 정리

- 청킹에는 세 가지 극단이 존재합니다. 전체를 하나로 묶으면 캐시 효율은 좋지만 불필요한 코드가 과도하게 전송되고, 페이지당 하나씩 나누면 코드 중복이 생기며, 모듈당 하나씩 나누면 요청 수가 폭증합니다. Turbopack은 이 사이에서 작은 청크들을 큰 청크로 병합하는 방식을 택합니다.
- 병합은 "청크 그룹" 단위로만 이루어져 코드 과잉 전송을 막고, A+B가 함께 필요한 페이지로 이동할 때만 진짜 이득이 발생한다는 수학적 분석(세션 확률 가중치 포함)을 바탕으로 병합 여부를 결정합니다.
- 실측 결과 nextjs.org 기준으로 기본 전략이 병합 없음 대비 요청 수를 절반 이상 줄이면서도 코드량은 비슷하거나 더 적었고, 전체 병합은 요청 수를 더 줄이지만 코드량이 10% 늘었습니다. 즉 "정답"은 사이트의 내비게이션 패턴에 따라 달라집니다.
- Next.js 16.3에서는 `generateComponentChunks`(런타임에 병합/비병합 청크 중 더 저렴한 쪽 선택), `firstPageLoadPriority`/`priorityRoutes`/`clusters`(실제 사용자 흐름 기반 튜닝), CJS 트리 셰이킹, 공유 런타임, 경량 기본 런타임 등 빌드 시점 추측의 한계를 보완하는 실험적 기능들이 추가됐습니다.
- 실무에서는 대규모 Next.js 서비스라면 `next.config.js`의 `experimental.turbopackChunking` 옵션들을 실제 애널리틱스 데이터와 함께 튜닝해볼 가치가 있고, 특히 `turbopackSharedRuntime`과 `turbopackCjsTreeShaking`은 큰 수고 없이 번들 크기를 줄일 수 있는 기능이라 먼저 시도해볼 만합니다.
