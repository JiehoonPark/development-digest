## 아티클

SVAR 팀은 React, Vue, Svelte 세 프레임워크로 동일한 데이터 그리드, 간트 차트, 캘린더 같은 고성능 UI 컴포넌트를 만들어 배포하고 있습니다. 보통 프레임워크 비교글은 한 프레임워크에 정통한 사람이 나머지 둘은 문서만 훑어보고 쓰는 경우가 많은데, 이 팀은 실제로 세 프레임워크 모두에서 같은 컴포넌트를 고성능으로 구현해야 했던 흔치 않은 입장에 있습니다. 이 글에서는 그 경험을 바탕으로 데이터 그리드를 세 프레임워크에 걸쳐 만들면서 무엇을 배웠는지 공유합니다. 결론부터 말하면 다소 의외인데, 빠른 데이터 그리드를 만들 때 정말 비용이 드는 부분은 프레임워크와 거의 무관했고, 프레임워크 간 실질적인 차이는 흔히 말하는 "프레임워크 전쟁"이 시사하는 것보다 훨씬 좁았습니다. 그래서 이 글은 의도적으로 승자를 가리지 않습니다.

## 프레임워크와 무관한 성능 문제

데이터 그리드는 이런 비교에 아주 좋은 테스트 케이스입니다. 누구나 한 번쯤 만들거나 써봤고, 구조는 단순하지만 다루는 데이터양은 다른 컴포넌트와 비교가 안 될 정도로 많습니다. 1,000행은 지극히 평범한 수준이고 10,000행도 드물지 않으니, 처음부터 이를 염두에 두고 설계해야 합니다.

실제로 SVAR React DataGrid는 20만 행, 2만 열을 렌더링하는 데모를 제공하는데, 이 정도의 수치에도 그리드는 부드럽게 동작합니다.

반대로 10,000행을 그냥 직접 렌더링해버리면 어떤 프레임워크든 똑같이 무너집니다. 요즘 하드웨어가 워낙 빨라서 완전히 죽지는 않더라도 심각하게 느려지는데, React, Vue, Svelte 모두 결국 브라우저에게 수십만 개의 DOM 노드를 만들고 배치하라고 요청하게 되고, 병목은 브라우저 자체가 됩니다. 즉 프레임워크는 거의 상관이 없어지는 거죠. 이 실패 지점이 바로 비용 계층 구조의 정점을 보여줍니다.

- HTML을 만들어내는 작업이 어떤 프레임워크에서든 가장 느립니다.
- JavaScript 연산은 저렴하지만, 컴포넌트 규모가 커지면 더 이상 공짜가 아닙니다.
- 프레임워크 자체의 오버헤드(가상 DOM이냐 컴파일된 DOM 조작이냐)는 앞의 두 가지에 비하면 오차 범위 수준입니다.

이 순서를 이해하고 나면, 아래에서 소개할 구체적인 기법들이 대부분 자연스럽게 납득이 갑니다.

## SVAR DataGrid의 공통 아키텍처

여기서는 데이터 그리드가 React, Vue, Svelte 각각에서 "프레임워크 네이티브"처럼 동작하도록 어떻게 설계했는지 설명합니다.

### 엔진과 통합 레이어

프레임워크 독립성은 설계 단계에서부터 신경 쓸 가치가 있습니다. SVAR의 그리드는 프레임워크에 무관한 코어(데이터 구조, 설정 정규화, 레이아웃 계산 등)와 프레임워크별로 얇게 얹히는 통합 레이어로 나뉩니다.

어려운 작업은 모두 코어에서 이루어집니다. 통합 레이어는 코어의 상태를 각 프레임워크의 반응형 프리미티브로 변환해줄 뿐이고, 이 분리 구조 덕분에 React, Vue, Svelte 버전을 동시에 유지보수하는 일이 현실적으로 가능해졌습니다.

꼭 세 프레임워크에 동시 배포할 필요가 없더라도 이 아이디어는 참고할 만합니다. 단일 React 앱 안에서도 무거운 로직을 컴포넌트 밖으로 빼두면 테스트하기 쉽고, 프로파일링하기 쉽고, 렌더 사이클에서 벌어지는 우발적인 문제에서도 자유로워집니다.

### 기본값으로 깔고 가는 가상화(Virtualization)

전체 데이터를 다 렌더링하는 건 애초에 선택지가 아니므로, SVAR의 대부분의 컴포넌트처럼 이 그리드도 렌더링 가상화를 사용합니다. 컨테이너의 크기를 측정하고, 화면에 실제로 들어오는 행과 열만 렌더링하는 방식입니다.

동시에 보이지 않는 placeholder를 그려서 마치 전체 데이터셋이 렌더링된 것처럼 보이고 동작하게 만듭니다. 스크롤이 발생하면 데이터 스토어에 새로 보여야 할 구간을 요청하고, 이를 일반적인 React, Svelte, Vue 컴포넌트로 렌더링합니다.

세 프레임워크 중 어느 것도 이 작업을 위한 전용 기능을 제공하지 않습니다. 프리미티브도, 내장 헬퍼도 없습니다. 가상화는 순수하게 DOM 엔지니어링의 영역이고, 개발자가 직접 해결해야 할 몫입니다. 프레임워크가 담당하는 부분은 "화면에 보여주기로 결정한 15개 행을 다시 렌더링하는 것"뿐이고, 이 부분은 세 프레임워크 모두 문제없이 잘 해냅니다.

그런데 가상화는 데이터가 렌더링되기도 전에 첫 번째 문제를 만들어냅니다. 어떤 행이 보이는지 알려면 컨테이너의 크기가 필요한데, 크기를 얻으려면 일단 뭔가를 렌더링해야 합니다. 일종의 "닭과 달걀" 문제인 셈이죠.

세 프레임워크 모두에서 통하는 패턴은 다음과 같습니다: 먼저 스타일이 적용된 빈 컨테이너를 렌더링하고, ResizeObserver를 붙인 뒤, 첫 번째로 0이 아닌 크기 값이 들어올 때까지 실제 데이터 렌더링을 미루는 것입니다. 컨테이너 높이를 결정하는 CSS가 아직 로딩 중일 수 있으므로 0이라는 값도 정상적인 중간 상태로 취급해야 합니다.

```js
// React, but the same logic ports to Svelte and Vue as is
const [size, setSize] = useState({ height: 0 });
useEffect(() => {
  const element = viewportRef.current;
  if (!element) return;

  const observer = new ResizeObserver(
    ([entry]) => setSize({ height: entry.contentRect.height })
  );
  observer.observe(element);

  return () => observer.disconnect();
}, []);

if (!size.height) return null;
return render();
```

여기서 React만 갖고 있는 것이 하나 있는데, 바로 `useLayoutEffect`입니다. 이 훅은 DOM이 만들어진 후, 브라우저가 화면을 그리기 전에 실행되므로, 컨테이너를 측정하고 상태를 갱신한 결과를 사용자가 보는 첫 프레임에 바로 반영할 수 있습니다.

```js
// react only
const [size, setSize] = useState({ height: 0 });
useLayoutEffect(() => {
  const element = viewportRef.current;
  setSize({ height: element.offsetHeight });
});

if (!size.height) return null;
return render();
```

사람들은 흔히 `useLayoutEffect`를 위험한 함정(footgun)이라고 조롱하는데, 대체로 맞는 말입니다. 하지만 가상화 컴포넌트의 초기 크기 측정은 이 훅이 정말로 제 값을 하는 몇 안 되는 사례 중 하나입니다.

다만 솔직히 말하면, 실제로는 결국 ResizeObserver 방식으로 되돌아가는 경우가 많습니다. 레이아웃이 `useLayoutEffect` 콜백 시점에 아직 준비되지 않은 경우가 흔하기 때문인데, 크기가 외부 스타일시트나 폰트, 이미지 로딩에 의존하는 경우가 그렇습니다. 결국 observer는 어차피 필요하고, `useLayoutEffect`는 그것을 대체하는 게 아니라 그 위에 얹혀서 "첫 프레임을 더 매끄럽게 만드는" 최적화 정도의 역할을 합니다.

Svelte와 Vue에는 `useLayoutEffect`에 대응하는 것이 없습니다. Svelte의 `$effect.pre`는 DOM 업데이트 전에 실행되므로 측정하기엔 너무 이릅니다. `onMount`와 `tick()`은 DOM이 존재한 이후에 실행되지만, 여기서 만든 변경 사항은 다음 프레임에 그려지므로 그냥 ResizeObserver를 쓰는 것과 별 차이가 없습니다.

Vue도 마찬가지 구조입니다. `onBeforeUpdate`는 너무 이르고, `onUpdated`는 DOM을 볼 수는 있지만 거기서 만든 변경 사항은 다음 렌더링 프레임에 반영됩니다. 그러니 이건 React의 실질적인 장점이 맞지만, 아주 좁은 범위의 장점입니다. 다른 프레임워크들의 설계도 나름의 합리성이 있고, React가 이 훅을 갖게 된 것도 부분적으로는 자신의 렌더 사이클 방식 때문입니다.

### SSR에 대한 부연 설명

가상화와 서버 사이드 렌더링(SSR)은 정의상 충돌합니다. 서버는 사용자의 뷰포트에 어떤 행이 들어올지 알 수 없으니, 올바른 구간을 렌더링할 방법이 없습니다. 하지만 경험상 이 충돌이 실제로 야기하는 문제는 생각보다 크지 않습니다.

SSR을 쓰는 주된 이유는 첫 페인트 속도 개선인데, 이는 가상화가 이미 자기 방식대로 해결하는 문제입니다. 또 다른 이유는 SEO인데, 애초에 10만 행 중 15행만 렌더링하는 컴포넌트에서는 SEO가 제대로 될 리가 없습니다.

순수 React나 Vue를 쓴다면 이 충돌을 체감할 일이 거의 없습니다. 하지만 Next.js나 Nuxt를 쓴다면 이야기가 다른데, 보통 hydration mismatch 오류가 줄줄이 뜨는 형태로 나타납니다. 해결책은 놀랍도록 단순합니다: 그리드를 클라이언트 전용 컴포넌트로 표시하면 오류가 사라집니다. 이는 받아들이고 넘어가면 되는 트레이드오프입니다.

### 내부 로직: 메모이제이션과 파생 상태

여기서 짚고 넘어갈 부분이 있습니다. SVAR 컴포넌트는 폭넓은 사용자층을 대상으로 하기 때문에 모든 React 버전에서 동작해야 하고, 그래서 여전히 코드에 수동으로 메모이제이션 지시를 넣고 있습니다. 만약 최신 코드베이스에서 작업하며 React Compiler를 사용할 수 있는 상황이라면, 컴파일러가 이를 자동으로, 아마 수동으로 넣는 것보다 훨씬 잘 처리해줄 겁니다. 그런 경우라면 아래 `useMemo` 관련 내용은 무시해도 됩니다. 유효한 기법이지만 React Compiler가 도입되면 쓸모없어지는 기법이니까요.

React의 원래 성능 전제는 "HTML 렌더링은 느리고 JavaScript는 빠르니, 컴포넌트 코드를 다시 실행하는 건 괜찮다"는 것이었습니다. 단순한 버튼이라면 이 전제는 완벽히 통합니다.

하지만 데이터 그리드는 뭔가를 렌더링하기 전에 데이터와 설정을 정규화하고, 레이아웃을 계산하고, 열의 기하학적 구조를 결정해야 합니다. 팀의 간트 컴포넌트는 이보다 더 많은 계산을 합니다. 이 정도 규모에서는 매 렌더링마다 모든 걸 다시 실행하는 게 더 이상 괜찮지 않습니다.

`useMemo`와 `useCallback`이 React의 표준적인 답이고, 복잡한 컴포넌트에서는 정말 든든한 친구가 되어줍니다.

```js
// React
const normalizedHeaders = useMemo(() => normalize(columns), [columns]);
const columnCount = normalizedHeaders.length;
```

Svelte는 같은 아이디어를 `$derived`로 표현합니다.

```js
// Svelte
const normalizedHeaders = $derived(normalize(columns));
const columnCount = $derived(normalizedHeaders.length);
```

Vue는 `computed`를 씁니다.

```js
// Vue
const normalizedHeaders = computed(() => normalize(columns));
const columnCount = computed(() => normalizedHeaders.value.length);
```

내부의 반응형 메커니즘은 완전히 다르지만, 실제 사용법은 거의 차이가 없습니다. 세 프레임워크 모두 "입력값이 바뀌기 전까지는 이 값을 보존한다"는 동일하고 저렴한 계약을 제공합니다.

실제로 그리드의 가상화 계산 로직(보이는 행의 범위, 좌/우/중앙 열 분할, 전체 스크롤 높이 등)을 포팅할 때, `useMemo`, `$derived.by`, `computed` 사이를 거의 한 줄 단위로 대응시켜가며 옮길 수 있었습니다. 문법은 `$x`, `x.value`, 그냥 값 이렇게 조금씩 달라지지만, 로직 자체는 그대로 옮겨집니다. 한 프레임워크를 알면 나머지 둘도 이 부분에서는 이미 이해한 것과 다름없습니다.

이 유사성 속에서 진짜로 갈라지는 지점이 하나 있습니다. React는 의존성 배열을 직접 손으로 작성해야 합니다. 그리드의 `renderRows` 메모는 여덟 개의 의존성을 나열하는데, 하나라도 빠뜨리면 갱신되지 않는 그리드가 되어버리고 디버깅이 매우 괴로워집니다. Svelte와 Vue는 의존성을 자동으로 추적합니다.

### React, Vue, Svelte의 기본 동작 방식이 만드는 차이

프레임워크의 기본적인 동작 방식을 이야기하자면, 컴포넌트 코드가 언제 실행되는지에 구조적인 차이가 있고, 이것이 모든 것에 영향을 미칩니다. Svelte와 Vue는 컴포넌트의 setup 코드를 단 한 번만 실행합니다. React는 렌더링될 때마다 함수 본문 전체를 다시 실행합니다.

Svelte나 Vue에서는 "데이터 스토어를 생성한다"는 그냥 평범한 문장 하나로 표현됩니다. React에서는 같은 의도를 구현하기 위해 여러 관용구가 필요합니다. 스토어를 위한 `useMemo(() => new DataStore(...), [])`, 이벤트 버스 연결을 위한 null 체크가 들어간 `useRef`, 그리고 `useEffect` 바깥에 유지해야 하는 동기적인 첫 렌더링 초기화 호출(effect는 페인트 이후에 실행되어서 첫 프레임에는 너무 늦기 때문)까지, 하나의 개념에 네 가지 관용구가 필요한 셈입니다.

하지만 이 모델에는 이면도 있습니다. Svelte와 Vue는 컴포넌트의 setup 코드를 한 번만 실행하기 때문에, 반응성은 명시적으로 선택해서 켜는 것에 가깝습니다. 이는 우발적인 재계산이 애초에 설계상 드물다는 뜻이기도 합니다. 대신 위험은 다른 곳으로 옮겨갑니다. 애초에 어떤 값을 반응형으로 만드는 걸 깜빡하고, 조용히 절대 갱신되지 않는 무언가를 배포해버릴 수 있다는 거죠. 다만 실제로는 자동 의존성 추적과 린트 도구가 이런 경우 대부분을 잡아냅니다.

그러니 이는 우열이 아니라 트레이드오프입니다. React의 모델은 기본적으로 더 위험하지만 완전히 명시적이어서 무슨 일이 일어나는지 언제나 눈으로 확인할 수 있습니다. Svelte와 Vue의 모델은 기본적으로 더 안전하지만, 가끔 예상치 못한 방식으로 허를 찌를 수 있습니다.

그렇다고 모든 것을 `useMemo`로 감싸라는 뜻은 아닙니다. 대부분의 계산은 신경 쓸 필요도 없을 만큼 저렴합니다. 코드를 읽거나 더 나아가 프로파일링을 통해 무거운 부분을 찾아내고, 그 부분만 렌더링 사이에 보존하면 됩니다. 그게 전부입니다.

### 부연 설명: 하나의 스토어, 세 개의 어댑터

SVAR 컴포넌트에서는 메모이제이션만으로는 충분하지 않았습니다. 그래서 프레임워크와 무관한 반응형 스토어를 하나 만들고, 이를 각 프레임워크의 프리미티브에 맞게 어댑터로 연결하는 방식을 씁니다.

Svelte는 실제 `svelte/store`의 writable을 통해 `$store` 자동 구독 방식으로 이 스토어를 소비합니다. Vue는 작은 `subscribe()` 헬퍼를 통해 ref를 받아옵니다.

React는 `useState`와 `useEffect` 안의 구독을 조합한 `useStore(api, 'name')` 형태의 훅을 받습니다. React에는 장치가 하나 더 필요한데, 바로 변경 카운터를 반환하는 `useStoreWithCounter` 훅입니다. 배열이 제자리에서(in place) 변경되면 참조 동등성 비교로는 변경을 감지할 수 없기 때문에, 의존성으로 쓸 카운터가 따로 필요한 겁니다.

만약 단일 프레임워크만을 대상으로 한다면 이런 장치는 전혀 필요 없습니다. React와 Vue 모두 성숙한 외부 스토어 생태계를 갖추고 있고, Svelte 5의 `.svelte.js` 상태 모듈도 꽤 훌륭한 네이티브 선택지입니다. 다만 SVAR의 경우 하나의 스토어가 세 개의 프레임워크를 동시에 지원해야 했기 때문에 이런 선택지를 쓸 수 없었습니다.

원문은 이어서 "데이터 업데이트: 컴포넌트 트리가 개발자와 맞서 싸우는 지점"이라는 섹션을 시작하며, 데이터 업데이트 상황에서 개발자의 직관이 어긋나는 지점을 다루려던 참에 끊겨 있습니다.

## 정리

- 데이터 그리드처럼 대용량 데이터를 다루는 컴포넌트에서 진짜 성능 병목은 프레임워크 자체가 아니라 "HTML 생성 > JS 연산 > 프레임워크 오버헤드" 순서의 비용 구조에서 나옵니다. 이 순서를 이해하면 가상화, 메모이제이션 같은 기법이 왜 필요한지 자연스럽게 납득됩니다.
- 가상화는 세 프레임워크 어디에도 내장 지원이 없는, 순수하게 개발자가 직접 구현해야 하는 DOM 엔지니어링 영역입니다. 초기 크기 측정을 위한 ResizeObserver 패턴은 프레임워크에 관계없이 동일하게 적용됩니다.
- `useLayoutEffect`는 초기 측정 시나리오에서 React만의 실질적 장점이지만, 실무에서는 결국 ResizeObserver와 함께 써야 하는 "첫 프레임 최적화" 정도의 역할에 그칩니다.
- `useMemo`/`useCallback`, `$derived`, `computed`는 문법만 다를 뿐 거의 동일한 계약(입력이 안 바뀌면 값을 보존한다)을 제공하며, 로직 자체는 프레임워크 간에 거의 그대로 포팅됩니다. 차이는 React가 의존성 배열을 수동 관리해야 한다는 점 정도입니다.
- Svelte와 Vue는 setup 코드를 한 번만 실행해 우발적 재계산에서 자유롭지만 반응성을 깜빡할 위험이 있고, React는 매 렌더마다 함수 전체를 재실행해 명시적이지만 위험을 스스로 관리해야 합니다. 실무에서는 프레임워크를 하나만 쓰더라도 무거운 로직을 컴포넌트 밖으로 분리하는 설계 원칙 자체가 유효합니다.
