## 아티클

Next.js로 만든 사이트의 네트워크 탭을 열어보면 `36wnellv-yn9q.js` 같은 알 수 없는 이름의 JS 파일들이 잔뜩 로드되는 걸 볼 수 있습니다. 이런 파일 하나하나가 바로 "청크(chunk)"인데, Turbopack은 여러분의 코드, 의존하는 패키지, 그리고 이 모든 걸 연결하는 런타임을 담아 수십 개의 청크를 만들어냅니다. 이 글에서는 Turbopack이 어떤 기준으로 코드를 청크로 나누는지, 그리고 Next.js 16.3에서 추가된 새로운 청킹 기능들을 살펴보겠습니다.

## 청크란 무엇인가

압축을 풀어보면 청크는 대략 이런 모습입니다.

```js
(globalThis.TURBOPACK || (globalThis.TURBOPACK = [])).push([
"object" == typeof document ? document.currentScript : void 0,
7284,
(e) => {
"use strict";
function r() {
for (var e, r, o = 0, t = "", l = arguments.length; o < l; o++) {
// ...
}
return t;
}
e.s(["clsx", 0, r, "default", 0, r]);
},
395264,
(e) => {
"use strict";
var r = e.i(7284);
let o = function () {
// ...
};
},
]);
//# debugId=e60a5ad0-3ac6-bb3a-e12b-6130e99fb7a6
```

"청킹(chunking)"이란 어떤 모듈을 어떤 청크에 담을지 결정하는 과정을 말합니다. 청킹 전략에는 여러 방식이 있고, 각각 트레이드오프가 존재합니다.

## 세 가지 극단적인 전략과 그 한계

**하나의 거대한 청크로 묶기.** 앱이 사용하는 355개 모듈을 전부 하나의 청크(1.09MB)에 담는 방식입니다. 모든 페이지가 같은 청크를 공유하므로 첫 로드 이후에는 항상 캐시 히트가 발생하고, 페이지 이동도 빨라집니다. 하지만 JS를 거의 쓰지 않는 페이지조차 사이트 전체의 JS를 다운로드해야 합니다. 사이트가 커질수록 모든 페이지 로드가 점점 무거워지므로 장기적으로는 지속 불가능합니다.

**페이지별로 하나씩.** 같은 355개 모듈을 8개 페이지 청크(총 1.20MB)로 나누면 청크가 슬림해지고 필요 이상의 코드를 보내는 일이 없습니다. 하지만 캐싱을 잃게 됩니다. 모든 페이지에 `<Footer />`가 들어간다면, 그 코드는 모든 페이지 청크마다 중복으로 포함됩니다. 방문자가 네 개의 페이지를 열면 같은 푸터 코드를 네 번 다운로드하는 셈입니다.

**모듈별로 하나씩.** 355개 모듈을 355개 청크로 완전히 쪼개면(총 1.09MB) 아무것도 과다하게 전송되지 않고, 페이지 간 공유되는 모듈도 한 번만 다운로드됩니다. 문제는 작은 JS 파일들이 수백 개의 네트워크 요청으로 이어진다는 점입니다. HTTP/2가 요청 비용을 많이 낮췄다고 해도 요청마다 여전히 오버헤드가 붙고, gzip 같은 압축 알고리즘도 파일 하나 안에서만 반복 패턴을 찾을 수 있기 때문에 작은 파일이 많으면 압축 효율이 떨어집니다. 압축 사전(compression dictionaries)이 도움이 되긴 하지만 이 문제를 근본적으로 해결하지는 못합니다.

## 요청 수를 줄일 것인가, 코드량을 줄일 것인가

결국 우리가 원하는 건 "다운로드 용량은 최소로, 요청 수도 최소로"인데, 이 두 목표는 서로 충돌합니다. 청크가 크고 적을수록 요청 수는 줄지만 페이지 간 재사용성이 떨어지고, 청크가 작고 많을수록 재사용성은 좋지만 요청 수가 늘어납니다.

Turbopack의 해법은 작은 청크들을 더 큰 청크로 합치는 것입니다. 어려운 부분은 "어떤 청크를 언제 합쳐야 실제로 이득인지" 판단하는 일입니다.

이를 위해 **청크 그룹(chunk group)**이라는 개념이 필요합니다. 청크 그룹이란 함께 로드되는 청크들의 묶음입니다. 예를 들어 `/home` 페이지가 사용하는 모든 청크는 하나의 그룹을, `/blog`가 사용하는 청크는 또 다른 그룹을 이룹니다. 청크 그룹은 "과다 전송" 문제를 해결해줍니다. Turbopack은 같은 그룹 안의 청크끼리만 합치는데, 어차피 한 그룹의 청크는 항상 함께 로드되므로 합쳐도 원래 다운로드하던 것보다 더 보내는 일은 생기지 않습니다.

## 언제 합치는 것이 이득인가

그렇다면 브라우저에 과도한 요청을 주지 않으면서 캐시 히트율을 최적화하려면 어떻게 해야 할까요? 이를 파악하기 위해 두 가지 방문 패턴을 상상해봅니다. 하나는 페이지 하나만 보고 떠나는 경우, 다른 하나는 한 페이지를 보고 다른 페이지로 이동하는 경우입니다. (세 페이지 이상 이동하는 세션도 같은 논리로 확장됩니다.)

`<Footer />`의 청크를 A, `<VideoPlayer />`의 청크를 B라고 합시다. A는 모든 페이지에서 쓰이고 B는 홈페이지에서만 쓰입니다. 둘 다 홈페이지 청크 그룹에 속하므로 합칠 후보입니다.

방문자가 홈페이지만 보고 떠난다면 합치는 게 항상 이득입니다. 두 개 대신 한 개의 요청이면 되고, 어차피 둘 다 필요했던 코드니까요.

두 번째 페이지로 이동하는 경우엔 그 페이지가 A와 B 둘 다 필요로 하는지, 하나만 필요로 하는지에 따라 달라집니다. 예컨대 홈페이지에서 법률 고지 페이지로 이동한다고 하면, 법률 고지 페이지는 A만 필요하고 B는 필요 없습니다. A와 B가 하나의 파일로 합쳐져 있으니 그 합쳐진 파일은 이 페이지에서는 쓸모가 없고, 브라우저는 결국 A를 따로 다시 다운로드하게 됩니다. 방문자는 A를 두 번 받은 셈이 됩니다.

즉 합치기가 내비게이션에 걸쳐 이득을 보려면 두 페이지 모두 A와 B를 필요로 해야 합니다. 그래야 합쳐진 파일이 그대로 재사용되어 요청 하나를 절약합니다.

가능한 두 페이지 세션 시나리오를 정리하면 다음과 같습니다. 각 행은 "첫 페이지가 필요로 하는 것 → 두 번째 페이지가 필요로 하는 것" 형태이며, A와 B를 합쳤을 때 요청 수와 다운로드 코드량이 어떻게 변하는지를 보여줍니다.

| 내비게이션 | 요청 수 변화 | 다운로드 코드량 변화 |
|---|---|---|
| A → A | 0 | 0 |
| A → B | 0 | 0 |
| B → B | 0 | 0 |
| A → A + B | 0 | + A |
| B → A + B | 0 | + B |
| A + B → A | 0 | + A |
| A + B → B | 0 | + B |
| A + B → A + B | −1 | 0 |

A와 B를 합칠지 판단할 때는, A만 쓰는 청크 그룹의 수, B만 쓰는 청크 그룹의 수, A+B 둘 다 쓰는 청크 그룹의 수를 계산하고 각 시나리오의 확률로 비용/이득을 가중합니다. 마지막으로 한 페이지만 방문하는 경우와 두 페이지 이상 방문하는 경우의 확률로도 가중치를 매기는데, 대략 세션의 2/3는 단일 페이지, 1/3은 두 페이지 이상 방문한다고 추정합니다.

## Next.js 16.3의 새로운 청킹 기능

지금까지의 청킹 알고리즘에는 두 가지 한계가 있었습니다. 첫째, 합치기 결정은 빌드 타임에 이뤄지기 때문에 실제 방문자의 브라우저가 무엇을 이미 캐시하고 있는지 반영할 수 없습니다. 둘째, 알고리즘은 방문자가 사이트를 어떻게 돌아다닐지 추측에 의존할 수밖에 없어서, 단일 페이지 방문에 2/3라는 가중치를 임의로 부여합니다. 이번 여름 Turbopack 팀 인턴십에서 이 두 가지 문제, 그리고 애초에 청크에 담기는 코드량 자체를 줄이는 작업을 진행했습니다.

### 더 똑똑한 청크 페칭

합치기의 비용은 방문자가 A가 포함된 페이지를 보고 이어서 A+B가 필요한 페이지로 이동할 때 A를 두 번 다운로드하게 되는 것이었습니다. 번들러는 빌드 타임에 브라우저가 무엇을 이미 갖고 있는지 알 수 없지만, 런타임은 알 수 있습니다.

Next.js 16.3 이상에서 `next.config.js`의 `experimental.turbopackChunking.generateComponentChunks`를 활성화하면 Turbopack이 합쳐진 청크와 함께 합치지 않은 버전의 청크도 함께 생성합니다. 각 병합 청크를 구성하는 항목들과 이미 로드된 항목을 추적해서, 요청 시점에 더 저렴한 쪽(병합된 청크 전체 또는 누락된 조각만)을 선택할 수 있게 됩니다.

반대의 경우도 마찬가지로 작동합니다. 방문자가 이미 병합된 A+B를 로드했다면 A를 단독으로 다시 로드하는 걸 건너뛸 수 있습니다.

이렇게 하면 소프트 내비게이션에서 불필요한 코드를 덜 로드하면서도 합치기의 이점은 그대로 누릴 수 있습니다. (원문에는 이 차이를 보여주는 데모 앱 링크가 함께 제공되었습니다.)

또한 `only-if-cached` 지시자를 활용해 방문자가 사이트에 도착했을 때 이미 캐시된 것이 무엇인지 확인하는 실험도 진행 중입니다. 이렇게 되면 사이트를 떠났다가 나중에 다시 돌아오는 방문자에게도 같은 개선 효과를 확장할 수 있습니다.

### 애널리틱스 기반 청킹

청킹 알고리즘은 웹사이트에 대해 많은 가정을 전제로 합니다. 앞서 나온 2/3 가중치도 하나의 추정치일 뿐입니다. 많은 사이트에 대체로 맞는 기본값이긴 하지만, 특정 사이트에는 정확하지 않을 수 있습니다. 실제 방문자가 사이트를 어떻게 이동하는지 알고 있다면 이제 그 정보를 직접 알려줄 수 있습니다.

`next.config.js`의 `experimental.turbopackChunking`에서 다음을 설정할 수 있습니다.

- **firstPageLoadPriority**: 단일 페이지 방문과 두 페이지 이상 방문 사이의 가중치를 조정합니다. 0~1 사이 값으로, 값이 높을수록 내비게이션 성능을 희생해서라도 최초 로드 속도를 우선시합니다. 이탈률(bounce rate)을 초깃값으로 쓰는 것도 합리적이며, 기본값은 0.67입니다.
- **priorityRoutes**: 로드 속도가 가장 중요한 페이지 목록입니다. 이 라우트들에서는 청크를 더 적극적으로 합칩니다.
- **clusters**: 함께 자주 방문되는 라우트 그룹으로, 각각 정규식 배열로 정의합니다. 클러스터 안에서는 겹치는 청크를 더 적극적으로 합칩니다. 단, 클러스터에 A만 쓰는 페이지나 B만 쓰는 페이지가 A+B를 함께 쓰는 페이지와 섞여 있다면 합치기를 덜 적극적으로 수행합니다.

### 청크를 더 작고 더 적게

지금까지는 코드를 어떻게 묶을지에 대한 이야기였다면, 마지막은 애초에 더 적은 코드를 전송하는 방법입니다. 다음 기능들을 작업했습니다.

- **CJS 모듈 트리 셰이킹**: 지금까지는 ESM에만 트리 셰이킹을 지원해서 CJS 모듈의 사용하지 않는 import/export도 클라이언트로 그대로 전송되고 있었습니다. `experimental.turbopackCjsTreeShaking`으로 활성화할 수 있으며, 향후 버전에서는 기본으로 켜질 예정입니다. 아울러 분석하고 트리 셰이킹할 수 있는 ESM 모듈의 범위도 넓혔는데, 동적 import 안의 배럴 파일(barrel file) 지원 개선도 포함됩니다.
- **공유 Turbopack 런타임**: 페이지마다 따로 있던 런타임 청크를 하나의 공유 런타임 청크로 대체합니다. `experimental.turbopackSharedRuntime`으로 활성화할 수 있으며, 최초 로드 이후의 모든 내비게이션에서 블로킹 요청 하나와 약 10KB의 클라이언트 JS를 절약합니다. 이 역시 향후 기본으로 켜질 예정입니다.
- **더 가벼운 기본 런타임**: 런타임이 기본적으로 WebAssembly와 Web Worker 코드를 포함하지 않도록 변경했습니다. 해당 모듈을 실제로 사용하는 경우에만 로딩 코드를 삽입합니다.

이 새로운 기능들은 Next.js 16.3 이상 버전에서 사용해볼 수 있습니다.

## 정리

- 청킹은 "요청 수를 줄일 것인가, 다운로드 코드량을 줄일 것인가"라는 트레이드오프 사이의 균형점을 찾는 문제입니다. 하나의 거대한 청크, 페이지별 청크, 모듈별 청크 모두 각자의 극단적인 단점을 갖습니다.
- Turbopack은 청크 그룹(함께 로드되는 청크의 묶음) 단위로만 병합을 수행해 과다 전송을 막고, 방문자의 단일 페이지 방문/다중 페이지 내비게이션 확률을 가중치로 삼아 합칠 가치가 있는 청크를 판단합니다.
- 실측 결과 nextjs.org에서는 Turbopack 기본 설정이 합치지 않는 방식 대비 요청 수를 절반 이하로 줄이면서 코드량도 소폭 줄였고, 무조건 최대로 합치는 방식은 요청 수는 더 줄지만 전체 전송량은 10% 늘어났습니다.
- Next.js 16.3에서는 `generateComponentChunks`로 런타임에 병합/비병합 청크 중 더 저렴한 쪽을 선택하고, `firstPageLoadPriority`·`priorityRoutes`·`clusters` 설정으로 사이트별 실제 이동 패턴을 반영할 수 있게 되었으며, CJS 트리 셰이킹·공유 런타임·경량 기본 런타임으로 애초에 전송되는 코드량 자체도 줄였습니다.
- 실무에서는 사이트의 실제 이탈률과 페이지 이동 패턴을 파악해 `firstPageLoadPriority`나 `clusters` 같은 설정을 조정하면, 기본값보다 더 최적화된 청킹 전략을 적용할 수 있습니다.
