## 아티클

# 바이브 코딩 실전: 휴가 중에도 PR 52개를 머지한 방법

Theo(T3.gg)는 회사와 유튜브 채널 운영에 집중하면서 예전만큼 코드를 짤 시간이 없어졌다고 고백합니다. 그런데 최근 T3 Chat 저장소의 기여 그래프를 보면 주당 PR 머지 개수가 1~3개에서 23개, 37개, 41개, 급기야 52개까지 치솟았습니다. 심지어 52개를 기록한 주는 데프콘(DefCon) 출장 중이었고, 비행기와 우버 안에서, 그리고 호텔의 형편없는 인터넷으로 작업한 결과였다는데요. 이 글에서는 그가 어떻게 "파트타임 코더"임에도 이 정도 생산성을 낼 수 있었는지, 실제 워크플로우와 프롬프트 작성법을 그대로 뜯어봅니다.

## 인프라: 노트북이 병목이 되지 않게 하라

Theo가 강조하는 첫 번째 원칙은 "작업이 절대 자신의 로컬 컴퓨터에서 실행되면 안 된다"는 것입니다. 다른 작업(이메일, 촬영, 스폰서 업무 등)을 하고 있는 노트북이 AI 에이전트 작업 때문에 발목 잡히거나 병목이 되어서는 안 된다는 의미입니다.

그의 실제 셋업은 이렇습니다.

- 다른 방에 스펙이 과도하게 좋은(사실 그럴 필요도 없는) 리눅스 박스를 두고, 여기에 모든 코드베이스와 T3 Code 서버를 올려둡니다.
- T3 Code에서 이 리눅스 박스(BB1)를 실행 대상으로 선택하면, 해당 머신이 가진 harness, codec, Claude 등을 그대로 활용해 작업이 진행됩니다.
- 작업은 워크트리(worktree) 단위로 진행합니다. 워크트리가 지금 존재하는 문제들에 대한 최선의 해법이라고는 생각하지 않지만, 파일시스템이 이를 잘 처리해준다면 여러 개를 동시에 띄워놓고 쓰기에 충분히 괜찮은 추상화라고 설명합니다.

이런 구조 덕분에 자신은 다른 일을 하면서도 백그라운드에서 여러 개의 에이전트 스레드가 동시에 돌아가게 만들 수 있다는 것이 핵심입니다.

## 실제 워크플로우: 새 스레드 → 붙여넣기 → 원격 실행

Theo가 보여주는 실전 절차는 매우 단순합니다.

1. 새 스레드 생성 (단축키로 실행)
2. 내용 붙여넣기
3. 로컬이 아닌 원격 머신(BB1)에서 실행되도록 지정

여기에 손을 다쳐서 음성 인식 도구인 Whisper Flow를 활용해 말로 프롬프트를 작성하는 모습도 보여줍니다.

## 프롬프트 설계: 목표, 우선순위, 예외를 명확히 구분하기

이번 영상에서 실제로 다룬 버그는, 컴포저에서 `$` 기호로 스킬(skill)을 호출할 때 프로젝트 안팎을 가리지 않고 잘 작동하지만, 만약 스킬이 "수동 호출만 가능(manually invoked only)"으로 설정돼 있으면 `$` 방식은 동작하지 않고 반드시 `/` 슬래시 커맨드로만 호출된다는 이슈였습니다. 슬래시 커맨드는 모델이 스스로 트리거할 수 없는 스킬도 활성화할 수 있지만, `$` 방식은 그렇지 못하다는 게 원인입니다. Theo 본인도 수동 전용 스킬을 거의 쓰지 않아서 몰랐던 버그라고 인정합니다.

이 문제를 해결하기 위해 그가 실제로 음성으로 작성한 프롬프트는 다음과 같습니다.

> "This is an issue that's been affecting a number of users as of recent. I was unaware of it till now. I want to make a fix that is both simple in its implementation and not confusing to users when they try to use it. In my opinion, you should be able to use the dollar sign to call any skill anywhere in the composer and have it link correctly. I'm not sure about the characteristics in cloud code as to how these behaviors are triggered or even how the skill that I'm seeing in the composer becomes the right text for the model to add it in. I want you to do a thorough audit of both Claude Code's behavior as well as how we are implementing that behavior. If you see a simple fix that we can apply to solve the problem, stop and let me know so we can apply it ASAP. Come back when you have a confident solution to the problem with a good experience for our users."

이 프롬프트를 문장 단위로 뜯어보면 다음과 같은 설계 원칙이 담겨 있습니다.

- **"많은 사용자에게 영향을 주고 있다"**: 필수는 아니지만, 이 작업이 사이드 프로젝트 수준이 아니라 실제 사람들에게 영향을 주는 중요한 문제라는 맥락을 심어줘 모델이 실험적으로가 아니라 신뢰성 있게 접근하도록 유도합니다.
- **"단순하고 사용자에게 혼란스럽지 않게"**: 속도나 디테일보다 단순함과 명확한 사용자 경험을 우선순위로 명시합니다. 이 문장은 "타협 불가(no compromise)" 라인이라고 강조합니다. 명확한 기대치를 못박아 둔 것입니다.
- **"제 생각에는(in my opinion)"**: 이 표현을 붙여서, 만약 자신의 접근 방식이 타당하지 않다면 모델이 정직하게 이를 지적하고 반박할 여지를 열어둡니다. 이런 일회성 이슈에는 Matt Grilling 스킬 같은 걸 쓸 수도 있지만, 50개 질문에 답하게 만들 필요는 없다고 판단해 이렇게 처리했습니다.
- **"확실하지 않다(I'm not sure about)"**: 자신의 이해 수준이 어디까지인지 명시적으로 알려줍니다. 이는 모델이 이슈 설명이나 자신이 알려준 내용을 맹신하지 않게 만들고, 동시에 자신이 이해하지 못하는 부분을 응답할 때 더 자세히 설명하도록 유도하는 이중 효과가 있습니다.
- **"철저히 감사(audit)해달라"**: 이건 명확한 요청(ask)입니다. 앞서 말한 "최종 목표(전체적으로 원하는 결과)"와는 별개로, 이번 스레드에서 구체적으로 무엇을 해야 하는지 지정한 것입니다. 자신이 코드베이스 구조를 알고 있기 때문에 문제의 원인이 어디 있는지도 특정해줍니다.
- **"간단한 해결책을 찾으면 멈추고 알려달라"**: 에이전트가 4~5개의 서브 에이전트를 동원해 여러 방향을 탐색하고 있을 때, 확신이 서는 순간 곧바로 멈추고 보고할 수 있는 권한을 부여하는 문장입니다. 굳이 17가지 옵션 중 하나를 억지로 골라낼 때까지 무한정 탐색하지 않도록 하는 장치입니다.
- **"확신이 드는 해결책(confident solution)을 갖고 돌아와달라"**: "코드"가 아니라 "해결책"이라고 명시함으로써, 코드를 직접 작성하지 말고 먼저 방안을 제시하라는 의도를 분명히 합니다. Theo는 이렇게 명시적으로 말하지 않으면 모델은 "하고 싶은 대로" 행동한다고 강조합니다.

프롬프트를 완성한 뒤에는 굳이 기다리고 싶지 않다는 이유로 풀 액세스(full access) 모드로 전환하고, "왜 안 되겠어"라는 태도로 사고 강도(reasoning effort)를 최고 수준으로 올려서 실행시킵니다.

## 알아두면 좋은 버그: 스킬 트리거 방식

영상 중간에 스트리밍 시청자가 제보한 실전 팁도 소개됩니다. `$` 기호로 스킬을 트리거하는 방식은 프로젝트 내부/외부 스킬 모두에 잘 작동하지만, 만약 해당 스킬이 "수동으로만 호출 가능(manually invoked only)"으로 설정되어 있다면 `$` 방식으로는 절대 작동하지 않고 오직 `/` 슬래시 커맨드로만 호출됩니다. 슬래시 커맨드는 모델이 스스로 트리거할 수 없는 스킬조차 활성화할 수 있는 유일한 경로이기 때문입니다. Theo는 수동 전용 스킬을 거의 쓰지 않아서 이 버그를 지금까지 몰랐다고 밝힙니다.

## 정리

- **로컬 머신을 병목으로 만들지 마라**: 다른 방의 별도 리눅스 박스에 코드베이스와 에이전트 서버를 올려두고, 워크트리 단위로 여러 작업을 동시에 원격 실행하는 구조가 핵심입니다.
- **프롬프트는 목표·우선순위·예외를 분리해서 써라**: "무엇을 해야 하는지(최종 목표)", "무엇이 타협 불가능한 원칙인지", "어디까지가 확실하고 어디부터는 모델이 스스로 판단해야 하는지"를 각각 다른 문장으로 명확히 구분해서 전달해야 합니다.
- **모델에게 멈출 권한을 줘라**: "확신이 서면 바로 멈추고 알려달라"는 지시를 넣으면, 불필요하게 모든 경우의 수를 다 탐색할 때까지 기다릴 필요가 없어집니다.
- **명시하지 않으면 모델은 알아서 행동한다**: "코드가 아니라 해결책을 가져와달라"처럼 원치 않는 행동을 막으려면 반드시 명시적으로 적어야 합니다. 그렇지 않으면 모델은 자기 판단대로 움직입니다.
- **`$` 트리거와 슬래시 커맨드의 차이를 알아두자**: 수동 전용 스킬은 `$`로 호출되지 않고 반드시 `/` 슬래시 커맨드가 필요하다는 점은 실무에서 놓치기 쉬운 세부 사항입니다.
