!important 없이 우선순위 정하기 — @layer와 :is()·:where()

스타일이 안 먹을 때 붙이는 !important가 왜 다음 충돌을 부르는지, 캐스케이드 레이어와 명시도 조절로 같은 문제를 어떻게 푸는지 MDN 근거로 정리합니다.

요약

  • !important는 명시도와 선언 순서를 건너뛰고, 같은 출처·레이어 안에서 맨 위로 올라갑니다 [1][2].
  • @layer로 레이어 순서를 먼저 선언하면, 나중 레이어의 규칙이 명시도와 상관없이 이깁니다 [1][3].
  • :is()는 인자 중 가장 높은 명시도를, :where()는 항상 0을 가지므로 선택자 무게를 올리고 내리는 데 쓸 수 있습니다 [4][5].
  • 유틸리티 클래스, 동작 줄이기 설정, 사용자 스타일시트처럼 "항상 적용"이 의도인 곳에서는 !important가 여전히 맞는 도구입니다 [1][2].

!important가 캐스케이드에서 하는 일

두 규칙이 같은 요소의 같은 속성을 지정하면, 브라우저는 캐스케이드(cascade) 알고리즘으로 하나만 고릅니다. 중요도, 출처, 레이어, 명시도, 선언 순서를 차례로 비교하고, 앞 단계에서 승자가 정해지면 뒤 단계는 보지 않습니다 [6]. !important를 이해하려면 이 순서에서 명시도가 어디쯤 있는지부터 알아야 합니다.

명시도는 세 칸짜리 점수입니다

명시도(specificity)는 선택자의 무게입니다. MDN은 이를 ID - CLASS - TYPE 세 칸으로 셉니다 [4]. ID 선택자는 첫 칸, 클래스·속성 선택자·의사 클래스는 둘째 칸, 타입 선택자와 의사 요소는 셋째 칸에 1씩 더합니다. 전체 선택자 *와 :where()는 0-0-0입니다 [4].

p { color: gray; }               /* 0-0-1 */
.button { color: blue; }         /* 0-1-0 */
#header .button { color: red; }  /* 1-1-0 */

비교는 왼쪽 칸부터 합니다. ID 칸이 크면 나머지 칸은 보지 않고 이깁니다 [4]. 세 칸이 모두 같으면 나중에 선언된 규칙이 이깁니다 [4]. 인라인 스타일(style="...")은 이 모든 선택자보다 무겁습니다 [1].

!important는 이 비교를 건너뜁니다

!important를 붙인 선언은 명시도와 선언 순서를 무시하고, 같은 출처와 같은 레이어 안에서 맨 위로 올라갑니다 [1][2].

p {
  color: red !important;
}

#main p {
  color: blue;
}
/* #main p(1-0-1)가 더 무겁지만 문단은 빨간색 */

MDN도 같은 출처·레이어라면 선택자를 아무리 무겁게 써도 중요 선언(important declaration)을 이기지 못한다고 설명합니다 [2]. 중요 선언끼리 부딪치면 그때 다시 명시도를 비교합니다 [2].

왜 한 번 쓰면 번지는가

원문 필자는 !important의 문제를 "캐스케이드와 함께 일하는 대신 우회하는 것"으로 봅니다 [1]. 다크 테마 예제가 대표적입니다.

.button {
  color: red !important;
}

.dark .button {
  color: white;
}
/* .dark .button(0-2-0)이 더 무거워도 버튼은 계속 빨간색 */

이 규칙을 고치려는 다음 사람에게는 두 가지 선택지만 남습니다. 원래의 !important를 지우고 다른 곳이 깨질 위험을 지거나, !important를 하나 더 붙이는 것입니다 [1]. 왜 처음 것을 붙였는지 아무도 모르면 대개 두 번째를 고르게 됩니다.

자주 하는 실수: 단축 속성에 붙이기

단축 속성(shorthand property)에 !important를 붙이면 모든 하위 속성이 중요 선언이 됩니다 [2]. background: blue !important는 background-color만이 아니라 background-image, background-size 같은 하위 속성까지 전부 잠급니다. MDN은 이것을 !important를 피하라고 권하는 여러 이유 중 하나로 듭니다 [2].

캐스케이드 레이어로 순서를 먼저 정하기

캐스케이드 레이어(cascade layers)는 스타일을 우선순위 그룹으로 묶는 기능입니다. 선택자 무게로 싸우는 대신, 어느 그룹이 이길지 미리 선언합니다 [1][6]. @layer는 2022년 3월부터 주요 브라우저에서 쓸 수 있는 Baseline 널리 사용 가능(Widely available) 기능입니다 [3].

레이어 순서 선언하기

@layer 문 하나로 레이어 이름과 순서를 함께 정합니다. 먼저 선언한 레이어가 가장 약하고, 마지막 레이어가 가장 강합니다 [3].

@layer reset, defaults, components, utilities;

@layer defaults {
  a:any-link {
    color: maroon; /* 0-1-1 */
  }
}

@layer utilities {
  [data-color='brand'] {
    color: green; /* 0-1-0 */
  }
}
/* <a data-color="brand">는 초록색: utilities가 나중 레이어 */

레이어 사이에서는 명시도와 선언 순서를 보지 않습니다 [3]. 명시도는 같은 레이어 안에서만 비교됩니다 [1][4]. 순서를 정한 뒤에는 같은 이름으로 @layer를 다시 써서 규칙을 덧붙일 수 있고, 이때 레이어 순서는 바뀌지 않습니다 [3].

외부 CSS를 맨 아래 레이어에 넣기

레이어가 가장 쓸모 있는 곳은 명시도가 높은 서드파티 CSS를 덮어쓸 때입니다 [1]. @import에 layer()를 붙이면 가져온 스타일시트 전체가 그 레이어에 들어갑니다 [3].

@layer framework, components;
@import url('framework.css') layer(framework);

@layer components {
  .card { padding: 2rem; }
}
/* framework.css가 #app .card를 써도 padding은 2rem */

MDN도 외부 스타일을 덮어쓸 때 !important 대신 서드파티 스타일시트를 첫 번째 레이어로 가져오라고 권합니다 [2]. 단, 외부 스타일에 중요 선언이 없을 때만 이 방법이 통합니다 [1][2].

자주 하는 실수: @import 위치

@import는 @charset과 @layer 문을 빼면 모든 규칙보다 앞에 와야 합니다 [3]. 위 예제처럼 @layer framework, components; 문 다음에는 올 수 있지만, @layer components { ... } 블록 뒤에 두면 안 됩니다 [3].

레이어 밖의 스타일이 가장 강합니다

레이어에 넣지 않은 일반 선언은 이름 있는 레이어와 익명 레이어의 일반 선언을 모두 이깁니다 [3]. 레이어를 도입하는 중간 단계에서 이 규칙을 놓치면 "레이어를 마지막에 선언했는데 왜 안 먹지?"라는 일이 생깁니다.

p {
  color: rebeccapurple;
}

@layer type {
  .box p {
    color: green; /* 명시도는 더 높지만 레이어 안 */
  }
}
/* .box 안의 p는 보라색 */

레이어 밖 규칙이 먼저 선언됐어도 결과는 같습니다 [3].

!important는 레이어 순서를 뒤집습니다

중요 선언에서는 레이어 순서가 거꾸로 됩니다. 먼저 선언한 레이어의 중요 선언이 가장 강하고, 레이어 밖의 중요 선언이 가장 약합니다 [6][2].

@layer defaults, components, utilities;
/* 강한 순서
   1. defaults의 !important
   2. components의 !important
   3. utilities의 !important
   4. utilities 일반 선언
   5. components 일반 선언
   6. defaults 일반 선언 */

원문 필자는 그래서 레이어 안의 !important를 "맨 위로 뛰어오르는 지름길"이 아니라 "아래 레이어가 이 스타일은 꼭 지켜야 한다고 주장하는 방법"으로 봅니다 [1]. utilities에 !important를 붙여 이기려 하면 오히려 defaults의 !important에 집니다.

선택자 무게 싸움 대신레이어 순서를 먼저

선택자 명시도 조절하기

레이어를 당장 도입하기 어렵다면 선택자 자체의 무게를 조절할 수 있습니다. 올리는 방법과 내리는 방법이 모두 있습니다.

:is()로 무게 올리기

:is() 자체는 무게가 없고, 인자 목록 중 가장 무거운 선택자의 명시도를 가져옵니다 [4]. 그래서 요소와 맞지 않아도 되는 ID를 인자에 끼워 넣어 무게만 올릴 수 있습니다 [1][4].

:is(p, #fakeId) { }   /* 1-0-0 */
p:not(#fakeId) { }    /* 1-0-1 */

원문의 예제는 #sidebar a에 밀리는 .nav-link를 이렇게 올립니다 [1].

#sidebar a {
  color: gray;  /* 1-0-1 */
}

.nav-link {
  color: blue !important; /* 피하고 싶은 방법 */
}

a:is(#some_id, .nav-link) {
  color: blue;  /* 1-0-1, 나중 선언이라 이김 */
}

자주 하는 실수: 계산을 끝까지 하지 않기

원문은 :is(#some_id, .nav-link)만 써서 ID 수준으로 올렸다고 설명합니다 [1]. 하지만 MDN 계산법대로 세면 이 선택자는 1-0-0이고, #sidebar a는 1-0-1입니다 [4]. ID 칸이 같으니 TYPE 칸에서 #sidebar a가 이깁니다. 위 예제처럼 a를 붙여 1-0-1로 맞추고 뒤에 선언하거나, 상대 선택자보다 확실히 무겁게 만들어야 합니다.

또 하나, #some_id가 실제 마크업에 있으면 그 요소에도 스타일이 적용됩니다 [1]. 쓰지 않는 ID를 골라야 합니다.

:where()로 무게 내리기

:where()는 인자와 관계없이 명시도가 항상 0입니다 [5]. 나중에 누구든 쉽게 덮어써야 하는 리셋이나 기본 스타일에 맞습니다 [1].

:where(ul, ol) {
  padding: 0;        /* 0-0-0 */
}

.menu {
  padding: 1rem;     /* 0-1-0 → 이김 */
}

:is()로 썼다면 :is(ul, ol)는 0-0-1이라 결과는 같지만, 인자에 클래스가 들어가는 순간 차이가 납니다. MDN 예제에서 :is(section.is-styling, aside.is-styling, footer.is-styling) a는 나중의 footer a에 덮이지 않고, 같은 인자를 :where()로 감싼 쪽만 덮입니다 [5].

자주 하는 실수: 출처까지 0이 되는 줄 알기

:where()는 명시도만 0으로 만듭니다. 출처는 그대로라서, 0-0-0인 작성자 스타일도 브라우저 기본 스타일(a:any-link, 0-1-1)을 이깁니다 [6]. 명시도는 서로 다른 출처 사이에서는 비교하지 않기 때문입니다 [6].

같은 선택자 반복하기

클래스를 두 번 이어 쓰면 같은 요소를 고르면서 무게만 늘어납니다 [1].

.button {
  color: blue;  /* 0-1-0 */
}

.button.button {
  color: red;   /* 0-2-0 → 이김 */
}

가장 간단하지만, 원문 필자는 자주 쓰면 읽기 어려워진다고 봅니다 [1]. 임시방편으로만 쓰고 이유를 주석으로 남기는 편이 좋습니다.

선언 순서 바꾸기

명시도가 같으면 나중 규칙이 이깁니다 [4]. 일반적인 규칙이 계속 이긴다면, 무게를 올리기 전에 그 파일이 내 파일보다 늦게 로드되는지부터 확인합니다 [1]. 원문은 리셋·기본 → 레이아웃 → 컴포넌트 → 유틸리티처럼 일반적인 것에서 구체적인 것으로 파일을 배치하는 방식을 권합니다 [1]. 이 순서는 그대로 @layer 선언 순서가 되기도 합니다.

!important가 맞는 자리

원문 필자는 좋은 !important와 나쁜 !important의 차이를 의도에서 찾습니다. 캐스케이드를 이해하고 "이 선언은 항상 적용돼야 한다"고 판단했는지, 임시 반창고로 붙였는지입니다 [1].

한 가지 일을 어디서나 해야 하는 유틸리티

.visually-hidden 같은 유틸리티 클래스는 어디에 붙든 같은 일을 해야 합니다 [1]. 더 무거운 선택자가 조용히 풀어 버리면 의미가 없습니다.

.visually-hidden {
  position: absolute !important;
  width: 1px !important;
  height: 1px !important;
  overflow: hidden !important;
  clip-path: inset(50%) !important;
}

사용자 설정을 존중할 때

사용자가 동작 줄이기를 켰다면 모든 애니메이션을 사실상 끄는 규칙이 어떤 컴포넌트 스타일에도 밀리면 안 됩니다 [1].

@media screen and (prefers-reduced-motion: reduce) {
  * {
    animation-duration: 0.001ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.001ms !important;
  }
}

사용자 스타일시트도 같은 이유입니다. 사용자 출처의 중요 선언은 작성자 출처의 중요 선언을 이기므로, 큰 글꼴이 필요한 사용자는 사이트에 !important가 있어도 자기 스타일을 적용할 수 있습니다 [2]. 원문 필자는 이 경우 !important가 사실상 유일하게 믿을 수 있는 방법이라고 봅니다 [1].

쓸 때는 주석을 남깁니다

MDN은 UI 요구 사항 때문에 일부러 중요 선언을 만들 때, 유지보수하는 사람이 덮어쓰지 말아야 하는 이유를 CSS 주석으로 남기라고 권합니다 [2]. "왜 붙였는지 아무도 모른다"는 상황이 !important가 번지는 출발점이기 때문입니다 [1].

정리

상황 !important 대신 근거
서드파티 CSS가 너무 무거움 @import ... layer(framework)로 맨 아래 레이어에 넣기 [3][2]
스타일 그룹 간 우선순위 충돌 @layer reset, defaults, components, utilities; [1][3]
특정 규칙 하나만 조금 더 무겁게 a:is(#some_id, .nav-link) 또는 .button.button [1][4]
리셋이 컴포넌트를 덮어씀 :where(...)로 명시도 0 만들기 [5]
명시도가 같은데 엉뚱한 규칙이 이김 로드·선언 순서 확인 [1][4]
유틸리티, 동작 줄이기, 사용자 스타일 !important 유지 + 이유 주석 [1][2]

!important를 하나 지울 때마다 "이 충돌은 어느 단계에서 풀려야 하나"를 먼저 묻습니다. 그룹 간 문제면 레이어, 규칙 하나의 문제면 명시도, 둘 다 아니면 순서입니다.

프론트엔드 팀이 해 볼 것

  1. 프로젝트에서 !important를 검색해 유틸리티·접근성 용도가 아닌 것을 골라내고, 각각 레이어·명시도·순서 중 어디서 풀 문제인지 표시해 보세요.
  2. 서드파티 CSS 하나를 @import url(...) layer(...)로 가장 먼저 선언한 레이어에 넣고, 덮어쓰던 !important를 지운 뒤 화면이 같은지 확인하세요.
  3. 리셋 스타일의 선택자를 :where()로 감싸고, 개발자 도구 Styles 패널에서 취소선이 그어진 선언이 어떻게 바뀌는지 비교하세요.
