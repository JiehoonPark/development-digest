규칙을 적었다고 안전해질까 — AI 코딩 에이전트 하네스

규칙 파일은 방향을 알려 주고, 권한과 훅은 실행 범위를 제한합니다. 도구·스킬·검증 루프까지 연결해 에이전트의 완료 주장을 확인 가능한 결과로 바꾸는 방법을 정리합니다.

요약

  • 규칙 파일은 판단에 쓰는 문맥이지 행동을 강제로 막는 설정이 아닙니다.[1]
  • 실행 전 훅은 도구 호출을 차단할 수 있지만, 실행 후 훅은 이미 성공한 호출 뒤에 동작합니다.[2]
  • 스킬은 작업별 절차를 필요할 때 불러오는 수단이고, 권한·샌드박스는 실행 범위를 다루는 별도 장치입니다.[3][4][5]

팀 저장소에 코딩 에이전트를 들인다면

팀 저장소에 코딩 에이전트를 들이는 일을 맡았다고 가정해 봅시다. 첫 작업은 할인 금액 계산 함수를 고치는 것입니다. 실제 회사 사례가 아니라, 실행과 검증의 책임을 나누기 위한 가정입니다.

  • 할인 뒤 원 미만을 버린다는 기존 동작 계약을 지킵니다.
  • 이번 작업에서는 구현만 고치고, 기존 검사를 삭제하거나 기대값을 약화하지 않습니다.
  • 의존성 추가·외부 통신·배포는 작업 범위에 넣지 않습니다.
  • 완료 보고에는 변경 파일, 실제 검사 결과, 확인하지 못한 항목을 구분합니다.

요청을 자세히 쓰는 것은 출발점입니다. 하지만 “검사를 지우지 마세요”를 읽었다고 검사 파일을 바꿀 수 없게 되는 것은 아닙니다. Claude Code 공식 문서도 규칙 파일을 강제 설정이 아니라 문맥으로 설명합니다.[1]

이 글에서 **하네스(harness)**는 모델에 정보를 주고, 도구 실행을 관리하고, 결과를 다음 판단으로 돌려주는 실행 계층을 뜻합니다. 특정 제품이나 표준 파일의 이름으로 쓰는 말은 아닙니다. 기존 에이전트 제품 위에 팀의 규칙·제한·검사를 연결하는 관점으로 이해하면 됩니다.

설정과 동작 설명은 2026-11 문서 기준입니다. 제품 세션을 유료로 실행한 비교 실험은 하지 않았습니다. 아래 훅은 로컬에서 독립 실행하며, 제품에 설정이 실제로 연결됐는지는 별도로 확인해야 합니다. 기존 글 「PR 리뷰 봇을 코드로 만든다 — Cursor Agent SDK 정리」가 봇 제작과 배포를 다뤘다면, 여기서는 저장소에서 무엇을 허용하고 무엇을 완료 증거로 삼을지에 집중합니다.

하네스의 구성 요소는 서로 대신할 수 없습니다

규칙 파일과 스킬: 항상 필요한 사실과 작업별 절차

규칙 파일은 프로젝트 구조, 실행 명령, 변경 금지 범위처럼 매번 설명해야 하는 배경입니다. Claude Code의 CLAUDE.md와 Codex의 AGENTS.md가 대표적이며, AGENTS.md는 에이전트용 빌드·검사·관례를 담는 일반 Markdown 형식입니다.[1][6][7]

다음은 가정한 할인 프로젝트의 규칙 내용입니다. 제품 설정 키가 아니라 사람이 작성하는 지침이며, 명령과 경로는 해당 프로젝트에 맞춰야 합니다.

- 구현은 src/price.mjs, 계약 검사는 tests/price.test.mjs에 있습니다.
- 이번 작업에서는 기존 검사와 기대값을 바꾸지 않습니다.
- 수정 뒤 node --test tests/price.test.mjs를 실행합니다.
- 변경 파일·검사 결과·미검증 항목을 나누어 보고합니다.

문서를 길게 만드는 것보다 실제 적용 범위를 확인하는 편이 먼저입니다. Codex는 프로젝트 루트부터 현재 작업 디렉터리까지 지침을 모으며, 더 가까운 디렉터리의 지침이 뒤에 붙어 앞선 지침을 덮어씁니다.[6] 파일이 존재한다는 사실만으로 지금 작업에 적용됐다고 단정하면 안 됩니다.

스킬(skill)은 특정 작업의 지침·참고 자료·선택적 스크립트를 묶은 재사용 절차입니다. Claude Code는 스킬 본문을 사용할 때 읽으며, Codex도 이름과 설명을 먼저 보고 필요한 SKILL.md 본문을 읽습니다.[4][5] 늘 필요한 계약은 규칙에 남기고, 할인 기능 검토 때만 필요한 다음 절차는 스킬로 분리할 수 있습니다.

할인 기능 검토 절차의 예
입력 단위와 유효 범위 확인
→ 원 미만 처리와 경계값 검사
→ 기존 기대값이 약해지지 않았는지 확인
→ 실행 결과와 미검증 범위 보고

실수하기 쉬운 지점은 스킬을 읽은 것을 실행 완료로 취급하는 것입니다. 절차를 읽었다면 이제 검사를 할 준비가 된 것이지, 검사 결과가 생긴 것은 아닙니다. 규칙과 스킬은 설명을 배치하는 방법이고, 다음의 실행 장치를 대체하지 않습니다.

도구와 권한·샌드박스: 할 수 있는 일과 해도 되는 일

도구(tool)는 모델의 제안을 실제 파일 변경이나 명령 실행으로 연결하는 통로입니다. 모델 컨텍스트 프로토콜(MCP)은 서버가 이름과 입력 스키마를 가진 도구를 노출하고, 클라이언트가 목록을 조회하거나 호출하는 규약입니다.[8] 외부 시스템을 연결할 수 있다는 뜻이지 연결한 시스템이 자동으로 안전해진다는 뜻은 아닙니다.

권한(permission)은 어떤 도구와 자원에 접근하도록 허용할지 결정합니다. 샌드박스(sandbox)는 셸 명령과 자식 프로세스의 파일시스템·네트워크 접근을 운영체제 수준에서 제한합니다. Claude Code 문서는 이 둘을 상호 보완하는 계층으로 구분합니다.[3]

“외부 통신을 하지 말라”는 문장, 통신 도구를 허용하지 않는 권한, 명령의 네트워크 접근을 격리하는 샌드박스는 역할이 다릅니다. 처음에는 파일 읽기와 필요한 검사처럼 범위를 좁게 잡고, 쓰기·셸·외부 연동이 각각 어떤 경계를 갖는지 적는 편이 좋습니다. 권한 질문이 번거롭다는 이유만으로 제한을 모두 푸는 것은 문제를 해결한 것이 아니라 제한을 없앤 것입니다.

훅과 검증 루프: 실행 시점과 완료 조건

훅(hook)은 정해진 이벤트에서 자동으로 실행되는 처리입니다. Claude Code의 PreToolUse는 도구 호출 전, PostToolUse는 호출 성공 후에 실행됩니다.[2] 명령 훅은 이벤트 정보를 표준 입력의 JSON으로 받으므로, 모델에게 다시 판단을 요청하지 않고 정해진 조건을 코드로 검사할 수 있습니다.[2]

검증 루프는 수정 결과를 검사하고, 실패 출력을 다음 수정 판단에 전달하는 흐름입니다. 파일 쓰기 성공은 디스크에 내용이 저장됐다는 뜻일 뿐, 할인 계산이 맞다는 뜻이 아닙니다. 완료 조건에는 검사 성공뿐 아니라 검사 대상, 마지막 수정 이후의 결과인지, 사람이 검토해야 할 항목까지 포함해야 합니다.

그림은 책임을 나눈 개념도이지 모든 제품 내부의 고정 실행 순서는 아닙니다. 특히 실행 전 차단과 실행 후 검사를 같은 것으로 생각하면 안 됩니다. 파일 변경을 금지하려면 쓰기 전에 막아야 하고, 구현이 올바른지는 변경 뒤에 검사해야 합니다.

짧은 훅으로 검사 파일 변경을 막아 보기

이번 예제에서는 기존 계약 검사를 보호하기 위해 검사 폴더를 대상으로 한 편집 요청을 거절합니다. 제품 연결 설정을 먼저 보면 역할이 드러납니다. 프로젝트의 .claude/settings.json에 훅을 정의할 수 있고, matcher는 파일 경로가 아니라 도구 이름을 고릅니다.[2]

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "node hooks/protect-tests.mjs"
      }]
    }]
  }
}

이 설정은 프로젝트 루트에서 실행하는 예시입니다. hooks 안에서 PreToolUse 이벤트를 고르고, matcher로 Edit 또는 Write 호출을 선택하며, type과 command로 실행할 명령을 정합니다.[2] 작업 디렉터리가 달라지는 구성에서는 스크립트 경로도 그 기준에 맞춰 확인해야 합니다.

다음 스크립트를 위 명령이 가리키는 파일로 저장하면 됩니다. hook_event_name, tool_name, tool_input으로 이벤트를 식별하고, 파일 입력의 file_path를 검사합니다.[2]

import fs from 'node:fs';
let event;
try {
  event = JSON.parse(fs.readFileSync(0, 'utf8'));
  if (event?.hook_event_name !== 'PreToolUse'
      || !['Edit', 'Write'].includes(event.tool_name)
      || typeof event.tool_input?.file_path !== 'string') {
    throw new Error('형식 불일치');
  }
} catch {
  console.error('입력 오류: PreToolUse Edit/Write JSON을 확인하세요.');
  process.exit(2);
}
const file = event.tool_input.file_path;
if (['Edit', 'Write'].includes(event.tool_name)
    && file.split(/[\\/]/).includes('tests')) {
  console.error('검사 파일 변경 차단: 구현을 고치고 기존 검사를 유지하세요.');
  process.exit(2);
}

PreToolUse 명령 훅의 종료 코드 2는 도구 호출을 차단하는 신호이며, 표준 오류에 쓴 메시지가 차단 이유로 전달됩니다.[2] 반대로 출력 없이 종료 코드 0으로 끝나면 훅이 판단을 내리지 않은 것이므로 일반 권한 흐름이 이어집니다.[2] 정상 종료는 무조건 승인과 다릅니다.

다음은 독립 실행을 위해 이 스크립트가 읽는 필드만 남긴 입력입니다. 제품이 보내는 전체 이벤트를 재현한 JSON은 아닙니다. Write 입력에서 file_path는 절대 경로, content는 쓸 내용입니다.[2]

{
  "hook_event_name": "PreToolUse",
  "tool_name": "Write",
  "tool_input": {
    "file_path": "/project/tests/price.test.mjs",
    "content": "// 검사를 지운 잘못된 제안\n"
  }
}

이 JSON을 입력 파일로 저장하고 실행합니다. 스크립트는 경로 문자열만 검사하므로 실제 파일을 만들거나 바꾸지 않습니다.

node hooks/protect-tests.mjs < hook-input.json
printf '종료 코드: %s\n' "$?"

위 스크립트에 차단 입력, 소스 파일 경로로 바꾼 입력, 깨진 JSON을 각각 전달해 독립 실행한 결과입니다. 소스 입력은 경로를 /project/src/price.mjs로 바꾸었고, 나머지는 같게 두었습니다.

[차단 입력]
검사 파일 변경 차단: 구현을 고치고 기존 검사를 유지하세요.
종료 코드: 2
[소스 입력]
표준 오류 출력 없음
종료 코드: 0
[깨진 JSON]
입력 오류: PreToolUse Edit/Write JSON을 확인하세요.
종료 코드: 2

이 훅은 검사 폴더가 경로 조각에 포함되는지만 봅니다. 셸로 파일을 쓰거나 심볼릭 링크를 거치는 우회, 다른 편집 도구, 훅 자체의 변조는 막지 못합니다. 따라서 교육용 경로 검사이지 보안 샌드박스가 아닙니다. 또한 JSON 파싱 오류를 처리하는 것과 훅 프로세스가 아예 시작되지 못하는 것은 다른 실패입니다. 다른 종료 코드나 시작 실패를 모두 같은 차단으로 해석하지 말고 제품의 실패 처리 규칙을 확인해야 합니다.[2]

차단이 잘돼도 구현 검사는 남습니다. 같은 할인 문제를 다룬 로컬 실습에서는 정해진 제안을 내는 가짜 모델에 실제 파일 쓰기와 검사를 연결했습니다. 검사를 지우려는 제안을 막은 뒤, 잘못된 반올림 구현의 검사 실패를 다음 판단에 돌려주었을 때만 버림 구현을 선택하게 했습니다. 아래는 그 실습에 남은 실행 기록 일부입니다.

[검사] 종료 코드 1
[피드백] 검사 실패를 가짜 모델에 전달합니다. 다음 구현 후보를 선택합니다.
[검사] 종료 코드 0
[완료] 현재 파일의 검사 통과. 사람의 변경 검토는 별도입니다.

이 기록은 모델 성능의 증거가 아닙니다. 실패에 따라 미리 준비된 구현을 선택하는 실습으로, 실패 결과를 다음 판단에 돌려주는 연결을 확인한 것입니다. 검사 파일을 보존하는 조건과 구현이 검사를 통과하는 조건은 따로 있어야 합니다.

실무에서 부딪히는 문제

다음은 위 구성에서 점검할 수 있는 가상 상황입니다. 특정 팀에서 관측한 발생 빈도나 성과를 뜻하지 않습니다.

규칙은 있는데 다른 검사 명령을 씁니다

증상: 사용하지 않는 패키지 관리자를 고르거나 오래된 명령을 반복합니다. 원인: 작업 위치가 다르거나, 상위·하위 지침이 충돌하거나, 긴 절차에 핵심 명령이 묻혔을 수 있습니다. 대응: 실제 작업 디렉터리와 적용된 지침부터 확인하고, 기본 검사 명령을 짧게 남깁니다. Codex는 현재 디렉터리에 따라 지침 탐색 범위가 달라지므로 이 확인이 필요합니다.[6]

스킬을 더 만드는 것이 먼저는 아닙니다. 누구나 같은 문서로 같은 검사를 실행할 수 있는 상태를 만든 뒤, 특정 기능에만 필요한 절차를 분리합니다.

편집 도구는 막았는데 같은 파일이 바뀝니다

증상: 훅의 차단 로그는 있는데 보호 대상 내용이 달라집니다. 원인: 제한한 편집 도구 밖에서 파일을 썼을 수 있습니다. 대응: 셸·외부 도구를 포함해 쓰기 통로를 목록으로 만들고, 각 통로의 권한과 격리를 확인합니다. 셸과 그 자식 프로세스까지 자원 접근을 제한하는 역할은 샌드박스의 영역입니다.[3]

검사 파일과 훅을 에이전트가 자유롭게 수정할 수 있게 두면서 그 파일만으로 제한을 보장한다고 생각하지 않아야 합니다. 검사 변경이 필요한 작업은 별도 검토로 다루되, 새 테스트 작성까지 무조건 금지하는 정책으로 확대하지 않습니다.

검사는 성공했는데 완료 근거가 없습니다

증상: 성공 메시지는 있지만 실행된 검사 목록이 없거나, 검사 뒤에 구현이 다시 바뀌었습니다. 원인: 다른 폴더에서 검사를 실행했거나 대상이 빠졌거나 이전 결과를 재사용했을 수 있습니다. 대응: 명령·작업 위치·검사 대상·결과를 함께 남기고 마지막 변경 뒤에 다시 검사합니다.

검사가 시작됐다는 사실과 통과했다는 사실도 나눕니다. 화면 기능이라면 함수 검사만으로 클릭 동작과 모바일 배치까지 확인했다고 보고하지 않습니다. 확인하지 못한 부분은 미검증으로 남기는 것이 더 정확합니다.

훅을 늘릴수록 작업이 느려지고 수정이 끝나지 않습니다

증상: 작은 편집마다 전체 검사가 돌거나 같은 오류를 반복해서 고칩니다. 원인: 실행 빈도와 검사 비용, 재시도 중단 조건을 함께 설계하지 않았기 때문입니다. 대응: 편집 직후의 빠른 검사와 완료 전 전체 검사를 나누고, 시도 횟수·총시간·사람에게 넘길 조건을 작업 전에 정합니다.

느린 검사를 생략해 완료 처리하는 대신 기다리는 상태를 분명히 둡니다. 반복 예산이 끝났다면 실패 원인과 현재 변경을 보고하고 멈춰야 합니다. 오래 실행했다는 사실은 완료의 근거가 아닙니다.

새 프로젝트에 세팅한다면

  1. 범위와 완료 조건을 먼저 적습니다. 수정 대상, 건드리지 않을 영역, 필요한 검사와 화면 확인을 정합니다. “잘 동작한다” 대신 무엇을 관찰하면 완료인지 씁니다.
  2. 검사 명령을 사람이 먼저 실행합니다. 원래 실패하던 검사와 이번 변경 때문에 실패한 검사를 나눌 기준을 확보합니다. 실행 위치와 필요한 환경도 함께 기록합니다.
  3. 규칙 파일은 짧게 시작합니다. 구조·명령·변경 경계를 담고 실제 세션에서 읽혔는지 확인합니다. 파일 이름만 맞추고 적용 여부를 생략하지 않습니다.
  4. 권한과 격리를 정한 뒤 훅을 더합니다. 반복해서 막아야 할 명확한 행동만 코드로 검사합니다. 차단 입력뿐 아니라 정상 입력, 깨진 입력, 실행 실패도 확인합니다.
  5. 반복 절차만 스킬로 분리합니다. 어떤 요청에 사용하는지 설명을 분명히 쓰고, 절차의 마지막에는 결과와 미검증 범위를 보고하게 합니다.
  6. 작은 변경으로 전체 경로를 확인합니다. 규칙 읽기부터 도구 실행, 차단, 검사 실패 전달, 재검사까지 이어지는지 봅니다. 통과 결과가 있어도 변경 검토와 배포 승인은 별도로 둡니다.

처음부터 별도 에이전트 프레임워크를 만들 필요는 없습니다. 사용하는 제품의 권한·훅·스킬에 팀의 검사 명령을 연결하고, 실제로 비어 있는 책임만 보완하는 편이 관리할 것이 적습니다.

  • 처음 보는 저장소를 탐색한다면 읽기 중심과 사람 확인을 고릅니다. 검사 경로를 확인하기 전에 쓰기 권한부터 넓히지 않습니다.
  • 반복해서 어기는 명확한 제약이 있다면 실행 전 제한을 더합니다. 모호한 설계 판단까지 경로 검사에 맡기지는 않습니다.
  • 반복 수정을 위임한다면 검증 루프와 중단 조건을 함께 둡니다. 완료 주장 대신 마지막 변경에 대응하는 검사 결과를 받습니다.

좋은 하네스는 규칙 파일의 길이로 결정되지 않습니다. 무엇을 설명하고, 어디서 막고, 어떤 결과로 완료를 판단하는지 구분할 수 있어야 합니다.

프론트엔드 팀이 해 볼 것

  1. 현재 저장소의 검사 명령을 직접 실행하고, 작업 위치·검사 대상·결과를 규칙 초안에 적습니다.
  2. 보호할 파일을 정한 뒤 훅에 차단 입력·정상 입력·깨진 JSON을 각각 전달해 결과를 비교합니다.
  3. 작은 변경 하나를 맡겨 마지막 수정 뒤 검사 결과와 미검증 항목이 구분돼 보고되는지 확인합니다.
