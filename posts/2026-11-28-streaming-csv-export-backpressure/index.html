100만 행 CSV 내보내기, 다 모으지 말고 커서로 읽으며 흘려 보내기

주문 100만 건을 CSV로 내려받는 기능을 세 가지 서버 구현으로 만들어 메모리와 첫 바이트 시간을 재 봅니다. 브라우저에서 받는 두 방법, 엑셀 한글 깨짐을 막는 BOM, 배포 뒤 만나는 취소·중간 오류·서버 멈춤까지 로컬에서 실행해 봅니다.

주문 100만 건 CSV 내보내기를 맡았다고 가정해 봅시다

관리자 화면의 "주문 내역 내려받기" 버튼을 맡았다고 가정해 봅시다. 설계를 설명하려고 정한 요구사항입니다.

  • 기간을 넓게 잡으면 주문이 100만 건을 넘을 수 있습니다.
  • 버튼을 누르면 곧바로 다운로드가 시작돼야 합니다.
  • 내보내기가 돌아가는 동안에도 같은 서버의 다른 API는 느려지면 안 됩니다.
  • 운영팀은 파일을 엑셀에서 더블클릭해 엽니다. 한글이 깨지면 안 됩니다.

가장 쉬운 구현은 주문을 전부 조회해 CSV 문자열 하나로 만들어 보내는 것입니다. 100만 행에서는 이 방식의 메모리와 첫 바이트 시간이 문제가 됩니다. 그래서 같은 데이터를 세 가지 방식으로 내보내며 서버가 무엇을 들고 있는지 재고, 그다음 브라우저와 엑셀 쪽으로 넘어갑니다.

실험 데이터는 직접 만든 주문 100만 행(Node.js 내장 SQLite)이고, 내보낸 CSV는 86.2 MB입니다. 아래 숫자는 제 맥에서 방식마다 서버를 새로 띄워 세 번씩 재고 가운데 값을 적었습니다. RSS는 프로세스가 실제로 차지한 메모리이고, MB는 1024×1024바이트입니다.

서버: 다 모으지 말고 커서로 읽으며 흘려 보내기

다 모아서 보내기

먼저 CSV 한 줄을 만드는 함수 line과, 행을 500개씩 묶어 문자열 조각으로 내놓는 제너레이터를 둡니다. 제너레이터는 yield에서 멈췄다가 다음 값을 달라고 할 때 이어서 실행되는 함수라, 세 방식에서 그대로 씁니다. 측정용 코드는 뺐습니다.

function* csvChunks(rows) {
  let buf = "\uFEFF" + line(HEADER);
  let n = 0;
  for (const r of rows) {
    buf += line([r.id, r.ordered_at, r.customer, r.product, r.qty, r.amount, r.memo]);
    if (++n % 500 === 0) {
      yield buf;
      buf = "";
    }
  }
  if (buf) yield buf;
}

첫 방식은 all()로 모든 행을 배열로 받은 뒤 조각을 이어 붙여 한 번에 보냅니다.

const rows = db.prepare(SQL).all();
const body = [...csvChunks(rows)].join("");
res.writeHead(200, headers);
res.end(body);

86.2 MB를 보내는 동안 서버 메모리가 1310.5 MB까지 올랐습니다. 행 객체 100만 개와 CSV 문자열이 함께 메모리에 있기 때문입니다.

커서로 한 행씩 읽기

커서는 조회 결과를 한꺼번에 넘기지 않고, 요청할 때마다 다음 행을 꺼내 주는 장치입니다. Node.js 내장 SQLite에서는 준비된 문장의 iterate()가 이 역할을 합니다. iterate()는 결과 행을 객체로 하나씩 내놓는 반복자를 돌려줍니다.[3] 이 메서드는 v22.13.0에 추가됐습니다.[3]

이 반복자를 csvChunks에 넘기면 행을 다 읽기 전에 첫 조각이 나옵니다. 남은 문제는 응답에 넣는 속도입니다.

응답에 쓰는 속도를 받는 쪽에 맞추기

HTTP 응답 객체 res는 쓰기 스트림입니다. res.write()는 데이터를 커널 버퍼까지 다 넘겼으면 true, 일부라도 사용자 메모리에 쌓였으면 false를 돌려주고, 버퍼가 비면 'drain' 이벤트를 냅니다.[1] 이렇게 받는 쪽이 느릴 때 보내는 쪽을 멈추게 하는 흐름 조절을 배압(backpressure)이라고 부릅니다. Node.js 안내서는 write()가 false를 돌려줘도 계속 쓰면 버퍼가 끝없이 커지고 메모리 부족으로 이어질 수 있다고 설명합니다.[7]

이 규칙을 직접 지키는 대신 pipeline에 맡깁니다. pipeline은 스트림과 제너레이터를 이으면서 오류를 전달하고 끝나면 정리까지 해 주는 함수입니다.[2] 제너레이터는 Readable.from으로 읽기 스트림으로 바꿉니다. Readable.from은 기본으로 객체 모드를 켜고[2], 객체 모드 스트림의 기본 버퍼 기준은 16개입니다.[2]

res.writeHead(200, headers);
await pipeline(
  Readable.from(csvChunks(db.prepare(SQL).iterate())),
  res,
);

비교를 위해 write()의 반환값을 무시하고 반복문으로 쓰는 버전도 만들었습니다.

for (const chunk of csvChunks(db.prepare(SQL).iterate())) res.write(chunk);
res.end();

stream  최고 RSS 132.8 MB · 첫 바이트 0.009초 · 전체 1.79초
nobp    최고 RSS 373.8 MB · 첫 바이트 1.75초  · 전체 1.78초

pipeline 버전은 첫 바이트가 곧바로 나갔고 메모리도 가장 적었습니다. 반환값을 무시한 버전은 커서를 썼는데도 첫 바이트가 1.75초 뒤에 나갔고, 그동안 86.2 MB가 메모리에 쌓였습니다. 동기 반복문이 끝날 때까지 소켓으로 내보낼 틈이 없었던 것으로 보입니다.

curl 속도를 초당 8 MB로 묶어 한 번씩 재자 둘 다 11.0초가 걸렸지만, 최고 RSS는 pipeline 버전이 107.3 MB, 반환값을 무시한 버전이 373.9 MB였습니다.

브라우저: 링크로 받을까, fetch로 받을까

서버가 이름과 다운로드 여부를 정한다

Content-Disposition 응답 헤더의 attachment는 브라우저에 화면에 띄우지 말고 내려받으라고 알립니다.[4] filename*은 RFC 5987 인코딩을 쓰는 이름이고, 두 이름을 다 이해하는 브라우저는 filename*을 우선하며, 호환성을 위해 둘 다 넣기를 권합니다.[4]

const name = "주문내역_2026-11-28.csv";
const headers = {
  "Content-Type": "text/csv; charset=utf-8",
  "Content-Disposition": `attachment; filename="orders.csv"; filename*=UTF-8''${encodeURIComponent(name)}`,
};

크롬은 이 응답을 주문내역_2026-11-28.csv라는 이름으로 저장했습니다. <a>의 download 속성은 같은 출처 URL과 같은 출처 blob:, data:에서만 동작하고, Content-Disposition의 filename이 download 속성의 이름보다 우선합니다.[8]

두 방법의 시작 시간 비교

데모 페이지의 두 버튼을 크롬 자동화로 눌러 다운로드 시작·끝 시간을 쟀습니다. ①은 링크를 눌러 브라우저에 맡기고, ②는 fetch로 끝까지 받아 Blob을 만든 뒤 저장합니다.

async function downloadViaBlob(url, filename, onProgress) {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  const reader = res.body.getReader();
  const chunks = [];
  let received = 0;
  for (;;) {
    const { done, value } = await reader.read();
    if (done) break;
    chunks.push(value);
    received += value.length;
    onProgress(received);
  }
  const blob = new Blob(chunks, { type: "text/csv;charset=utf-8" });
  const href = URL.createObjectURL(blob);
  const a = document.createElement("a");
  a.href = href;
  a.download = filename;
  a.click();
  setTimeout(() => URL.revokeObjectURL(href), 1000);
  return blob.size;
}

②는 진행률을 직접 그릴 수 있고 요청에 인증 헤더를 넣기 쉽습니다. 대신 파일 전체가 탭 메모리에 올라가고, 다 받기 전에는 다운로드 목록에 아무것도 없습니다. 만든 URL은 revokeObjectURL()로 풀어 줘야 합니다.[9] 서버가 흘려 보내도 받는 쪽이 다 모으면 그 이점이 사라집니다.

엑셀에서 열리는 CSV: BOM과 칸 규칙

앞의 세 바이트

마이크로소프트 지원 문서는 UTF-8 CSV를 BOM(Byte Order Mark)과 함께 저장했으면 엑셀에서 그대로 열 수 있고, 아니면 데이터 가져오기 기능으로 열라고 안내합니다.[5] UTF-8에서 BOM은 바이트 순서와 상관없이 UTF-8임을 알리는 표시로만 쓰이고, 바이트로는 EF BB BF입니다.[10] 위 제너레이터가 맨 앞에 "\uFEFF"를 붙인 이유입니다.

내려받은 파일의 앞 세 바이트와, 같은 바이트를 다른 인코딩으로 읽은 결과입니다. 엑셀 화면이 아니라 TextDecoder로 재현한 것입니다.

쉼표·따옴표·줄바꿈과 수식

RFC 4180은 줄바꿈, 큰따옴표, 쉼표가 든 칸을 큰따옴표로 감싸고, 칸 안의 큰따옴표는 큰따옴표 하나를 더 붙여 나타낸다고 정리합니다.[11] 레코드 구분은 CRLF입니다.[11]

또 하나는 수식 주입(CSV Injection)입니다. 스프레드시트 프로그램은 =로 시작하는 칸을 수식으로 해석하고, OWASP는 =, +, -, @, 탭, CR, LF로 시작하는 칸을 위험하다고 봅니다.[6] 칸 앞에 작은따옴표를 붙이는 대응도 소개하지만, 엑셀에서 저장했다 다시 열면 믿을 수 없다고 경고합니다.[6]

export function cell(v) {
  if (v === null || v === undefined) return "";
  if (typeof v === "number") return String(v);
  let s = String(v);
  if (/^[=+\-@\t\r]/.test(s)) s = "'" + s;
  if (/[",\r\n]/.test(s)) s = `"${s.replaceAll('"', '""')}"`;
  return s;
}

export const line = (cols) => cols.map(cell).join(",") + "\r\n";

기계식 키보드, 갈축   →   "기계식 키보드, 갈축"
선물 포장 "리본" 부탁   →   "선물 포장 ""리본"" 부탁"
1층 도착 시\n전화 주세요   →   "1층 도착 시\n전화 주세요"
=HYPERLINK("http://example.com","확인")   →   "'=HYPERLINK(""http://example.com"",""확인"")"
-5   →   '-5
12900   →   12900

숫자형은 검사하지 않으므로 금액은 숫자로 남지만, 문자열로 저장된 -5는 '-5가 됩니다. 이 파일을 다른 프로그램이 다시 읽는다면 이 규칙도 함께 알려야 합니다.

배포 뒤 부딪히는 네 가지 문제

내보내기 중에 다른 API가 멈춥니다

증상: 큰 내보내기가 돌아가는 동안 가벼운 API까지 응답하지 않습니다. 내보내기를 받는 동안 20ms마다 다른 요청을 보내 응답 시간을 쟀습니다.

stream  (빠른 클라이언트)  다른 요청   1번 · 가장 느림 1741ms
yield   (빠른 클라이언트)  다른 요청  79번 · 가운데 0.9ms · 가장 느림 2ms
stream  (8 MB/s)          다른 요청 398번 · 가운데 0.3ms · 가장 느림 68ms
yield   (8 MB/s)          다른 요청 486번 · 가운데 0.3ms · 가장 느림 6ms

원인: Node.js 내장 SQLite의 API는 모두 동기로 실행됩니다.[3] 받는 쪽이 빨라 버퍼가 차지 않으면 행 읽기와 CSV 만들기가 쉬지 않고 이어져 다른 요청이 차례를 얻지 못한 것으로 보입니다. 대응: Node.js 안내서는 긴 계산을 나눠 돌리며 다른 대기 중인 이벤트에 주기적으로 차례를 넘기라고 권합니다.[12] 조각마다 setImmediate로 한 번 쉬게 하자, 전체 시간은 1.8초로 같고 다른 요청은 2ms 안에 응답했습니다.

async function* yielding(gen) {
  for (const chunk of gen) {
    yield chunk;
    await new Promise((r) => setImmediate(r));
  }
}

사용자가 취소했는데 서버는 끝까지 읽습니다

증상: 다운로드를 취소해도 DB 부하가 그대로입니다. curl을 초당 2 MB로 묶고 1초 뒤 끊었습니다.

stream  클라이언트가 받은 바이트 2047338 · 서버가 읽은 행 38000 · Premature close
nobp    클라이언트가 받은 바이트 0      · 서버가 읽은 행 1000000

원인과 대응: pipeline은 실패하면 연결된 스트림에 stream.destroy(err)를 부릅니다.[2] 그래서 연결이 끊기자 제너레이터의 finally가 실행되고 커서도 멈췄습니다. 반환값을 무시한 반복문은 연결이 끊겨도 100만 행을 다 읽었습니다. 커서를 직접 돌린다면 res의 'close' 이벤트에서 반복을 멈추는 코드를 따로 넣어야 합니다.

중간에 DB 오류가 나도 상태 코드는 이미 200입니다

증상: 60만 번째 행에서 일부러 오류를 냈습니다. 스트림 방식은 헤더를 이미 보내 500으로 바꿀 수 없습니다.

stream    HTTP 200 · 54173665바이트 받고 끊김 · curl exit 18
buffered  HTTP 500 · 2.74초 뒤 · 최고 RSS 1018.9 MB

대응: 헤더를 보낸 뒤 오류가 나면 res.destroy(err)로 연결을 끊어, 잘린 파일이 완성된 파일처럼 보이지 않게 합니다. 이렇게 하자 크롬은 링크 다운로드를 취소 상태로 끝내고 다운로드 폴더에 파일을 남기지 않았고, ②의 fetch는 TypeError: network error를 던졌습니다.

다시 읽으면 첫 열 이름이 맞지 않습니다

증상: 내보낸 CSV를 다른 서버에서 읽었더니 row["주문번호"]가 undefined입니다. 원인: BOM이 첫 열 이름에 붙어 남았습니다. Node.js Buffer.toString()은 BOM을 남겼고, TextDecoder는 기본 설정에서 지웠습니다.

Buffer.toString 첫 열 이름: "﻿주문번호" 길이 5 === '주문번호'? false
TextDecoder 첫 열 이름: "주문번호" === '주문번호'? true

대응: 엑셀용 파일과 시스템 간 연동용 파일을 나누거나, 읽는 쪽에서 맨 앞 \uFEFF를 지웁니다.

  • 운영팀이 엑셀로 연다면 BOM을 붙이고 수식 시작 문자를 처리합니다. 다른 시스템이 읽는 파일이면 BOM 없는 형식을 따로 둡니다.[5][6]

프론트엔드 팀이 해 볼 것

  1. 지금 서비스의 내보내기 API가 조회 결과를 배열로 다 받는지 찾아보고, 가장 큰 기간으로 내려받으며 서버 메모리를 기록해 봅니다.
  2. 내보낸 CSV의 앞 세 바이트가 EF BB BF인지, =나 +로 시작하는 값이 그대로 들어가는지 확인합니다.
  3. 내보내기 도중 다운로드를 취소했을 때 서버의 DB 조회가 멈추는지 로그로 확인합니다.
