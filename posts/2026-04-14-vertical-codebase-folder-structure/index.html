components·hooks·utils 폴더를 버리는 이유 — 기능별 수직 구조

코드를 "무엇인가"(컴포넌트, 훅, 유틸)가 아니라 "무엇을 하는가"로 묶으면 함께 바뀌는 코드가 한곳에 모입니다. TkDodo가 제안하는 수직 구조를 폴더 예시, 공유 코드 처리, 경계를 강제하는 도구, Feature-Sliced Design과의 차이까지 나눠 정리했습니다.

요약

  • 원문 필자는 components/hooks/types/utils로 나누는 수평 구조가 도메인이 아니라 종류로 묶기 때문에 규모가 커질수록 탐색과 변경이 어려워진다고 봅니다[1]
  • 대안은 src/dashboards/, src/profiling/처럼 하는 일 단위로 묶는 수직 구조이고, 여러 페이지에서 쓰는 코드도 독립된 하나의 수직으로 만듭니다[1]
  • 같은 폴더에 모으는 것만으로는 결합도가 줄지 않으므로 package.json의 exports나 린트 규칙으로 공개 인터페이스를 강제해야 합니다[1][2][3]
  • Feature-Sliced Design도 도메인별 슬라이스를 쓰지만, 고정된 레이어와 같은 레이어 슬라이스 간 import 금지라는 더 엄격한 규칙을 둡니다[4]

종류별로 나누면 생기는 일

수평 구조(horizontal split)는 파일을 components/, hooks/, types/, utils/처럼 기술적 종류로 나눕니다. 원문 필자는 이 방식이 많은 코드베이스에서 보이지만 가장 싫어하는 구조라고 말합니다[1].

src/
├── components/
│   ├── ThemeProvider.tsx
│   ├── TodoList.tsx
│   └── Widget.tsx
├── hooks/
│   ├── useTheme.ts    // ThemeProvider 옆이 아니라 useTodo 옆에 있음
│   └── useTodo.ts
├── types/
└── utils/
    └── widget.ts      // Widget이 쓰는 함수가 여기로 떨어져 나감

필자의 예처럼 useTheme은 useTodo 옆에 놓이지만, 함께 바뀌는 ThemeProvider 옆에는 없습니다[1]. 폴더는 "이건 훅이다"만 알려 줍니다.

함께 바뀌는 코드는 함께 둔다

필자의 출발점은 "함께 바뀌는 코드는 함께 있어야 한다"입니다. 파일 사이를 오갈수록 인지 부하가 늘기 때문입니다[1]. 컴포넌트의 props 타입을 별도 파일로 빼는 사람은 드뭅니다.

// src/components/widget.tsx
export type WidgetProps = { id: string }

export function Widget(props: WidgetProps) {}
// props를 보려고 다른 파일을 열 필요가 없음

여기에 데이터 패칭을 붙이면 문제가 드러납니다. 원문 예제는 useSuspenseQuery에 widgetQueryOptions(props.id)를 넘깁니다[1].

// src/components/widget.tsx
export function Widget(props: WidgetProps) {
  const { data } = useSuspenseQuery(
    widgetQueryOptions(props.id),
  )
}
// widgetQueryOptions는 어디에? → "유틸이니까" src/utils/widget.ts

widgetQueryOptions는 이 위젯 전용인데도 컴포넌트·훅이 아니라는 이유로 utils/로 갑니다. 필자는 그런 폴더를 꽤 임의적인 분류라고 봅니다[1].

규모가 커지면

Sentry 코드베이스가 원문의 사례입니다. 10년 넘게 이 구조로 개발하면서 최상위 components 디렉터리에 200개가 넘는 파일이 쌓였고, 공통점은 컴포넌트라는 것뿐입니다[1]. 목록에는 analyticsArea.tsx와 workflowEngine이 나란히 있습니다[5].

흩어진 사례도 구체적입니다[1].

  • utils/analytics의 함수는 components/analyticsArea와 논리적으로 묶여 있습니다.
  • utils/feedback이 내보내는 함수는 components/feedback 안에서만 쓰입니다.
  • 프로파일링 코드는 components/profiling, types/profiling, utils/profiling, views/profiling 네 곳에 나뉘어 있습니다.

필자는 수평 구조가 낮은 결합도·높은 응집도와 정반대를 만든다고 봅니다. 어떤 컴포넌트든 어떤 유틸을 import할 수 있고, 느슨하게만 관련된 코드가 한 폴더에 모입니다[1].

하는 일로 묶는 수직 구조

수직 구조(vertical structure)는 코드를 무엇을 하는지로 묶습니다. 위젯 관련 코드는 컴포넌트·훅·타입·상수 상관없이 전부 src/widgets/에 둡니다[1].

src/
├── dashboards/
│   ├── DashboardPage.tsx
│   └── useDashboard.ts
├── widgets/
│   ├── Widget.tsx
│   ├── widgetQueryOptions.ts  // 유틸이지만 위젯 옆에
│   └── types.ts
└── profiling/                 // 프로파일링 팀이 소유
    ├── ProfilingPage.tsx
    └── utils.ts

무엇을 하는 코드인지만 알면 위치를 찾을 수 있고, 함께 바뀌는 코드가 모여 응집도가 올라갑니다[1]. 팀 구성·코드 오너(codeowners)와 겹치는 경우가 많다는 점은 부수 효과입니다[1].

어디서 자를까

올바른 수직을 찾는 것이 가장 어렵습니다. 기계적인 규칙이 없어 직접 판단해야 합니다. 필자가 권하는 출발점은 라우트와 페이지입니다[1].

  1. /dashboard 페이지가 있으면 dashboards 묶음부터 만듭니다.
  2. 대시보드에 위젯이 있으면 처음엔 그 안에 둡니다.
  3. 위젯이 커지거나 /explore 페이지에서도 위젯을 만든다면 widgets를 독립된 수직으로 꺼냅니다.

공유 코드도 하나의 수직

여러 곳에서 쓰는 코드는 어떻게 할까요? 필자의 답은 그 코드 자체를 하나의 수직으로 만드는 것입니다[1]. Sentry의 PageFilters는 여러 페이지에서 쓰이고 흔히 말하는 "기능(feature)"은 아니지만, 그 자체로 하나의 도메인입니다[1]. 원문은 컴포넌트가 components/pageFilters, 타입이 types/core, 유틸이 utils/withPageFilters에 흩어져 있어 찾기 어렵고 소유자가 불분명하다고 설명합니다[1].

# 수평: 세 군데를 열어야 하는 변경
components/pageFilters/
types/core
utils/withPageFilters

# 수직: 한 폴더 안에서 끝나는 변경
pageFilters/
├── pageFilterBar.tsx
├── usePageFilters.tsx
├── store.tsx
├── parse.tsx
└── types.tsx

아래쪽 파일 이름은 원문이 링크한 시점의 components/pageFilters 폴더에 실제로 있는 파일들입니다[6].

자주 하는 실수: shared 폴더를 새 utils로 만들기

여러 곳에서 쓴다고 전부 shared/에 넣으면 이름만 바뀐 utils/가 됩니다. 공유 코드도 "무엇을 하는가"로 이름을 붙여야 합니다.

폴더 이름을 정하는 질문무엇인가 말고무엇을 하는가

경계: 모으는 것만으로는 부족하다

한 수직으로 모으면 응집도는 오르지만 결합도가 저절로 줄지는 않습니다. 필자는 한 기능용 유틸이 예상 밖의 곳에서 재사용돼 작은 변경도 위험해진 경험을 이야기합니다. 그래서 공개 인터페이스와 비공개 부분을 가르는 경계가 필요합니다[1].

폴더 수준: index 파일

가장 가벼운 방법은 수직마다 index 파일을 두고 밖에서 쓸 것만 다시 내보내는 것입니다. Feature-Sliced Design 문서는 공개 API(public API)를 모듈 묶음과 그것을 쓰는 코드 사이의 계약이자 관문이라고 정의하고, 보통 re-export를 담은 index 파일로 구현한다고 설명합니다[7].

// src/widgets/index.ts
export { Widget } from "./Widget";
export type { WidgetProps } from "./Widget";
// widgetQueryOptions는 내보내지 않음 → 위젯 내부 구현

같은 문서는 export *처럼 전부 내보내면 인터페이스가 무엇인지 알 수 없고 내부 구현이 노출돼 리팩터링이 어려워진다고 경고합니다[7].

다만 index 파일은 약속일 뿐이라, 내부 파일을 직접 import해도 막지 못합니다.

패키지 수준: 모노레포와 exports

필자는 경계를 만드는 가장 좋은 방법으로 모노레포를 꼽습니다. 수직마다 패키지를 만들고, 공개 인터페이스를 package.json의 exports 필드로 정의합니다. 필자는 pnpm workspaces가 이 용도에 꽤 좋았다고 말합니다[1].

exports 필드는 Node.js v12.7.0에서 기존 main 필드보다 강력한 대안으로 도입됐습니다[8]. webpack 문서에 따르면 exports를 지정하면 거기 적힌 경로만 import할 수 있고, 나머지 요청은 ModuleNotFound 오류가 됩니다[3].

{
  "name": "@acme/widgets",
  "exports": {
    ".": "./index.ts"
  }
}

// packages/dashboards/DashboardPage.tsx
import { Widget } from "@acme/widgets"; // OK: "."에 있음
import { widgetQueryOptions } from "@acme/widgets/widgetQueryOptions";
// → ModuleNotFound: exports에 없는 경로

수직끼리 의존은 가능하지만 명시적이 됩니다[1]. pnpm에서는 "@acme/widgets": "workspace:*"처럼 workspace: 프로토콜로 선언하면 로컬 워크스페이스 패키지로만 해석됩니다[9].

규칙 수준: 린트로 방향 강제하기

어떤 수직이 어떤 수직에 의존할 수 없다는 규칙도 만들 수 있습니다. 필자는 Nx가 이를 기본으로 지원하지만 모노레포가 아니어도 구조를 강제할 수 있다고 말하고, Sentry는 eslint-plugin-boundaries로 의존 방향을 강제하기 시작했다고 소개합니다[1].

Nx는 프로젝트에 태그를 달고 @nx/enforce-module-boundaries 규칙의 depConstraints로 허용할 의존을 선언합니다[2].

// eslint.config.mjs (Nx)
'@nx/enforce-module-boundaries': [
  'error',
  {
    allow: [],
    depConstraints: [
      { sourceTag: 'scope:shared', onlyDependOnLibsWithTags: ['scope:shared'] },
      { sourceTag: 'scope:admin', onlyDependOnLibsWithTags: ['scope:shared', 'scope:admin'] },
    ],
  },
],
// scope:shared가 scope:admin을 import → 린트 오류

태그가 없는 프로젝트는 다른 어떤 프로젝트에도 의존할 수 없으니 태그 누락에 주의하세요[2].

eslint-plugin-boundaries는 boundaries/elements 설정으로 요소 종류와 경로 패턴을 정의하고, boundaries/dependencies 규칙에 default: "disallow"와 허용 정책을 적는 방식입니다[10].

// eslint.config.js (eslint-plugin-boundaries)
settings: {
  "boundaries/elements": [
    { type: "dashboards", pattern: "src/dashboards/*" },
    { type: "widgets", pattern: "src/widgets/*" },
  ],
},
rules: {
  "boundaries/dependencies": [2, {
    default: "disallow",
    policies: [
      { from: { element: { type: "dashboards" } },
        allow: { to: { element: { type: "widgets" } } } },
    ],
  }],
},
// widgets → dashboards import → 경계 위반 오류

규칙을 적은 뒤에는 일부러 금지된 import를 하나 넣어 오류가 나는지부터 확인하세요.

Feature-Sliced Design과 비교

Feature-Sliced Design(FSD)은 프론트엔드 코드 구성 규칙과 관례를 모은 방법론입니다[4]. 도메인으로 나눈다는 방향은 같지만 규칙이 훨씬 많습니다.

FSD는 레이어(layer), 슬라이스(slice), 세그먼트(segment)의 3단계 계층을 씁니다. 예를 들어 pages 레이어 안의 article-reader 슬라이스가 다시 ui, api 세그먼트로 나뉩니다[4].

관점 원문의 수직 구조 FSD
최상위 단위 도메인 폴더를 자유롭게 정함[1] 이름이 표준화된 레이어(현재 7개, Processes는 deprecated)[4]
도메인 분할 수직 = 하는 일 레이어 안의 슬라이스[4]
수직 안의 분할 규정 없음 ui·api·model·lib·config 같은 세그먼트[4]
의존 규칙 패키지 의존성·린트로 팀이 정함[1] 아래 레이어만 import, 같은 레이어 슬라이스끼리는 금지[4]
공유 코드 독립된 수직으로 만듦[1] 레이어에 따라 재사용 범위를 조절, 범용 코드는 Shared[4]

FSD는 목적별 분할을 없애지 않고 도메인 안쪽(세그먼트)으로 밀어 넣습니다[4]. 또 FSD의 Features는 사용자에게 가치를 주는 행동을 뜻하는 특정 레이어인데[4], 원문 필자는 PageFilters 같은 코드를 담기 위해 "feature"라는 말을 일부러 피합니다[1].

FSD 문서도 지금 구조가 문제를 일으키지 않으면 바꿀 가치가 없을 수 있다고 적습니다[4]. 도메인 폴더로 모으는 것부터 시작해도 됩니다.

대가

필자가 꼽는 비용은 둘입니다. 코드마다 맞는 수직을 고르기 어렵고, 비공개 코드 때문에 여러 팀이 같은 것을 각자 다시 만들 수 있습니다. 둘 다 팀 간 소통으로 풀어야 합니다[1].

정리

질문 수평 구조 수직 구조
폴더 기준 기술적 종류(components, hooks, utils) 하는 일(dashboards, widgets, profiling)
기능 하나 수정 여러 폴더를 오감 한 폴더 안에서 끝남
여러 곳에서 쓰는 코드 utils/, components/에 쌓임 독립된 수직(pageFilters)
경계 어디서든 import 가능 index 파일 → exports → 린트 규칙
비용 시작은 쉽고 나중에 바꾸기 어려움[1] 묶는 기준을 정하는 판단과 팀 간 소통[1]
  • 새 코드를 둘 때 "이건 무엇인가"가 아니라 "이건 무엇을 하는가"를 묻습니다.
  • 라우트·페이지 단위로 시작하고, 여러 곳에서 쓰이면 독립된 수직으로 꺼냅니다.
  • 모은 다음에는 공개 인터페이스를 정하고 도구로 강제해야 결합도가 줄어듭니다.

프론트엔드 팀이 해 볼 것

  1. 프로젝트의 utils/(또는 hooks/)에서 파일 하나를 골라, import하는 곳이 한 기능뿐인지 검색해 본다
  2. 페이지 하나를 골라 그 페이지에서만 쓰는 컴포넌트·훅·유틸을 한 폴더로 옮기고 index.ts에 공개할 것만 다시 내보낸다
  3. 수직 폴더 두 개 사이의 허용 방향을 정해 eslint-plugin-boundaries나 Nx depConstraints 규칙으로 적어 본다
