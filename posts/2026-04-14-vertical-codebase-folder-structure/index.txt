18:T55be,<h2 id="종류별로-나누면-생기는-일">종류별로 나누면 생기는 일</h2>
<p>수평 구조(horizontal split)는 파일을 <code>components/</code>, <code>hooks/</code>, <code>types/</code>, <code>utils/</code>처럼 기술적 종류로 나눕니다. 원문 필자는 이 방식이 많은 코드베이스에서 보이지만 가장 싫어하는 구조라고 말합니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<pre data-lang="text"><code class="hljs language-text">src/
├── components/
│   ├── ThemeProvider.tsx
│   ├── TodoList.tsx
│   └── Widget.tsx
├── hooks/
│   ├── useTheme.ts    // ThemeProvider 옆이 아니라 useTodo 옆에 있음
│   └── useTodo.ts
├── types/
└── utils/
    └── widget.ts      // Widget이 쓰는 함수가 여기로 떨어져 나감
</code></pre>
<p>필자의 예처럼 <code>useTheme</code>은 <code>useTodo</code> 옆에 놓이지만, 함께 바뀌는 <code>ThemeProvider</code> 옆에는 없습니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>. 폴더는 "이건 훅이다"만 알려 줍니다.</p>
<h3 id="함께-바뀌는-코드는-함께-둔다">함께 바뀌는 코드는 함께 둔다</h3>
<p>필자의 출발점은 "함께 바뀌는 코드는 함께 있어야 한다"입니다. 파일 사이를 오갈수록 인지 부하가 늘기 때문입니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>. 컴포넌트의 props 타입을 별도 파일로 빼는 사람은 드뭅니다.</p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-comment">// src/components/widget.tsx</span>
<span class="hljs-keyword">export</span> <span class="hljs-keyword">type</span> <span class="hljs-title class_">WidgetProps</span> = { <span class="hljs-attr">id</span>: <span class="hljs-built_in">string</span> }

<span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">Widget</span>(<span class="hljs-params"><span class="hljs-attr">props</span>: <span class="hljs-title class_">WidgetProps</span></span>) {}
<span class="hljs-comment">// props를 보려고 다른 파일을 열 필요가 없음</span>
</code></pre>
<p>여기에 데이터 패칭을 붙이면 문제가 드러납니다. 원문 예제는 <code>useSuspenseQuery</code>에 <code>widgetQueryOptions(props.id)</code>를 넘깁니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-comment">// src/components/widget.tsx</span>
<span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">Widget</span>(<span class="hljs-params"><span class="hljs-attr">props</span>: <span class="hljs-title class_">WidgetProps</span></span>) {
  <span class="hljs-keyword">const</span> { data } = <span class="hljs-title function_">useSuspenseQuery</span>(
    <span class="hljs-title function_">widgetQueryOptions</span>(props.<span class="hljs-property">id</span>),
  )
}
<span class="hljs-comment">// widgetQueryOptions는 어디에? → "유틸이니까" src/utils/widget.ts</span>
</code></pre>
<p><code>widgetQueryOptions</code>는 이 위젯 전용인데도 컴포넌트·훅이 아니라는 이유로 <code>utils/</code>로 갑니다. 필자는 그런 폴더를 꽤 임의적인 분류라고 봅니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<h3 id="규모가-커지면">규모가 커지면</h3>
<p>Sentry 코드베이스가 원문의 사례입니다. 10년 넘게 이 구조로 개발하면서 최상위 <code>components</code> 디렉터리에 200개가 넘는 파일이 쌓였고, 공통점은 컴포넌트라는 것뿐입니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>. 목록에는 <code>analyticsArea.tsx</code>와 <code>workflowEngine</code>이 나란히 있습니다<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup>.</p>
<p>흩어진 사례도 구체적입니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<ul>
<li><code>utils/analytics</code>의 함수는 <code>components/analyticsArea</code>와 논리적으로 묶여 있습니다.</li>
<li><code>utils/feedback</code>이 내보내는 함수는 <code>components/feedback</code> 안에서만 쓰입니다.</li>
<li>프로파일링 코드는 <code>components/profiling</code>, <code>types/profiling</code>, <code>utils/profiling</code>, <code>views/profiling</code> 네 곳에 나뉘어 있습니다.</li>
</ul>
<p>필자는 수평 구조가 낮은 결합도·높은 응집도와 정반대를 만든다고 봅니다. 어떤 컴포넌트든 어떤 유틸을 import할 수 있고, 느슨하게만 관련된 코드가 한 폴더에 모입니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<h2 id="하는-일로-묶는-수직-구조">하는 일로 묶는 수직 구조</h2>
<p>수직 구조(vertical structure)는 코드를 무엇을 하는지로 묶습니다. 위젯 관련 코드는 컴포넌트·훅·타입·상수 상관없이 전부 <code>src/widgets/</code>에 둡니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<pre data-lang="text"><code class="hljs language-text">src/
├── dashboards/
│   ├── DashboardPage.tsx
│   └── useDashboard.ts
├── widgets/
│   ├── Widget.tsx
│   ├── widgetQueryOptions.ts  // 유틸이지만 위젯 옆에
│   └── types.ts
└── profiling/                 // 프로파일링 팀이 소유
    ├── ProfilingPage.tsx
    └── utils.ts
</code></pre>
<p>무엇을 하는 코드인지만 알면 위치를 찾을 수 있고, 함께 바뀌는 코드가 모여 응집도가 올라갑니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>. 팀 구성·코드 오너(codeowners)와 겹치는 경우가 많다는 점은 부수 효과입니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<h3 id="어디서-자를까">어디서 자를까</h3>
<p>올바른 수직을 찾는 것이 가장 어렵습니다. 기계적인 규칙이 없어 직접 판단해야 합니다. 필자가 권하는 출발점은 라우트와 페이지입니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<ol>
<li><code>/dashboard</code> 페이지가 있으면 <code>dashboards</code> 묶음부터 만듭니다.</li>
<li>대시보드에 위젯이 있으면 처음엔 그 안에 둡니다.</li>
<li>위젯이 커지거나 <code>/explore</code> 페이지에서도 위젯을 만든다면 <code>widgets</code>를 독립된 수직으로 꺼냅니다.</li>
</ol>
<h3 id="공유-코드도-하나의-수직">공유 코드도 하나의 수직</h3>
<p>여러 곳에서 쓰는 코드는 어떻게 할까요? 필자의 답은 그 코드 자체를 하나의 수직으로 만드는 것입니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>. Sentry의 <code>PageFilters</code>는 여러 페이지에서 쓰이고 흔히 말하는 "기능(feature)"은 아니지만, 그 자체로 하나의 도메인입니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>. 원문은 컴포넌트가 <code>components/pageFilters</code>, 타입이 <code>types/core</code>, 유틸이 <code>utils/withPageFilters</code>에 흩어져 있어 찾기 어렵고 소유자가 불분명하다고 설명합니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<pre data-lang="text"><code class="hljs language-text"># 수평: 세 군데를 열어야 하는 변경
components/pageFilters/
types/core
utils/withPageFilters

# 수직: 한 폴더 안에서 끝나는 변경
pageFilters/
├── pageFilterBar.tsx
├── usePageFilters.tsx
├── store.tsx
├── parse.tsx
└── types.tsx
</code></pre>
<p>아래쪽 파일 이름은 원문이 링크한 시점의 <code>components/pageFilters</code> 폴더에 실제로 있는 파일들입니다<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup>.</p>
<h4>자주 하는 실수: shared 폴더를 새 utils로 만들기</h4>
<p>여러 곳에서 쓴다고 전부 <code>shared/</code>에 넣으면 이름만 바뀐 <code>utils/</code>가 됩니다. 공유 코드도 "무엇을 하는가"로 이름을 붙여야 합니다.</p>
<aside class="poster" aria-label="폴더 이름을 정하는 질문 무엇인가 말고 무엇을 하는가"><span class="poster-line" aria-hidden="true">폴더 이름을 정하는 질문</span><span class="poster-line" aria-hidden="true">무엇인가 말고</span><span class="poster-line poster-accent" aria-hidden="true">무엇을 하는가</span></aside>
<h2 id="경계-모으는-것만으로는-부족하다">경계: 모으는 것만으로는 부족하다</h2>
<p>한 수직으로 모으면 응집도는 오르지만 결합도가 저절로 줄지는 않습니다. 필자는 한 기능용 유틸이 예상 밖의 곳에서 재사용돼 작은 변경도 위험해진 경험을 이야기합니다. 그래서 공개 인터페이스와 비공개 부분을 가르는 경계가 필요합니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<h3 id="폴더-수준-index-파일">폴더 수준: index 파일</h3>
<p>가장 가벼운 방법은 수직마다 index 파일을 두고 밖에서 쓸 것만 다시 내보내는 것입니다. Feature-Sliced Design 문서는 공개 API(public API)를 모듈 묶음과 그것을 쓰는 코드 사이의 계약이자 관문이라고 정의하고, 보통 re-export를 담은 index 파일로 구현한다고 설명합니다<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup>.</p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// src/widgets/index.ts</span>
<span class="hljs-keyword">export</span> { <span class="hljs-title class_">Widget</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"./Widget"</span>;
<span class="hljs-keyword">export</span> <span class="hljs-keyword">type</span> { <span class="hljs-title class_">WidgetProps</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"./Widget"</span>;
<span class="hljs-comment">// widgetQueryOptions는 내보내지 않음 → 위젯 내부 구현</span>
</code></pre>
<p>같은 문서는 <code>export *</code>처럼 전부 내보내면 인터페이스가 무엇인지 알 수 없고 내부 구현이 노출돼 리팩터링이 어려워진다고 경고합니다<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup>.</p>
<p>다만 index 파일은 약속일 뿐이라, 내부 파일을 직접 import해도 막지 못합니다.</p>
<h3 id="패키지-수준-모노레포와-exports">패키지 수준: 모노레포와 exports</h3>
<p>필자는 경계를 만드는 가장 좋은 방법으로 모노레포를 꼽습니다. 수직마다 패키지를 만들고, 공개 인터페이스를 <code>package.json</code>의 <code>exports</code> 필드로 정의합니다. 필자는 pnpm workspaces가 이 용도에 꽤 좋았다고 말합니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<p><code>exports</code> 필드는 Node.js v12.7.0에서 기존 <code>main</code> 필드보다 강력한 대안으로 도입됐습니다<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup>. webpack 문서에 따르면 <code>exports</code>를 지정하면 거기 적힌 경로만 import할 수 있고, 나머지 요청은 ModuleNotFound 오류가 됩니다<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup>.</p>
<pre data-lang="json"><code class="hljs language-json"><span class="hljs-punctuation">{</span>
  <span class="hljs-attr">"name"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"@acme/widgets"</span><span class="hljs-punctuation">,</span>
  <span class="hljs-attr">"exports"</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span>
    <span class="hljs-attr">"."</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"./index.ts"</span>
  <span class="hljs-punctuation">}</span>
<span class="hljs-punctuation">}</span>
</code></pre>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// packages/dashboards/DashboardPage.tsx</span>
<span class="hljs-keyword">import</span> { <span class="hljs-title class_">Widget</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"@acme/widgets"</span>; <span class="hljs-comment">// OK: "."에 있음</span>
<span class="hljs-keyword">import</span> { widgetQueryOptions } <span class="hljs-keyword">from</span> <span class="hljs-string">"@acme/widgets/widgetQueryOptions"</span>;
<span class="hljs-comment">// → ModuleNotFound: exports에 없는 경로</span>
</code></pre>
<p>수직끼리 의존은 가능하지만 명시적이 됩니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>. pnpm에서는 <code>"@acme/widgets": "workspace:*"</code>처럼 <code>workspace:</code> 프로토콜로 선언하면 로컬 워크스페이스 패키지로만 해석됩니다<sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup>.</p>
<h3 id="규칙-수준-린트로-방향-강제하기">규칙 수준: 린트로 방향 강제하기</h3>
<p>어떤 수직이 어떤 수직에 의존할 수 없다는 규칙도 만들 수 있습니다. 필자는 Nx가 이를 기본으로 지원하지만 모노레포가 아니어도 구조를 강제할 수 있다고 말하고, Sentry는 <code>eslint-plugin-boundaries</code>로 의존 방향을 강제하기 시작했다고 소개합니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<p>Nx는 프로젝트에 태그를 달고 <code>@nx/enforce-module-boundaries</code> 규칙의 <code>depConstraints</code>로 허용할 의존을 선언합니다<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup>.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// eslint.config.mjs (Nx)</span>
<span class="hljs-string">'@nx/enforce-module-boundaries'</span>: [
  <span class="hljs-string">'error'</span>,
  {
    <span class="hljs-attr">allow</span>: [],
    <span class="hljs-attr">depConstraints</span>: [
      { <span class="hljs-attr">sourceTag</span>: <span class="hljs-string">'scope:shared'</span>, <span class="hljs-attr">onlyDependOnLibsWithTags</span>: [<span class="hljs-string">'scope:shared'</span>] },
      { <span class="hljs-attr">sourceTag</span>: <span class="hljs-string">'scope:admin'</span>, <span class="hljs-attr">onlyDependOnLibsWithTags</span>: [<span class="hljs-string">'scope:shared'</span>, <span class="hljs-string">'scope:admin'</span>] },
    ],
  },
],
<span class="hljs-comment">// scope:shared가 scope:admin을 import → 린트 오류</span>
</code></pre>
<p>태그가 없는 프로젝트는 다른 어떤 프로젝트에도 의존할 수 없으니 태그 누락에 주의하세요<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup>.</p>
<p><code>eslint-plugin-boundaries</code>는 <code>boundaries/elements</code> 설정으로 요소 종류와 경로 패턴을 정의하고, <code>boundaries/dependencies</code> 규칙에 <code>default: "disallow"</code>와 허용 정책을 적는 방식입니다<sup class="cite"><a href="#source-10" aria-label="출처 10">[10]</a></sup>.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// eslint.config.js (eslint-plugin-boundaries)</span>
<span class="hljs-attr">settings</span>: {
  <span class="hljs-string">"boundaries/elements"</span>: [
    { <span class="hljs-attr">type</span>: <span class="hljs-string">"dashboards"</span>, <span class="hljs-attr">pattern</span>: <span class="hljs-string">"src/dashboards/*"</span> },
    { <span class="hljs-attr">type</span>: <span class="hljs-string">"widgets"</span>, <span class="hljs-attr">pattern</span>: <span class="hljs-string">"src/widgets/*"</span> },
  ],
},
<span class="hljs-attr">rules</span>: {
  <span class="hljs-string">"boundaries/dependencies"</span>: [<span class="hljs-number">2</span>, {
    <span class="hljs-attr">default</span>: <span class="hljs-string">"disallow"</span>,
    <span class="hljs-attr">policies</span>: [
      { <span class="hljs-attr">from</span>: { <span class="hljs-attr">element</span>: { <span class="hljs-attr">type</span>: <span class="hljs-string">"dashboards"</span> } },
        <span class="hljs-attr">allow</span>: { <span class="hljs-attr">to</span>: { <span class="hljs-attr">element</span>: { <span class="hljs-attr">type</span>: <span class="hljs-string">"widgets"</span> } } } },
    ],
  }],
},
<span class="hljs-comment">// widgets → dashboards import → 경계 위반 오류</span>
</code></pre>
<p>규칙을 적은 뒤에는 일부러 금지된 import를 하나 넣어 오류가 나는지부터 확인하세요.</p>
<h2 id="feature-sliced-design과-비교">Feature-Sliced Design과 비교</h2>
<p>Feature-Sliced Design(FSD)은 프론트엔드 코드 구성 규칙과 관례를 모은 방법론입니다<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup>. 도메인으로 나눈다는 방향은 같지만 규칙이 훨씬 많습니다.</p>
<p>FSD는 레이어(layer), 슬라이스(slice), 세그먼트(segment)의 3단계 계층을 씁니다. 예를 들어 <code>pages</code> 레이어 안의 <code>article-reader</code> 슬라이스가 다시 <code>ui</code>, <code>api</code> 세그먼트로 나뉩니다<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup>.</p>
<table>
<thead>
<tr>
<th>관점</th>

</thead>

</tr>

<p>FSD는 목적별 분할을 없애지 않고 도메인 안쪽(세그먼트)으로 밀어 넣습니다<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup>. 또 FSD의 Features는 사용자에게 가치를 주는 행동을 뜻하는 특정 레이어인데<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup>, 원문 필자는 <code>PageFilters</code> 같은 코드를 담기 위해 "feature"라는 말을 일부러 피합니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
<p>FSD 문서도 지금 구조가 문제를 일으키지 않으면 바꿀 가치가 없을 수 있다고 적습니다<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup>. 도메인 폴더로 모으는 것부터 시작해도 됩니다.</p>
<h3 id="대가">대가</h3>
<p>필자가 꼽는 비용은 둘입니다. 코드마다 맞는 수직을 고르기 어렵고, 비공개 코드 때문에 여러 팀이 같은 것을 각자 다시 만들 수 있습니다. 둘 다 팀 간 소통으로 풀어야 합니다<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>.</p>
