위에서 아래로만 import한다 — Feature-Sliced Design 실전 입문

Feature-Sliced Design은 레이어·슬라이스·세그먼트 세 단계와 몇 가지 import 규칙으로 프론트엔드 폴더 구조를 표준화합니다. 글 목록과 좋아요 버튼이 있는 작은 앱을 직접 나눠 보면서 레이어 규칙, 공개 API, @x 교차 import, Steiger 린터 검사까지 정리했습니다.

요약

  • 레이어는 app·pages·widgets·features·entities·shared(그리고 deprecated된 processes)로 이름이 고정돼 있고, 한 슬라이스의 파일은 자기보다 엄격히 아래 레이어만 import할 수 있다[1]
  • 슬라이스마다 index 파일로 공개 API를 두고, export *는 인터페이스를 감추고 내부 구현을 실수로 노출하므로 이름을 하나씩 적는다[2][3]
  • 같은 레이어 슬라이스끼리의 import는 금지가 기본이고, entities에서만 @x 표기로 특정 슬라이스 전용 공개 API를 연다[2][4]
  • Steiger와 @feature-sliced/steiger-plugin을 설치하면 npx steiger ./src 한 줄로 이 규칙들을 검사할 수 있다[5]

레이어: 위에서 아래로만 import한다

Feature-Sliced Design(FSD)은 프론트엔드 애플리케이션의 코드 배치 규칙과 관례를 모은 방법론입니다. 라이브러리가 아닌 애플리케이션이면 언어·UI 프레임워크·상태 관리 도구와 상관없이 쓸 수 있습니다.[6] 기능별로 폴더를 모으는 이유는 「components·hooks·utils 폴더를 버리는 이유 — 기능별 수직 구조」에서 다뤘으니, 여기서는 FSD만의 규칙에 집중합니다.

FSD는 레이어(layer) → 슬라이스(slice) → 세그먼트(segment) 3단계로 코드를 나눕니다.[6] 레이어는 이름이 표준으로 정해진 최상위 폴더이고, 위에서부터 다음과 같습니다.[6][1]

레이어 담는 것
app 라우팅, 진입점, 전역 스타일, 프로바이더
processes deprecated. features와 app으로 옮기도록 권장
pages 페이지 전체, 중첩 라우팅에서는 페이지의 큰 부분
widgets 그 자체로 완결된 큰 UI 블록
features 사용자에게 가치를 주는 행동
entities 비즈니스 개념(user, article 등)
shared 비즈니스와 떨어진 재사용 코드

모든 레이어를 쓸 필요는 없고, 대부분의 프로젝트는 최소한 shared, pages, app을 갖습니다.[1] 핵심 규칙은 하나입니다. 슬라이스 안의 파일은 자기보다 엄격히 아래 레이어의 슬라이스만 import할 수 있습니다.[1]

// features/like-article/api/likeArticle.ts
import { apiFetch } from "@/shared/api";          // OK: 아래 레이어
import type { Article } from "@/entities/article"; // OK: 아래 레이어
import { FeedPage } from "@/pages/feed";           // ❌ 위 레이어
import { CommentForm } from "@/features/comment";  // ❌ 같은 레이어 다른 슬라이스

app과 shared는 슬라이스 없이 세그먼트로 바로 나뉘고, 세그먼트끼리는 자유롭게 import할 수 있습니다. shared에는 비즈니스 도메인이 없고, app은 모든 도메인을 묶기 때문입니다.[1]

FSD의 import 규칙위에서 아래로만

슬라이스와 세그먼트: 글 목록·좋아요 앱 나누기

슬라이스는 레이어 안을 비즈니스 도메인으로 나눈 폴더이고 이름은 도메인이 정합니다.[7] 세그먼트는 슬라이스 안을 목적으로 나눈 폴더입니다. 관례 이름은 ui(화면 표시), api(백엔드 통신), model(스키마·스토어·비즈니스 로직), lib(슬라이스 안에서 쓰는 라이브러리 코드), config(설정·기능 플래그)입니다.[7] components, hooks, types는 본질만 말하고 목적을 말하지 않아 나쁜 이름으로 꼽힙니다.[7]

피드의 글마다 좋아요 버튼이 붙는 앱을 나눠 봅니다. 공식 튜토리얼의 Conduit 예제도 이런 피드를 다룹니다.[8]

src/
├── app/routes/index.ts
├── pages/feed/
│   ├── ui/FeedPage.tsx
│   └── index.ts
├── features/like-article/
│   ├── api/likeArticle.ts
│   ├── ui/LikeButton.tsx
│   └── index.ts
├── entities/
│   ├── article/
│   │   ├── api/getArticles.ts
│   │   ├── model/article.ts
│   │   ├── ui/ArticleCard.tsx
│   │   └── index.ts
│   └── user/
│       ├── model/user.ts
│       ├── @x/article.ts   # article 전용 공개 API
│       └── index.ts
└── shared/api/
    ├── client.ts
    └── index.ts

좋아요가 feature인 이유는 피드와 글 상세 두 페이지에서 쓰이기 때문입니다. 여러 페이지에서 재사용된다는 것이 feature로 만들 좋은 신호입니다.[1] 재사용되지 않는 큰 UI 블록은 위젯이 아니라 페이지 안에 두므로 widgets는 비워 둡니다.[1]

엔티티의 UI는 같은 모습을 여러 곳에서 재사용하는 것이 목적이고, 다른 비즈니스 로직은 props나 슬롯으로 붙입니다.[1] 그래서 ArticleCard는 좋아요를 모르고 actions 자리만 둡니다.

// entities/article/ui/ArticleCard.tsx
import type { ReactNode } from "react";
import type { Article } from "../model/article";

export function ArticleCard({ article, actions }: { article: Article; actions?: ReactNode }) {
  return (
    <article>
      <h2>{article.title}</h2>
      {actions}
    </article>
  );
}

두 슬라이스는 위 레이어인 페이지가 조립합니다. 같은 레이어끼리 서로 알게 하지 않고 위에서 엮는 제어의 역전(IoC) 방식입니다.[4]

// pages/feed/ui/FeedPage.tsx
import { ArticleCard, type Article } from "@/entities/article";
import { LikeButton } from "@/features/like-article";

export function FeedPage({ articles }: { articles: Article[] }) {
  return (
    <main>
      {articles.map((article) => (
        <ArticleCard
          key={article.slug}
          article={article}
          actions={<LikeButton article={article} />}
        />
      ))}
    </main>
  );
}
// ArticleCard와 LikeButton은 서로를 import하지 않음

자주 하는 실수: features를 너무 잘게 쪼개기

like-button, like-count, unlike처럼 동작마다 슬라이스를 만들면 중요한 feature가 묻힙니다. 공식 문서는 모든 것이 feature일 필요는 없다고 하고, 새로 온 사람이 pages와 features만 보고 큰 기능을 찾을 수 있게 하라고 권합니다.[1] 늘 함께 바뀌며 서로 import하는 슬라이스는 합칩니다.[4]

자주 하는 실수: shared에 비즈니스 로직 넣기

// ❌ shared/lib/article.ts — shared가 '글'이라는 도메인을 알게 됨
export const canLike = (article: { favorited: boolean }) => !article.favorited;

shared에는 비즈니스 로직이 없어야 합니다.[7] 이 함수는 entities/article/model로 옮깁니다. shared/lib도 헬퍼 모음이 아니라 날짜·색처럼 관심사 하나에 집중한 라이브러리를 README와 함께 두는 곳입니다.[1]

공개 API와 @x 교차 import

공개 API(public API)는 슬라이스와 그것을 쓰는 코드 사이의 계약이자 관문이고, 보통 다시 내보내기(re-export)만 담은 index 파일로 만듭니다.[2] 슬라이스 밖에서는 내부 파일이 아니라 공개 API만 참조할 수 있습니다.[7]

// entities/article/index.ts
export type { Article } from "./model/article";
export { getArticles } from "./api/getArticles";
export { ArticleCard } from "./ui/ArticleCard";

export *를 피하는 이유

export * from "./ui/Comment"처럼 쓰면 파일을 다 열어 보기 전에는 인터페이스를 알 수 없고, 내부 구현이 실수로 노출돼 리팩터링이 어려워집니다.[2] 내부 모듈에 export를 하나 추가하면 공개 API도 같이 늘고, 나중에 지우면 그사이 쓰기 시작한 코드가 깨집니다.[3] export * as model from "./model" 같은 네임스페이스 재내보내기도 같은 문제를 남깁니다.[3]

배럴 파일 일반론은 「파일만 나누면 끝일까 — JavaScript 모듈 경계 설계」에서 다뤘습니다. FSD는 경로 규칙을 정해 둡니다. 같은 슬라이스 안은 전체 경로의 상대 경로로, 다른 슬라이스는 별칭을 쓴 절대 경로로 import합니다. 자기 index를 "../"로 가져오면 순환 import가 생기기 때문입니다.[2] shared는 세그먼트마다 공개 API를 두고[8], shared/ui가 번들을 키우면 @/shared/ui/button처럼 컴포넌트마다 index를 둡니다.[2]

자주 하는 실수: 슬라이스 내부 파일 직접 import

import { ArticleCard } from "@/entities/article/ui/ArticleCard"; // ❌
import { ArticleCard } from "@/entities/article";                // ✅

index 파일은 직접 import를 막지 못하고, IDE 자동 import가 내부 경로를 고르는 일도 있어 공식 문서는 Steiger 검사를 권합니다.[2]

@x: 엔티티 전용 창구

교차 import(cross-import)는 같은 레이어 다른 슬라이스의 import이고, 공식 가이드는 이를 코드 스멜로 봅니다.[4] 다만 비즈니스 개념은 서로를 참조하는 일이 많아서, 한 엔티티가 특정 엔티티 전용 공개 API를 열 수 있습니다. A/@x/B는 "A crossed with B"로 읽습니다.[2]

// entities/user/@x/article.ts
export type { User } from "../model/user";

// entities/article/model/article.ts
import type { User } from "@/entities/user/@x/article";

export interface Article {
  slug: string;
  title: string;
  author: User;
  favorited: boolean;
}

@x는 entities에서만, 최소한으로 씁니다.[2] 엔티티를 너무 잘게 나눠서 생기는 경우가 많으니 합칠지부터 따지고, @x는 최후의 수단으로 둡니다.[4] features·widgets에서는 합치기, entities로 내리기, 위 레이어에서 조립하기, 공개 API로만 쓰기 중에서 고릅니다.[4]

Steiger로 규칙 검사하기

Steiger는 파일 구조·아키텍처 린터이고 FSD 규칙은 플러그인으로 설치합니다. 아직 베타라 일부 API가 바뀔 수 있습니다.[5]

npm i -D steiger
npm i -D @feature-sliced/steiger-plugin
npx steiger ./src          # 한 번 검사
npx steiger ./src --watch  # 감시 모드

설정 없이도 동작하고, 조정할 때는 steiger.config.js를 둡니다. 형식은 ESLint 설정을 본떴고 0.5.0에서 바뀌었습니다.[5]

// steiger.config.js
import { defineConfig } from "steiger";
import fsd from "@feature-sliced/steiger-plugin";

export default defineConfig([
  ...fsd.configs.recommended,
  { rules: { "fsd/no-wildcard-exports": "error" } }, // 기본은 꺼짐
]);
규칙 잡는 것
fsd/forbidden-imports 위 레이어 import, 같은 레이어 교차 import[5]
fsd/no-public-api-sidestep 공개 API를 우회한 내부 파일 import[5]
fsd/excessive-slicing 묶이지 않은 슬라이스가 너무 많음(현재 임계값 20)[9]
fsd/insignificant-slice 한 곳에서만 쓰여 위 레이어로 합칠 슬라이스[10]
fsd/no-wildcard-exports 공개 API의 export *, 기본 꺼짐[5][3]

앞의 @/entities/user 직접 import는 forbidden-imports에 걸리고 @x/article 경로는 통과합니다.[11] @/entities/article/ui/ArticleCard는 no-public-api-sidestep 위반입니다.[12] 설정한 뒤에는 일부러 features/like-article에서 @/pages/feed를 import해 오류가 나는지부터 확인하세요.

정리

질문 FSD의 답
최상위 폴더는? 표준 레이어 중 필요한 것만, processes는 deprecated[1]
누가 누구를 import하나? 엄격히 아래 레이어만, app·shared 안은 자유[1]
슬라이스 안은? ui·api·model·lib·config처럼 목적으로[7]
밖에 보여 줄 것은? index의 공개 API만, export * 없이[2]
엔티티끼리 참조하면? @x 전용 창구, 그 전에 합칠지 검토[2][4]
feature끼리 엮으려면? 페이지 같은 위 레이어에서 조립[4]
규칙은 누가 지키나? Steiger와 FSD 플러그인[5]

프론트엔드 팀이 해 볼 것

  1. 프로젝트의 최상위 폴더를 FSD 레이어에 대응시켜 보고, shared나 utils 안에 비즈니스 로직이 있는 파일을 세어 본다
  2. 가장 많이 쓰는 슬라이스 하나의 index 파일에서 export *를 이름 목록으로 바꾼다
  3. npm i -D steiger @feature-sliced/steiger-plugin 후 npx steiger ./src를 실행해 fsd/forbidden-imports 위반부터 확인한다
