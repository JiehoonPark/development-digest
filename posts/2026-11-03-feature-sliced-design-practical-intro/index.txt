17:T5b24,<h2 id="레이어-위에서-아래로만-import한다">레이어: 위에서 아래로만 import한다</h2>
<p>Feature-Sliced Design(FSD)은 프론트엔드 애플리케이션의 코드 배치 규칙과 관례를 모은 방법론입니다. 라이브러리가 아닌 애플리케이션이면 언어·UI 프레임워크·상태 관리 도구와 상관없이 쓸 수 있습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> 기능별로 폴더를 모으는 이유는 「components·hooks·utils 폴더를 버리는 이유 — 기능별 수직 구조」에서 다뤘으니, 여기서는 FSD만의 규칙에 집중합니다.</p>
<p>FSD는 레이어(layer) → 슬라이스(slice) → 세그먼트(segment) 3단계로 코드를 나눕니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> 레이어는 이름이 표준으로 정해진 최상위 폴더이고, 위에서부터 다음과 같습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup><sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>

<p>모든 레이어를 쓸 필요는 없고, 대부분의 프로젝트는 최소한 shared, pages, app을 갖습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 핵심 규칙은 하나입니다. <em>슬라이스 안의 파일은 자기보다 엄격히 아래 레이어의 슬라이스만 import할 수 있습니다.</em><sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// features/like-article/api/likeArticle.ts</span>
<span class="hljs-keyword">import</span> { apiFetch } <span class="hljs-keyword">from</span> <span class="hljs-string">"@/shared/api"</span>;          <span class="hljs-comment">// OK: 아래 레이어</span>
<span class="hljs-keyword">import</span> <span class="hljs-keyword">type</span> { <span class="hljs-title class_">Article</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"@/entities/article"</span>; <span class="hljs-comment">// OK: 아래 레이어</span>
<span class="hljs-keyword">import</span> { <span class="hljs-title class_">FeedPage</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"@/pages/feed"</span>;           <span class="hljs-comment">// ❌ 위 레이어</span>
<span class="hljs-keyword">import</span> { <span class="hljs-title class_">CommentForm</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"@/features/comment"</span>;  <span class="hljs-comment">// ❌ 같은 레이어 다른 슬라이스</span>
</code></pre>
<p>app과 shared는 슬라이스 없이 세그먼트로 바로 나뉘고, 세그먼트끼리는 자유롭게 import할 수 있습니다. shared에는 비즈니스 도메인이 없고, app은 모든 도메인을 묶기 때문입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<aside class="callout-rule" aria-label="기억할 규칙"><p class="callout-head"><span class="callout-tag">규칙</span><strong>FSD import 규칙</strong></p><ol><li>레이어는 자기보다 아래 레이어만 import합니다.</li><li>같은 레이어의 다른 슬라이스는 import하지 않습니다.</li><li>슬라이스 밖에서는 공개 API(<code>index.ts</code>)만 참조합니다.</li></ol></aside>
<p>팀에서 이런 요청을 받았다고 가정해 봅시다. "피드의 글마다 좋아요 버튼을 달고, 나중에 글 상세 페이지에도 같은 버튼을 붙여 주세요." 이 버튼은 서버에 요청을 보내는 사용자 행동이므로 features에 두고, 글 카드는 어디서나 같은 모습으로 쓰이는 비즈니스 개념이므로 entities에 둡니다. 두 페이지가 버튼을 함께 쓰니 pages 안에 넣지 않는 것입니다.</p>
<figure><img src="/development-digest/figures/fsd-like-button-layers.svg" alt="좋아요 버튼을 추가할 때 레이어별 파일 위치" loading="lazy"><figcaption>그림 1 · 화살표는 import 방향입니다. 버튼(features)이 피드 페이지(pages)를 import하면 규칙 위반입니다</figcaption></figure>
<h2 id="슬라이스와-세그먼트-글-목록좋아요-앱-나누기">슬라이스와 세그먼트: 글 목록·좋아요 앱 나누기</h2>
<p>슬라이스는 레이어 안을 비즈니스 도메인으로 나눈 폴더이고 이름은 도메인이 정합니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 세그먼트는 슬라이스 안을 목적으로 나눈 폴더입니다. 관례 이름은 <code>ui</code>(화면 표시), <code>api</code>(백엔드 통신), <code>model</code>(스키마·스토어·비즈니스 로직), <code>lib</code>(슬라이스 안에서 쓰는 라이브러리 코드), <code>config</code>(설정·기능 플래그)입니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> <code>components</code>, <code>hooks</code>, <code>types</code>는 본질만 말하고 목적을 말하지 않아 나쁜 이름으로 꼽힙니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<p>피드의 글마다 좋아요 버튼이 붙는 앱을 나눠 봅니다. 공식 튜토리얼의 Conduit 예제도 이런 피드를 다룹니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>

<p>좋아요가 feature인 이유는 피드와 글 상세 두 페이지에서 쓰이기 때문입니다. 여러 페이지에서 재사용된다는 것이 feature로 만들 좋은 신호입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 재사용되지 않는 큰 UI 블록은 위젯이 아니라 페이지 안에 두므로 widgets는 비워 둡니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<p>엔티티의 UI는 같은 모습을 여러 곳에서 재사용하는 것이 목적이고, 다른 비즈니스 로직은 props나 슬롯으로 붙입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 그래서 <code>ArticleCard</code>는 좋아요를 모르고 <code>actions</code> 자리만 둡니다.</p>

</code></pre>
<h4>자주 하는 실수: features를 너무 잘게 쪼개기</h4>
<p><code>like-button</code>, <code>like-count</code>, <code>unlike</code>처럼 동작마다 슬라이스를 만들면 중요한 feature가 묻힙니다. 공식 문서는 모든 것이 feature일 필요는 없다고 하고, 새로 온 사람이 pages와 features만 보고 큰 기능을 찾을 수 있게 하라고 권합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 늘 함께 바뀌며 서로 import하는 슬라이스는 합칩니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<h4>자주 하는 실수: shared에 비즈니스 로직 넣기</h4>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// ❌ shared/lib/article.ts — shared가 '글'이라는 도메인을 알게 됨</span>
<span class="hljs-keyword">export</span> <span class="hljs-keyword">const</span> <span class="hljs-title function_">canLike</span> = (<span class="hljs-params"><span class="hljs-attr">article</span>: { favorited: <span class="hljs-built_in">boolean</span> }</span>) => !article.<span class="hljs-property">favorited</span>;
</code></pre>
<p>shared에는 비즈니스 로직이 없어야 합니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 이 함수는 <code>entities/article/model</code>로 옮깁니다. <code>shared/lib</code>도 헬퍼 모음이 아니라 날짜·색처럼 관심사 하나에 집중한 라이브러리를 README와 함께 두는 곳입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h2 id="공개-api와-x-교차-import">공개 API와 @x 교차 import</h2>
<p>공개 API(public API)는 슬라이스와 그것을 쓰는 코드 사이의 계약이자 관문이고, 보통 다시 내보내기(re-export)만 담은 index 파일로 만듭니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 슬라이스 밖에서는 내부 파일이 아니라 공개 API만 참조할 수 있습니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// entities/article/index.ts</span>
<span class="hljs-keyword">export</span> <span class="hljs-keyword">type</span> { <span class="hljs-title class_">Article</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"./model/article"</span>;
<span class="hljs-keyword">export</span> { getArticles } <span class="hljs-keyword">from</span> <span class="hljs-string">"./api/getArticles"</span>;
<span class="hljs-keyword">export</span> { <span class="hljs-title class_">ArticleCard</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"./ui/ArticleCard"</span>;
</code></pre>
<h3 id="export-를-피하는-이유">export *를 피하는 이유</h3>
<p><code>export * from "./ui/Comment"</code>처럼 쓰면 파일을 다 열어 보기 전에는 인터페이스를 알 수 없고, 내부 구현이 실수로 노출돼 리팩터링이 어려워집니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 내부 모듈에 export를 하나 추가하면 공개 API도 같이 늘고, 나중에 지우면 그사이 쓰기 시작한 코드가 깨집니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> <code>export * as model from "./model"</code> 같은 네임스페이스 재내보내기도 같은 문제를 남깁니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>배럴 파일 일반론은 「파일만 나누면 끝일까 — JavaScript 모듈 경계 설계」에서 다뤘습니다. FSD는 경로 규칙을 정해 둡니다. 같은 슬라이스 안은 전체 경로의 상대 경로로, 다른 슬라이스는 별칭을 쓴 절대 경로로 import합니다. 자기 index를 <code>"../"</code>로 가져오면 순환 import가 생기기 때문입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> shared는 세그먼트마다 공개 API를 두고<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup>, <code>shared/ui</code>가 번들을 키우면 <code>@/shared/ui/button</code>처럼 컴포넌트마다 index를 둡니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h4>자주 하는 실수: 슬라이스 내부 파일 직접 import</h4>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-keyword">import</span> { <span class="hljs-title class_">ArticleCard</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"@/entities/article/ui/ArticleCard"</span>; <span class="hljs-comment">// ❌</span>
<span class="hljs-keyword">import</span> { <span class="hljs-title class_">ArticleCard</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"@/entities/article"</span>;                <span class="hljs-comment">// ✅</span>
</code></pre>
<p>index 파일은 직접 import를 막지 못하고, IDE 자동 import가 내부 경로를 고르는 일도 있어 공식 문서는 Steiger 검사를 권합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h3 id="x-엔티티-전용-창구">@x: 엔티티 전용 창구</h3>
<p>교차 import(cross-import)는 같은 레이어 다른 슬라이스의 import이고, 공식 가이드는 이를 코드 스멜로 봅니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 다만 비즈니스 개념은 서로를 참조하는 일이 많아서, 한 엔티티가 특정 엔티티 전용 공개 API를 열 수 있습니다. <code>A/@x/B</code>는 "A crossed with B"로 읽습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// entities/user/@x/article.ts</span>
<span class="hljs-keyword">export</span> <span class="hljs-keyword">type</span> { <span class="hljs-title class_">User</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"../model/user"</span>;

<span class="hljs-comment">// entities/article/model/article.ts</span>
<span class="hljs-keyword">import</span> <span class="hljs-keyword">type</span> { <span class="hljs-title class_">User</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">"@/entities/user/@x/article"</span>;

<span class="hljs-keyword">export</span> <span class="hljs-keyword">interface</span> <span class="hljs-title class_">Article</span> {
  <span class="hljs-attr">slug</span>: <span class="hljs-built_in">string</span>;
  <span class="hljs-attr">title</span>: <span class="hljs-built_in">string</span>;
  <span class="hljs-attr">author</span>: <span class="hljs-title class_">User</span>;
  <span class="hljs-attr">favorited</span>: <span class="hljs-built_in">boolean</span>;
}
</code></pre>
<p><code>@x</code>는 entities에서만, 최소한으로 씁니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 엔티티를 너무 잘게 나눠서 생기는 경우가 많으니 합칠지부터 따지고, <code>@x</code>는 최후의 수단으로 둡니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> features·widgets에서는 합치기, entities로 내리기, 위 레이어에서 조립하기, 공개 API로만 쓰기 중에서 고릅니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<h2 id="steiger로-규칙-검사하기">Steiger로 규칙 검사하기</h2>
<p>Steiger는 파일 구조·아키텍처 린터이고 FSD 규칙은 플러그인으로 설치합니다. 아직 베타라 일부 API가 바뀔 수 있습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<pre data-lang="bash"><code class="hljs language-bash">npm i -D steiger
npm i -D @feature-sliced/steiger-plugin
npx steiger ./src          <span class="hljs-comment"># 한 번 검사</span>

<p>설정 없이도 동작하고, 조정할 때는 <code>steiger.config.js</code>를 둡니다. 형식은 ESLint 설정을 본떴고 0.5.0에서 바뀌었습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>

]);
</code></pre>
