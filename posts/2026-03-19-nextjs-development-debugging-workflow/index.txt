18:T5c14,<h2 id="시작이-느린가-렌더링이-느린가">시작이 느린가, 렌더링이 느린가</h2>
<p>개발 중의 대기 시간은 한 종류가 아닙니다. 서버를 켜고 주소가 준비될 때까지 기다리기도 하고, 코드를 저장한 뒤 화면이 바뀌기를 기다리기도 합니다. 화면이 나타난 뒤에는 오류 원인을 찾느라 시간을 씁니다.</p>
<p>Next.js 16.2는 개발 서버 시작, 렌더링 성능과 함께 오류를 관찰하는 도구를 개선했습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 여기서는 탐색 캐시나 배포용 청크 구성보다 <strong>실행하고, 재현하고, 원인을 확인하는 개발 과정</strong>에 집중합니다.</p>
<h3 id="성능-수치는-측정-구간과-함께-읽기">성능 수치는 측정 구간과 함께 읽기</h3>
<p>릴리스 첫머리는 개발 서버 시작을 “~400% faster next dev startup”, 렌더링을 “~50% faster rendering”으로 소개합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 다만 시작 속도 상세 설명에는 같은 장비와 기본 애플리케이션에서 Next.js 16.1 대비 “~87% faster”라고 적혀 있습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 이 글에서는 서로 다른 표현을 임의로 환산하거나 같은 측정 결과라고 단정하지 않습니다.</p>
<p>개발 시작 시간(Time-to-URL)은 <code>next dev</code> 실행 후 로컬 주소가 준비되기까지의 구간입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 아래 명령으로 개발 서버를 켜되, 주소가 준비된 시점과 페이지 렌더링이 끝난 시점을 별도로 기록하는 편이 좋습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<pre data-lang="bash"><code class="hljs language-bash">npx next dev
<span class="hljs-comment"># 개발 모드 서버를 시작합니다.</span>
<span class="hljs-comment"># 주소 준비와 페이지 렌더링 완료를 구분해 관찰합니다.</span>
</code></pre>
<p>릴리스 본문에는 시작 과정의 세부 구현이 설명돼 있지 않습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 따라서 뒤에서 다룰 JSON 처리 개선을 시작 속도의 원인으로 연결하지 않습니다. 업그레이드 전후를 비교할 때도 같은 프로젝트와 장비, 같은 관찰 구간을 맞춰야 수치의 의미가 남습니다.</p>
<h3 id="렌더링에서는-json을-읽는-방식이-달라졌습니다">렌더링에서는 JSON을 읽는 방식이 달라졌습니다</h3>
<p>서버 컴포넌트(RSC) 페이로드 역직렬화는 전달받은 데이터를 다시 객체로 복원하고 RSC 표현을 해석하는 과정입니다. 기존 구현은 <code>JSON.parse</code>의 변환 콜백(reviver)을 사용했고, 키·값 쌍마다 V8의 C++ 구현에서 JavaScript 콜백으로 넘어가는 비용이 발생했습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup><sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<p>아래는 콜백이 붙은 파싱과 일반 파싱을 비교하는 최소 예제입니다. React 구현이나 성능 벤치마크를 재현하는 코드는 아니며, 두 호출 형태만 보여 줍니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-keyword">const</span> payload = <span class="hljs-string">'{"title":"개발 로그"}'</span>;
<span class="hljs-keyword">const</span> withReviver = <span class="hljs-title class_">JSON</span>.<span class="hljs-title function_">parse</span>(payload, <span class="hljs-function">(<span class="hljs-params">key, value</span>) =></span> value);
<span class="hljs-keyword">const</span> withoutReviver = <span class="hljs-title class_">JSON</span>.<span class="hljs-title function_">parse</span>(payload);
<span class="hljs-comment">// 두 객체의 title은 모두 '개발 로그'입니다.</span>
<span class="hljs-comment">// 위 예제에서는 별도의 RSC 변환을 수행하지 않습니다.</span>
</code></pre>
<p>새 구현은 콜백 없이 <code>JSON.parse()</code>를 실행한 뒤, JavaScript의 재귀 순회로 RSC 변환을 수행합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 순회 중에도 <code>$</code>로 시작하지 않는 일반 문자열은 특수 문자열 해석을 건너뜁니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 객체를 다시 훑는 일이 추가돼도 언어 실행 경계를 반복해서 넘는 비용을 없애는 쪽이 유리했던 사례입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup><sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<p>원문은 역직렬화를 “up to 350% faster”, 실제 Next.js 애플리케이션의 HTML 렌더링을 “25% to 60% faster”라고 구분하며, 후자는 RSC 페이로드 크기에 따라 달라진다고 설명합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 이 수치를 API 응답이나 데이터베이스 조회까지 포함한 전체 요청의 개선율로 옮겨 쓰면 안 됩니다.</p>
<h3 id="저장-후-갱신은-또-다른-경로입니다">저장 후 갱신은 또 다른 경로입니다</h3>
<p>서버 Fast Refresh도 시작 속도와 구분해야 합니다. 이전 방식은 바뀐 모듈과 import 연결에 있는 모듈들의 <code>require.cache</code>를 비워 변경되지 않은 <code>node_modules</code>까지 다시 불러오는 일이 있었습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 새 방식은 Turbopack의 모듈 그래프를 이용해 실제로 바뀐 모듈만 다시 불러오도록 범위를 줄입니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<p>이 기능은 기본으로 활성화되지만, 해당 릴리스에서 Proxy와 Route Handler는 기존 방식을 유지합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 서버 컴포넌트 수정 후 갱신이 빨라졌다는 관찰을 모든 서버 코드에 그대로 적용하지 않는 것이 좋습니다.</p>
<h2 id="서버-실행과-화면-불일치의-흔적-읽기">서버 실행과 화면 불일치의 흔적 읽기</h2>
<h3 id="server-function-로그에서-확인할-것">Server Function 로그에서 확인할 것</h3>
<p>서버 함수(Server Function)는 서버에서 실행하도록 지정한 함수입니다. 함수나 파일 맨 위의 <code>'use server'</code>로 표시하며, 클라이언트 컴포넌트에서는 별도 파일에 정의된 서버 함수를 가져와 호출할 수 있습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<p>개발 중에는 Next.js가 실행된 서버 함수의 이름, 인자, 실행 시간과 정의된 파일을 터미널에 기록합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 다음 예제는 저장이나 인증 로직 없이 호출 여부만 확인하도록 만든 진단용 함수입니다. 서버 함수 파일과 이를 호출하는 페이지를 나눕니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// app/actions.ts</span>

<span class="hljs-keyword">export</span> <span class="hljs-keyword">async</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">inspectLabel</span>(<span class="hljs-params"><span class="hljs-attr">label</span>: <span class="hljs-built_in">string</span></span>) {
  <span class="hljs-keyword">return</span> label;
}
<span class="hljs-comment">// 반환값은 전달받은 문자열 그대로입니다.</span>
</code></pre>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-comment">// app/page.tsx</span>

<span class="hljs-comment">// 반환값을 화면에 표시하는 예제는 아닙니다.</span>
</code></pre>
<p>버튼을 눌렀다면 함수 이름과 정의 파일을 먼저 확인하고, 그다음 인자와 시간을 읽습니다. 로그의 숫자부터 보기보다 의도한 함수를 호출했는지 확인하는 순서입니다. 실제 데이터 변경 함수로 확장할 때는 입력 검증과 인증·인가를 별도로 구현해야 합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<p>이 로그를 운영 환경의 감사 로그로 생각하면 안 됩니다. 릴리스가 설명하는 범위는 개발 터미널입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 인자도 표시되는 만큼 예제에는 민감한 데이터를 넣지 않는 편이 안전합니다. 공식 서버 함수 문서 역시 인증 토큰을 인자로 받기보다 쿠키나 헤더에서 인증 정보를 읽도록 안내합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<h3 id="hydration-diff의-부호는-출처를-가리킵니다">Hydration Diff의 부호는 출처를 가리킵니다</h3>
<p>하이드레이션(hydration)은 서버가 만든 HTML에 이벤트 핸들러를 연결해 상호작용 가능한 화면으로 만드는 과정입니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 서버에서 미리 렌더링한 트리와 브라우저의 첫 렌더링 결과가 다르면 불일치가 발생합니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 오류 화면은 이를 <code>+ Client / - Server</code>로 표시해 각각 어느 쪽의 내용인지 구분합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<p>원인을 재현하려면 브라우저 전용 값으로 첫 렌더링을 갈라 보면 됩니다. 공식 문서가 원인으로 드는 <code>typeof window !== 'undefined'</code> 검사를 사용한 의도적인 오류 예제입니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-comment">// app/page.tsx — 위 페이지 예제와 교체해 실행합니다.</span>
<span class="hljs-string">'use client'</span>;

<span class="hljs-keyword">export</span> <span class="hljs-keyword">default</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">MismatchPage</span>(<span class="hljs-params"></span>) {
  <span class="hljs-keyword">const</span> isBrowser = <span class="hljs-keyword">typeof</span> <span class="hljs-variable language_">window</span> !== <span class="hljs-string">'undefined'</span>;
  <span class="hljs-keyword">return</span> <span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">p</span>></span>{isBrowser ? '브라우저' : '서버'}<span class="hljs-tag">&#x3C;/<span class="hljs-name">p</span>></span></span>;
}
<span class="hljs-comment">// 서버 출력: '서버', 브라우저 첫 출력: '브라우저'</span>
<span class="hljs-comment">// 개발 오류 화면에서 + Client와 - Server 쪽을 비교합니다.</span>
</code></pre>
<p><code>+</code>를 정상, <code>-</code>를 오류라고 읽지 않습니다. 표시는 값의 출처를 알려 줄 뿐 어느 쪽이 의도한 결과인지는 애플리케이션 코드로 판단해야 합니다. 이 예제의 문제는 양쪽의 첫 출력이 다르다는 것입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup><sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<p>브라우저에서만 내용을 바꾸려는 의도라면 처음에는 같은 값을 렌더링하고 <code>useEffect</code>에서 상태를 바꾸는 방식으로 수정할 수 있습니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-comment">// app/page.tsx — 불일치 예제를 대체합니다.</span>
<span class="hljs-string">'use client'</span>;

<span class="hljs-keyword">import</span> { useEffect, useState } <span class="hljs-keyword">from</span> <span class="hljs-string">'react'</span>;

<span class="hljs-keyword">export</span> <span class="hljs-keyword">default</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">MatchedPage</span>(<span class="hljs-params"></span>) {
  <span class="hljs-keyword">const</span> [isClient, setIsClient] = <span class="hljs-title function_">useState</span>(<span class="hljs-literal">false</span>);
  <span class="hljs-title function_">useEffect</span>(<span class="hljs-function">() =></span> {
    <span class="hljs-title function_">setIsClient</span>(<span class="hljs-literal">true</span>);
  }, []);
  <span class="hljs-keyword">return</span> <span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">p</span>></span>{isClient ? '브라우저' : '공통 화면'}<span class="hljs-tag">&#x3C;/<span class="hljs-name">p</span>></span></span>;
}
<span class="hljs-comment">// 서버와 브라우저의 첫 출력: '공통 화면'</span>
<span class="hljs-comment">// Effect 실행 후 브라우저 출력: '브라우저'</span>
</code></pre>
<p>불일치를 보자마자 <code>suppressHydrationWarning</code>을 붙이는 것도 피해야 합니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 공식 문서는 이를 불가피한 차이를 위한 제한적인 탈출구로 설명하며, 설정된 요소의 불일치 텍스트를 React가 수정하려고 시도하지 않는다고 명시합니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 먼저 차이가 생긴 입력과 렌더링 분기를 확인하는 편이 낫습니다.</p>
<aside class="callout-pitfall" aria-label="증상과 확인할 곳"><p class="callout-head"><span class="callout-tag">증상</span><strong>하이드레이션 경고를 끄고 싶어진다</strong></p><p><code>suppressHydrationWarning</code>을 붙이기 전에, 서버와 클라이언트가 다른 값을 만든 입력과 분기부터 찾습니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p></aside>
<h2 id="프로덕션-모드에서만-느리다면">프로덕션 모드에서만 느리다면</h2>
<p><code>next start --inspect</code>는 프로덕션 모드 서버에 Node.js 디버거를 연결하는 실행 방식입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 개발 모드의 로그만으로 판단하기 어려운 문제를 프로덕션 빌드에서 재현할 때 사용할 수 있습니다. 단, 프로덕션 모드라는 말이 곧 실제 서비스 서버에서 실행하라는 뜻은 아닙니다.</p>
<p>실습은 로컬에서 빌드한 결과로 시작하는 편이 안전합니다. <code>next start</code>를 실행하려면 먼저 <code>next build</code>로 빌드해야 하며, 아래 명령은 빌드가 성공했을 때만 서버를 시작합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<pre data-lang="bash"><code class="hljs language-bash">npx next build &#x26;&#x26; npx next start --inspect
<span class="hljs-comment"># 프로덕션 빌드를 만든 뒤 디버거 연결이 가능한 서버를 시작합니다.</span>
</code></pre>
<p>Chrome 주소창에서 <code>chrome://inspect</code>를 열고 대상의 검사 링크를 선택하면 Node용 DevTools에 연결할 수 있습니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> CPU 사용 구간을 보려면 Performance 패널에서 기록을 시작하고, 조사할 요청을 재현한 뒤 기록을 멈춥니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<p>결과의 Bottom-Up은 선택 구간에서 활동별로 누적된 시간을 보는 데 쓰고, Call Tree는 어떤 상위 호출이 하위 작업을 발생시켰는지 추적하는 데 씁니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> 먼저 오래 걸린 활동을 찾고 호출 경로를 따라가는 식으로 읽으면 원인 후보를 좁히기 좋습니다.</p>
<p>흔히 빠뜨리는 것은 요청 재현입니다. 서버에 연결했다는 사실만으로 문제 상황의 프로파일이 만들어지지는 않습니다. 느린 동작을 기록 구간 안에 넣고, 개발 서버에서의 관찰과 프로덕션 빌드에서의 관찰을 구분해 남기세요.</p>
<h2 id="에이전트에도-문서와-브라우저-오류가-필요합니다">에이전트에도 문서와 브라우저 오류가 필요합니다</h2>
<h3 id="설치된-버전의-문서를-읽게-하기">설치된 버전의 문서를 읽게 하기</h3>
<p>에이전트가 과거에 학습한 API만 보고 코드를 작성한다면 프로젝트와 맞지 않는 구현을 제안할 수 있습니다. <code>create-next-app</code>은 기본으로 <code>AGENTS.md</code>를 포함하며, 설치된 패키지의 문서를 먼저 읽으라고 지시합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> Next.js 16.2 이상에서는 문서가 <code>node_modules/next/dist/docs/</code>에 마크다운으로 동봉됩니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<p>기존 프로젝트에는 루트의 <code>AGENTS.md</code>에 다음처럼 읽을 위치를 명시할 수 있습니다. 공식 예제의 관리 구간 표시를 유지하고 지시문만 한국어로 쓴 예입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<pre data-lang="md"><code class="hljs language-md">&#x3C;!-- BEGIN:nextjs-agent-rules -->
Next.js 코드를 작성하기 전에
node<span class="hljs-emphasis">_modules/next/dist/docs/에서 관련 문서를 읽습니다.
설치된 버전의 문서를 기준으로 구현합니다.
&#x3C;!-- END:nextjs-agent-rules -->
</span></code></pre>
<p>프로젝트 고유 규칙은 주석 표시 바깥에 둡니다. 공식 설명에 따르면 이후 갱신은 표시 사이의 Next.js 관리 구간만 교체합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 파일을 추가했다고 모든 에이전트의 정확성이 보장되는 것은 아니므로, 실제로 어떤 문서를 참고했는지도 작업 결과에서 확인하는 편이 좋습니다.</p>
<h3 id="브라우저-로그를-터미널로-모으기">브라우저 로그를 터미널로 모으기</h3>
<p>브라우저 로그 전달(browser log forwarding)은 클라이언트 오류를 개발 터미널에서도 읽게 하는 기능입니다. 기본값은 오류만 전달하며 <code>logging.browserToTerminal</code>로 범위를 조절합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 에이전트가 터미널만 볼 때도 브라우저 오류가 관찰에서 빠지지 않도록 돕습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// next.config.ts</span>
<span class="hljs-keyword">const</span> nextConfig = {
  <span class="hljs-attr">logging</span>: {
    <span class="hljs-attr">browserToTerminal</span>: <span class="hljs-string">'warn'</span>,
  },
};
<span class="hljs-keyword">export</span> <span class="hljs-keyword">default</span> nextConfig;
<span class="hljs-comment">// 개발 중 브라우저의 경고와 오류를 터미널에 전달합니다.</span>
</code></pre>
<p><code>'error'</code>는 오류만, <code>'warn'</code>은 경고와 오류, <code>true</code>는 모든 콘솔 출력, <code>false</code>는 전달 중단입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 위 예제처럼 필요한 수준을 먼저 고르고, 일반 콘솔 출력까지 조사해야 할 때 범위를 넓히는 편이 읽기 쉽습니다.</p>
<p>서버 함수 실행 로그와 브라우저 로그가 같은 터미널에 보이더라도 실행 장소는 다릅니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup><sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 에이전트에 수정을 맡길 때는 재현한 동작, 브라우저에서 난 오류, 서버에서 호출된 함수를 함께 전달하세요. 한쪽 로그만 보고 다른 쪽 코드부터 고치는 일을 줄일 수 있습니다.</p>
