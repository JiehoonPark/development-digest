아일랜드로 이해하는 RSC — Astro 개발자를 위한 서버 컴포넌트

Astro의 Astro 컴포넌트와 클라이언트 아일랜드는 React의 서버 컴포넌트와 클라이언트 컴포넌트에 거의 그대로 대응합니다. 같은 화면을 두 방식으로 써 보며 어디까지 같고 어디서 갈라지는지 코드로 비교합니다.

요약

  • Astro 컴포넌트는 서버에서만 실행되고 클라이언트 아일랜드는 브라우저에서도 실행되며, RSC의 서버 컴포넌트와 클라이언트 컴포넌트가 같은 역할을 나눠 맡는다[1][2]
  • Astro는 쓰는 자리에 client:* 지시어를 붙여 하이드레이션을 고르고, RSC는 파일 맨 위 'use client'로 모듈 단위 경계를 긋는다[3][4]
  • 두 방식 모두 경계를 넘는 props는 직렬화돼야 하지만, RSC는 서버 함수와 JSX를 props로 넘길 수 있다[5][3][6]
  • Astro 아일랜드는 서로 다른 루트라 Context를 공유하지 못하고, RSC는 화면 전체가 하나의 React 트리라 Context가 서버 영역을 건너 내려간다[1][7]

두 세계와 그 사이의 문

Astro 프로젝트에는 두 종류의 컴포넌트가 있습니다. .astro 파일로 쓰는 Astro 컴포넌트는 빌드 중이나 요청 시 서버에서 HTML로 렌더링되고, 클라이언트 런타임이 없습니다[2]. React·Vue 같은 프레임워크로 쓴 컴포넌트에 client:* 지시어를 붙이면 브라우저에서 하이드레이션되는 클라이언트 아일랜드(client island)가 됩니다[8].

React Server Components(RSC)도 같은 두 역할을 나눕니다. 이름만 서버 컴포넌트와 클라이언트 컴포넌트로 바뀝니다[1]. 원문 필자는 Astro를 안다면 RSC 사고 모델의 80%를 이미 갖고 있다고 봅니다[1].

같은 화면, 두 가지 코드

글 제목을 파일에서 읽어 오고, 그 아래에 좋아요 버튼을 두는 화면입니다. 먼저 Astro입니다[1].

---
// PostPreview.astro — 서버에서만 실행
import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';
const { slug } = Astro.props;
const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
---
<article>
  <h1>{title}</h1>
  <LikeButton client:load />
</article>
<!-- readFile 코드는 브라우저로 가지 않음. LikeButton만 하이드레이션 -->

같은 화면을 RSC로 쓰면 다음과 같습니다[1].

// PostPreview.tsx — 서버 컴포넌트
import { readFile } from 'fs/promises';
import { LikeButton } from './LikeButton';

async function PostPreview({ slug }) {
  const title = await readFile(`./posts/${slug}/title.txt`, 'utf8');
  return (
    <article>
      <h1>{title}</h1>
      <LikeButton />
    </article>
  );
}

// LikeButton.tsx — 클라이언트 컴포넌트
'use client';
import { useState } from 'react';

export function LikeButton() {
  const [liked, setLiked] = useState(false);
  return (
    <button onClick={() => setLiked(!liked)}>
      {liked ? '❤️' : '🤍'} Like
    </button>
  );
}
// 클릭할 때마다 🤍 ↔ ❤️ 전환

서버 쪽이 전처리를 하고 상호작용 부분만 클라이언트 쪽에 넘기며, 데이터는 위에서 아래로만 흐릅니다[1]. 문법 차이는 셋입니다. 서버 컴포넌트는 평범한 async 함수이고, props는 Astro.props 대신 함수 인자로 받으며, 세계를 가르는 표시는 .astro 확장자 대신 'use client'입니다[1].

자주 하는 실수: 반대 방향으로 import하기

Astro에서는 프레임워크 컴포넌트 안에서 .astro 파일을 import할 수 없습니다[5]. RSC에서도 클라이언트 쪽에서 import한 코드는 클라이언트에서 실행되고, 그 코드가 DB 같은 서버 기능을 쓰면 빌드 오류가 납니다[1]. 서버 결과를 클라이언트 쪽 안에 넣으려면 import 대신 children으로 넘깁니다.

문은 어디에 내는가: client:* 와 'use client'

두 방식의 가장 큰 차이는 "이 컴포넌트를 브라우저에서도 돌릴지"를 정하는 위치입니다.

Astro: 쓰는 자리에서 고른다

Astro에서 프레임워크 컴포넌트는 지시어가 없으면 서버에서 정적 HTML로만 렌더링되고 JavaScript는 보내지 않습니다[5][4]. 같은 컴포넌트라도 쓰는 자리마다 다르게 정할 수 있고, 하이드레이션 시점도 고를 수 있습니다[4].

---
import Counter from '../components/Counter.jsx';
---
<Counter />                <!-- 정적 HTML만, JS 없음 -->
<Counter client:load />    <!-- 페이지 로드 즉시 하이드레이션 -->
<Counter client:visible /> <!-- 뷰포트에 들어오면 하이드레이션 -->
<Counter client:only="react" /> <!-- 서버 렌더링 없이 클라이언트에서만 -->

client:idle은 requestIdleCallback 이후, client:media는 미디어 쿼리가 맞을 때 하이드레이션합니다[4]. client:only는 서버에서 실행하지 않으므로 프레임워크 이름을 값으로 넘겨야 합니다[4].

RSC: 정의한 파일에서 정한다

RSC에는 정적/하이드레이션을 고르는 지시어가 없습니다. 원문 필자의 설명으로는, 상호작용하게 만든 컴포넌트에서 상호작용을 떼는 건 실수라는 것이 React의 관점입니다. 상호작용이 필요 없다면 'use client'를 지우면 서버에서만 실행됩니다[1].

'use client'는 쓰는 자리가 아니라 모듈에 붙습니다. 파일 맨 위에 쓰면 그 모듈과 전이 의존성이 모두 클라이언트 코드가 됩니다[3]. 경계가 모듈 의존성 트리에 그어지는 원리와 번들러의 역할은 이전 글 「RSC가 번들러와 붙어 다니는 이유」에서 다뤘습니다.

양쪽에서 쓸 수 있는 컴포넌트

Astro에서는 문법이 달라 한 코드가 두 역할을 겸할 수 없습니다. RSC는 양쪽이 모두 React라서, 상태도 서버 기능도 쓰지 않는 컴포넌트는 어느 쪽에서든 import할 수 있습니다[1].

// Markdown.tsx — 지시어 없음, useState도 DB도 쓰지 않음
export function Markdown({ text }) {
  return <div>{/* text를 직접 파싱해 렌더링 */}</div>;
}
// 서버 컴포넌트가 import → 서버에서 실행 (Astro 컴포넌트처럼)
// 클라이언트 컴포넌트가 import → 브라우저에서도 실행 (아일랜드처럼)

원문 필자는 이 성질을 축복이자 저주로 봅니다. "지금 어느 세계에 있는가"를 계속 신경 쓰게 되지만, 정적이던 UI가 동적으로 바뀌어도 문법을 바꿔 옮기거나 복제할 필요 없이 'use client' 위치만 옮기면 된다는 것입니다[1].

자주 하는 실수

Astro의 client:*는 .astro 파일에 직접 import한 프레임워크 컴포넌트에만 쓸 수 있고, 동적 태그에는 지원되지 않습니다[4]. Astro 컴포넌트에 붙이면 오류가 납니다[5].

경계를 넘는 props는 직렬화된다

서버의 값을 브라우저 컴포넌트에 넘기려면 네트워크로 보낼 형태로 바꿔야 합니다. 두 방식 모두 그렇지만 허용 범위가 다릅니다.

Astro: 데이터만 건너간다

하이드레이션되는 컴포넌트의 props는 직렬화됩니다. 지원 타입은 일반 객체, number, string, Array, Map, Set, RegExp, Date, BigInt, URL, Uint8Array 등 형식화 배열과 Infinity입니다[5]. 함수는 서버 렌더링 중에만 쓸 수 있고, 클라이언트에서 실행할 수 있는 형태로 넘길 방법이 없습니다[5].

---
import Counter from '../components/Counter.jsx';
const onIncrement = () => console.log('clicked');
---
<Counter startingCount={1} client:load />
<!-- 숫자: 직렬화되어 브라우저에서도 1로 시작 -->
<Counter onIncrement={onIncrement} client:load />
<!-- 함수: 서버 렌더링에만 쓰이고 브라우저에서는 실행 불가 -->

RSC: 서버 함수와 JSX도 건너간다

RSC도 서버 컴포넌트가 클라이언트 컴포넌트에 넘기는 props는 직렬화할 수 있어야 합니다[3]. 'use server' 문서의 직렬화 목록에서 일반 함수는 빠지고, 반환값 규칙은 클라이언트 컴포넌트 props 규칙과 같다고 적혀 있습니다[6]. 차이는 서버 함수(Server Function)입니다. 서버 함수는 props로 클라이언트 컴포넌트에 넘길 수 있고, 클라이언트에서 부르면 인자를 직렬화한 네트워크 요청이 서버로 갑니다[6].

// actions.ts — 파일의 모든 export가 서버 함수
'use server';
export async function likePost(slug) {
  // 서버에서 실행: 좋아요 수 저장
}

// PostPreview.tsx — 서버 컴포넌트
import { likePost } from './actions';
import { SavedLikeButton } from './SavedLikeButton';

async function PostPreview({ slug }) {
  return <SavedLikeButton slug={slug} onLike={likePost} />;
}
// slug: 문자열로 직렬화
// onLike: 함수 본문이 아니라 서버를 호출하는 참조로 전달

// SavedLikeButton.tsx — 클라이언트 컴포넌트
'use client';

export function SavedLikeButton({ slug, onLike }) {
  return <button onClick={() => onLike(slug)}>Like</button>;
}
// 클릭 → 브라우저가 서버에 likePost(slug) 요청

JSX도 props로 넘길 수 있어서, 클라이언트 컴포넌트가 서버 컴포넌트의 렌더 결과를 children으로 받아 그릴 수 있습니다[3]. Astro에서 Astro 컴포넌트를 슬롯으로 넘기는 패턴[5]과 같은 역할입니다.

자주 하는 실수: 서버 함수 인자를 믿기

서버 함수의 인자는 클라이언트가 마음대로 정할 수 있으므로, 신뢰할 수 없는 입력으로 보고 검증과 권한 확인을 해야 합니다[6]. Astro 펜스 안의 서버 코드[2]와 달리 서버 함수는 브라우저에서 부를 수 있는 진입점입니다.

하나의 트리가 되면 달라지는 것

Astro: 아일랜드는 서로 다른 루트

Astro 아일랜드는 다른 아일랜드와 격리되어 실행됩니다[8]. 아일랜드 안에 다시 아일랜드를 넣어도 React 입장에서는 각각 별도 루트라서, Context를 아일랜드끼리 넘길 수 없습니다[1][7]. Astro 공식 문서는 대신 Nano Stores를 권합니다. 의존성 없이 1KB 미만이고 프레임워크에 묶이지 않는다는 이유입니다[7].

// src/cartStore.js
import { atom } from 'nanostores';
export const isCartOpen = atom(false);

// CartFlyoutToggle.jsx — 아일랜드 A
import { useStore } from '@nanostores/react';
import { isCartOpen } from '../cartStore';

export default function CartButton() {
  const $isCartOpen = useStore(isCartOpen);
  return (
    <button onClick={() => isCartOpen.set(!$isCartOpen)}>Cart</button>
  );
}
// 아일랜드 B(CartFlyout)도 같은 isCartOpen을 읽어 열림 상태를 맞춤

RSC: Context가 서버 영역을 건너간다

RSC에서는 화면 전체가 내부적으로 하나의 React 트리입니다. 클라이언트 Context Provider 아래에 서버 컴포넌트가 있고, 그 아래 어디서든 클라이언트 컴포넌트가 그 Context를 읽을 수 있습니다. 원문 필자는 이를 "프랙털 아일랜드"라고 부릅니다[1].

// CartProvider.tsx
'use client';
import { createContext, useState } from 'react';
export const CartContext = createContext(null);

export function CartProvider({ children }) {
  const [isOpen, setIsOpen] = useState(false);
  return (
    <CartContext.Provider value={{ isOpen, setIsOpen }}>
      {children}
    </CartContext.Provider>
  );
}
// 서버 레이아웃이 <CartProvider>로 감싸면 그 아래
// 어느 클라이언트 컴포넌트든 useContext(CartContext)로 읽음

화면 갱신과 페이지 이동

Astro 컴포넌트의 결과물은 HTML이라서, 링크를 누르면 View Transitions로 다듬더라도 페이지 HTML이 교체됩니다[1]. RSC는 React 트리를 JSON 비슷한 형식으로 보내, 첫 화면은 HTML로 그리고 이동 때는 다시 받아 기존 트리에 합칩니다[1]. 원문 필자는 이를 "MPA처럼 생각하지만 SPA처럼 느껴진다"고 표현합니다. 입력값·스크롤 위치 같은 상태를 유지한 채 서버 부분만 새로 받는다는 뜻입니다[1].

아일랜드는 각자의 루트RSC는 하나의 트리

주의점: RSC는 프레임워크가 아니다

RSC는 프레임워크가 구현하는 더 낮은 수준의 구성 요소이고, 원문 기준 공식 지원 구현은 Next.js App Router와 Parcel RSC입니다[1]. 원문 필자는 RSC의 개발 경험이 아직 거칠다고 보면서도, RSC가 어렵다면 Astro가 같은 개념으로 들어가는 완만한 길이 된다고 권합니다[1].

정리

질문 Astro RSC
서버 전용 컴포넌트 .astro 파일[2] 지시어 없는 컴포넌트(기본값)[3]
브라우저 컴포넌트 프레임워크 컴포넌트 + client:*[4] 'use client' 파일과 그 의존성[3]
경계를 정하는 위치 컴포넌트를 쓰는 자리 모듈(파일) 맨 위
정적/하이드레이션 선택 지시어 유무·종류로 선택[4] 선택지 없음, 지시어를 지우면 서버 전용[1]
경계를 넘는 함수 지원하지 않음[5] 서버 함수만 가능[6]
서버 결과를 클라이언트 안에 슬롯으로 전달[5] children 등 JSX props로 전달[3]
상태 공유 아일랜드마다 루트, Nano Stores 권장[7] 하나의 트리, Context 사용[1]
페이지 이동 HTML 교체[1] 트리를 다시 받아 합침[1]

.astro 파일은 서버 컴포넌트로, client:*가 붙은 컴포넌트는 'use client' 파일로 옮겨 생각하면 됩니다. 대응이 깨지는 곳은 경계를 정의 위치에서 정한다는 점, 서버 함수와 JSX가 경계를 건넌다는 점, 화면 전체가 하나의 트리라는 점입니다.

프론트엔드 팀이 해 볼 것

  1. 지금 Astro 프로젝트에서 client:* 가 붙은 컴포넌트를 모두 찾아, RSC로 옮긴다면 'use client'가 필요한 파일 목록으로 적어 본다
  2. 아일랜드 사이에 Nano Stores로 공유하는 상태를 하나 골라, RSC라면 어느 클라이언트 Provider 아래에 둘지 그려 본다
  3. 서버 함수를 쓰는 코드가 있다면 모든 인자에 검증과 권한 확인이 들어 있는지 점검한다
