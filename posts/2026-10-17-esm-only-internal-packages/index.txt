17:T6a79,<h2 id="파일이-esm인지-cjs인지는-누가-정하나">파일이 ESM인지 CJS인지는 누가 정하나</h2>
<p>Node.js에는 원래 쓰던 CommonJS(CJS)와 브라우저도 쓰는 표준 ECMAScript 모듈(ESM), 두 모듈 시스템이 있습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 같은 <code>.js</code> 파일도 어느 쪽으로 해석되느냐에 따라 문법과 경로 규칙이 달라집니다.</p>
<h3 id="type-필드와-확장자">type 필드와 확장자</h3>
<p>판단 기준은 확장자와 가장 가까운 상위 <code>package.json</code>의 <code>"type"</code> 필드입니다. <code>.mjs</code>는 항상 ESM, <code>.cjs</code>는 항상 CJS이고, <code>.js</code>는 <code>"type": "module"</code>이면 ESM, <code>"type": "commonjs"</code>이거나 필드가 없으면 CJS로 읽힙니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<pre data-lang="json"><code class="hljs language-json"><span class="hljs-punctuation">{</span>
  <span class="hljs-attr">"name"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"@acme/ui"</span><span class="hljs-punctuation">,</span>
  <span class="hljs-attr">"type"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"module"</span>
<span class="hljs-punctuation">}</span>
</code></pre>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// 위 package.json 아래에 있는 파일들</span>
<span class="hljs-comment">// dist/index.js    → ES 모듈</span>
<span class="hljs-comment">// dist/legacy.cjs  → 확장자가 우선이라 항상 CommonJS</span>
</code></pre>
<p>TypeScript도 같은 규칙을 따릅니다. <code>module</code>을 <code>node16</code>·<code>nodenext</code> 계열로 두면 <code>.ts</code>·<code>.d.ts</code> 파일도 가장 가까운 <code>package.json</code>의 <code>type</code>을 보고 ESM인지 CJS인지 정합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup><sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<h4>자주 하는 실수: type 필드 생략</h4>
<p><code>type</code>이 없는 패키지의 <code>.js</code> 파일은 애매한(ambiguous) 입력으로 취급됩니다. Node.js는 먼저 CJS로 실행해 보고, ESM 문법 때문에 실패하면 ESM으로 다시 평가합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 이 방식에는 성능 비용이 있습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> Node.js 문서는 모든 소스가 CJS인 패키지라도 <code>type</code> 필드를 항상 쓰라고 권합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup><sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h3 id="esm에서-달라지는-규칙">ESM에서 달라지는 규칙</h3>
<p>ESM으로 바꾸면 경로를 쓰는 방식이 엄격해집니다. <code>import</code>는 확장자를 찾아 주지 않고, 폴더를 모듈로 읽지도 않습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 확장자를 빼면 Node.js에서 <code>ERR_MODULE_NOT_FOUND</code> 오류가 납니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> <code>require</code>나 <code>module</code> 같은 전역 값도 바로 쓸 수 없습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// type: module 패키지 안의 src/index.js</span>
<span class="hljs-keyword">import</span> { helper } <span class="hljs-keyword">from</span> <span class="hljs-string">'./foo'</span>;            <span class="hljs-comment">// Node.js: ERR_MODULE_NOT_FOUND</span>
<span class="hljs-keyword">import</span> { helper } <span class="hljs-keyword">from</span> <span class="hljs-string">'./foo.js'</span>;         <span class="hljs-comment">// OK</span>
<span class="hljs-keyword">import</span> { setup } <span class="hljs-keyword">from</span> <span class="hljs-string">'./startup/index.js'</span>; <span class="hljs-comment">// 폴더 index도 끝까지 적어야 함</span>
</code></pre>
<h2 id="exports와-이중-패키지의-함정">exports와 이중 패키지의 함정</h2>
<h3 id="exports-필드의-역할">exports 필드의 역할</h3>
<p><code>"exports"</code>는 패키지의 진입점을 정하는 필드로, 기존 <code>"main"</code>보다 강력한 대안으로 v12.7.0에 들어왔습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> <code>exports</code>를 쓰면 여기 적은 경로만 외부에서 불러올 수 있고, 나머지 요청은 모듈을 찾지 못한다는 오류가 납니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> webpack도 <code>main</code>·<code>module</code>·<code>browser</code>보다 <code>exports</code>를 우선합니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<p>조건부 내보내기(conditional exports)는 불러오는 방식에 따라 다른 파일을 연결합니다. ESM 문법이나 <code>import()</code>로 요청하면 <code>import</code> 조건이, <code>require()</code>로 요청하면 <code>require</code> 조건이 켜집니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> 조건은 적힌 순서대로 검사합니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<pre data-lang="json"><code class="hljs language-json"><span class="hljs-punctuation">{</span>
  <span class="hljs-attr">"exports"</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span>
    <span class="hljs-attr">"."</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span>
      <span class="hljs-attr">"import"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"./dist/index.mjs"</span><span class="hljs-punctuation">,</span>
      <span class="hljs-attr">"require"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"./dist/index.cjs"</span>
    <span class="hljs-punctuation">}</span>
  <span class="hljs-punctuation">}</span>
<span class="hljs-punctuation">}</span>
</code></pre>
<p>토스뱅크도 그동안 ESM과 CJS로 각각 빌드하고 이렇게 <code>exports</code>로 환경별 코드와 타입을 제공해 왔습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h3 id="같은-패키지인데-객체가-둘">같은 패키지인데 객체가 둘</h3>
<p>위 설정에서 <code>import</code>와 <code>require()</code>는 서로 다른 파일을 실행합니다. 두 파일이 각자 만든 객체는 내용이 같아도 다른 객체입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 서비스는 ESM 쪽을, 서비스가 쓰는 다른 패키지는 CJS 쪽을 읽으면 이런 일이 생깁니다.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// 서비스 코드(ESM) — dist/index.mjs 가 실행됨</span>
<span class="hljs-keyword">import</span> { <span class="hljs-title class_">ThemeContext</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">'@acme/theme'</span>;

<span class="hljs-comment">// 서비스가 쓰는 다른 패키지(CJS) — dist/index.cjs 가 실행됨</span>
<span class="hljs-keyword">const</span> { <span class="hljs-title class_">ThemeContext</span> } = <span class="hljs-built_in">require</span>(<span class="hljs-string">'@acme/theme'</span>);

<span class="hljs-comment">// 두 ThemeContext 는 서로 다른 객체</span>
<span class="hljs-comment">// → 서비스의 Provider 가 넣은 값을 다른 패키지의 Hook 이 읽지 못함</span>
</code></pre>
<p>패키지를 한 버전만 설치해도 생기는 문제이고, 이를 이중 패키지 위험(Dual package hazard)이라고 부릅니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h3 id="타입-경로도-둘">타입 경로도 둘</h3>
<p>TypeScript도 <code>exports</code>의 <code>import</code>·<code>require</code> 조건을 따라 선언 파일을 찾습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> 그래서 이중 패키지라면 진입점마다 선언 파일이 따로 있어야 하고, 선언 파일 하나로 두 진입점을 함께 타이핑하면 TypeScript가 한쪽만 있다고 판단해 오류가 납니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<p>토스뱅크 원문의 예처럼 CJS 경로에서 외부 타입을 못 찾으면 그 타입이 <code>any</code>가 되고, 이를 확장한 props도 <code>any</code>가 돼 잘못된 값을 넘겨도 에러가 나지 않습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-keyword">import</span> <span class="hljs-keyword">type</span> { <span class="hljs-title class_">ExternalProps</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">'external-library'</span>;

<span class="hljs-keyword">type</span> <span class="hljs-title class_">ButtonProps</span> = {
  <span class="hljs-attr">loading</span>?: <span class="hljs-built_in">boolean</span>;
} &#x26; <span class="hljs-title class_">ExternalProps</span>; <span class="hljs-comment">// ExternalProps 를 못 찾으면 ButtonProps 전체가 any</span>
</code></pre>
<h2 id="requireesm이-바꾼-전제">require(esm)이 바꾼 전제</h2>
<p>이중 패키지를 냈던 가장 큰 이유는 CJS 사용처였습니다. 예전 Node.js에서는 CJS의 <code>require()</code>로 ESM을 불러올 수 없었기 때문입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> TypeScript 4.7 문서도 당시 CJS에서 ESM을 불러오는 방법은 동적 <code>import()</code>뿐이라고 적었습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<h3 id="cjs에서-esm-불러오기">CJS에서 ESM 불러오기</h3>
<p>이 기능은 v23.0.0·v22.12.0·v20.19.0부터 <code>--experimental-require-module</code> 플래그 없이 쓸 수 있고, v25.4.0에서 실험 기능 딱지를 뗐습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> <code>require()</code>는 ESM의 모듈 네임스페이스 객체를 동기로 돌려줍니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// point.mjs</span>
<span class="hljs-keyword">export</span> <span class="hljs-keyword">default</span> <span class="hljs-keyword">class</span> <span class="hljs-title class_">Point</span> {

<h4>자주 하는 실수: 기본 내보내기를 바로 쓰기</h4>
<p>반환값은 네임스페이스 객체라서 기본 내보내기는 <code>.default</code>에 들어 있습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> <code>__esModule</code>은 변환 도구용 실험 속성이라 직접 쓴 CJS 코드는 기대지 않아야 합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<p>또 하나의 조건은 불러오는 ESM과 그 의존 모듈이 모두 동기여야 한다는 점입니다. 최상위 <code>await</code>가 있으면 <code>require()</code>로 불러올 수 없습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup><sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> ESM 전용 패키지라면 최상위 <code>await</code>를 금지해 두세요.</p>
<h3 id="사내-패키지라서-가능한-선택">사내 패키지라서 가능한 선택</h3>
<p>공개 라이브러리는 구버전 Node.js를 포함한 다양한 환경에서 쓰이므로 여전히 두 형식을 함께 낼 이유가 있습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 토스뱅크 기술그룹은 사내에서만 쓰는 패키지라 사용처를 파악하고 지원 환경도 함께 맞출 수 있었고, 이런 예측 가능한 환경에서는 한 형식이면 충분하다고 판단했습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> ESM을 고른 이유로는 JavaScript의 표준 모듈 시스템이라는 점과 트리 셰이킹에 유리하다는 점을 들었습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<aside class="poster" aria-label="사용처를 아는 사내 패키지라면 ESM 하나로 충분하다"><span class="poster-line" aria-hidden="true">사용처를 아는 사내 패키지라면</span><span class="poster-line poster-accent" aria-hidden="true">ESM 하나로 충분하다</span></aside>
<p>ESM 전용 패키지의 <code>package.json</code>은 진입점이 하나로 줄어듭니다. <code>types</code> 조건은 항상 맨 앞에 둡니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<pre data-lang="json"><code class="hljs language-json"><span class="hljs-punctuation">{</span>

<p>사용처의 TypeScript 설정도 확인해야 합니다. TypeScript 문서의 비교표를 보면 <code>node16</code>·<code>node18</code>·<code>nodenext</code> 가운데 <code>require(esm)</code>을 반영하는 <code>module</code> 값은 <code>nodenext</code>뿐입니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<h2 id="토스뱅크의-세-가지-기준을-설정으로-옮기기">토스뱅크의 세 가지 기준을 설정으로 옮기기</h2>
<p>ESM 전용 전환 다음 글에서 토스뱅크는 패키지가 갖출 기준 세 가지를 정했습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 원문은 빌드 도구 이름을 밝히지 않았으므로, 아래 설정은 기준을 TypeScript 옵션으로 옮긴 예입니다.</p>
<h3 id="기준-1-호스트-실행-환경에서-동작한다">기준 1: 호스트 실행 환경에서 동작한다</h3>
<p>토스뱅크의 서비스는 각자 지원 범위에 맞춰 패키지를 트랜스파일합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 그래도 문법은 호스트 트랜스파일러가 그 변환을 지원해야 하고, API는 실행 환경이 제공하거나 폴리필로 채워야 합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 예를 들어 <code>Proxy</code>는 폴리필만으로 전체 동작을 구현할 수 없습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>도구 쪽 빈틈도 있습니다. rolldown의 한 PR은 Chrome 133 target에서 변환기가 실행되지 않아 <code>using</code> 선언이 그대로 출력되던 문제를 고쳤습니다.<sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup> target을 낮게 줘도 도구가 지원하지 않는 변환은 일어나지 않습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>토스뱅크는 호스트의 API 지원 범위를 타입 검사에 반영했습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> TypeScript에서는 <code>lib</code> 옵션이 이 역할을 맡습니다. 문서는 런타임이 상위 ECMAScript 버전의 API를 일부만 제공할 때 <code>lib</code>을 바꾸라고 안내합니다.<sup class="cite"><a href="#source-10" aria-label="출처 10">[10]</a></sup></p>
<pre data-lang="json"><code class="hljs language-json"><span class="hljs-punctuation">{</span>
  <span class="hljs-attr">"compilerOptions"</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span>

  <span class="hljs-punctuation">}</span>
<span class="hljs-punctuation">}</span>
</code></pre>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-keyword">const</span> last = [<span class="hljs-number">1</span>, <span class="hljs-number">2</span>, <span class="hljs-number">3</span>].<span class="hljs-title function_">at</span>(-<span class="hljs-number">1</span>);

<p><code>at</code>은 <code>lib</code>의 ES2022 항목에 들어 있습니다.<sup class="cite"><a href="#source-10" aria-label="출처 10">[10]</a></sup> 다만 타입 검사는 API가 실제로 있는지까지 보장하지 않으므로, 실제 지원 여부와 문법 변환 가능 여부는 따로 확인해야 합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<h3 id="기준-2-원본의-문법과-모듈-구조를-유지한다">기준 2: 원본의 문법과 모듈 구조를 유지한다</h3>
<p>패키지에서 문법을 미리 낮추면 이를 지원하는 호스트도 변환된 코드를 받습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// 원본</span>
<span class="hljs-keyword">const</span> name = user?.<span class="hljs-property">name</span>;

<span class="hljs-comment">// Optional Chaining 미지원 환경에 맞춰 미리 변환해 배포하면</span>
<span class="hljs-keyword">const</span> name = user === <span class="hljs-literal">null</span> || user === <span class="hljs-keyword">void</span> <span class="hljs-number">0</span> ? <span class="hljs-keyword">void</span> <span class="hljs-number">0</span> : user.<span class="hljs-property">name</span>;
</code></pre>
<p>그래서 토스뱅크는 패키지 빌드에서 TypeScript를 JavaScript로 바꾸는 일만 하고, 환경별 문법 변환과 최종 번들링은 호스트에 맡겼습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>모듈 구조를 유지하는 이유는 파일 단위 지시문입니다. <code>'use client'</code>는 파일 맨 위에 두며 모듈 전체에 적용되고, 서버와 클라이언트의 경계를 정합니다.<sup class="cite"><a href="#source-11" aria-label="출처 11">[11]</a></sup></p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-comment">// src/Counter.tsx</span>

<span class="hljs-comment">// src/formatPrice.ts — 지시문 없음</span>
<span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">formatPrice</span>(<span class="hljs-params"><span class="hljs-attr">value</span>: <span class="hljs-built_in">number</span></span>) { <span class="hljs-comment">/* ... */</span> }

<p>두 파일이 분리돼 있으면 Server Component에서도 <code>formatPrice</code>를 불러 호출할 수 있습니다. 하나로 번들링하고 전체에 <code>'use client'</code>를 적용하면 <code>formatPrice</code>도 클라이언트 코드가 됩니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<h4>자주 하는 실수: bundler 해석으로만 검사하기</h4>
<p><code>moduleResolution: "bundler"</code>는 상대 경로에 확장자를 요구하지 않습니다.<sup class="cite"><a href="#source-12" aria-label="출처 12">[12]</a></sup> 이 설정으로만 검사한 <code>export * from "./utils"</code>는 Node.js에서 <code>ERR_MODULE_NOT_FOUND</code>를 냅니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> Node.js에서 동작하는 모듈 코드는 대부분 번들러에서도 동작하므로<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup>, 패키지가 테스트나 서버에서 Node.js로 직접 실행될 수 있다면 경로에 확장자를 적어 두는 편이 안전합니다.</p>
<h3 id="기준-3-사용처에서-원본을-보며-디버깅한다">기준 3: 사용처에서 원본을 보며 디버깅한다</h3>
