17:T5602,<h2 id="원문-필자가-찾은-것-세-층을-보는-봇-검사">원문 필자가 찾은 것: 세 층을 보는 봇 검사</h2>
<p>봇 검사(bot detection)는 지금 요청을 보낸 쪽이 사람이 쓰는 실제 브라우저인지 자동화 도구인지 가려내는 일입니다. 오래된 방식은 화면에 퍼즐을 띄우는 CAPTCHA였고, Cloudflare Turnstile은 퍼즐 없이 백그라운드에서 이 판단을 하려는 도구입니다.</p>
<p>Cloudflare 공식 문서는 Turnstile이 작은 비대화형 JavaScript 챌린지를 여러 번 실행해 방문자와 브라우저 환경에 대한 신호를 모은다고 설명합니다. 여기에는 작업 증명(proof-of-work), 공간 증명(proof-of-space), 웹 API 탐지, 브라우저 특이점과 사람의 행동을 감지하는 챌린지가 포함됩니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<h3 id="복호화한-프로그램의-구성">복호화한 프로그램의 구성</h3>
<p>원문 필자는 ChatGPT 네트워크 트래픽에서 Turnstile 프로그램 377개를 복호화했고, 377개 모두에서 같은 55개 속성을 수집했다고 보고합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 필자는 이 속성을 세 층으로 나눕니다.</p>

<h3 id="제목과-본문의-간격">제목과 본문의 간격</h3>
<p>원문 제목은 "Cloudflare가 React 상태를 읽기 전까지 입력할 수 없다"고 말하지만, 본문은 입력을 막는 코드 자체를 보여 주지는 않습니다. 본문이 다루는 것은 프로그램의 복호화 과정과 수집 항목입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 그래서 이 글에서는 "입력을 막는다"를 원문 필자의 관찰로만 다루고, 내 앱에서 같은 상황을 만들 때 알아야 할 원리를 따로 정리합니다.</p>
<aside class="poster" aria-label="지문은 흉내 낼 수 있어도 앱 부팅은 흉내 내기 어렵다"><span class="poster-line" aria-hidden="true">지문은 흉내 낼 수 있어도</span><span class="poster-line poster-accent" aria-hidden="true">앱 부팅은 흉내 내기 어렵다</span></aside>
<h2 id="앱-층-검사가-가능한-이유-하이드레이션이-남기는-흔적">앱 층 검사가 가능한 이유: 하이드레이션이 남기는 흔적</h2>
<p>원문 필자가 말하는 "애플리케이션 층"을 이해하려면, 서버 렌더링한 React 앱이 브라우저에서 어떻게 깨어나는지 알아야 합니다.</p>
<h3 id="하이드레이션이란">하이드레이션이란</h3>
<p>하이드레이션(hydration)은 서버가 만든 HTML에 React가 컴포넌트 로직을 "붙여서", 정적인 HTML 스냅샷을 브라우저에서 동작하는 앱으로 바꾸는 과정입니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> React 문서는 사용자가 JavaScript가 로드되기 전까지 한동안 서버가 만든 HTML을 보고 있다고 설명합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-keyword">import</span> { hydrateRoot } <span class="hljs-keyword">from</span> <span class="hljs-string">"react-dom/client"</span>;
<span class="hljs-keyword">import</span> <span class="hljs-title class_">App</span> <span class="hljs-keyword">from</span> <span class="hljs-string">"./App.js"</span>;

<span class="hljs-title function_">hydrateRoot</span>(<span class="hljs-variable language_">document</span>.<span class="hljs-title function_">getElementById</span>(<span class="hljs-string">"root"</span>), <span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">App</span> /></span></span>);
<span class="hljs-comment">// 이 호출이 끝나야 이벤트 핸들러와 상태가 HTML에 연결됨</span>
</code></pre>
<p>즉 화면에 입력창이 보인다고 해서 앱이 준비된 것은 아닙니다. HTML만 받은 상태와 JavaScript까지 실행한 상태는 겉모습이 같아도 내부가 다릅니다.</p>
<h3 id="reactroutercontext는-어디서-오나"><code>__reactRouterContext</code>는 어디서 오나</h3>
<p>원문 필자는 <code>__reactRouterContext</code>를 React Router가 DOM에 붙이는 내부 자료 구조라고 설명합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> React Router 소스를 보면 이것은 <code>declare global</code> 안에 선언된 window 전역 변수이고, 그 타입에는 <code>state: HydrationState</code>와 스트림 관련 필드가 들어 있습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// react-router/lib/dom/global.ts (발췌)</span>
<span class="hljs-keyword">export</span> <span class="hljs-keyword">type</span> <span class="hljs-title class_">WindowReactRouterContext</span> = <span class="hljs-title class_">ServerHandoff</span> &#x26; {
  <span class="hljs-attr">state</span>: <span class="hljs-title class_">HydrationState</span>; <span class="hljs-comment">// Deserialized via the stream</span>
  <span class="hljs-attr">stream</span>: <span class="hljs-title class_">ReadableStream</span>&#x3C;<span class="hljs-title class_">Uint8Array</span>> | <span class="hljs-literal">undefined</span>;
  <span class="hljs-attr">streamController</span>: <span class="hljs-title class_">ReadableStreamDefaultController</span>&#x3C;<span class="hljs-title class_">Uint8Array</span>>;
};
</code></pre>
<p><code>state</code>는 주석대로 스트림에서 역직렬화된 값입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 클라이언트 진입점의 <code>createHydratedRouter</code>는 초기 상태 스냅샷이 <code>window.__reactRouterContext.state</code>로 디코딩될 때까지 기다린 뒤, 그 상태(<code>loaderData</code> 포함)로 하이드레이션 데이터를 만들어 라우터에 넘깁니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>여기서 원문 필자의 주장이 왜 성립하는지 보입니다. HTML만 받아 두고 JavaScript 번들을 실행하지 않는 도구에는 디코딩된 <code>state.loaderData</code>가 생기지 않습니다. 필자도 같은 이유로, 헤드리스 브라우저가 HTML만 읽거나 봇 프레임워크가 브라우저 API만 흉내 내면 이 값이 없다고 분석합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h3 id="자주-하는-실수-로더-데이터를-비밀-저장소처럼-쓰기">자주 하는 실수: 로더 데이터를 비밀 저장소처럼 쓰기</h3>
<p><code>loaderData</code>가 window 전역 아래 들어간다는 것은, 같은 페이지에서 실행되는 모든 스크립트가 그 값을 읽을 수 있다는 뜻입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup><sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 분석 스크립트, 광고 태그, 봇 검사 SDK도 예외가 아닙니다.</p>
<p>내 앱에서 직접 확인해 보는 것이 가장 빠릅니다. React Router 프레임워크 모드로 서버 렌더링한 페이지를 열고 개발자 도구 콘솔에서 아래를 실행합니다.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// 내 앱 페이지의 개발자 도구 콘솔에서</span>
<span class="hljs-keyword">typeof</span> <span class="hljs-variable language_">window</span>.<span class="hljs-property">__reactRouterContext</span>; <span class="hljs-comment">// "object"</span>
<span class="hljs-title class_">Object</span>.<span class="hljs-title function_">keys</span>(<span class="hljs-variable language_">window</span>.<span class="hljs-property">__reactRouterContext</span>.<span class="hljs-property">state</span>.<span class="hljs-property">loaderData</span>);
<span class="hljs-comment">// 라우트 id 목록, 예: ["root", "routes/home"]</span>
</code></pre>
<p>로더가 돌려준 값은 화면에 쓰지 않아도 페이지 안에 남습니다. 세션 토큰, 내부 ID, 다른 사용자 정보처럼 화면에 필요 없는 값은 로더 응답에서 빼는 것이 원칙입니다.</p>
<h2 id="하이드레이션-전-입력-다루기">하이드레이션 전 입력 다루기</h2>
<p>원문 제목이 말하는 "준비될 때까지 입력할 수 없는" 상태를 내 앱에서 의도적으로 만든다면, 하이드레이션 완료를 기준으로 입력을 열면 됩니다. ChatGPT가 이 방식을 쓴다는 근거는 자료에 없으므로, 아래는 일반적인 React 패턴입니다.</p>
<h3 id="useeffect로-하이드레이션-완료-감지"><code>useEffect</code>로 하이드레이션 완료 감지</h3>
<p>React 문서는 Effect가 클라이언트에서만 실행되고 서버 렌더링 중에는 실행되지 않는다고 설명합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 이 성질을 쓰면 "클라이언트에서 커밋까지 끝났다"는 신호를 얻을 수 있습니다.</p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-keyword">import</span> { useEffect, useState } <span class="hljs-keyword">from</span> <span class="hljs-string">"react"</span>;

<span class="hljs-keyword">function</span> <span class="hljs-title function_">useIsHydrated</span>(<span class="hljs-params"></span>) {
  <span class="hljs-keyword">const</span> [isHydrated, setIsHydrated] = <span class="hljs-title function_">useState</span>(<span class="hljs-literal">false</span>);
  <span class="hljs-title function_">useEffect</span>(<span class="hljs-function">() =></span> <span class="hljs-title function_">setIsHydrated</span>(<span class="hljs-literal">true</span>), []);
  <span class="hljs-keyword">return</span> isHydrated;
}

<span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">PromptInput</span>(<span class="hljs-params"></span>) {
  <span class="hljs-keyword">const</span> isHydrated = <span class="hljs-title function_">useIsHydrated</span>();
  <span class="hljs-keyword">return</span> <span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">textarea</span> <span class="hljs-attr">disabled</span>=<span class="hljs-string">{!isHydrated}</span> <span class="hljs-attr">aria-busy</span>=<span class="hljs-string">{!isHydrated}</span> /></span></span>;
}
<span class="hljs-comment">// 서버 HTML: &#x3C;textarea disabled></span>
<span class="hljs-comment">// 하이드레이션 직후 effect 실행 → disabled 해제</span>
</code></pre>
<p>서버와 클라이언트의 첫 렌더는 둘 다 <code>isHydrated === false</code>라서 결과가 같고, 그 뒤 Effect가 상태를 바꿉니다. 하이드레이션 규칙을 지키면서 두 번째 렌더에서만 입력을 엽니다.</p>
<h3 id="자주-하는-실수-렌더-중-typeof-window-검사">자주 하는 실수: 렌더 중 <code>typeof window</code> 검사</h3>
<p>같은 일을 더 짧게 하려고 렌더 로직에서 환경을 직접 검사하면 문제가 생깁니다.</p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-comment">// 잘못된 예: 서버는 disabled, 클라이언트 첫 렌더는 enabled</span>
&#x3C;textarea disabled={<span class="hljs-keyword">typeof</span> <span class="hljs-variable language_">window</span> === <span class="hljs-string">"undefined"</span>} />
</code></pre>
<p>React 문서는 렌더 로직 안의 <code>typeof window !== 'undefined'</code> 같은 검사와 <code>window.matchMedia</code> 같은 브라우저 전용 API를 하이드레이션 오류의 흔한 원인으로 꼽습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 불일치가 나면 좋으면 느려지는 정도지만, 나쁘면 이벤트 핸들러가 엉뚱한 요소에 붙을 수 있다고 경고합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<h3 id="입력을-막을-때의-비용">입력을 막을 때의 비용</h3>
<p>입력을 막는 순간, JavaScript가 늦게 오거나 실패한 사용자는 아무것도 할 수 없습니다. 막을 범위는 "제출"처럼 정말 준비가 필요한 동작으로 좁히고, 입력 자체는 열어 두는 편이 안전한 경우가 많습니다. 막는다면 <code>aria-busy</code>나 안내 문구로 왜 비활성인지 보여 주세요.</p>
<h2 id="내-앱에-turnstile을-붙일-때">내 앱에 Turnstile을 붙일 때</h2>
<p>ChatGPT는 Cloudflare 엣지 헤더까지 확인하는 특수한 통합으로 보이지만<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>, 공식 문서는 Turnstile을 Cloudflare CDN으로 트래픽을 보내지 않는 사이트에도 넣을 수 있다고 설명합니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<h3 id="spa는-명시적-렌더링">SPA는 명시적 렌더링</h3>
<p>Turnstile 위젯은 <code>cf-turnstile</code> 클래스를 자동으로 찾는 암묵적 렌더링과, <code>turnstile.render()</code>를 직접 호출하는 명시적 렌더링 두 가지로 붙입니다. 공식 문서는 SPA처럼 폼이 첫 로드 뒤에 만들어지는 경우 명시적 렌더링을 권합니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> 스크립트 URL에 <code>?render=explicit</code>를 붙여 불러온 뒤 아래처럼 씁니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-keyword">import</span> { useEffect } <span class="hljs-keyword">from</span> <span class="hljs-string">"react"</span>;

<span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">TurnstileBox</span>(<span class="hljs-params">{ onToken }: { onToken: (t: <span class="hljs-built_in">string</span>) => <span class="hljs-built_in">void</span> }</span>) {
  <span class="hljs-title function_">useEffect</span>(<span class="hljs-function">() =></span> {
    <span class="hljs-keyword">const</span> widgetId = turnstile.<span class="hljs-title function_">render</span>(<span class="hljs-string">"#turnstile-container"</span>, {
      <span class="hljs-attr">sitekey</span>: <span class="hljs-string">"&#x3C;YOUR-SITE-KEY>"</span>,
      <span class="hljs-attr">callback</span>: onToken,
    });
    <span class="hljs-keyword">return</span> <span class="hljs-function">() =></span> turnstile.<span class="hljs-title function_">remove</span>(widgetId);
  }, [onToken]);
  <span class="hljs-keyword">return</span> <span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">div</span> <span class="hljs-attr">id</span>=<span class="hljs-string">"turnstile-container"</span> /></span></span>;
}
</code></pre>
<p>정리 함수에서 <code>turnstile.remove</code>를 부르는 이유가 있습니다. React는 개발 모드 Strict Mode에서 실제 setup 전에 setup과 cleanup을 한 번 더 실행합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 정리하지 않으면 개발 중에 위젯이 두 개 생깁니다.</p>
<h3 id="토큰은-서버에서-검증">토큰은 서버에서 검증</h3>
<p>위젯이 준 토큰만으로는 아무것도 보장되지 않습니다. 서버가 <code>POST https://challenges.cloudflare.com/turnstile/v0/siteverify</code>에 비밀 키와 토큰을 보내 결과를 받아야 합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-keyword">const</span> result = <span class="hljs-keyword">await</span> <span class="hljs-title function_">fetch</span>(
  <span class="hljs-string">"https://challenges.cloudflare.com/turnstile/v0/siteverify"</span>,
  {
    <span class="hljs-attr">method</span>: <span class="hljs-string">"POST"</span>,
    <span class="hljs-attr">headers</span>: { <span class="hljs-string">"Content-Type"</span>: <span class="hljs-string">"application/json"</span> },

<p>토큰은 최대 2048자, 생성 후 300초 동안 유효하며 한 번만 검증할 수 있습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> 사용자가 5분 넘게 폼을 붙잡고 있다가 제출하면 검증은 <code>timeout-or-duplicate</code> 오류로 실패하고, 이때는 <code>turnstile.reset</code>으로 위젯을 새로 고쳐 토큰을 다시 받아야 합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<h3 id="자주-하는-실수">자주 하는 실수</h3>
<ul>
<li>토큰이 왔다는 사실만 보고 클라이언트에서 통과 처리하기: 검증은 반드시 서버 Siteverify 호출로 합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></li>
<li>실패한 요청을 같은 토큰으로 재시도하기: 토큰은 한 번만 쓸 수 있습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> 서버 쪽 재시도가 필요하면 문서가 안내하는 <code>idempotency_key</code>를 씁니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></li>
<li>클라이언트 난독화를 비밀로 믿기: 원문 필자는 내부 프로그램의 XOR 키가 같은 응답 안에 들어 있어 "가벼운 열람은 막지만 분석은 막지 못한다"고 평가합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 브라우저로 보낸 코드와 데이터는 결국 읽힌다고 가정하세요.</li>
</ul>
