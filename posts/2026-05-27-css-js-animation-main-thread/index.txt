17:T57c0,<h2 id="애니메이션은-어느-스레드에서-도는가">애니메이션은 어느 스레드에서 도는가</h2>
<p>애니메이션이 부드러우려면 브라우저가 화면을 일정한 간격으로 다시 그려야 합니다. 웹에서는 보통 초당 60프레임(60 FPS)을 목표로 하고, 그러려면 한 프레임의 작업이 16.7ms 안에 끝나야 합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 이 시간 안에 누가 그 작업을 맡느냐가 CSS와 JS의 차이를 만듭니다.</p>
<h3 id="메인-스레드와-컴포지터-스레드">메인 스레드와 컴포지터 스레드</h3>
<p>메인 스레드(main thread)는 스타일 계산, 레이아웃, 페인트, 그리고 JavaScript 실행을 모두 맡는 스레드입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> React가 상태에 맞춰 DOM을 갱신하는 일도, <code>fetch</code> 응답을 파싱하는 일도 여기서 일어납니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<p>컴포지터 스레드(compositor thread)는 이미 그려 둔 레이어를 합쳐 화면에 내보내는 일을 따로 맡습니다. CSS 애니메이션과 Web Animations는 보통 이 컴포지터 스레드에서 처리되므로, 메인 스레드가 무거운 작업을 하는 동안에도 끊기지 않습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h3 id="같은-움직임-두-가지-구현">같은 움직임, 두 가지 구현</h3>
<p>좌우로 튀는 공을 CSS 키프레임으로 쓰면 이렇습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<pre data-lang="css"><code class="hljs language-css"><span class="hljs-keyword">@keyframes</span> bounce {
  <span class="hljs-selector-tag">to</span> {
    <span class="hljs-attribute">transform</span>: <span class="hljs-built_in">translateX</span>(<span class="hljs-built_in">calc</span>(<span class="hljs-built_in">var</span>(--bounce-magnitude) * -<span class="hljs-number">1</span>));
  }

<span class="hljs-selector-class">.ball</span> {
  <span class="hljs-attr">--bounce-magnitude</span>: <span class="hljs-number">200px</span>;

<p>같은 효과를 JS로 만들 때는 <code>requestAnimationFrame()</code>을 씁니다. 이 메서드는 다음 화면 갱신 직전에 콜백을 한 번 호출하고, 다음 프레임에도 움직이려면 콜백 안에서 다시 호출해야 합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-keyword">const</span> element = <span class="hljs-variable language_">document</span>.<span class="hljs-title function_">getElementById</span>(<span class="hljs-string">"some-element-you-want-to-animate"</span>);

<p>이 예제는 1ms에 0.1px씩 움직여 2초 뒤 200px 위치에서 멈춥니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<h3 id="느린-건-계산이-아니라-줄-서기">느린 건 계산이 아니라 줄 서기</h3>
<p>JS 버전이 느리다고 하면 흔히 매 프레임 위치를 계산하는 비용이나 JS와 DOM 사이를 오가는 비용을 떠올립니다. 원문 필자는 이 비용이 저사양 기기에서도 1ms에 한참 못 미쳐 프레임 속도에 영향을 주지 않는다고 봅니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 차이는 JS 루프가 앱의 다른 모든 작업과 같은 메인 스레드에서 돈다는 점입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<p>직접 확인하려면 메인 스레드를 일부러 막아 보면 됩니다.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-keyword">function</span> <span class="hljs-title function_">blockMainThread</span>(<span class="hljs-params">durationMs</span>) {
  <span class="hljs-keyword">const</span> end = performance.<span class="hljs-title function_">now</span>() + durationMs;
  <span class="hljs-keyword">while</span> (performance.<span class="hljs-title function_">now</span>() &#x3C; end) {} <span class="hljs-comment">// 이 동안 메인 스레드는 다른 일을 못 함</span>

<span class="hljs-comment">// requestAnimationFrame 공: 3초마다 0.5초씩 멈춤</span>
<span class="hljs-comment">// CSS transform 공: 대개 멈추지 않고 계속 움직임</span>
</code></pre>
<p>데이터를 새로 불러온 직후 로딩 스피너가 잠깐 얼어붙는 현상도 같은 이유입니다. JS로 돌린 스피너가 응답 처리와 메인 스레드를 두고 경쟁하기 때문입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h4>자주 하는 실수: 경과 시간 대신 프레임 수로 계산하기</h4>
<p><code>requestAnimationFrame()</code> 콜백이 불리는 빈도는 대체로 화면 주사율을 따르는데, 60Hz가 가장 흔하지만 120Hz, 144Hz 화면도 많습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 콜백마다 <code>x += 2</code>처럼 고정값을 더하면 고주사율 화면에서 애니메이션이 더 빨라집니다. 콜백의 첫 번째 인자인 <code>timestamp</code>로 경과 시간을 구해 위치를 계산해야 합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<h2 id="무엇을-움직이느냐가-먼저다">무엇을 움직이느냐가 먼저다</h2>
<p>CSS로 썼다고 해서 늘 컴포지터 스레드에서 도는 것은 아닙니다. 어떤 속성을 움직이느냐에 따라 메인 스레드가 다시 끼어듭니다.</p>
<h3 id="렌더링-파이프라인">렌더링 파이프라인</h3>
<p>브라우저는 화면을 그릴 때 스타일 → 레이아웃 → 페인트 → 합성(composite)을 순서대로 거칩니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 애니메이션 중에는 바뀐 단계부터 다시 시작하므로, 레이아웃을 바꾸는 속성은 페인트와 합성까지 모두 다시 하게 만듭니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>

<p>web.dev는 브라우저가 싸게 움직일 수 있는 속성으로 <code>transform</code>과 <code>opacity</code> 두 가지를 꼽습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 그 밖의 속성은 렌더링 파이프라인에 주는 영향을 먼저 확인하고, 레이아웃이나 페인트를 일으키는 속성은 꼭 필요할 때만 쓰라고 권합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>

}
</code></pre>
<p>web.dev의 예제에서 <code>top</code>/<code>left</code> 버전은 프레임의 50%를 떨어뜨렸고, <code>transform</code> 버전은 1%만 떨어뜨렸습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> Chrome DevTools의 Rendering 탭에서 FPS meter를 켜면 버려진 프레임 비율을 직접 확인할 수 있습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<aside class="poster" aria-label="버려진 프레임 top/left 50% transform 1%"><span class="poster-line" aria-hidden="true">버려진 프레임</span><span class="poster-line" aria-hidden="true">top/left 50%</span><span class="poster-line poster-accent" aria-hidden="true">transform 1%</span></aside>
<h3 id="css냐-js냐보다-앞서는-질문">CSS냐 JS냐보다 앞서는 질문</h3>
<p>애니메이션이 레이아웃이나 페인트를 일으키면 CSS든 JS든 메인 스레드가 일해야 하고, 그 비용이 CSS·JS 실행 비용을 압도해 둘을 비교하는 의미가 사라집니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> MDN도 같은 점을 짚습니다. Firefox에서 <code>&#x3C;div></code> 1000개를 움직인 실험에서 두 방식이 모두 메인 스레드에서 돌 때는 FPS가 거의 같았고, 메인 스레드 밖 애니메이션(OMTA)을 켜자 CSS 쪽 FPS가 크게 올랐습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<h4>자주 하는 실수: will-change를 미리 뿌려 두기</h4>
<p><code>will-change: transform</code>은 요소를 새 레이어로 올리라고 브라우저에 알리는 속성입니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 레이어마다 메모리를 쓰고 텍스처를 GPU로 올려야 해서, 메모리가 적은 기기에서는 해결하려던 문제보다 더 큰 성능 문제를 만들 수 있습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 자주 바뀌지 않는 요소라면 변화가 일어나기 직전에 JS로 붙이고 끝나면 떼고, 실제 성능 문제가 있을 때만 쓰라는 것이 web.dev의 권고입니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<h2 id="js로-쓰면서-메인-스레드를-비켜-가기">JS로 쓰면서 메인 스레드를 비켜 가기</h2>
<h3 id="web-animations-api">Web Animations API</h3>
<p>Web Animations API(WAAPI)는 브라우저의 애니메이션 엔진을 JavaScript로 다룰 수 있게 열어 둔 API이고, CSS 애니메이션과 CSS 트랜지션의 바탕이 되도록 설계됐습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 키프레임과 길이를 JS 값으로 정하면서도 CSS 애니메이션과 같은 엔진에 맡길 수 있다는 뜻입니다.</p>
<p>가장 짧은 사용법은 <code>Element.animate()</code>입니다. 애니메이션을 만들고 요소에 적용한 뒤 바로 재생하며, 만든 <code>Animation</code> 객체를 돌려줍니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 앞의 튀는 공을 WAAPI로 옮기면 이렇습니다.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-keyword">const</span> ball = <span class="hljs-variable language_">document</span>.<span class="hljs-title function_">querySelector</span>(<span class="hljs-string">".ball"</span>);

<span class="hljs-keyword">const</span> keyframes = [
  { <span class="hljs-attr">transform</span>: <span class="hljs-string">"translateX(0)"</span> },
  { <span class="hljs-attr">transform</span>: <span class="hljs-string">"translateX(-200px)"</span> },
];
<span class="hljs-keyword">const</span> timing = {
  <span class="hljs-attr">duration</span>: <span class="hljs-number">1000</span>,
  <span class="hljs-attr">iterations</span>: <span class="hljs-title class_">Infinity</span>,
  <span class="hljs-attr">direction</span>: <span class="hljs-string">"alternate"</span>,
};

<span class="hljs-keyword">const</span> bounce = ball.<span class="hljs-title function_">animate</span>(keyframes, timing);
<span class="hljs-comment">// CSS의 animation: bounce 1000ms infinite alternate 와 같은 움직임</span>
</code></pre>
<p>옵션 이름은 CSS 속성과 거의 일대일로 대응합니다. <code>direction</code>의 <code>"alternate"</code>는 반복마다 방향을 바꾸고, <code>iterations</code>에 <code>Infinity</code>를 주면 요소가 있는 동안 계속 반복합니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> 키프레임은 따로 위치를 정하지 않으면 개수에 맞춰 균등하게 나뉘고, 특정 위치에 두려면 <code>offset: 0.3</code>처럼 지정합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<h3 id="재생을-코드로-제어하기">재생을 코드로 제어하기</h3>
<p>CSS 애니메이션을 멈추거나 되돌리려면 클래스를 붙였다 떼는 식의 우회가 필요했지만, WAAPI는 <code>Animation</code> 객체의 메서드로 바로 제어합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup><sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js">bounce.<span class="hljs-title function_">pause</span>();            <span class="hljs-comment">// 일시 정지</span>
bounce.<span class="hljs-property">playbackRate</span> = <span class="hljs-number">2</span>;   <span class="hljs-comment">// 두 배 속도</span>
bounce.<span class="hljs-title function_">reverse</span>();          <span class="hljs-comment">// 방향을 뒤집어 재생</span>
bounce.<span class="hljs-title function_">play</span>();             <span class="hljs-comment">// 다시 재생</span>

<span class="hljs-keyword">const</span> fadeOut = ball.<span class="hljs-title function_">animate</span>([{ <span class="hljs-attr">opacity</span>: <span class="hljs-number">1</span> }, { <span class="hljs-attr">opacity</span>: <span class="hljs-number">0</span> }], <span class="hljs-number">300</span>);
<span class="hljs-keyword">await</span> fadeOut.<span class="hljs-property">finished</span>;    <span class="hljs-comment">// 재생이 끝나면 resolve되는 Promise</span>
</code></pre>
<p><code>finished</code>는 재생이 끝날 때를 알려 주는 Promise라서, 다음 동작을 이어 붙이기 쉽습니다.<sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup></p>
<h4>자주 하는 실수: 끝나고 원래 자리로 돌아가는 요소</h4>
<p><code>fill</code> 옵션의 기본값은 <code>"none"</code>이라서, 애니메이션이 끝나면 요소는 시작 전 스타일로 돌아갑니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> 마지막 상태를 유지하려면 <code>fill: "forwards"</code>를 주거나, <code>commitStyles()</code>로 현재 스타일을 요소의 <code>style</code> 속성에 기록합니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup><sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup> 또 <code>duration</code>의 기본값은 0이어서, 길이를 빼먹으면 애니메이션이 실행되지 않습니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<h3 id="라이브러리-선택에도-같은-기준">라이브러리 선택에도 같은 기준</h3>
<p>원문 필자는 메인 스레드를 막는 시뮬레이션에서 Motion(이전 이름 Framer Motion)과 GSAP를 비교했습니다. 둘 다 JS 라이브러리지만 Motion만 끊기지 않았는데, Motion이 내부적으로 WAAPI를 쓰기 때문이라고 설명합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 필자는 GSAP가 WAAPI로는 구현하기 어려운 기능을 많이 갖춘 강력한 라이브러리라서, 잘못된 선택이 아니라 다른 트레이드오프를 고른 것이라고 봅니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<p>WAAPI를 써도 <code>width</code>처럼 레이아웃을 일으키는 속성을 움직이면 메인 스레드가 일해야 한다는 점은 같습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 라이브러리를 고를 때도, 직접 짤 때도 "무엇을 움직이는가"를 먼저 확인해야 합니다.</p>
<h2 id="언제-무엇을-고를까">언제 무엇을 고를까</h2>
<p>원문 필자는 가능하면 CSS 애니메이션·트랜지션을 쓰고, CSS만으로 안 될 때 Motion 같은 WAAPI 기반 라이브러리를 쓴다고 말합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> View Transitions, <code>linear()</code>, Animation Timeline 같은 새 CSS 기능 덕분에 라이브러리가 필요한 경우가 많지 않다는 것이 필자의 의견입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> MDN도 가능하면 CSS 트랜지션·애니메이션을 쓰고, 정말 복잡한 경우에만 JS 애니메이션에 기대라고 정리합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<p>어떤 방법을 고르든 움직임을 줄이고 싶어 하는 사용자를 배려해야 합니다. 큰 요소의 확대·이동 같은 움직임은 전정 기관 장애가 있는 사람에게 불편을 줄 수 있고, <code>prefers-reduced-motion</code>으로 그 설정을 감지할 수 있습니다.<sup class="cite"><a href="#source-10" aria-label="출처 10">[10]</a></sup></p>
<pre data-lang="css"><code class="hljs language-css"><span class="hljs-selector-class">.animation</span> {
  <span class="hljs-attribute">animation</span>: pulse <span class="hljs-number">1s</span> linear infinite both;
}

<span class="hljs-comment">/* 움직임 줄이기를 켠 사용자에게는 크기 변화 대신 투명도만 */</span>
<span class="hljs-keyword">@media</span> (<span class="hljs-attribute">prefers-reduced-motion</span>: reduce) {
  <span class="hljs-selector-class">.animation</span> {
    <span class="hljs-attribute">animation</span>: dissolve <span class="hljs-number">4s</span> linear infinite both;
  }
}
</code></pre>
