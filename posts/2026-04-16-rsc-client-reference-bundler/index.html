RSC가 번들러와 붙어 다니는 이유 — 'use client'와 클라이언트 참조

React Server Components는 데이터뿐 아니라 실행할 코드까지 클라이언트로 넘겨야 합니다. 컴포넌트 함수를 어떻게 직렬화하는지, 그 과정에서 번들러가 맡는 일이 무엇인지 코드로 따라갑니다.

요약

  • RSC의 직렬화기는 JSX 트리뿐 아니라 'use client' 모듈 같은 코드도 보내야 해서, 코드 대신 모듈을 가리키는 참조를 직렬화합니다[1][2].
  • 'use client'는 렌더 트리가 아니라 모듈 의존성 트리에 서버·클라이언트 경계를 긋고, 호환 번들러가 이 import를 경계로 처리합니다[3].
  • 번들러 바인딩은 빌드 때 'use client' 파일로 청크를 만들고, 서버에서는 모듈을 참조로 보내는 법을, 클라이언트에서는 그 청크를 불러오는 법을 React에 알려 줍니다[1].
  • RSC를 구현하는 번들러용 하위 API는 semver를 따르지 않아 React 19.x 마이너 버전 사이에서도 바뀔 수 있습니다[4].

RSC는 데이터와 함께 코드를 보낸다

React Server Components(RSC)는 서버에서 렌더링한 React 트리를 직렬화해 클라이언트로 보내고, 클라이언트가 이를 다시 React 트리로 되살리는 구조입니다. React 저장소에서는 직렬화기가 packages/react-server, 역직렬화기가 packages/react-client에 있습니다[1]. react-server README는 RSC를 본질적으로 Suspense·Lazy 같은 React 기본 요소를 지원하는 범용 직렬화·역직렬화 기능이라고 설명합니다[2].

직렬화하기 쉬운 것: 태그와 props

일반 HTML 태그로 된 트리는 평범한 객체로 바꾸면 됩니다[1].

// <p>Hello, world</p> 를 직렬화하면
{
  type: 'p',
  props: {
    children: 'Hello, world'
  }
}
// → JSON 문자열로 보내고, 받는 쪽에서 그대로 <p>를 만든다

react-server가 렌더링할 수 있는 값은 structuredClone()이 다루는 타입의 상위 집합입니다. 복제 가능한 타입에 더해 Symbol, Promise, Iterator·Iterable, async Iterator·Iterable도 보낼 수 있습니다[2].

직렬화하기 어려운 것: 컴포넌트 함수

문제는 상태와 이벤트를 가진 컴포넌트입니다. 아래 Counter는 서버에서 렌더 결과만 찍어 보내서는 안 됩니다. 클라이언트에서 실제로 동작해야 하므로 코드 자체가 건너가야 합니다[1].

// client.js
'use client';
import { useState, useEffect } from 'react';

export function Counter({ initialCount }) {
  const [count, setCount] = useState(initialCount);
  // ...
}

// 서버 컴포넌트에서
import { Counter } from './client';

<Counter initialCount={10} />
// → type 자리에 들어갈 것이 문자열 'p'가 아니라 함수다

가장 단순한 방법은 함수 소스를 문자열로 JSON에 넣는 것입니다. 원문 필자는 이 방법이 나쁘다고 봅니다. 클라이언트에서 문자열을 eval해야 하고, 같은 컴포넌트가 여러 번 나오면 같은 코드를 여러 번 보내게 되기 때문입니다[1].

코드 대신 주소를 보낸다

그래서 RSC는 코드를 정적 JS 파일로 따로 제공한다고 가정하고, 직렬화 결과에는 그 파일을 가리키는 참조만 넣습니다. <script> 태그가 src로 파일을 가리키는 것과 비슷합니다[1].

{
  type: '/src/client.js#Counter', // client.js를 불러와 Counter를 꺼낸다
  props: {
    initialCount: 10
  }
}
// → props(데이터)는 값으로, Counter(코드)는 주소로 보낸다
코드가 아니라모듈 주소를 보낸다

'use client'는 모듈 그래프에 긋는 경계

어떤 모듈을 "주소로 보낼 코드"로 취급할지 정하는 표시가 'use client'입니다. 파일 맨 위에 쓰면 그 모듈과 그 모듈이 의존하는 모든 모듈(전이 의존성)이 클라이언트 코드가 됩니다. 서버 컴포넌트가 이런 파일을 import하면, 호환 번들러는 그 import를 서버 실행 코드와 클라이언트 실행 코드의 경계로 처리합니다[3].

렌더 트리가 아니라 모듈 트리

react.dev의 예제를 줄이면 다음과 같습니다. InspirationGenerator.js에만 'use client'가 있습니다[3].

// App.js — 지시어 없음
import FancyText from './FancyText';
import InspirationGenerator from './InspirationGenerator';
import Copyright from './Copyright';

export default function App() {
  return (
    <>
      <FancyText title text="Get Inspired App" />
      <InspirationGenerator>
        <Copyright year={2004} />
      </InspirationGenerator>
    </>
  );
}
// App            → 서버 컴포넌트
// FancyText      → 서버 컴포넌트 (App이 직접 렌더링)
// Copyright      → 서버 컴포넌트 (클라이언트 컴포넌트의 children인데도)
// InspirationGenerator → 클라이언트 컴포넌트

Copyright는 클라이언트 컴포넌트 안에 그려지지만 서버 컴포넌트입니다. Copyright를 import하고 호출하는 쪽은 App이고, InspirationGenerator는 이미 렌더링된 결과를 children으로 받을 뿐이기 때문입니다[3]. 예제에서는 InspirationGenerator도 FancyText를 import해 씁니다. 이 사용처는 클라이언트 컴포넌트이므로, FancyText 정의는 서버에서도 실행되고 클라이언트에도 내려갑니다[3].

자주 하는 실수

  • 지시어는 import보다 위, 파일 맨 처음에 둡니다. 주석은 위에 와도 되지만, 작은따옴표나 큰따옴표로만 쓰고 백틱은 안 됩니다[3].
  • 이미 클라이언트 모듈인 파일에서 import한 모듈에 'use client'를 또 붙여도 아무 효과가 없습니다[3].
  • 서버 모듈이 'use client' 모듈에서 가져온 값은 React 컴포넌트이거나 클라이언트 컴포넌트에 넘길 수 있는 직렬화 가능한 props여야 합니다. 그 밖의 용도로 쓰면 예외가 납니다[3].
  • 서버 컴포넌트를 표시하는 지시어는 없습니다. "use server"는 서버 컴포넌트가 아니라 서버 함수용입니다[4].

클라이언트 참조와 서버 참조

번들러가 경계를 찾으면 그다음은 React가 그 모듈을 "참조"로 다룰 수 있게 해야 합니다. react-server에는 렌더링할 수 있는 참조가 두 종류 있습니다[2].

클라이언트 참조(client reference)

RSC 프레임워크가 번들링 중 "use client"를 만나면, 그 모듈에서 export한 값들을 registerClientReference로 등록해야 합니다. 그러면 Flight(RSC 렌더러의 코드명)는 그 값을 서버 모듈 그래프의 직접 의존성이 아니라 클라이언트에서 불러올 참조로 해석하고, 출력에 코드를 불러오는 방법을 기록합니다[2]. 참조는 컴포넌트가 아니어도 됩니다[2].

// 'use client' 모듈 두 개에서 가져온 값
import { alert } from '...';      // 함수
import { ClientComp } from '...'; // 컴포넌트

createResponse(
  <App>
    <ClientComp onClick={alert} message={"hello world"} />
  </App>,
  ...)
// → ClientComp도, onClick에 넘긴 alert 함수도 참조로 직렬화된다

일반 함수는 직렬화 대상이 아닙니다. 서버 함수 인자로도 서버 함수가 아닌 함수는 지원하지 않습니다[5]. 여기서 alert는 클라이언트 모듈의 export라서 함수 본문 대신 주소로 보낼 수 있습니다.

서버 참조(server reference)

방향이 반대인 참조도 있습니다. "use server"가 붙은 함수는 클라이언트에서 호출할 수 있는 서버 진입점이 되고, registerServerReference()로 등록해 Flight가 서버 참조로 인식하게 합니다[2]. 클라이언트에서 서버 함수를 부르면 인자를 직렬화한 네트워크 요청이 서버로 가고, 반환값도 직렬화되어 돌아옵니다[5].

// actions.js
'use server';

export async function likeComment(id) {
  let newLikeCount = await db.incrementLikeCount(id);
  return newLikeCount;
}
// → 클라이언트에는 함수 본문이 아니라 호출용 참조만 전달된다

Parcel에서는 서버 함수마다 Parcel이 만든 id가 있고, 클라이언트는 이 id와 호출 인자를 HTTP 요청으로 서버에 보냅니다[6]. 네트워크 호출은 항상 비동기이므로 'use server'는 async 함수에만 쓸 수 있습니다. 인자는 클라이언트가 마음대로 정할 수 있으니 신뢰할 수 없는 입력으로 보고 검증·권한 확인을 해야 합니다[5].

번들러 바인딩이 하는 세 가지 일

참조를 문자열 하나로 만드는 것까지는 번들러 없이도 됩니다. React 저장소에는 번들러 없이 ESM으로 RSC를 돌리는 개념 증명 예제(fixtures/flight-esm)도 있습니다[1][7]. 원문 필자는 이 예제가 기록용에 가깝다고 봅니다. 추가 최적화 없이 단순하게 하면 너무 비효율적이라는 이유입니다[1].

모듈을 하나씩 받으면 생기는 폭포

브라우저가 /src/client.js를 받아 실행해 보기 전에는 그 파일이 무엇을 import하는지 모릅니다. 의존성을 발견할 때마다 새 요청을 보내야 하니 요청이 줄줄이 이어지는 폭포(waterfall)가 생깁니다[1].

// client.js 를 받아 파싱한 뒤에야 다음 요청이 시작된다
import { useState } from 'react';          // 요청 2
import { formatDate } from './formatters'; // 요청 3
// formatters.js 가 또 무언가를 import하면 → 요청 4 ...

원문 필자는 이 문제의 답이 클라이언트 앱에서 오래 써 온 번들링이라고 봅니다[1]. 그래서 실제로 쓰는 RSC 통합은 번들러마다 따로 있고, Parcel·Webpack용 바인딩이 React 저장소에 있습니다[1].

빌드·서버·클라이언트

바인딩이 하는 일은 세 단계로 나뉩니다[1].

  1. 빌드: 'use client' 파일을 찾아 그 파일들을 진입점으로 번들 청크를 만듭니다.
  2. 서버: 모듈을 클라이언트로 보내는 표기법을 React에 알려 줍니다. 예를 들어 'chunk123.js#Counter'처럼 청크 이름으로 가리킵니다.
  3. 클라이언트: 그 참조를 받으면 번들러 런타임에 모듈 로드를 요청하는 방법을 React에 알려 줍니다.
// 번들러 바인딩을 거친 뒤 (원문의 예시 표기)
{
  type: 'chunk123.js#Counter',
  props: { initialCount: 10 }
}

react-server README의 render 함수 예시도 직렬화할 트리(model)와 함께 clientManifest: ClientManifest를 인자로 받습니다[2]. 직렬화기가 클라이언트 모듈 정보를 바깥에서 받는다는 점이 API 모양에도 드러납니다.

실제 API: Parcel

원문은 serialize/deserialize라는 이름을 예시로 들고, 실제 이름은 바인딩마다 다르다고 밝힙니다. @parcel/rsc는 react-server-dom-parcel 위의 얇은 래퍼로, 직렬화를 renderRSC, 역직렬화를 fetchRSC로 제공합니다[1]. Parcel은 v2.14.0부터 RSC를 기본 지원하며 아직 베타이고, react·react-dom v19.1.0 이상이 필요합니다[6].

// server/server.js
import { renderRSC } from "@parcel/rsc/node";

app.get("/comments", (req, res) => {
  let stream = renderRSC(<Comments />);
  res.set("Content-Type", "text/x-component");
  stream.pipe(res);
});
// → 컴포넌트 트리를 직렬화한 RSC 페이로드를 스트림으로 응답

// src/App.js
import {fetchRSC} from '@parcel/rsc/client';

let request = null;
function Comments() {
  request ??= fetchRSC('http://localhost:3000/comments');
  return request;
}
// → Suspense 안에서 렌더링하면 페이로드 속 참조를 따라 청크를 불러온다

역직렬화한 결과는 클라이언트에서 직접 쓴 JSX와 같아서 렌더링하거나 상태에 넣거나 HTML로 바꿀 수 있습니다[1]. Parcel 문서는 서버가 응답 렌더링에 필요한 클라이언트 컴포넌트와 CSS를 클라이언트에 알려 주므로, 리소스가 데이터와 병렬로 로드된다고 설명합니다[6].

자주 하는 실수: 하위 API를 직접 고정하지 않기

React 19의 RSC 자체는 마이너 버전 사이에 깨지지 않지만, 번들러·프레임워크가 RSC를 구현할 때 쓰는 하위 API는 semver를 따르지 않습니다. React는 특정 버전에 고정하거나 Canary 릴리스를 쓰라고 권합니다[4]. react-server-dom-parcel도 README에서 실험적 바인딩이라고 밝힙니다[8]. 또 Parcel은 현재 "use server"를 파일 맨 위에만 지원하고 함수 안 인라인 지시어는 지원하지 않습니다[6].

정리

단계 하는 일 담당
표시 'use client'로 모듈 트리에 경계를 긋는다[3] 개발자
빌드 경계 파일을 진입점으로 청크를 만든다[1] 번들러
등록 export를 registerClientReference로 참조 등록[2] 프레임워크·바인딩
직렬화 데이터는 값으로, 코드는 'chunk123.js#Counter' 같은 주소로[1] React 서버 + 바인딩
역직렬화 번들러 런타임으로 청크를 불러와 JSX로 복원[1] React 클라이언트 + 바인딩
  • 경계는 렌더 트리가 아니라 import 관계로 정해집니다. 클라이언트 컴포넌트의 children이어도 서버 컴포넌트일 수 있습니다[3].
  • 서버 컴포넌트에 남은 코드는 클라이언트 번들에 들어가지 않습니다. react.dev 예제에서는 마크다운 렌더링 라이브러리 75K(gzip)를 내려받지 않아도 됩니다[4].
  • 번들러 없이도 RSC는 돌아가지만, 원문 필자는 모듈 폭포 때문에 현실적인 통합은 번들러별로 만들어진다고 봅니다[1].

프론트엔드 팀이 해 볼 것

  1. 프로젝트에서 'use client'가 붙은 파일을 검색하고, 각 파일이 끌고 들어가는 import를 따라가 클라이언트 번들에 들어갈 모듈 목록을 적어 봅니다.
  2. 클라이언트 컴포넌트의 children으로 넘기는 서버 컴포넌트가 있다면, 그 컴포넌트를 클라이언트 파일에서 직접 import하고 있지 않은지 확인합니다.
  3. Parcel RSC 레시피로 renderRSC·fetchRSC 예제를 띄우고, 개발자 도구 네트워크 탭에서 text/x-component 응답에 담긴 참조와 이어지는 청크 요청을 확인합니다.
