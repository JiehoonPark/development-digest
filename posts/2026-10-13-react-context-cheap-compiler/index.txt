<p><code>useContext</code>는 Context를 읽는 동시에 구독(subscribe)하는 훅입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 가장 가까운 Provider가 Object.is 비교로 다른 값을 받으면, React는 그 Context를 읽는 자식을 모두 다시 렌더링합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> "필요한 부분만 바뀌었는지"는 따지지 않습니다.</p>

<h3 id="자주-하는-실수-memo로-막으려-하기">자주 하는 실수: memo로 막으려 하기</h3>

<h2 id="셀렉터는-왜-없을까">셀렉터는 왜 없을까</h2>
<p>Context 셀렉터는 Context에서 필요한 값만 골라내고, 그 값이 바뀔 때만 렌더링하게 하는 API입니다. 원문 필자는 아래 같은 모양을 예로 듭니다. React에는 이런 API가 없습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>

<h3 id="제거된-changedbits와-멈춘-rfc">제거된 changedBits와 멈춘 RFC</h3>
<p>비슷한 장치는 예전에 있었습니다. React 16.3.2의 <code>createContext</code>는 두 번째 인자로 <code>calculateChangedBits</code> 함수를 받았습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> Provider가 바뀐 비트를 표시하면 소비자는 <code>unstable_observedBits</code>로 관심 있는 비트만 구독하는 방식이었습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<p>이 기능은 PR #20953에서 제거됐습니다. Context 업데이트를 건너뛰려고 넣었지만 실제로 쓸모가 없었고, Context 셀렉터 같은 다른 제안이 있다는 이유였습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 그 셀렉터 RFC는 선택한 값이 바뀌지 않으면 컴포넌트가 업데이트되지 않는 새 훅을 제안했고, 이를 위해 Context 전파를 더 게으르게(lazy) 바꾸는 변경에 의존합니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<h3 id="usesyncexternalstore로-우회하기-전에">useSyncExternalStore로 우회하기 전에</h3>
<p>많은 팀이 이 지점에서 외부 스토어와 <code>useSyncExternalStore</code>를 고릅니다. 공식 문서는 가능하면 <code>useState</code>·<code>useReducer</code> 같은 내장 state를 쓰라고 권하고, 이 훅은 주로 React가 아닌 기존 코드와 연동할 때 유용하다고 말합니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> 외부 스토어가 non-blocking Transition 중에 바뀌면 React가 그 업데이트를 blocking으로 다시 처리한다는 주의점도 있습니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<p>원문 필자는 React의 기본 도구에서 벗어날수록 동시성 렌더링 같은 기능을 놓칠 위험이 있다고 봅니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 이것은 필자의 해석이고, 공식 문서가 외부 스토어를 금지하는 것은 아닙니다.</p>

<span class="hljs-comment">// 선택이 바뀌면: Radio 5,000개는 렌더링</span>
<span class="hljs-comment">// RadioView는 checked가 바뀐 2개만 렌더링, 나머지 4,998개는 건너뜀</span>
</code></pre>
<p>바깥 <code>Radio</code>는 여전히 매번 렌더링되지만 하는 일은 비교 한 번과 JSX 한 줄뿐입니다. <code>memo</code>는 기본으로 각 prop을 Object.is로 비교하고<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup>, <code>checked</code>는 불리언, <code>onSelect</code>는 <code>setValue</code>라 안정적입니다. 그래서 4,998개의 <code>RadioView</code>가 일을 건너뜁니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>

<p>스토어 방식은 바뀐 라디오 2개만 렌더링하는데도 큰 차이가 나지 않았습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 필자도 좁은 벤치마크라 일반적인 순위로 보면 안 된다고 단서를 답니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<h3 id="자주-하는-실수-자식에게-새-함수-넘기기">자주 하는 실수: 자식에게 새 함수 넘기기</h3>
<p>나누기만 하고 props를 잘못 넘기면 효과가 사라집니다. 렌더링 중에 만든 함수는 매번 새 값이라 <code>memo</code>가 쓸모없어집니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<pre data-lang="jsx"><code class="hljs language-jsx"><span class="hljs-comment">// 잘못된 예: 화살표 함수가 매 렌더링마다 새로 생김</span>
&#x3C;<span class="hljs-title class_">RadioView</span> checked={checked} onSelect={<span class="hljs-function">() =></span> context.<span class="hljs-title function_">onSelect</span>(value)} />
<span class="hljs-comment">// → 5,000개 RadioView가 모두 다시 렌더링</span>

<span class="hljs-comment">// 올바른 예: 안정된 핸들러와 원시값을 따로 넘김</span>
<span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">RadioView</span> <span class="hljs-attr">checked</span>=<span class="hljs-string">{checked}</span> <span class="hljs-attr">onSelect</span>=<span class="hljs-string">{context.onSelect}</span> <span class="hljs-attr">value</span>=<span class="hljs-string">{value}</span> /></span></span>
</code></pre>
<p><code>context</code> 객체를 통째로 넘기는 것도 같은 실수입니다. <code>value</code>가 바뀔 때마다 새 객체가 되므로 모든 <code>RadioView</code>가 새 prop을 받습니다.</p>
<h2 id="react-compiler가-바꾸는-점">React Compiler가 바꾸는 점</h2>
<p>React Compiler는 빌드 단계에서 컴포넌트에 메모이제이션을 넣어 주는 도구입니다. 설치와 기본 원리는 이전 글 "useMemo를 손으로 쓰지 않는 React"에서 다뤘으니 여기서는 Context와 만나는 지점만 봅니다. <code>memo</code> 문서에 따르면 컴파일러는 모든 컴포넌트에 <code>memo</code>와 같은 효과를 적용합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<h3 id="나누지-않아도-된다">나누지 않아도 된다</h3>
<p>컴파일러를 켜면 <code>RadioView</code>를 따로 만들 필요가 없습니다. 원문의 컴파일러 버전은 이렇습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<pre data-lang="jsx"><code class="hljs language-jsx"><span class="hljs-keyword">function</span> <span class="hljs-title function_">Radio</span>(<span class="hljs-params">{ value }</span>) {
  <span class="hljs-keyword">const</span> context = <span class="hljs-title class_">React</span>.<span class="hljs-title function_">useContext</span>(<span class="hljs-title class_">RadioContext</span>);
  <span class="hljs-keyword">const</span> checked = context.<span class="hljs-property">value</span> === value;
  <span class="hljs-keyword">const</span> onSelect = context.<span class="hljs-property">onSelect</span>;

  <span class="hljs-keyword">return</span> (
    <span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">input</span>
      <span class="hljs-attr">type</span>=<span class="hljs-string">"radio"</span>
      <span class="hljs-attr">name</span>=<span class="hljs-string">"demo"</span>
      <span class="hljs-attr">checked</span>=<span class="hljs-string">{checked}</span>
      <span class="hljs-attr">onChange</span>=<span class="hljs-string">{()</span> =></span> onSelect(value)}
    /></span>
  );
}
<span class="hljs-comment">// 선택이 바뀌면: Radio 5,000개는 여전히 렌더링</span>
<span class="hljs-comment">// checked·onSelect·value가 그대로인 4,998개는 이전 JSX를 재사용</span>
</code></pre>
<p>모든 <code>Radio</code>가 렌더링되는 것은 그대로입니다. 대신 컴파일러가 <code>checked</code>, <code>onSelect</code>, <code>value</code>가 바뀌지 않은 라디오의 JSX를 다시 씁니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 공식 문서도 컴파일러가 이전에 만든 JSX를 재사용해 자식 렌더링을 건너뛴다고 설명합니다.<sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup> 나누기와 같은 생각인데, 메모이제이션이 별도 컴포넌트가 아니라 소비자의 렌더링 안에서 일어납니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<p><code>onChange={() => onSelect(value)}</code> 같은 화살표 함수도 괜찮습니다. 공식 문서는 화살표 함수가 있든 없든 컴파일러가 올바르게 최적화한다고 말합니다.<sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup></p>
<h3 id="원문의-주장과-공식-동작-구분하기">원문의 주장과 공식 동작 구분하기</h3>
<p>Joseph Savona는 RFC 댓글에서 컴파일러가 이미 Context 셀렉터에서 원하는 것의 상당 부분을 해 준다고 주장했습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 이것은 의견이고, Context의 전파 방식이 바뀐 것은 아닙니다. Provider 값이 바뀌면 모든 소비자가 렌더링된다는 공식 동작은 그대로이고<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup>, 컴파일러는 그 렌더링 안의 일을 줄일 뿐입니다.</p>
<aside class="poster" aria-label="렌더 횟수보다 렌더 한 번의 비용"><span class="poster-line" aria-hidden="true">렌더 횟수보다</span><span class="poster-line poster-accent" aria-hidden="true">렌더 한 번의 비용</span></aside>
<p>원문 필자는 사용자가 기다리는 것은 렌더링 횟수가 아니라 각 렌더링이 하는 일이고, 렌더링을 피하기보다 싸게 만드는 데 집중하자고 제안합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<h3 id="자주-하는-실수">자주 하는 실수</h3>
<ul>
<li><strong>값을 파생하지 않고 객체를 그대로 쓰기</strong>: JSX가 <code>context</code> 객체 전체에 의존하면 재사용할 근거가 없습니다. 원문처럼 <code>checked</code> 같은 원시값을 먼저 계산합니다.</li>
<li><strong>기존 메모이제이션 일괄 삭제</strong>: 컴파일러를 켰다고 Provider의 <code>useMemo</code>를 지우면 컴파일 결과가 달라질 수 있습니다. 공식 문서는 그대로 두거나 꼼꼼히 테스트한 뒤 지우라고 권합니다.<sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup></li>
<li><strong>컴포넌트 팩토리 남겨 두기</strong>: 필자는 컴파일러가 없을 때를 위해 <code>withContextSelector</code>라는 감싸개를 만들었지만, 이는 컴포넌트 팩토리라 React 린트 규칙이 권하지 않습니다. 나중에 컴파일러로 옮기면 지워야 효과를 다 얻는다고 필자는 말합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></li>
</ul>
