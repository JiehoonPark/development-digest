17:T658f,<h2 id="5만-행-주문-목록을-맡았다고-가정해-봅시다">5만 행 주문 목록을 맡았다고 가정해 봅시다</h2>
<p>관리자 화면의 주문 목록을 맡았다고 가정해 봅시다. 실제 서비스 수치가 아니라 방식을 비교하려고 정한 조건입니다.</p>
<ul>
<li>한 번에 5만 건을 내려받아 한 화면에서 스크롤로 훑습니다.</li>
<li>행 높이는 48px로 같고, 주문 번호·이름·금액만 보입니다.</li>
<li>정렬 버튼을 누르면 즉시 순서가 바뀌어 보여야 합니다.</li>
<li>키보드와 스크린 리더로도 목록을 탐색할 수 있어야 합니다.</li>
</ul>
<p>방식은 세 가지를 비교합니다. 5만 행을 모두 DOM에 넣는 <strong>전체 렌더링</strong>, 그 위에 CSS 한 줄을 더한 <strong>content-visibility</strong>, 보이는 행만 만드는 **가상 스크롤(virtual scrolling)**입니다. 실험 코드는 의존성 없는 HTML과 ES 모듈이고, 같은 행 생성 함수 <code>renderRow</code>를 세 방식이 함께 씁니다.</p>
<p>측정은 로컬 맥의 headless Chrome 157에서 방식마다 페이지를 새로 열어 5회 반복한 중앙값입니다. DOM 노드는 문서 전체 노드 수, 레이아웃·스타일은 첫 렌더링부터 스크롤 이동 한 번까지 누적한 시간입니다. 정렬 클릭은 그 클릭에 속한 이벤트 항목 중 가장 긴 <code>duration</code>입니다. 기기와 브라우저가 바뀌면 숫자도 바뀝니다. 아래 수치는 방식끼리의 상대 비교로만 읽어야 합니다.</p>
<h2 id="무엇을-재야-느린지-알-수-있습니다">무엇을 재야 느린지 알 수 있습니다</h2>
<h3 id="long-task와-이벤트-타이밍">Long Task와 이벤트 타이밍</h3>
<p>메인 스레드를 50ms 이상 쉬지 않고 점유하는 작업을 Long Task라고 합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 메인 스레드는 한 번에 작업 하나만 처리하므로, 긴 작업이 도는 동안에는 클릭에 대한 반응도 기다립니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> 큰 리플로(reflow)나 오래 걸리는 이벤트 처리기가 대표적인 원인입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 이를 알려 주는 <code>PerformanceLongTaskTiming</code>은 MDN에서 실험적·비표준 기능으로 표시되어 있으므로, 지원하지 않는 브라우저에서는 값이 비어 있을 수 있습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<p>클릭 같은 상호작용의 지연은 <code>PerformanceEventTiming</code>으로 봅니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> <code>processingStart - startTime</code>은 처리기가 시작되기까지 기다린 시간, <code>processingEnd - processingStart</code>는 처리기가 실행된 시간입니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 실험 페이지에는 두 관찰자를 다음과 같이 붙였습니다.</p>

<p>이벤트 항목은 기본적으로 104ms 이상일 때만 보고되고, <code>durationThreshold</code>로 낮출 수 있는 최솟값은 16ms입니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 기간 값은 8ms 단위로 반올림됩니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 빠른 방식의 클릭을 놓치지 않으려고 16을 넣었습니다.</p>
<h3 id="inp는-현장-지표입니다">INP는 현장 지표입니다</h3>
<p>INP(Interaction to Next Paint)는 방문 동안 일어난 클릭·탭·키 입력의 지연을 관찰해, 이상치를 빼고 가장 긴 값을 페이지 대표값으로 씁니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 200ms 이하는 좋음, 500ms 초과는 나쁨이며, 기준은 현장 데이터의 75번째 백분위수입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 스크롤 자체는 INP가 재는 상호작용이 아닙니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<p>이 글의 수치는 스크립트로 한 번 누른 실험실 값입니다. INP 점수가 아니라, 정렬 클릭 하나가 다음 그리기를 얼마나 막는지 비교하는 용도로만 씁니다.</p>
<h2 id="content-visibility-dom은-두고-렌더링만-건너뜁니다">content-visibility: DOM은 두고 렌더링만 건너뜁니다</h2>
<p><code>content-visibility: auto</code>를 준 요소는 레이아웃·스타일·페인트 격리를 켜고, 사용자와 관련 없을 때는 내용 렌더링을 건너뜁니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 화면 밖 행의 크기를 계산하지 않으므로 자리를 지킬 추정 크기가 필요합니다. <code>contain-intrinsic-size</code>의 <code>auto &#x3C;length></code>는 한 번 렌더링된 실제 크기를 기억하고, 기억이 없을 때만 지정한 길이를 씁니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<pre data-lang="css"><code class="hljs language-css"><span class="hljs-selector-class">.cv</span> <span class="hljs-selector-class">.row</span> { <span class="hljs-attribute">content-visibility</span>: auto; <span class="hljs-attribute">contain-intrinsic-size</span>: auto <span class="hljs-number">48px</span>; }
</code></pre>
<p>5만 행에 이 한 줄을 더한 결과입니다(Chrome 157 headless, 5회 중앙값).</p>
<pre data-lang="text"><code class="hljs language-text">방식          첫 렌더링  DOM 노드  레이아웃  스타일  가장 긴 작업  정렬 클릭
전체 렌더링    807ms    350,020   345ms    76ms    799ms       808ms
content-vis   571ms    350,020    45ms    51ms    622ms       616ms
</code></pre>
<p>레이아웃 시간은 345ms에서 45ms로 줄었지만, 노드 수는 같고 Long Task는 사라지지 않았습니다. 5만 행의 DOM을 자바스크립트로 만드는 비용은 CSS가 건너뛸 수 있는 단계가 아니기 때문입니다. 정렬 클릭의 처리기 시간도 319ms로, 전체 렌더링의 329ms와 비슷했습니다. CPU를 4배 느리게 한 조건에서도 가장 긴 작업은 2,359ms에서 1,810ms로 줄어든 데 그쳤습니다.</p>
<p>반대로 DOM이 남아 있다는 점은 장점입니다. <code>auto</code>로 건너뛴 내용은 페이지 내 찾기와 탭 이동에서 평소처럼 쓸 수 있어야 합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 실험에서도 화면 밖 <code>주문 40000</code> 행의 텍스트가 DOM에 그대로 있었습니다. 서버가 HTML로 긴 글이나 섹션을 내려주는 페이지에 잘 맞는 이유입니다. web.dev의 여행 블로그 예제는 섹션 단위로 적용해 첫 렌더링 시간이 232ms에서 30ms가 됐다고 보고합니다.<sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup></p>
<h3 id="스크롤바가-커졌다-줄었다-합니다">스크롤바가 커졌다 줄었다 합니다</h3>
<p><strong>증상:</strong> 내려갈수록 스크롤바 크기와 위치가 바뀌고, 어느 지점에서 화면이 튑니다. <strong>원인:</strong> 크기 격리된 요소는 기본적으로 내용이 없는 것처럼 배치되므로, 블록 높이를 주지 않으면 높이가 0이 됩니다.<sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup> 추정값이 실제와 크게 다르면 렌더링 순간 다시 배치됩니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<p><strong>대응:</strong> 실제 행 높이에 가까운 값을 <code>auto</code>와 함께 줍니다. 크기가 제각각이면 가장 흔한 크기로 시작하되, <code>auto</code>가 기억한 크기를 쓰는 것은 한 번 렌더링된 뒤라는 점을 감안합니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<h2 id="가상-스크롤-보이는-행만-만듭니다">가상 스크롤: 보이는 행만 만듭니다</h2>
<figure><img src="/development-digest/figures/virtual-scroll-window.svg" alt="가상 스크롤의 spacer와 보이는 범위" loading="lazy"><figcaption>그림 1 · 높이는 전체만큼 빌리고, DOM은 보이는 범위만큼만 만든다</figcaption></figure>
<p>가상 스크롤은 전체 높이만큼 빈 상자를 깔고, 스크롤 위치로 계산한 범위의 행만 그 위에 절대 위치로 올립니다. 행 높이가 고정이면 범위 계산은 나눗셈 하나입니다.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">getRange</span>(<span class="hljs-params">{ scrollTop, viewportHeight, rowHeight, count, overscan }</span>) {
  <span class="hljs-keyword">const</span> first = <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">floor</span>(scrollTop / rowHeight);
  <span class="hljs-keyword">const</span> visible = <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">ceil</span>(viewportHeight / rowHeight);
  <span class="hljs-keyword">const</span> start = <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">max</span>(<span class="hljs-number">0</span>, first - overscan);
  <span class="hljs-keyword">const</span> end = <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">min</span>(count - <span class="hljs-number">1</span>, first + visible + overscan);
  <span class="hljs-keyword">return</span> { start, end };
}
</code></pre>
<p><code>overscan</code>은 빠르게 스크롤할 때 빈 칸이 보이지 않도록 위아래로 더 만드는 여유분입니다. 600px 높이, 48px 행, 여유분 5로 node에서 실행한 결과입니다.</p>
<pre data-lang="text"><code class="hljs language-text">고정 높이, 맨 위: { start: 0, end: 18 }

<p>스크롤 이벤트는 프레임보다 자주 올 수 있으므로 <code>requestAnimationFrame</code>으로 한 프레임에 한 번만 다시 그립니다. 각 행에는 전체에서의 위치와 개수를 ARIA 속성으로 적습니다.</p>

<p>첫 화면의 행은 19개였고, 다섯 번 모두 Long Task가 기록되지 않았습니다. 정렬 클릭은 배열을 뒤집고 보이는 행만 다시 만들기 때문에 처리기 시간이 2ms 이하였습니다. 다만 클릭 지연은 실행마다 0<del>112ms, 첫 렌더링은 13</del>125ms로 흔들렸습니다. 0은 16ms 문턱보다 짧아 항목이 남지 않은 경우입니다. 처리기가 거의 일을 하지 않으면 남은 값은 다음 프레임을 기다린 시간이 대부분이라, 이 차이는 구현보다 프레임 시점의 영향으로 봐야 합니다. CPU 4배 감속에서도 처리기 시간은 3ms 이하, 클릭 지연은 0~136ms였습니다.</p>
<h3 id="페이지-내-찾기로-화면-밖-행을-찾을-수-없습니다">페이지 내 찾기로 화면 밖 행을 찾을 수 없습니다</h3>
<p><strong>증상:</strong> 사용자가 브라우저 찾기로 주문 번호를 검색하면 결과가 없습니다. <strong>원인:</strong> 화면 밖 행은 DOM에 없습니다. 실험에서도 가상 스크롤 쪽에는 <code>주문 40000</code> 텍스트가 없었습니다. <strong>대응:</strong> 목록 위에 데이터 배열을 검색하는 입력을 두고, 찾은 행 번호로 <code>scrollTop</code>을 옮깁니다. 브라우저 찾기와 똑같이 동작한다고 기대하게 만들지 않습니다.</p>
<p>스크린 리더도 DOM에 있는 행만으로 개수를 셉니다. 일부 항목만 DOM에 있을 때 브라우저가 계산한 개수는 틀릴 수 있으므로, 각 항목에 <code>aria-setsize</code>로 전체 개수, <code>aria-posinset</code>으로 위치를 적습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 실험의 첫 행은 <code>aria-posinset="1"</code>, <code>aria-setsize="50000"</code>으로 나왔습니다.</p>
<h3 id="높이가-다른-행에서-위치가-어긋납니다">높이가 다른 행에서 위치가 어긋납니다</h3>
<p><strong>증상:</strong> 메모가 긴 행이 섞이면 스크롤할 때 행이 겹치거나 건너뜁니다. <strong>원인:</strong> 나눗셈 공식은 모든 행의 높이가 같다는 가정 위에 있습니다. <strong>대응:</strong> 행마다 위쪽 끝 위치를 누적해 두고, 스크롤 위치에 해당하는 행을 이진 탐색으로 찾습니다. 측정 전에는 추정 높이를 쓰고, 실제로 재면 누적값을 다시 계산합니다.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">buildOffsets</span>(<span class="hljs-params">heights</span>) {
  <span class="hljs-keyword">const</span> offsets = <span class="hljs-keyword">new</span> <span class="hljs-title class_">Array</span>(heights.<span class="hljs-property">length</span> + <span class="hljs-number">1</span>);
  offsets[<span class="hljs-number">0</span>] = <span class="hljs-number">0</span>;
  <span class="hljs-keyword">for</span> (<span class="hljs-keyword">let</span> i = <span class="hljs-number">0</span>; i &#x3C; heights.<span class="hljs-property">length</span>; i++) offsets[i + <span class="hljs-number">1</span>] = offsets[i] + heights[i];
  <span class="hljs-keyword">return</span> offsets; <span class="hljs-comment">// offsets[i] = i번째 행의 위쪽 끝, 마지막 값 = 전체 높이</span>
}
</code></pre>
<p>추정 48px로 시작했다가 3번 행을 재 보니 120px였다고 가정한 실행 결과입니다.</p>
<pre data-lang="text"><code class="hljs language-text">추정 전체 높이: 480 측정 후: 552
scrollTop 200의 첫 행 — 추정: 4 측정 후: 3
5번 행 위치 — 추정: 240 측정 후: 312
</code></pre>
<p>한 행의 측정이 그 아래 모든 행의 위치를 72px씩 밀었습니다. 사용자가 보고 있는 행 위쪽에서 이런 보정이 일어나면 화면이 튀므로, 보정량만큼 <code>scrollTop</code>도 함께 옮겨야 합니다.</p>
<h3 id="직접-만들까-라이브러리를-쓸까">직접 만들까, 라이브러리를 쓸까</h3>
<p>고정 높이·세로 한 방향이라면 직접 구현은 위 코드 정도로 끝납니다. 가변 높이 측정, 가로·격자, 위로 쌓이는 채팅까지 가면 라이브러리가 맡는 범위가 커집니다. 이 글의 측정에는 라이브러리를 넣지 않았고, 아래는 TanStack Virtual 문서를 기준으로 한 비교입니다.</p>
<p>TanStack Virtual은 마크업과 스타일을 제공하지 않는 헤드리스(headless) 도구이며, React·Vue·Svelte·Solid·Lit·Angular용 어댑터가 있습니다.<sup class="cite"><a href="#source-10" aria-label="출처 10">[10]</a></sup> 동적으로 크기를 잴 때는 <code>estimateSize</code>에 가능한 큰 추정값을 주고 <code>measureElement</code>로 실제 크기를 재도록 안내합니다.<sup class="cite"><a href="#source-11" aria-label="출처 11">[11]</a></sup> <code>overscan</code> 기본값은 1이며, 늘리면 렌더링 시간이 늘지만 빈 항목이 보일 가능성은 줄어듭니다.<sup class="cite"><a href="#source-11" aria-label="출처 11">[11]</a></sup> <code>getItemKey</code>의 기본값은 인덱스이므로 고유 ID를 돌려주도록 바꾸라고 권합니다.<sup class="cite"><a href="#source-11" aria-label="출처 11">[11]</a></sup> 채팅·로그처럼 위로 과거 항목이 붙는 목록에는 <code>anchorTo: 'end'</code>를 씁니다.<sup class="cite"><a href="#source-11" aria-label="출처 11">[11]</a></sup></p>
<p>직접 만든 코드는 이런 경우를 하나씩 다시 구현해야 합니다. 요구사항이 고정 높이 하나로 끝나지 않을 조짐이 보이면, 그때 라이브러리로 옮기는 편이 비용이 덜 듭니다.</p>
<h2 id="페이지네이션과-무한-스크롤">페이지네이션과 무한 스크롤</h2>
<p>5만 건을 한 번에 받는 것 자체가 늘 필요한 것은 아닙니다. 서버에서 나눠 받는다면 번호가 있는 페이지네이션과, 끝에 닿을 때 다음 묶음을 붙이는 무한 스크롤 중 하나를 고르게 됩니다. 페이지네이션은 "3페이지의 5번째"처럼 위치를 주소로 남기고 공유하기 쉽습니다. 무한 스크롤은 훑어보기에 편하지만, 목록 아래 바닥글에 닿기 어렵고 뒤로 가기 후 위치 복원을 직접 챙겨야 합니다.</p>
<p>무한 스크롤로 만든 목록에서 누적된 행이 많아지면 결국 앞의 가상 스크롤이 다시 필요합니다. 두 문제는 서로 다른 층입니다. 받아 오는 방식은 서버 부담과 데이터 일관성을, 그리는 방식은 브라우저 부담을 정합니다.</p>
<h3 id="다음-묶음에-같은-주문이-또-나옵니다">다음 묶음에 같은 주문이 또 나옵니다</h3>
<p><strong>증상:</strong> 최신순 목록을 내리다 보면 방금 본 주문이 다음 묶음에 다시 나옵니다. <strong>원인:</strong> 첫 묶음을 받은 뒤 새 주문이 맨 앞에 들어오면, 건너뛸 개수(offset)로 자른 다음 묶음은 그만큼 밀립니다. node로 재현한 결과입니다.</p>

<h3 id="스크린-리더가-끝없는-목록에서-길을-잃습니다">스크린 리더가 끝없는 목록에서 길을 잃습니다</h3>
<p>ARIA의 <code>feed</code> 역할은 스크롤하면서 항목이 앞이나 뒤에 붙는 목록을 위한 패턴입니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 항목은 포커스를 받을 수 있어야 하고, 항목을 붙이는 동안에는 컨테이너에 <code>aria-busy="true"</code>를 두었다가 끝나면 되돌립니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 전체 개수를 모르거나 자주 바뀌면 <code>aria-setsize="-1"</code>을 씁니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> Page Down·Page Up으로 항목 사이를 옮기는 키보드 동작도 페이지 코드가 구현할 몫입니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
