정렬 한 번에 1초 멈추는 5만 행 목록, 무엇부터 고칠까

5만 행 주문 목록이 클릭 한 번에 1초 가까이 멈추는 장면에서 출발해, 원인이 그리기가 아니라 노드를 만드는 데 있음을 확인하고 content-visibility와 가상 스크롤 중 무엇을 고를지, 고른 대가로 무엇을 직접 챙겨야 하는지 정리합니다.

정렬 버튼을 눌렀는데 화면이 1초 가까이 멈춥니다

관리자 화면에서 주문 5만 건을 한 페이지에 보여 주는 목록을 맡았다고 가정해 봅시다. 실제 서비스 수치가 아니라, 방식을 비교하려고 정한 조건입니다. 행 높이는 48px로 같고, 위에는 최신순과 오래된순을 바꾸는 버튼 하나가 있습니다.

가장 단순하게, 5만 행을 한꺼번에 화면에 넣어 봤습니다. 아래 녹화의 위쪽 막대는 브라우저가 화면을 새로 그린 기록입니다. 막대가 낮고 고르면 화면이 매끄럽게 움직이고 있다는 뜻이고, 한 칸이 높이 솟으면 그 시간 동안 화면이 멈춰 있었다는 뜻입니다.

정렬 버튼을 누른 뒤 화면이 바뀌기까지 916ms가 걸렸습니다. 사용자 입장에서는 버튼이 눌리지 않은 것처럼 보이다가, 1초쯤 뒤에 목록이 갑자기 뒤집힙니다.

이 글은 이 멈춤에서 출발해 두 가지를 판단할 수 있게 하는 것이 목표입니다.

  • 멈춤의 원인이 어디에 있는지 개발자 도구와 숫자로 짚는 법
  • 흔히 거론되는 두 해법, CSS 속성 content-visibility와 가상 스크롤(virtual scrolling) 중 무엇을 고르고, 고른 대가로 무엇을 직접 챙겨야 하는지

왜 멈추는가: 그리는 일보다 만드는 일이 무겁습니다

개발자 도구로 먼저 봅니다

크롬 개발자 도구(F12)의 성능 탭에서 녹화 버튼(●)을 누르고, 정렬 버튼을 한 번 클릭한 뒤 녹화를 멈추면 그 사이에 브라우저가 한 일이 시간 순서대로 펼쳐집니다.

읽는 순서는 이렇습니다.

  1. 기본 트랙 맨 위의 빨간 빗금 막대가 하나의 작업입니다. 빗금은 브라우저가 "이 작업이 너무 길다"고 표시한 것입니다.
  2. 그 아래 이벤트: click부터 render → renderAll → replaceChildren으로 내려가는 막대는, 클릭이 어떤 함수를 거쳐 어디서 시간을 썼는지 보여 줍니다. 막대가 넓을수록 오래 걸린 함수입니다.
  3. 오른쪽 끝의 보라색 레이아웃은 새로 만든 행들의 위치와 크기를 계산하는 시간입니다.

녹화 중에는 기록하는 일 자체가 부담이 돼서 시간이 평소보다 길게 잡힙니다. 그래서 성능 탭에서는 정확한 ms보다 어느 막대가 넓은지를 봅니다. 이 녹화에서는 클릭 처리 시간 대부분이 renderAll 안에서 행을 만드는 데 들어갔습니다.

같은 기록을 코드로 모으기

개발자 도구는 내 컴퓨터에서만 볼 수 있습니다. 여러 번 재서 비교하거나 실제 사용자에게서 모으려면 같은 기록을 코드로 받아야 합니다.

브라우저는 오래 걸린 작업과 늦게 반응한 클릭을 스스로 기록해 둡니다. 이 기록을 받으려면 PerformanceObserver라는 관찰 객체를 만들고, observe()로 어떤 종류를 받을지 알려 주면 됩니다.[7] 기록이 생길 때마다 넘겨준 함수가 불립니다.

  • 종류를 "longtask"로 주면 메인 스레드를 50ms 이상 붙잡은 작업이 하나씩 들어옵니다(PerformanceLongTaskTiming 객체).[1] 페이지가 열리는 동안 쌓인 기록까지 받으려면 buffered: true를 함께 줍니다.[1]
  • 종류를 "event"로 주면 클릭 같은 입력이 얼마나 늦게 처리됐는지가 들어옵니다(PerformanceEventTiming 객체).[7]
new PerformanceObserver((l) => {
  for (const e of l.getEntries()) metrics.longtasks.push({ start: e.startTime, duration: e.duration });
}).observe({ type: "longtask", buffered: true });
new PerformanceObserver((l) => {
  for (const e of l.getEntries()) {
    metrics.events.push({
      name: e.name, interactionId: e.interactionId, duration: e.duration,
      delay: e.processingStart - e.startTime, handler: e.processingEnd - e.processingStart,
    });
  }
}).observe({ type: "event", durationThreshold: 16, buffered: true });

두 번째 관찰자에서 뽑는 값은 두 가지입니다. processingStart - startTime은 클릭 후 처리 함수가 시작되기까지 기다린 시간, processingEnd - processingStart는 처리 함수가 실행된 시간입니다.[7] 클릭 기록은 기본적으로 104ms 이상 걸린 것만 들어오고, durationThreshold로 16ms까지 낮출 수 있습니다.[7] 빠른 방식의 클릭도 놓치지 않으려고 16을 넣었습니다.

메인 스레드는 한 번에 작업 하나만 처리합니다.[6] 그래서 긴 작업이 도는 동안에는 클릭에 대한 반응도 줄을 서서 기다립니다. 녹화에서 막대가 솟은 구간이 바로 이 시간입니다.

PerformanceLongTaskTiming은 MDN에서 실험적·비표준 기능으로 표시되어 있어, 지원하지 않는 브라우저에서는 기록이 비어 있을 수 있습니다.[1] 실제 사용자에게서는 같은 문제를 INP(Interaction to Next Paint)라는 지표로 봅니다. 방문하는 동안의 클릭·탭·키 입력 지연 가운데 이상치를 빼고 가장 긴 값을 대표값으로 쓰며, 200ms 이하를 좋음으로 봅니다.[2] 이 글의 숫자는 제가 스크립트로 한 번 누른 값이라 INP 점수는 아닙니다. 방식끼리 비교하는 용도로만 읽어 주세요.

5만 행이면 요소가 35만 개입니다

아래 숫자들은 제 크롬 브라우저에서 잰 값입니다. 방식마다 다섯 번씩 재서, 한 번 튄 값에 휘둘리지 않도록 가운데 값을 적었습니다. 컴퓨터와 브라우저가 다르면 숫자도 달라지니, 방식끼리 비교하는 용도로 봐 주세요.

행 하나는 div 안에 span이 세 개라서, 5만 행이면 문서 전체의 요소(노드)가 35만 개를 넘습니다.

방식          첫 렌더링  DOM 노드  레이아웃  스타일  가장 긴 작업  정렬 클릭
전체 렌더링    807ms    350,020   345ms    76ms    799ms       808ms

정렬 클릭의 처리 함수만 329ms를 썼습니다. 배열을 뒤집는 데는 거의 시간이 들지 않으니, 나머지는 요소 35만 개를 지우고 다시 만드는 비용입니다. 성능 탭에서 renderAll이 넓었던 것과 같은 이야기입니다. 그 뒤 위치 계산(레이아웃)과 그리기가 이어지면서 화면이 바뀌기까지 800ms가 넘게 걸렸습니다.

해법은 두 방향입니다. 요소는 그대로 두고 화면 밖을 그리지 않게 하거나, 아예 보이는 행만 만들거나입니다. 앞쪽부터 해 보겠습니다.

첫 번째 시도: CSS 한 줄로 화면 밖을 건너뛰기

CSS에는 "지금 화면에 보이지 않는 부분은 그리는 일을 미뤄도 된다"고 알려 주는 속성이 있습니다. content-visibility: auto입니다. 이 속성을 받은 요소는 안쪽 내용을 바깥과 분리해 계산하고, 사용자와 관련이 없을 때(화면 밖에 있을 때)는 내용의 렌더링을 건너뜁니다.[3]

다만 건너뛴 행은 크기도 계산하지 않으니, 그 자리를 지킬 예상 크기를 따로 알려 줘야 합니다. 그 역할을 하는 속성이 contain-intrinsic-size입니다. 값에 auto 48px처럼 auto를 붙이면, 한 번이라도 실제로 그려진 행은 그때의 크기를 기억해 쓰고, 아직 그려진 적 없는 행만 48px로 둡니다.[8]

.cv .row { content-visibility: auto; contain-intrinsic-size: auto 48px; }

같은 목록에 이 한 줄만 더해 녹화했습니다.

처음 그릴 때의 위치 계산(레이아웃) 시간은 345ms에서 45ms로 줄었습니다. 그런데 녹화에서 보이듯 두 가지는 나아지지 않았습니다.

첫째, 정렬 클릭이 여전히 느립니다. 처리 함수 시간은 319ms로 전체 렌더링의 329ms와 거의 같았습니다. 요소를 만드는 일은 자바스크립트가 하는 일이라, CSS가 건너뛸 수 있는 단계가 아니기 때문입니다.

둘째, 이 실험에서는 스크롤할 때 오히려 끊김이 생겼습니다. 같은 휠 스크롤을 세 번씩 반복해 화면 갱신 간격을 쟀더니, 전체 렌더링과 가상 스크롤은 모든 갱신이 33ms 안에 끝났습니다. content-visibility는 40번 가운데 30~34번이 50ms를 넘었습니다. 화면에 새로 들어오는 행마다 미뤄 두었던 렌더링을 그 자리에서 하기 때문으로 보입니다. 기기와 브라우저에 따라 다를 수 있으니, 도입하기 전에 실제 목록에서 같은 방법으로 재 보는 편이 안전합니다.

증상내려갈수록 스크롤바 길이가 바뀌고 화면이 튄다

크기 계산을 건너뛴 요소는 높이를 따로 주지 않으면 높이가 0인 것처럼 배치되고, 예상 크기가 실제와 다르면 그려지는 순간 자리가 다시 잡힙니다.[9][8] 실제 행 높이에 가까운 값을 auto와 함께 줍니다.

그렇다고 쓸모없는 속성은 아닙니다. 건너뛴 내용도 문서에는 그대로 남아 있어서, 페이지 내 찾기(Ctrl+F)와 Tab 키 이동은 평소처럼 동작해야 합니다.[3] 서버가 HTML로 내려주는 긴 글이나 섹션 목록이 여기에 맞습니다. web.dev의 여행 블로그 예제는 섹션 단위로 적용해 첫 렌더링 시간이 232ms에서 30ms가 됐다고 보고합니다.[9] 자바스크립트로 수만 개의 요소를 만드는 목록에는 맞지 않을 뿐입니다.

결국 만드는 요소의 수 자체를 줄여야 합니다.

두 번째 시도: 보이는 행만 만들기

가상 스크롤은 목록 전체 높이만큼 빈 상자를 깔아 스크롤바를 실제처럼 만들어 두고, 지금 스크롤 위치에서 보이는 행만 골라 그 위에 올려놓는 방식입니다. 나머지 행은 데이터 배열에만 있고 화면에는 없습니다.

먼저 결과부터 보겠습니다.

문서에 있는 행은 22개였고, 정렬 클릭은 14ms 만에 화면에 반영됐습니다. 다섯 번 재는 동안 긴 작업은 한 번도 기록되지 않았습니다. 성능 탭으로 같은 클릭을 녹화해도 막대가 거의 보이지 않습니다.

방식          첫 렌더링  DOM 노드  레이아웃  스타일  가장 긴 작업  정렬 클릭
가상 스크롤     81ms       337     11ms     1ms    (없음)       56ms

표의 정렬 클릭 56ms는 다섯 번의 가운데 값이고, 처리 함수 시간은 2ms 이하였습니다. 클릭 지연은 실행마다 0~112ms로 흔들렸는데, 처리 함수가 거의 일을 하지 않으니 남은 값은 대부분 다음 화면 갱신을 기다린 시간입니다.

어느 행부터 보이는지는 나눗셈 하나로 구합니다

행 높이가 모두 같다면, 스크롤한 거리를 행 높이로 나누면 맨 위에 보이는 행의 번호가 나옵니다.

export function getRange({ scrollTop, viewportHeight, rowHeight, count, overscan }) {
  const first = Math.floor(scrollTop / rowHeight);
  const visible = Math.ceil(viewportHeight / rowHeight);
  const start = Math.max(0, first - overscan);
  const end = Math.min(count - 1, first + visible + overscan);
  return { start, end };
}

overscan은 빠르게 스크롤할 때 빈 칸이 보이지 않도록 위아래로 몇 행 더 만들어 두는 여유분입니다. 600px 높이, 48px 행, 여유분 5로 실행한 결과입니다.

고정 높이, 맨 위: { start: 0, end: 18 }
고정 높이, 중간: { start: 9995, end: 10018 }
고정 높이, 끝: { start: 49982, end: 49999 }

스크롤 이벤트는 화면이 한 번 갱신되는 사이에도 여러 번 올 수 있습니다. 그래서 requestAnimationFrame(다음 화면 갱신 직전에 함수를 한 번 실행해 주는 브라우저 함수)으로 갱신마다 한 번만 다시 그립니다.

  container.addEventListener("scroll", () => {
    if (!frame) frame = requestAnimationFrame(paint);
  }, { passive: true });

각 행에는 위치와 함께 접근성 속성 두 개를 적습니다. 이 두 줄이 필요한 이유는 바로 아래에서 다룹니다.

      row.style.transform = `translateY(${i * rowHeight}px)`;
      row.setAttribute("aria-posinset", String(i + 1));
      row.setAttribute("aria-setsize", String(items.length));

대신 잃는 것: 화면 밖 행은 문서에 없습니다

빨라진 대가는 분명합니다. 사용자가 Ctrl+F로 주문 40000을 찾으면 결과가 없습니다. 그 행이 문서에 아예 없기 때문입니다. 실험에서도 가상 스크롤 쪽 문서에는 그 글자가 없었습니다. 목록 위에 데이터 배열을 검색하는 입력창을 두고, 찾은 행 번호로 스크롤 위치(scrollTop)를 옮기는 식으로 대신해야 합니다.

스크린 리더도 문서에 있는 행만 보고 개수를 셉니다. 그래서 각 행에 전체 개수와 자기 순서를 직접 적어 줍니다. aria-setsize는 전체 개수, aria-posinset은 그 안에서 몇 번째인지입니다. 일부 항목만 문서에 있을 때 쓰라고 만든 속성입니다.[4] 실험의 첫 행에는 aria-posinset="1", aria-setsize="50000"이 붙었습니다.

행 높이가 제각각이면 나눗셈이 깨집니다

메모가 긴 행이 섞이면 나눗셈 공식은 쓸 수 없습니다. 이때는 행마다 위쪽 끝이 몇 px에 있는지 누적해서 표로 만들어 두고, 스크롤 위치에 해당하는 행을 그 표에서 찾습니다.

export function buildOffsets(heights) {
  const offsets = new Array(heights.length + 1);
  offsets[0] = 0;
  for (let i = 0; i < heights.length; i++) offsets[i + 1] = offsets[i] + heights[i];
  return offsets; // offsets[i] = i번째 행의 위쪽 끝, 마지막 값 = 전체 높이
}

처음에는 모든 행을 48px로 짐작해 두었다가, 3번 행을 실제로 재 보니 120px였다고 가정하면 이렇게 바뀝니다.

추정 전체 높이: 480 측정 후: 552
scrollTop 200의 첫 행 — 추정: 4 측정 후: 3
5번 행 위치 — 추정: 240 측정 후: 312

한 행을 잰 결과가 그 아래 모든 행을 72px씩 밀었습니다. 사용자가 보고 있는 행보다 위에서 이런 보정이 일어나면 화면이 튀므로, 밀린 만큼 스크롤 위치도 함께 옮겨야 합니다.

여기까지 오면 직접 만들 일이 많아집니다. 이런 계산만 맡아 주는 라이브러리로 TanStack Virtual이 있습니다. 화면 모양(마크업·스타일)은 건드리지 않고 계산만 하며, React·Vue·Svelte·Solid·Lit·Angular에서 쓸 수 있습니다.[10] 높이를 재야 하는 목록이라면 estimateSize에 넉넉한 예상 크기를 주고 measureElement로 실제 크기를 재도록 안내하고, 채팅처럼 위로 과거 메시지가 붙는 목록에는 anchorTo: 'end'를 씁니다.[11] 행 높이가 고정 하나로 끝나지 않을 조짐이 보이면, 그때 라이브러리로 옮기는 편이 비용이 덜 듭니다.

그런데 5만 건을 꼭 한 번에 받아야 할까요

지금까지는 그리는 방식을 바꿨습니다. 한 걸음 물러나면, 5만 건을 한 번에 받는 것 자체가 늘 필요한 것은 아닙니다. 서버에서 나눠 받는다면 번호가 있는 페이지네이션이나, 목록 끝에 닿을 때 다음 묶음을 붙이는 무한 스크롤을 고르게 됩니다.

무한 스크롤에는 흔한 함정이 하나 있습니다. 최신순 목록을 내리다 보면 방금 본 주문이 다음 묶음에 또 나옵니다. 첫 묶음을 받은 뒤 새 주문이 맨 앞에 들어오면, "앞에서 몇 개를 건너뛰고(offset) 몇 개를 달라"는 요청이 그만큼 밀리기 때문입니다. 작은 배열로 재현한 결과입니다.

function pageByOffset(offset, limit) {
  return orders.slice(offset, offset + limit).map((o) => o.id);
}
function pageByCursor(beforeId, limit) {
  return orders.filter((o) => beforeId === null || o.id < beforeId).slice(0, limit).map((o) => o.id);
}

첫 묶음: [ 100, 99, 98, 97 ]
offset=4 다음 묶음: [ 98, 97, 96, 95 ]
cursor<97 다음 묶음: [ 96, 95, 94, 93 ]

"몇 개 건너뛰기" 대신 "마지막으로 받은 97번보다 뒤"를 요청하면(커서 방식) 새 주문이 끼어도 밀리지 않습니다. 끝없이 붙는 목록이라면 접근성 역할 feed를 쓰고, 항목을 붙이는 동안 목록에 aria-busy="true"를 두었다가 끝나면 되돌립니다.[5]

받아 오는 방식과 그리는 방식은 다른 층의 문제입니다. 무한 스크롤로 받아도 쌓인 행이 수천 개를 넘으면 결국 앞의 가상 스크롤이 다시 필요합니다.

정리

처음의 1초 멈춤은 화면을 그리는 비용보다 요소 35만 개를 만드는 비용에서 왔습니다. 그래서 그리기만 줄이는 CSS로는 클릭이 빨라지지 않았고, 만드는 행 수를 줄인 가상 스크롤에서야 해결됐습니다. 대신 화면 밖 행이 문서에서 사라지는 만큼, 검색과 접근성은 직접 채워야 합니다.

  • 서버가 HTML로 내려준 긴 문서나 섹션 목록이라면 content-visibility를 고릅니다. 검색과 접근성을 그대로 두고 첫 렌더링을 줄입니다.
  • 수천 행 이상을 자바스크립트로 만들고 정렬·필터가 잦다면 가상 스크롤을 고릅니다. 목록 안 검색 입력과 aria-setsize·aria-posinset을 완료 조건에 넣습니다.
  • 행 높이가 제각각이거나 위로 쌓이는 채팅이라면 라이브러리를 고릅니다. 높이 측정·보정·위치 고정을 다시 만드는 비용이 큽니다.
  • 위치를 기억하고 공유해야 한다면 페이지네이션을, 훑어보기가 중심이면 커서 방식 무한 스크롤을 고릅니다.

어느 쪽이든 바꾸기 전에 성능 탭으로 지금 목록의 클릭을 한 번 녹화해 두면, 바꾼 뒤 어느 막대가 사라졌는지 눈으로 비교할 수 있습니다.

프론트엔드 팀이 해 볼 것

  1. 가장 긴 목록 화면에 longtask와 event 관찰자를 붙이고, 정렬·필터 클릭의 처리기 시간을 기록합니다.
  2. 목록 API가 offset으로 다음 묶음을 받는다면, 첫 묶음 뒤에 항목을 하나 추가해 중복이 생기는지 시험합니다.
  3. 가상 스크롤을 쓰는 화면에서 브라우저 찾기와 스크린 리더로 전체 개수가 어떻게 안내되는지 확인합니다.
