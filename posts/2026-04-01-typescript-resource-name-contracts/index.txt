18:T5c37,<h2 id="경로는-문자열이-아니라-식별-규칙입니다">경로는 문자열이 아니라 식별 규칙입니다</h2>
<p>같은 청구서를 가리키는데 화면에서는 ID만 넘기고, 댓글 서비스에서는 조직 경로까지 붙이며, 다른 코드에서는 서비스 도메인을 직접 덧붙인다고 가정해 봅시다. 문제는 문자열 보간 문법 자체가 아닙니다. 무엇을 어디까지 포함해야 같은 대상을 뜻하는지 호출자가 매번 판단한다는 점입니다.</p>
<p>Robin Wieruch는 여러 서비스가 있는 모노레포에서 이름 변경이 다른 서비스의 문자열 조립 코드를 깨뜨렸다고 회고합니다. 코드 리뷰를 늘리기보다 공통 명명 규칙을 정하는 편이 낫다는 것이 원문 필자의 판단입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 여기서는 폴더를 기능별로 나누는 방법 대신, 서비스 사이에서 전달하는 식별자 계약에 집중합니다.</p>
<h3 id="개별-대상과-대상의-종류를-구분합니다">개별 대상과 대상의 종류를 구분합니다</h3>
<p>리소스 이름(resource name)은 특정 대상을 식별합니다. Google AIP-122는 컬렉션 이름과 리소스 ID를 번갈아 배치하고, 경로 조각을 슬래시로 나누는 형태를 제시합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 원문은 여기에 리소스 타입(resource type)을 구분해, 개별 청구서와 청구서라는 종류를 따로 표현합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-keyword">const</span> relativeName = <span class="hljs-string">"organizations/acme/invoices/april"</span>;
<span class="hljs-keyword">const</span> fullName =
  <span class="hljs-string">"//billing.acmeapis.com/organizations/acme/invoices/april"</span>;
<span class="hljs-keyword">const</span> invoiceType = <span class="hljs-string">"billing.acmeapis.com/Invoice"</span>;

<span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(relativeName); <span class="hljs-comment">// organizations/acme/invoices/april</span>
<span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(invoiceType); <span class="hljs-comment">// billing.acmeapis.com/Invoice</span>
</code></pre>
<p>첫 값은 서비스 안에서 쓰는 상대 이름입니다. 둘째는 소유 서비스까지 표시하는 전체 이름이고, 마지막은 특정 청구서가 아닌 종류를 나타냅니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup><sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 예제의 도메인과 ID는 설명용입니다. 서비스 도메인, 컬렉션, 타입의 철자까지 각 화면에서 직접 쓰지 않도록 만드는 것이 목표입니다.</p>
<p>이 구분을 놓치면 댓글의 연결 대상을 저장할 때 타입 문자열만으로 충분하다고 생각하기 쉽습니다. 원문은 댓글에 <code>resourceType</code>과 <code>resource</code>를 따로 두는 예를 제시합니다. 전자는 청구서에 달린 댓글 전체를 고르고, 후자는 특정 청구서의 댓글을 찾는 데 쓰입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h2 id="타입으로-제한할-것과-검증할-것을-나눕니다">타입으로 제한할 것과 검증할 것을 나눕니다</h2>
<h3 id="서비스-이름과-경로-모양을-좁힙니다">서비스 이름과 경로 모양을 좁힙니다</h3>
<p>원문은 <code>ServiceName</code>을 문자열 유니온으로 제한하고, 도메인 접미사는 공유 상수로 관리하자고 제안합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 템플릿 리터럴 타입(template literal type)은 타입 위치에서 문자열 조각을 결합할 수 있으므로, 이 원칙을 경로의 고정 부분까지 확장할 수 있습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 다음은 원문의 구현을 복사한 것이 아니라 공식 문법을 적용한 최소 예제입니다.</p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-keyword">type</span> <span class="hljs-title class_">ServiceName</span> =

<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-keyword">const</span> <span class="hljs-attr">emptyId</span>: <span class="hljs-title class_">InvoicePath</span> = <span class="hljs-string">"organizations//invoices/april"</span>;

<p>공식 Handbook의 템플릿 리터럴 타입 예제도 이벤트 이름처럼 문자열 조합의 제약을 타입으로 표현합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 여기서 얻는 것은 정적 코드의 모양 검사입니다. 빈 ID나 추가 경로 조각까지 막으려면 별도로 입력을 검사해야 합니다.</p>
<h3 id="검증된-이름에는-별도-표식을-붙입니다">검증된 이름에는 별도 표식을 붙입니다</h3>
<p>브랜드 타입(branded type)은 원문의 코드에 나오지 않습니다. 이 글에서는 TypeScript 공식 Playground의 명목적 타이핑 예제를 보완해서 사용합니다. 공식 예제는 문자열과 <code>__brand</code> 속성을 교차시켜 일반 문자열을 그대로 대입하지 못하게 만들고, 타입에게 유효하다고 알려 주는 것과 실제 검증을 구분합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-keyword">type</span> <span class="hljs-title class_">InvoiceName</span> = <span class="hljs-title class_">InvoicePath</span> &#x26; {

<h2 id="빌더와-파서가-같은-규칙을-쓰게-합니다">빌더와 파서가 같은 규칙을 쓰게 합니다</h2>
<p>원문은 ID 묶음을 이름으로 바꾸는 <code>encodeResourceId</code>와, 이름에서 ID를 꺼내는 <code>decodeResourceId</code>의 호출 예를 보여 주지만 구현 본문은 싣지 않습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 아래는 같은 분리를 청구서 경로에 한정해 직접 구현한 예제이며, 원문 유틸리티와 같은 API는 아닙니다.</p>
<h3 id="파서는-구조와-id를-함께-검사합니다">파서는 구조와 ID를 함께 검사합니다</h3>
<p>파서(parser)는 외부 문자열을 받아 규칙에 맞는지 검사한 뒤 사용할 구조로 바꾸는 함수입니다. 여기서는 실패하면 <code>null</code>, 성공하면 브랜드가 붙은 이름과 ID 묶음을 반환하게 합니다. <code>RegExp.prototype.test()</code>는 패턴이 일치하면 <code>true</code>, 아니면 <code>false</code>를 반환합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>

<h3 id="빌더는-검증을-우회하지-않습니다">빌더는 검증을 우회하지 않습니다</h3>

<h2 id="서비스-경계를-넘을-때만-전체-이름을-씁니다">서비스 경계를 넘을 때만 전체 이름을 씁니다</h2>
<h3 id="전체-이름은-요청-url이-아닙니다">전체 이름은 요청 URL이 아닙니다</h3>
<p>AIP-122는 소유 API가 모호할 수 있는 참조에 전체 이름을 쓰도록 설명합니다. 서비스가 다르다는 이유만으로 항상 전체 이름을 붙이라는 뜻은 아닙니다. 소유 API가 명확한 참조에는 전체 이름을 쓰지 말라는 주의도 있습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<p>다음 함수는 앞에서 검증한 청구서 이름을 청구 서비스의 전체 이름으로 바꾸는 최소 예제입니다. <code>ServiceName</code>이면 무엇이든 받게 하지 않고, 청구서의 소유 서비스를 함수 안에 고정합니다.</p>

<p>전체 이름에는 프로토콜이나 API 버전을 넣지 않습니다. AIP-122는 전체 이름과 실제 요청 URI를 구분하고, 서비스의 접속 주소가 여러 개여도 전체 이름은 달라지지 않는다고 설명합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 따라서 이 문자열 앞에 프로토콜만 붙여 요청 주소로 사용하지 마세요. 어느 클라이언트와 접속 주소로 요청할지는 별도 문제입니다.</p>
<h3 id="상대-이름을-받던-코드의-계약도-확인합니다">상대 이름을 받던 코드의 계약도 확인합니다</h3>
