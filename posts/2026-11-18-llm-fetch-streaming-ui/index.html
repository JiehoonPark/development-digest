LLM 답변이 흐르는 동안 — fetch 스트림 UI의 경계 처리

답변을 조각으로 받는 것과 읽기 편하게 보여 주는 것은 다른 문제입니다. 한글 디코딩부터 중단, 중간 에러, 자동 스크롤과 미완성 마크다운까지 가짜 토큰 서버의 재현 기록을 바탕으로 구현 기준을 정리합니다.

LLM 답변 화면을 맡았다고 가정해 봅시다

문서 도우미의 답변 화면입니다. 아래는 실제 서비스 수치가 아니라 방법을 고르기 위한 가정입니다.

  • 질문을 본문에 담아 보내고, 도착한 답변부터 보여 줍니다.
  • 중단을 누르면 받은 글은 남기고, 서버의 생성 작업도 취소하도록 연결합니다.
  • 사용자가 위로 올려 읽는 동안에는 화면을 아래로 끌어내리지 않습니다.
  • 마크다운이 덜 도착해도 읽을 수 있게 표시합니다.
  • 도중에 실패하면 완료와 구별하고, 읽던 답변을 지우지 않습니다.

브라우저와 애플리케이션 서버 사이만 다룹니다. 실행 결과와 화면은 고정 답변을 잘라 보내는 가짜 토큰 서버의 기존 재현 기록입니다. 코드는 그 구현을 재구성했으며, 유료 모델의 속도나 과금 특성을 검증한 결과는 아닙니다.

fetch()의 응답에는 본문을 읽을 수 있는 ReadableStream이 있고, getReader()로 얻은 읽개(reader)의 read()를 반복해 조각을 받습니다.[1][6] 생성이 끝나기 전부터 읽을 기회를 주는 방식입니다.

예제 서버에 stream: false를 보내면 완성된 답변을 JSON으로 돌려줍니다. 요청의 method, headers, body와 응답의 json()은 Fetch 문서의 방식입니다.[7]

async function receiveOnce() {
  const response = await fetch("/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ stream: false }),
  });
  if (!response.ok) throw new Error("요청 실패");
  return (await response.json()).text;
}

기존 로컬 실행에서 한 번에 받기는 완료 후에야 표시됐습니다. 스트리밍은 먼저 글자가 왔지만 전체 완료까지 빨라지지는 않았습니다. 첫 표시와 전체 완료는 따로 측정해야 합니다.

바이트와 이벤트의 경계는 다릅니다

서버 전송 이벤트(Server-Sent Events, SSE)는 text/event-stream 형식의 텍스트이며, 메시지를 빈 줄로 구분합니다.[3] event는 이벤트 종류, data는 내용이고, 여러 데이터 줄은 개행으로 이어 붙입니다.[3] delta, error, done은 예제 서버의 계약입니다.

글자는 온전해도 JSON이 덜 왔을 수 있고, 이벤트가 끝나도 마크다운은 미완성일 수 있습니다. 각 경계에서 남은 조각을 보관해야 합니다.

한글이 가끔 깨진다면 디코더의 상태부터 봅니다

예제 서버에서 바이트 중간을 나눠 보내자 답변에 �가 섞였습니다. 조각마다 디코딩을 끝내면 다음 조각의 바이트와 합칠 기회를 잃습니다.

TextDecoder의 decode()는 stream을 true로 지정하면 이후 호출에 데이터가 더 온다는 뜻으로 처리합니다.[8] 같은 디코더를 유지하고, 마지막에는 입력 없이 호출해 남은 내용을 마무리합니다.[8]

async function decodeText(body) {
  const reader = body.getReader();
  const decoder = new TextDecoder();
  let text = "";
  try {
    while (true) {
      const { value, done } = await reader.read();
      if (done) break;
      text += decoder.decode(value, { stream: true });
    }
    return text + decoder.decode();
  } finally {
    reader.releaseLock();
  }
}

기존 비교 실행의 앞부분입니다.

독립 디코딩: "## debounce�� throttle\n\n둘 다 **���무 자주 실�"
연속 디코딩: "## debounce와 throttle\n\n둘 다 **너무 자주 실행되는 "

이후 예제에서는 TextDecoderStream을 사용합니다. 이 객체는 바이너리 텍스트 스트림을 문자열 스트림으로 바꾸며 pipeThrough()에 연결할 수 있습니다.[2]

다음 파서는 서버가 LF 줄 끝을 보내기로 한 예제 전용입니다. 빈 줄을 아직 만나지 못한 문자열은 버퍼에 남기고, 완성된 이벤트만 소비자에게 넘깁니다.

async function* sseEvents(body) {
  const decoded = body.pipeThrough(new TextDecoderStream());
  const reader = decoded.getReader();
  let buffer = "";
  try {
    while (true) {
      const { value, done } = await reader.read();
      if (done) break;
      buffer += value;
      let cut;
      while ((cut = buffer.indexOf("\n\n")) !== -1) {
        const block = buffer.slice(0, cut);
        buffer = buffer.slice(cut + 2);
        let event = "message";
        const data = [];
        for (const line of block.split("\n")) {
          if (line.startsWith(":")) continue;
          if (line.startsWith("event:")) {
            event = line.slice(6).replace(/^ /, "");
          }
          if (line.startsWith("data:")) {
            data.push(line.slice(5).replace(/^ /, ""));
          }
        }
        if (data.length) yield { event, data: data.join("\n") };
      }
    }
  } finally {
    await reader.cancel().catch(() => {});
    reader.releaseLock();
  }
}

표준은 LF뿐 아니라 CRLF와 CR 줄 끝도 허용합니다.[9] 재연결이나 마지막 이벤트 식별자도 관리하지 않는 예제입니다. 외부 서버를 받는 제품에서는 줄 끝, 주석, 여러 데이터 줄, 잘린 메시지를 검증한 파서를 사용합니다.

읽개를 붙이면 스트림이 잠기므로 다른 읽개를 동시에 붙일 수 없습니다.[1] 중간 종료 시에도 읽기 취소와 잠금 해제를 정리합니다.

연결 종료와 답변 완료를 구별합니다

전송 함수는 onDelta로 문자열을 전달하고 정상 완료만 반환합니다. 화면은 종료 이유를 표시하되 받은 텍스트를 지우지 않습니다.

async function receiveAnswer({ signal, onDelta, fault = "none" }) {
  const response = await fetch("/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ fault }),
    signal,
  });
  if (!response.ok) throw new Error("요청이 거절됐습니다");
  if (!response.body) throw new Error("응답 본문이 없습니다");

  for await (const event of sseEvents(response.body)) {
    if (event.event === "done") return;
    if (event.event === "error") {
      const data = JSON.parse(event.data);
      throw new Error(data.error.message);
    }
    if (event.event === "delta") {
      onDelta(JSON.parse(event.data).text);
    }
  }
  throw new Error("완료 표시 없이 연결이 끝났습니다");
}

비동기 반복은 앞서 만든 생성자를 순회합니다. 스트림은 파서 안에서 읽습니다. 모르는 이벤트는 무시하고 완료 이벤트에서 반환합니다.

중단했는데 계속 생성된다면 서버 쪽 연결을 확인합니다

AbortController의 abort()는 요청뿐 아니라 응답 본문의 소비도 중단할 수 있습니다.[4] AbortSignal은 중단한 뒤 재사용할 수 없으며, 그 신호를 넘긴 다음 요청은 즉시 거절됩니다.[5] 요청마다 새 컨트롤러를 만듭니다.

function startAnswer(onDelta, onStatus) {
  const controller = new AbortController();
  const finished = receiveAnswer({
    signal: controller.signal,
    onDelta,
  }).then(
    () => onStatus("완료"),
    (error) => onStatus(
      error.name === "AbortError" ? "중단됨" : error.message
    ),
  );
  return { stop: () => controller.abort(), finished };
}
// const run = startAnswer(받은글추가, 상태표시);
// 중단 버튼에서는 run.stop()을 호출합니다.

기존 중단 실험의 클라이언트 출력입니다.

잡힌 오류: AbortError · This operation was aborted

서버 로그에서도 연결 종료와 생성 정지를 확인했습니다. 브라우저가 직접 멈춘 것이 아니라, 서버가 연결 종료를 감지해 다음 조각을 만들지 않도록 구현한 결과입니다.

실제 서비스에서도 서버의 모델 요청에 취소를 전달하고 작업 종료를 확인해야 합니다. 브라우저의 취소 표시만으로 공급자의 작업이나 과금까지 즉시 멈췄다고 판단하지 않습니다.

정상 응답으로 시작했는데 중간에 실패할 수 있습니다

fetch()는 오류 상태 응답을 받았다는 이유만으로 거절되지 않으므로 response.ok를 확인해야 합니다.[7] 그러나 그것만으로 생성 완료를 판단하지는 않습니다. 이 예제는 시작 후 장애를 응답 본문의 오류 이벤트로 보내고 연결을 닫도록 만들었습니다.

기존 장애 실험에서는 답변 뒤에 다음 이벤트가 왔고, 완료 이벤트는 오지 않았습니다.

event: error
data: {"type":"error","error":{"type":"overloaded_error","message":"Overloaded"}}

오류 이벤트나 완료 표시 없는 종료는 실패로 처리합니다. 전송 종료와 답변 완료를 구별하지 않으면 일부만 받은 답변을 완성본처럼 저장하게 됩니다.

중간 실패에서는 글을 유지하고 재시도를 사용자에게 맡깁니다. 고정 문자열 서버는 받은 길이 뒤부터 재전송했지만, 새 모델 요청에 길이만 보내서는 같은 답변이 이어진다고 보장할 수 없습니다. 이어 받기는 작업 식별자와 저장된 이벤트, 재전송 범위를 서버 계약으로 정해야 합니다.

사용자가 읽는 위치와 미완성 문법을 지킵니다

화면은 읽는 위치와 다시 그릴 범위를 따로 결정합니다.

위로 올려 읽는데 바닥으로 끌려 내려갑니다

기존 데모에서는 스크롤 이벤트에 저장한 바닥 여부가 뒤늦게 갱신돼 사용자를 아래로 보냈습니다. 대응은 DOM 변경 직전에 현재 위치를 재는 것입니다.

scrollHeight는 보이지 않는 부분까지 포함한 콘텐츠 높이입니다.[10] 바닥 판단에는 scrollTop, clientHeight도 사용하며, 스크롤 위치가 소수일 수 있으므로 정확한 등식 대신 허용 범위를 둡니다.[10] 아래 threshold는 제품이 정하는 바닥 근처의 거리이고, 문서가 권장한 고정 수치가 아닙니다.

function renderKeepingPosition(log, jump, draw, threshold) {
  const distance = log.scrollHeight - log.scrollTop - log.clientHeight;
  const stick = distance < threshold;
  draw(); // 여기에서만 새 답변을 DOM에 반영합니다.
  if (stick) log.scrollTop = log.scrollHeight;
  jump.hidden = stick;
}

기존 재현에서는 이 순서로 바꾼 뒤 읽는 위치가 유지되고 새 내용 보기 버튼이 나타났습니다. 캡처의 수치는 데모 상태값입니다.

코드 블록이 덜 왔는데 화면 모양이 계속 바뀝니다

완성된 문서만 받는다고 가정하면 미완성 문법을 다루기 어렵습니다. 데모는 코드 블록 밖의 빈 줄까지를 확정하고 쓰는 중인 꼬리만 다시 그렸습니다.

function stableBoundary(text) {
  let pos = 0, inFence = false, boundary = 0;
  const lines = text.split("\n");
  for (let i = 0; i < lines.length - 1; i++) {
    const fence = "\u0060\u0060\u0060"; // 백틱 세 개
    if (lines[i].startsWith(fence)) inFence = !inFence;
    pos += lines[i].length + 1;
    if (lines[i] === "" && !inFence) boundary = pos;
  }
  return boundary;
}

이 함수는 단순한 문단과 백틱 코드 블록용입니다. 참조 링크나 중첩 문법까지 고려하면 앞부분이 불변이라고 보장하지 못합니다. 범용 마크다운은 증분 렌더러를 검토하거나 완료 시 전체를 다시 해석합니다.

기존 화면에서는 닫는 기호가 오기 전에도 코드 영역이 유지됐습니다. 미완성 꼬리를 별도 표시한 결과입니다. 기호를 잠시 숨기더라도 누적 원문은 보존합니다.

화면 갱신은 requestAnimationFrame()의 다음 다시 그리기 전 콜백으로 묶을 수 있습니다.[11] 예약 중에는 원문만 누적하고, 종료 시 남은 표시를 마무리합니다.

원문을 HTML로 바로 삽입하지 않습니다. 데모의 이스케이프 처리는 범용 마크다운 보안 처리를 대체하지 않습니다.

정리

다른 선택지인 EventSource는 연결이 닫히면 기본적으로 재연결하며, close()로 종료할 수 있습니다.[9] 예제 서버의 완료 이벤트에 종료를 연결하면 다음처럼 쓸 수 있습니다. addEventListener()로 이름 있는 이벤트를 받는 방법은 MDN 예제와 같습니다.[3]

const events = new EventSource("/api/chat-es");
events.addEventListener("delta", (event) => {
  console.log(JSON.parse(event.data).text);
});
events.addEventListener("done", () => events.close());

기존 실험에서는 닫는 처리를 빼자 응답 종료 뒤 연결 오류가 표시되고, 재연결해 생성이 재시작됐습니다. 위 코드는 이를 막는 대응입니다. 브라우저가 답변 완료의 뜻까지 판단하지는 않습니다.

질문 본문을 보낼 때는 Fetch의 요청 옵션을 사용할 수 있습니다.[7] 반면 EventSource 생성자는 URL과 자격 증명 설정을 중심으로 동작하므로, 질문 전송을 별도 요청으로 분리하는 설계도 함께 검토해야 합니다.[9]

기준 fetch 스트림 EventSource 한 번에 받기
화면에 표시하는 시점 이벤트가 도착할 때 이벤트가 도착할 때 완성된 응답을 받은 뒤
질문 전송 요청 본문과 함께 처리 별도 질문 요청과 결합 검토 요청 본문과 함께 처리
파싱 책임 디코딩·이벤트 파서 직접 관리 브라우저의 이벤트 처리 사용 완성된 JSON 해석
종료 처리 앱의 완료 표시와 취소 구분 완료 시 명시적 종료 검토 응답 성공과 실패 처리
중간 내용 보존 누적 상태를 직접 유지 누적 상태를 직접 유지 중간 내용은 표시하지 않음
감수할 비용 파서·상태·화면 정책 구현 재연결과 생성 작업의 관계 설계 완료까지 기다리는 화면
  • 질문을 본문에 담고 중단·부분 실패를 직접 통제해야 한다면 fetch 스트림을 고릅니다.
  • 이미 생성한 작업의 알림을 계속 구독하고 재연결이 필요하다면 EventSource를 고릅니다.
  • 완성된 결과만 보여 줘도 요구사항을 만족한다면 한 번에 받기를 고릅니다.

글자 경계, 답변 완료, 사용자의 읽는 위치를 각각 지켜야 스트리밍 UI가 완성됩니다.

프론트엔드 팀이 해 볼 것
