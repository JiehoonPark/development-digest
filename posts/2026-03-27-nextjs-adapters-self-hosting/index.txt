16:T5283,<h2 id="실행-가능과-운영-조건을-나눠야-합니다">실행 가능과 운영 조건을 나눠야 합니다</h2>
<p>Vercel 밖에 배포한다고 Next.js 기능을 포기해야 하는 것은 아닙니다. 공식 배포 가이드는 단일 <code>next start</code> 프로세스가 서버 컴포넌트(Server Components), ISR, 부분 사전 렌더링(Partial Prerendering, PPR), Cache Components, Server Actions 등의 기능을 처리한다고 설명합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 먼저 Node.js 서버를 실행하는 방식과, 빌드 결과를 특정 플랫폼의 함수·저장소로 나누는 방식을 구분해야 합니다.</p>
<p>의존성을 설치한 기존 프로젝트라면 다음 명령이 단일 서버 배포의 출발점입니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup><sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<pre data-lang="bash"><code class="hljs language-bash">npx next build
npx next start
<span class="hljs-comment"># 빌드한 앱을 Next.js 프로덕션 서버로 실행</span>
</code></pre>
<p>이 경로를 확인하지 않고 “외부 배포에는 반드시 어댑터부터 필요하다”고 판단하기 쉽습니다. 하지만 어댑터는 플랫폼별 빌드·배포 통합을 위한 도구이지, 자체 호스팅을 처음 가능하게 만든 기능이 아닙니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup><sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h3 id="같은-페이지-안에서도-인프라-요구가-달라집니다">같은 페이지 안에서도 인프라 요구가 달라집니다</h3>
<p>Next.js는 정적·동적 콘텐츠의 경계를 경로가 아니라 컴포넌트 수준에 둡니다. 한 응답에 정적 화면 뼈대와 나중에 도착하는 동적 부분이 함께 들어갈 수 있고, 캐시한 함수는 페이지의 나머지 부분과 별도로 재검증할 수 있습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> 이 글에서는 컴포넌트 작성법 대신, 그 결과를 전달하고 보관할 배포 환경에 집중합니다.</p>
<p>이 구조에서 점진적 전달을 유지하려면 응답을 모아 두지 않는 스트리밍 경로가 필요합니다. 스트리밍을 버퍼링하는 환경에서도 응답 전체는 전달되지만, 먼저 준비된 화면을 먼저 보여 주는 이점은 사라집니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 서버가 실행됐다는 사실만으로 사용자에게 도착하는 방식까지 확인됐다고 볼 수는 없습니다.</p>
<p>공식 문서는 이를 기능적 충실도(functional fidelity)와 성능적 충실도(performance fidelity)로 구분합니다. 전자는 기능이 올바르게 동작하는지, 후자는 정적 화면 뼈대를 원본 서버 대신 CDN에서 전달하는 것처럼 성능 특성을 얼마나 살리는지에 관한 기준입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 다만 여러 인스턴스에서 무효화가 전파되지 않는 문제를 단순히 “조금 느린 배포”로 분류해서는 안 됩니다. 원문은 캐시 동기화와 재검증 전파를 올바른 동작에 필요한 조건으로 강조합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h2 id="adapter-api는-빌드-결과의-의미를-전달합니다">Adapter API는 빌드 결과의 의미를 전달합니다</h2>
<p>어댑터(adapter)는 Next.js의 빌드 결과를 받아 플랫폼의 인프라에 맞게 연결하는 코드입니다. 원문은 Next.js 16.2의 안정화된 Adapter API가 타입과 버전을 갖춘 애플리케이션 설명을 제공한다고 밝힙니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 단순히 생성된 파일 목록만 넘기는 것이 아닙니다.</p>

<p>위 항목은 원문이 열거한 공개 출력 정보입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 특정 플랫폼이 이 정보를 실제로 어떻게 배치하는지는 어댑터의 구현 책임입니다. 정보를 제공하는 계약과 그 계약을 이용해 인프라를 구성한 결과는 구별해야 합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup><sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h3 id="설정을-고치는-시점과-출력을-받는-시점">설정을 고치는 시점과 출력을 받는 시점</h3>
<p><code>modifyConfig</code>는 설정을 읽을 때 호출되고, <code>onBuildComplete</code>는 전체 빌드 출력을 사용할 수 있을 때 호출됩니다. 원문은 이 공개 계약의 호환성을 깨는 변경에는 Next.js의 새 메이저 버전이 필요하며, Vercel 어댑터에도 별도 비공개 훅이 없다고 설명합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<p>이미 구현된 로컬 어댑터 모듈이 있다면 다음처럼 경로를 지정합니다. 아래는 공식 설정 예제이며, <code>./my-adapter.js</code> 파일 자체를 만들어 주는 설정은 아닙니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// next.config.js</span>
<span class="hljs-comment">/** <span class="hljs-doctag">@type</span> {<span class="hljs-type">import('next').NextConfig</span>} */</span>
<span class="hljs-keyword">const</span> nextConfig = {
  <span class="hljs-attr">adapterPath</span>: <span class="hljs-built_in">require</span>.<span class="hljs-title function_">resolve</span>(<span class="hljs-string">'./my-adapter.js'</span>),
}
<span class="hljs-variable language_">module</span>.<span class="hljs-property">exports</span> = nextConfig
<span class="hljs-comment">// 빌드 과정에서 지정한 어댑터 모듈 사용</span>
</code></pre>
<p><code>adapterPath</code>는 최상위 옵션이며, 문서의 버전 이력은 <code>v16.2.0</code>에서 실험적 옵션에서 이동했다고 명시합니다. 배포 플랫폼은 <code>NEXT_ADAPTER_PATH</code> 환경 변수로도 어댑터를 지정할 수 있습니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 이를 넣었다는 이유만으로 캐시 저장소나 CDN이 구성됐다고 생각하면 안 됩니다. 빌드 시점 출력은 어댑터가 맡고, 런타임 캐시는 별도의 캐싱 인터페이스가 맡습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h3 id="opennext가-필요했던-이유">OpenNext가 필요했던 이유</h3>
<p>원문에 따르면 OpenNext는 Next.js 빌드 출력을 공급자가 소비할 수 있는 형태로 바꾸고, 프레임워크 동작을 각 플랫폼의 기능에 대응시켰습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 당시의 어려움은 공개되지 않은 매니페스트를 읽고, 설정 파일을 고치고, 재검증 같은 백그라운드 작업의 종료를 내부 구현에서 알아내야 했다는 점입니다. GitHub의 배포 어댑터 RFC는 이를 해결할 문제로 열거합니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<p>따라서 RFC의 제안 코드와 현재 설정 문서를 같은 지위로 복사하면 안 됩니다. 이 글의 설정은 공식 <code>adapterPath</code> 문서를 따르고, RFC는 설계 배경을 설명하는 근거로만 사용합니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup><sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 원문이 소개한 공개 테스트 모음은 스트리밍·캐싱·클라이언트 탐색 등을 검사하고 Vercel에도 같은 기준을 적용합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 어댑터 이름만 확인하는 데서 멈추지 말고, 사용할 조합의 호환성 테스트 결과를 확인해야 합니다.</p>
<h2 id="docker에서는-실행-파일과-설정-시점을-확인합니다">Docker에서는 실행 파일과 설정 시점을 확인합니다</h2>
<p>독립 실행 출력(standalone output)은 프로덕션 실행에 필요한 파일과 일부 의존성을 모으는 방식입니다. <code>output: 'standalone'</code>을 설정하면 <code>.next/standalone</code> 폴더와 최소 서버인 <code>server.js</code>가 생성됩니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 아래는 앞의 어댑터 설정과 별개로, 자체 호스팅 프로젝트에 적용하는 예입니다.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// next.config.js</span>
<span class="hljs-variable language_">module</span>.<span class="hljs-property">exports</span> = {
  <span class="hljs-attr">output</span>: <span class="hljs-string">'standalone'</span>,
}
<span class="hljs-comment">// 빌드 결과: .next/standalone</span>
</code></pre>
<h3 id="서버-파일만-복사하면-정적-파일이-빠집니다">서버 파일만 복사하면 정적 파일이 빠집니다</h3>
<p>생성된 서버는 <code>next start</code> 대신 실행할 수 있지만, <code>public</code>과 <code>.next/static</code>은 기본적으로 복사하지 않습니다. CDN에서 제공할 수도 있고, 독립 실행 폴더에 직접 복사하면 같은 서버가 제공합니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> <code>public</code> 폴더가 있는 프로젝트에서 로컬로 배포 묶음을 확인하는 명령은 다음과 같습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<pre data-lang="bash"><code class="hljs language-bash">npx next build
<span class="hljs-built_in">cp</span> -r public .next/standalone/
<span class="hljs-built_in">cp</span> -r .next/static .next/standalone/.next/
node .next/standalone/server.js
<span class="hljs-comment"># 복사한 public 및 .next/static도 같은 서버에서 제공</span>
</code></pre>
<p>Docker 이미지에 넣을 때도 “서버가 켜지는가”와 “정적 자산을 어디서 제공하는가”를 따로 확인해야 합니다. 실행 폴더만 옮기고 정적 자산의 제공 경로를 빠뜨리는 실수를 피하려는 점검입니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 이미지 최적화를 쓴다면 배포 가이드가 요구하는 <code>sharp</code> 패키지도 확인합니다. 이미지 최적화는 빌드 시점이 아니라 런타임에 수행됩니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup><sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>모노레포라면 추적 범위도 확인해야 합니다. 기본 추적 기준은 Next.js 프로젝트 폴더이므로, 그 바깥의 파일은 <code>outputFileTracingRoot</code>로 범위를 넓혀야 포함할 수 있습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 개발 환경에 있는 파일이 배포 묶음에도 반드시 들어간다고 가정하지 마세요.</p>
<h3 id="환경-변수는-언제-읽는지가-중요합니다">환경 변수는 언제 읽는지가 중요합니다</h3>
<p><code>NEXT_PUBLIC_</code> 접두사가 붙은 변수는 <code>next build</code> 중 브라우저용 자바스크립트에 삽입됩니다. 반면 서버의 동적 렌더링 중 읽는 환경 변수는 실행 시점의 값을 사용할 수 있어, 같은 Docker 이미지를 환경별로 승격하는 방식에 적합합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>아래는 문서의 <code>connection</code> 예제를 화면에 값을 표시하도록 최소화한 코드입니다. 노출해도 되는 예제 값만 사용하며, 비밀 값을 렌더링하지 않습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-comment">// app/page.tsx</span>
<span class="hljs-keyword">import</span> { connection } <span class="hljs-keyword">from</span> <span class="hljs-string">'next/server'</span>

<span class="hljs-keyword">export</span> <span class="hljs-keyword">default</span> <span class="hljs-keyword">async</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">Page</span>(<span class="hljs-params"></span>) {
  <span class="hljs-keyword">await</span> <span class="hljs-title function_">connection</span>()
  <span class="hljs-keyword">const</span> value = process.<span class="hljs-property">env</span>.<span class="hljs-property">MY_VALUE</span>
  <span class="hljs-keyword">return</span> <span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">p</span>></span>{value}<span class="hljs-tag">&#x3C;/<span class="hljs-name">p</span>></span></span>
}
<span class="hljs-comment">// 동적 렌더링 중 서버의 MY_VALUE를 읽어 표시</span>
</code></pre>
<p>이 예에서 중요한 것은 환경 변수 이름보다 <code>await connection()</code> 뒤에서 읽는다는 점입니다. 문서는 이 호출이 동적 렌더링을 선택하므로 해당 값을 런타임에 평가한다고 설명합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 브라우저용 변수도 컨테이너를 다시 시작하면 바뀔 것이라고 기대하는 것이 흔한 혼동입니다. 배포 설정표에 “빌드할 때 고정하는 값”과 “서버 요청 처리 중 읽는 값”을 나눠 적어 두세요.</p>
<h2 id="인스턴스를-늘리면-캐시의-경계도-바뀝니다">인스턴스를 늘리면 캐시의 경계도 바뀝니다</h2>
<p>단일 서버의 캐시와 여러 서버가 공유하는 캐시는 운영 조건이 다릅니다. 공식 자체 호스팅 문서는 영속적인 로컬 디스크를 가진 단일 서버에서는 기본 캐시가 동작하지만, 임시 디스크나 여러 컨테이너에서는 각 인스턴스가 별도 캐시를 가진다고 설명합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 같은 이미지를 실행한다고 같은 캐시를 보는 것은 아닙니다.</p>
<h3 id="저장소-연결과-무효화-전파를-함께-봅니다">저장소 연결과 무효화 전파를 함께 봅니다</h3>
<p>서버 캐시 경로에는 <code>cacheHandler</code>, <code>'use cache'</code> 지시문의 백엔드에는 <code>cacheHandlers</code>를 사용합니다. 단수형과 복수형은 서로 다른 런타임 캐시 경로를 담당합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 아래는 이미 구현한 서버 캐시 핸들러를 연결하고 기본 메모리 캐시를 끄는 공식 설정입니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-comment">// next.config.js</span>
<span class="hljs-variable language_">module</span>.<span class="hljs-property">exports</span> = {
  <span class="hljs-attr">cacheHandler</span>: <span class="hljs-built_in">require</span>.<span class="hljs-title function_">resolve</span>(<span class="hljs-string">'./cache-handler.js'</span>),
  <span class="hljs-attr">cacheMaxMemorySize</span>: <span class="hljs-number">0</span>,
}
<span class="hljs-comment">// 기본 메모리 캐시를 끄고 사용자 정의 핸들러 연결</span>
</code></pre>
<p>이 설정만 복사한다고 공유 캐시가 생기지는 않습니다. <code>cache-handler.js</code>는 실제로 구현해야 하며, 문서는 <code>get</code>, <code>set</code>, <code>revalidateTag</code>, <code>resetRequestCache</code>를 구현하는 클래스를 요구합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 프로세스 안의 <code>Map</code>에 저장하면 다시 인스턴스별 캐시가 되므로, 모든 인스턴스가 접근하는 저장소와 공유 태그 인덱스가 필요합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>무효화만 공유하고 데이터 표현을 놓쳐서도 안 됩니다. 문서는 캐시 항목에 <code>Buffer</code>와 <code>Map</code>이 들어갈 수 있어 단순한 <code>JSON.stringify</code>와 <code>JSON.parse</code>만으로는 복원할 수 없다고 경고합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 렌더링 철학 문서도 HTML 응답과 클라이언트 탐색에 쓰는 RSC 페이로드가 어긋나면 탐색 중 데이터가 불일치할 수 있다고 설명합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<p>따라서 테스트는 첫 페이지 로드에서 끝내지 않는 편이 좋습니다. 한 인스턴스에서 갱신을 일으킨 뒤 다른 인스턴스로 요청을 보내고, 새로고침과 클라이언트 탐색에서 같은 변경을 확인하는 절차를 권합니다. 이는 실제 장애 사례를 재현했다는 뜻이 아니라, 문서의 캐시 조정 요구를 배포 점검으로 옮긴 것입니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup><sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h3 id="프록시-뒤에서도-점진적으로-도착하는지-봅니다">프록시 뒤에서도 점진적으로 도착하는지 봅니다</h3>
<p>자체 호스팅 가이드는 Next.js 서버 앞에 역방향 프록시(reverse proxy)를 두어 비정상 요청·느린 연결 공격·요청 크기 제한 등을 처리하도록 권합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 동시에 배포 가이드는 점진적 전달을 위해 플랫폼이 응답을 버퍼링하지 않아야 한다고 명시합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 프록시가 있다는 사실과 스트리밍이 유지된다는 사실은 별도로 확인해야 합니다.</p>
<p>정적 화면 뼈대와 느린 동적 영역이 있는 경로를 골라 서버 직접 접속과 실제 배포 경로를 비교해 보세요. 최종 HTML이 같은지만 보지 말고, 먼저 준비된 부분이 먼저 보이는지 확인합니다. 이는 자료가 설명하는 스트리밍 조건을 확인하기 위한 점검 제안이며, 특정 공급자의 성능을 평가한 결과는 아닙니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup><sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
