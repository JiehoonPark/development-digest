프론트엔드 모노레포 — pnpm workspace와 Turborepo로 시작하기

앱 하나와 공유 패키지 둘로 이뤄진 작은 저장소를 직접 꾸려 봅니다. 패키지 위치 선언, 내부 패키지 연결, 버전 통일, 진입점 방식, 빌드 순서와 캐시, 일부만 빌드하는 필터까지 설정 단위로 정리했습니다.

저장소 뼈대 잡기

모노레포(monorepo)는 여러 프로젝트를 저장소 하나에 두는 방식이고, pnpm은 이를 워크스페이스(workspace)로 기본 지원합니다.[1] Turborepo는 패키지 매니저의 워크스페이스 위에서 태스크를 실행합니다.[2]

패키지 위치 선언

워크스페이스 루트에는 pnpm-workspace.yaml이 있어야 하고, packages 필드에 프로젝트 디렉터리를 적습니다.[1] Turborepo 문서는 애플리케이션은 apps/, 라이브러리와 도구는 packages/로 나누는 것부터 시작하라고 권합니다.[2] 이 글의 예제 저장소는 다음과 같습니다.

# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

# 결과 구조
# apps/web/package.json          → web (Next.js 앱)
# packages/ui/package.json       → @repo/ui
# packages/config/package.json   → @repo/config (tsconfig 공유)

apps나 packages 아래 package.json이 있는 디렉터리는 모두 패키지가 됩니다.[2] 다만 Turborepo는 apps/**처럼 중첩된 패키지를 지원하지 않아서, apps/a와 apps/a/b에 각각 패키지를 두면 오류가 납니다.[2] 이름에 @repo/ 같은 네임스페이스 접두사를 붙이면 npm 레지스트리 패키지와의 충돌을 피할 수 있습니다.[2]

루트 package.json에는 도구만

루트 package.json은 워크스페이스의 바탕입니다. 공식 예시는 turbo run 스크립트와 turbo 개발 의존성만 둡니다.[2]

{
  "private": true,
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev",
    "lint": "turbo run lint"
  },
  "devDependencies": {
    "turbo": "latest"
  }
}

turbo 명령은 루트 package.json에만 씁니다. 패키지의 스크립트에 넣으면 turbo가 재귀로 호출될 수 있습니다.[7] 락파일도 꼭 커밋합니다. Turborepo는 락파일로 내부 패키지 사이의 의존 관계를 파악하고, 락파일이 없으면 예측할 수 없게 동작할 수 있습니다.[2]

자주 하는 실수: 루트에 앱 의존성 몰기

react나 next를 루트에 한 번만 설치하면 편해 보이지만, Turborepo 문서는 의존성을 실제로 쓰는 패키지에 설치하라고 권하고, 루트에 둘 것은 turbo, husky, lint-staged 같은 저장소 관리 도구뿐이라고 설명합니다.[6] 루트 package.json의 의존성을 바꾸면 모든 태스크가 캐시를 놓치기 때문입니다.[5][6] 여러 패키지에 한 번에 설치할 때는 필터를 씁니다.[6]

pnpm add jest --save-dev --recursive --filter=web --filter=@repo/ui

내부 패키지 연결과 버전 통일

workspace: 프로토콜

내부 패키지(Internal Package)는 소스 코드가 워크스페이스 안에 있는 라이브러리입니다. 버전 대신 패키지 매니저의 워크스페이스 문법으로 설치합니다.[3]

{
  "name": "web",
  "dependencies": {
    "next": "latest",
    "@repo/ui": "workspace:*"
  },
  "devDependencies": {
    "@repo/config": "workspace:*"
  }
}

workspace: 프로토콜을 쓰면 pnpm은 로컬 워크스페이스 패키지가 아닌 것으로는 해석하지 않습니다.[1] 패키지를 pnpm pack이나 pnpm publish로 묶을 때는 workspace:*가 실제 버전으로 바뀝니다.[1]

// 워크스페이스의 foo가 1.5.0일 때 발행 전 변환
"foo": "workspace:*"   // → "1.5.0"
"qar": "workspace:^"   // → "^1.5.0"

자주 하는 실수: 버전 범위로 적기

"@repo/ui": "^1.0.0"처럼 일반 범위를 쓰면 결과가 설정에 따라 달라집니다. linkWorkspacePackages의 기본값은 false이고, 이때 로컬 패키지는 workspace:를 쓸 때만 링크됩니다.[1] true로 켜도 선언한 범위를 만족하는 로컬 버전이 없으면 레지스트리에서 설치하며, pnpm 문서도 이 동작이 불확실성을 낳는다고 설명합니다.[1] saveWorkspaceProtocol 기본값은 rolling이라, pnpm add로 추가하면 savePrefix에 따라 workspace:*나 workspace:^ 같은 형태로 저장됩니다.[1]

catalog: 로 외부 버전 맞추기

카탈로그(catalog)는 의존성 버전 범위를 재사용 가능한 상수로 정의하는 기능입니다.[8] Turborepo 문서는 pnpm v9.5 이상에서 쓸 수 있다고 안내합니다.[6]

# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
catalog:
  react: ^18.3.1

// apps/web/package.json, packages/ui/package.json 모두
"react": "catalog:"
// → "^18.3.1"을 직접 쓴 것과 같음

업그레이드는 pnpm-workspace.yaml 한 줄만 고치면 되고, 버전을 하나로 유지하기 쉬워져 중복으로 인한 런타임 충돌과 번들 크기 증가를 피할 수 있습니다.[8] 발행할 때 catalog:는 실제 범위로 바뀝니다.[8]

내부 패키지의 진입점

다른 패키지가 내부 패키지를 쓰는 통로는 exports 필드입니다.[2] type과 조건부 내보내기 규칙은 「사내 패키지는 ESM 하나로 — exports 설정과 토스뱅크의 세 가지 기준」에서 다뤘으니 모노레포에서의 선택만 봅니다. Turborepo 문서는 하위 경로(subpath)마다 진입점을 두는 방식이 배럴 파일을 피하게 해 준다고 설명합니다.[2] 배럴 파일이 실행 의존성을 넓히는 문제는 「파일만 나누면 끝일까 — JavaScript 모듈 경계 설계」를 참고하세요.

Just-in-Time 패키지

Just-in-Time 패키지는 사용하는 앱의 번들러가 컴파일합니다. TypeScript 파일을 그대로 내보내므로 빌드 스크립트가 없습니다.[3]

{
  "name": "@repo/ui",
  "exports": {
    "./button": "./src/button.tsx"
  },
  "scripts": {
    "check-types": "tsc --noEmit"
  }
}

// packages/ui/src/button.tsx
import type { ReactNode } from "react";

export function Button({ children }: { children: ReactNode }) {
  return <button>{children}</button>;
}

// apps/web/app/page.tsx
import { Button } from "@repo/ui/button";

export default function Page() {
  return <Button>Submit</Button>;
}

설정은 가장 적지만 소비하는 쪽이 TypeScript를 변환할 수 있어야 하고, 자체 빌드가 없어 Turborepo가 캐시할 수 없습니다.[3] 이 패키지에서는 compilerOptions.paths도 쓸 수 없어서, TypeScript 5.4 이상이면 Node.js 하위 경로 가져오기(imports)를 대신 쓰라고 권합니다.[3][9]

Compiled 패키지

Compiled 패키지는 tsc 같은 도구로 스스로 컴파일합니다.[3] 같은 @repo/ui를 이 방식으로 바꾸면 타입은 소스를, 실행은 dist를 가리킵니다.

{
  "name": "@repo/ui",
  "exports": {
    "./button": {
      "types": "./src/button.tsx",
      "default": "./dist/button.js"
    }
  },
  "scripts": {
    "build": "tsc"
  }
}

빌드 결과는 태스크의 outputs에 넣어야 Turborepo가 캐시합니다.[3] 편집기에서 정의로 이동이 원본 소스로 가려면 declaration과 declarationMap을 켭니다.[9][10] 발행할 패키지라면 types가 소스를 가리킬 수 없으니 선언 파일을 따로 만들어야 합니다.[9]

설정 공유 패키지

tsconfig도 패키지로 공유합니다. 공식 예시는 base.json을 두고 각 패키지의 tsconfig.json이 extends로 이어받게 합니다.[9]

// apps/web/tsconfig.json
{
  "extends": "@repo/config/base.json",
  "include": ["src"]
}

루트에는 tsconfig.json을 두지 않는 편이 좋습니다. 패키지마다 자기 설정을 가져야 타입 검사 캐시가 쉬워지고, 루트 변경은 모든 태스크의 캐시를 깨기 때문입니다.[9]

turbo.json: 순서, 캐시, 필터

dependsOn으로 순서 정하기

tasks의 각 키는 turbo run으로 실행할 태스크이고, 같은 이름의 패키지 스크립트를 찾아 실행합니다.[4] "build": {}만 두면 모든 build가 병렬로 돌고 파일 출력도 캐시하지 않아서, 공식 문서도 잘못된 설정이라고 표시합니다.[4]

{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": [
        ".next/**",
        "!.next/cache/**",
        "!.next/dev/**",
        "dist/**"
      ]
    },
    "topo": { "dependsOn": ["^topo"] },
    "check-types": { "dependsOn": ["topo"] }
  }
}
// turbo run build → @repo/ui의 build 완료 후 web의 build

^는 직접 의존하는 패키지의 태스크를 먼저 실행하라는 뜻입니다.[4] ^ 없이 쓰면 같은 패키지 안의 태스크를 가리킵니다.[4] check-types에는 공식 가이드의 전달 노드(Transit Node) topo를 썼습니다. 태스크는 병렬로 돌리면서 다른 패키지의 소스 변경은 해시에 반영하는 방법입니다.[9]

outputs와 캐시 입력

outputs는 태스크가 성공했을 때 캐시할 파일입니다. 이 키가 없으면 파일을 캐시하지 않고, 다음 실행에서 캐시가 맞아도 파일은 복원되지 않습니다.[4] 글롭은 패키지 기준 상대 경로입니다.[4]

증상캐시가 맞았는데 dist가 없다

turbo.json의 outputs에 빌드 결과 경로가 있는지 확인합니다. 없으면 캐시가 맞아도 파일은 복원되지 않습니다.[4]

캐시가 맞으려면 무엇이 해시에 들어가는지 알아야 합니다. 전역 해시에는 해석된 turbo.json, 루트에 영향을 주는 락파일 변경, globalDependencies 파일, globalEnv 변수 값 등이 들어갑니다.[5] 패키지 해시에는 패키지의 package.json, 그 패키지에 영향을 주는 락파일 변경, 그리고 기본으로 패키지 디렉터리의 Git 추적 파일 전체가 들어갑니다.[5] 둘 중 하나라도 바뀌면 캐시를 놓칩니다.[5]

"build": {
  "inputs": ["$TURBO_DEFAULT$", "!README.md"]
}
// README.md만 바꾸면 build는 캐시 히트

inputs를 직접 적으면 기본 동작 전체를 대체해 .gitignore도 무시되므로, 기본값을 유지하려면 $TURBO_DEFAULT$를 함께 씁니다.[4] 예상과 달리 캐시를 놓친다면 --summarize로 두 실행의 입력을 비교하고, --dry로 실행 없이 태스크와 해시를 확인합니다.[5][11]

--filter로 일부만 실행

패키지 이름, 의존 관계, Git 변경으로 실행 범위를 좁힐 수 있습니다.[7]

turbo build --filter=@repo/ui     # ui만
turbo build --filter=...@repo/ui  # ui와 ui에 의존하는 패키지
turbo dev --filter=web...         # web과 web이 의존하는 패키지
turbo build --filter=[HEAD^1]     # 직전 커밋 이후 바뀐 패키지
turbo run build --affected        # --filter=...[main...HEAD]와 같음

--filter를 여러 개 쓰면 합집합이지만, --affected와 --filter를 함께 쓰면 둘 다 만족하는 패키지만 고릅니다.[7][11] CI에서 --affected를 쓸 때는 체크아웃 이력이 충분해야 합니다. 너무 얕으면 모든 패키지를 바뀐 것으로 봅니다.[11] pnpm도 pnpm --filter "...[origin/master]" test처럼 바뀐 패키지와 그 의존자를 고를 수 있습니다.[12]

정리

할 일 설정 놓치면
패키지 위치 pnpm-workspace.yaml의 apps/*, packages/* 중첩 패키지는 Turborepo 오류
내부 패키지 연결 "@repo/ui": "workspace:*" 레지스트리 설치 등 불확실한 해석
외부 버전 통일 catalog: + pnpm-workspace.yaml의 catalog 패키지마다 버전이 갈라짐
진입점 Just-in-Time은 소스, Compiled는 dist + build Just-in-Time은 빌드 캐시 불가
빌드 순서 "dependsOn": ["^build"] 의존 패키지보다 앱이 먼저 빌드
캐시 outputs에 dist/**, .next/** 캐시 히트여도 파일 없음
루트 의존성 turbo 같은 관리 도구만 바꿀 때마다 전체 캐시 미스
일부 실행 --filter, --affected 매번 전체 빌드

프론트엔드 팀이 해 볼 것

  1. 저장소의 turbo.json에서 파일을 만드는 태스크마다 outputs가 있는지 확인하고, turbo run build를 두 번 돌려 두 번째 실행 뒤에도 dist나 .next가 그대로 있는지 봅니다.
  2. 내부 패키지 의존성 중 버전 범위로 적힌 것을 찾아 workspace:*로 바꾸고 pnpm install로 락파일을 갱신합니다.
  3. 루트 package.json의 dependencies를 훑어 앱이나 라이브러리에서만 쓰는 패키지를 해당 패키지로 옮깁니다.
