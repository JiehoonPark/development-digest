배포는 새로, 에셋은 오래 — 프론트엔드 HTTP 캐시 헤더

HTML과 해시 파일명 에셋에 같은 캐시 정책을 적용하면 배포 반영과 재사용이 충돌합니다. 저장 여부, 재검증, 공유 범위를 나누고 실제 응답 헤더로 확인하는 방법을 정리합니다.

요약

  • 내용이 바뀔 때 URL도 바뀌는 에셋은 긴 max-age와 immutable로 재사용하고, HTML은 no-cache와 검증자를 조합합니다.[1][2]
  • no-cache는 저장 금지가 아니라 재사용 전 검증이며, 저장 자체를 막는 지시어는 no-store입니다.[2]
  • ETag를 If-None-Match로 보내고 값이 일치하면 본문 없는 304 응답으로 저장된 내용을 재사용합니다.[3][4]

저장과 재사용은 다른 결정입니다

이런 상황을 가정해 봅시다. 금요일 저녁에 결제 화면을 고쳐 배포했는데, 일부 사용자가 "버튼을 눌러도 아무 반응이 없다"고 문의합니다. 강력 새로고침을 하면 멀쩡해집니다. 이전 HTML이 이전 자바스크립트 파일을 계속 가리키거나, 새 HTML과 이전 에셋이 섞이면 이런 일이 생길 수 있습니다. 이 글의 정책은 그 섞임을 막는 것이 목적입니다.

배포 뒤에도 예전 화면이 보인다고 캐시를 전부 끄면, 바뀌지 않은 파일까지 다시 받게 됩니다. 반대로 모든 응답을 오래 재사용하면 새 에셋을 가리켜야 하는 HTML도 이전 상태로 남을 수 있습니다. MDN은 이 문제를 에셋의 URL 변경과 HTML의 재검증으로 나누어 설명합니다.[1]

HTTP 캐시는 요청에 대응하는 응답을 저장하고 다음 요청에서 재사용하는 장치입니다. 브라우저처럼 한 사용자에게 속한 개인 캐시(private cache)와, 여러 사용자의 응답을 재사용하는 CDN 같은 공유 캐시(shared cache)를 구분합니다.[1] 여기서는 프레임워크 내부 데이터 캐시가 아니라, 배포된 파일의 HTTP 응답 정책에 집중합니다.

no-cache는 “저장하지 말라”가 아닙니다

no-cache는 응답을 저장할 수 있지만 재사용하기 전에 원본 서버의 검증을 거치라는 뜻입니다. no-store는 개인 캐시와 공유 캐시 모두에 해당 응답을 저장하지 말라고 지시합니다.[2] 이름보다 저장 가능 여부와 재사용 조건을 따로 읽어야 합니다.

Cache-Control: no-cache

위 헤더의 결과는 “저장한 응답을 검증한 뒤 재사용”입니다. 화면을 최신으로 유지하면서 바뀌지 않은 본문은 다시 받지 않으려는 경우에 맞습니다.[2] 반면 저장을 허용하지 않으려는 응답에는 다음 정책을 적용합니다.[2]

Cache-Control: no-store

두 헤더는 서버 응답에 넣는 대안이지 함께 붙이는 기본 묶음이 아닙니다. 캐시를 걱정해 여러 지시어를 무조건 나열하기보다 필요한 정책을 선택해야 합니다.[1] 또한 no-store만으로 개인정보 보호가 완성되지는 않습니다. 명세도 악의적이거나 손상된 캐시까지 이 지시어의 준수를 보장하지 않는다고 경고합니다.[5]

max-age는 파일의 보관 기한이 아닙니다

신선한 응답(fresh)은 보통 검증 없이 재사용할 수 있는 상태이며, 오래된 응답(stale)은 신선도가 만료된 상태입니다. 오래되었다고 저장된 본문이 즉시 삭제되는 것은 아닙니다. 재검증으로 다시 사용할 수도 있습니다.[1][2]

Cache-Control: max-age=604800
Age: 86400

MDN의 이 예제에서 신선도 수명은 일주일이고, 응답은 이미 하루의 나이를 갖습니다.[1] max-age는 응답을 받은 시점이 아니라 원본 서버에서 생성된 시점부터 센 시간입니다.[2] 따라서 max-age를 “브라우저 디스크에 반드시 이만큼 남겨 둔다”는 보장으로 읽으면 안 됩니다. 명세에서 캐시는 선택적 기능이며, 저장 가능한 응답을 항상 저장하도록 강제하지도 않습니다.[5]

에셋은 URL로 바꾸고, HTML은 검증합니다

해시 파일명은 오래 재사용할 수 있는 전제입니다

캐시 무효화용 URL 변경(cache busting)은 내용이 바뀔 때 URL도 바꾸는 방식입니다. MDN은 파일명이나 쿼리에 버전·해시를 넣어 이전 응답과 새 응답을 구별하는 예제를 제시합니다.[1][2] 다음은 그중 파일명 해시를 쓰는 최소 HTML 예제입니다.

<script src="bundle.YsAIAAAA-QG4G6kCMAMBAAAAAAAoK.js"></script>
<!-- 내용이 바뀌면 파일명과 이 참조를 함께 바꿉니다. -->

이 파일이 모든 사용자에게 동일한 공개 에셋이고, 같은 URL의 내용은 바뀌지 않는다면 다음 응답 정책을 사용할 수 있습니다.[1]

Cache-Control: public, max-age=31536000, immutable

max-age=31536000은 MDN 가이드가 이 패턴의 예제에 쓰는 값입니다. public은 공유 캐시 저장을 명시합니다. MDN은 HTML이 Basic·Digest 인증 아래에 있으면 에셋이 공유 캐시에 저장되지 않으므로 public, s-maxage, must-revalidate 중 하나가 필요하다고 설명합니다.[2] immutable은 신선도 수명 동안 응답이 바뀌지 않는다고 알려 불필요한 재검증을 피하게 합니다.[1][2] 영구 보관이나 영구 신선도를 뜻하지는 않습니다.

자주 하는 실수는 bundle.js처럼 고정된 URL의 파일을 덮어쓰면서 같은 헤더를 적용하는 것입니다. 캐시가 신선한 응답을 이미 갖고 있으면 서버에 요청 자체를 보내지 않으므로, 서버는 그 경로에 대해 할 수 있는 일이 없습니다.[1][2] 파일명에 해시가 “들어 있는 모양”보다 내용 변경마다 URL이 실제로 바뀌는 배포 규칙이 중요합니다.[1]

HTML은 새 에셋을 알려 주는 진입점입니다

HTML은 어떤 에셋 URL을 읽을지 결정합니다. HTML 자체가 저장되어 재사용되면 서버에서 내용을 바꿔도 최신 버전을 표시할 수 없습니다.[1] MDN은 클라이언트가 쓰는 JavaScript와 CSS의 버전이 서로 어긋나면 화면이 깨질 수 있다고도 지적합니다.[1] 주소를 유지하면서 배포 내용을 반영해야 하는 HTML에는 다음처럼 no-cache와 검증자를 조합합니다.[1]

Cache-Control: no-cache
ETag: "AAPuIbAOdvAGEETbgAAAAAAABAAE"

이 예제의 ETag 값은 MDN 문서에 나온 예시입니다. 실제 서비스에서는 해당 HTML 버전을 나타내는 값을 서버가 생성해야 하며, 이 문자열을 고정 설정으로 복사하면 안 됩니다.[1][3]

이 정책은 “HTML을 매번 전부 다운로드한다”가 아닙니다. 바뀌었는지 확인하고 그대로라면 본문을 재사용합니다.[1] 다만 no-cache가 뒤로 가기 같은 방문 기록 이동에서도 반드시 재검증을 일으킨다고 가정하면 안 됩니다. MDN은 방문 기록 복원과 일반적인 HTTP 캐시 재사용을 구분합니다.[2]

ETag에서 304까지, 실제로 확인합니다

검증자는 본문을 다시 보내기 전에 비교합니다

ETag는 특정 리소스 버전을 식별하는 응답 헤더입니다. 생성 방식은 정해져 있지 않으며 내용의 해시나 수정 시각의 해시, 리비전 번호 등을 사용할 수 있습니다.[3] 클라이언트는 저장한 값을 다음 요청의 If-None-Match에 넣습니다.[3][4]

If-None-Match: "AAPuIbAOdvAGEETbgAAAAAAABAAE"

서버의 현재 값과 일치하면 조건부 GET 또는 HEAD 요청에 304 Not Modified를 반환합니다. 일치하는 값이 없으면 리소스를 200 상태로 돌려줍니다.[4] 304에는 본문이 없고, 같은 요청의 200 응답이었다면 보냈을 Cache-Control, Date, ETag, Vary 같은 헤더를 담습니다.[4][6] 앞의 HTML 응답을 검증했다면 상태 줄과 핵심 헤더는 다음 모양이 됩니다.

HTTP/1.1 304 Not Modified
Cache-Control: no-cache
ETag: "AAPuIbAOdvAGEETbgAAAAAAABAAE"

네트워크 왕복까지 없어진 것은 아닙니다. 이 흐름은 요청 없이 끝나는 캐시 적중이 아니라, 확인 요청은 보내되 본문 재전송을 생략한 상태입니다.

curl로 조건부 요청을 재현합니다

먼저 MDN에서 사용하는 방식대로 curl로 응답 헤더를 조회합니다. 아래 주소는 실제 요청할 수 있는 MDN 페이지이며, --http1.1은 출력 형식을 읽기 쉽게 고정하기 위한 옵션입니다.[6]

curl --http1.1 -I https://developer.mozilla.org/en-US/
# 출력의 Cache-Control, ETag, Vary를 확인합니다.

이어서 방금 받은 ETag 전체를 따옴표까지 복사해 조건부 요청을 보냅니다. 아래 값은 MDN 자료의 예시이므로 실행 전에 첫 응답의 값으로 바꿔야 합니다.[6]

curl --http1.1 -I \
  --header 'If-None-Match: "b20a0973b226eeea30362acb81f9e0b3"' \
  https://developer.mozilla.org/en-US/
# 현재 ETag와 일치하면 304, 내용이 바뀌어 불일치하면 200

MDN 문서가 같은 명령으로 받은 응답은 다음과 같습니다. Date, Age 값은 실행할 때마다 달라집니다.[6]

HTTP/1.1 304 Not Modified
Date: Wed, 28 Aug 2024 10:36:35 GMT
Expires: Wed, 28 Aug 2024 11:02:17 GMT
Age: 662
ETag: "b20a0973b226eeea30362acb81f9e0b3"
Cache-Control: public, max-age=3600
Vary: Accept-Encoding

이 명령은 -I로 헤더를 조회하므로, 화면에 본문이 안 보인다는 사실만으로 검증 성공을 판정하면 안 됩니다. 반드시 상태 줄을 확인합니다. ETag는 큰따옴표로 둘러싸며 약한 검증자라면 W/ 접두사가 붙을 수 있으므로, 실제 응답의 값을 그대로 전달하는 편이 안전합니다.[3][4]

MDN 페이지의 캐시 수명을 우리 HTML 정책의 정답으로 복사하지는 않습니다. 이 요청은 조건부 검증을 관찰하기 위한 예제입니다. 우리 배포 정책은 공개 주소에서 별도로 확인해야 합니다.

# example.com과 파일명은 실제 배포 주소로 바꿉니다.
curl --http1.1 -I https://example.com/index.html
# 적용 목표: Cache-Control: no-cache
# 검증자가 설정됐다면 ETag도 확인합니다.

curl --http1.1 -I https://example.com/bundle.YsAIAAAA-QG4G6kCMAMBAAAAAAAoK.js
# 적용 목표: Cache-Control: public, max-age=31536000, immutable

주석은 설정을 적용한 뒤 확인할 기대 정책이지, 예시 도메인을 조회해 얻은 측정 결과가 아닙니다. 실제 헤더가 다르면 서버뿐 아니라 CDN 설정도 확인합니다. 관리형 캐시는 자체 설정으로 동작을 제어할 수 있기 때문입니다.[1]

공유 범위와 오래된 응답의 허용 범위를 정합니다

private와 Vary는 서로 대신할 수 없습니다

private는 개인 캐시에만 저장하도록 제한합니다. public은 공유 캐시에 저장할 수 있음을 명시하며, Authorization이 있는 요청처럼 공유 저장이 제한되는 경우에도 영향을 줄 수 있습니다.[2] 따라서 공개 에셋에 쓴 헤더를 로그인 HTML 전체에 복사하면 안 됩니다.

Cache-Control: no-cache, private

사용자별 HTML을 개인 캐시에 저장하되 재사용 전에 검증하려는 정책입니다.[1][2] 쿠키가 있다는 사실만으로 응답이 자동으로 개인용이 되지는 않습니다. 저장 자체를 원하지 않는다면 앞서 설명한 no-store를 선택합니다.[1][2]

반면 Vary는 같은 URL에서도 어떤 요청 헤더에 따라 응답을 구별해야 하는지 알려 줍니다.[7] 예를 들어 서버가 요청 언어에 맞춰 다른 문서를 만든다면 다음 응답 헤더를 사용합니다.[1]

Vary: Accept-Language

이 경우 서로 다른 언어 요청의 응답을 구분해 캐시합니다.[1] 사용자별 내용을 보호하려고 Vary에 쿠키를 넣지 말고 Cache-Control: private를 명시해야 합니다. 또한 같은 URL의 일반 응답과 304 응답에는 일관된 Vary 값을 사용해야 합니다.[1][7]

stale-while-revalidate는 최신성의 타협입니다

stale-while-revalidate는 신선도 만료 뒤 일정 시간 동안 오래된 응답을 먼저 사용하면서 백그라운드에서 검증하도록 허용합니다.[2] 다음은 MDN의 예제입니다.

Cache-Control: max-age=604800, stale-while-revalidate=86400

응답은 일주일 동안 신선합니다. 그 뒤 하루 동안 들어오는 요청에는 오래된 응답을 재사용하면서 뒤에서 검증할 수 있습니다.[2] 그 기간에 요청이 없다가 허용 기간이 끝난 후 요청이 들어오면 일반적인 재검증을 수행합니다. 백그라운드 검증은 그 기간에 들어온 요청을 계기로 일어납니다.[2]

이 설정은 예시일 뿐 모든 데이터에 권할 수 있는 수명은 아닙니다. 이전 화면이 잠깐 보여도 되는지부터 결정해야 합니다. 새 에셋 참조를 바로 확인하려고 선택한 HTML의 no-cache 정책과는 목표가 다릅니다.[1][2]

특히 no-cache와 이 지시어를 함께 붙여 “항상 검증하면서 오래된 응답도 먼저 제공한다”고 기대하면 안 됩니다. 명세는 no-cache 등 명시적인 지시어가 금지한 경우 오래된 응답을 제공하지 못하도록 규정합니다.[5]

정리

대상과 요구 응답 정책 확인할 전제
공개 해시 파일명 에셋 public, max-age=31536000, immutable 내용 변경 시 URL도 변경[1]
최신 여부를 확인할 HTML no-cache와 ETag 재사용 전 검증, 동일하면 304[1][3]
사용자별 HTML no-cache, private 공유 저장 금지, 개인 캐시에서 검증[1][2]
저장을 허용하지 않을 응답 no-store 개인정보 보호 전체를 보장하지 않음[5]
일시적으로 이전 내용 허용 max-age와 stale-while-revalidate 허용 기간과 재검증 동작 확인[2]

캐시 정책은 “켜기와 끄기”보다 세 질문으로 정리하면 명확합니다. 누가 저장해도 되는지, 언제 검증해야 하는지, 내용이 바뀌면 URL도 바뀌는지를 정합니다. 배포 점검에서는 HTML과 에셋의 응답 헤더를 각각 읽고, 조건부 요청으로 검증 흐름까지 확인하세요.

프론트엔드 팀이 해 볼 것

  1. 배포된 HTML과 해시 파일명 에셋의 응답 헤더를 각각 조회해 캐시 정책이 분리되어 있는지 확인합니다.
  2. HTML의 실제 ETag를 If-None-Match에 넣어 조건부 요청을 보내고, 내용이 같을 때 304가 반환되는지 확인합니다.
  3. 로그인 HTML의 private 여부와 고정 URL에 immutable을 적용한 경로가 없는지 점검합니다.

목차

  • 저장과 재사용은 다른 결정입니다
  • no-cache는 “저장하지 말라”가 아닙니다
  • max-age는 파일의 보관 기한이 아닙니다
  • 에셋은 URL로 바꾸고, HTML은 검증합니다
  • 해시 파일명은 오래 재사용할 수 있는 전제입니다
  • HTML은 새 에셋을 알려 주는 진입점입니다
  • ETag에서 304까지, 실제로 확인합니다
  • 검증자는 본문을 다시 보내기 전에 비교합니다
  • curl로 조건부 요청을 재현합니다
  • 공유 범위와 오래된 응답의 허용 범위를 정합니다
  • private와 Vary는 서로 대신할 수 없습니다
  • stale-while-revalidate는 최신성의 타협입니다
