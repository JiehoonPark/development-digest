실시간 알림, 폴링·SSE·WebSocket 중 무엇을 고를까

주문 알림을 세 방식으로 받아 보면 차이는 전송 속도보다 연결을 유지하고 복구하는 책임에 있습니다. 실제 요청·응답을 비교하고, 재연결 뒤에도 알림을 빠뜨리지 않는 설계 기준을 정리합니다.

주문 알림을 맡았다고 가정해 봅시다

쇼핑몰 관리자 화면의 새 주문 알림을 맡았다고 가정해 봅시다. 실제 서비스의 측정값이 아니라, 방식을 비교하기 위해 다음 요구사항을 정합니다.

  • 새 주문이 들어오면 열린 화면의 배지와 알림 목록에 반영합니다.
  • 데이터는 주로 서버에서 브라우저로 흐르고, 관리자는 가끔 읽음 처리를 보냅니다.
  • 여러 탭을 열어 둘 수 있으며, 서버 앞에는 리버스 프록시가 있습니다.
  • 연결이 끊긴 사이 생긴 알림도 복구하고, 이미 표시한 알림을 중복으로 쌓지 않습니다.

먼저 늦게 보여도 되는지, 브라우저도 계속 메시지를 보내는지, 재접속 때 어디부터 복구할지를 나눕니다. 알림 수신과 읽음 처리가 반드시 같은 통로를 써야 하는 것은 아닙니다.

**폴링(polling)**은 브라우저가 반복해서 새 데이터를 묻는 방식입니다. **서버 전송 이벤트(Server-Sent Events, SSE)**는 열린 연결로 서버가 텍스트 이벤트를 보내는 단방향 방식입니다.[4] WebSocket은 연결을 만든 뒤 같은 연결에서 데이터를 보내고 받는 API를 제공합니다.[3] “연결이 열려 있다”는 공통점보다 누가 언제 말을 보내는지가 선택에 더 중요합니다.

아래 코드는 같은 로컬 데모의 요청 계약을 기준으로 합니다. 알림 생성은 POST /api/notify, 목록 조회는 /api/notifications, SSE는 /api/stream, WebSocket은 /ws입니다. 이 경로와 메시지 이름은 예제를 위해 정한 것이며 표준이 정한 주소가 아닙니다. 서버에는 인증을 넣지 않았으므로 공개 서비스에 그대로 노출하는 코드는 아닙니다.

출력은 데모의 실제 실행 기록입니다. 포트, 알림 번호, 시각은 실행 당시 값이지 성능 수치가 아닙니다. 브라우저 코드는 해당 서버의 페이지에서 실행합니다.

같은 알림을 세 방식으로 받기

폴링: 요청할 때마다 이후 목록을 받습니다

이 데모에서 서버는 받은 위치를 since로 전달받아 더 큰 ID의 알림을 돌려줍니다. 서버 측 핵심은 다음 필터입니다. notifications는 메모리에 보관한 알림 배열이고, after는 이 글의 예제 함수입니다.

const after = (id) => notifications.filter((n) => n.id > id);

// /api/notifications 요청을 처리하는 서버 코드 발췌
const items = after(Number(url.searchParams.get("since") ?? 0));
res.writeHead(200, {
  "Content-Type": "application/json",
  "Cache-Control": "no-store",
});
res.end(JSON.stringify({ items, lastId }));

브라우저에서는 응답을 처리한 뒤 다음 요청을 예약하도록 작성할 수 있습니다. 고정 간격 타이머에서 요청을 무조건 시작하는 대신, 앞 요청이 끝난 뒤 기다리는 형태입니다. 아래 대기 시간은 동작을 보기 위한 예제 값입니다.

let lastSeen = 0;
const POLL_DELAY_MS = 5000;

async function poll() {
  try {
    const response = await fetch(
      `/api/notifications?since=${lastSeen}`,
      { cache: "no-store" },
    );
    if (!response.ok) throw new Error("알림 조회 실패");
    const { items } = await response.json();
    for (const item of items) {
      console.log(item.text);
      lastSeen = item.id;
    }
  } catch (error) {
    console.error(error);
  } finally {
    setTimeout(poll, POLL_DELAY_MS);
  }
}
poll();

이미 알림을 받은 위치로 조회한 실제 결과는 빈 목록입니다. 서버에 연결할 수 있다는 사실과 새 알림이 있다는 사실을 구분할 수 있습니다.

$ curl "http://127.0.0.1:4110/api/notifications?since=2"
{"items":[],"lastId":2}

폴링은 읽기 쉬운 요청·응답 흐름을 유지하는 대신, 변경이 없어도 조회를 반복합니다. 지연은 다음 요청을 기다리는 시간에 요청·처리 시간까지 더해집니다. 따라서 “항상 한 주기 안에 도착한다”는 보장으로 설명하면 안 됩니다. 위 코드는 비교용 루프이며, 실제 화면에서는 화면을 떠날 때 예약과 진행 중인 요청을 정리하는 수명 관리도 붙여야 합니다.

SSE: 응답을 끝내지 않고 이벤트를 보냅니다

SSE 응답의 형식은 text/event-stream이며, 이벤트는 빈 줄로 구분합니다.[4] id는 마지막 이벤트 ID를 갱신하고, event는 이벤트 이름, data는 전달할 데이터를 나타냅니다.[4] 서버는 새 알림을 만들 때 다음 함수를 호출합니다.

function writeSse(res, item) {
  res.write(`id: ${item.id}\n`);
  res.write("event: notification\n");
  res.write(`data: ${JSON.stringify(item)}\n\n`);
}

브라우저에서는 EventSource를 생성하고 이름 있는 이벤트를 addEventListener로 받습니다.[4] 이 데모가 정한 이벤트 이름은 notification입니다.

const source = new EventSource("/api/stream");
source.addEventListener("notification", (event) => {
  console.log(JSON.parse(event.data));
});
source.onerror = () => console.log("연결 상태 확인 필요");
// 화면에서 수신을 끝낼 때: source.close();

실제 실행에서는 마지막으로 받은 알림을 요청 헤더에 지정하고 연결했습니다. 서버에 남아 있던 다음 알림이 먼저 도착했고, 연결 중 새로 만든 알림이 그 뒤에 왔습니다.

$ curl -N -H 'Last-Event-ID: 1' http://127.0.0.1:4110/api/stream
retry: 3000

id: 2
event: notification
data: {"id":2,"text":"주문 #1002 결제 완료","at":"2026-11-16T15:45:13.590Z"}

id: 3
event: notification
data: {"id":3,"text":"주문 #1003 결제 완료","at":"2026-11-16T15:45:14.775Z"}

retry는 재연결 대기 시간을 밀리초로 전달하는 필드입니다.[4] 다만 명세는 브라우저가 추가로 기다리는 경우도 허용하므로, 지정한 시간에 반드시 연결이 복구된다는 뜻은 아닙니다.[2] 이 출력은 서버의 재전송과 이어 보내기를 확인한 것이지, 브라우저 자동 재연결을 curl이 대신 검증한 결과는 아닙니다.

이름 있는 이벤트를 보내 놓고 onmessage에만 처리 코드를 넣는 실수도 주의해야 합니다. event가 지정되면 그 이름에 맞는 수신 처리가 필요합니다.[1] 네트워크에는 데이터가 보이는데 목록이 바뀌지 않는다면 연결부터 다시 만들기 전에 이벤트 이름을 대조합니다.

WebSocket: 복구 요청과 응답을 같은 연결로 주고받습니다

WebSocket에서는 open 이후 send()로 보내고 message로 받습니다.[3] 데모에서는 접속 직후 마지막 ID를 보내는 hello, 읽음 확인을 요청하는 read를 직접 정의했습니다. 이들은 WebSocket 표준 메시지가 아니라 애플리케이션의 약속입니다.

const socket = new WebSocket("ws://127.0.0.1:4110/ws");
socket.addEventListener("open", () => {
  socket.send(JSON.stringify({ type: "hello", lastId: 2 }));
  socket.send(JSON.stringify({ type: "read", id: 3 }));
});
socket.addEventListener("message", (event) => {
  console.log("받음:", event.data);
});
// 실험을 끝낼 때: socket.close();

로컬에서 연결해 같은 메시지를 보냈을 때 기록한 출력입니다. 수신 위치 뒤의 알림과 읽음 요청에 대한 응답이 같은 연결로 돌아왔습니다.

받음: {"type":"notification","item":{"id":3,"text":"주문 #1003 결제 완료","at":"2026-11-16T15:45:14.775Z"}}
받음: {"type":"read-ack","id":3}

다만 이 데모의 읽음 처리는 받은 번호를 되돌려줄 뿐입니다. 응답이 왔다고 데이터베이스에 읽음 상태가 저장됐다고 해석하면 안 됩니다. 실제 기능이라면 권한 검사와 저장 성공 이후에 확인 메시지를 보내야 합니다. 위 연결 주소도 로컬 실험용이므로 배포 환경의 보안 연결 주소로 그대로 사용할 수는 없습니다.

양방향 전송이 된다는 사실만으로 재접속 정책까지 완성되지는 않습니다. 이 예제에는 연결 종료 후 다시 접속하는 로직이 없습니다. 운영 코드에는 재시도 간격을 늘리는 백오프(backoff), 시도를 분산하는 지터(jitter), 로그아웃이나 화면 종료 때 재시도를 중단하는 조건을 별도로 정해야 합니다.

재연결과 알림 복구는 다른 일입니다

SSE에서 브라우저는 재연결할 때 마지막 이벤트 ID가 비어 있지 않으면 Last-Event-ID 헤더로 전달합니다.[2] 여기까지가 브라우저의 역할입니다. 서버가 그 ID 뒤의 알림을 어디에 보관하는지, 얼마나 보관하는지까지 브라우저가 해결해 주지는 않습니다.

데모 서버는 요청에서 받은 ID를 after에 넣고 남아 있는 알림을 먼저 보냅니다. 앞의 출력에서 이전 알림이 다시 나타난 이유는 자동 재연결이라는 이름의 마법이 아니라 이 조회 코드입니다.

const lastSeen = Number(req.headers["last-event-id"] ?? 0);
for (const item of after(lastSeen)) {
  writeSse(res, item);
}

연결을 끊는 실험과 프로세스를 재시작하는 실험은 다릅니다. 데모에서 연결만 끊으면 배열은 남지만, 서버 프로세스를 종료하면 메모리의 알림 목록과 ID 카운터도 사라집니다. 연결 복구가 성공했다고 배포 중 알림 유실까지 막았다고 주장할 수 없습니다.

운영 설계에서는 전송 방식보다 앞서 복구 계약을 정하는 편이 낫습니다. 알림 이력과 위치를 영속 저장하고, 클라이언트가 보낸 위치가 보관 범위보다 오래되면 현재 목록을 다시 받도록 정합니다. 새 연결이 다른 서버로 가더라도 같은 이력을 읽을 수 있어야 합니다. 이는 폴링에도 필요한 조건이며, 매번 새 요청을 보낸다는 이유로 자동 충족되지 않습니다.

새 EventSource 객체의 마지막 이벤트 ID는 빈 문자열에서 시작합니다.[2] 따라서 같은 객체의 자동 재연결과 페이지를 새로 연 뒤의 복구도 구분해야 합니다. 새 화면의 초기 목록 조회와 이후 스트림 사이에서 알림이 빠지지 않도록, 시작 위치를 넘기는 절차를 서버와 함께 설계합니다.

화면에는 중복 적용 방어도 필요합니다. 다음은 같은 ID의 알림을 두 번 쌓지 않는 최소 예입니다. 이 집합은 화면 수명 동안만 유지되므로 새로고침 이후 복구나 서버 저장을 대신하지 않습니다.

const seen = new Set();
function displayOnce(item) {
  if (seen.has(item.id)) return;
  console.log(item.text);
  seen.add(item.id);
}

이벤트를 수신했다는 사실과 업무 처리가 끝났다는 사실도 분리합니다. 배지를 갱신하다 실패하거나 읽음 저장이 거절될 수 있습니다. 전송 계층의 수신 위치만 보고 업무 성공을 판정하지 않고, 실패한 처리를 다시 조회하거나 재시도할 기준을 남깁니다.

배포 뒤 증상으로 점검할 네 가지

이벤트가 몇 개씩 몰려 도착합니다

증상: 서버는 알림을 만들었는데 화면에는 나중에 묶여 나타납니다. 원인 후보: 이벤트를 끝내는 빈 줄이 빠졌거나, 전송 경로의 버퍼가 데이터를 보류하고 있을 수 있습니다. 명세도 블록 단위 버퍼링이 이벤트 전달을 지연시킬 수 있다고 설명합니다.[2]

대응: 서버에 직접 연결한 결과와 프록시를 통과한 결과를 비교하고, 먼저 메시지 경계를 확인합니다. MDN 서버 예제에는 X-Accel-Buffering: no 헤더와 출력 버퍼를 비우는 처리가 함께 있습니다.[4] 다만 이 헤더 하나로 모든 중간 장비의 버퍼링이 꺼졌다고 단정하지 말고, 실제 경로에서 작은 이벤트가 바로 전달되는지 검증해야 합니다.

데이터가 없을 때 연결이 끊기는 문제는 메시지가 몰리는 문제와 별도로 봅니다. SSE에서는 콜론으로 시작하는 주석 줄을 주기적으로 보내 타임아웃 예방에 사용할 수 있습니다.[4] 주기는 배포 경로의 설정을 확인해 정하고, 연결 유지 신호가 유실 복구까지 보장한다고 해석하지 않습니다.

탭을 더 열자 일부 화면만 연결을 기다립니다

증상: 처음 연 탭은 정상인데 추가한 탭의 스트림이 열리지 않습니다. 원인 후보: MDN은 HTTP/2를 사용하지 않는 SSE에서 브라우저와 도메인 단위의 연결 한도가 6개라고 경고합니다.[4] 탭마다 독립된 여유분을 받는 것으로 계산하면 놓치기 쉬운 조건입니다.

대응: 개발자 도구에서 실제 연결 프로토콜과 열린 스트림을 확인합니다. HTTP/2에서는 동시 스트림 수를 클라이언트와 서버가 협상합니다.[4] 프로토콜 전환 가능 여부를 검토하고, 화면을 떠난 연결이 계속 남아 있지 않은지도 봅니다. 수신을 종료할 때는 EventSource.close()로 연결을 닫습니다.[1]

폴링 응답은 비어 있는데 요청은 계속 쌓입니다

증상: 알림은 거의 없는데 조회 요청과 빈 응답이 이어집니다. 원인: 변경 여부와 무관하게 묻는 폴링 방식의 비용입니다. 요청이 느려졌는데도 고정 간격으로 새 요청을 시작하면, 이전 응답이 끝나기 전에 다음 요청까지 겹칠 수 있습니다.

대응: 앞 예제처럼 응답 처리 후 다음 조회를 예약하고, 화면이 보이지 않을 때의 중단 정책과 복귀 시 즉시 조회를 함께 정합니다. 요청 실패도 무조건 같은 간격으로 반복하기보다 대기 시간을 늘릴지 판단합니다. 변경 빈도에 비해 빈 응답이 많고 지연 요구가 엄격하다면 SSE 전환을 검토하되, 실제 요청량을 측정하고 결정합니다.

메시지는 오는데 화면이 점점 느려집니다

증상: 연결 상태는 정상인데 목록 갱신이 밀리거나 메모리 사용이 증가합니다. 원인 후보: 받는 속도가 처리 속도를 넘을 수 있습니다. MDN은 WebSocket API가 백프레셔(backpressure)를 제공하지 않아, 이런 상황에서 버퍼가 메모리를 채우거나 앱이 응답하지 않을 수 있다고 경고합니다.[3]

대응: 연결을 더 빠르게 만드는 대신 무엇을 생략할 수 있는지 정합니다. 최신 배지 값만 필요하면 중간 갱신을 합칠 수 있지만, 주문 이력이라면 삭제해서는 안 됩니다. 이력은 보관한 뒤 나눠 조회하고, 스트림은 변경 사실을 알려 주도록 역할을 줄이는 방법도 있습니다. 처리 대기량과 표시 완료까지 걸린 시간을 함께 관찰해야 전송 성공과 화면 성공을 구분할 수 있습니다.

이 요구사항에서는 SSE를 먼저 고르되, 알림 이력의 보관과 복구를 별도 작업으로 잡습니다. 드물게 보내는 읽음 처리는 일반 요청으로 분리할 수 있으므로, 그 기능만으로 양방향 스트림이 필요해지지는 않습니다.

  • 일정한 조회 지연을 허용하고 반복 요청 비용도 감당할 수 있다면 폴링을 고릅니다. 연결을 유지하는 운영보다 요청·응답 흐름의 단순함을 우선하는 선택입니다.
  • 변경을 빠르게 받아야 하고 데이터가 주로 서버에서 화면으로 흐른다면 SSE를 고릅니다. 재연결 지원을 활용하되, 서버의 재전송과 화면의 중복 방어까지 완료 조건에 넣습니다.
  • 양쪽이 계속 메시지를 주고받아야 한다면 WebSocket을 고릅니다. 애플리케이션 메시지 규약, 재접속, 유실 복구, 느린 수신자 대응 비용을 함께 받아들입니다.

선택을 바꿔도 알림 ID와 복구 계약은 유지할 수 있게 설계하는 편이 좋습니다. 전송 방법을 바꾸는 일과 “어디까지 처리했는가”를 다시 정의하는 일을 분리하면, 폴링으로 시작했다가 스트림을 도입할 때도 변경 범위를 줄일 수 있습니다.

프론트엔드 팀이 해 볼 것

  1. 개발 환경에서 스트림만 끊는 경우와 서버 프로세스를 재시작하는 경우를 나눠 시험하고, 각각 어떤 알림이 복구되는지 기록합니다.
  2. 프록시를 통과한 연결과 서버 직접 연결을 비교해, 이벤트가 생성된 순서대로 지연 없이 전달되는지 확인합니다.
  3. 마지막 수신 위치가 보관 범위 밖일 때의 처리와 새 화면의 초기 동기화 절차를 API 계약에 적습니다.
