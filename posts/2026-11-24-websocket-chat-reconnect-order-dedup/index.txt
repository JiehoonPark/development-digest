17:T61dc,<h2 id="채팅-연결-관리를-맡았다고-가정해-봅시다">채팅 연결 관리를 맡았다고 가정해 봅시다</h2>
<p>고객 상담 채팅의 WebSocket 연결 관리를 맡았다고 가정해 봅시다. 설계를 설명하기 위해 정한 요구사항입니다.</p>
<ul>
<li>와이파이가 바뀌거나 노트북을 덮었다 열어도 새로고침 없이 대화를 이어 갑니다.</li>
<li>끊긴 사이 상대가 보낸 메시지도 빠짐없이, 보낸 순서대로 보입니다.</li>
<li>내가 보낸 메시지는 재전송이 일어나도 한 번만 저장되고 한 번만 보입니다.</li>
<li>채팅 서버는 두 대 이상이고, 같은 방 사람이 서로 다른 서버에 붙을 수 있습니다.</li>
</ul>
<p>WebSocket API는 연결을 연 뒤 같은 연결로 메시지를 보내고 받게 해 줍니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup> 위 네 가지는 API가 대신해 주지 않습니다. 연결 확인, 재연결 시점, 메시지 번호, 서버 사이 전달은 모두 애플리케이션의 약속입니다.</p>
<p>출력은 Node.js 22에서 로컬 데모를 실제로 실행한 기록입니다. 브로커 프로세스 하나가 메시지 저장소와 Redis Pub/Sub 역할을 흉내 내고, 채팅 서버 A·B가 그 브로커에 붙습니다. 클라이언트는 브라우저와 같은 전역 <code>WebSocket</code>만 씁니다. 시간 값은 성능 측정이 아닙니다.</p>
<figure><img src="/development-digest/figures/websocket-chat-fanout.svg" alt="서버 A에 붙은 alice의 메시지가 저장소에서 번호를 받고 pub/sub으로 서버 B의 bob에게 가는 흐름과, 재연결한 bob이 저장소에서 빠진 번호를 읽어 오는 흐름" loading="lazy"><figcaption>그림 1 · 순서와 복구는 저장소가, 실시간 전달은 pub/sub이 맡는다</figcaption></figure>
<h2 id="끊김을-알아채고-다시-붙기">끊김을 알아채고 다시 붙기</h2>
<h3 id="서버-쪽-하트비트-프로토콜-ping과-pong">서버 쪽 하트비트: 프로토콜 Ping과 Pong</h3>
<p>랜선을 뽑은 것처럼 끊기면 서버와 클라이언트 모두 끊긴 줄 모르는 상태가 생길 수 있습니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 그래서 주기적으로 상대가 응답하는지 확인하는 하트비트(heartbeat)를 둡니다.</p>
<p>WebSocket 프로토콜에는 이 용도의 제어 프레임이 있습니다. Ping의 opcode는 <code>0x9</code>, Pong은 <code>0xA</code>이고, Ping을 받은 쪽은 Close 프레임을 이미 받은 경우가 아니면 Pong으로 응답해야 합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> Node.js의 <code>ws</code> 라이브러리는 이 Pong을 자동으로 보냅니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 아래 데모 서버 코드는 <code>ws</code> README 예제와 같은 구조입니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js">wss.<span class="hljs-title function_">on</span>(<span class="hljs-string">"connection"</span>, <span class="hljs-function">(<span class="hljs-params">ws</span>) =></span> {

  ws.<span class="hljs-title function_">on</span>(<span class="hljs-string">"pong"</span>, <span class="hljs-function">() =></span> { ws.<span class="hljs-property">isAlive</span> = <span class="hljs-literal">true</span>; });

<span class="hljs-keyword">const</span> interval = <span class="hljs-built_in">setInterval</span>(<span class="hljs-function">() =></span> {

<p><code>close()</code> 대신 <code>terminate()</code>를 씁니다. <code>terminate()</code>는 연결을 즉시 없애고 <code>close()</code>는 닫기 타이머를 기다립니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 자동 Pong을 끈(<code>autoPong: false</code>) 클라이언트를 붙여 1000ms 간격으로 돌린 결과입니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup></p>
<pre data-lang="text"><code class="hljs language-text">   76ms silent 연결됨

</code></pre>
<p><code>1006</code>은 닫기 프레임 없이 비정상으로 닫혔다는 예약 코드입니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> 사용자가 나간 것이 아니므로 클라이언트는 재연결 대상으로 봅니다.</p>
<h3 id="브라우저-쪽-하트비트-메시지로-묻기">브라우저 쪽 하트비트: 메시지로 묻기</h3>
<p>브라우저 <code>WebSocket</code>의 인스턴스 메서드는 <code>close()</code>와 <code>send()</code>뿐입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 프로토콜 Ping을 보낼 수 없으므로 일반 메시지로 묻고 답을 기다립니다.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-title function_">startHeartbeat</span>(<span class="hljs-params">socket</span>) {
  <span class="hljs-variable language_">this</span>.<span class="hljs-property">lastPongAt</span> = <span class="hljs-title class_">Date</span>.<span class="hljs-title function_">now</span>();

<p>서버는 <code>ping</code>에 <code>pong</code>으로 답하고, 클라이언트는 받을 때마다 <code>lastPongAt</code>을 갱신합니다. 연결만 받고 아무 응답도 하지 않는 서버에 간격 1000ms, 제한 3000ms로 붙인 결과입니다.</p>
<pre data-lang="text"><code class="hljs language-text"> 3614ms blackhole: 연결 받음

<p>버린 소켓의 <code>close</code> 이벤트가 새 연결이 열린 뒤에 왔습니다. 여기서 재연결을 또 시작하면 연결이 두 개가 됩니다. 데모는 버릴 때 <code>this.socket</code>을 먼저 비우고, <code>close</code> 처리기에서 <code>socket !== this.socket</code>이면 무시합니다.</p>
<h3 id="다시-붙는-간격-지수-백오프와-지터">다시 붙는 간격: 지수 백오프와 지터</h3>
<p>상한 있는 지수 백오프(capped exponential backoff)는 시도마다 대기 시간에 일정한 수를 곱하되 최대값을 넘지 않게 하는 방식입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> AWS 아키텍처 블로그의 시뮬레이션에서는 백오프만으로는 호출이 여전히 뭉쳐 있었고, 무작위성을 더하는 지터(jitter)를 넣자 호출이 거의 일정한 비율로 퍼졌습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 그 글은 대기 시간 전체를 무작위로 고르는 방식을 "Full Jitter"라고 부릅니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-keyword">export</span> <span class="hljs-keyword">const</span> <span class="hljs-variable constant_">BASE_MS</span> = <span class="hljs-number">500</span>;
<span class="hljs-keyword">export</span> <span class="hljs-keyword">const</span> <span class="hljs-variable constant_">CAP_MS</span> = <span class="hljs-number">8000</span>;
<span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">backoffDelay</span>(<span class="hljs-params">attempt, random = <span class="hljs-built_in">Math</span>.random</span>) {
  <span class="hljs-keyword">const</span> ceiling = <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">min</span>(<span class="hljs-variable constant_">CAP_MS</span>, <span class="hljs-variable constant_">BASE_MS</span> * <span class="hljs-number">2</span> ** attempt);
  <span class="hljs-keyword">return</span> <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">floor</span>(<span class="hljs-title function_">random</span>() * ceiling);
}
</code></pre>
<p>상한은 500ms에서 두 배씩 늘어 <code>attempt=4</code>부터 8000ms에 머뭅니다. 같은 순간 끊긴 클라이언트 1000개의 첫 재시도 시각을 100ms 칸으로 센 결과입니다. 지터 없음은 <code>random</code>에 1에 가까운 고정값을 넘겼습니다.</p>
<pre data-lang="text"><code class="hljs language-text">지터 없음(1000개):
  0~99ms: 0
  100~199ms: 0
  200~299ms: 0
  300~399ms: 0
  400~499ms: 1000
전체 지터(1000개):
  0~99ms: 200
  100~199ms: 187
  200~299ms: 230
  300~399ms: 185
  400~499ms: 198
</code></pre>
<p>시도 횟수는 <code>open</code>이 아니라 놓친 메시지까지 받은 뒤 0으로 되돌립니다. 열리자마자 서버가 끊는 상황에서 <code>open</code>마다 초기화하면 대기 시간이 첫 단계에 머뭅니다.</p>
<h2 id="순서와-중복은-메시지-번호로-맞춥니다">순서와 중복은 메시지 번호로 맞춥니다</h2>
<h3 id="받는-쪽-seq로-버리고-기다리기">받는 쪽: seq로 버리고 기다리기</h3>
<p>저장소가 방마다 1씩 늘어나는 번호 <code>seq</code>를 붙인다고 정합니다. 클라이언트는 마지막으로 화면에 올린 번호 <code>lastSeq</code>만 기억합니다. 같거나 작은 번호는 중복이고, 건너뛴 번호는 앞 번호가 올 때까지 보관합니다.</p>
<pre data-lang="js"><code class="hljs language-js"><span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">createInbox</span>(<span class="hljs-params">onShow</span>) {
  <span class="hljs-keyword">let</span> lastSeq = <span class="hljs-number">0</span>;
  <span class="hljs-keyword">const</span> early = <span class="hljs-keyword">new</span> <span class="hljs-title class_">Map</span>(); <span class="hljs-comment">// 앞 번호가 아직 안 온 메시지</span>
  <span class="hljs-keyword">return</span> {
    <span class="hljs-keyword">get</span> <span class="hljs-title function_">lastSeq</span>() { <span class="hljs-keyword">return</span> lastSeq; },
    <span class="hljs-title function_">receive</span>(<span class="hljs-params">msg</span>) {
      <span class="hljs-keyword">if</span> (msg.<span class="hljs-property">seq</span> &#x3C;= lastSeq || early.<span class="hljs-title function_">has</span>(msg.<span class="hljs-property">seq</span>)) <span class="hljs-keyword">return</span> <span class="hljs-string">"duplicate"</span>;
      <span class="hljs-keyword">if</span> (msg.<span class="hljs-property">seq</span> > lastSeq + <span class="hljs-number">1</span>) { early.<span class="hljs-title function_">set</span>(msg.<span class="hljs-property">seq</span>, msg); <span class="hljs-keyword">return</span> <span class="hljs-string">"gap"</span>; }
      <span class="hljs-title function_">onShow</span>(msg);

        <span class="hljs-keyword">const</span> next = early.<span class="hljs-title function_">get</span>(lastSeq + <span class="hljs-number">1</span>);
        early.<span class="hljs-title function_">delete</span>(next.<span class="hljs-property">seq</span>);
        <span class="hljs-title function_">onShow</span>(next);

<p>1, 3, 2, 2, 4 순서로 넣은 결과입니다. 3은 보관됐다가 2가 오자 함께 표시되고, 두 번째 2는 버려졌습니다.</p>
<pre data-lang="text"><code class="hljs language-text">  화면에 표시: #1 안녕하세요
도착 #1 → shown
도착 #3 → gap
  화면에 표시: #2 두 번째
  화면에 표시: #3 세 번째
도착 #2 → shown
도착 #2 → duplicate
  화면에 표시: #4 네 번째
도착 #4 → shown
lastSeq=4
</code></pre>
<p>번호는 한 곳에서 매깁니다. 서버마다 따로 붙이거나 클라이언트 시각으로 정렬하면 서버가 둘 이상일 때 같은 번호나 뒤바뀐 순서가 생깁니다.</p>
<h3 id="보내는-쪽-ack가-사라져도-한-번만-저장하기">보내는 쪽: ack가 사라져도 한 번만 저장하기</h3>
<p>저장은 됐는데 확인 응답(ack)이 오기 전에 끊기면, 클라이언트는 실패로 보고 다시 보냅니다. 서버가 이를 새 메시지로 받으면 같은 말이 두 번 저장됩니다. 그래서 클라이언트는 메시지마다 <code>crypto.randomUUID()</code>로 <code>clientId</code>를 만들어 ack를 받을 때까지 보관하고, 재연결 뒤 다시 보냅니다. 서버는 같은 <code>clientId</code>가 오면 저장하지 않고 처음 번호로 ack만 보냅니다.</p>
<p>서버 A가 1번을 저장한 직후 ack 없이 끊도록 만든 실행입니다(clientId는 줄였습니다).</p>
<pre data-lang="text"><code class="hljs language-text">  430ms [A] seq=1 저장 후 ack 보내기 전에 연결 끊김(재현)
  433ms alice close code=1006 wasClean=false
  434ms alice 1번째 재시도 443ms 뒤
  885ms [B] alice 입장 lastSeq=0 → 놓친 메시지 1개 전송
  888ms [B] clientId=dfdc957c-… 이미 저장됨 → seq=1 로 ack 만 다시 보냄
 1930ms alice outbox 남은 수: 0
 1931ms bob 화면: #1 한 번만 보여야 함
</code></pre>
<p>alice는 서버 B로 재연결했지만, 중복 검사를 공유 저장소에서 하므로 1번은 한 번만 저장됐습니다.</p>
<h3 id="끊긴-사이-메시지-lastseq부터-이어-받기">끊긴 사이 메시지: lastSeq부터 이어 받기</h3>
<p>재연결하면 <code>open</code> 이벤트 안에서 <code>lastSeq</code>를 담은 <code>hello</code>를 보내고, 서버는 그보다 큰 번호를 저장소에서 읽어 보냅니다. <code>open</code> 전에 <code>send()</code>를 부르면 <code>InvalidStateError</code>가 납니다.<sup class="cite"><a href="#source-9" aria-label="출처 9">[9]</a></sup> bob을 끊은 사이 alice가 두 번 보낸 실험입니다.</p>
<pre data-lang="text"><code class="hljs language-text">  628ms bob 연결을 강제로 끊음(네트워크 끊김 흉내)
  635ms bob close code=4000 wasClean=true
  635ms bob 1번째 재시도 293ms 뒤
  935ms bob 화면: #2 alice: 끊긴 사이 1
  935ms bob 화면: #3 alice: 끊긴 사이 2
  936ms [A] bob 입장 lastSeq=1 → 놓친 메시지 2개 전송
 2153ms bob 화면: #1, #2, #3
</code></pre>
<p>bob은 처음의 B가 아니라 A로 재연결했지만 빠진 번호를 받았습니다. 서버 로그가 화면 줄보다 늦게 찍힌 것은 서버가 별도 프로세스라 출력이 늦게 합쳐졌기 때문입니다.</p>
<h2 id="서버가-여러-대일-때-pubsub이-맡는-일">서버가 여러 대일 때 pub/sub이 맡는 일</h2>
<p>각 서버는 자기에게 붙은 연결만 압니다. 서버 A가 메시지를 저장한 뒤 자기 연결에만 보내면 B에 붙은 bob은 받지 못합니다. 같은 시나리오를 pub/sub 없이, 그리고 있이 실행한 결과입니다.</p>
<pre data-lang="text"><code class="hljs language-text"># --no-pubsub
  444ms alice 화면: #1 alice: A 서버에서 보냄
  742ms bob 화면 메시지 수: 0
# pub/sub
  430ms alice 화면: #1 alice: A 서버에서 보냄
  430ms bob 화면: #1 alice: A 서버에서 보냄
  729ms bob 화면 메시지 수: 1
</code></pre>
<p>Redis Pub/Sub에서 발행자는 특정 수신자가 아니라 채널로 보내고, 구독자는 관심 있는 채널을 구독해 받습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 모든 채팅 서버가 방 채널을 구독하고, 저장한 서버가 <code>room:lobby</code> 같은 채널로 발행하면 각 서버가 자기 연결에 전달합니다.</p>
<p>Redis 문서는 Pub/Sub이 at-most-once 전달이며, 구독자가 오류나 연결 끊김으로 처리하지 못한 메시지는 영영 사라진다고 설명합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 그래서 저장을 먼저 하고 pub/sub은 알림 통로로만 씁니다. 더 강한 보장이 필요하면 메시지를 보관하고 at-least-once 전달도 지원하는 Redis Streams를 검토할 수 있습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<aside class="callout-rule" aria-label="기억할 규칙"><p class="callout-head"><span class="callout-tag">규칙</span><strong>서버가 여러 대일 때 나누는 역할</strong></p><ol><li>번호와 중복 검사는 공유 저장소 한 곳에서</li><li>pub/sub은 저장이 끝난 메시지를 알리는 데만</li><li>재연결 복구는 pub/sub이 아니라 저장소 조회로</li></ol></aside>
<h2 id="배포-뒤-증상으로-점검할-네-가지">배포 뒤 증상으로 점검할 네 가지</h2>
<h3 id="서버를-재시작하자-접속이-한꺼번에-몰립니다">서버를 재시작하자 접속이 한꺼번에 몰립니다</h3>
<p><strong>증상:</strong> 배포 직후 연결 수가 뾰족하게 솟고, 실패한 연결이 다음 주기에 또 몰립니다. <strong>원인 후보:</strong> 재연결 대기에 지터가 없거나, 시도 횟수를 <code>open</code>마다 초기화해 백오프가 첫 단계에 머뭅니다.</p>
<p><strong>대응:</strong> <code>backoffDelay</code>처럼 상한까지 늘리고 0과 상한 사이에서 고릅니다. AWS의 비교에서 지터 없는 지수 백오프는 지터를 넣은 방식들보다 일도 많고 시간도 더 걸렸습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h3 id="다른-서버에-붙은-사람-메시지가-가끔-빠집니다">다른 서버에 붙은 사람 메시지가 가끔 빠집니다</h3>
<p><strong>증상:</strong> 드물게 한 개가 빠지고, 새로고침하면 보입니다. <strong>원인 후보:</strong> 실시간 전달만 믿고 있습니다. Pub/Sub은 처리하지 못한 메시지를 다시 보내지 않습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p><strong>대응:</strong> 번호가 건너뛴 것을 신호로 저장소를 다시 읽습니다. 데모 브로커가 2번 전달을 일부러 버리게 하고, 클라이언트가 <code>gap</code> 뒤 500ms 안에 2번이 오지 않으면 <code>resync</code>를 보내게 했습니다.</p>
<pre data-lang="text"><code class="hljs language-text">  484ms [broker] seq=2 전달 유실(재현)
  536ms bob #3 → gap
 1042ms [B] bob resync lastSeq=1 → 2개 전송
 1042ms bob 화면: #2 alice: 둘 (pub/sub에서 유실)
 1042ms bob 화면: #3 alice: 셋
</code></pre>
<p>이 방법은 다음 메시지가 와야 빈틈을 압니다. 방의 마지막 메시지 유실은 드러나지 않으므로 화면이 다시 보일 때 한 번 <code>resync</code>하는 규칙을 함께 둡니다.</p>
<h3 id="로그아웃했는데-계속-다시-붙으려-합니다">로그아웃했는데 계속 다시 붙으려 합니다</h3>
<p><strong>증상:</strong> 토큰이 만료된 뒤에도 백오프 상한 간격으로 끝없이 재연결합니다. <strong>원인 후보:</strong> 모든 <code>close</code>를 재연결 대상으로 처리합니다.</p>
<p><strong>대응:</strong> 서버가 이유를 닫기 코드로 알립니다. <code>4000</code><del><code>4999</code>는 애플리케이션끼리 약속해 쓰는 사설 범위이고<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup>, 브라우저 <code>close()</code>도 <code>1000</code> 또는 <code>3000</code></del><code>4999</code>만 받습니다.<sup class="cite"><a href="#source-10" aria-label="출처 10">[10]</a></sup> 데모는 <code>4001</code>을 인증 만료로 정했고, 클라이언트는 <code>close code=4001</code>을 받자 재연결하지 않았습니다.</p>
<h3 id="연결은-정상인데-화면이-점점-느려집니다">연결은 정상인데 화면이 점점 느려집니다</h3>
<p><strong>증상:</strong> 메시지가 몰리는 방에서 입력이 밀리고 메모리가 늘어납니다. <strong>원인 후보:</strong> <code>WebSocket</code> 인터페이스는 백프레셔(backpressure)를 지원하지 않아, 처리보다 빨리 도착한 메시지가 메모리를 채우거나 앱을 멈추게 할 수 있습니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<p><strong>대응:</strong> 받은 메시지를 모아서 한 번에 그립니다. 보내는 쪽은 <code>bufferedAmount</code>로 아직 전송되지 않은 바이트 수를 볼 수 있고, 이 값은 연결이 닫혀도 0으로 돌아가지 않으므로 <code>readyState</code>도 함께 봅니다.<sup class="cite"><a href="#source-11" aria-label="출처 11">[11]</a></sup></p>
