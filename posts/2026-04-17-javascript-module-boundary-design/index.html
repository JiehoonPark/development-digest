파일만 나누면 끝일까 — JavaScript 모듈 경계 설계

모듈 경계는 폴더보다 내보내는 이름과 의존 방향에서 드러납니다. 공개 인터페이스, 순환 의존, 초기화 부수 효과, 배럴 파일을 작은 실행 예제로 점검합니다.

공개 인터페이스는 무엇을 숨길지 정하는 일

파일을 잘게 나누었는데 작은 수정마다 여러 파일을 고친다면, 분할보다 연결 방식을 살펴볼 차례입니다. CSS-Tricks 원문 필자는 JavaScript 모듈을 단순한 파일 분할 수단이 아니라 시스템의 경계를 만드는 도구로 봅니다.[1] 핵심 질문은 “어느 폴더에 둘까”에서 “밖에서 무엇을 알아도 되는가”로 바뀝니다.

기능별로 파일을 모으는 기준은 「components·hooks·utils 폴더를 버리는 이유」 글에서 다뤘습니다. 패키지 배포 형식과 진입점 설정도 별도 주제이므로 여기서는 반복하지 않습니다. 이번에는 파일 사이의 연결과 실행 시점을 다룹니다.

상태 대신 조작 방법을 내보내기

공개 인터페이스(public interface)는 다른 모듈이 사용하도록 내놓은 이름과 동작의 약속입니다. 원문은 호출자가 의존 대상의 구현 세부 사항까지 알 때 강한 결합이 생기며, 변경이 다른 모듈로 번진다고 설명합니다.[1] 다음은 내보내기 문법을 이용해 상태는 숨기고 조작 함수만 공개한 최소 예제입니다.[4]

각 코드 블록에서 파일 이름 주석에 따라 파일을 나눕니다. 예제들은 서로 독립적이며, 브라우저에서는 진입 파일을 type="module"인 스크립트로 불러옵니다.[3] 함수와 데이터 이름은 설명용으로 직접 정의한 것이며 외부 라이브러리 API가 아닙니다.

// cart.js
let itemCount = 0;

export function addItem() {
  itemCount += 1;
}

export function getItemCount() {
  return itemCount;
}

// main.js
import { addItem, getItemCount } from "./cart.js";

addItem();
console.log(getItemCount()); // 1

호출자는 개수를 보관하는 변수 이름을 몰라도 됩니다. 이 예제에서 바깥에 약속한 것은 항목을 추가하는 동작과 개수를 읽는 동작뿐입니다. 내부 저장 방식을 바꾸더라도 이 약속을 유지하는 방향으로 수정 범위를 검토할 수 있습니다.

자주 하는 실수는 내부에서 필요하다는 이유만으로 모든 이름을 내보내는 것입니다. 검토할 때는 “이 함수를 쓰는가”뿐 아니라 “외부가 이 상태를 직접 알아야 하는가”를 묻습니다. 명시적으로 공개한 목록 자체가 변경 검토의 기준이 됩니다.

정적 import는 맨 첫 줄이라는 뜻이 아니다

정적 import는 모듈의 최상위에만 올 수 있고 경로는 문자열 리터럴이어야 합니다. 함수나 조건문 안에는 둘 수 없지만, 파일의 첫 문장이어야 하는 것은 아닙니다.[3] 원문의 “파일 맨 위”라는 표현은 이 구분을 놓치기 쉬우므로 최상위 스코프 제한으로 이해해야 합니다.[1][3]

// greeting.js
export function greet() {
  return "안녕하세요";
}

// main.js
console.log(greet()); // 안녕하세요
import { greet } from "./greeting.js";

MDN은 가져오기 선언이 호이스팅되어 바인딩을 모듈 전체에서 사용할 수 있다고 설명합니다.[3] 위 배치는 문법 설명용이지 권장 스타일은 아닙니다. 선언을 위에 모으면 의존 대상을 찾기 편하지만, 배치 순서로 실행 시점을 제어하려 해서는 안 됩니다.

이처럼 문법을 제한하면 도구가 평가 전에 의존 관계를 분석할 수 있습니다.[3] 다만 분석 가능한 문법을 쓴다는 사실과 잘 설계된 의존 관계를 갖췄다는 사실은 다릅니다. 원문도 별도의 의존 규칙 없이 자유롭게 가져오면 유지보수가 어려워진다고 지적합니다.[1]

순환 의존은 값을 읽는 순간 문제가 된다

순환 의존(circular dependency)은 모듈들이 직접 또는 다른 모듈을 거쳐 서로를 참조하는 관계입니다. 원문 필자는 이런 연결이 재사용을 어렵게 하고 변경 영향을 넓힌다고 봅니다.[1] 실행 중 오류가 나는 조건과 설계상 불편한 조건을 구분해야 합니다.

선언은 연결됐지만 값은 준비되지 않았다

가져온 이름은 값의 복사본이 아니라 원본의 변경을 반영하는 라이브 바인딩(live binding)입니다.[3] 하지만 연결된 이름이 있다는 사실만으로 그 값이 초기화됐다는 뜻은 아닙니다. MDN은 순환 가져오기 중 아직 초기화되지 않은 변수를 읽으면 ReferenceError가 발생하는 예를 제시합니다.[2]

// a.js — 진입 파일
import { b } from "./b.js";
export const a = 2;

// b.js
import { a } from "./a.js";
console.log(a);
// ReferenceError: Cannot access 'a' before initialization
export const b = 1;

진입 파일을 실행하려면 먼저 의존 대상이 평가돼야 합니다. 그런데 그 의존 대상이 진입 파일의 아직 준비되지 않은 값을 읽습니다.[2] 문제는 소스에서 가져오기 문장이 위에 있는지 아래에 있는지가 아니라, 값을 읽는 시점과 초기화가 실행되는 순서입니다.[2]

반대로 MDN은 값 접근을 비동기로 미뤄 양쪽 모듈이 평가된 뒤 읽는 예가 정상 동작한다고 설명합니다.[2] 따라서 “순환 의존은 문법 오류”라고 외우면 틀립니다. 오류 없이 실행되더라도 서로의 준비 시점에 기대는 구조인지는 별도로 검토해야 합니다.

공통 값의 소유자를 따로 정하기

위 관계에서 필요한 것이 공통 값뿐이라면, 값을 소유한 모듈을 분리하는 방식으로 되돌아오는 연결을 없앨 수 있습니다. 다음은 앞의 실패 예제를 고친 설계 예시입니다. 공유할 대상을 정한 뒤 양쪽이 그 대상을 읽도록 바꿉니다.

// values.js
export const a = 2;

// b.js
import { a } from "./values.js";
console.log(a); // 2
export const b = 1;

// a.js — 진입 파일
import { a } from "./values.js";
import { b } from "./b.js";
console.log(a, b); // 2 1

이제 의존 관계는 진입 파일에서 b.js와 values.js로, b.js에서 values.js로 향합니다. 값을 소유한 파일이 호출자를 다시 가져오지 않습니다. 이 관계는 위 예제에서 직접 확인할 수 있는 설계상의 변화입니다.

다만 순환을 없애려고 모든 값을 거대한 공통 유틸 파일에 옮기는 것은 피하는 편이 좋습니다. 원문도 여러 책임을 맡은 유틸 모듈을 응집된 기능별로 나누라고 제안합니다.[1] 추출할 대상은 “여러 곳에서 필요하다”는 이유만이 아니라 하나의 책임으로 설명할 수 있어야 합니다.

가져오기만 했는데 실행되는 코드

부수 효과(side effect)는 반환값 외에 외부에서 관찰할 수 있는 변화를 만드는 동작입니다. 모듈을 가져오는 것만으로 로그를 남기거나 전역 환경을 바꾸면, 호출 코드에 함수 실행이 보이지 않아도 일이 일어납니다. 원문은 부수 효과와 공유 가변 상태 등을 암묵적 결합의 원인으로 지적합니다.[1]

가져오기 선언의 위치로 초기화를 늦출 수 없다

값을 받지 않는 import "./파일.js"는 부수 효과만을 위해 모듈을 실행하는 문법입니다. MDN은 전역 변수를 변경하는 폴리필을 대표 용도로 들며, 가져온 모듈의 부수 효과는 현재 모듈 본문보다 먼저 발생한다고 설명합니다.[3]

// startup.js
console.log("설정 적용");

// main.js
console.log("화면 시작");
import "./startup.js";
// 출력 순서:
// 설정 적용
// 화면 시작

이 예제에는 순환 의존이 없습니다. 선언이 아래에 있어도 “화면 시작” 다음에 초기화되지 않습니다. 호출자가 위에서 준비한 데이터를 가져온 모듈의 최상위 코드가 곧바로 읽으리라고 기대하면, 선언 위치와 실제 실행 순서를 혼동하게 됩니다.[3]

부수 효과 전용 가져오기 자체가 잘못은 아닙니다. 폴리필처럼 목적이 명확한 경우도 있습니다.[3] 다만 값만 꺼내 쓰려는 코드와 앱 전체를 초기화하는 코드를 같은 통로에 섞지 않는 편이 의도를 드러내기 쉽습니다.

실행 시점이 중요하면 호출로 표현하기

다음은 초기화를 이름 있는 함수로 공개하고, 입력과 호출 시점을 진입 파일에 드러낸 설계 예시입니다. 함수 내보내기와 가져오기 문법은 앞의 예제와 같습니다.[4][3]

// startup.js
export function initialize(mode) {
  console.log(`설정 적용: ${mode}`);
}

// main.js
import { initialize } from "./startup.js";

console.log("설정 준비"); // 첫 번째 출력
initialize("preview"); // 설정 적용: preview
console.log("화면 시작"); // 마지막 출력

바뀐 것은 로그 내용보다 실행 책임입니다. 초기화가 언제 필요한지 아는 진입 파일이 호출하고, 초기화 함수는 전달받은 값으로 동작합니다. 다른 코드가 이 파일의 함수를 참조한다는 이유만으로 같은 초기화를 실행할 필요도 없습니다.

자주 하는 실수는 이 변경을 멱등성 보장으로 받아들이는 것입니다. 이 함수는 호출할 때마다 로그를 남깁니다. 명시적 호출은 책임을 보이게 할 뿐이므로 중복 실행을 허용할지, 누가 호출할지는 여전히 정해야 합니다.

배럴 파일은 공개 창구이지 공짜 우회로가 아니다

배럴 파일(barrel file)은 다른 파일의 내보내기를 모아 다시 내보내는 파일입니다. 보통 진입점 역할을 하며, MDN은 export … from으로 별도의 가져오기 선언 없이 재내보낼 수 있다고 설명합니다.[4] 문제는 공개할 이름을 모으는 일과 실행할 의존성을 모으는 일이 함께 일어난다는 점입니다.

명시적으로 골라도 부수 효과는 남는다

다음은 이름을 골라 재내보내더라도 다른 의존 파일의 최상위 코드가 실행되는 예제입니다. 재내보내기 문법과 모듈 부수 효과의 동작을 결합했습니다.[4][3] 번들러 변환 없이 ES 모듈로 실행하는 상황입니다.

// login.js
export function login() {
  return "로그인 화면";
}

// metrics.js
console.log("측정 모듈 초기화");
export const metricName = "auth";

// index.js
export { login } from "./login.js";
export { metricName } from "./metrics.js";

// main.js
import { login } from "./index.js";
console.log(login());
// 출력 순서:
// 측정 모듈 초기화
// 로그인 화면

호출자는 로그인 함수만 요청했지만 배럴은 측정 모듈도 의존 대상으로 연결합니다. “이름을 하나만 가져왔다”와 “파일 하나만 평가된다”는 같은 말이 아닙니다.[3][4] 이 예제에서는 측정 초기화를 앞 절처럼 명시적 함수 호출로 옮기거나, 측정 기능을 별도 진입점으로 분리하는 선택을 검토할 수 있습니다.

원문 필자는 배럴이 가져오기 구문을 간결하게 하지만, 큰 프로젝트에서는 빌드와 트리 셰이킹 비용을 치를 수 있다고 평가합니다.[1] 이를 “배럴은 항상 번들을 크게 만든다”는 보편 법칙으로 바꾸지는 않아야 합니다. 여기서 직접 확인한 것은 위 예제의 실행 순서이지 특정 빌드 도구의 최적화 결과가 아닙니다.

전체 재내보내기와 공개 목록을 구분하기

export *는 대상의 이름 있는 내보내기를 모으지만 기본 내보내기는 포함하지 않습니다. 서로 다른 바인딩에서 같은 이름이 들어오면 충돌한 이름을 직접 가져올 때 오류가 날 수도 있습니다.[4] 공개할 목록을 의도적으로 적는 이유는 단순히 문장을 길게 쓰려는 것이 아닙니다.

위 배럴은 내보내는 이름이 드러나므로 어떤 것을 외부 계약으로 삼았는지 검토할 수 있습니다. 반면 전체 재내보내기는 내부 파일에 이름을 추가할 때 공개 목록도 넓어집니다.[4] 내부 편의를 위한 함수를 추가한 것인지, 외부에 약속할 기능을 추가한 것인지 구분하는 검토가 필요합니다.

실무에서는 경계 바깥의 호출자에게 좁은 진입점을 제공하되, 내부 파일까지 자기 배럴을 거쳐 연결할 필요가 있는지 점검하는 방식을 권합니다. 특히 내부 모듈에서 배럴을 가져왔을 때 그 배럴이 다시 자신을 재내보내면 순환 경로가 생깁니다. 파일 이름을 바꾸는 대신 실제 가져오기·재내보내기 경로를 따라가야 합니다.

정리

점검할 경계 확인할 질문 이 글의 선택 기준
공개 인터페이스 호출자가 내부 상태까지 알아야 하나? 상태보다 필요한 조작을 공개합니다
의존 방향 따라가다 출발한 모듈로 돌아오나? 공통 책임의 소유자를 정합니다
초기화 시점 가져오기만 해도 일이 일어나나? 시점이 중요한 작업은 호출로 드러냅니다
배럴 파일 공개 목록과 실행 의존성을 혼동했나? 이름을 좁히고 부수 효과도 점검합니다

원문은 모든 프로젝트에 맞는 구조는 없으며, 작은 프로젝트에 정교한 아키텍처를 적용하는 것은 과할 수 있다고 말합니다.[1] 폴더를 전부 바꾸기보다 자주 수정하는 기능의 진입 파일부터 읽어 보세요. 공개한 이름, 되돌아오는 의존성, 최상위에서 실행되는 코드만 따라가도 먼저 손댈 경계를 고를 수 있습니다.

프론트엔드 팀이 해 볼 것
