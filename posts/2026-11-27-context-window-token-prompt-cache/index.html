2026년 11월 27일 (금)토큰컨텍스트프롬프트 캐시

긴 에이전트 대화가 비싸지는 이유 — 컨텍스트 창, 토큰, 프롬프트 캐시

코딩 에이전트는 요청마다 대화 전체를 다시 보냅니다. 토큰을 직접 세고, 캐시 비용을 모의 계산하고, 큰 로그를 거르는 훅을 돌려 보며 어디서 비용과 품질이 새는지 짚습니다.

에이전트 사용량이 왜 늘었는지 설명하는 일을 맡았다고 가정해 봅시다

팀이 코딩 에이전트를 몇 달째 쓰고 있는데, 같은 일을 하는 것 같은데도 사용량이 사람마다 크게 다르다는 이야기가 나왔다고 가정해 봅시다. 설명을 위해 정한 요구사항입니다.

  • 한 번의 요청에 무엇이 실려 가는지, 토큰을 어떻게 세는지 설명할 수 있어야 합니다.
  • 프롬프트 캐시가 맞는 경우와 놓치는 경우를 구분해, 놓치는 습관을 고칠 수 있어야 합니다.
  • 긴 로그나 큰 파일을 에이전트에게 넘기는 방식을 정해야 합니다.
  • 대화를 언제 끊고 새로 시작할지 기준이 있어야 합니다.

이 글은 이 네 가지에 답합니다. 에이전트를 오래 쓸수록 "답이 이상해진다"와 "사용량이 빨리 찬다"는 불만이 같이 나오는데, 둘 다 대화에 쌓인 내용이 매 요청 다시 실려 가기 때문입니다.

기준 자료는 Claude Code·Claude API·OpenAI API 문서이고 2026-11-27에 확인했습니다. 실습은 macOS에서 Python과 jq로 실제로 돌린 결과이고, 유료 모델 API는 호출하지 않았습니다.

컨텍스트 창에 무엇이 들어가고 어떻게 세나

창에 들어가는 것

컨텍스트 창(context window)은 모델이 답을 만들 때 참고할 수 있는 모든 텍스트이고, 그 답 자체도 포함합니다.[1] 요청에 실린 시스템 프롬프트, messages 안의 모든 메시지(도구 결과·이미지·문서 포함), 도구 정의가 전부 창을 차지하고, 이번 턴의 출력과 확장 사고(extended thinking)도 셉니다.[1] 창 크기는 모델에 따라 최대 100만 토큰이고, 그 밖의 모델은 20만 토큰입니다.[1]

크다고 좋은 것은 아닙니다. Claude API 문서는 토큰 수가 늘수록 정확도와 기억이 떨어지는 현상을 컨텍스트 부패(context rot)라고 부르고, 공간이 얼마나 남았는지만큼 무엇을 넣느냐가 중요하다고 설명합니다.[1] 입력만으로 창을 넘으면 API는 invalid_request_error("prompt is too long")로 거절합니다.[1]

에이전트에서는 사용자가 아무것도 입력하기 전에 이미 창이 찹니다. Claude Code 문서의 예시 세션은 시스템 프롬프트 4,200, 자동 메모리 680, 프로젝트 CLAUDE.md 1,800토큰처럼 시작 전에 들어가는 항목을 나열하고, 파일을 하나 읽을 때마다 1,100~2,400토큰씩 더합니다.[6] 문서는 이 숫자가 설명용이고 실제 값은 /context로 보라고 덧붙입니다.[6] 예시의 시작 전 항목을 더하면 7,850토큰이고, 뒤의 모의 계산에 이 값을 씁니다.

토큰은 글자 수가 아니다

토큰은 모델이 텍스트를 자르는 단위라서, 같은 뜻이라도 언어와 형식에 따라 개수가 크게 다릅니다. 직접 세어 봤습니다. 아래 숫자는 OpenAI가 공개한 토크나이저 라이브러리 tiktoken 0.14.0의 o200k_base 인코딩으로 센 값입니다. Claude는 토크나이저가 달라 숫자 자체는 다르니, 형식에 따른 차이만 참고하세요.

종류                글자     바이트    토큰     글자/토큰
한국어 문장            40      96    20      2.00
영어 문장             77      77    14      5.50
JSON(들여쓰기)       106     106    45      2.36
JSON(한 줄)         64      64    25      2.56
로그 한 줄            76      76    41      1.85

같은 요청을 한국어로 쓰면 영어보다 글자는 짧아도 토큰은 더 많았습니다. JSON은 들여쓰기만 빼도 45에서 25로 줄었고, 타임스탬프와 요청 ID가 든 로그는 글자당 토큰이 가장 많았습니다.

모델끼리도 다릅니다. Claude API 문서는 Claude Opus 4.7부터 쓰는 새 토크나이저가 같은 입력에 대략 30퍼센트 더 많은 토큰을 낸다고 하고, 예전 모델에서 잰 값을 재사용하지 말라고 합니다.[7] 정확한 값이 필요하면 messages/count_tokens 엔드포인트에 실제로 보낼 요청을 넣어 셉니다. 무료이지만 분당 요청 수 제한이 있고, 결과는 추정치입니다.[7]

프롬프트 캐시: 앞부분이 같아야 싸다

요청마다 대화 전체가 다시 간다

모델은 요청 사이에 아무것도 기억하지 않으므로, Claude Code는 메시지를 보낼 때마다 시스템 프롬프트, 프로젝트 맥락, 지난 메시지와 도구 결과 전부를 다시 보냅니다.[3] 새 내용은 끝에 붙으니 요청의 대부분은 직전 요청과 똑같고, 프롬프트 캐시는 그 같은 부분을 다시 처리하지 않게 해 줍니다.[3]

규칙은 세 가지만 기억하면 됩니다.

  • 캐시는 요청의 시작 부분, 즉 접두사(prefix)를 정확히 맞춰 찾습니다. 앞부분 어디가 바뀌면 그 뒤는 전부 다시 계산되고, 파일별·구역별 캐시는 없습니다.[3]
  • 접두사는 tools, system, messages 순서로 쌓이고, 어느 단계가 바뀌면 그 단계와 뒤 단계가 모두 무효가 됩니다.[2]
  • 기본 수명은 5분이고, 캐시를 쓸 때마다 추가 비용 없이 갱신됩니다.[2]

가격은 기본 입력가에 곱하는 배수로 정해집니다. 5분 캐시에 쓰는 토큰은 1.25배, 캐시에서 읽는 토큰은 0.1배이고, 일부 모델은 읽기가 더 쌉니다(Claude Opus 5.5는 0.05배).[2] 너무 짧은 프롬프트는 표시를 해도 캐시되지 않으며, 최소 길이는 Claude Opus 5.5가 512토큰, Claude Sonnet 4.6이 1,024토큰입니다.[2] 오류 없이 그냥 캐시되지 않으므로 응답의 cache_creation_input_tokens와 cache_read_input_tokens가 둘 다 0인지로 확인합니다.[2]

OpenAI도 원리가 같습니다. 같은 접두사를 재사용하고 기본으로 켜져 있으며, GPT-5.6 이후 모델은 최소 1,024토큰부터 캐시하고 기본 수명은 30분입니다.[8] 문서의 계산으로는 한 번 쓰고 아홉 번 읽으면 캐시 없이 열 번 처리하는 10배 대신 2.15배가 듭니다.[8]

놓치면 얼마나 차이 나나

규칙을 그대로 옮긴 모의 계산기로 30턴 대화의 입력 비용을 비교했습니다. 시작 7,850토큰에 턴마다 1,500토큰이 붙는다고 가정했습니다. 배수는 문서의 표준값인 쓰기 1.25배·읽기 0.1배입니다.[2] 실제 요금이 아니라 "기본 입력가로 몇 토큰어치인가"를 셉니다.

for t in range(1, TURNS + 1):
    length = START + PER_TURN * t
    if every_miss or t in miss_at or prev == 0:
        cost += length * WRITE          # 앞부분이 달라 전부 새로 씀
    else:
        cost += prev * READ + (length - prev) * WRITE  # 직전 요청까지 읽고 새 턴만 씀
    prev = length

30턴 대화 · 입력 토큰 합계 933,000
시나리오                            기본가 환산      캐시 없음 대비      캐시 읽기 비율
캐시 없음                          933,000        100.0%          0.0%
캐시 정상(접두사 유지)                  154,078         16.5%         94.3%
15턴에서 한 번 놓침                   187,255         20.1%         91.2%
매 요청 맨 앞에 현재 시각              1,166,250        125.0%          0.0%

한 번 놓치는 것은 견딜 만하지만, 매 요청 앞부분이 바뀌면 캐시 쓰기 할증만 내고 읽기는 한 번도 못 해 캐시가 없을 때보다 비쌉니다. Claude API 문서도 타임스탬프가 든 블록에 캐시 지점을 두면 매번 새로 쓰기만 하고 읽지 못한다는 예를 "흔한 실수"로 듭니다.[2]

증상턴이 지나도 cache_creation_input_tokens가 계속 높다

접두사 어딘가가 매번 바뀌고 있다는 뜻입니다. 시스템 프롬프트의 날짜·요청 ID 같은 값을 끝으로 옮기고, 캐시 지점은 요청마다 내용이 같은 마지막 블록에 둡니다.[2][3]

Claude Code에서 캐시를 놓치게 하는 행동도 문서에 정리돼 있습니다. 모델 전환은 모델마다 캐시가 따로라서 내용이 같아도 처음부터 다시 읽고, 대부분의 모델에서는 사고 수준(effort) 변경도 같습니다.[3] 대화 압축과 Claude Code 업그레이드 뒤 첫 요청도 캐시를 다시 쌓습니다.[3] 반대로 저장소 파일 편집, 세션 중 CLAUDE.md 편집, 권한 모드 변경, 스킬 호출은 캐시를 지킵니다.[3] 문서의 권고는 모델과 사고 수준을 세션 처음에 정하고, 압축은 작업 사이의 자연스러운 쉼에 하라는 것입니다.[3]

덜어 내기: 압축, 새 세션, 큰 파일

압축은 공짜가 아니다

창이 차면 Claude Code는 대화를 구조화된 요약으로 바꿉니다(압축, compaction). 한계에 가까워지면 자동으로 하고, /compact focus on the auth bug fix처럼 남길 것을 지정해 직접 할 수도 있습니다.[6] 압축 뒤에는 시스템 프롬프트와 루트 CLAUDE.md가 다시 들어가고, 최근 수정한 파일을 최대 다섯 개까지 다시 읽으며, 호출했던 스킬 본문은 스킬당 5,000토큰·합계 25,000토큰까지만 돌아옵니다.[6]

압축 요약을 만드는 것도 요청입니다. 시스템 프롬프트, 도구, 요약할 대화 전체를 다시 보내므로, 캐시가 살아 있으면 싸지만 캐시 수명이 지난 오래된 세션을 이어서 압축하면 대화 전체를 캐시 없이 처리합니다.[3] 버릴 길로 들어섰다면 /rewind로 앞 턴까지 잘라 내는 편이 낫습니다. 이미 캐시된 접두사로 돌아가기 때문입니다.[3]

관계없는 작업은 새 세션에서

Claude Code 문서는 관계없는 세 작업을 모은 세션이 네 번째 작업의 매 턴마다 앞의 세 작업을 다시 읽는다고 지적합니다.[4] 앞의 계산기로 이 상황을 쟀습니다. 10턴짜리 작업 세 개를 끝낸 세션에서 네 번째 작업 10턴을 이어 할 때와, /clear 뒤 새로 시작할 때입니다. 이어 하는 쪽도 캐시는 정상으로 맞는다고 가정했습니다.

4번째 작업 10턴                    입력 토큰 합계      기본가 환산
한 세션에서 이어 하기                   611,000      78,350
/clear 뒤 새로 시작                 161,000      42,378
이어 하기가 입력 토큰 3.8배, 비용 1.8배

캐시가 다 맞아도 1.8배를 더 냅니다. 읽기가 싸도 0은 아니고, 쌓인 앞 작업은 품질에도 끼어듭니다. /clear는 비용이 들지 않으며, 같은 것을 두 번 고쳐도 안 되면 세 번째 수정 대신 /clear 후 새 프롬프트를 쓰라는 것이 문서의 권고입니다.[4]

큰 파일과 긴 출력은 걸러서 넘긴다

에이전트의 도구에도 한도가 있습니다. Claude Code의 Read 도구는 한 번에 최대 25,000토큰을 돌려주고, 256KB가 넘는 파일은 통째로 읽기를 거절해 offset과 limit로 나눠 읽게 합니다.[9] Bash 출력은 대략 30,000자까지 바로 보여 주고, 넘으면 파일로 저장한 뒤 경로와 앞부분 2,000자 미리보기만 줍니다.[9]

그래서 넘기는 방식을 사람이 정하는 편이 낫습니다. 1만 줄짜리 서버 로그에 에러 세 건을 심고 방식별로 토큰을 셌습니다(같은 o200k_base 기준).

로그 10,000줄 · 721,863바이트
넘기는 방식                 토큰     전체 대비  에러 포함
파일 전체             366,901   100.00%  3건
tail -n 100         3,725     1.02%  1건
grep ERROR            143     0.04%  3건
grep -C 2 ERROR       592     0.16%  3건
ERROR 묶어 세기            70     0.02%  3건

파일 전체는 256KB를 넘으니 Read로는 한 번에 읽히지도 않습니다. tail -n 100은 에러를 한 건만 담았고, 앞뒤 두 줄을 붙인 grep -C 2가 원인을 보기에 충분하면서 전체의 0.16%였습니다.

이 거르기를 사람이 매번 지시하지 않게 하는 방법이 훅(hook)입니다. Claude Code 비용 문서는 테스트 명령의 출력을 마지막 100줄로 줄이는 PreToolUse 훅을 예로 듭니다.[5] 문서의 스크립트를 그대로 옮기고, Claude Code가 넘기는 모양의 입력 JSON을 넣어 돌렸습니다.

pattern='^(npm test|pytest|go test)( [^;&|<>`$#\\[:cntrl:]]*)?$'
if [[ "$cmd" =~ $pattern ]]; then
  filtered_cmd="$cmd 2>&1 | tail -n 100"
  echo "$input" | jq --arg filtered "$filtered_cmd" \
    '{hookSpecificOutput: {hookEventName: "PreToolUse", updatedInput: (.tool_input + {command: $filtered})}}'
else
  echo "{}"
fi

입력 command: npm test
{"hookSpecificOutput":{"hookEventName":"PreToolUse","updatedInput":{"command":"npm test 2>&1 | tail -n 100"}}}
입력 command: npm test; rm -rf /
{}
입력 command: ls -la
{}

테스트 명령만 바꾸고, ;로 다른 명령을 이어 붙인 입력은 그대로 둡니다. 다만 위 로그 실험처럼 마지막 100줄은 앞쪽 실패를 놓칠 수 있으니, 실패 요약이 끝에 모이는 러너인지 먼저 확인합니다.

실무에서 부딪히는 문제

점심 먹고 돌아오면 첫 답이 느리고 비싸다

캐시 수명이 지나 접두사를 처음부터 다시 처리하기 때문입니다.[5] Claude Code는 구독 사용 범위 안에서는 메인 대화에 1시간 캐시를, API 키나 클라우드 제공자에서는 5분 캐시를 기본으로 씁니다.[3] promptCacheTtl을 1h로 정할 수 있지만, 1시간 캐시 쓰기는 기본 입력가의 2배라 쉬지 않고 이어 일하면 오히려 손해입니다.[2][3]

압축한 뒤 팀 규칙을 잊는다

paths:가 붙은 규칙이나 하위 폴더의 CLAUDE.md는 해당 파일을 읽을 때 대화 기록으로 들어가서, 압축되면 다른 내용과 함께 요약돼 사라집니다.[6] 압축 뒤에도 남아야 하는 규칙은 paths:를 빼거나 루트 CLAUDE.md로 옮깁니다.[6] 반대로 루트 CLAUDE.md는 매 세션 전부 들어가므로, 특정 작업에만 쓰는 긴 절차는 스킬로 옮기고 200줄 아래로 유지하라는 것이 문서의 권고입니다.[5]

서브에이전트에 넘겼는데 사용량이 줄지 않는다

서브에이전트는 자기 컨텍스트 창에서 큰 파일을 읽고 요약만 돌려주므로 메인 대화는 가벼워집니다.[6] 하지만 그 요청도 같은 사용량에서 나가고, 메인 대화가 이미 가진 맥락을 처음부터 모아야 해서 오히려 느릴 수 있습니다.[4] 서브에이전트의 첫 요청은 부모와 접두사가 달라 부모 캐시를 읽지 못합니다.[3] 넘길 일은 긴 출력이 나오는 일로 좁히고, 짧은 요약을 돌려 달라고 요청합니다.[4]

캐시 계속 맞음 대화 구간 다시 쌓음 처음부터 위임 쪽은 처음부터
맞는 상황 같은 작업 진행 중 같은 작업, 긴 탐색 뒤 관계없는 작업으로 전환 긴 로그·넓은 검색
  • 같은 작업 안에서 탐색 기록이 쌓였다면 /compact에 남길 것을 적어 압축합니다. 작업 사이의 쉼에 하면 압축 비용이 작업 중간에 끼지 않습니다.[3]
  • 관계없는 작업으로 넘어가거나 같은 수정을 두 번 실패했다면 /clear 후 새 프롬프트로 시작합니다.[4]
  • 결과가 길게 나오는 명령은 훅이나 검색으로 걸러 넘기고, 넓은 조사만 서브에이전트에 맡깁니다.[5]
  • 모델과 사고 수준은 세션 처음에 정하고, 시스템 프롬프트 앞쪽에 매번 바뀌는 값을 넣지 않습니다.[3]

지금 프로젝트에 세팅한다면

  1. 루트 CLAUDE.md를 명령·관례·주의점 위주로 줄이고, 작업별 절차는 스킬로 뺍니다.[5]
  2. 상태 줄이나 /usage로 캐시 읽기와 쓰기 토큰을 보이게 해 둡니다. Claude Code v2.1.251 이후에는 /usage에 세션의 캐시 적중 비율이 나옵니다.[3]
  3. 테스트·빌드 출력을 줄이는 PreToolUse 훅을 넣고, 실패 요약이 잘리지 않는지 한 번 돌려 봅니다.[5]
  4. 직접 API를 부르는 기능이 있다면 바뀌지 않는 지시와 도구 정의를 앞에, 날짜·사용자 입력을 뒤에 두고 응답의 캐시 필드를 로그로 남깁니다.[2]

프론트엔드 팀이 해 볼 것

  1. 지금 쓰는 에이전트 세션에서 /context를 열어 시작 전에 들어가는 항목과 크기를 확인해 보세요.[6]
  2. 직접 API를 부르는 코드가 있다면 응답의 cache_creation_input_tokens와 cache_read_input_tokens를 몇 턴 기록해, 쓰기가 매번 줄지 않는지 보세요.[2]
  3. 가장 길게 나오는 테스트나 빌드 명령 하나에 문서의 테스트 출력 거르기 훅을 붙여 보고, 줄인 출력만으로 실패 원인을 찾을 수 있는지 확인해 보세요.[5]
