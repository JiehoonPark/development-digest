18:T62d1,<h2 id="서버-주도-앱의-화면-전환이-느린-이유">서버 주도 앱의 화면 전환이 느린 이유</h2>
<p>서버 컴포넌트(Server Components) 앱에서 링크를 누르면 보통 이런 순서로 일이 일어납니다. 링크를 누르고, 아무 일도 일어나지 않다가, 서버가 응답하면 다음 페이지가 나타납니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 클라이언트 주도 앱(SPA)은 다릅니다. 누르는 순간 다음 페이지의 뼈대가 보이고, 데이터가 도착하면 나머지가 채워집니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>Next.js 팀은 서버 컴포넌트가 화면 전환을 느리게 느껴지게 만들었다고 인정합니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 16.3의 Instant Navigations는 서버 렌더링 모델을 유지하면서 SPA 같은 반응성을 얻으려는 도구 묶음입니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup></p>
<h3 id="메워야-할-간격은-두-개">메워야 할 간격은 두 개</h3>
<p>즉시 전환을 막는 간격은 서버가 응답을 만드는 시간과, 클라이언트와 서버가 주고받는 시간 두 가지입니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 앞의 것은 응답을 스트리밍하거나 캐시하면 사라지고, 뒤의 것은 누르기 전에 UI를 미리 받아 두는 프리페치(prefetch)로 메웁니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<h3 id="즉시의-정의">"즉시"의 정의</h3>
<p>공식 문서는 사용자가 누르는 순간 브라우저가 새 페이지를 그리기 시작하고, 정적·캐시·대체(fallback) 콘텐츠가 바로 보이며, 나머지는 서버가 대체 UI 자리에 스트리밍하는 상태를 즉시 전환이라고 정의합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> 이 정의는 캐시가 채워져 있다고 가정하므로, 캐시가 비어 있으면 첫 전환은 여전히 기다릴 수 있습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<p>두 기능은 설정 파일에서 켭니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-comment">// next.config.ts</span>

<p>두 옵션은 다음 메이저 릴리스에서 모든 앱에 켜지고 설정 항목은 사라질 예정입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h2 id="stream-cache-block-await마다-정하는-세-가지">Stream, Cache, Block — await마다 정하는 세 가지</h2>
<p>Cache Components를 켜면 서버의 <code>await</code> 하나하나가 선택지가 되고, 개발 도구의 Instant Insights가 이를 해결책 세 가지와 함께 오류로 보여 줍니다.<sup class="cite"><a href="#source-4" aria-label="출처 4">[4]</a></sup></p>
<h3 id="stream-suspense로-감싸기">Stream: Suspense로 감싸기</h3>
<p>데이터를 기다리는 부분을 <code>&#x3C;Suspense></code>로 감싸면 사용자는 로딩 상태를 바로 보고, 나머지 UI는 뒤이어 스트리밍됩니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> <code>cookies()</code>·<code>headers()</code>처럼 요청 시점에만 알 수 있는 값을 읽는 컴포넌트도 이 방식으로 처리합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>

<h3 id="cache-use-cache로-결과-재사용">Cache: use cache로 결과 재사용</h3>
<p><code>'use cache'</code>를 붙인 함수의 결과는 요청 사이에서 재사용되므로, 사용자는 이전에 캐시된 UI를 바로 봅니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 캐시 지시어는 비동기 함수 결과에 수명을 부여하고, 그래서 Next.js가 그 결과를 정적 셸(static shell)에 넣을 수 있습니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>

<h3 id="block-일부러-기다리기">Block: 일부러 기다리기</h3>
<p>글 페이지에 로딩 셸을 보이고 싶지 않은 블로그처럼, 서버 응답을 기다리는 편이 나은 라우트도 있습니다. 이때는 페이지나 레이아웃에서 <code>instant</code>를 <code>false</code>로 내보냅니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>

<h2 id="partial-prefetching-링크가-아니라-라우트마다-한-번">Partial Prefetching — 링크가 아니라 라우트마다 한 번</h2>
<p>서버가 막히지 않아도 클라이언트와 서버 사이의 왕복은 남습니다. 16.2까지는 화면에 보이는 모든 링크마다 프리페치 요청을 보냈고, 같은 라우트를 가리키는 링크도 예외가 아니었습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 사이드바에 채팅 링크가 스무 개 있으면 요청도 스무 번이었습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<h3 id="app-shell-하나를-같이-쓴다">App Shell 하나를 같이 쓴다</h3>
<p>Partial Prefetching을 켜면 Next.js는 링크마다가 아니라 라우트마다 재사용 가능한 셸 하나를 프리페치하고, 세션 동안 클라이언트에 캐시합니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 채팅 링크 스무 개라면 <code>/chat/[id]</code> 셸 하나만 받습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> 이 셸을 App Shell이라고 부르며, 정적 콘텐츠와 URL에 의존하지 않는 캐시 콘텐츠로 이루어집니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>

<p>App Shell에는 캐시 수명(stale time)이 5분 이상인 콘텐츠만 들어가고, 프리셋 가운데 <code>seconds</code>를 뺀 나머지가 이 조건을 만족합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h3 id="셸보다-더-받고-싶을-때">셸보다 더 받고 싶을 때</h3>
<p>트랙 상세처럼 헤더까지 바로 보여야 하는 링크에는 <code>prefetch={true}</code>를 붙입니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 그러면 그 링크의 <code>params</code>, <code>searchParams</code>, 전체 URL을 클릭 전에 풀어서, URL에 의존하는 <code>'use cache'</code> 읽기도 프리페치에 포함할 수 있습니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup><sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-keyword">import</span> <span class="hljs-title class_">Link</span> <span class="hljs-keyword">from</span> <span class="hljs-string">'next/link'</span>;

<span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">Link</span> <span class="hljs-attr">href</span>=<span class="hljs-string">{</span>`/<span class="hljs-attr">track</span>/${<span class="hljs-attr">track.id</span>}`} <span class="hljs-attr">prefetch</span>=<span class="hljs-string">{true}</span>></span>
  {track.title}
<span class="hljs-tag">&#x3C;/<span class="hljs-name">Link</span>></span></span>;
<span class="hljs-comment">// 링크가 화면에 들어오면 이 URL 전용 콘텐츠까지 미리 받음</span>
</code></pre>
<p>이런 링크는 화면에 들어오는 순간 서버를 호출할 수 있으니 꼭 필요한 곳에만 씁니다.<sup class="cite"><a href="#source-7" aria-label="출처 7">[7]</a></sup> 이미 셸에 들어 있는 정적·캐시 콘텐츠라면 <code>prefetch={true}</code>를 지웁니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h4>자주 하는 실수: 바뀐 prefetch={true}를 그대로 두기</h4>
<p>이전의 <code>prefetch={true}</code>는 캐시되지 않은 동적 콘텐츠까지 받는 전체 프리페치였지만, 플래그를 켜면 그 콘텐츠는 빠집니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 기존 앱이라면 켜기 전에 이런 링크가 무엇을 미리 보여 주고 있었는지 확인해야 합니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h4>자주 하는 실수: params를 경계 밖에서 await하기</h4>
<p><code>params</code>와 <code>searchParams</code>는 링크마다 달라서 공유 App Shell에 들어갈 수 없습니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 레이아웃이 경계 밖에서 <code>params</code>를 기다리면 그 레이아웃의 셸이 특정 URL에 묶입니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup> 공식 예제는 <code>params</code> 프로미스를 그대로 넘기고, <code>await</code>는 Suspense 안쪽 컴포넌트에서 합니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<pre data-lang="tsx"><code class="hljs language-tsx"><span class="hljs-comment">// app/[category]/layout.tsx (요약)</span>
<span class="hljs-keyword">async</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">CategoryHeader</span>(<span class="hljs-params">{ params }</span>) {

    <span class="xml"><span class="hljs-tag">&#x3C;<span class="hljs-name">div</span>></span>
      <span class="hljs-tag">&#x3C;<span class="hljs-name">Suspense</span> <span class="hljs-attr">fallback</span>=<span class="hljs-string">{</span>&#x3C;<span class="hljs-attr">div</span>></span>Loading...<span class="hljs-tag">&#x3C;/<span class="hljs-name">div</span>></span>}>
        <span class="hljs-tag">&#x3C;<span class="hljs-name">CategoryHeader</span> <span class="hljs-attr">params</span>=<span class="hljs-string">{props.params}</span> /></span>

<p>이 구조 덕분에 <code>generateStaticParams</code>로 빌드하지 않은 URL도 첫 방문에 App Shell을 바로 내보내고, 뒤에서 완성한 페이지를 다음 방문자에게 캐시로 줍니다.<sup class="cite"><a href="#source-8" aria-label="출처 8">[8]</a></sup></p>
<h2 id="도입-순서와-검증">도입 순서와 검증</h2>
<h3 id="켜는-순서">켜는 순서</h3>
<p>공식 문서는 Cache Components를 먼저 도입하고, 그다음 Partial Prefetching으로 넘어가도록 안내합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup> 손으로 옮긴다면 기존 전체 프리페치 링크를 검토하고, 플래그를 켜고, URL 데이터를 Suspense 뒤로 옮기는 순서입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup> 아직 준비되지 않은 라우트는 <code>export const instant = false</code>로 검증에서 빼 두었다가 나중에 돌아옵니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<p>검증은 개발 모드에서 기본으로 모든 Page·Default 세그먼트에 돌아가고, <code>experimental.instantInsights.validationLevel</code>을 <code>'manual-warning'</code>으로 두면 <code>instant</code>를 명시적으로 내보낸 세그먼트만 검사합니다.<sup class="cite"><a href="#source-6" aria-label="출처 6">[6]</a></sup></p>
<h3 id="눈으로-보고-테스트로-고정한다">눈으로 보고, 테스트로 고정한다</h3>
<p>실제 프리페치는 프로덕션에서만 동작하므로 개발 중에는 사용자가 클릭 직후 무엇을 볼지 알기 어렵습니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup> DevTools의 Navigation Inspector는 전환을 셸 상태에서 멈춰 보여 주고, Resume을 누르면 완성된 페이지로 넘어갑니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<p>리팩터링 중에 Suspense 경계가 옮겨지거나 공유 레이아웃에 <code>cookies()</code>를 읽는 컴포넌트가 들어가면, 즉시 뜨던 전환이 느려질 수 있습니다. <code>@next/playwright</code>의 <code>instant()</code>는 네트워크를 기다리지 않고 즉시 보여야 할 것만 단언하게 해 줍니다.<sup class="cite"><a href="#source-3" aria-label="출처 3">[3]</a></sup></p>
<pre data-lang="ts"><code class="hljs language-ts"><span class="hljs-keyword">import</span> { expect, test } <span class="hljs-keyword">from</span> <span class="hljs-string">'@playwright/test'</span>;

});
</code></pre>
<p><code>instant()</code> 블록 안은 셸에 있어야 할 것, 밖은 스트리밍 뒤에 올 것입니다. 기준선은 Partial Prefetching을 끈 프로덕션 빌드에서 잡아야 합니다. <code>next dev</code>에서는 자동 프리페치가 돌지 않기 때문입니다.<sup class="cite"><a href="#source-2" aria-label="출처 2">[2]</a></sup></p>
<h3 id="덤-개발-서버-메모리">덤: 개발 서버 메모리</h3>
<p>코드를 바꾸지 않아도 16.3으로 올리면 <code>next dev</code>의 Turbopack 메모리 사용량이 최대 90% 줄어듭니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 디스크 캐시와 메모리 축출(eviction)이 기본으로 켜져, 방문한 라우트를 메모리에 계속 쥐고 있지 않기 때문입니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup> 50개 라우트 컴파일 뒤 vercel.com 대시보드는 21.5GB에서 2GB로, nextjs.org는 4,600MB에서 840MB로 줄었습니다.<sup class="cite"><a href="#source-1" aria-label="출처 1">[1]</a></sup> 절감 폭은 앱마다 다릅니다.<sup class="cite"><a href="#source-5" aria-label="출처 5">[5]</a></sup></p>
