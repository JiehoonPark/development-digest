클릭했는데 아무 일도 없는 화면 — Next.js 16.3 Instant Navigations

서버 컴포넌트 앱의 화면 전환이 느리게 느껴지는 이유와, Next.js 16.3이 Suspense·use cache·Partial Prefetching으로 이 간격을 메우는 방식을 정리합니다. 기존 앱에서 무엇을 바꿔야 하는지도 코드로 짚습니다.

요약

  • Next.js 16.3의 Instant Navigations는 cacheComponents와 partialPrefetching 두 플래그로 켜는 선택 기능이고, 다음 메이저 버전에서 기본 동작이 될 예정입니다.[1][2]
  • 서버에서 await하는 지점마다 Suspense로 스트리밍할지, 'use cache'로 캐시할지, export const instant = false로 기다릴지 정해야 합니다.[3][4]
  • Partial Prefetching은 링크마다 요청하던 프리페치를 라우트마다 App Shell 하나로 바꾸고, 같은 라우트로 가는 링크가 그 셸을 함께 씁니다.[3][2]
  • 업그레이드만 해도 개발 서버 메모리가 줄어, Vercel 대시보드는 50개 라우트 컴파일 뒤 21.5GB에서 2GB가 됐습니다.[1][5]

서버 주도 앱의 화면 전환이 느린 이유

서버 컴포넌트(Server Components) 앱에서 링크를 누르면 보통 이런 순서로 일이 일어납니다. 링크를 누르고, 아무 일도 일어나지 않다가, 서버가 응답하면 다음 페이지가 나타납니다.[3] 클라이언트 주도 앱(SPA)은 다릅니다. 누르는 순간 다음 페이지의 뼈대가 보이고, 데이터가 도착하면 나머지가 채워집니다.[3]

Next.js 팀은 서버 컴포넌트가 화면 전환을 느리게 느껴지게 만들었다고 인정합니다.[1] 16.3의 Instant Navigations는 서버 렌더링 모델을 유지하면서 SPA 같은 반응성을 얻으려는 도구 묶음입니다.[1]

메워야 할 간격은 두 개

즉시 전환을 막는 간격은 서버가 응답을 만드는 시간과, 클라이언트와 서버가 주고받는 시간 두 가지입니다.[3] 앞의 것은 응답을 스트리밍하거나 캐시하면 사라지고, 뒤의 것은 누르기 전에 UI를 미리 받아 두는 프리페치(prefetch)로 메웁니다.[3]

"즉시"의 정의

공식 문서는 사용자가 누르는 순간 브라우저가 새 페이지를 그리기 시작하고, 정적·캐시·대체(fallback) 콘텐츠가 바로 보이며, 나머지는 서버가 대체 UI 자리에 스트리밍하는 상태를 즉시 전환이라고 정의합니다.[6] 이 정의는 캐시가 채워져 있다고 가정하므로, 캐시가 비어 있으면 첫 전환은 여전히 기다릴 수 있습니다.[6]

두 기능은 설정 파일에서 켭니다.[6]

// next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
};

export default nextConfig;

두 옵션은 다음 메이저 릴리스에서 모든 앱에 켜지고 설정 항목은 사라질 예정입니다.[2]

Stream, Cache, Block — await마다 정하는 세 가지

Cache Components를 켜면 서버의 await 하나하나가 선택지가 되고, 개발 도구의 Instant Insights가 이를 해결책 세 가지와 함께 오류로 보여 줍니다.[4]

Stream: Suspense로 감싸기

데이터를 기다리는 부분을 <Suspense>로 감싸면 사용자는 로딩 상태를 바로 보고, 나머지 UI는 뒤이어 스트리밍됩니다.[3] cookies()·headers()처럼 요청 시점에만 알 수 있는 값을 읽는 컴포넌트도 이 방식으로 처리합니다.[6]

// app/dashboard/page.tsx
import { Suspense } from 'react';
import { cookies } from 'next/headers';

async function TeamTopics() {
  const team = (await cookies()).get('team')?.value;
  const topics = await db.topics.forTeam(team);
  return <TopicList topics={topics} />;
}

export default function Page() {
  return (
    <Suspense fallback={<Skeleton />}>
      <TeamTopics />
    </Suspense>
  );
}
// 클릭 직후: <Skeleton /> → 데이터 도착 후: <TopicList />

Cache: use cache로 결과 재사용

'use cache'를 붙인 함수의 결과는 요청 사이에서 재사용되므로, 사용자는 이전에 캐시된 UI를 바로 봅니다.[3] 캐시 지시어는 비동기 함수 결과에 수명을 부여하고, 그래서 Next.js가 그 결과를 정적 셸(static shell)에 넣을 수 있습니다.[6]

// app/products/page.tsx
async function getProducts() {
  'use cache';
  const res = await fetch('https://api.example.com/products');
  return res.json();
}

export default async function Page() {
  return <ProductList products={await getProducts()} />;
}
// 셸에 목록이 이미 들어 있어 대체 UI 없이 바로 보임

캐시 함수의 인자는 캐시 키가 됩니다.[7] 세션 값이 필요하면 cookies()는 캐시 함수 밖에서 읽고 값만 인자로 넘깁니다.[2]

Block: 일부러 기다리기

글 페이지에 로딩 셸을 보이고 싶지 않은 블로그처럼, 서버 응답을 기다리는 편이 나은 라우트도 있습니다. 이때는 페이지나 레이아웃에서 instant를 false로 내보냅니다.[3]

// page.tsx 또는 layout.tsx
export const instant = false;
// 이 라우트는 서버 응답을 기다린 뒤 전환되고, 검증 오류도 사라짐

자주 하는 실수: 루트 레이아웃의 Suspense를 믿기

페이지를 직접 열 때는 문서 루트부터 전체가 렌더링되므로, 루트 레이아웃의 <Suspense>가 모든 것을 받아 줍니다.[6] 하지만 /store/shoes에서 /store/hats로 이동하면 /store 레이아웃 아래만 다시 렌더링되고, 루트 레이아웃의 경계는 이 범위 바깥이라 동작하지 않습니다.[6]

// app/layout.tsx — 직접 방문에는 효과가 있지만
<Suspense fallback={<Spinner />}>{children}</Suspense>
// /store/shoes → /store/hats 이동에서는 쓰이지 않음

즉시 전환 여부는 공유 레이아웃 아래, 실제로 다시 렌더링되는 범위의 Suspense 경계와 캐시가 결정합니다.[6]

서버의 await마다셋 중 하나를 고른다Stream·Cache·Block

Partial Prefetching — 링크가 아니라 라우트마다 한 번

서버가 막히지 않아도 클라이언트와 서버 사이의 왕복은 남습니다. 16.2까지는 화면에 보이는 모든 링크마다 프리페치 요청을 보냈고, 같은 라우트를 가리키는 링크도 예외가 아니었습니다.[3] 사이드바에 채팅 링크가 스무 개 있으면 요청도 스무 번이었습니다.[3]

App Shell 하나를 같이 쓴다

Partial Prefetching을 켜면 Next.js는 링크마다가 아니라 라우트마다 재사용 가능한 셸 하나를 프리페치하고, 세션 동안 클라이언트에 캐시합니다.[3] 채팅 링크 스무 개라면 /chat/[id] 셸 하나만 받습니다.[3] 이 셸을 App Shell이라고 부르며, 정적 콘텐츠와 URL에 의존하지 않는 캐시 콘텐츠로 이루어집니다.[2]

<Link> 사용 이전(Cache Components 기본) Partial Prefetching 이후
<Link href="/x"> 캐시된 페이지 렌더를 프리페치 /x의 공유 App Shell을 프리페치
<Link href="/x" prefetch> 캐시된 렌더와 동적 콘텐츠까지 App Shell + URL별 캐시 콘텐츠
prefetch={false} 프리페치 안 함 그대로 안 함

App Shell에는 캐시 수명(stale time)이 5분 이상인 콘텐츠만 들어가고, 프리셋 가운데 seconds를 뺀 나머지가 이 조건을 만족합니다.[2]

셸보다 더 받고 싶을 때

트랙 상세처럼 헤더까지 바로 보여야 하는 링크에는 prefetch={true}를 붙입니다.[7] 그러면 그 링크의 params, searchParams, 전체 URL을 클릭 전에 풀어서, URL에 의존하는 'use cache' 읽기도 프리페치에 포함할 수 있습니다.[7][2]

import Link from 'next/link';

<Link href={`/track/${track.id}`} prefetch={true}>
  {track.title}
</Link>;
// 링크가 화면에 들어오면 이 URL 전용 콘텐츠까지 미리 받음

이런 링크는 화면에 들어오는 순간 서버를 호출할 수 있으니 꼭 필요한 곳에만 씁니다.[7] 이미 셸에 들어 있는 정적·캐시 콘텐츠라면 prefetch={true}를 지웁니다.[2]

자주 하는 실수: 바뀐 prefetch={true}를 그대로 두기

이전의 prefetch={true}는 캐시되지 않은 동적 콘텐츠까지 받는 전체 프리페치였지만, 플래그를 켜면 그 콘텐츠는 빠집니다.[2] 기존 앱이라면 켜기 전에 이런 링크가 무엇을 미리 보여 주고 있었는지 확인해야 합니다.[2]

자주 하는 실수: params를 경계 밖에서 await하기

params와 searchParams는 링크마다 달라서 공유 App Shell에 들어갈 수 없습니다.[2] 레이아웃이 경계 밖에서 params를 기다리면 그 레이아웃의 셸이 특정 URL에 묶입니다.[8] 공식 예제는 params 프로미스를 그대로 넘기고, await는 Suspense 안쪽 컴포넌트에서 합니다.[8]

// app/[category]/layout.tsx (요약)
async function CategoryHeader({ params }) {
  const { category } = await params; // 경계 안쪽에서 await
  const data = await getCategory(category);
  return <h1>{data?.name ?? 'Category'}</h1>;
}

export default function CategoryLayout(props) {
  return (
    <div>
      <Suspense fallback={<div>Loading...</div>}>
        <CategoryHeader params={props.params} />
      </Suspense>
      {props.children}
    </div>
  );
}

이 구조 덕분에 generateStaticParams로 빌드하지 않은 URL도 첫 방문에 App Shell을 바로 내보내고, 뒤에서 완성한 페이지를 다음 방문자에게 캐시로 줍니다.[8]

도입 순서와 검증

켜는 순서

공식 문서는 Cache Components를 먼저 도입하고, 그다음 Partial Prefetching으로 넘어가도록 안내합니다.[6] 손으로 옮긴다면 기존 전체 프리페치 링크를 검토하고, 플래그를 켜고, URL 데이터를 Suspense 뒤로 옮기는 순서입니다.[2] 아직 준비되지 않은 라우트는 export const instant = false로 검증에서 빼 두었다가 나중에 돌아옵니다.[2]

검증은 개발 모드에서 기본으로 모든 Page·Default 세그먼트에 돌아가고, experimental.instantInsights.validationLevel을 'manual-warning'으로 두면 instant를 명시적으로 내보낸 세그먼트만 검사합니다.[6]

눈으로 보고, 테스트로 고정한다

실제 프리페치는 프로덕션에서만 동작하므로 개발 중에는 사용자가 클릭 직후 무엇을 볼지 알기 어렵습니다.[3] DevTools의 Navigation Inspector는 전환을 셸 상태에서 멈춰 보여 주고, Resume을 누르면 완성된 페이지로 넘어갑니다.[3]

리팩터링 중에 Suspense 경계가 옮겨지거나 공유 레이아웃에 cookies()를 읽는 컴포넌트가 들어가면, 즉시 뜨던 전환이 느려질 수 있습니다. @next/playwright의 instant()는 네트워크를 기다리지 않고 즉시 보여야 할 것만 단언하게 해 줍니다.[3]

import { expect, test } from '@playwright/test';
import { instant } from '@next/playwright';

test('product title is available immediately', async ({ page }) => {
  await page.goto('/products/shoes');
  // Assert what's visible without waiting for network
  await instant(page, async () => {
    await page.click('a[href="/products/hats"]');
    await expect(page.locator('h1')).toContainText('Baseball Cap');
    await expect(page.getByText('Checking inventory...')).toBeVisible();
  });
  await expect(page.getByText('12 in stock')).toBeVisible();
});

instant() 블록 안은 셸에 있어야 할 것, 밖은 스트리밍 뒤에 올 것입니다. 기준선은 Partial Prefetching을 끈 프로덕션 빌드에서 잡아야 합니다. next dev에서는 자동 프리페치가 돌지 않기 때문입니다.[2]

덤: 개발 서버 메모리

코드를 바꾸지 않아도 16.3으로 올리면 next dev의 Turbopack 메모리 사용량이 최대 90% 줄어듭니다.[1] 디스크 캐시와 메모리 축출(eviction)이 기본으로 켜져, 방문한 라우트를 메모리에 계속 쥐고 있지 않기 때문입니다.[5] 50개 라우트 컴파일 뒤 vercel.com 대시보드는 21.5GB에서 2GB로, nextjs.org는 4,600MB에서 840MB로 줄었습니다.[1] 절감 폭은 앱마다 다릅니다.[5]

정리

하고 싶은 것 쓰는 것 주의할 점
클릭 즉시 로딩 상태 보이기 <Suspense> 공유 레이아웃 아래에 둔다[6]
이전 결과를 바로 보이기 'use cache' 수명 5분 미만은 셸에 안 들어감[2]
일부러 서버 응답 기다리기 export const instant = false 검증에서도 빠진다[2]
라우트당 셸 하나만 프리페치 partialPrefetching: true 기존 prefetch={true} 동작이 바뀐다[2]
URL별 콘텐츠까지 미리 받기 <Link prefetch={true}> 링크가 보이면 서버를 호출한다[7]
회귀 막기 instant() 테스트 프로덕션 빌드에서 기준선을 잡는다[2]

Instant Navigations는 "서버 렌더링이냐 SPA냐"를 고르는 문제가 아닙니다. 서버의 await 하나마다 사용자가 클릭 직후 무엇을 볼지 정하는 문제입니다.

프론트엔드 팀이 해 볼 것

  1. 프로젝트에서 prefetch={true}와 prefetch 속성을 검색해, 각 링크가 지금 무엇을 미리 보여 주는지 목록으로 만들어 봅니다.
  2. 루트 레이아웃에만 <Suspense>가 있는 라우트를 찾아, 형제 페이지끼리 이동할 때 로딩 상태가 뜨는지 확인합니다.
  3. 가장 자주 쓰는 화면 전환 하나에 @next/playwright의 instant() 테스트를 추가해, 즉시 보여야 할 요소를 고정합니다.
