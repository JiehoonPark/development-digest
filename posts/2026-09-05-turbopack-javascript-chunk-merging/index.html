청크는 잘게 쪼갤수록 빠를까 — Turbopack이 청크를 합치는 기준

번들러가 JavaScript를 여러 파일로 나누는 이유와, 요청 수와 코드 양 사이에서 Turbopack이 청크를 합칠지 정하는 방식을 다룹니다. 번들 크기와 로딩에 영향을 주는 코드 습관도 함께 정리합니다.

요약

  • 청크를 크게 합치면 요청 수가 줄고, 잘게 나누면 페이지 간 재사용이 늘어나서 두 목표가 서로 부딪힙니다.[1]
  • Turbopack은 함께 로드되는 청크 묶음인 청크 그룹 안에서만 청크를 합치고, 한 페이지만 보고 떠나는 세션을 2/3로 가정해 합칠지 계산합니다.[1]
  • Next.js 16.3부터 experimental.turbopackChunking으로 컴포넌트 청크와 방문 패턴 가정을 직접 설정할 수 있지만, 아직 실험 기능입니다.[1][2]
  • 정적 import/export는 트리 셰이킹의 기반이고, import()는 필요할 때만 모듈을 불러오므로 둘을 구분해 쓰는 습관이 번들 크기를 좌우합니다.[3][4]

청크를 나누는 세 가지 극단

청크란

청크(chunk)는 번들러가 만들어 내는 JavaScript 파일 하나입니다. Next.js 앱의 Network 탭에 보이는 무작위 이름의 .js 파일들이 바로 청크이고, 그 안에는 직접 작성한 코드, 의존 패키지, 이들을 연결하는 런타임 코드가 들어 있습니다.[1] 어떤 코드를 어느 청크에 넣을지 정하는 과정을 청킹(chunking)이라고 합니다.[1]

하나로, 페이지마다, 모듈마다

모듈 355개짜리 사이트를 세 가지 방식으로 나누면 결과가 이렇게 달라집니다.[1]

방식 청크 수 전체 크기 문제
전부 한 청크 1개 1.09 MB 가벼운 페이지도 모든 페이지의 코드를 받음
페이지당 한 청크 8개 1.20 MB 공통 코드가 청크마다 중복돼 캐시를 못 씀
모듈당 한 청크 355개 1.09 MB 작은 파일마다 네트워크 요청이 생김

한 청크로 묶으면 사이트가 커질수록 모든 페이지가 무거워집니다.[1] 페이지마다 나누면 모든 페이지에 쓰이는 <Footer />가 청크마다 들어가서, 네 페이지를 연 방문자는 같은 푸터 코드를 네 번 받습니다.[1]

자주 하는 실수: 잘게 쪼갤수록 좋다고 생각하기

모듈마다 청크를 만들면 중복도 과잉 전송도 없습니다. 대신 요청이 수백 개가 됩니다. HTTP/2로 요청 비용이 줄었어도 요청마다 부담이 있고, gzip 같은 압축은 한 파일 안에서만 반복 패턴을 찾기 때문에 작은 파일이 많을수록 압축 효율도 떨어집니다.[1]

청킹은 줄다리기요청 수 vs 코드 양

Turbopack이 청크를 합치는 기준

Turbopack은 작은 청크를 큰 청크로 합칩니다. 어려운 부분은 어떤 청크를, 언제 합쳐야 실제로 이득인지 정하는 일입니다.[1]

청크 그룹 안에서만 합친다

청크 그룹(chunk group)은 함께 로드되는 청크의 묶음입니다. /home이 쓰는 청크들이 한 그룹, /blog가 쓰는 청크들이 또 한 그룹이 됩니다.[1] 공식 문서는 라우트와 동적 import를 청크 그룹의 예로 듭니다.[2]

Turbopack은 같은 그룹의 청크끼리만 합칩니다. 그룹 안의 청크는 어차피 함께 로드되므로, 합쳐도 페이지가 받지 않던 코드가 끼어들지 않습니다.[1]

두 번째 페이지에서 손해가 생긴다

남은 문제는 캐시입니다. 모든 페이지에 쓰이는 푸터를 A, 홈에서만 쓰는 비디오 플레이어를 B라고 하겠습니다. 홈만 보고 떠나는 방문자에게는 합치기가 항상 이득입니다. 요청이 한 번으로 줄기 때문입니다.[1]

홈에서 A만 쓰는 페이지로 이동하면 사정이 달라집니다. 합친 파일은 그 페이지에 쓸모가 없어서 A를 따로 다시 받게 됩니다.[1] 원문의 설명을 코드 모형으로 옮기면 다음과 같습니다.

function filesFor(needs, merged) {
  const needsBoth = needs.includes("A") && needs.includes("B");
  if (merged && needsBoth) return ["A+B"];
  return needs;
}

function visit(pages, merged) {
  const cache = new Set();
  const downloaded = [];
  for (const needs of pages) {
    for (const file of filesFor(needs, merged)) {
      if (cache.has(file)) continue;
      cache.add(file);
      downloaded.push(file);
    }
  }
  return downloaded;
}

visit([["A", "B"]], true);             // ["A+B"]       요청 1번 (따로 두면 2번)
visit([["A", "B"], ["A"]], true);      // ["A+B", "A"]  A를 두 번 받음
visit([["A"], ["A", "B"]], true);      // ["A", "A+B"]  역시 A를 두 번 받음
visit([["A", "B"], ["A", "B"]], true); // ["A+B"]       재사용 성공, 요청 1번 절약

두 페이지를 보는 세션에서 합치기가 이득인 경우는 두 페이지 모두 A와 B를 함께 쓸 때뿐입니다.[1] 그래서 Turbopack은 A만 쓰는 그룹, B만 쓰는 그룹, 둘 다 쓰는 그룹의 수를 세어 각 시나리오의 확률로 득실을 가중합니다. 여기에 한 페이지만 보는 세션을 2/3, 두 페이지 이상 보는 세션을 1/3로 가정합니다.[1]

실제 사이트에서 비교한 결과

원문 필자는 nextjs.org에서 같은 8단계 탐색을 세 가지 설정으로 측정했습니다.[1]

설정 첫 페이지 로드 8단계 전체
합치지 않음 363.6 KiB (요청 76) 561.6 KiB (요청 96)
Turbopack 기본값 344.2 KiB (요청 24) 554.8 KiB (요청 38)
그룹마다 한 청크 315.3 KiB (요청 6) 610.0 KiB (요청 15)

기본값은 합치지 않을 때보다 요청을 절반 넘게 줄이면서 코드도 조금 덜 보냈습니다. 최대로 합치면 첫 로드는 가장 가볍지만 전체로는 코드를 10% 더 보냈습니다.[1] 다만 탐색을 덜 했다면 최대 병합이 더 나았을 것이라고 원문은 덧붙입니다.[1]

기본 임계값

크기 기준은 next.config의 experimental.turbopackChunking에 있고, 기본값은 다음과 같습니다.[2]

turbopackChunking: {
  minChunkSize: 50000,          // 바이트
  maxChunkCountPerGroup: 40,    // 그룹당 청크 수 상한
  maxMergeChunkSize: 200000,    // 이보다 크면 합치지 않음
  minComponentChunkSize: 20000,
  generateComponentChunks: false,
},

minChunkSize보다 작은 청크는 하나 넘게 만들지 않도록 합치고, 한 그룹의 청크는 maxChunkCountPerGroup개를 넘지 않으며, maxMergeChunkSize보다 큰 청크는 다른 청크와 합치지 않습니다.[2] 여기서 크기는 압축·축소 전 코드의 바이트 수라서, 압축·축소한 결과물보다 대략 5배 큽니다.[2]

Next.js 16.3에서 바뀐 것

빌드 시점의 병합은 브라우저의 캐시 상태를 모르고, 방문 패턴을 추측해야 합니다. Next.js 16.3의 새 옵션은 이 두 한계를 겨냥합니다.[1] 공식 문서는 turbopackChunking이 실험 기능이며 프로덕션에는 권장하지 않는다고 적고 있습니다.[2]

컴포넌트 청크

generateComponentChunks를 켜면 합친 청크와 함께, 합치기 전의 구성 청크(컴포넌트 청크)도 같이 만들어집니다.[1][2] 런타임은 각 합친 청크가 어떤 조각으로 이뤄졌는지, 그중 무엇을 이미 받았는지 추적해서 합친 파일과 빠진 조각 중 더 싼 쪽을 고릅니다.[1] 반대로 A+B를 이미 받았다면 A를 따로 다시 받지 않습니다.[1] minComponentChunkSize보다 작은 컴포넌트 청크는 따로 만들지 않고 하나로 묶습니다.[2]

팀은 사이트를 떠났다가 나중에 돌아온 방문자에게도 같은 효과를 주려고 only-if-cached 지시어를 실험하고 있습니다.[1] only-if-cached는 Cache-Control 요청 지시어 중 하나입니다.[5]

방문 패턴 알려주기

2/3이라는 가중치는 많은 사이트에 맞는 추정일 뿐, 특정 사이트에 맞는 값은 아닙니다.[1] 실제 방문 패턴을 알면 다음 옵션으로 알려 줄 수 있습니다.[1][2]

const nextConfig = {
  experimental: {
    turbopackChunking: {
      generateComponentChunks: true,
      firstPageLoadPriority: 0.5, // 이탈률이 50%라면
      priorityRoutes: [/^\/$/],   // 첫 진입이 많은 홈
      clusters: [[/^\/dashboard/, /^\/settings/]],
    },
  },
} satisfies NextConfig
  • firstPageLoadPriority: 0~1 사이 값입니다. 높을수록 첫 로드를 위해 더 적극적으로 합칩니다. 기본값은 0.67이고, 더 나은 값이 없으면 이탈률(bounce rate)을 쓰라고 안내합니다.[1][2]
  • priorityRoutes: 방문자가 처음 들어오는 경우가 많은 라우트입니다. 이 라우트의 번들은 더 적극적으로 합치고, priorityBoost(기본 1.5)로 정도를 조절합니다.[2]
  • clusters: 함께 방문하는 라우트 묶음을 정규식 배열로 적습니다. 클러스터 안에서 공유되는 청크를 더 쉽게 합칩니다.[2]

주의할 점: 클러스터를 넓게 잡기

클러스터에 A만 쓰는 페이지, B만 쓰는 페이지, 둘 다 쓰는 페이지가 섞여 있으면 오히려 덜 합칩니다.[1] 실제로 함께 방문되고 같은 코드를 쓰는 라우트만 묶는 편이 낫습니다.

처음부터 덜 보내기

  • CJS 트리 셰이킹: 전에는 ESM만 트리 셰이킹해서 CJS 모듈의 쓰지 않는 코드가 클라이언트로 갔습니다. experimental.turbopackCjsTreeShaking으로 켜며, 이후 버전에서 기본값이 될 예정입니다.[1]
  • 공유 런타임: 페이지마다 있던 런타임 청크를 하나로 대체합니다. experimental.turbopackSharedRuntime으로 켜며, 첫 탐색 이후 탐색마다 차단 요청 하나와 약 10KB를 아낍니다.[1]
  • 가벼운 기본 런타임: WebAssembly와 Web Worker 로딩 코드는 실제로 쓸 때만 넣습니다.[1]

번들 크기를 좌우하는 코드 습관

청킹 설정보다 먼저 바꿀 수 있는 것은 코드입니다.

정적 import는 트리 셰이킹의 재료

트리 셰이킹(tree shaking)은 쓰지 않는 코드를 제거하는 것이고, import와 export 문으로 모듈 간 사용 관계를 파악합니다.[4] 아래 모듈 예제는 MDN 모듈 안내서의 코드입니다.[6] MDN은 초기 의존성은 정적 형태로 불러오는 편이 정적 분석과 트리 셰이킹에 유리하다고 설명합니다.[3]

export const name = "square";
export function draw(ctx, length, x, y, color) {
  ctx.fillStyle = color;
  ctx.fillRect(x, y, length, length);
  return { length, x, y, color };
}

// 쓰는 것만 이름으로 가져오면 나머지 export는 제거 대상이 됨
import { draw } from "./modules/square.js";

CJS 모듈은 그동안 Turbopack의 트리 셰이킹 대상이 아니었으므로[1], ESM 배포판이 있다면 그쪽을 고르는 편이 낫습니다.

나중에 필요한 코드는 import()로

import()는 모듈을 비동기로 불러와 프로미스를 돌려주고, 필요할 때만 평가됩니다.[3] Next.js에서는 next/dynamic이나 import()로 Client Component와 라이브러리를 실제로 필요할 때 받게 할 수 있습니다.[7]

'use client'
import { useState } from 'react'

const names = ['Tim', 'Joe', 'Bel', 'Lee']

export default function Page() {
  const [results, setResults] = useState()
  return (
    <input
      type="text"
      onChange={async (e) => {
        const { value } = e.currentTarget
        const Fuse = (await import('fuse.js')).default
        const fuse = new Fuse(names)
        setResults(fuse.search(value))
      }}
    />
  )
}
// fuse.js는 사용자가 입력을 시작한 뒤에야 받음

자주 하는 실수: 모든 것을 동적으로

MDN은 동적 import를 꼭 필요할 때만 쓰라고 권합니다.[3] 첫 화면에 바로 필요한 코드를 import()로 미루면 요청만 하나 더 생깁니다. 또 Server Component가 Client Component를 동적으로 import하면 자동 코드 분할이 아직 지원되지 않습니다.[7]

동적 import와 배럴 파일

배럴 파일(barrel file)은 export { foo } from "bar"처럼 다른 모듈을 다시 내보내는 파일입니다. Turbopack은 일반 import에서는 재내보내기를 따라가지만, 비동기 import에서는 따라가지 못해 배럴 뒤의 모듈을 트리 셰이킹하지 못한 적이 있습니다.[8] 체인 정의를 비동기로 import한 사례에서는 수정 후 클라이언트 그래프에 정의 파일 712개 중 11개만 남았습니다.[8]

// chains/index.js
export { foo } from "./foo";
export { bar } from "./bar";

// 쓰는 모듈만 필요한데 배럴 전체를 동적으로 가져옴
const { foo } = await import("./chains");

원문은 이 부분을 개선했다고 적지만[1], 동적 import 대상이 배럴이면 빌드 결과를 한 번 확인할 만합니다.

청크를 왜 합치나 요청 수와 압축 손실을 줄이려고. 대신 페이지 간 재사용이 줄어듦[1]
무엇끼리 합치나 같은 청크 그룹(라우트, 동적 import) 안의 청크만[1][2]
언제 합치나 한 페이지 세션 2/3 가정으로 득실을 가중해 이득일 때[1]
기본값의 효과 nextjs.org 8단계 탐색에서 요청 96 → 38[1]
16.3 실험 옵션 generateComponentChunks, firstPageLoadPriority, priorityRoutes, clusters[1][2]
코드에서 할 일 초기 코드는 정적 import, 나중 코드는 import(), CJS·배럴은 결과 확인[3][4][8]

청크를 몇 개로 나눌지는 번들러가 정하지만, 무엇을 버리고 무엇을 미룰지는 코드가 정합니다.

프론트엔드 팀이 해 볼 것

  1. 배포된 사이트의 Network 탭에서 JS만 걸러 첫 페이지와 두 번째 페이지의 요청 수와 전송 크기를 적어 둡니다.
  2. 첫 화면에서 바로 쓰지 않는 무거운 라이브러리 하나를 골라 이벤트 핸들러 안의 import()로 옮기고 같은 측정을 반복합니다.
  3. 테스트 브랜치에서 firstPageLoadPriority를 실제 이탈률로 바꿔 빌드하고, 프로덕션에는 넣지 않은 채 결과만 비교합니다.
