RSC는 왜 번들러와 통합될까?
via Dan Abramov (overreacted)
💡알면 좋은 정보frontend

React Server Components는 데이터뿐 아니라 클라이언트 컴포넌트의 실행 코드까지 함께 직렬화해서 전달해야 하는데, 이 코드를 파일 단위로 하나씩 네트워크로 가져오면 워터폴이 발생해 비효율적입니다. Dan Abramov는 이 문제를 해결하기 위해 RSC가 Parcel, Webpack, Vite 같은 번들러와 통합되는 구조를 설명하고, react-server/react-client 내부 패키지와 번들러 바인딩이 어떻게 모듈 직렬화·역직렬화를 가능하게 하는지 코드 예시로 보여줍니다.

💡
RSC를 사용하는 Next.js 등 프레임워크의 번들러 설정이 왜 그렇게 복잡하고 React 버전과 긴밀히 맞물려야 하는지 근본 원리를 이해하면, RSC 기반 아키텍처를 설계하거나 디버깅할 때 훨씬 명확한 멘탈 모델을 가질 수 있습니다.

왜 더 많은 개발자들은 "플랫폼을 쓰지" 않을까
via Hacker News (Top)
💡알면 좋은 정보frontend

웹 표준 옹호자들은 오랫동안 '플랫폼을 써라'고 외쳐왔지만, 실제로는 많은 개발자들이 직접 라이브러리를 만들거나 npm 패키지를 선호한다. 이 글은 역사적 배경, 익숙함, React 생태계의 역할 분담, 문서화 차이 같은 구조적 요인과 함께, 직접 만드는 것이 주는 재미와 학습 효과(이케아 효과)라는 더 근본적인 이유를 다룬다. 저자는 CSS와 ClickHouse 사례를 들어 플랫폼에 대한 무지가 낳는 비효율도 짚으며, AI 코딩이 이 현상에 미칠 낙관적/비관적 영향까지 전망한다.

💡
프론트엔드 개발자가 라이브러리에 의존할지 플랫폼 네이티브 API를 쓸지 결정할 때, 단순한 기술적 우열이 아니라 습관·문서화·학습 동기 같은 심리적·구조적 요인까지 이해해야 더 나은 판단을 내릴 수 있다.
